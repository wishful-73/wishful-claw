# S-153 工具产出物统一落点：agent 读不回自己刚截的图

- **登记日期**：2026-09-28
- **登记来源**：老大 10:13「截图输出目录不在允许的列表，这个放入36迭代的需求」
- **分支**：`dev/v2-iter-36`
- **状态**：✅ 已实施

---

## 一、现象（本会话实测）

一次会话里连做三次 `BrowserScreenshot`，输出尾部都带着 `filePath`：

```
C:\Users\龚翼\wishful-claw\image\1790561476872-9f225ef2-0593-4ba7-a622-c378dacc06ce.png
```

紧接着 `Read` 这个路径 —— **被沙箱直接拒掉**：

```
Sandbox: "C:\Users\龚翼\wishful-claw\image\1790561476872-….png" is outside the allowed
working directories (D:\claw\wishful-claw, C:\Users\龚翼\.wishful-claw-dev). …
```

净效果：**agent 能截图、拿得到路径，但读不回来** —— 自己刚产出的东西自己看不见。
报错文案还在劝它「把目录加进项目工作目录」，而那个目录根本不是项目目录。

---

## 二、落盘位置是谁定的

`src/main/lib/image-persist.ts`：`persistImageBuffer()` 在**没有 `targetPath`** 时无条件落
`join(homedir(), 'wishful-claw', 'image')`。

**调用链（`BrowserScreenshot`）**：

| 环节 | 位置 | 是否传 `targetPath` |
|---|---|---|
| 截图编码 | `renderer/src/lib/tools/browser-native-ui.ts` `executeBrowserScreenshot` | **不传**（只传 `data` + `mediaType`） |
| IPC 落盘 | `main/ipc/misc-handlers.ts` `image:persist-generated` | 透传（此处为 `undefined`） |
| 兜底落盘 | `main/lib/image-persist.ts` | ⇒ `~/wishful-claw/image` |

**同目录的另一个写入方**：`CaptureAppWindow`（`main/ipc/reverse-handlers/window-capture-handler.ts`）
**只在给了 `targetPath` 时才写盘**，不给就不落盘 ⇒ **不受本条影响**，也未改动。

---

## 三、根因

沙箱根集合 = 会话对应项目的 `workingFolder` + **本实例数据根**
（`PathBoundary.WithDataRoot` → `WishfulClawDataDir.Root`）。

`~/wishful-claw/image` 与数据根**不是同一个目录**，而且差在两个要命的地方：

| | 路径 | dev / 打包实例 |
|---|---|---|
| **数据根** | `~\.wishful-claw-dev` / `~\.wishful-claw` | **分家** —— `PathBoundary.cs` 明写「开发只看开发、生产只看生产」就是靠它保证 |
| **截图目录** | `~\wishful-claw\image` | **名字不带点、两类实例共用一份** |

⇒ 两条结论：

1. 「数据根已经在集合里」**覆盖不到**截图目录，必须显式处理；
2. 截图目录恰好**破坏**了「dev / prod 互不可见」这条既定原则 —— 开发实例写下的截图，打包实例的 agent 也能读到。

---

## 四、裁定：范围收窄 + 落点三路分家

老大 2026-09-28 口径演进（后覆盖前）：

1. **10:13 登记** —— 曾列三选一（A 把截图目录加进沙箱「系统根」／B 迁到数据根／C 截图时传 `targetPath`）。
2. **11:22** —— 「大截图输出溢出，这个**不是我们能解决的**，如果图片确实大，那么 agent 上下文有限，怎么处理都处理不了」
   ⇒ **大截图溢出结掉、不立项、不给编号**（见 §七）。
3. **11:22** —— 「你这有点过度解读了，我的意思**就是浏览器截图，这种内置的，没有指定路径的**」
   ⇒ **范围 = 内置工具、且未指定 `targetPath` 的产出物**，只此一处，不再扩到「所有工具产出物」。
4. 曾提的「迁数据根一刀切」「渲染端拼绝对路径当 `targetPath`」两个旧方案**均作废**。

**最终做法 —— 按会话作用域三路分家**（与 `MemoryPathResolver.ResolveRoot` 对齐）：

| 会话 | 默认落点 | 为何在沙箱内 |
|---|---|---|
| 本地项目 | `{workingFolder}\.wishful-claw\image` | 项目沙箱根就是 `workingFolder` 本身，子路径天然放行 |
| SSH 项目 | `{dataRoot}\projects\{projectId}\image` | 数据根无条件挂进沙箱；子路径跟随记忆落点 |
| 全局 / 其它 | `{dataRoot}\image` | 数据根无条件挂进沙箱 |

判据用 `scope`（`'global' | 'project'`），**不能只看有没有 `workingFolder`** —— 全局会话也可能带它
（`cron-runtime.ts` 的 `workingFolder: project?.workingFolder ?? event.workingFolder ?? null`）。
项目分支缺了本分支需要的事实（SSH 无 `projectId` / 本地无 `workingFolder`）时**一律回落数据根** ——
那是唯一「任何沙箱都覆盖得到」的保底位置。

## 七、备注

- 本条只解决「内置产出物读不回来」的**目录归属**问题。
- **大截图输出溢出：结掉，不立项**。上下文有限是硬约束，怎么摆都解决不了（老大 11:22 裁定）。
  成因备查：`ToolCallProcessor.cs` 的 `MaxToolOutputBytes = 32 * 1024`；`Read` 走 registry 分支有
  contentBlocks 豁免，`BrowserScreenshot` 走渲染端反向请求只填 `toolOutput`，base64 撞上限即被截断。
- 顺带确证一条能力事实：Read 不认 `.svg` 只是「手写 SVG 无法自检」的表层原因；真缺口是**产出物回读链路**，
  而 **浏览器截图 → Read 这条路已经通了**（小图实测通过）。
