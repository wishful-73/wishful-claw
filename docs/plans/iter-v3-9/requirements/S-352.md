## 1. 原话 / 来源

> 2026-11-09 10:33 老大（钉死归属原则）：

> 本仓主要是负责做插件底座。不负责具体功能实现

> 2026-11-09 10:36 老大：

> R-3直接标关闭。 然后其他缺口，进行新迭代下的需求登记

**这条需求是「本仓只做底座」原则的直接产物** —— R-2「说」（文字转语音）的合成属插件，不在本仓；但插件合成出来的音频**要能发到渠道**，这是通道能力，属底座。就像 R-1「听」本仓只交付录音采集（入站收音频），这条补的是**出站发音频**，两者正对称。

## 2. 现象

用户视角：装了语音插件、也合成出了音频，**但发不出去** —— 除了飞书，其余渠道只能发文字。

从代码看更直接：**入站能收图能收音频，出站只能发字符串。** 同一个渠道，收的方向有媒体概念，发的方向没有。

## 3. 代码链路（2026-11-09 实读）

### 3.1 统一接口只认文本

`src/main/channels/channel-types.ts:132-156`：

```ts
export interface MessagingChannelService {
  // ...
  // Unified messaging operations
  sendMessage(chatId: string, content: string): Promise<{ messageId: string }>
  replyMessage(messageId: string, content: string): Promise<{ messageId: string }>
  getGroupMessages(chatId: string, count?: number): Promise<ChannelMessage[]>
  listGroups(): Promise<ChannelGroup[]>
  // ...
}
```

**两个出站方法，参数都是 `content: string`。没有 media / image / file / audio 任何形态。**

### 3.2 入站却是四类媒体字段

`src/main/channels/channel-types.ts:97-127` —— `ChannelIncomingMessageData`：

| 字段 | 含义 |
|---|---|
| `images?: Array<{base64, mediaType}>` | 收到的图片 |
| `audio?: {fileKey, fileName?, mediaType?, durationMs?}` | 收到的音频（含**时长**） |
| `mediaRefs?: Array<{url, contentType?, fileName?}>` | 待下载地址，瞬态不落库 |
| `msgType?: string` | 平台原始类型（text / image / file） |

⇒ **不对称就在这里：入站四个字段，出站零字段。**

> 2. **微信不是「未验证」，是「已经做完了，同样绕过统一接口」** —— 我登记时只看 `weixin-api.ts:209 sendItems` 就下了「协议层可能有」的结论，没往上翻一层。实际上 `WeixinService` 上**已有** `sendImage(chatId, buffer, text?)` / `sendFile(chatId, buffer, fileName, text?)`（`weixin-service.ts:159/168`），`channel-weixin-handlers.ts:27/47` 在用它。**这跟飞书是同一个病：能力早就有，长在渠道私有分支里。**

### 3.4 飞书那条特例的代价

`sendImageMessage` 只在飞书的 IPC handler 里被调，**不在统一接口上**。后果：

1. 上层（自动回复、agent 工具、插件）想发图/文件，**必须认识飞书**，写飞书专属分支；
2. 其余六家加同样的能力，等于**每家复制一套私有 IPC 通道**；
3. 插件拿不到平台无关的「发媒体」入口 —— 它们只能调统一接口，而统一接口没有这条路。

⇒ **这正是「底座该收口而没收口」的典型：一家有、六家没有，且有的那家长在渠道私有分支里。**

## 4. 根因

**统一接口 `MessagingChannelService` 的出站侧从设计上就只有文本。** 不是哪家漏了实现，是**接口层缺这一格能力**。飞书那两个方法之所以是私有实现，正是因为接口上没有位置放它们。

## 5. 修复方向

### 5.1 先验、后设计

八家里 **六家的媒体发送能力完全没验过**，直接写接口等于猜协议。

**凭证现状（老大 2026-11-09 10:55 给）**：

> 「目前飞书是当前笔记本在用的，主要是飞书的限制比较少，目前飞书+微信，这两个可以直接扫码绑定的都在用。」

⇒ **飞书、微信可真机验证**；钉钉 / Discord / QQ / Telegram / 企业微信 / WhatsApp **无凭证**。

| 要验的 | 为什么必须验 | 凭证 |
|---|---|---|
| 飞书 `msg_type: 'audio'` 的格式与时长限制 | 现有 `sendFileMessage` 硬编码 `msg_type: 'file'`，发语音要另走 audio 分支；飞书对 opus 与时长有限制 | ✅ 有 |
| 微信 iLink `item_list` 支持哪些 item 类型 | `sendItems(items: Record<string, unknown>[])` 什么都装得下，但服务端认不认是另一回事；现有 `sendImage`/`sendFile` 是怎么组 item 的要先读懂 | ✅ 有 |
| 钉钉 / 企业微信是否真的支持机器人发语音 | 企业 IM 的机器人 API 常常只给文本 / 卡片 / 文件，**不一定有「语音消息」这个形态** | ❌ 无 |
| Discord / Telegram / QQ / WhatsApp | Telegram 有 `sendVoice`（OGG/OPUS）、Discord 是附件上传、WhatsApp 走 Cloud API 的 media 端点 —— 各家形态完全不同 | ❌ 无 |

**没验完不写接口。** 猜着设计出来的抽象，最后会被某一家的限制推翻。

**无凭证六家的处置**：`supportedMediaKinds` 留空或不实现 `sendMedia`，统一入口自动降级成文本。**这是正确结论，不是失败** —— 能力声明本来就要能表达「不支持」。将来拿到凭证再补，接入点不用改。

### 5.2 抽象形态：`sendMedia` 还是按类型分方法

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A · 单一 `sendMedia`** | `sendMedia(chatId, {kind: 'image' \| 'file' \| 'audio', path, mimeType?, durationMs?})` | 一个入口，扩展新形态改 union 即可 | 各家语义差异被压平，调用方不知道某渠道支不支持某 kind |
| **B · 按类型分方法** | `sendImage` / `sendFile` / `sendVoice`，全部可选（`?`） | 与入站的 `images` / `audio` 对称；不支持就是不支持，能被类型系统表达 | 方法数随形态增长 |
| **C · 能力声明 + 单一入口** | A 的单一入口 + `supportedMediaKinds: readonly MediaKind[]` 只读声明 | 调用方能**先问再发**；不支持的渠道可优雅降级（退回文字） | 多一个字段要各家维护 |

**方案已定：C。** 理由：

- 入站已经是「四字段」形态，出站如果也走单一入口 + 能力声明，两边刚好镜像；
- **降级路径是刚需** —— 老大的原始诉求是「用户不方便看文字就直接听语音」，那么「这家发不了语音」就必须能退回发文字，而不是抛错。C 的 `supportedMediaKinds` 让这件事在调用前就能判断；
- B 的可选方法虽然类型安全，但调用方要写 `if (service.sendVoice)` 这种判断，跟 C 的 `includes('audio')` 是一回事，C 更容易统一遍历。

> **裁定（老大 2026-11-09 10:46）**：「**发不了就只能退避发文字呗**」
>
> ⇒ **降级是既定行为，不是可选优化。** 具体落法：`sendMedia` 前查 `supportedMediaKinds`，不含目标 kind 就直接走 `sendMessage(text)` —— **不抛错、不静默丢弃、不弹窗**。调用方（插件）不需要知道这家支持什么，底座替它退。

### 5.3 实施顺序

1. **能力探测与文档化** —— 八家逐个验，结论回填本单；不动代码；
2. **接口扩展 + 飞书收编** —— `MessagingChannelService` 加 `supportedMediaKinds` + `sendMedia?`，只让飞书实现，把现有私有通道收编进来，**不改行为**；
3. **微信收编** —— 同构操作，独立一刀；

第 2 步是关键：**先把已经有的能力收编到统一接口上**，不改任何行为，纯粹是搬家，能建立「接口改了但行为没变」的信心。跟 v3-iter-8 把 S-324（判据不变）排最前的道理一样。

### 6.1 刀 1（2026-11-09）：接口扩展 + 飞书收编 —— **已交付**

| `channels/providers/feishu/feishu-service.ts` | 加 `supportedMediaKinds` + `sendMedia`（4 行委托） |
| `ipc/channel-handlers/channel-handler-utils.ts` | 两个函数搬走后改成 re-export，调用方零改动 |
| `ipc/channel-handlers/channel-feishu-handlers.ts` | 两处（IPC + tool executor）改走 `service.sendMedia`，**去掉两份重复实现** |

**为什么把读源工具从 IPC 层搬到渠道层**

`FeishuService.sendMedia` 要读本地文件或 URL。如果直接 import `channel-handler-utils.ts` 的 `readBinarySource`，会绕成：

```
channel-handler-utils → channel-manager → providers/feishu-service → feishu-outbound-media → channel-handler-utils
```

**循环依赖**。所以搬到 `channels/channel-media-source.ts`，IPC 层 re-export 保持调用方不变。

**一处行为变化，如实记**

原 `plugin:feishu:send-file` 的 `fileType` 参数（`args.fileType`）能覆盖飞书的 `file_type`。收编后统一入口**按扩展名推断**，不再读这个参数。

- 核查过：全仓 `fileType` 只在飞书 handler 内部出现，**从来没有任何调用方传过**（`PLUGIN_FEISHU_SEND_FILE` 只在 routing 白名单里，没有业务调用点）。
- ⇒ **实际行为不变**。该参数保留在类型里并标了 `@deprecated`，需要精确控制的场景请直接用 `service.api.media.uploadFile`。

**`feishu-service.ts` 501 行 → 加豁免注释**

收编后 501 行，超 500 硬上限。已按 AGENTS.md §大文件拆分第 5 条第 3 类加豁免，理由写进文件头：WS 生命周期 / 流式卡片轮转 / 入站媒体下载 / 群名用户名缓存共享多份可变状态，拆开要新增中间层；出站媒体已抽走，剩下是渠道服务本体。

**门禁**：`npm run typecheck` 三配置 0 错｜`npm test` **130/130**（与基线一致）。

### 6.2 后续刀的预期代价

- **微信收编**：同构，但 `WeixinService.sendImage` 的第三个参数 `text?: string`（图片附言）在统一载荷里没有对应格。要么忽略、要么加可选字段 —— 到时按调用方实际情况定。
- **无凭证六家**：接不进来是正常结论。`supportedMediaKinds` 空 = 降级发文本。
- **微信 `item_list`**：开放式 `Record<string, unknown>` 结构，接进去以后**类型系统管不住**，只能靠运行时校验。这一点要如实写进注释，不能假装有类型安全。

## 7. 刻意不做

1. **不做媒体格式转码** —— 插件给什么格式就发什么格式，发不了就由插件自己转。本仓不做 ffmpeg 这层。（跟「本仓不做具体功能实现」一致）
2. **不做语音消息的时长控制 / 切分** —— 属插件的事。
3. **不碰入站侧** —— 入站四字段已经能用，这单只补出站。
4. **不做「媒体消息落库」的改造** —— 发出去的消息怎么记，沿用现有消息记录逻辑。
5. **不替插件决定「什么时候该发语音」** —— 那是插件的判断，本仓只提供通道。
