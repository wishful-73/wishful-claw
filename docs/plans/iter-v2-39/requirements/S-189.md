> 「Target session must be a project session 首次派发报这个」

---

## 二、现象

**全局 PM 会话**里调 `create_session(projectId=…)` 建出一个项目会话，紧接着给它派活（`send_work_request`）⇒ **第一次必定失败**，回执：

```
Target session must be a project session
```

**重启应用后再派同一个会话，成功。** ⇒ 「**首次**」二字的来源。

---

## 三、根因（静态读码定位，**未实测**）

**一句话：`create_session` 工具走的是 worker 直插 SQL，INSERT 列表里**漏了 `scope` 列**，新行 `scope = NULL`；而派发校验按 `scope = 'project'` 判定，NULL 不匹配 ⇒ 当场判为「不是项目会话」。启动时那段补写把它补回 `'project'`，所以重启后就好了。**

逐跳（自工具到报错）：

| # | 位置 | 事实 |
|---|---|---|
| 1 | `Tools/Providers/ProjectToolsProvider.cs:69` | `create_session`（`availableModes: global`，PM 侧可见） |
| 2 | `AgentRuntimeProjectExecutor.cs:43` → `:195` `CreateSessionAsync` | 直接 `db.Execute(INSERT INTO sessions …)`，**不经渲染端、不经 `DbSessionTools.Create`** |
| 3 | `AgentRuntimeProjectExecutor.cs:219-231` | 构造 `SessionEntity`，只设 `Id / Title / Mode / CreatedAt / UpdatedAt / MessageCount / ProjectId / WorkingFolder / SshConnectionId / Pinned` —— **`Scope` 从未赋值**（`SessionEntity.Scope` 默认 `null`） |
| 4 | `AgentRuntimeProjectExecutor.cs:236-238` | INSERT 列清单 = `id, title, mode, created_at, updated_at, message_count, project_id, working_folder, ssh_connection_id, pinned, model_selection_mode` —— **没有 `scope`**（**也没有 `collaboration_mode` / `permission_mode`**） |
| 5 | `DbClient.cs:92` | 建表就是 `scope TEXT,` —— **可空、无默认值** |
| 6 | `DbClient.cs:535` | 迁移也是 `EnsureColumn("sessions", "scope", "TEXT")` —— 同样无默认 |
| 7 | `DbClient.cs:545-547` | 补写 `UPDATE sessions SET scope = CASE WHEN project_id IS NULL THEN 'global' ELSE 'project' END WHERE scope IS NULL OR scope NOT IN ('global','project')` —— **只在 DB 初始化时跑一次，不在插入时跑** |
| 8 | `AgentRuntimeGlobalTaskExecutor.cs:195-216` | PM 派活 → 建 dispatch 记录 |
| 9 | `DbGlobalTaskDispatchTools.cs:108-112` | 校验 `SELECT COUNT(*) FROM sessions WHERE id = @id AND scope = 'project'` ⇒ **0** ⇒ 返回 `"Target session must be a project session"` |
| 10 | 重启 | 第 7 步补写把 `scope` 补成 `'project'` ⇒ 同一会话再派发成功 ⇒ 与「首次失败」吻合 |

**这个 NULL 会被「懒修复」—— 所以只是「首次」失败**：

- `rowToSession`（`stores/chat-store/db-helpers.ts:219-238`）**自己就会调 `normalizeSessionContext`**：`scope=null` + `projectId` 有值 ⇒ 归一化成 `'project'`（`lib/session-context.ts:44-49` 的 `input.projectId ? 'project' : 'global'` 兜底）。
- 紧接着 `rowToSession:266` → `persistNormalizedSessionContext`（`:193-217`）发现 `row.scope !== session.scope` ⇒ **`void dbUpdateSession(...)` 把这行的 `scope` / `collaboration_mode` / `permission_mode` / `projectId` 写回 DB**（fire-and-forget）。
- ⇒ **这行只要被渲染端读过一次（`dbGetSession` / `dbLoadAll` 启动全量、侧栏加载），DB 里的 NULL 就被补成 `'project'`。**
- 而 PM 的 `send_work_request`（`AgentRuntimeGlobalTaskExecutor.cs:195-216`）→ `DbGlobalTaskDispatchTools.Create` 走的是 **C# 侧直查 DB，不经过渲染端**，补写还没发生 ⇒ **撞上 NULL ⇒ 报错**。
- ⇒ 重启（`dbLoadAll` 全量归一化）或其它任何「先读过这行」的操作之后，同一个会话再派发就成功 —— **「首次」二字的准确来源**。

**⚠️ 订正（2026-10-12 09:0x 自查）**：本节早先一版写过「`handleProjectSendSessionMessage` 也会被 scope=NULL 带偏（丢 projectId / 工作目录）」—— **那条是错的，已删**。`handleProjectSendSessionMessage`（`lib/tools/project-send-message.ts:77-79`）拿到的 `targetSession` 来自 `chatStore.sessions` 或 `dbGetSession`，**两者都过了 `rowToSession` 的归一化**，`scope` 已是 `'project'` ⇒ 普通 `send_session_message` 路径**无此症状**。本 bug **只在 C# 侧直查 DB 的那一跳（`DbGlobalTaskDispatchTools`）成立**。

**为什么 UI 建的会话没事**：渲染端走 `DbSessionTools.Create`（`DbSessionTools.cs:87-133`），INSERT 里**有** `scope` / `collaboration_mode` / `permission_mode`；`create_session` 工具这条旁路把这三列漏了。

## 四、修复方向（**已定：A + B** —— 老大 2026-10-12 09:07 裁定「根据你的推荐登记，不着急动手」）

**A（采纳 · 主改 · 最小且正确）**：`AgentRuntimeProjectExecutor.CreateSessionAsync` —— 让 `SessionEntity.Scope = "project"`，并把 `scope` 补进 INSERT 列清单与参数（`projectId` 是必填，这里出的一定是项目会话，**`scope` 的取值无歧义**）。

**为什么不连 `collaboration_mode` / `permission_mode` 一起硬写**：这两列的缺省**取决于渲染端的用户设置**，worker 读不到 ——
- `collaboration_mode` 缺省 = `settings.projectSessionDefaultCollaborationMode`（默认 `'cowork'`）；
- `permission_mode` 缺省 = `settings.autoApprove ? 'fullAccess' : 'default'`（`db-helpers.ts:233-236`）。

硬写成 `'cowork'` / `'fullAccess'` 会**盖掉用户设置**，反而不如现在「留 NULL、由渲染端按当前设置归一化」正确（`rowToSession` 已经在做这件事）。⇒ **A 只补 `scope` 一列。**

**B（采纳 · 互补 · 让消费方更结实）**：把 `DbGlobalTaskDispatchTools.Create` 的判定（`DbGlobalTaskDispatchTools.cs:108-112`）从 `scope = 'project'` 改成与全项目其它地方**同一条规则** —— `project_id IS NOT NULL`（对齐 `session-context.ts:127-129` 的 `getSessionScope()` 与 `DbClient.cs:545-547` 的启动补写）。这样即使别的路径再漏写 `scope` 也不会当场误判。

**C（否决）**：给 `sessions.scope` 加 `DEFAULT 'global'` —— 只挡 `NULL`，挡不住「项目会话拿到 global 默认」，**不解决本 bug**。
