# S-267 · 截图成功但页面是白的 —— 工具报告成功，实际什么都没画

> 归属：v3-iter-4（产品 1.0.4）｜登记并交付 2026-10-29 10:40
> **状态：已交付（刀 1g，自动化回归全绿）**，真机待验。
> 来源：dev 实例第 6 轮审查（`.wishful-claw/notes/review-feedback-round6.md` §三 缺陷 A）；老大 2026-10-29 10:08「根据你推荐推进」。
> 本条与 **S-264 / S-266** 同一个病根：**坏数据包装成好东西发出去**。那两条治的是图，本条治的是「工具成功回执」。

## 一、现象

| 步骤 | 返回 | 真实情况 |
|---|---|---|
| `BrowserNavigate` 打开 `file:///…/download.html` | `success: true` | 主文档 200，但 `<script type="module" src="./src/*.tsx">` 全部 `ERR_ABORTED` |
| `BrowserGetContent` | 标题正确（`<title>` 在静态 HTML 里就有） | 正文 `content: ""` |
| `BrowserScreenshot` | 一张 6204 字节的**纯白 PNG** | `capturePage()` 确实成功了 —— 画布本来就是白的 |

全程零报错。日志里的 `ERR_ABORTED` 只落在 **subresource** 上，`did-fail-load` 只报主框架，所以事件层也收不到。

## 二、为什么危险

老大的流程是「预览 html → 让 agent 截图看效果 → 改壳子」。如果预览页是**未构建的 SPA**：

> agent 拿到白图 ⇒ 以为看到了 ⇒ **照着白图去改壳子**。

这和 `DesktopScreenshot` 不落盘（S-268）是同一类缺陷：**工具报告成功，实际没做成**。而 400 那条线（S-261/S-262）至少还会喊一声。

「未构建」是极易踩到的场景：`website/` 下 `index.html` / `download.html` / `go.html` 三个都是 Vite 外壳 —— `<div id="root"></div>` + `<script type="module" src="./src/*.tsx">`。`file://` 打开时 `.tsx` 不转译，页面必然全白。

## 三、为什么选「加一句警告」而不是「报错」

dev 给了两条路：①截图侧检出白图附警告；②`BrowserNavigate` 在 `did-fail-load` 时别报 success。

**②治不了根**：本例里 `did-fail-load` 根本不触发（主文档是成功的），改它对这个场景零效果。

**①也不该把工具判成 `isError`**：截图确实成功了，报失败会让模型以为要重试，而它真正需要的是一条「你看到的是空的，别据此判断」。

⇒ 做法：**结果不变、`isError` 不变，只在文本尾部追加一段警告**。

## 四、判据设计（宁可漏报，不许误报）

两个条件同时成立才警告：

| # | 条件 | 为什么 |
|---|---|---|
| 1 | 视口抽样**近全白** | 白底页面本身完全可以是正常的（用户就要一张白图） |
| 2 | **且** DOM 里几乎没有元素、没有可见文本 | 只有「白 + 空」才等于「壳在、内容没渲染」 |

细节：

- **抽样 512 个点**（`pixelCount / 512` 步长）。一张 2K 截图 800 万像素，逐点扫会卡住渲染进程。
- **近白阈值 250/255**，留 5 档余量给抗锯齿和滚动条阴影。
- **全透明像素按空白算**：webview 未绘制区域是透明的，它和白一样代表「这里什么都没有」。
- **DOM 元素数上限 12**：未渲染的外壳通常只剩 `html / head / script / body / #root`。
- **任何一步取不到数据都返回 null（不警告）**：这是诊断增强，不能自己变成新的报错源。

## 五、落地

| 文件 | 动作 |

| `src/renderer/src/lib/tools/browser-screenshot-blank.ts` | **新建**。`isViewportNearlyBlank`（BGRA 抽样）+ `UNRENDERED_DOCUMENT_PROBE` + `detectBlankScreenshotWarning` |

| `src/renderer/src/lib/tools/browser-native-ui.ts` | `executeBrowserScreenshot` 在文本尾部拼 `blankWarning`（`+` 拼接，无条件覆盖原文本） |

**为什么单独开文件**：`browser-native-ui.ts` 已有 481 行，塞进去必然破 500 行门禁；而「判白 + 文档探针 + 结论文本」三件事自洽，独立成文件正好。

## 六、判据（验收）

1. **白图 + 空 DOM** ⇒ 结果文本含 `WARNING`，且含 `file://` / dev server 的指引。
2. **白图 + 有内容**（例如纯白背景但页面有文字）⇒ **不警告**（DOM 判据挡住）。
3. **正常截图** ⇒ 文本与修复前逐字一致，且不执行 DOM 探针（`isViewportNearlyBlank` 先返回 false 就退出）。
4. **`toBitmap()` 抛错** ⇒ 静默返回 null，不中断截图。
5. **`executeJavaScript` 抛错** ⇒ 静默返回 null，不中断截图。
6. **`isError` 不变** —— 截图成功永远是成功。

## 八、不做的事

- **不做 OCR / 不做「页面上有几个可见字符」的精确图像分析** —— 判据只要够挡住「纯白空壳」。
- **不改 `BrowserNavigate` 的 `success`** —— 主文档确实加载成功了，改它是撒谎，而且对本场景无效。
- **不合并进 S-264 / S-266** —— 那两条在 C# 侧管图像字节，本条在渲染端管截图回执，改动面零交集。
