# S-288 · 聊天窗图片点开只能「装进窗口」，不能放大看细节

> 归属：**移交 v3-iter-5**（2026-10-30 15:09 老大登记）。
> 定性：**体验缺口 + 能力不齐**，不是崩溃类缺陷。
> ⚠️ 入口待老大补一句确认（见 §五）。

## 一、原话

老大 2026-10-30 15:09：

> 「现在**图片预览 限制了高宽  我点开图片查看看不到放大版本**，其次……这些下个迭代处理。」

## 二、现状：项目里有三套图片查看，能力不一样

| 位置 | 组件 | 能力 |
|---|---|---|
| **聊天窗内图片**（工具输出 / 截图卡 / 生成图 / 消息内嵌图） | `components/chat/ImagePreview.tsx` | 缩略 `max-w-lg` + `aspectRatio`；点开 = 全屏浮层，`motion.img className="h-full w-full object-contain"`（`:416-425`）—— **只有 `object-contain`，无缩放、无拖拽、无 1:1** |
| 右侧预览面板 / 点本地图片路径 | `lib/preview/viewers/image-viewer.tsx` | `ZoomIn / ZoomOut / RotateCw / Maximize2 / Copy`，`clampScale` 0.25 ~ 5 |
| 聊天窗里点开「本地图片」 | `components/chat/LocalImagePreviewDialog.tsx` | 复用上一层，注释原文：「保证缩放 / 旋转 / 复制 / 拖拽一套能力完全一致」 |

**问题是同一件事只落到了两处，聊天窗这条主路径没落。**

`object-contain` 只会把图**等比塞进容器**：一张 2520×1680 的桌面截图在 1080p 屏上被压到
≈1000×667，等于丢掉了 60% 的像素 —— 「点开了，但还是看不清」，正是老大说的「看不到放大版本」。
`ImagePreview.tsx:348` 那句 `Click to enlarge` 在这一点上是名不副实的。

## 三、方案

### 3.1 主修：lightbox 换成 `ImageViewer`

`ImageViewer` 已经是项目统一入口（`ViewerProps` 接收 `filePath`），`LocalImagePreviewDialog`
已经证明「拿它当浮层宿主」这条路走得通。改 `ImagePreview.tsx` 的 `isOpen` 分支：
把 `motion.img` + 右上角手搓的 复制 / 下载 / 关闭 三个按钮，换成 `ImageViewer`
（它自带复制与缩放，`download` 通过 `actions` 传进去，别重写一套）。

目标能力与另两处**逐项一致**：缩放 0.25~5、旋转、最大化、复制、拖拽。

### 3.2 补修：缩略给高度上限

`max-w-lg` 只有宽度约束，竖图（1080×1920）算下来 ≈910 px 高，一屏就没了。
加 `max-h-[320px]` 之类的上限，`img` 改 `object-cover`（或 `contain` + 背景色），
让缩略回到「一行消息里的预览」而不是「半屏海报」。

### 3.3 与 S-284 的关系（重要）

S-284 之后历史消息里只剩 `filePath`，缩略靠 `useImageDisplaySrc` → `oc-media://` 取图。
**`ImagePreview` 的点击只在 `effectiveSrc` 非空时才 `setIsOpen(true)`**（`:307-309`）。
若 `oc-media://` 取不到文件，缩略会一直停在 `Loading image...`，**点了什么都不发生** ——
这也能表现为「点开看不到放大版本」。实施时**先跑一次 S-284 的真机验收第 2 条**
（重开旧会话，截图能否正常显示），再判断是不是本条要治的东西。

## 四、代价与风险

- `ImageViewer` 的 `ViewerProps` 需要 `filePath`；纯 `data:` / `blob:` / `http:` 来源的图没有路径。
  两条路：①给它加一个 `src` 入参（改公共组件，影响另两处）；②无 `filePath` 时退回现有的
  `object-contain` 浮层。**倾向 ②**：改动面小，且项目里 `filePath` 是常态（S-283 之后截图与
  生成图都落盘）。
- `ImagePreview.tsx` 现 436 行，换掉 lightbox 后**大概率突破 500 行上限**。按 AGENTS.md
  拆分规范，lightbox 本身就是一个独立呈现单元 —— 直接拆成 `ImageLightbox.tsx`。

## 五、入口待确认（需要老大一句话）

老大 15:09 那条来自 dev 实例的测试，而**极简档下桌面截图不出卡**（S-248 之后的
`PROCESS_LINE_CARD_ONLY_TOOL_NAMES` 不含它，只有一行文字），所以「点开的图」可能不在截图卡上。
三个候选：

1. 详情 / 紧凑档里截图卡上的缩略 → `ImagePreview`（本条主修对象）；
2. 消息里的**图片附件 / 粘贴图** → `InputArea/image-preview-strip` 的路子，不是同一个组件；
3. 点开本地图片路径 → `LocalImagePreviewDialog` + `ImageViewer`（这条本来就是全能力的）。

**实施前问一句「在哪点的」即可，不用提前改。** 若是 3，本条只剩 §3.2 的缩略上限。

## 六、验收方向

1. 详情档点开一张 2520×1680 的截图 → 能滚轮 / 按钮放大到 1:1，能拖动看边角。
2. 竖图缩略不超过约 320 px 高。
3. `data:` 来源的图（无 `filePath`）点开不报错、仍是原样全屏。
4. 三个入口的能力清单一致（缩放 / 旋转 / 复制 / 下载）。

## 七、刻意不做

| 不做 | 为什么 |
|---|---|
| 不做图片画廊（左右翻页） | 老大要的是「能放大看细节」，不是浏览体验升级；一张一张点是当前语义。 |
| 不动 `ImageViewer` 的缩放区间 | 0.25~5 是既有口径，另两处已在用。 |
| 不重写一份缩放容器 | 项目里已经有两处复用 `ImageViewer`，第三处照做即可 —— 再写一份就是第四种口径。 |

## 八、实施记录（v3-iter-5 刀 5）

### 8.1 主修：lightbox 换 `ImageViewer`，并拆成独立文件

`ImagePreview.tsx` 436 → **365 行**，浮层整体搬进新文件 `ImageLightbox.tsx`（171 行）。两个文件都在 500 行内，**不需要豁免头**。`ImagePreviewAction` 类型一并搬过去，`ImagePreview.tsx` 只做 `export type` 转发，外部三个调用点一行未动。

分工：

| 来源 | 浮层形态 |
|---|---|
| 有 `filePath`（S-283 之后的截图 / 生成图 / 历史消息） | `Dialog` + `ImageViewer`：缩放 0.25~5 / 旋转 / 最大化 / 复制 / 拖拽，与右侧面板、`LocalImagePreviewDialog` 同一套 |
| 无 `filePath`（`data:` / `blob:` / `http:`） | 保留原 `object-contain` 浮层，行为不变 |

按 §四 倾向 ② 走：**没给 `ImageViewer` 加 `src` 入参**。理由是那两处入口已经在用 `filePath`，加一个覆盖源要连带改它们的取图路径与 canvas 复制（`oc-media://` 有 taint 风险），
而缩略能出图本身就意味着 `filePath` 可读（缩略走 `useImageDisplaySrc` → `oc-media://`）——「缩略看得见、浮层读不到」这只组合不会出现。

下载：`ImageViewer` 没有下载能力，浮层自己在 `DialogContent` 右上角补一个按钮（`right-12`，让开内置的关闭 X），
复用 `ImagePreview` 原有的 `handleDownload`，四条能力才齐（§六 验收 4）。

### 8.2 顺带修掉的真因：`sm:max-w-lg` 压掉了 `max-w-[95vw]`

`DialogContent` 自带 `sm:max-w-lg`（`ui/dialog.tsx:56`）。Tailwind 变体优先级高于裸工具类，所以
`LocalImagePreviewDialog` 那句 `max-w-[95vw]` **在 ≥640px 视口上是无效的** —— 浮层一直是 512px 宽。
两处都补了 `sm:max-w-[95vw]`。

这条属于 §五 候选 3 的入口，但根因与本条完全一致（「点开了还是看不清」），**不修等于没解决**，所以一并修。两行改动，不扩面。

### 8.3 缩略高度上限（§3.2）

`ImagePreview` 缩略容器加 `max-h-[320px]` + `bg-muted/10`，`img` 从 `w-full h-auto` 改 `h-full w-full object-contain`。

`aspectRatio` **保留**：它是加载前后高度一致的保证（去掉就是 S-233 那类抖动）。2520×1680 的横图算出来 341px 高、被压到 320，
左右各留 16px 底色 —— 宁可留白不裁切，缩略的职责是「认得出是哪张」。

### 8.4 新增门禁 `tests/image-lightbox`（13 断言）

纯 className 缺陷抽不出纯函数（抽一个 `shouldShowBig()` 只会造一次性导出），所以做成**源码闸**，
先例是 `tests/data-dir` 的源码行序闸。钉四类易回归点：

1. **两处 `DialogContent` 必须有 `sm:max-w-[95vw]`** —— 少写它，浮层悄悄退回 512px，肉眼极难发现；
2. `filePath` 分支必须渲染 `ImageViewer`，且 `content=""` / `viewMode="preview"` 两个必填入参不能漏；
3. 没有 `filePath` 时必须保留 `motion.img` + `object-contain` 回退；
4. 缩略必须同时有 `max-h-[320px]` / `max-w-lg` / `aspectRatio` 三件，且 `ImagePreview` 里不许再留 `AnimatePresence`。

**反向验证**：删掉 `ImageLightbox.tsx` 的 `sm:max-w-[95vw]` ⇒ 红
`ImageLightbox.tsx 的 DialogContent 必须写 sm:max-w-[95vw] —— 否则内置 sm:max-w-lg 会在 ≥640px 视口把浮层压回 512px`，加回复绿。

### 8.5 又踩了一次同一个坑（接 §8.4 of S-290）

反向验证时用 `(Get-Content -Raw) -replace | Set-Content` 改 `.tsx`：PS 5.1 的 `Get-Content -Raw` 按 ANSI 解码 ⇒ 中文注释整片变乱码，
`Set-Content -Encoding UTF8` 又追加 BOM。**整个文件重写才复原。**

规矩再补一条硬约束：**在任何文本文件上都不用 PowerShell 做读改写，一律 Edit 工具或 `[IO.File]::ReadAllText/WriteAllText` + `UTF8Encoding($false)`。**
