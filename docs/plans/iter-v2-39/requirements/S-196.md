## 二、现象

一条 assistant 消息的操作栏同时显示三个数字，**互相矛盾**：

```
15:58 · 481h56m · 共 7m40s
```

| 显示位 | 来源 | 值 | 对不对 |
|---|---|---|---|
| `15:58` | `finishedAt = updatedAt ?? createdAt` | 15:58 本地 | ✅ |
| `481h56m` | `elapsedMs = updatedAt − createdAt` | 481h56m（≈ 20 天） | ❌ |
| `共 7m40s` | `totalElapsedMs`（prop） | 7m40s | ✅ |

同一张卡片上，「本轮耗时」比「整轮总耗时」大 **3800 倍**。

## 四、根因

### 4.1 病灶：`adjustCompactArtifactTimestamps`

`src/renderer/src/stores/chat-store/index.ts:2098`：

```ts
function adjustCompactArtifactTimestamps(messages: ChatMessage[], boundaryIndex: number): void {
  const summaryIndex = boundaryIndex + 1
  if (summaryIndex >= messages.length) return
  const prev = messages[boundaryIndex - 1]
  const next = messages[summaryIndex + 1]
  if (!next) return // appended at the end — fresh timestamps are already correct
  const lower = prev ? prev.createdAt : 0
  const upper = next.createdAt
  if (upper - lower >= 3) {
    messages[boundaryIndex].createdAt = upper - 2      // ← 把「今天」改写成「历史位置 - 2ms」
    messages[summaryIndex].createdAt = upper - 1       // ← 同上，- 1ms
  } else if (prev) { /* … */ }
}
```

调用点 `:2158-2163`（仅在 `isNewBoundary`，即工件是**本次新建**时）：

```ts
if (isNewBoundary) {
  const boundaryIndex = mergedMessages.findIndex((m) => m.id === boundaryId)
  if (boundaryIndex >= 0) adjustCompactArtifactTimestamps(mergedMessages, boundaryIndex)
}
```

**它的用意是正确的**（见 `:1997-2002` 注释）：DB 按 `(created_at, sort_order)` 排序，工件若带「现在」的时间戳，重载时会被推到转写末尾，所以要把它们**挪到压缩发生点**。09-23 那对工件的 `created_at` = `...606` / `...607`，正是其后一条 `user_1790143290608`（`06:01:30.608`）**减 2ms / 减 1ms** —— 与数据库**逐位吻合**，证明它们是被这个函数改写的。

**问题是**：它改的是 `createdAt` —— 一个**同时被渲染层当语义时间用**的字段。

### 4.2 渲染层把工件时间当成了「这一刀落下的时刻」

`src/renderer/src/components/chat/renderable-chat-items.ts`：

```ts
function resolveCutTime(pair, liveState): number | null {   // :180
  if (!pair) return liveState?.startedAt ?? null
  const score = Math.max(pair.boundary.createdAt, pair.summary.createdAt)   // ← :185
  return score > 0 ? score : null
}
```

切分时的「段首尾相接」逻辑（`:386-435`）：

```ts
let cursorTime = message.createdAt                 // :389  第一段起点 = 消息创建时间
for (const { pair, splitAt } of splits) {
  const cutTime = resolveCutTime(pair, liveState)  // :393
  // …切出「这一刀之前」的段：createdAt = cursorTime, updatedAt = cutTime
  if (cutTime !== null) cursorTime = cutTime       // :412 / :433  下一段起点 = 这一刀的时间
}
// 末段：createdAt = cursorTime, updatedAt = message.updatedAt
```

⇒ 末段（唯一显示耗时的段）拿到 `createdAt = 09-23 06:01:30`。

操作栏 `AssistantMessage/action-bar.tsx:64`：

```ts
const elapsedMs =
  updatedAt != null && createdAt != null && updatedAt > createdAt ? updatedAt - createdAt : null
```

⇒ `10-13 07:58:23 − 09-23 06:01:30` = **481h56m**。

### 4.3 同卡片里「共 7m40s」为什么是对的

`renderable-chat-items.ts:451`：

```ts
const totalElapsedMs =
  message.updatedAt != null && message.updatedAt > message.createdAt
    ? message.updatedAt - message.createdAt
    : undefined
```

⇒ 用的是**原始消息**的 `createdAt`（`10-13 07:50:43`，没被改过）⇒ **7m40s** ✅

**两条公式一模一样，差别只在 `createdAt` 这个 prop 是不是被切分逻辑顶替过** —— 这正是矛盾的来源，也解释了「为什么同一条消息两个耗时都能显示出来」。

### 4.4 一句话

> **`adjustCompactArtifactTimestamps` 为了「重载时排序正确」改写了工件的 `createdAt`；渲染层又把同一个字段当成「这一刀的时间」用 ⇒ 段起点被拽回 20 天前。**

两者各自都说得通，**叠在一起才出错**。所以修哪一边都行，但**不能都不动**。

### 4.5 影响面

不只在跨天场景发作：**任何一次压缩**，只要工件被重定位到「比当前消息更早」的位置，末段耗时都会**虚增成「当前消息起点 → 压缩点」的跨度**。跨天会话只是把误差放大到肉眼可见（20 天）。全库扫 `displayAnchor` 与工件 `created_at` 不一致者共 **3 条**。

### 4.6 「落刀时刻」和「工件在转写里的位置」是两个概念

老大的现场时序（§一）说明这次压缩**实际发生在今天 07:50 前后**，工件却躺在 **09-23**。两者都对，混的只是概念：

| 概念 | 值 | 谁要它 |
|---|---|---|
| **压缩动作发生的时刻** | 今天 07:50 前后 | 用户看的「耗时」—— 应该用这个 |
| **工件在转写流里的归属位置** | 09-23 06:01:30 | DB 排序、重载后回放位置 —— 用这个 |

该会话里确实存在 09-23 的真实旧消息（`user_1790143290608`，**不是**工件：`created_at` 与 id 内嵌时间戳一致，未被改写）。本次压缩把**更早**的 57 条压成摘要，保留段从它开始 —— 所以工件的**归属位置**就在 09-23，`adjustCompactArtifactTimestamps` 的 `upper−2 / upper−1` 正是把它对齐到这条消息之前。

⇒ **重定位本身没错**：不这么做，工件重载后会被排到 20 天后的末尾，摘要卡片就跑到消息后面去了。**错在渲染层把「归属位置」当成了「动作时刻」。**

⇒ 所以修的方向仍是 §五：**另找一个不受重定位污染的「动作时刻」来源**。

## 五、修复方向（已定案 —— 2026-10-13 16:58）

| | **方案 A：渲染侧 clamp** | **方案 B：给 relocate 的时间另存一份** | **方案 C：改用锚点消息的时间** |
|---|---|---|---|
| 做法 | `cursorTime` 取值后夹到 `[message.createdAt, message.updatedAt]` | `adjustCompactArtifactTimestamps` 改写 `createdAt` 的同时，把真实落刀时间写进 meta（如 `compactSummary.cutAt`），`resolveCutTime` 优先读它 | `resolveCutTime` 不再读工件 `createdAt`，改读 `displayAnchor` 指向的 assistant 消息的时间 |
| 效果 | `481h56m` 立刻消失 | 语义正确，分段耗时准确 | 语义正确，且**不用改 schema** |
| 风险 | **治标**：clamp 到同一值后，各段时间戳趋同 ⇒ 退回端口注释里点名的那个老毛病（「看着像同一个耗时重复了好几遍」）；且首段 `finishedAt`（`:62`）也会显示错的历史时间 | 动 `meta` schema，需兼容历史数据 | 需要按 `assistantMessageId` 反查消息对象；锚点消息若在流式中，其 `updatedAt` 可能未定 |
| **结论** | ⚠️ **仅作兜底**（单独上会把分段弄没） | ✅ **定案采用** | ❌ **出局**（§5.1 ② 已证伪） |

**倾向方案 C（并保留 A 的 clamp 作兜底）** —— 理由：

1. **锚点才是真相。** `displayAnchor.assistantMessageId` 是「这次压缩挂在哪条消息上」的权威记录，它**今天仍在指今天**（§3.3），没被 relocate 污染；工件的 `createdAt` 已经被当成排序键用了，**再当语义时间就是复用不当**。
2. **不动 schema、不动 DB、不动排序逻辑** —— `adjustCompactArtifactTimestamps` 的排序用意是对的，不该为显示问题去改它。
3. **clamp 必须同时加**：锚点消息可能缺 `updatedAt`（老消息）或锚点解析失败，此时兜底夹到消息自身区间，保证**永远不出现超出本轮跨度的数字**。

> ⚠️ **原倾向的方案 C 已被证伪**（见 §5.1 ②：`displayAnchor.assistantMessageId` **恒等于**要切的那条消息自己 ⇒ 取它的时间等于把切点拽回消息开头，会吃掉真分段）。

**定案：方案 B + A 兜底** —— 理由：

1. **只有 B 拿得到「落刀时刻」。** `adjustCompactArtifactTimestamps` 执行的那一刻，工件 `createdAt` 还等于真实落刀时刻 —— 在改写**之前**把它存进 `meta` 即可，改动小且精准（§5.1 ③）。
2. **A 单独上会把分段弄没。** clamp 之后，被重定位过的切点一律塌到消息起点，各段时间戳趋同 ⇒ 退回端口注释点名的老毛病（「看着像同一个耗时重复了好几遍」）—— 那正是「来时的路」（老大对回到旧行为极敏感）。
3. **A 仍要留作兜底**：历史数据没有 `cutAt`（本例那 3 条），此时夹到消息自身区间，保证**任何情况都不出现超出本轮跨度的数字**。
4. **动的是 `meta`（JSON），不是 DDL**，无迁移；只需确认没有别的读取方把 `compactBoundary` / `compactSummary` 的键当**封闭集合**用。

> **已定案**（2026-10-13 16:58 老大「根据你的建议去登记」）。A 是最小止血（一行），B 是正解，两者一起上；另加 §5.1 ④ 的段数补丁。

### 5.1 实测补充（2026-10-13 16:48 之后，查线上库）

**① 一条捷径被实测证伪 —— 库里已经不存「落刀那一刻」。**

原本想：`adjustCompactArtifactTimestamps` 只改 `createdAt`，工件的 `updated_at` 或许还留着真实落刀时刻 ⇒ 改读 `updatedAt` 即可。直接查库否掉了：

```
compact-boundary-7def1ab8…  created=2026-09-23 06:01:30  updated=2026-09-23 06:01:30
compact-summary-f9574e8c…   created=2026-09-23 06:01:30  updated=2026-09-23 06:01:30
```

⇒ 两个字段一样，**想拿真实时刻只能在改写时另存一份（方案 B）**，或退而求其次用锚点（方案 C）。**「读 `updatedAt`」这条出局。**

**② 方案 C 出局 —— 锚点指向的消息就是「要切的那条消息自己」。**

`renderable-chat-items.ts` 的配对逻辑决定了这一点：

- `:300-306` 按 `anchor.assistantMessageId` 把工件对塞进 `anchoredPairsByAssistantId`；
- `:365-376` 再按 `message.id` 把对取出来，对**这条消息**做切分。

⇒ `anchor.assistantMessageId` **恒等于** `message.id`（不等就根本走不到切分分支）。而 `displayAnchor.afterContentBlockCount` 的语义是「在这条消息的第 N 个 block 之后」——**它就是切点本身**，只是**没带时间戳**。

⇒ 方案 C 取「锚点消息的 `createdAt`」= 取**这条消息自己的起点** ⇒ 切点恒等于消息开头：

- 第一段 `createdAt == updatedAt` ⇒ 被 `:199` 的 `end <= start` 丢弃；
- 末段 = 全长。

⇒ 本例（压缩发生在消息**之前**）结果碰巧对（`7m40s`），但只要压缩真发生在**流式中途**（`afterContentBlockCount > 0`），C 会把本该分段的切点一起拽回消息开头 ⇒ **分段被吃掉且不可恢复**。§五表里 C 的「语义正确、分段耗时准确」**站不住 —— 出局**。

**③ 修正后的倾向：B（改写时另存真实落刀时刻）+ A（兜底）。**

`adjustCompactArtifactTimestamps` 执行的那一刻，工件的 `createdAt` **还等于真实落刀时刻**（改写之前）⇒ 顺手存下来即可：

```ts
const cutAt = messages[boundaryIndex].createdAt   // 改写前 = 真实落刀时刻
messages[boundaryIndex].createdAt = upper - 2     // 排序键照改，语义不变
// meta 另存：compactBoundary.cutAt = cutAt；summary 侧同理 compactSummary.cutAt
```

`resolveCutTime` **优先读 `cutAt`**，读不到（历史数据，如本例那 3 条）时用 **A 的 clamp 兜底**。

- 不动排序语义（`createdAt` 照改）、不动 DDL（`meta` 是 JSON）、历史数据自动走兜底；
- 兜底保证「任何情况下数字都不会超出本轮跨度」；
- 代价 = 动 `meta` 结构，需确认无其它读取方把 `compactBoundary` / `compactSummary` 的键当**封闭集合**用。

**④ 无论 A 还是 B，都还得补一处：`totalElapsedMs` 只在真切出 ≥2 段时才挂。**

这条与方案选择无关 —— `renderable-chat-items.ts:438-463` 挂 `totalElapsedMs` 时**不看段数**，`action-bar.tsx:153` 也只看 `!= null`。第一段被丢弃、实际只剩一段时仍会多报一个「共 X」：

```
15:58 · 7m40s · 共 7m40s
```

⇒ 判据：加末段前 `assistantItemIndexes.length >= 1`（即真的切过）。少了这一处，这条需求只修好数字、没修好观感。

**⑤ 顺手记两条待查（不属本条，本轮不动）：**

- 上一条 assistant 消息 `wc-agent-1790163027380-digexd`：`created_at` = 09-23 11:30:27（与 id 内嵌时间戳一致，**未被改写**），但 `updated_at` = **10-13 07:51:32** —— 比 `lklq6m` 的 `createdAt`（07:50:43）**晚 49 秒**，两条消息时间区间重叠。09-23 那条消息的流是 10-13 才收的尾。
- 该会话 09-23 之前的 assistant 消息 `updated_at` **全是 `null`** ⇒ `elapsedMs` 要求 `updatedAt != null`，这批消息**一个耗时都不显示**。

## 六、代价与取舍

**动的是 `meta`（JSON 列），不是 DDL** —— 加 `cutAt` 无迁移，历史数据读不到就走兜底。已确认全仓没有把 `compactBoundary` / `compactSummary` 的键当**封闭集合**用的读取方（消费点全是逐字段可选读；`sidecar-mapping.ts:82-87` 只做 `displayAnchor` 剥离，不枚举键）。

**接受的代价一：兜底会让老数据的分段塌成一段。** `clampCutTime` 把被重定位过的切点夹回消息起点后，首段 `createdAt == updatedAt`，各段时间戳趋同 —— 这正是 port 注释点名的老毛病（「看着像同一个耗时重复了好几遍」）。可接受，因为：① 只影响**没有 `cutAt` 的老数据**（全库 3 条）；② 新数据一律走 `cutAt`，分段完好；③ 不夹的后果是显示 `481h56m`，比「分段看不清」严重得多 —— 这是「宁可想不起分段，也不能报出荒谬数字」。

**接受的代价二：`cutAt` 存的是一对工件的 `max(createdAt)`。** 与 `resolveCutTime` 原口径一致（「取边界与摘要里更晚的那个」，见 `context-compression.ts` 判活压缩用同一口径），所以两个工件 `meta` 里存的是同一个值 —— 冗余但语义统一，读哪边都一样。

**不接受的代价**：为显示问题去改 `adjustCompactArtifactTimestamps` 的排序语义 —— 那会把「重载后工件被推到转写末尾」这个真实问题放回来。

---

## 七、刻意不做

1. **不动 `adjustCompactArtifactTimestamps` 的排序语义** —— 它解决的是「重载后工件被推到末尾」这个真实问题，改它会把 DB 排序搞坏。
2. **不改 `totalElapsedMs` 的算法** —— 它是对的，且是这个 bug 的「参照物」（正是它让矛盾暴露出来）。
3. **不给操作栏加「异常值」静默屏蔽**（如「超过 24h 就不显示」）—— 那是掩盖，不是修复。
4. **不顺手做 S-194（token 单位）那边的格式化收敛** —— 两件事无关。
