# S-290 · 截图经能力代理调用时 image 块被 32 KB 截断 —— S-283「本轮看得见图」的前提落空

> 归属：**移交 v3-iter-5**（2026-10-30 19:30 老大定「登记到下个迭代吧，当前迭代越弄越久」）。
> 定性：**不是回归，是老缺陷** —— 截断逻辑早于 S-283；但 S-283 的方案 A 明确押在「本轮 image 块照旧保留、模型看得见」，本条让那个前提第一次显形。
> 改动面：`ToolCallProcessor.OutputLimit.cs` 一处判据，**不动 S-283 / S-284 已交付的任何代码**。

## 一、来历

dev 实例 2026-10-30 19:24 真机截图，验 S-283 / S-284 时看日志撞见：

```
19:24:38.398 [worker] agent tool output truncated
  runId=wc-agent-1793359476027-uf70aq  tool=use_capability
  originalBytes=712499  truncatedBytes=32768
```

同一轮库里落的是干净数据（见 §三），说明**落库那份和送模型那份走了两条不同的路**。

老大 19:30 定：登记到下个迭代，本迭代不修。

## 二、根因：两个出口拿的不是同一份内容

`ToolCallProcessor.cs` 里同一个工具结果喂了两处，用的是**不同变量**：

| 行 | 去处 | 用的变量 | 后果 |
|---|---|---|---|
| `:389` | `tool_call_result` 事件 → 渲染层落库 | `toolOutput`（**完整** 712,499 B） | 完整 image 块，S-284 正常剥 `data` |
| `:412` | 交给模型（provider 报文） | `truncatedOutput`（**32,768 B**） | 残 JSON 文本，图不可用 |

`truncatedOutput = ApplyToolOutputLimit(...)`（`:395`），而 `ApplyToolOutputLimit`（`OutputLimit.cs:81-99`）的豁免名单只有两条：

```csharp
if (AgentRuntimeUseCapabilityExecutor.IsUseCapabilityTool(toolCall.Name))
{
    var action = (JsonHelpers.GetString(toolCall.Input, "action") ?? "").Trim().ToLowerInvariant();
    if (action is "list" or "inspect") return output;      // ← 只豁免这两个 action
}

if (string.IsNullOrEmpty(sessionId) || IsRetrievalTool(toolCall.Name))   // ← IsRetrievalTool 只有 Read
    return TruncateToolOutput(output);

return SpillToolOutput(toolCall.Name, output, sessionId);   // ← 截图走这里
```

截图是 `builtin:DesktopScreenshot`，经 `use_capability` 代理调用（`action` 不在豁免名单）⇒ 走 `SpillToolOutput`：712 KB 落进 `~/.wishful-claw-dev/spill/session-8deb…/f8b2990…`，内联只留 head 16 KB + 提示 + tail 16 KB。

**被截断的是 JSON 文本**，不是结构。`head` 里是 `[{"type":"image","source":{"type":"base64",…,"data":"<前 16 KB base64>`，`tail` 里是 base64 尾巴 + `"filePath":…` + 文本行。中间那段是 `[truncated N of 712499 UTF-8 bytes]` 提示。

⇒ 模型这一轮拿到的**不是 image 块，是一段砍断的 JSON 文本**。PNG 只到 16 KB（原 ≈700 KB），解不出来。

`:410-412` 那句注释挡住了另一条路：

```csharp
// S-145: 内部工具可以返回结构化 content（Read 读图 → image 块）。有它就用它 ——
// 文本截断是按字符做的，对 base64 图像块没有意义也不该动它。
toolContentBlocks ?? AgentRuntimeProviderSupport.CreateStringElement(truncatedOutput),
```

**注释写对了，但只有 `Read` 有 `toolContentBlocks`。** 截图工具返回的是字符串化 JSON，走的是 `??` 右边。

### 更危险的分支：spill 失败时退回**无提示**截断

`SpillToolOutput`（`:112-144`）失败时会退到 `TruncateToolOutput`（`:131`）：

```csharp
try { spill = SpillStore.SaveText(sessionId, toolName, output); }
catch (Exception ex)
{
    WorkerLog.Warn("agent tool output spill failed …");
    return TruncateToolOutput(output);   // ← 这条路没有任何"我落盘失败了"的提示
}
```

两条路的差别不在截断本身，在**模型知不知道**：

| 路径 | 模型看到的 | 能否自救 |
|---|---|---|
| spill 成功（19:24 的实测） | head 16 KB + `[tool output too large: … saved to <路径> — <取回提示>]` + tail 16 KB | 能 —— 提示里直接给了路径，模型当场就去 `Read` |
| spill 失败（`:131`） | head 16 KB + `[truncated N of 712499 UTF-8 bytes — rerun with narrower args]` + tail 16 KB | **不能** —— 这句话是给文本输出写的，「用更窄的参数重跑」对截图毫无意义，模型也没有路径可读 |

**截图没有 `path` 参数的替代路径**（`S-268` 记录的 `DesktopScreenshot` 的 `path` 参数无效、S-283 才补上默认落盘）。所以 spill 失败时模型手里只有一个坏图 + 一句误导性的提示。触发条件是磁盘满、会话目录权限、spill 目录被清 —— 概率低，但**一旦命中就是静默错误**：模型可能对着半张残图直接下结论（比如照残图算一个点击坐标），而我们这边只留一行 `spill failed` 的 warn 日志。

**方案 A 顺带把这个分支也消掉** —— 豁免短路排在 `SpillToolOutput` 之前，带 `filePath` 的 image 块压根不走 spill，也就不存在「spill 失败」这件事。

## 三、现场实测（两项都成立，不矛盾）

dev 库 `~/.wishful-claw-dev/index.db`，消息 `wc-agent-1793359476027-uf70aq`（19:24）的 `meta` 反序列化后：

```
DesktopScreenshot 落库 output 全文 459 字符：
[{"type":"image","source":{"type":"base64","mediaType":"image/png",
  "filePath":"C:\\Users\\龚翼\\.wishful-claw-dev\\screenshots\\2026-10\\0d16d3a54dc4f9cc.png"}},
 {"type":"text","text":"Captured desktop screenshot 2520x1680 (origin 0,0, scale 1.5) … Saved to C:\\…\\0d16d3a54dc4f9cc.png."}]

image block: data.length = 0   filePath = 有值
整条 meta = 10,909 字节（原始工具输出 712,499 字节）
```

**落库侧完全正确**：S-283 落盘 + 文本行 `Saved to`、S-284 补 `filePath` + 剥 `data`，三项全部生效，剥掉 98.5%。

同一轮 agent 的实际行为也印证了「它看不到图、只能去盘上补看」：

```
1. DesktopScreenshot        （完成的 output 被砍成 32 KB）
2. thinking: "The screenshot was captu…"
3. Read  C:\…\0d16d3a54dc4f9cc.png  →  "Read image: … (2520x1680, image/png)"
```

`Read` 读图走 `toolContentBlocks`（S-145），**不吃截断**，所以第二次能看见。功能没断，代价是**每次截图多一次模型往返**，且第一轮它据一个坏块做判断。

## 四、方案（推荐 A）

### A. 按「输出里有没有 image 块」判，不按工具名判

在 `ApplyToolOutputLimit` 最前面加一条短路：输出里存在 `"type":"image"` 且该块带 `filePath` 时，**只截文本块、image 块原样放行**。

```csharp
// image 块是结构化载荷，截断它等于把图砍成半截（S-290）。
// 判据看内容不看工具名 —— 谁将来返回 image 块都自动豁免，不靠名单维护。
if (ContainsImageBlockWithPath(output))
    return ExemptImageBlocks(output);
```

判据选「带 `filePath`」而不是「含 `"type":"image"`」的理由：**只有带 `filePath` 的才保证「截掉也能从盘上取回」**。没有路径的 image 块（用户粘贴图、外部来源）一旦放行就是纯吃上下文，该截还得截。

**成本要认**：豁免后这 700 KB 真的进 wire，本轮不再省 —— 这正是 S-283 方案 A 原本设计的样子（`S-283.md:55`「本轮不省」）。真正省 wire 的那一刀是 S-275（压缩时把 image 块换成路径占位），不靠截断。

### B. 备选（不推荐）：把 `DesktopScreenshot` 加进工具名豁免名单

一行就能生效，但把「工具名清单」当契约维护 —— S-270 的教训（出口越少越好、别靠枚举）正相反。而且 `CaptureAppWindow`、以后任何返回图的工具都要记得补名单，漏一个就是静默降级。

### C. 备选（不推荐）：让截图工具改成返回 `toolContentBlocks`

架构上最干净（直接走 `:412` 的 `??` 左边），但要动 `ToolDispatchRouter` 的返回契约与代理层转发，改动面远超一条截断判据。**留作以后重构时的方向，本需求不做。**

## 五、边界与取舍

- **不修 `SpillToolOutput` 本身**：落盘对超大文本输出（`WebFetch` 整页）是对的，本需求只动 image 块。
- **不动 `TruncateToolOutput`**：`Read` 走它，`Read` 有 `toolContentBlocks` 兜着，两套逻辑各自成立。
- **不按 `mediaType` 白名单**：视频 / PDF 现在是当二进制截断的，本条只管 image 块，别顺手扩面。
- **`data` 为空的旧消息不受影响**：S-284 剥过的落库副本 `data.length = 0`，命中不了「含 image 块」判据 —— 判据只在**当轮工具输出**上跑，不碰历史。
- **与 S-286 的关系**：S-286（`8×5` 尺寸摘要）的根因也是「image 块排在字符串化输出的最前面」，本条豁免后模型能正常看图，但**摘要正则那条 bug 独立存在**，仍需 S-286 单独修。

## 六、真机验收（5 条）

1. 让 agent 截图：**第一轮就能看图**并描述内容，不再先 `Read` 一次盘上文件；
2. 同一轮日志里**不再出现** `tool=use_capability … originalBytes=… truncatedBytes=32768`；
3. 落库 `meta` 仍远小于原始输出（`data` 照旧被剥成空串，S-284 不回退）；
4. 反证：让 agent 读一个 > 32 KB 的纯文本网页（非图），**仍然被截断 / 落盘**，不因本条而放行；
5. **spill 失败分支**：手工把 spill 目录设成不可写（或临时改 `SpillStore.SaveText` 抛错），再截图 —— 这一轮仍要能正常看图，且日志里**不出现** `spill failed`。这条验的是「豁免排在 spill 之前」，不是验 spill 本身。
