## 三、根因：`minKeep = 2` 绕过了尾部预算

压缩把对话切成「折叠区 + 原样保留的尾部」，分界由 `TailStart` 算（`src/runtime/WishfulClaw.Agent/ContextCompression.cs:557-583`）：

```csharp
private static int TailStart(List<AgentRuntimeChatMessage> conversation, int head, int budgetTokens)
{
    var start = conversation.Count;
    var acc = 0;
    var minKeep = 2;                                   // ← 最后 2 条无条件保留

    for (var i = conversation.Count - 1; i > head; i--)
    {
        if (IsCompactionSummary(conversation[i]) && conversation.Count - i > minKeep)
            break;
        var tok = EstimateMessageTokens(conversation[i]);
        if (conversation.Count - i > minKeep && acc + tok > budgetTokens)
            break;                                     // ← 预算只在 minKeep 之外生效
        acc += tok;
        start = i;
    }
    …
}
```

预算是 `DefaultTailTokens = 16384`（`:65`）。**但 `minKeep` 那两条不参与预算判断**。

一次「Read 一张截图」恰好产生**两条**消息：`assistant(tool_use)` + `user(tool_result)` —— 正好占满 `minKeep = 2`。

`EstimateMessageTokens`（`ContextCompression.TokenEstimation.cs:26-33`）对 tool_result 取 `tr.Content.GetRawText()`，**base64 全额计入**；`EstimateTextTokens`（`:45-51`）返回 `Math.Max(len/4, len)` = 243496。单这一条就估 **24 万 token**，是尾部预算的 **15 倍**，被 `minKeep` 原样抬过去。

于是压缩循环变成：

```
压掉 head→start（几千 token 的历史）
→ 摘要 300~5000 字符
→ 24 万 token 的图原样留在尾部
→ 下一轮 inputTokens 仍 > 144000
→ 立刻再压
```

**图换一张，就再压一轮** —— 这正是那 9 次压缩的时间点与 6 张截图完全对应的原因。

## 四、为什么偏偏是这一波

| 因素 | 叠加后果 |
|---|---|
| S-272 真机验收要求 agent 反复 `DesktopScreenshot` / 读图 | 图片工具结果密集产生 |
| 图片以 base64 内联进 tool_result（不是文件路径引用） | 单条 23~42 万字符 |
| `minKeep = 2` 恰好等于「一对 tool_use + tool_result」 | 最新一对图永远折不掉 |
| `DefaultTailTokens = 16384` 对单条超预算消息无例外条款 | 预算形同虚设 |

## 五、附带发现：估算把图片放大约 100 倍

`EstimateTextTokens` 对 base64 字符串按**字符数**算 token（243496 字符 ⇒ 243496 token）。而主流多模态模型对一张 1680×1120 的图实际只收 ~1000~1600 token。

这条单独看是「宁可高估」的安全侧偏差（早压比晚压安全），**但它同时污染了两个判断**：
- `ShouldCompress` 会因为一张图就判定超阈值；
- 尾部预算 16384 的语义失真（一条图 = 15 倍预算）。

**不在本条修**，只在 §七 建议里记一笔，避免扩大改动面。

## 七、待确认（四条已全部收敛，2026-10-30）

1. **占位化的边界** —— 收敛：只处理「保留尾部里单条估算超预算的消息」的 tool result。折叠区不用管（它本来就被摘要替代），用户自己发的图不碰（见 §九）。
2. **占位文案带不带原始路径** —— 收敛：**不带**。路径就在同一条 tool result 的 text 块里（S-283 的 `Saved to …`、Read 工具的文件头），抄一遍等于把路径解析逻辑焊死在压缩层，哪个工具一改格式就失效。文案只负责指路：「路径见本条结果的文字说明」。
3. **占位后是否可再生** —— 收敛：可再生的，模型重新 `Read` 同一路径就会产生一条新的完整图。本迭代**不做去重**：连续重读同一张图会反复烧 token，但那是 agent 的判断问题，压缩层去重会把「它到底看没看过」这件事搞成猜谜。
4. **§五 的估算污染是否单开一条** —— 收敛：**不单开**。本条的判据是「单条估算超预算」，估算把图放大 100 倍只会让占位化**更早**触发——方向是安全的（宁可早占位，不可晚占位）。真要修就得按供应商实测校准 `ceil(w/28)×ceil(h/28)`，那是另一条线，且收益只在「少触发几次压缩」，不改死循环本身。

## 八、代价与取舍（实施后回填）

**这一刀换了什么**：用「压缩后模型看不见被占位的那张图」换「会话不再被一张图拖死」。

- **模型看不见图，是真的看不见。** 占位化后 wire 里没有 image 块，模型只能拿到一行文本。它想看图必须自己 `Read` 一次那个路径 —— S-283 保证了图在盘上，但那是一次额外的工具往返，不是免费的。
- **最新一条也会被占。** 没有给「刚截的图」开例外。理由：24 万字符的单条本身就超预算 15 倍，留它一个死循环照旧 —— 那等于没修。「刚截的图」在压缩那一刻通常已经用过一轮，压缩本就是「牺牲细节换连续性」的操作。
- **conversation 侧被持久化。** 压缩结果会写回会话快照，所以被占位的 base64 从 DB 里也没了（只剩占位文本）。这是故意的：图在盘上，DB 里留几十兆 base64 只会让会话加载越来越慢。
- **判定用估算，不用真实 token。** 估算对 base64 按字符算，一张 20 万字符的图估 20 万 token（真实约 1500）。方向是安全的（早占位），代价是**小图也会被占**：只要 base64 字符数超 16384 就会被摘。换算过来约 12 KB 以上的 PNG 都会触发 —— 实际截图基本都超。

## 九、刻意不做（实施后回填）

| 不做 | 为什么 |
|---|---|
| **不动 `minKeep = 2`** | 拆散 `tool_use`/`tool_result` 配对会被上游判 HTTP 400，S-246 / S-261 / S-262 那条线好不容易才把 400 压下去。 |
| **不占位化用户上传的图** | 用户发的图是意图本身，不是工具产物；频率低、条数少。真要处理属方案 C。 |
| **不动非 tool_result 里的 image 块** | 同上，那是用户消息的一部分。 |
| **不做压缩后的去重** | 见 §七 第 3 条。 |
| **不改估算公式** | 见 §七 第 4 条。 |
