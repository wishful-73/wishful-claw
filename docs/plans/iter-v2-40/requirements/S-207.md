### 2.1 「跟取消一样的处理方式」= 什么（08:45 已坐实，非取消语义）

**指交互形态，不是指 `channel-cancel-commands.ts` 的取消语义。** 两者共用同一句式：**用户在渠道里发一段文字，主进程侧用一个识别函数精确匹配后裁决。**

| | 取消 | 提权审批（本需求，复用 §1.4） |
|---|---|---|
| 触发 | 用户主动发文字 | 发渠道消息**请用户**回复 |
| 匹配 | `isChannelCancelCommand`（`channel-cancel-commands.ts:25-33`），词表 `取消 / 取消执行 / 停止 / 停止执行 / 终止 / 终止执行 / 中断 / 中断执行 / /cancel / /canel / /stop / /interrupt`（`:6-19`），**先 `stripLeadingAtMention` + 去空白 + 转小写再精确匹配**（`:28-32`，注释明写「故意精确，避免普通文本里的这些词被误判」） | `channel-shell-approval.ts` 的同意词 `['同意','批准','允许','是','yes','y','ok','1']` / 拒绝词 `['拒绝','取消','否','no','n','0']`（`:18-21`），同样精确匹配 |
| 裁决 | 主进程拦截，不启动新 run | 渲染端拦截，**消费该消息**、不启动新 run |
| 未命中的文字 | 照常当普通请求 | 照常当普通请求（**不得吞**） |

⇒ **本需求不碰 `channel-cancel-commands.ts`**，只是沿用同一套「渠道文字指令」体例。

**层级关系（老大 17:58 纠正）**：**不是「收窄 YOLO」，而是「沙箱套在 YOLO 外面」** —— YOLO 的"全放行"作用域本来就是沙箱之内，沙箱这一层**根本不问 YOLO**。本需求**不改 YOLO 的既有语义**。

### 3.3 完整链路

```
① agent 越界 ⇒ 工具直接拒（现状不变），错误文案里**指路**（08:48 已定：要加）
② agent 调 RequestSandboxElevation（**无参数**）
③ worker: reverse-request "sandbox/elevation-request"（带 channelSession 标记）→ 主进程 → 渲染端
④ 分流：
   ├─ 桌面会话 ⇒ 弹【独立提权弹窗】：固定文案「Agent 申请临时关闭沙箱 1 小时」
```

### 3.4 ★ 可见性：桌面 + 渠道都给，只排无人值守角色

**渠道走文字 ⇒ 渠道必须可见**（"渠道不可见"的旧判断已废）。

| 项 | 取值 | 说明 |
|---|---|---|
| `visibleScopes` | `["*:chat@*", "*:cowork@*", "*:channel@*"]` | = `HumanAttended`（`["*:chat@*", "*:cowork@*"]`，`ToolVisibilityScopes.cs:55`）**＋ `*:channel@*`** |
| `excludedScopes` | `ToolVisibilityScopes.UnattendedRoles` | = `["*:*@subagent", "*:*@goalsubagent", "*:*@automation"]`（`:65`）—— **只排这三个角色，不排渠道** |

**为什么不能照抄 `NoHumanToAnswer`**：它是 `[.. UnattendedRoles, "*:channel@*"]`（`:83`），**含渠道** ⇒ 会把渠道也排除掉，与老大 08:34 相反。

**为什么排除那三个角色**：子 agent 是委托执行、后台定时任务无人值守 —— 它们**没有可回话的人**，给了就会把那一轮挂死。

**声明位置**：`ToolVisibilityScopes.cs:7-8` 的注释写明「一个工具独有的组合写 inline，不进共享表」⇒ **inline 声明在 provider 上**，不动 `ToolVisibilityScopes.cs`。

### 3.5 ★ 渠道文字审批的复用方式（§五-6 **已定：(a)**）

`channel-shell-approval.ts` 的 `pendingBySession` 保证**每会话最多一个待审批**（`:97-104`）—— 这条保证**不能破**。两种做法：

- **(a) 复用同一模块**，把提示文案参数化（现在 `buildShellApprovalPrompt` 硬编码「Agent 请求执行命令（xxx）…」，`:69-75`）。**【定案】**
- (b) 另建一个并行模块。**已否决** —— 两套 `pendingBySession` 会**绕过"每会话单待审批"的保证**。

**定案 (a)**：提权也是"工具审批"的一种，复用同一模块。**模块不改名**（避免无谓 churn），仅在文件头补一句注释说明它已是通用工具审批、非仅 shell。

### 3.6 ★ 越界文案加「指路」（08:48 已定：加）

`PathBoundary.BuildViolationMessage`（`:252-260`）现在给出两条出路（关沙箱 / 加工作目录）。**不加指路 ⇒ agent 不知道有这工具可用，这条链就永远走不到。** ⇒ **在返回文本里加一句**：「或用 `RequestSandboxElevation` 申请临时关闭沙箱（需用户同意）」。

**只改文案字符串，不碰判定逻辑** —— 与 08:28「不插入原有边界」不冲突（那条边界是**逻辑**，文案不属于它）。

### 3.7 临时关闭的「1 小时」状态存哪

| 端 | 存法 | 理由 |
|---|---|---|
| **渲染端** | **新增非持久化的到期时间戳**（如 `sandboxWaivedUntil`），**不进 `partialize` 白名单** | `sandboxEnabled` 本身是**持久化字段**（`settings-store.ts:462-488`），直接改它会**写盘、重启残留** —— 与"临时"矛盾 |
| **worker 侧** | 同一轮内持有内存豁免标记（带同一到期时刻） | **必须双端可见**：已在跑的那一轮用的是**启动时透传**的 policy（`ToolCallProcessor.cs:180`「一批算一次」），渲染端中途改值**不会影响本轮** ⇒ "批准后 agent 立刻重试"必须在 worker 侧就地生效 |

**两个时钟不冲突**：审批**等待**期（渠道 10 分钟 / 主进程 30 分钟）与批准后的**豁免期 1 小时**是两个维度。

**透传口径**：9 个透传点改为读一个统一 helper（如 `effectiveSandboxEnabled()` = `settings.sandboxEnabled && now >= waivedUntil`），**一处收口**。

**顺带好处**：`SystemPromptCache.cs:74` 的缓存 key 含沙箱标记，沙箱提示词段由 `PromptBuilder.cs:61` 决定 —— 临时关闭后**提示词会自动重建**。

### 3.8 UI

- **桌面独立提权弹窗**（**不复用**现有审批弹窗）：**固定文案**「Agent 申请临时关闭沙箱 1 小时，是否同意？」+ 同意 / 拒绝。
- **渠道文字**：同一固定文案 + 回复「同意 / 拒绝」+ 超时说明（沿用 `buildShellApprovalPrompt` 体例）。
- **可见状态 + 手动恢复**：临时关闭期间要有**可见倒计时**且**能手动立即恢复**（安全相关可见性，不能省）。

> **已知取舍**：工具无参数 ⇒ 用户在弹窗/消息里**看不到 agent 具体想访问哪**，只能就「关不关沙箱」表态。这是 08:48 明确定下的形态（换来的是链路极简、路径不经过不可信文本）。
