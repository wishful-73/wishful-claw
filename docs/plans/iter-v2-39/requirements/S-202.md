## 一、现象

用户点**停止按钮**（或全局 PM 调 `stop_session_run`）中止一轮运行后，聊天窗渲染出一张**错误卡片**。用户是自己主动停的，不是出错。

## 二、根因

`src/runtime/WishfulClaw.Agent/AgentRuntimeTools.cs:287` 的取消分支：

```csharp
catch (OperationCanceledException) when (state.IsCancellationRequested)
{
    // ⇒ 按 aborted 收尾
}
```

这条 catch **只覆盖标准取消异常**。abort 传到 HTTP / SSE 层之后，provider 抛上来的不一定是 `OperationCanceledException` —— 可能是它自己包的类型（网络层取消、流读取中断等）。

其余类型于是掉进下面的 `catch (Exception)` ⇒ 走「出错」分支：

- 发 `error` 事件（渲染层 `chat-store/index.ts` 的 `case 'error'` 据此写下一张**错误卡片**）；
- 按 `reason=error` 收尾。

⇒ **用户主动取消，被当成出错。**

## 三、修法

补一条 `catch (Exception ex) when (state.IsCancellationRequested)`，按 `reason=aborted` 收尾，与标准取消异常走同一条路：

```csharp
catch (Exception ex) when (state.IsCancellationRequested)
{
    WorkerLog.Info(...);
    await EmitLoopEndAsync(state, context, "aborted");
}
```

**判据是 `state.IsCancellationRequested`（取消意图），不是异常类型** —— 只要这一轮确实是被取消的，不管抛上来的是什么，都该按取消收尾。

## 四、验收判据

1. 用户点**停止** ⇒ **不渲染错误卡片**，按中止收尾。
2. 全局 PM 调 `stop_session_run` ⇒ 同上。
3. **回归护栏**：真出错（`IsCancellationRequested == false`）**仍走原「出错」分支**，行为一字不变。
4. 门禁四绿：`npm run typecheck` 0 错 / `npm test` 不降 / `dotnet build src/runtime/WishfulClaw.sln` 0 警告 0 错误 / 官网 `npm run build` 0 错。

## 五、非目标

1. **不改取消的触发链路**（`cancelStream` / abort 的传播路径）。
2. **不改渲染层**的 `case 'error'` 分支 —— 它写错误卡片是**对的**，真出错就该写。

## 六、与 S-188 补修的关系（**别混为一谈**）

同一条复现报告（老大 14:54）里三处现象：

**但它是第 1 条的放大器**：出错路径比中止路径**多送一个收尾事件**（先 `error` 再 `loop_end(reason="error")`），队列被收尾补冻冻回去的概率更高 —— 修掉它，第 1 条的复发面也小一圈。
