# S-268 · `DesktopScreenshot` 的 `path` 参数完全无效 —— 描述含糊、行为缺失

> 归属：**下一迭代**（v3-iter-5）｜登记 2026-10-29 10:40
> **状态：待开工（本轮只登记，不实施）。**
> 来源：dev 实例第 6 轮审查（`.wishful-claw/notes/review-feedback-round6.md` §三 缺陷 B）。
> 与 **S-267** 同一类缺陷：**工具报告成功，实际没做成**。但那边是诊断缺失，这边是**参数没实现**。

## 一、现象

| 观察 | 结果 |
|---|---|
| 工具描述 | `Capture a full desktop screenshot and return it to the agent.` —— **没有承诺 `path`** |
| 对比 `CaptureAppWindow` 描述 | 明确写 `Pass path to write the PNG to disk; without it you receive the image but nothing is saved` |
| 实测：`DesktopScreenshot` 传 `path` | 全盘搜 `shot-desktop*` **零命中**，图只回到上下文，没落盘 |

## 二、代码佐证（已核）

| 位置 | 事实 |
|---|---|
| `AgentRuntimeDesktopExecutor.cs:98-100`（`ExecuteScreenshotAsync`） | `CreateJsonObject(_ => { })` —— **空请求体**，`input` 里除了 `delayMs` 一个字段都没读，`path` 从未出现 |
| `AgentRuntimeDesktopExecutor.cs:126-138`（`ExecuteAppWindowCaptureAsync`） | 认真解析 `path`：`GetString(input, "path")` → 相对路径按 `workingFolder` 拼绝对 → 写进 `targetPath`，还留了注释说明为什么必须在 worker 侧解析（主进程 cwd 是程序目录） |

⇒ **两个工具的调用姿势长得一样，行为差一半。**

## 三、为什么这是缺陷而不是「功能没做」

模型不会先读描述再决定传不传 —— 它看到 `CaptureAppWindow` 这么用能成，自然照搬到 `DesktopScreenshot`。然后：

> 传了 `path` ⇒ 工具报成功 ⇒ 模型以为存了 ⇒ 下一轮去 Read 那个文件 ⇒ 文件不存在。

比直接报错更糟：**报错模型会换招，假成功让它继续往下走**。

## 四、两个选项（实施时二选一）

**A. 补上 `path` 支持**（倾向）
照 `ExecuteAppWindowCaptureAsync` 的形状抄：worker 侧解析 → 写进 `targetPath` → 主进程落盘。附带把描述改成与 `CaptureAppWindow` 对齐。

**B. 描述里明写「不支持落盘」**
成本近乎零，但模型仍会在需要落盘时无处可去 —— 而「截图存下来」是高频需求（做文档、做对比图）。

⇒ **建议 A**。理由：`CaptureAppWindow` 那套已经写好且带注释说明坑在哪，抄一遍成本很低；而 B 只是把「做不到」说出来，没解决需求。

## 五、待查（开工前）

- `src/main/ipc/desktop-control.ts:122` `captureDesktopScreenshot()` 是否已经支持接收 targetPath（`window:capture-self` 那条是支持的，桌面截图那条未必）。
- `DesktopScreenshotResult`（`desktop-control.ts:16`）有没有 `filePath` 字段。
- 落盘路径要不要过沙箱审批（`CaptureAppWindow` 有没有过）。

## 六、判据（验收，留给实施时钉）

1. 传 `path` ⇒ 文件真的存在，且内容与返回的图一致。
2. 不传 `path` ⇒ 行为与修复前一致（只回图，不落盘）。
3. 描述与 `CaptureAppWindow` 口径对齐。
4. 相对路径按会话 `workingFolder` 解析，不是主进程 cwd。

## 七、不做的事

- 不顺手改 `CaptureAppWindow` —— 它是对的。
- 不与 S-267 合并 —— 那条已在本迭代交付（渲染端截图诊断），本条在 worker + 主进程，改动面零交集。
