### 5.2 为什么是五个方法，不是一个方法加开关

`:89`（沙箱根集合）与 `:98`（建项目查重）的 SQL 只差一个 `AND (ssh_connection_id IS NULL OR ssh_connection_id = '')`。**看着该合并，实则相反**：

| 场景 | 要 ssh 过滤吗 | 滤掉的后果 |
|---|---|---|
| 沙箱根集合 | **要** | SSH 项目的工作目录是**远端路径**，塞进本地沙箱根毫无意义；更糟的是它可能与某个本地路径同形，把保护扩到不该到的地方 |
| 建项目查重 | **不要** | 查重问的是「这个目录已被哪个项目占了」，远端项目同样占着；滤掉就会重复建 |

两个方法的名字都点到「给谁用」（`ListSandboxRoots` / `ListForWorkingFolderDedup`），并且注释里互相指向对方，避免下一个人看到「两段一样的 SQL」就合并。

### 5.3 沙箱那两处的注释搬进了 Store，catch 留在调用点

`PathBoundary.cs` 原来的两段注释里记着两次事故：`:80-82` 的「父目录只加在全局分支 —— 项目会话拿到它等于能读写兄弟项目」（S-103），`:107-110` 的「`workingFolder` 漏传一处的后果不是少一层保护，而是**整个项目目录变成越界**」（S-144）。

这两段**整段搬进了 `DbProjectStore` 的方法注释**，不是留在调用点。理由：注释描述的是「这个查询为什么必须这样写」，而查询现在住在 Store 里；留在调用点就成了隔着一层楼的批注，读的人不知道它在说谁。

**`try/catch` 相反，留在调用点**（`PathBoundary.cs` 两处各一个，行为一字未改：Warn + 返回空集合 / null）。§二 那条要求是硬的 —— catch 抽进 Db 层，降级语义就变成「Db 层吞异常」，调用方再也看不到失败。

### 5.4 `ListAll` 保留了二选一

没改成 `WHERE (@filter IS NULL OR name LIKE @filter)`。§二 已经写死：那是语义之外的性能变更（SQLite 会放弃索引）。方法内部 `if (string.IsNullOrEmpty(nameFilter))` 两条分支，各自一条完整 SQL。

### 5.5 订正 §一 的「5 处」

§一 标题写「5 处」，表里列了 **6 行** —— 不是矛盾，是两种数法：

- **调用点数 = 5**：`:75/:76` 是同一次调用的两条候选 SQL，算一处
- **SQL 字面量数 = 6**：两条候选各算一条

本单以**调用点**为准判「归零」，5 个方法对上 5 个调用点，一一对应，没有遗漏。
