## 一、现象

聊天窗（外层滚动区）/ 思考块（内层 `max-h-80`）在流式输出与**组件收起 / 折叠 / 高度回收**时**视口上下跳**，其中最难受的是**回跳** —— `scrollTop` 反向（变小）移动。

老大已记的容忍边界（iter-30）：**单向往下贴底可接受，双向来回不行**。

---

## 二、历史定位（已定稿，勿重复推翻）

### 1. 真凶之一 = 全局 `* { scroll-behavior: smooth }`

`src/renderer/src/assets/main.css:323-325`。`scroll-behavior` 是**继承属性**且命中每个元素 ⇒ 任何 `el.scrollTop = x`（及不带 behavior 的 `scrollTo`）都从「瞬时跳变」变成「几百 ms 缓动动画」⇒ 每次赋值打断上一个动画 ⇒ 持续蠕动/抖动。

**修法（老大拍板「不动全局」）**：只给需要程序化跟随的滚动容器加 **inline** `scrollBehavior: 'auto'` —— `ThinkingBlock.tsx`（内层）、`MessageList/VirtualListContent.tsx`（外层）。**必须 inline**，因为 `*` 那条规则没包 `@layer`，优先级高于 Tailwind 的 `scroll-auto`。

### 2. 回跳主因 = 水位线收回那一帧的时序错位

`src/renderer/src/components/chat/MessageList/useMessageListScroll.ts:570-590`：

1. `isSessionOutputting` 翻 false ⇒ `contentHeightWatermarkRef.current = 0`（ref 立即清零）+ `setMinContentHeight(0)`（DOM 要等 re-render）；
2. 紧接着的 `scrollToBottomImmediate()` 因 ref 已清零，判定为「非水位线」分支 ⇒ `bottom = scrollHeight - clientHeight`，此刻 DOM 的 `min-height` **尚未撤掉** ⇒ `scrollHeight` 仍是含水位线的大值 ⇒ scrollTop 被强推到底（**向下跳**）；
3. 下一帧 `min-height` 真正撤掉 ⇒ `scrollHeight` 变小 ⇒ 浏览器 **clamp** scrollTop ⇒ **向上弹回**。

⇒ 一推一弹 = 回跳。恰好发生在「留白被收掉」的同一瞬间。

### 3. 次因 = 悬空救援分支主动回缩

同文件 `:164-168`：`scrollTop > realBottom + 1` 时**无条件** `scrollTop = target`；而 `getRealContentBottom()` 只遍历已渲染的虚拟行，虚拟器未渲染 / 卸载行时 `realBottom` 偏小 ⇒ 回缩到更小的 scrollTop ⇒ 回跳。

### 4. iter-29 T-8 的写法教训

`if (maxTop - scrollTop >= THINKING_SCROLL_BUFFER_PX) scrollTop = maxTop` 是「**攒够再跳**」的台阶化实现，与「恒定预留 + 连续跟随」方向相反。iter-30 已裁定：该写法**耗缓冲**，与设计意图完全反向。

## 三、定死的约束（动这块之前先重读）

1. **`scrollTop` 保持单调不减**（除用户手动滚动）。
2. **内容是自变量、滚动是因变量** —— 不为了让缓冲好看而给流式内容限速（老大明确否掉「不能让内容去适应缓冲」）。
3. **水位线只增不减** —— 收回 `min-height` 本身就制造 `scrollHeight` 骤减 ⇒ 必然 clamp；节流只是把位移合并成**一次更大的跳**。

## 七、实施（2026-09-24）

**裁定（老大 14:13）**：「高度回收，回收了不能立即又回收啊，需要有点延迟，或者说给冲突锁」⇒ 采「**回收方向专属的冷却窗口**」。不动全局 `scroll-behavior`（S-31 已定「不动全局」），不给水位线加节流（§三.3 已否）。

### 7.1 勘测落点

回跳发生在我方**主动书写 `scrollTop`** 的三处，都集中在 `useMessageListScroll.ts` 的 `scrollToBottomImmediate()`：

| 落点 | 行为 | 为什么会连着来 |
|---|---|---|
| 悬空救援分支（`scrollTop > realBottom + 1`） | 无条件 `scrollTop = followTarget` | 收缩使视口内零内容时会连续触发 |
| 余量双向跟随的**收回**方向（`remaining > gapCeiling`） | 把 scrollTop 往小拉回 `followTarget` | 折叠动画 200ms 内 ResizeObserver 每帧回报 ⇒ 每帧收一次 |
| 水位线撤销（`isSessionOutputting` 翻 false） | 先对齐真底，再 `applyMinHeight(0)` | 撤销帧紧随其后还有一次跟随回收 |

每一次单独看都是单向、一次到位的（iter-30 S-32 的成果）。疼的是**同一瞬间连着收几次** —— 三次的位移串起来就是上下拉锯。

### 7.2 修法

抽纯函数模块 `src/renderer/src/components/chat/MessageList/scroll-collapse-gate.ts`（零依赖 ⇒ renderer 与回归套件跑同一份代码，同 S-146 抽 `updater-error-format` 的做法）：

- `CollapseGate` 只存 `lastCollapseAt`（负无穷 = 从未回收）；
- `isCollapseCoolingDown(gate, now, config)` 判窗口，默认 **240ms**（比折叠动画 200ms 略长：整串收缩落在窗口内，窗口结束时几何已稳定，补一次就到目标）；
- `admitCollapse(gate, now)` 记账，入参不可变、同刻复用同一状态；
- 时钟异常（回拨 / `NaN`）一律按「不冷却」处理 —— 宁可多收一次，不能把视口永久锁死。

接入 `useMessageListScroll.ts` 四处：

1. **回收方向加锁** —— `remaining > gapCeiling` 且冷却中 ⇒ 直接跳过本次收回；窗口过了按**当时的**几何重判，**不补做**窗口里被压掉的那几次（补做 = 位移总量不变、只切成几刀落，照样看得出上下动）；
2. **唯一出口记账** —— 只在 `bottom < scrollTop`（回收方向）时 `admitCollapse`；向大（贴底 / 补提前量）**永远放行**，内容长出去不跟才是真问题；
3. **悬空救援不受锁阻挡**，但救完立刻记账 —— 挡了就是让用户盯着空白屏；
4. **切会话重置冷却锁** —— 上个会话的时间戳不能压住新会话的第一屏跟随。

### 7.3 边界（如实说）

本修法只治**我方主动书写 `scrollTop`** 造成的回收抖动。浏览器因 `scrollHeight` 骤减而**自行 clamp** 的位移不在此列 —— 那条链路由 §三.3「水位线只增不减」挡着。真机若仍见回跳，按「clamp 未被水位线挡住」这一方向另查。
