## 一、根因（已定位到字节）

文件 **不是整份乱码**，是**前半 UTF-8、后半 GBK 混在一份文件里**：

| 区间 | 字节数 | 编码 | 状态 |
|---|---|---|---|
| `0 ~ 18725` | 18,725 | 合法 UTF-8 | 中文正常 |
| `18725 ~ 22654` | 3,929 | **GBK（CP936）** | 当 UTF-8 读就成一堆 `????` |

判据：
- `New-Object Text.UTF8Encoding($false,$true).GetString($bytes)` → 抛在**索引 18725**，字节 `BD`
- 取 `[18725..]` 用 `Encoding.GetEncoding(936)` 解码 → **0 个 U+FFFD**，中文全对：

```
   阶段五处置记录（2026-10-26，实施方回填）

**处置后：? 0 / ?? 0（必修与建议修全部收口，??9 部分处理并说明）/ ?? 已记录**

### ? 必修
```

版本历史只有一个 commit（`fb7b5beb`，S-224），**入库那一刻就是混的**，不是后续编辑弄坏的。

## 二、能恢复到什么程度

- **中文：无损**。GBK 那 3,929 字节重新解码后一字不差
- **emoji：已永久丢失**。GBK 编码表里没有 emoji，当初那次错误转换把它们降级成了 `?`
  - 例：`**处置后：? 0 / ?? 0` 里的 `?` 原本大概率是 ✅ / ⚠️ 一类
  - 能从上下文推断的补回去；推断不出的**保持 `?` 不猜**，别编内容

## 三、修法

$p = 'docs\plans\iter-v3-1\plan-s224\review_report.md'
$b = [IO.File]::ReadAllBytes($p)

## 五、普查中纠正的一处误报（记住这个坑）

第一次扫的时候用 `Get-ChildItem | Select-String -Pattern '锟斤拷|\uFFFD…'`，输出显示「1020 处」整片 `????`，我一度判断「整文件乱码、不可恢复」。

**错在两处：**

1. `Select-String` 读文件用的是**默认编码**（PS 5.1 下不是 UTF-8），所以正常中文段也变 `????` —— 那是**显示层假象**，不是文件坏了

**以后查编码问题一律用字节级判据**（`UTF8Encoding($false,$true)` 严格解码），不要用 `Select-String` / `Get-Content` 的肉眼输出下结论。这条值得进 `AGENTS.md` 的排查规范。

## 六、实施记录（2026-11-06 10:3x）

### 6.1 切分点：单据里的 `18725` 是错的，实际是 `18726`

按 §三 那条 ⚠️「改文件前重新跑一遍确认」的要求逐字节复核，结果：

```
索引 18723 = 0x23  '#'
索引 18724 = 0x23  '#'
索引 18725 = 0x20  ' '     ← 合法 ASCII 空格
索引 18726 = 0xBD          ← GBK 首字节（BD D7 = 「决」）
索引 18727 = 0xD7
```

逐 k 测 `head = b[0..(k-1)]` 的严格 UTF-8 合法性：`k=18726` 合法、`k=18727` 起全部非法 ⇒ **真正的切分点是 18726**（`head` 取 `0~18725` 共 18,726 字节，末尾那个 `## ` 的半截标题头归 head）。

**为什么单据写成了 18725**：.NET 抛的异常原文是「无法将位于索引 18725 处的字节 [BD] 由指定的代码页转换为 Unicode」—— 报的是 **UTF-16 码元位置**，跟**字节索引**差了偏移。GBK 段之前若混过多字节汉字，两个口径就对不上。**不要拿异常消息里的数字当字节偏移用**，必须前缀法实测。

### 6.2 落地

```powershell
$head = [Text.Encoding]::UTF8.GetString([byte[]]$b[0..18725])          # 18,726 B 原样
$tail = [Text.Encoding]::GetEncoding(936).GetString([byte[]]$b[18726..]) # 3,928 B 按 GBK 解
$text = $head + $tail
$text = ($text -replace "`r`n","`n") -replace "`n","`r`n"               # 统一 CRLF
[IO.File]::WriteAllText($p, $text, (New-Object Text.UTF8Encoding($false)))
```

`22,654 B → 23,417 B`（+763 B 是中文从 GBK 双字节变 UTF-8 三字节，正常），**204 行**。

### 6.3 emoji 一个都没补 —— 这是我的主动取舍

GBK 编码表里没有 emoji，当初那次错误转换把它们downcast 成了 `?`。恢复出来长这样：

```
**处置后：? 0 / ?? 0（必修与建议修全部收口，??9 部分处理并说明）/ ?? 已记录**
### ? 必修
### ?? 建议修
### ?? 观察
```

从结构上**能猜**：`### ? 必修` 大概率是 `### ✅ 必修`、`### ?? 建议修` 大概率是 `### ⚠️ 建议修`（`⚠️` = U+26A0 + U+FE0F 两个 BMP 字符 → 恰好两个 `?`）。

**但一个都没补**。理由：

1. 这是 **2026-10-26 的历史迭代报告**，改内容就是篡改记录
2. 猜对的收益（好看）**远小于**猜错的风险（后人以为原文如此）
3. §二 自己写的规矩：「推断不出的**保持 `?` 不猜**，别编内容」—— `✅`/`⚠️` 属于「看起来很像」但不是「推得出来」

**结论：`?` 原样保留**。要还原 emoji 只能回 `fb7b5beb` 之前的源头，那份不存在。
