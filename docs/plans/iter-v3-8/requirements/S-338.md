## 二、必须先看懂的三个细节

### 2.1 边界用 `created_at`，**不能用** `through_created_at` / `through_sort_order`

`:224-231` 原文：

> The snapshot row's own `created_at` is a wall clock written once and never rewritten, so ordinary message saves can never move the boundary. **Do not compare against `through_created_at`/`through_sort_order`**: `sort_order` is the renderer's transcript index (`messages.indexOf`) and shifts when compression inserts the boundary+summary pair mid-transcript, which used to raise a false `invalid_cursor` and block the session permanently. `sort_order` stays a **pure tie-break inside ORDER BY**.

⇒ 抽方法时参数只收 `snapshotCreatedAt`（long）。**签名里不要出现 `throughSortOrder`** —— 一旦出现，下一个人就会拿它做过滤条件，回到那个「会话永久卡死」的 bug。

### 2.2 `sort_order` 只是 `ORDER BY` 的第二排序键

两处都是 `ORDER BY created_at ASC, sort_order ASC`。**不能简化成 `ORDER BY created_at`**（同一毫秒写入的多条会乱序，正文和工具结果会错位），也**不能提到 WHERE 里**。

### 2.3 `AttachPartsToEntities` 必须在过滤之前调

`:239-240`：「S-285：块结构在 parts 表里，必须在过滤/合成之前合并回 meta」。`:267-268` 同样一句。**这个方法调用留在 Agent 层、跟在查询后面** —— 它不是 messages 表的查询（它查 parts），别顺手一起搬。

## 三、风险

| 风险 | 处置 |
|---|---|
| `SELECT *` + `EntityMappers.MapMessage` | 显式列全字段。`messages` 是全库列最多的表，`SELECT *` 加列就会静默错位 —— 这一处全族最该改 |

| `AttachPartsToEntities` 顺序 | 见 §2.3。**调用点顺序不动** |
| 这个文件在会话恢复热路径上 | 搬完真机跑：一次压缩过的会话（走增量）、一次新建会话的首次加载（走全量）、一次压缩边界正好落在中间的会话（历史上会报 `invalid_cursor` 的那种） |
| `messages` 表数据量最大 | 两处都是 `session_id` 过滤，务必确认 `session_id` 有索引（S-328 §四「不顺便改索引」⇒ 只**核对**，不改） |

## 六、实施记录（2026-11-06，刀 28 —— 本族最后一刀代码）

### 6.1 落地形状：没新建文件，加进 `DbMessageTools.cs`

`messages` 和 S-334 的 `goal_*` 一样是「线接了一半」的地方 —— `DbMessageTools.cs`（180 行）里早就有一批收 `DbService db` 首参的表访问方法：

```
internal static void InsertMessage(DbService db, MessageEntity message)
internal static List<MessageRow> ToRowsWithParts(DbService db, List<MessageEntity> entities)
internal static void IncrementMessageCount(DbService db, string sessionId, int delta)
```

形状正是 S-335 立的样板。所以按「先看现有同类方法所在文件」的原则，`ListForRestore` **加进了同一个文件**（180 → 233 行），没有另开 `DbMessageStore.cs`。

这和刀 23~27 新建四个 `Db*Store.cs` 不矛盾：那四张表原本没有任何表访问方法（或只有端点），`messages` 有。

### 6.2 签名里刻意没有 `through_sort_order`

```csharp
public static List<MessageEntity> ListForRestore(DbService db, string sessionId, long? afterCreatedAt)
```

`afterCreatedAt` 为 null ⇒ 全量分支；有值 ⇒ 增量分支。**`long?` 这一个参数就是全部区分**，没有第三个"游标"参数。

§2.1 那条要求写进了方法注释，并把「为什么」也写全：快照行的 `created_at` 是一次写入、永不改写的壁钟时间；`sort_order` 是渲染端 transcript 下标，压缩插入 boundary+summary 对时会整体平移，拿它做过滤历史上报过假的 `invalid_cursor`、把会话永久卡死。注释里明写「签名里也刻意不接受它：一旦出现这个参数，下一个人就会拿它做过滤条件，回到那个 bug」——把**防御理由**而不只是结论留给下一个人。

### 6.3 显式列（9 个字段）

与刀 26/27 的判断一致：`messages` 是最热、最大的表，加列时静默错位代价最高，所以显式列 `id, session_id, role, content, meta, created_at, updated_at, usage, sort_order`，不用 `SELECT *`。

这和 `DbSessionStore.ListRecentByProject` 用 `SELECT *` 的差别还是**列数**：`messages` 9 列可控，`sessions` 29 列写显式反而制造同步负担。

### 6.4 两处 SQL 合成一个方法，但 `ORDER BY` 一个字没动

两条查询只差 `AND created_at > @snapshotCreatedAt`，合成一个方法里两个分支。`ORDER BY created_at ASC, sort_order ASC` **两个分支都完整保留** —— §2.2 那条：省掉第二段，同一毫秒写入的多条会乱序，正文和工具结果错位；也不能提到 WHERE 里。

### 6.5 `AttachPartsToEntities` 调用顺序没动

`S-285` 那句「块结构在 parts 表里，必须在过滤/合成之前合并回 meta」留在原地，两处调用点的相对位置一字未改 —— 它查的是 `message_parts`，不是 `messages`，不属于本单范围，只是紧挨着。
