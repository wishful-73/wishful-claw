## 5. 假说（按 §4.2 判据重排，**取证前不动代码**）

### H1（当前最强）：补位定时器链自激 / 阈值边界振荡 —— 「执行期唯一会自己排程的东西」

`useMessageListScroll.ts` 里执行期会**自己排下一次调用**的只有两条链，都是 S-176 加的：

| # | 位置 | 排程条件 | 周期 |
|---|---|---|---|
| ① | `scheduleShrinkProbe`（`:201-209`）→ `shrinkProbeDelay`（`scroll-watermark.ts:188-197`） | `tracker.lowSince !== null` 且未满 `refloorHoldMs(48ms)` | ≈48ms |
| ② | `scheduleReclaimRetry`（`:213-225`）→ `collapseRetryDelay`（`:207-216`） | 回收被冷却锁压掉且冷却未满 `cooldownMs(240ms)` | ≈240ms |

两条 timer 到点都回调 `scrollToBottomImmediate`，而它 `:250` **无条件**调 `scheduleShrinkProbe()` ⇒ 存在闭环回路。

**为什么会自己转起来**（关键在 `shrinkEpsilon = 24` 这个阈值边界）：

- `observeFloor` 的回落分支（`scroll-watermark.ts:115`）：`floor - raw < 24` ⇒ `lowSince` **清空**，不排程；
- 一旦实测底比下界低 **≥24px** ⇒ 记 `lowSince`，`shrinkProbeDelay` 返回 48ms ⇒ 排一次；
- ⇒ 实测底在 `floor - 24px` 上下**来回跨线**时，链就会「排一次 → 到点判为不够格/够格 → 再排一次」地空转，每次 timer 都可能写一次 `scrollTop`（`:316` 差值 >1px 才写）。

**为什么「等模型响应、无输出」时也转**：平时靠 bottom-anchor effect 喂帧；没有新内容时没人喂帧，只剩这两条 timer 在转 —— 正好对上老大描述的 ②。

**为什么「执行中抖动」比平时明显**：`getRealContentBottom()`（`:150-192`）在虚拟列表里逐行 `getBoundingClientRect()`，行集合逐帧变化时实测底会骤降一整行（`:235-237` 注释自己写着这点）⇒ 低/高交替的原料充足。

**坐实方式**：在 `:205`、`:221` 两个 timer 回调与 `:265`/`:292`/`:324` 三处写 `scrollTop` 处打时间戳序列（`performance.now()` + 调用点编号 + 写入值），抖动期间导出。**若 ② 场景下序列里仍持续出现 ①/② 的周期性记录，H1 坐实。**

### H2（次强）：`realBottom` 与 `clientHeight` 抖动导致 `remaining` 反复跨 `REFILL_AT`

`:308` 带内直接 return、带外写 `bottom = followTarget` ⇒ 余量在 `STREAMING_BOTTOM_FOLLOW_REFILL_AT(24px)` 上下振荡时同样会周期性写 `scrollTop`。与 H1 是同一条链上的两个触发点，取证一次能同时覆盖。

## 8. 静态复查（2026-10-27 16:44，老大「你再找找呢，看下能找到原因不」）

**结论先说**：静态能定位到**三条都成立的机制缺陷**，且能串成一条完整故事；但「哪一个是今天那次的真凶」静态定不了，缺一个驱动源的判据（见 §8.5）。

### 8.1 缺口 A：S-176 的防噪前提与实际噪声形态不符（**可证的设计错误**）

`scroll-watermark.ts:40-41` 的推理原文：

> 取值 48ms ≈ 3 帧 @60fps：噪声是「一帧往返」（≈16ms），48ms 要连续 3 帧偏低才可能误认，而一帧往返的噪声根本不会连续 3 帧偏低。

但噪声的真实形态不是「一帧往返」。`useMessageListScroll.ts:145-146` 这句注释自己写着：

> 虚拟化下 getRealContentBottom 的挂载行集合是动态的，**尾行在可见范围边界进出会让内容底骤降回升，跟随目标于是每帧变、每帧写 scrollTop —— 自激噪声**，取历史最大值即可滤掉。

而 `getRealContentBottom()`（`:182-192`）确实**只遍历 `virtualContentRef.current.children`** —— 只统计**已挂载**的行：

```ts
for (const child of content.children) {
  const childBottom = (child as HTMLElement).getBoundingClientRect().bottom - contentTop
  if (childBottom > bottom) bottom = childBottom
}
```

⇒ **挂载缺失造成的「偏低」不是一帧往返，而是持续到滚动位置改变为止。** 48ms 的时长阈值在设计上就挡不住它，因为偏低会一直持续。

⇒ 这是 S-176 与 S-150 的分界所在：S-150 用「只增不减」**无条件**滤掉这类骤降；S-176 为了承认「真收缩」，把下降放开了，用的却是一个**错误前提**。等于把 S-150 的防护拆了，换上来的锁对真实噪声无效。

### 8.2 缺口 B：悬空救援**无条件**写、且**在冷却锁外**（能产生几百 px 的跳）

`useMessageListScroll.ts:259-266`：

```ts
if (ref.scrollTop > realBottom + 1) {
  // 整屏悬空（收缩使视口内零内容）：无条件救回跟随姿态，一次到位。
  // S-150：救援**不受冷却锁阻挡**…
  collapseGateRef.current = admitCollapse(collapseGateRef.current, now)
  markProgrammaticScroll()
  ref.scrollTop = followTarget      // ← 一次到位，无条件
  return
}
```

`realBottom` 来自 `streamingBottomTrackerRef.current.floor`，也就是 §8.1 里那个**可能被错误压低**的下界。

⇒ 一旦 floor 被压低（A 成立一次），**下一次任何调用**都会判定「悬空」，把视口从底部一次拽到 `realBottom + gapTarget − clientHeight`。以 `gapTarget = 240` 计，这是**几百像素级的位移**，不是 1~2px 的颤。下一帧 floor 抬回真值 ⇒ 又贴底 ⇒ 一上一下。

⇒ 这条同时解释了「幅度明显」和「冷却锁完全无效」：救援本来就在锁外（`:261` 注释自陈）。

### 8.3 缺口 C：`ResizeObserver` 自触（把一个改动放大成一串调用）

`:813-823`：

```ts
const observer = new ResizeObserver(() => {
  if (canAutoScrollRef.current() && !isLoadingOlderMessagesRef.current) scrollToBottomImmediate()
})
observer.observe(viewport)
observer.observe(content)      // ← 就是 virtualContentRef
```

而 `applyMinHeight`（`:137`）改的**正是 `content` 的 `min-height`**，写在两处：`:295`（回收分支）、`:767`（抬水位线）。

⇒ 抬一次水位线 ⇒ `content` 尺寸变 ⇒ `ResizeObserver` 回调 ⇒ `scrollToBottomImmediate()` ⇒ 再判一次。水位线只增不减所以会收敛，但**每一次改动都被放大成一串调用**，每一串都要过一次 §8.1 / §8.2 的判定。

### 8.4 三条怎么串起来

**C 提供调用频率 → A 产生错误的 floor → B 把错误放大成几百像素的位移。**

单看任何一条都不足以解释症状，合起来才对得上老大报的三件事：
- 与内容是否在长无关（B 只看 floor，不看增长）⇒ 解释了「② 完全没有输出、等响应时也抖」
- 与回收无关（B 在冷却锁外）⇒ 解释了「当时并没有组件正在回收高度」
- 执行中更明显（`virtualListTotalSize` 每帧变 ⇒ bottom-anchor effect 每帧跑 ⇒ C/A/B 每帧过一次）⇒ 解释了「执行中抖」

### 8.5 静态定不了的那一环：驱动源

情形 ②（静置、无输出）要抖，必须**有人周期性调用**。静态查下来，静置时能自己跑的只有三处，且都有自停条件：

| 源 | 自停条件 | 行 |
|---|---|---|
| `scheduleShrinkProbe`（48ms 链） | `tracker.lowSince === null` ⇒ 不排 | `:201-209` |
| `scheduleReclaimRetry`（240ms 链） | 冷却到期 ⇒ `null` ⇒ 不排 | `:213-225` |
| `ResizeObserver` | 只在尺寸真变时触发 | `:817` |

⇒ 静置时若 `floor` 已收敛（`raw` 恒定 ⇒ `floor - raw < 24` ⇒ `lowSince` 清空），三条链**都会停**。

**所以情形 ② 存在一个我还没找到的驱动源。** 目前最可能的候选：**运行中耗时走表**（iter-39 S-197 的 `resolveRunningElapsedLabel`，每秒 tick）导致 MessageList 父级 re-render ⇒ `virtualListTotalSize` 重算 ⇒ 若值与上一帧差 1px 以上，bottom-anchor effect（`:731`，依赖 `virtualListTotalSize`）就重跑一次 ⇒ 过一次 A/B/C。

### 8.6 现在最值钱的一个判据（问老大一句就能收窄一半）

**抖动的频率，是不是跟输入框上方那个耗时秒数的跳动同步（约 1 秒一次）？**

- **是** ⇒ 驱动源锁定走表 tick，8.5 的候选成立，A+B 是放大器。修法就落在「floor 不许被挂载缺失压低」这一条上，走表那条只需断掉它对 totalSize 的间接影响。
- **不是**（连续颤 / 随机顿）⇒ 驱动源另有其人，必须上埋点。

### 9.3 实际改动：只落一处，且常规路径零影响

**改动点**：`scroll-watermark.ts` 新增 `observeGrowthOnly(tracker, raw)` —— **只升不降**的观测；`useMessageListScroll.ts` 在喂 floor 的两处（`scrollToBottomImmediate`、bottom-anchor effect）先判「尾部行是否挂载」，未挂载就改喂 `observeGrowthOnly`。

**判据**：`measureContentBottom()` 一次遍历同时返回 `{ bottom, tailMounted }`，`tailMounted` = 是否存在 `data-index === virtualRowCount - 1` 的行元素（`VirtualListContent.tsx:164` 每行都带 `data-index`）。

**为什么这条对常规路径零影响**：
- 贴底时视图底边停在内容底**下方** `gapTarget`（`resolveGapTarget`），最后一行必然在视口内 ⇒ 必然挂载 ⇒ `tailMounted = true` ⇒ 走原来的 `observeFloor`，行为**逐字节不变**。
- 只有「尾部跑出 overscan」这种盲区帧才走新分支。这恰恰是原先唯一会被误采信的帧。

**为什么盲区帧必须清 `lowSince`**：不清的话，盲区之前记的起点会残留，等下一次**可信**观测时 `shouldRefloor` 立刻判「已经等够了」而误采信 —— 等于绕过了整个防抖。所以 `observeGrowthOnly` 偏低时返回 `{ floor: 不动, lowSince: null }`。

**它修掉的是环的燃料**：盲区偏低不再压 `floor` ⇒ `:274` 的 `scrollTop > realBottom + 1` 不会被误判成「整屏悬空」⇒ 那条**无条件、几百像素、且在冷却锁外**的救援（`:280`）不会凭空触发 ⇒ 「拽走 → 滚回 → 重新挂载 → floor 抬回 → 再拽」的自持环断在第一步。

### 9.4 诚实结论

- 这条改动**本身**修的是一个确定存在的缺陷（盲区帧被当成真收缩），不是猜测。
- 但它**不保证**就是老大 17:17 说的那次偶发的真凶 —— 那一关仍然缺实证，而取证路线已被否。真机若再复发，判定口径是：观察**抖幅**。个位数 px 颤说明还走的是 `observeFloor` 那条（盲区不是主因）；上百 px 弹说明还有别的路径在写 `scrollTop`。
- 未动 `:259` 救援分支本身。它「无条件 + 锁外」的性质还在，只是现在少了一个误触发源。若复发且证实是救援所致，再单独立项收紧。
