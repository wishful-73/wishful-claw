# S-279 · 普通消息（`send_session_message`）发出去就没法回 —— 需要轻量回执

> 归属：**v3-iter-5**。登记 2026-10-30 08:19（老大一次给三条，本条是第 2 条）。
> 状态：**✅ 已交付（v3-iter-5 刀 9，2026-10-31 00:10）**，走 **C 方案**。实施记录见 §八。
> 老大原话：「全局会话发送的常规消息也要有可以回复的方式，因为现在是渲染成卡片了，所以可以携带一些参数过去，项目下会话回复的时候只需要拿到卡片标识之类的就能直接回复，不需要操心那么多参数。」

## 一、现象

全局会话和项目会话之间有两种通信：

| 工具 | 有 dispatch 记录 | 能回执 |
|---|---|---|
| `send_work_request` | 有（`gd_xxx`） | 能，靠 `reply_global_dispatch({ dispatchId, report })` |
| `send_session_message` | **没有** | **不能** |

所以「问一句 / 催一下 / 确认个细节」这类**普通消息**，项目会话回不了。模型只有两个选择：把答案写在自己会话里（全局会话看不到），或者干脆用 `send_work_request` 硬包一层（凭空建一个 dispatch，污染任务板）。

## 二、根因

`AgentRuntimeProjectExecutor.cs:274-328` `SendSessionMessageAsync`：

```csharp
var content = RequireString(input, "content");     // 裸文本，原样投递
...
w.WriteString("sessionId", sessionId);
w.WriteString("content", content);                 // ← 没有任何标识
```

投递端（`lib/tools/project-send-message.ts`）再走 `chatStore.sendMessage()`，**完全模拟用户输入**。

结果：目标会话收到一条普通用户消息，**没有 id、没有来源、没有回执通道**。而 `reply_global_dispatch` 的 schema 里 `dispatchId` 是必填（`GlobalDispatchReplyToolProvider.cs:28-36`）—— 没有 id 就没法回。

`send_session_message` 现有唯一的「回传」能力是 `followUp`（`SendSessionMessageAsync:285-316`），但那是**定时追问**：`delayMs >= 1000` 后全局侧主动再问一次，方向是反的，救不了这个场景。

## 三、目标形态（老大已给口径）

1. 全局会话的普通消息也渲染成卡片（与 S-278 同一套组件，只是 `kind` 不同）；
2. 卡片**携带标识**，项目会话回执时**只给卡片标识 + 正文**，不用重复传 sessionId / projectId / 全局任务等一堆参数；
3. 回执自动回到全局会话对应卡片的下面。

## 四、实现方向

**核心决定：普通消息也建一条轻量 dispatch 记录**，复用现有表与状态机，`kind` 区分。

| 项 | work request | 普通消息（新增） |
|---|---|---|
| `kind` | `work_request` | `message` |
| id 前缀 | `gd_` | 建议 `gm_`（`g`lobal `m`essage），或统一 `gd_` + kind 区分 |
| 绑全局任务 | 必填 | 可选（允许「就地问一句」不绑任务） |
| 进任务板 | 是 | 是（但默认折叠，避免噪音） |
| 回执工具 | `reply_global_dispatch` | **同一个工具**，`status` 只允许 `completed`（普通消息没有「进行中」） |

**回执工具要不要拆成两个？** 我的建议是**不拆** —— 一个 `reply_global_dispatch({ dispatchId, report, status? })` 够用，模型只需要记住「收到带标识的消息 → 用这个 id 回」。拆两个工具只会增加模型选错的概率（S-270 的教训：出口越少越好）。

**但要改的是 schema 必填项**：现在 `status` 是可选的、`report` 必填。普通消息的回执建议允许 `report` 为空（只是「收到 / 好」），此时自动填「已确认」。

## 五、待确认

1. **轻量 dispatch 会不会污染任务板**：每句问答都进看板显然不行。建议默认 `hidden_from_board=true`，只有 `work_request` 上板。
2. **id 前缀**：`gm_` 与 `gd_` 两套，还是一套 `gd_` 靠 kind 分？我倾向前者 —— 前缀能一眼看出类型，排查日志时省事。
3. **是否允许「回执再回执」**（全局会话对项目会话的回执再回一句）：按现在的机制会无限套娃。建议**只允许一层**：派发 → 回执，回执本身不再触发回执通道。
4. 与 S-278 的**实现顺序**：本条依赖 S-278 的 meta 通道（卡片标识要落进消息）。建议**同迭代同刀做**，顺序是 S-278 打底 → 本条扩 `kind`。
5. 与 **S-280（自动回执）** 的关系：普通消息**要不要也自动回执**？我的建议是**要**，但状态只标 `completed_implicit` 且卡片上明确写「未显式回复，已按本轮输出自动归档」—— 不能把沉默伪装成回答。

## 六、开工前查证（iter-v3-5 刀 10，2026-10-30）—— **卡住待拍板**

### 6.1 好消息：`kind` 值域和表都已经在了

- `GlobalTaskDispatchKindValues` 早就有 `Message = "message"` 与 `WorkRequest = "work_request"` 两个值，`kind` 列的默认值就是 `'message'`（`DbClient.Schema.cs:361`）。**不用加值域**。
- `DbGlobalTaskDispatchTools.Create` 已经校验 `kind must be 'message' or 'work_request'`（`:129`）。**不用改校验**。
- 所以「扩 `kind`」这件事本身是零改动的 —— 真正没做的是**`send_session_message` 从来不建记录**。

### 6.2 坏消息：卡在一条 NOT NULL 上

`global_task_dispatches.global_task_id TEXT NOT NULL`（`DbClient.Schema.cs:357`），而 `Create` 把 `globalTaskId` 列为必填并且要校验任务存在（`:86`、`:96-100`）。

§四 表格里写的「绑全局任务：**可选**（允许『就地问一句』不绑任务）」是我登记时的设计建议，**老大原话没这条要求**。但要不要它，决定的是完全不同的实现路径，且都超出「零迁移」：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A** | 放宽成可空：SQLite 改不了列约束 ⇒ 必须「建新表 → 拷数据 → 改名」重建 `global_task_dispatches` | 动既有表 + 全量数据搬运，`DbClient.Migrations.cs` 现有的 `EnsureColumn` 机制只支持加列，得新写一套重建迁移 | **高**。这张表是任务板的唯一数据源，迁移写错就是看板数据丢失 |
| **B** | 必绑任务：全局会话发普通消息前必须先有全局任务 | 零迁移 | 「就地问一句 / 催一下」这个原始场景直接没了 —— 价值砍一半 |
| **C**（推荐） | 普通消息另建轻量表 `global_message_dispatches`（`CREATE TABLE IF NOT EXISTS`，纯增量、老库自动建、零数据搬运）；回执工具按 `gm_` 前缀分表查 | 两套表、`reply_global_dispatch` 要分叉、S-280 的归档逻辑要覆盖两处 | **低**。不碰既有约束、不碰既有数据 |

**我推荐 C**。理由：A 拿任务板的数据安全去换一条「可以为空」的约束，不划算；B 把需求的核心场景砍了；C 的代价（两套状态机）是**确定的、局部的**，而 A 的代价是**不确定的、全局的**。而且 `gm_` 前缀本来就天然分表 —— §五 第 2 条建议的 `gm_` 前缀在 C 里从「好习惯」变成了「结构必需」，反而更自洽。

### 6.3 三个仍需老大点头的点

1. **A / B / C 选哪个**（我推 C）。
2. **§五 第 1 条**（`hidden_from_board`）：C 方案下天然不需要 —— 普通消息根本不在看板那张表里，看板查询压根扫不到。若选 A/B 才需要这个字段（又是一次 schema 改动）。
3. **§五 第 5 条**（普通消息要不要自动回执）：我的建议不变 —— 要，但标 `completed_implicit` 且卡片上写明「未显式回复」。

### 6.4 对刀 11（S-280）的影响

S-280 的核心判据「这一轮是不是在干这个 dispatch」用的是刀 9 已交付的 meta，**不依赖本条**。但 S-280 的三条硬规矩（显式覆盖隐式 / 隐式必须标明未显式回复 / 自动归档只写 dispatch 记录不塞消息）在 C 方案下要覆盖两张表 —— 先做 S-280 只覆盖 `work_request`，等本条落地再补第二处，就是 plan.md 警告的「同一个协议改两遍」。

**所以本条卡住 ⇒ 刀 11 也跟着卡**，除非老大同意「S-280 先只覆盖 `work_request`，第二处等本条」。

### 8.3 两个设计取舍

1. **为什么用 id 前缀而不是加一列 `table_name`**：回执入口拿到的只有 `dispatchId` 一个字符串，前缀是唯一不需要额外查询就能分辨表的信息。前缀常量集中一处，别处不许再写 `"gm_"` 字面量 —— 与 S-276 那轮「四处判据各写各的」同一个教训。
2. **为什么不拆两个回执工具**：`reply_global_dispatch` 仍是唯一入口，按前缀分表。S-270 的教训是出口越少越好。

### 8.4 回归

`tests/WishfulClaw.DispatchRouterRegressionTests`（真 sqlite）**72/72 通过**，本刀相关部分：

- `Create` / `Get` / `Update` / `Cancel` 全链路
