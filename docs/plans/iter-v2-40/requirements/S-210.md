# S-210：正文被折叠进过程块，外面只剩一句写死的「任务暂告一段落」

> 状态：**已登记 + 根因重定，待开工**（2026-10-20 登记；**10:14 老大指出「这个是聊天窗口的显示」后重查，根因与我首版登记的不是一回事**）。
> 类型：**bug**（显示层把已有正文吞掉；文案写死是次要问题）。
> 归属：**iter-v2-40**。
> 来源：**老大 2026-10-20 10:03** —— 「目前我们聊天窗 在用户终止执行或者 触发压缩后，之前的执行过程会折叠 并且显示一个固定值 任务暂告一段落 作为总结。这个我希望登记一个需求，能实际显示是用户取消执行，触发压缩等实际情况」。
> 轨道：**软件侧**（纯渲染端；Worker 侧零改动）。

---

## 一、现象

聊天窗里某些 assistant 消息，**执行过程折叠成一块，正文不见了**，下面只剩一句灰字 **「任务暂告一段落」**。老大在「用户终止执行 / 触发压缩后」注意到它。

## 二、根因（10-20 重查，实证钉死）

### 2.1 实测数据：这些消息**本来是有正文的**

拿正式库 `~/.wishful-claw/index.db` 最近 800 条 assistant 消息，按渲染链逐步复刻（`segments` → `buildChatMessageContent` → `renderItems` → `splitProcessAndFinal`）：

```
会渲染灰字「任务暂告一段落」= 83 条
  其中 DB 里其实有正文（text 列非空）= 83 条   ← 全部
```

**83 条一条不漏，全都有正文。** 也就是说灰字根本不是「这轮没说话」的标记，而是「这轮说的话被吞进折叠块了」的标记。

典型尾部形态（最后 3 块）：

| 尾部 | 说明 |
| --- | --- |
| `tool_use, tool_result, thinking` | 说完话 → 调工具 → 再思考，就结束了 |
| `text, tool_use, tool_use` | 说完话 → 连调两个工具（第二个没有 result，中止） |
| `tool_result, tool_use, tool_result` | 跑工具 → 说一句 → 又跑工具 |

### 2.2 切分规则把正文判成了「过程」

`components/chat/AssistantMessage/process-summary.ts:144-182`：

```ts
// 从尾部往前跳过 text/image/image_error/agent_error，遇到第一个"过程"项就切
for (let i = items.length - 1; i >= 0; i--) {
  const item = items[i]
  if (item.kind === 'block') {
    const block = normalizedContent?.[item.index]
    if (block && (block.type === 'text' || ...)) continue
  }
  return i + 1
}
```

规则是「**只有排在最后一个过程项之后的文字才算最终答复**」。于是：

- 消息以文字结尾（最常见的正常收尾）⇒ 文字进 `finalItems`，正常显示；
- 消息以**工具调用 / 思考 / tool_result 结尾** ⇒ 切点落在数组末尾 ⇒ `finalItems` 为空 ⇒ **这条消息里所有文字（不管写得多长）全被归进 `processItems` 塞进折叠块**，折叠块外面没有正文可显示，`content-renderer.tsx:499-505` 就用那句固定灰字兜底。

**「用户中止」和「压缩」只是提高命中率的时机**：中止时最后一步几乎总是工具调用（没有收尾文字），所以必然命中；这跟「结束原因」没有因果关系 —— 结束原因只是另一个可以改进的点，不是本 bug 的成因。

### 2.3 为什么 restart 后看起来「正常」

`content` 是数组的落库消息为 **0 条**（800 条里），全部靠 `meta.segments`；`buildChatMessageContent`（`lib/agent/chat-message-blocks.ts:11-90`）在每条 `tool_use` 段后面**追加一个内联 `tool_result` 块**（`:43-53`）。这个 `tool_result` 不在「可跳过」清单里 ⇒ 它天然成为切点 ⇒ 以工具结尾的消息重新加载后照样命中灰字。**不是刷新即好，是一直都在。**

## 三、目标

画面变成这样，两种情况分开：

**情况 A：这一轮确实说过话（绝大多数，83/83 都属于这种）**
- 末尾那段文字（或最后一段连续 `text` 块）作为正文显示在折叠块下方；
- **不再显示任何「暂告一段落」字样** —— 有正文就没必要补一句总结。

**情况 B：这一轮真的只有过程、一个字都没说**
- 才显示结束原因，且按真实原因分文案：

| `reason` | 建议文案 |
| --- | --- |
| `aborted` | 你中止了这一轮 |
| `max_iterations` | 达到迭代上限，这一轮停在这里 |
| `completed` | 这一轮没写收尾文字，工具已执行完 |
| `error` | 出错中断，详见上方错误卡片 |
| 无数据（老消息） | 保持现状「任务暂告一段落」 |

## 四、非目标

- **不改折叠块本身的语义**：中间的叙述文字（「我先看下这个文件…」）继续折叠，这是设计意图，不是 bug。
- **不改运行行为**：不动 `AgentLoop` 的停止 / 压缩判定。
- **子 agent 卡片不在本轮范围**（`SubAgentCard` 已有 `endReason` 三态显示）。

## 五、修法

### 5.1 切分修正（情况 A）

`splitProcessAndFinal` 增加一条兜底：**切点之后（`finalItems`）为空、但 `processItems` 里有 `text` 块时，把最后一段连续 `text` 块回填为 `finalItems`**（从尾部往前取连续 text，遇到非 text 即停）。不动其余口径。

- 纯函数，直接单测：`text,tool,tool` / `tool,tool` / `text,tool,text` / `thinking` 结尾各角色对照。
- 回填后 `hasProcessContent` 仍为真 ⇒ 折叠块照旧展示，只是外面有了正文。

### 5.2 结束原因（情况 B，也就是最初登记的那一半）

- `MessageMeta` 加 `runEnd?: { reason, at }`（`lib/api/types.ts:384-392`）；落库零 schema 改动（`db-helpers.ts:128-146` 整体展开 `meta`，`:170-176` 原样还原）；
- 写入点：`chat-store/index.ts` 的 `loop_end` 分支，在 final persist 之前写进 `envelope.runId` 对应消息的 `meta.runEnd`；
- 显示点：`content-renderer.tsx:501-505` 的 `executionPaused` 改为按 `runEnd.reason` 取键，抽成**不 import IPC 的纯函数**（B1 教训），未知 / 缺失回落 `executionPaused`。

## 六、待确认

1. **回填的正文是否加视觉区分**（比如加一句「以下是这一轮的收尾」或降低透明度）。默认**不加**，直接当正文渲染 —— 它本来就该在那儿。
2. **回填取几段**：默认**最后一段连续 text**（遇到 tool_use / thinking 即停）。若一段都没有（纯工具轮），走情况 B。
3. **`aborted` 是否细分**「点停止」与「运行中插消息打断」（后端同报 `aborted`，细分要改 Worker 侧 reason 值）。默认不细分。

## 八、风险

- **回填后可能出现「文字重复」**：若某条消息尾部本来就有 text 走到 `finalItems`，不会进回填分支（条件限定 `finalItems` 为空），不重复。
- **`tool_result` 不是渲染项**（`index.tsx:365-388` 只对 `tool_use` 分组，其余按 block 入列）—— 回填要按 `normalizedContent` 的块类型判断，别按 renderItem 种类。
- **长会话性能**：切分是每帧渲染路径上的纯计算，回填是尾部线性扫描，可忽略。
