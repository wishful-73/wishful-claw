## 一、诉求

**不是**搬本仓的 `docs/`。**本期本仓 `docs/` 一字不动。**

要的是把这套已经在跑的模式做成**产品能力**：任何人用 WishfulClaw 做项目时，agent 能按「迭代 → 需求登记 → 计划 → 实施 → 验收」这套流程干活，产出落在**那个项目工作目录的 `.wishful-claw/`** 下，不落进用户的源码树。

## 二、为什么值得做

这套流程不是设计出来的，是**跑出来的**：本仓已经走完 **60 个**迭代目录、单迭代 `changelog.md` 85 KB 的裁定流水、每需求一份 `requirements/S-NNN.md`。它的价值已经被验证 —— 大量「当时为什么这么定」的结论都靠它留了下来（`docs/plans/iter-v3-6/requirements/S-309.md` §4.2.2 那条硬约束就是典型）。

现在这套东西**只存在于本仓的 `docs/` 里**，换个项目就带不走。

## 六、裁定

### 6.1 目录名 —— ✅ 已定：`.wishful-claw/workflow/`（16:07）

`plans` 被计划模式占用（`AgentRuntimePlanExecutor.cs:24`），`goals/{goalId}/plans` 被 goal 占用（`GoalPlanTracker.cs:13`），都不能改名。`workflow/` 语义对得上、不撞车。

### 6.2 注入通道 —— ✅ 已定：指针式 + AGENTS.md 决定读不读（16:11 再订正）

**老大原话**：「新建项目就会复制一份放在那里，然后系统提示里面会提一句 我们有开发工作流放到指定路径，但是读不读是 AGENTS.md 去决定……而不是现在直接塞到提示里面」

这套能成立的根据（本轮实测）：

1. **AGENTS.md 天生就是策略文件** —— 它在 persona 四件套里（`PromptBuilder.cs:417`），**无条件全量注入**（20,000 字符预算）。它必须先被注入，才可能去决定「我还要读什么」。这是整套设计的支点。
2. **AGENTS.md 能按项目写** —— persona 两级：`PersonaStore.GetPersona`（`:162-172`）先读 `<项目>/.wishful-claw/personas/<id>/`，miss 才回落全局；`SystemPromptCache.GetPersonaFingerprint`（`:92-95`）同样双路径。
3. 于是：**软件只给指针，策略写在 AGENTS.md 里，agent 自己决定读不读。**

具体：
- 新建项目 → 复制 `dev-workflow.md` 到 `.wishful-claw/`；
- 系统提示加一行（大意「本项目带开发工作流规范，位于 `.wishful-claw/workflow/dev-workflow.md`；是否遵循见 AGENTS.md」）—— 只有一行，规范正文多长都不进上下文；
- 读不读 = AGENTS.md 里写的那句话 + agent 自主 `Read`。

**否决**：skill 项目级化（`SkillCatalog.cs:449` 把根写死在 `~/.agents/skills/`，要连带动作用域、`SkillConfigStore`、渲染层 `SkillsMenu` 与整条调用链）；纯靠 agent 自觉（换会话就忘）。

### 6.3 触发方式 —— ✅ 由 6.2 消解：**不需要软件开关**

原 a（用户显式开口）/ b（设置项默认值）/ c（全局一刀切）三选一**作废**。新方案 d：**AGENTS.md 即策略**。

- 想要这套流程的项目：AGENTS.md 里写一句「本项目按迭代流程走，开工前先读 `.wishful-claw/workflow/dev-workflow.md`」；
- 不想要的项目：AGENTS.md 不提，或直接删模板文件；
- 软件侧**零开关、零配置 UI**。

代价：多一层「先看 AGENTS.md 才知道有那么个文件」的间接；把 AGENTS.md 清空的用户会彻底不知道有这文件（可接受 —— 文件就在目录里，删不删随他）。

### 6.4 本仓怎么过渡 —— ✅ 已定：**将来整体切新模式**（16:07）

老大原话：「本仓可以后续都走新模式，等更新软件以后再来调整我们文档都行」。

⇒ 不做永久双轨：
1. **本期**：只做产品能力，本仓 `docs/` 一字不动；
2. **产品可用后**：本仓 `docs/plans/` 的滚动流程迁进 `.wishful-claw/workflow/`，`docs/` 只留对外可公开的说明性文档。

⚠️ 迁移前必须解决版本化：`docs/plans/` 现有 **60 个**迭代目录、`iterations` 38 / `progress` 51 / `reviews` 15 个文件，而 `.gitignore:77` 是 `.wishful-claw/*` **全忽略** ⇒ 搬进去全部失去版本化。两条路：开白名单 `!.wishful-claw/workflow/**`，或历史留原地、只迁滚动流程。

### 6.5 `iterations` / `progress` / `reviews` 是否一并产品化 —— ✅ 暂定：本期只做核心三件

本期只做：**规范正文** + **迭代目录** + **需求单** + 三套模板。`iterations` / `progress` / `reviews` 作为**可选模板**，用不用随项目。

理由：这套流程是为我们自己的节奏磨出来的，一上来全搬会过重。

### 6.6 同构改造热记忆 —— ✅ 已定方向：同样改成指针式（16:11 老大一并提出）

**现状**：`BuildMemoryContext`（`PromptBuilder.cs:224-272`）把当前 scope 的 MEMORY.md **全文**塞进系统提示，预算 6,000 字符。scope 判定：SSH 项目 → `project:ssh:{id}`；本地项目 → `project:{workingFolder}`；无工作目录 → `global`。

**改成**：系统提示只提路径，读不读由 AGENTS.md 决定。

**已有可复用的按需通道**：`MemoryRecallService`（`src/runtime/WishfulClaw.Workspace/Memory/MemoryRecallService.cs`）在 Agent Loop 前用 FTS/LIKE **检索相关条目**注入 —— 跟「全文塞」是两条独立路，指针化之后它留着当主动召回兜底。

**前提缺陷已单独立项（S-314）**：记忆变更后系统提示**根本不重建** —— `SystemPromptCache.Invalidate` / `Clear` 全仓 0 处调用（死代码），且 `GetPersonaFingerprint`（`SystemPromptCache.cs:83-124`）只扫 `personas/<id>/*.md`，MEMORY.md 不在其中，压根没进 cacheKey。⇒ 单会话内提示里的热记忆是过期快照，**跨会话也不刷新，只有 worker 重启才重建**。所以现状不是「略旧」，是「白占 6,000 字符还过期」。§6.6 落地后该缺陷随之消失，S-314 是本条的验收依据。

**必须说清的风险**：

- 全文注入的好处是「不读也不会漏」；改成按需后 agent 可能压根不读 ⇒ **忘事**。而老大的真实痛点恰恰是「全局 PM 忘事」（11-02 原话）。
- 缓解：①AGENTS.md 里写死「用户提到过去的事，先读 MEMORY.md」；②`MemoryRecallService` 自动召回保留兜底；③留一个设置项「热记忆全文注入」的口子，可回滚。
- 这条影响**所有会话**（不分项目），建议实施时**单独一刀、可独立回滚**，别和 §6.2 混在一起。

## 八、风险

1. **白写一轮** —— 这套流程是为我们自己的节奏磨的，直接产品化可能过重。§6.5 已收窄到核心三件；
2. **编号冲突** —— `S-NNN` 项目内递增，多 agent 并发登记会重号（本仓 S-296 撞过）；需要「先读最大号再加一」的硬规矩或文件锁；
3. **迁移断链** —— 代码注释里有 **14 处**引用 `docs/plans/…`（11 个文件）是「这条规矩的出处」，搬走即断链；但**没有运行时代码读 `docs/`**（14 处全是注释），功能不会坏，只是注释失效；
4. **用户误以为污染** —— 有人会在意 `.wishful-claw/` 出现在自己仓库，即便进了 `.gitignore`。首次落盘时要说明它不进 git；
5. **指针化的通病** —— 见 §6.6 风险，热记忆尤甚：省下的 token 可能换来「忘事」。
