## 一、老大原话

> 「登记一个需求 全局任务增加一个可选属性 可以选择挂某一个项目下 项目下会话可以查询当前项目的任务」

两件事：

1. **`global_tasks` 增加可选的「归属项目」属性** —— 建任务时能选挂到某个项目下，也可以不挂（保持现在的纯全局）。
2. **项目下会话可以查询「当前项目」的任务** —— 项目会话里的 agent 能看到挂在自己项目下的全局任务。

### 2.4 工具可见性（**这是本条最容易踩的地方**）

`src/runtime/WishfulClaw.Agent/Tools/Providers/GlobalTaskToolsProvider.cs`，6 个工具：

`list_global_tasks`（`:20`）/ `create_global_task`（`:39`）/ `update_global_task`（`:58`）/ `list_global_dispatches`（`:85`）/ `send_work_request`（`:103`）/ `update_dispatch`（`:126`）

**每一个**都写着：

```csharp
availableModes: new[] { "global" },
visibleScopes: ToolVisibilityScopes.GlobalSideAndWorkRuns
```

而 `ToolVisibilityScopes.GlobalSideAndWorkRuns` = `["global:*@*", "*:cowork@*"]`（`src/runtime/WishfulClaw.Core/Tools/ToolVisibilityScopes.cs:39`），注释（`:34-38`）写得很明确：

> The global side's own capabilities: global tasks, sessions, dispatches and the hot memory that belongs to the user rather than to a project. **A project chat is deliberately excluded** — it has a project to work in — while the work runs that serve those requests are included.

⇒ **项目会话今天完全看不到任何全局任务工具**。这是刻意设计的边界，不是遗漏。

### 2.5 项目会话侧有没有别的 task 工具

全仓搜 `"list_tasks"` / `"create_task"` / `"update_task"` / `list_todos` / `"add_todo"` —— **零命中**。

`tasks` 表是 session 级 Todo（`GlobalTaskToolsProvider.cs:9` 注释：「they never touch session-scoped Todos (tasks table)」），与 `global_tasks` 是两套东西。所以项目会话现在**既看不到全局任务，也没有平级的替代品**。

### 2.6 加列机制已经成熟

`src/runtime/WishfulClaw.Infrastructure/Db/DbClient.Migrations.cs` 已有 `EnsureColumn` 体系，`:22-72` 里 20+ 条先例（`sessions` 十几个列、`projects` 两个、`global_task_dispatches.source_session_id` 一条）。

⇒ **不需要手写迁移逻辑**，加一行 `EnsureColumn("global_tasks", "project_id", "TEXT");` 即可，老库启动自动补列，零数据搬运。注意 `CREATE TABLE IF NOT EXISTS` 对已存在的表不生效，所以 DDL 与 `EnsureColumn` **两处都要改**（新库靠 DDL、老库靠迁移）。

> **⚠️ 2026-11-03 订正：上面这段结论是错的，别照抄。**
> `EnsureColumn` 在 `RunMigrations()` 里，而 `Initialize()` 先跑 `CreateSchema()`；
> 索引 `ix_global_tasks_project` 就在 `CreateSchema()` 的 DDL 数组里 ⇒ 补列来不及，老库直接炸。
> **正确做法**：索引引用的新列，必须在 DDL 循环**之前**补（见 §6.5）。

## 三、要做什么

### 3.1 schema（纯增量）

1. `DbClient.Schema.cs` 的 `global_tasks` DDL 加 `project_id TEXT`（可空）。
2. `DbClient.Migrations.cs` 加 `EnsureColumn("global_tasks", "project_id", "TEXT");`。
3. 建索引 `ix_global_tasks_project ON global_tasks(project_id)` —— 项目会话要按项目过滤，没有索引会全表扫。

**不回填**：老任务的 `project_id` 保持 NULL = 不挂项目，语义正确，不需要猜它原来属于谁。

### 3.2 契约与 DB 端点

| 改哪 | 怎么改 |
|---|---|
| `GlobalTaskSelect`（`DbGlobalTaskTools.cs:16-17`） | 字段列表加 `project_id` |
| `GlobalTaskEntity` / `GlobalTaskRow`（`GlobalTaskEntity.cs:25-47` / `:51-89`） | 各加 `ProjectId`（row 用 `[JsonPropertyName("project_id")]`），`FromEntity` 补一行 |
| `EntityMappers.MapGlobalTask` | 补 `project_id` 读取 |
| `DbGlobalTaskTools.List`（`:19-52`） | 加 `projectId` 过滤参数；**另需一种「只看未挂项目」的表达**（见 §3.4 决策 2） |
| `DbGlobalTaskTools.Create`（`:72+`） | INSERT 补 `project_id` |
| `DbGlobalTaskTools.Update` | patch 支持 `projectId`，**且支持置空**（挂回全局） |

### 3.3 工具层

**全局侧（改现有）**

- `create_global_task` 加可选参数 `projectId`：「Optional project id. Omit to keep the task global.」
- `update_global_task` 的 `patch` 加 `projectId`，并允许传空串/null 表示「挂回全局」
- `list_global_tasks` 加可选参数 `projectId`（过滤）+ 一个「未挂项目」的表达

**项目侧（新增，只读）**

新增 `list_project_tasks`，只做一件事：列出**挂在本项目下**的全局任务。

- **projectId 由服务端从当前 session 推导，不接受模型传参** —— 这是本条的硬边界。让模型自己传 projectId，等于把「能不能看别的项目的任务」交给模型判断。
- 返回字段与 `list_global_tasks` 一致，项目会话据此知道「上头给我派了什么事」。

### 3.4 三个语义决策（**已定，按此实施**）

| # | 问题 | 采用 | 理由 |
|---|---|---|---|
| 1 | 挂了项目的任务，全局任务板还显不显示？ | **显示**，加一个归属标签 | 老大原话是「**可选属性**」——属性不等于搬家。任务板是全局的唯一数据源，按项目隐藏会让全局 PM 看不到全貌 |
| 2 | 项目会话能不能看到「没挂项目」的全局任务？ | **不能**，只返回 `project_id = 当前项目` 的 | 「查询当前项目的任务」字面就是这个意思。放开会让每个项目都看到全部全局任务，边界就没了 |
| 3 | 项目会话能不能改任务状态？ | **不能**，本次只读 | 老大只说了「查询」。项目会话改全局任务状态会绕开 `update_dispatch` 的回执链路（那条链有状态机和 `latest_report`），越权且难追溯 |

### 3.5 可见性怎么给（实施时要选，两选一）

`list_project_tasks` 需要一个项目会话能拿到的 grant。现有 scope 里**没有**「项目会话专属」的集合，`GlobalSideAndWorkRuns` 含 `*:cowork@*`（项目 cowork 会话也能命中）。

- **方案 A（推荐）**：新开 `ToolVisibilityScopes.ProjectSideOnly = ["project:*@*"]`，只授 `list_project_tasks`。语义最干净，与 `GlobalSideOnly`（`:41-48`）对称 —— 那节的注释本身就是「deliberately not `*:cowork@*`，那个 grant 会把工具漏进项目会话」，这里正好是它的镜像。
- **方案 B**：沿用 `GlobalSideAndWorkRuns`，靠「全局会话没有 projectId ⇒ 返回空列表」兜底。**不推荐** —— 工具出现在全局会话的工具表里但永远返回空，既浪费上下文，也会诱导模型乱试。

## 四、验收判据

1. 建一个**不挂项目**的全局任务 ⇒ 项目会话 `list_project_tasks` 返回**空**，全局 `list_global_tasks` 能看到它。
2. 建一个**挂 A 项目**的全局任务 ⇒ A 项目会话能看到，B 项目会话**看不到**。
3. `update_global_task` 把 `projectId` 置空 ⇒ 任务挂回全局，A 项目会话立刻看不到了。
4. **反向验证**：把服务端 projectId 推导改成「用模型传进来的参数」⇒ 应当能构造出「A 项目会话查到 B 项目任务」，此时判据必须红。这条是本需求唯一的安全边界，必须做反向验证。
5. 老库升级：拿一个 1.0.5 的 `index.db` 副本启动 ⇒ `project_id` 列自动补上、老任务全为 NULL、任务板显示正常、无报错。

## 五、风险

- **schema 增量但不可逆**：加列本身安全（`EnsureColumn` 只加不删），但一旦有代码依赖 `project_id`，回退版本时旧代码不认这列 —— 无害，只是这列被忽略。**不需要备份强制要求**，但收尾前建议留一份库副本。
- **`GlobalTaskSelect` 是写死的字符串**：加列后如果只改了 DDL 没改这行，`MapGlobalTask` 读不到值会**静默返回空**，不报错。这是本条最容易漏的一处，验收判据 2 能兜住。
- **项目会话的 projectId 来源**：必须从 session 记录（`sessions.project_id`）取，不能用 `workingFolder` 反推 —— 两个项目可能共用同一个工作目录（同仓库多项目）。

#### 判据 5（老库升级）—— 2026-11-03 实测失败，已修

拿 `.wishful-claw-dev` 的老库启动 ⇒ `SqliteException: SQLite Error 1: 'no such column: project_id'`，
`DbClient.CreateSchema()` 整体失败 ⇒ cron 恢复、会话列表、sub-agent 索引全部报错，界面读不出数据。

**根因是 §2.6 那句判断错了**，原文写「加一行 `EnsureColumn` 即可，老库启动自动补列」——
但 `DbClient.Initialize()` 的顺序是 `CreateSchema()` → `RunMigrations()`，而
`ix_global_tasks_project ON global_tasks(project_id)` 正好在 `CreateSchema()` 的 DDL 数组里，
`EnsureColumn("global_tasks", "project_id", "TEXT")` 排在后面**根本来不及**。
`CREATE TABLE IF NOT EXISTS` 又不会给已存在的表补列 ⇒ 老库建这条索引时直接炸。
影响面是**所有 1.0.5 及更早的用户升级**，不是个别机器。

**修法**：把补列提到 DDL 循环之前（`DbClient.Schema.cs`，`EnsureColumn` 对不存在的表自行忽略，
新库不受影响），并顺带预防性补 `agent_timeline_events.project_id` —— S-25 时期的库同样缺这列，
`ix_timeline_project_created` 是同一个坑。

**修后实测**：`52 DDL statements applied` → `migrations completed` →
`initialization completed successfully`，无报错。

**教训**：`EnsureColumn` 能补列，但**补的时机**必须早于任何引用该列的 DDL。
以后再加「新列 + 索引」时，索引语句与 `EnsureColumn` 的先后关系要一起想。
