# S-324  `StripDataUrlPrefix` 整串复制 —— 一张图 600 KB 复制两遍只为看前 64 字符

> 登记：2026-11-05 15:04，15:14 从合单拆出独立编号。
> 状态：**已完成（2026-11-05，刀 6 提交 `ebfdad75`）**。`StripDataUrlPrefixSpan` 零分配版落地，两处热路径去除整串复制；回归 `ImageMediaGateRegressionTests` 53/53（新增 15 条 span/string 逐字节比对）。
> 性质：**纯性能优化**。判据（识别出什么 media type）**必须一模一样**。
> 独立于 S-322 / S-323。

## 一、来源

同 S-322 / S-323。

## 二、现象：组包分配实测放大 5.13 倍

私有仓实测（`docs/analysis-2026-11-05-round2.md` §2）：一条 0.86 MB 的请求，组包阶段分配量放大 **5.13x**（UTF-16 口径）。

## 三、代码链路（主仓实读）

### 3.1 string 版前缀剥离

`src/runtime/WishfulClaw.Agent/ProviderContentHelpers.cs:44-49`：

```csharp
public static string StripDataUrlPrefix(string dataUrl)  // 返回新的 string
```

### 3.2 两处热路径都在用整串

| 位置 | 写法 | 问题 |
|---|---|---|
| `ProviderContentHelpers.cs:62` | `StripDataUrlPrefix(imageBase64).Trim()` | **`Trim()` 把 600 KB 整串再复制一遍**，只为看前 64 字符；而且这一行上游对同一张图已经算过一次 |
| `Tools/FileTools/ImageFileProbe.cs:159` | `HasCompleteContainerInBase64` | 同样对整串做判断 |

.NET `string` 是 UTF-16 ⇒ 一个 600 KB 的 base64 在内存里是 **1.2 MB**，复制一次 1.2 MB，两处两遍就是 2.4 MB 的瞬时垃圾，**每张图每轮**。

## 四、修复方向

**`ReadOnlySpan<char>` 版**：只在原 slice 上做判断，不产生新字符串。

- 新增 span 版 `TryStripDataUrlPrefixSpan(ReadOnlySpan<char>, out ReadOnlySpan<char> dataUrlStart, out string? mediaType)`
- `:62` 与 `ImageFileProbe.HasCompleteContainerInBase64` 改用 span 版，**去掉那个 `Trim()` 整串复制**
- **保留 string 版**给真要产 string 的调用点（改完全仓 grep 一遍确认还有谁在用）

判断逻辑一行不改，只改「怎么读」。

## 五、代价与取舍

| 取舍 | 说明 |
|---|---|
| 两种签名并存 | span 版 + string 版共存，可选调用。**不要为了「干净」硬删 string 版** —— 那会把改动半径放大到看不见的地方 |
| 收益量级小 | 单张图省 2.4 MB 瞬时分配，**不改稳态内存**（稳态归 S-322）。这条是省 CPU 秒数，别指望它降 GB |

## 六、验收

| # | 项 | 怎么验 |
|---|---|---|
| 1 | **判据一模一样** | 构造 `data:image/png;base64,xxx` / `data:image/jpeg;base64,xxx` / 纯 base64（无前缀）/ 空串 / 带首尾空白，五种输入新旧实现结果**逐字节一致** |
| 2 | **行为无变化** | 发一张图，模型正常收到图（不报 media type 错误） |
| 3 | **回归测试可搬** | 私有仓 `RequestBuildAllocationRegressionTests` 里对应的断言 |

门禁同 S-322。
