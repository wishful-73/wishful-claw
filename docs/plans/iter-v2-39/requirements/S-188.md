## 二、三个缺口（老大点名）

| # | 缺口 | 用户能做 | PM 能做 |
|---|---|---|---|
| 1 | **看不到**项目会话排队的消息 | 输入框上方队列面板可见 | ❌ |
| 2 | **撤销**排队中的消息 | 「取回」/「删除」/「清空」（⚠️ **「取回」依赖输入框，PM 侧不存在这个条件**） | ❌ |
| 3 | **停止**项目会话的运行 | 停止按钮 | ❌ |

⇒ 后果：**只能干着急**（PM 派了活、发现跑偏或无回应，手里没有任何干预手段）。

**「停止」的裁定语义（老大 15:11）**：

> 「停止就是会话本身在运行中，需要让会话停下来，然后重新发消息给会话呀」

⇒ = §五 表原第 ② 项里的**最小语义**：**只停当前这一轮运行**（`cancelStream(sessionId)`），**队列保留、派发照旧** —— 停完之后 PM 还能（也应该能）**重新发消息给这个会话**。**不丢队列、不暂停派发。**

⇒ 对应落点：**`useChatStore.getState().cancelStream(sessionId)`**（`stores/chat-store/index.ts:541`）。**不碰** `clearPendingSessionMessages` / `pausePendingSessionDispatch`（那是「停 + 清队列」「停 + 暂停」两种更重的语义，本需求不做）。**不用** `requestStopAgent(runId)`（死代码，且 PM 拿不到 `runId`）。

### 2.1 「停止」与「队列派发」的实际关系（2026-10-11 补记 → 第三刀）

第二刀的实现落点**就是**上面定的 `cancelStream(sessionId)`；而 `cancelStream`（`stores/chat-store/index.ts:541-561`）**第一件事**就是 `pausePendingSessionDispatch(sessionId)`，紧接着本轮以 `aborted` 结束、`:1741-1743` 又暂停一次。⇒ **实际行为 = 「队列保留，但派发被冻住」**，与本节上方的「**派发照旧**」**不一致**。

**冻住之后没有自动出口**：所有自动派发路径传的 `resumePaused` 都是 `false`（`chat-store/index.ts:1750` 的 loop_end、`use-chat-actions.ts:936` 的自重试），连「停完再发一条新消息、那一轮跑完」也不会解冻；此前全仓只有 UI 队列面板的「继续」按钮（`use-queued-messages.ts:113`，`resumePaused` 默认 `true`）能解。PM 没有输入框 ⇒ 停了就永远卡住，唯一出路是 `clear_session_queue`（等于丢消息）。

**老大裁定（2026-10-11 13:10）**：

> 「那加个方法去触发队列的继续」

⇒ **第三刀 `resume_session_queue`**，与 UI 的「继续」按钮等价。⇒ **本档上方的「派发照旧」按此修订为：停 = 队列保留 + 派发冻结；恢复由 `resume_session_queue`（或用户点「继续」）触发。**

**实现要点（第三刀）**：新增渲染端 `resumePendingSessionDispatch(sessionId)`（**只解冻、不派发**，与 `pausePendingSessionDispatch` 对称）—— **不能只调 `dispatchNextQueuedMessageForSession`**：那条路在「有活跃 run」时会**直接 return 且不解冻**（`use-chat-actions.ts:872-874`）。先解冻再派发，有活跃 run 时本轮结束（loop_end 的 `dispatch(…, false)`）就能自动续上。**未新增渲染端状态、未改 DB。**

## 三、落点勘察（只读）

### 3.1 PM 现有工具面 —— 确实一个都没有

**全局会话（PM）当前可用的工具**：

| 来源 | 工具 |
|---|---|
| `Tools/Providers/ProjectToolsProvider.cs` | `list_projects` / `get_project_details` / `create_project` / `create_session` / `send_session_message` / `update_session_follow_up` |
| `Tools/Providers/GlobalTaskToolsProvider.cs` | `list_global_tasks` / `create_global_task` / `update_global_task` / `list_global_dispatches` / `send_work_request` / `update_dispatch` |
| `Tools/Providers/GlobalDispatchReplyToolProvider.cs` | `reply_global_dispatch` |

⇒ **没有任何「看队列 / 撤队列 / 停运行」的工具**。PM 对项目会话只有**投递**能力（`send_session_message` / `send_work_request`），**没有观测与干预**能力。

**作用域**：`ToolVisibilityScopes.GlobalSideOnly = ["global:*@*"]`（`send_session_message` / `update_session_follow_up` / `create_project` 走这条）。

### 3.2 队列在哪 —— **渲染端内存态**（结构性根因）

`src/renderer/src/hooks/use-chat-actions.ts:726`：

```ts
const _pendingMessages = new Map<string, PendingSessionMessageItem[]>()
```

**模块级 Map，活在渲染进程内存里** —— **不落库、无 IPC 出口**。

导出的读写 API（**全在渲染端**）：

| API | 行 | 作用 |
|---|---|---|
| `getPendingSessionMessages(sessionId)` | `:772` | 读队列 |
| `getPendingSessionMessageCountForSession(sessionId)` | `:306` | 读条数 |
| `hasPendingSessionMessagesForSession(sessionId)` | `:950` | 有无排队 |
| `removePendingSessionMessage(sessionId, messageId)` | `:847` | 删单条 |
| `clearPendingSessionMessages(sessionId)` | `:297` | 清空（返回清掉几条） |
| `pausePendingSessionDispatch(sessionId)` | `:840` | 暂停派发 |
| `dispatchNextQueuedMessageForSession(sessionId)` | `:867` | 恢复派发 |

⇒ **PM 跑在 worker（C#）侧，物理上看不到这个 Map。** 这不是「忘了做工具」，是**数据不在它那一边** —— 必须过桥。

### 3.3 运行态在哪 —— 两处，语义还不一样

| 入口 | 位置 | 语义 |
|---|---|---|
| `hasActiveSessionRunForSession(sessionId)` | `use-chat-actions.ts:943` | **准确**：`_startingSessionSends` ∪ `chatStore.streamingMessages[sid]` ∪ `agentStore.runningSessions[sid] === 'running' \| 'retrying'` |
| `useChatStore.getState().cancelStream(sessionId?)` | `stores/chat-store/index.ts:541` | **真停运行**，且**支持指定会话** ✅ |
| `abortSession(sessionId)` / `stopSessionStreaming(sessionId)` | `use-chat-actions.ts:292 / :956` | ⚠️ **只清 UI 流式状态**（`setStreamingMessageId(sid, null)`），**不真停** |
| `bridge.requestStopAgent(runId)` | `lib/ipc/agent-bridge.ts:93`（`agent/request-stop`） | worker 侧按 **runId** 停 —— **全仓零调用点（死代码）** |
| `AgentRuntimeRunState.Cancel(reason)` / `RequestStop(reason)` | `AgentRuntimeRunState.cs` | worker 侧每 run 一份，含**运行级** `_queuedMessages`（与渲染端队列**不是一回事**） |

⚠️ **两个坑**：

1. **别拿 `abortSession` 当「停止」** —— 它只把 UI 的流式指示清掉，worker 还在跑。真停要 `cancelStream`。
2. **worker 的运行态按 `runId` 索引**，PM 手里**没有**目标会话当前的 `runId` ⇒ 就算把 `requestStopAgent` 接上也**够不着**；而 `cancelStream(sessionId)` 是**按会话**的，反而对得上 PM 的视角。

**现成先例**：`use-channel-auto-reply.ts:448` 已经在程序里直接调 `useChatStore.getState().cancelStream(payload.sessionId)` —— **「由代码按会话停某一轮」这条路已经跑通**。

### 3.4 现成的桥 —— 反向请求

`send_session_message` 就是走**反向请求**回渲染端，由渲染端用正常 `sendMessage` 投递：

- worker：`AgentRuntimeProjectExecutor.SendSessionMessageAsync` → `AgentRuntimeReverseRequests`
- 渲染端处理器：`src/renderer/src/lib/tools/project-send-message.ts`

⇒ **三个缺口全部可以复用这条桥**：worker 发反向请求 → 渲染端读/改自己的内存态 → 回结果。**不必把队列搬进 DB。**

### 3.5 顺带一个不准的点：`get_project_details` 的「活跃」是启发式

`AgentRuntimeProjectExecutor.GetProjectDetailsAsync`：会话取最近 20 条，`activeSessionId` = `updated_at` 在 **1 小时内**的最近一条。

⇒ **「活跃」≠「在跑」**：一小时没动但在跑的判成不活跃；刚更新但早跑完的判成活跃。**PM 现在看到的运行信息是猜的。**
