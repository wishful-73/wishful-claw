> 登记：2026-11-02 08:53（老大口述）+ 09:01 补充参数要求
> 归属：**v3-iter-6 刀 8** —— 老大 09:05 裁定「这个也是本迭代做」
> 类型：功能新增（新工具 + 新 DB 端点，零 schema 改动）

## 一、老大原话

第一轮（08:53）：

> 「我们讨论一个需求，如果成立的话，需要再登记一个。当前 agent 在执行过程中会对上下文进行压缩，所以在多轮执行后，之前用户说过的话，特别是比如昨天说的这种，可能 agent 就不知道了。所以想提供一个工具，agent 可以去查看用户发送过的历史消息，以及它回复的总结看是否需要」

澄清（08:55）：

> 「不需要跨会话，就当前会话的，也不需要什么 query 之类的，我要的是用户发送的消息，现在我的目标其实是项目下的会话用户少参与，基本都是跟全局 PM 沟通，但是现在的情况是全局 PM 忘事。这点是最麻烦的，我希望能通过全局任务 + 用户的发言，能让全局 PM 追溯消息」

补充参数（09:01）：

> 「我需要你参数增加一个日期，其实就单日用户发言来说其实并不多」

⇒ 三条被明确否掉的方向：**不跨会话**、**不做关键词搜索**、**不做 query 语义检索**。要的就是「把用户在**这个会话**里说过的话按**日期**列出来」。

## 二、要解决的痛点

工作模式是「全局 PM 统管、项目会话少参与」。全局会话跑得越久，上下文压缩越多次，**用户早期说过的话就彻底离开上下文**。PM 于是重复问已经定过的事、忘掉已经拍过的板。

现在没有任何工具能把它捞回来：`SessionRestoreTools.RestoreFromDb` 只在**懒重建**时用（`AgentLoop.cs:98-101`），重建的是 worker 自己的权威对话，模型不能主动触发。

## 三、现状（读码事实，带行号）

### 3.1 数据是现成的，谓词也是现成的

`src/runtime/WishfulClaw.Infrastructure/Db/DbMessageToolsQueries.cs`：

| 项 | 行号 | 说明 |
|---|---|---|
| `RealUserTurnPredicate` | `:34-35` | `role = 'user' AND (meta IS NULL OR meta NOT LIKE '%compactSummary%')` —— **已经排除压缩摘要卡**，只认真正的用户发言。S-276 引入，实测把虚高的 71 修正到 51 |

⇒ 谓词直接复用，**不用新写过滤逻辑**。

### 3.2 但 `ListByTurns` 不能直接当工具用

它是**前端分页加载**的接口：返回一整轮的所有消息，含 assistant 正文、工具调用块、思考流。单轮体量可能上万 token。塞进 agent 上下文是自杀。

⇒ 需要一个**精简投影**的新端点，只回 user 侧。

### 3.3 sessionId 在服务端拿得到（关键安全线）

`src/runtime/WishfulClaw.Agent/AgentLoop.cs:69`：

```csharp
var sessionId = state.SessionId ?? "";
```

sessionId 来自 **run state**，是服务端已知的。对比工具侧的现有惯例 —— `ProjectToolsProvider.cs:91/145/161/178/196/215` 的 `sessionId` **全部是模型传参**，`AgentRuntimeContextCompressionTools.cs:36` 也是 `JsonHelpers.GetString(parameters, "sessionId")`。

⇒ **本工具不能沿用「模型传 sessionId」这个惯例**。理由见 §4.2。

### 3.4 时区：Db 层没有任何日期解析先例

全仓 `src/runtime/WishfulClaw.Infrastructure/Db/*.cs` 搜 `ToLocalTime|yyyy-MM-dd|ParseExact` —— **零命中**。

`messages.created_at` 是 **unix 毫秒**（`ListByTurns` 用 `GetInt64` + `SqliteParameter("@before", ...)` 直传）。

⇒ 「某一天」必须在这里自己换算，且**必须按用户本地时区**算，不能用 UTC。这是本条最容易错的地方：UTC 切日会让「北京时间早上 7 点说的话」落到前一天。

### 3.5 零 schema 改动

`messages` 表已有 `session_id` / `role` / `created_at` / `content` / `meta`，全部够用。**不加列、不加索引**（`session_id + created_at` 是现有高频查询路径，已有索引）。

## 四、设计

### 4.1 工具：`list_user_messages`

```
参数：
  date   可选，string，"YYYY-MM-DD"，按用户本地时区切单日
  limit  可选，number，默认 50，clamp 1-200

不传 date  ⇒ 返回最近 limit 条用户消息（跨日，倒序取再正序排）
传 date    ⇒ 返回那一天的全部用户消息（受 limit 上限约束）
```

**为什么砍掉 `beforeCreatedAt`**：既然按日切，翻页靠「换 date」，不需要第二套游标机制。两套并存只会让模型乱用。

**返回形态**（精简，只 user 侧）：

```json
{
  "messages": [
    {
      "createdAt": 1762000000000,
      "text": "登录页那个按钮改成主色",
      "attachmentSummary": "图片 ×1"
    }
  ],
  "truncated": false,
  "totalOnDate": 7
}
```

- `text`：正文原文，**不截断**（用户发言通常短；真要长文本那也是需求本身）
- `attachmentSummary`：`null` / `"图片 ×1"` / `"粘贴 400 字"` / `"图片 ×1，粘贴 400 字"`。**必须有** —— 否则 PM 看到「你看看这个」完全不知道在说什么
- `truncated` + `totalOnDate`：撞到 limit 时明确告知，让模型自己缩窄日期或加大 limit

### 4.2 三条硬边界（写死，不可放宽）

| # | 边界 | 理由 |
|---|---|---|
| 1 | **sessionId 由服务端从 run state 注入，模型不能传** | 让模型传 sessionId = 把「能不能读别的会话」交给模型判断。全局 PM 一旦传了项目会话 id，就绕开了「只当前会话」的约定。这是本条唯一的安全边界 |
| 2 | **只返回 `role='user'`** | 老大原话「我要的是用户发送的消息」。assistant 回复本来就该由 agent 自己的记忆/摘要承担，混进来会让工具返回体量翻倍且噪声大 |
| 3 | **只读，无任何写操作** | 纯查询，不涉及状态变更 |

**边界 1 的实施前提**：需要确认 `ToolDispatchRouter` → executor 层能拿到 `state.SessionId`。`AgentRuntimeTools.HasActiveSessionRun(sessionId)` 说明存在 active run 注册表，路径应该通。**实施第一步先验证这一点**，不通就停下来报告，不要退回「模型传参」方案。

### 4.3 可见性：全局 + 项目会话都给

| 会话类型 | 给不给 | 理由 |
|---|---|---|
| 全局会话（PM） | **给** | 老大的主痛点 |
| 项目会话 | **给** | 压缩是无差别的，项目会话同样会忘事。工具成本一模一样，没有理由只给一边 |

`ToolVisibilityScopes` 现有集合里，`GlobalSideAndWorkRuns` = `["global:*@*", "*:cowork@*"]`（`ToolVisibilityScopes.cs:39`）**正好覆盖两边**，直接用，不新开 scope。

⚠️ 但这意味着工具会同时出现在全局和项目会话的工具表里 —— 如果后续发现项目会话不需要，改一个 scope 常量即可，不影响实现。

## 五、验收判据

1. 全局会话里问「我昨天说过什么」⇒ PM 调 `list_user_messages` 且**不传 date** 能拿到最近发言；传昨天日期能拿到昨天全部发言。
2. **时区验证（重点）**：北京时间 `2026-11-02 07:30` 发一条，传 `date="2026-11-02"` ⇒ **必须能查到**。若按 UTC 切会落到 `11-01`，此时判据红。
3. 压缩过的长会话：翻到压缩点之前的用户发言，工具**能拿到**（这正是本需求存在的意义）。
4. 带图片的消息 ⇒ `attachmentSummary` 显示 `"图片 ×1"`，不是 `null`。
5. 压缩摘要卡**不出现在结果里**（复用 `RealUserTurnPredicate`，S-276 已验证）。
6. **反向验证**：把 sessionId 注入改成「模型传参」⇒ 应当能构造出「全局 PM 读到项目会话的用户消息」，此时判据必须红。
7. 单日发言超过 limit ⇒ `truncated=true` 且 `totalOnDate` 是真实总数。

## 六、风险

- **`ListByTurns` 被误改**：新端点是**并列新增**，绝不能改 `ListByTurns` 的参数或返回形态 —— 前端历史加载依赖它，改了会连带 S-276 的分页逻辑。
- **时区换算写错方向**：`DateTime.SpecifyKind(parsed, DateTimeKind.Local).ToUniversalTime().ToUnixTimeMilliseconds()` 是正确写法；写成 `parsed.ToUniversalTime()` 会因为 `DateTime.ParseExact` 默认 `Kind=Unspecified` 而按机器本地解释两次，出现偏移。验收判据 2 能兜住。
- **`date` 格式不校验**：模型可能传 `2026/11/02` 或 `11-02`。必须 `TryParseExact("yyyy-MM-dd")`，失败返回明确错误信息让模型自己纠正，**不要静默当成今天**。
- **返回体量**：单日 200 条上限已够。若某天真的爆量，`truncated` 会告知，模型自己缩。
- **与 S-300 的关系**：老大提到「通过**全局任务 + 用户的发言**追溯」。**派发明细不用新做** —— 09:05 老大原话「任务派发明细，本身就有对应的查询，这个不需要去做」，核对属实：`list_global_dispatches`（`GlobalTaskToolsProvider.cs:85`）早已存在，且 **`projectId` 可选筛选全链路都已实现**：工具参数 `:93` → executor 拷贝 `AgentRuntimeGlobalTaskExecutor.cs:171` → DB 真过滤 `DbGlobalTaskDispatchTools.cs:43-47`（`AND project_id = @pid`）。查单个项目、查全部都能用。本条**不含**任何派发明细改动。

### 8.2 边界 1 的验证结论

需求 §4.2 要求「实施第一步先验证 `state.SessionId` 能拿到，不通就停下来」。**结论：通。**

`AgentRuntimeTools.ExecuteRunAsync` 把 run state 的 `SessionId` 注入 `state.Parameters`，executor 直接读该参数，`ToolDispatchRouter` 分支不读模型入参。测试 `RunExecutorBoundarySuite` 反向验证：模型在入参里传 `sessionId="session-other"` ⇒ 读不到另一会话的私货，仍读 run 参数那个会话。

### 8.3 时区（判据 2）

`date` 用 `TryParseExact("yyyy-MM-dd")` 解析后**按本地时区**取当日 `[00:00, 24:00)` 的毫秒区间。测试里造了一条「本地 07:30」的消息并按当天日期查，能查到；同一套数据若按 UTC 切日会落到前一天 —— 该反向判据已在 `RunDateSuite` 钉住（本地偏移为正时，昨天必须查不到它）。
