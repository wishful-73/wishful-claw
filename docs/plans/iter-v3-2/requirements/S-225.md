# S-225：聊天窗时间轴渲染详细度分级（3 档 · 全局设置 + 聊天窗快捷入口）

## 1. 原话 / 来源

> 2026-10-26 老大（首轮，5 档）：

> 我们聊天窗渲染组件，需要分等级，这个是参考 OpenCode 的桌面端。1. 纯文本，只看消息，类似我们执行结束后折叠，默认执行中也折叠，只看外层总消息。2. 安静型。3. 紧凑型。4. 详情。5. 一切。

> 2026-10-26 老大（订正，补三张截图）：

> 我们不需要这么多颗粒细化。估计我们 3 档就行。

> 2026-10-26 09:38 老大（作用域）：

> 这个是全局的，但是可以在聊天窗找地方调整显示方式，比如放到右侧悬浮块里。

性质：**软件侧渲染层重构**，无数据面改动（全局设置除外）。

## 2. 目标

把散落在各组件里的展开 / 折叠策略**收敛成一个可调的单一旋钮**（三档渲染详细度）——
不再是「工具卡自己一套、思考块自己一套、子 Agent 卡自己一套」。

三档共用一个副标题（OpenCode 原文口径）：「选择时间轴上显示的活动量。**消息始终可见**。」
⇒ 正文永远显示，档位只控「活动 / 过程」这一层，不控消息本身。

## 3. 现状（2026-10-26 实查）

全仓**没有**任何渲染密度 / 详细度设置项 —— `compactMode` / `density` / `timelineDetail` /
`verbosity` / `showThinking` 在 `src/renderer/src` 下均 **0 命中**。

现有机制是分散且各自为政的：工具 run 分组、单个工具卡输出、思考块、子 Agent 卡、文件变更卡、
压缩卡**各自决定**展开态，互相不知道对方。七处具体位置见 §6。

⇒ 本需求本质是**关系统一**，不是新增一套渲染器。工作量主要在关系统一，不在画滑块。

## 4. 三档定义

### 4.1 OpenCode 原文（截图，作为口径基线）

| OpenCode 档 | 文案 |
|---|---|
| 安静 | 对已使用的编辑和子代理进行分组。隐藏其他活动。 |
| 紧凑型 | 隐藏详细信息，将工具分组，并折叠思考内容。 |
| 详情 | 展开 shell 输出和编辑。单独显示子代理，并在已使用中对其他活动进行分组。 |

### 4.2 我们的 3 档（建议，待老大点头）

| 档 | 名称 | 看到什么 | 来源 |
|---|---|---|---|
| 1 | 纯文本 | 只看消息。执行中与执行结束都折叠，只留外层总消息 | 老大首轮原话 |
| 2 | 紧凑（默认） | 隐藏详细信息，工具分组，折叠思考内容 | OpenCode「紧凑型」原文 |
| 3 | 详情 | 展开 shell 输出与编辑，单独显示子代理，余下活动分组 | OpenCode「详情」原文 |

**建议丢掉首轮的「安静」和「一切」**，理由：安静与紧凑边界模糊（都在「分组 + 隐藏其他」，
只差折叠思考这一条）；「一切」≈ 现在的默认行为（全展开），作为档位没有增益。
若老大要的是「安静」而非「纯文本」当第 1 档，一句话切换即可。

## 5. 两个入口

1. **设置页**：主落点。3 刻度滑块 + 档位说明 + 高级区（截图形态：滑块下方随档位显示一句说明，
   再下方「高级」区放细化开关，例如「Changed files —— List the files each turn changed when it finishes」）。
2. **聊天窗内快捷调整**（老大原话「可以在聊天窗找地方调整显示方式，比如放到右侧悬浮块里」）：
   两处改的是**同一个全局值**，聊天窗侧只是快捷通道。

**聊天窗入口落点待定 —— 实查结果**：右侧没有空槽位可用。现有的是
`components/chat/MessageList/AssistantReplyRail.tsx`（助手回复**定位导轨**：竖条 marker + 悬停预览 +
点击跳转，`items` 为空时不渲染）。它语义是导航不是设置，**不建议把档位开关塞进这条导轨**。候选：

- **甲**：导轨外侧 / 上方加一个独立齿轮钮，点开是紧凑的 3 档选择器（同层但不混语义）
- **乙**：新起一个聊天窗右侧悬浮块（类似 S-221 官网那套悬浮导航思路，但只放这一个入口）
- **丙**：输入框工具条里一个图标（不进右侧）

## 6. 阶段一勘察结论（2026-10-26）

七个决策点全部实查定位，详见 [plan-s225/plan.md](../plan-s225/plan.md) §二：

| # | 渲染单元 | 位置 | 现有默认 |
|---|---|---|---|
| 1 | 工具 run 分组折叠 | `execution-outline.ts:314-315` | `ordinary>0 && active==0` |
| 2 | 工具可见性分级 | `execution-outline.ts:222-233` | ordinary / force / hidden 三级 |
| 3 | 单个工具卡输出区 | `ToolCallCard/index.tsx:75-77` | `forceOpen \|\| isLiveCommandTool \|\| hasVisualOutput` |
| 4 | 思考块 | `ThinkingBlock.tsx:66` | `!isThinking && hasThinkingContent` |
| 5 | 子 Agent 卡 | `SubAgentCard.tsx:310,314-324` | 初始 `!isBackground`，跑完自动折叠 |
| 6 | 文件变更卡 | `FileChangeCard.tsx:34` | `useState(!forceOpen)` |
| 7 | 压缩卡 | `ContextCompressionMessage.tsx:79` | `useState(false)` |

**两个关键结论**：

1. `AssistantMessage/index.tsx:299-327` 的 `toolRunCollapseState` 已是
   「用户覆盖 Map ?? 档位派生默认值」结构 —— 实施主线是**推广这个范式**到另外 6 个单元，
   不是发明新机制。
2. #3~#7 全是 `useState(初值)`，切档不会让已挂载卡片重新折叠。必须用**受控派生 hook**
   解决（否掉「塞 key 强制重挂载」与「useEffect 监听档位」两个做法，理由见 plan §2.3）。

## 7. 三条建议（不反对就按这个做）

| # | 问题 | 建议 | 理由 |
|---|---|---|---|
| 1 | 第 1 档叫「纯文本」还是「安静」 | **纯文本** | 老大首轮原话；OpenCode 的「安静」写的是「隐藏其他活动」，与「只看消息」不是一回事 |
| 2 | 默认档 | **紧凑**（= 当前线上行为） | 升级观感零变化 |
| 3 | 聊天窗入口 | **甲：导轨上方独立齿轮钮** | 丙在输入框工具条 —— 老大 10-26 上午刚说输入框上方东西太多；乙与 S-221 官网悬浮块概念混 |

「高级」细化开关区**不做** —— 老大明确「不需要这么多颗粒细化」。

## 8. 已定，不再讨论

- 作用域：**全局设置**（2026-10-26 老大拍板），不是会话级，不进 DB 的会话表
- 入口数量：设置页 + 聊天窗快捷通道，两处同一份全局值
- **正文消息三档全部始终显示**（OpenCode「消息始终可见」口径）
- **错误 / 待审批（`attention` 类）三档强制展开** —— 安全底线，档位不得藏错误
- **压缩卡不参与档位** —— 它是分隔卡不是活动，三档一致恒折叠

## 10. 风险

1. **现有展开策略分散在 7 个组件**，靠阶段二产出的「档位 × 渲染单元」矩阵统一，否则会写成七套 if。
2. 与 S-210 / S-215 的收尾口径（按事实显示收尾原因）**不能打架**：档位只控过程层，不改收尾文案与耗时统计。
3. 设置项持久化要走既有 settings store，注意与 dev 实例数据目录隔离（S-223）一致。
4. `buildToolExecutionOutline` 是 memo 依赖链上游（`AssistantMessage/index.tsx:252`），
   加 `density` 进 deps 后要防止每次渲染重建 outline。
5. **单文件 500 行硬上限**：`ToolCallCard/index.tsx` 已 565 行，改动须带豁免头。

## 11. 范围外

不改执行逻辑；不动数据面与 DB（除第 3 条定为会话级外）；
不改折叠块「按事实显示收尾原因」的既有口径（S-210 / S-215）；
不动输出块内部的长度截断阈值（`output-blocks/text-output.tsx` 的 16 行 / 500 字符 / 40 行）。
