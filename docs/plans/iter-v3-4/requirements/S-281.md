# S-281 · 主窗口根容器挂了一层全窗口 `backdrop-blur-xl`，而窗口不透明 —— 纯烧管线，零视觉效果

> 归属：**移交 v3-iter-5**（不影响功能，不阻塞收尾）。
> 登记 2026-10-30 11:05。
> 来源：2026-10-30 排查渲染进程内存期间顺带发现，非老大提出。
> 定性依据：读码 + 进程实测（本次排查全部为实测数据，见 §四）。

## 一、现象

`src/renderer/src/main.tsx:196` 与 `:302` 两个根容器：

```tsx
<div className="flex h-screen w-screen flex-col overflow-hidden rounded-2xl border border-border bg-background/95 backdrop-blur-xl">
```

`backdrop-blur-xl` = 24px 高斯模糊，作用范围是**整个窗口**（`h-screen w-screen`）。

但主窗口**不是透明窗口**：

```
src/main/quick-launcher/window.ts:146   transparent: true,        ← 快捷启动小窗
src/main/clipboard-enhancer.ts:588      transparent: true,        ← 剪贴板小窗
```

全仓只有这两处 `transparent: true`，**主窗口创建处没有任何 `transparent` / `vibrancy` / `backgroundMaterial`**，即默认不透明 + 不透明背景色。

## 二、根因

窗口不透明 ⇒ 模糊采样的「背后」是窗口自身的背景色，不是桌面壁纸或其它窗口内容 ⇒ **模糊结果与不模糊完全一致，肉眼零差别**。

这段写法应当是早期照抄「圆角透明窗」样式时带进来的：`rounded-2xl` 是给透明窗口做圆角的，配合 `backdrop-blur` 才有意义；主窗口既然不透明，这两个 class 只是装饰性残留。

## 三、代价

Chromium 只要看到 `backdrop-filter: blur(24px)` 就会建立模糊管线，与「背后到底有没有东西」无关：

| 项 | 影响 |
|---|---|
| 每帧 | 全屏区域需要额外一次模糊 pass（窗口 1280×800 @150% ≈ 190 万像素） |
| 图层 | 根容器被迫成为独立合成层，内容变化时该层整体重绘 |
| 与流式输出叠加 | 长文本流式期间每帧都在重算整屏模糊 —— 这是 S-256 / S-274 那类卡顿问题的放大器 |

**注意：本条不是本次内存暴涨的原因**（内存已由对照实验定性为 dev 加载方式，见 §四），也不该拿它去解释内存。它吃的是 CPU/GPU，不是内存。

## 四、排查留档（供后续参考，不必重做）

2026-10-30 针对渲染进程 2.3 GB 做过对照实验，结论与本条无关，但有参考价值：

| 实例 | renderer WS | 条件 |
|---|---|---|
| dev（vite dev server） | 1256 MB | 启动 5 分钟即到位，之后横盘 |
| preview（构建产物，同代码同数据） | 240 MB | 启动 45 秒 |
| 生产 1.0.3（打包 asar） | 337 MB | 运行 17 小时 |

差异全在 V8 堆外（`jsHeapUsed` 三档都只有 100 MB 上下），来源是 vite dev 要加载 78.5 MB 未压缩预构建依赖 + 871 个未压缩源码模块，而生产走 45 MB minify bundle。**dev 的内存数值不具备性能判据价值**，验收应走 `npx electron-vite preview --skipBuild`。

附带排除的两条：CDP `jsEventListeners` 会在 335～10985 之间大幅波动（不是累积泄漏），我们自己的 add/remove 账本净存活稳定在 263；`Memory.startSampling`（native 分配栈）在 Windows 上返回空 profile，此路不通。

## 五、修法

**A（推荐）** 删掉两处根容器的 `backdrop-blur-xl`，`bg-background/95` 一并改 `bg-background`（95% 半透明在不透明窗口上同样是白算）。

**B** 若将来确实要做窗口毛玻璃（Win11 Mica / Acrylic），则应走 `backgroundMaterial: 'mica'` 主进程方案，而不是靠 DOM 的 `backdrop-filter` —— 后者在 Electron 里拿不到桌面内容。

## 六、附带核查：全仓 20 处 `backdrop-blur` 要逐一看

grep 结果里除根容器外，其余都在弹层 / 浮层（`ModelSettingsPopover`、`SubAgentCard`、`ChangeReviewSheet`、`AssistantReplyRail`、`queued-messages-panel` 等）。**这些多数是需要的**（浮层背后确实有内容可透），但每一处都值得确认一次「背后是真有东西，还是同样压在不透明底上」。

`virtual-list-content.tsx:178/302`（滚动到底部按钮）与 `sandbox-elevation-chip.tsx:54` 这类小面积元素，模糊成本低、视觉收益存疑，可一并评估。

## 七、验收

1. 改前 / 改后各截一张主窗口图，**肉眼应无差别**（这是本条的判据，不是「看起来更好」）。
2. dev 下观察 `renderer counts` 的 `layouts` / `styleRecalc` 增速是否下降（需临时加回观测，不必进提交）。
3. 长文本流式期间主观流畅度对照。

## 八、不做的事

- 不动那两个透明小窗（`quick-launcher` / `clipboard-enhancer`）的任何样式 —— 它们的 `backdrop-blur` 是真需要的。
- 不引入 `backgroundMaterial` 之类的主进程毛玻璃方案，除非老大明确要做视觉升级。
