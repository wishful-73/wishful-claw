## 二、现象

两条独立的问题，同属「辅助通道」这一个主题：

1. **persona 生成在后端自建了一条 HTTP 链。** `WishfulClaw.Persona` 里躺着 `PersonaGenerator.cs`（100 行私有 HTTP 调用 + `GenerateAsync` + `ParseDraftResponse` / `ExtractJsonFromText`）与 `PersonaGenerationPrompt.cs`（system prompt 拼装），硬编码 `max_tokens 4096` / `temperature 0.8`。而**同一个原理**的提示词优化（`lib/prompt-optimizer/optimizer.ts`）是**纯 renderer** 单次 `provider/complete` 调用。同一个「单次辅助补全」，两套实现、两个归属地。

2. **辅助通道一条头链都没有。** renderer 侧手拼载荷：

   ```ts
   // use-prompt-optimizer.ts（改前）
   const providerConfig = { type, apiKey, baseUrl, model, providerId, maxTokens: 4096, temperature: 0.7, systemPrompt: '' }
   ```

   `optimizer.ts` 再手拼一次，只取 `providerId / type / baseUrl / apiKey` 四要素发给 `provider/complete`；后端 `ProviderCompletionService.BuildRequest` 只补一个 `Authorization`。

   ⇒ 用户在设置里配的 **User-Agent**、**自定义 `requestOverrides` 头**、**`organization` / `project`**、**opencode-go 的 `x-opencode-session`**，走提示词优化 / 人格生成时**全部失效** —— 而同一 provider 走正常聊天时是生效的。

## 四、根因

两条：

1. **归属错位。** persona 生成是「一次辅助补全请求」，不是「人格领域能力」。把它放在 `WishfulClaw.Persona` 里，等于给一个纯 HTTP 调用套了领域项目的壳 —— 于是解析、提示词、超时、重试全得在 C# 侧再造一遍，与 renderer 的提示词优化天然分叉。

2. **载荷构造没有单点。** 主链早在 S-89 就立了 `buildProviderPayload`（`lib/agent/provider-payload.ts`）作为「发给 Worker 的 provider 元素」唯一构造点，文件头注释写明「every field the Worker reads had to be remembered at each one — and it was not」。**辅助通道这两个调用点没被那次收敛覆盖**：`use-prompt-optimizer.ts` 与 `optimizer.ts` 各自手拼，字段自然丢。

## 五、修复方向

**A. 头链（09:07 第 1 条）**

- 新建 `Agent/ProviderHttpHeaders.cs`：`ApplyOpenAiChat(request, provider, sessionId)`（UA + `organization`/`project` + `requestOverrides` + opencode-go 门禁）、`ApplyAnthropic(request, provider)`（UA + `requestOverrides`），语义对齐主链。
- `ProviderCompletionService.BuildRequest` 两个协议分支各调一次；鉴权头（Bearer / `x-api-key` / `anthropic-version`）留在调用点 —— 那是鉴权，不是 provider 配置。
- **头链数据来源**：`ResolveHeaderProvider` 优先用 renderer 载荷，但**仅当载荷的 `providerId` 等于解析器实际选中的 provider**；不一致（configured / fallback / global 三档）则读 `ProviderStore.GetProviderJson(resolved.ProviderId)`。否则会出现「头链按 A 的配置发、请求打到 B」的错配。

**B. persona 退出后端（08:54 / 08:55）**

- 删 `PersonaGenerator.cs` + `PersonaGenerationPrompt.cs` 整文件；`PersonaModule` 摘掉 `persona/generate` 注册。
- renderer 新建 `lib/persona/generator.ts`：system prompt（含参考人格段）、tolerant JSON 提取、`parseDraft`，调 `provider/complete`（`requestKind: 'persona'`）。**提示词文本与提取逻辑从 C# 原样移植**，不改行为。
- 参考人格的 4 段 md 由 renderer 调 `persona/get` 取（原本在 C# 侧读 `PersonaStore`）。
- `persona-store.generatePersona` 签名由 `(prompt, provider: Record<string, unknown>, ...)` 改为 `(prompt, provider: AIProvider, modelId, ...)`，内部走 `buildProviderPayload`。

**C. 载荷单点**

- `use-prompt-optimizer.ts`：删手拼的 `providerConfig`，改 `buildProviderPayload(activeProvider, modelId, useSettingsStore.getState())`。
- `optimizer.ts`：`optimizePrompt` 第二参由 `ProviderConfig` 改为 `Record<string, unknown>`（`buildProviderPayload` 的产物），`completeOnce` 整包直传。

## 六、代价与取舍

- **persona 生成改走 `provider/complete`** ⇒ 白拿重试退避（10 次，429/408/5xx）、`AuxiliaryUsageLog` 用量记录、头链。代价：解析与提示词搬到 TS 侧 —— 与提示词优化同构，可接受。
- **`providerRole` 的处理两路不同**：persona 路径**不传** `providerRole: 'global'`（否则 `TryResolveExplicit` 直接 `return false`，用户在弹窗选的 provider 被忽略 —— S-168 已踩过）；优化器路径**保留** `providerRole: 'global'`（它有意让配置的 `promptOptimizerProviderId` 优先）。两条语义都在注释里写明。
- **`ResolveHeaderProvider` 的 id 匹配**是必要的保守：不匹配就读文件。代价是多一次文件读取（仅 configured / fallback / global 三档命中），换来「头链永远对得上实际调用的 provider」。
- **`AuxiliarySessionId` 常量**（`"wishful-claw-auxiliary"`）与 `ProviderTestService.ConnectionTestSessionId` 并列 —— 辅助调用不是会话，但上游只要求非空稳定值。

## 七、刻意不做

- **主链 5 份头链收敛 → S-172**。老大 09:07 原话「主链流式写的 5 份记录成下一个需求」。主链改动面大（4 文件 + 3 份 debug 版 + 各协议差异），混进本刀无法单独验证。
- **不动 `ProviderCompletionResolver` 四档语义**（`explicit → configured → fallback → global`）。S-168 已确认解析顺序是对的，问题在传参。
- **不给辅助通道加 `request_debug` 事件**。辅助通道不发该事件，`ProviderHttpHeaders` 因此**不带 debug 变体**；主链收敛（S-172）时各 provider 自带 debug 版。
- **不动 `ProviderTestService`**。它是连接测试，语义是「验证配置可用」，用固定 session id，且有 4 条断言钉着。
- **不动视频工具的 UA 装配**（`SeedanceVideoTools.cs` / `XaiVideoTools.cs`）。走视频端点、非 chat 协议，是否并入留给 S-172 一并判断。
