# S-262 · 400 请求级拒绝 —— 把失败变成 agent 的观察，而不是会话的死刑

> 归属：v3-iter-4（产品 1.0.4）｜登记 2026-10-29 08:24
> 来源：老大 2026-10-29 08:15 / 08:18 / 08:20 三次口述。
> 与 **S-261 / S-246 / S-236 / S-237** 同一条线，本条是**通用兜底**（S-261 是图像专项）。

## 一、老大的原话（三句，逐句都是约束）

> 「我的想法是不只是图片 只要是 400 的请求，在收到以后，就把之前的请求文调整一下，然后告知报错了」
>
> 「我的意思是请求 400 了，说明请求文有问题，能收集并且告知 agent 上一步操作 400 了，但是又不会直接卡死直接导致 agent 中断执行」
>
> 「根据你的推荐 开始推进」

三句拆成三条硬要求：

| # | 要求 | 反面（不许这样） |
|---|---|---|
| 1 | **收集** —— 400 的报文要留得住 | 只记一个 `HTTP 400` 什么都不剩 |
| 2 | **告知 agent** —— 让它知道「我上一步操作被拒了」 | 静默重试，模型全程不知情 |
| 3 | **不中断** —— run 继续跑，别把整个会话钉死 | 一个 400 直接终止 run，用户现场报废 |

## 二、与既有四条需求的关系（下轮别当重复需求剔掉）

| 需求 | 管什么 | 本条的差别 |
|---|---|---|
| **S-237**（2026-10-27） | 把 400 从重试里摘出来（`IsRetryableStatus = 429 \|\| >=500`） | 本条的「重试」**不是重发同一条请求**，是改完请求文再发，且额度与指纹双重设限（见 §4.3） |
| **S-246 / S-236** | 图像格式闸门 + 剥图自愈 | 只覆盖 image 块 |
| **S-261**（刀 1b） | 图像 400 的 marker 补齐 + url 形态闸门 | 仍然只覆盖图；本条的 catch 分支排在它**之后**做兜底 |
| **工具配对修复** | 缺 tool_result 造成的 400 | 只覆盖配对 |

**本条的定位**：前三条都认不出、或认出了但额度用尽时，**最后一道「不许静默死」的保险**。它不抢前三条的活。

## 三、勘察结论（2026-10-29，读码定案）

### 3.1 现有自愈骨架已经长成，形状可以直接复用

`AgentLoop.cs:375-493` 是一个 `while (true)` 包着的 catch 链，**本来就是「400 之后改请求文再发」的成熟路子**，已有两个分支在里面：

| 分支 | 位置 | 动作 |
|---|---|---|
| 上下文超限 | `:387-429` | 错误驱动压缩，然后重发 |
| 工具配对错 | `:430-452` | `sessionConv.RepairToolPairing()` 补缺失结果，重发 |
| 图像不支持 | `:453-492` | 剥图 + 记住 + emit 事件，重发 |

第四个分支（本条）挂在链尾，判据**绝不会抢前面三条**（C# `catch ... when` 按书写顺序匹配，前面命中就进不去）。

### 3.2 「告知模型」也有三份现成先例

| 先例 | 位置 | 形态 |
|---|---|---|
| `InjectSessionTodo` | `AgentLoop.SessionTodo.cs` | 临时副本注入 |
| `InjectEmptyTurnNudge`（S-209） | `AgentLoop.EmptyTurn.cs:40` | 置标记 → 下轮注入一条 user 提醒 → `continue` |
| `InjectSandboxTransition`（S-207） | `AgentLoop.SandboxTransition.cs:36` | 比对实时状态 → 变化时注入一次 |

三者清一色：**临时副本、不落库、不进 durable conversation、压缩摘要看不见**。本条沿用同一形状。

### 3.3 关键架构事实：能改的只有 wire 副本

```
ExecuteLoopAsync
  conversation            ← sessionConv.GetConversation() 的活引用（durable）
  └─ ExecuteTurnAsync(conversation, ...)            :718
       ├─ wireConversation = InjectSessionTodo(conversation)      :731
       ├─                    InjectSubAgentTurnReminder(...)      :734
       ├─                    InjectEmptyTurnNudge(...)            :738
       ├─                    InjectSandboxTransition(...)         :741
       ├─                    StripImagesWhenModelCannotSee(...)   :746
       └─ provider.ExecuteTurnAsync(wireConversation, ...)        :748-762
```

**⇒ 要让下一次重发不带坏数据，唯一的合法落点是注入链上再挂一个 `InjectProviderRejectionNotice`。**
改 `conversation` 等于改用户历史（用户切回会话会发现内容变了），是 S-236 / S-261 都写死的红线，本条不破。

### 3.4 400 一定带结构化判定，不用猜文案

三条 provider 主链路（`OpenAIChatProvider.Sse.cs:42` / `OpenAIResponsesProvider.cs:154` / `AnthropicMessagesProvider.cs:79`）**全部**走 `ProviderHttpException.CreateAsync`，异常带 `StatusCode`（`ProviderRetryPolicy.cs:20-36`，`public`）。

⇒ 判据可以直接写 `StatusCode == 400`，**不依赖任何上游文案**。这是本条比 S-261 更硬的地方。

### 3.5 工具结果的结构（替换时必须保 `ToolUseId`）

`AgentRuntimeChatMessage(UserToolResults(toolResults))` —— 内部表示是 `role="user"` + `ToolResults` 列表，不是 OpenAI 的 `role="tool"`。

`AgentRuntimeToolResult(ToolUseId, Content: JsonElement, IsError)`。

**⇒ 替换只能换 `Content` / `IsError`，绝不能删消息，也不能换 `ToolUseId`** —— 删了或换 id 立刻制造配对错，把 400 变成另一种 400。

## 四、定案

### 4.1 「调整请求文」的具体动作 —— 替换本轮最后一条工具结果

收到 400 时：

1. 在 wire 副本里找**最后一条带 `ToolResults` 的消息**；
2. 把它的每条结果换成 `Content = "工具执行结果被上游拒绝（HTTP 400）：<报文>。这次结果不可用，请换一种方式重试。"`、`IsError = true`、**`ToolUseId` 原样保留**；
3. `continue` 重发。

**为什么这是对的动作（三条）：**

- **它同时满足「告知」和「修好」** —— 模型下一轮就在对话里看到「我上一步失败了 + 原因」，自己决定换工具 / 换参数 / 直接告诉用户；而坏数据从本轮请求里消失了，重发**真的有可能成功**。只追加一条提醒治不了根 —— 坏数据还在，必再 400。
- **工具结果不是用户内容** —— 替换它不违约。工具结果本来就可能是一条「执行失败」，渲染端本来就支持 `IsError`。
- **`ToolUseId` 不动 ⇒ 配对不破**，不会把 400 引成另一个 400。

### 4.2 三道安全阀（缺一不可，直接对治 2026-10-27 的教训）

S-237 撤掉 400 重试的原因是实打实的账：`MissingSessionID` 从 attempt 1/20 一路烧到 20/20，请求体一个字没变，每次十几分钟。所以本条必须自带三道防火墙：

| # | 安全阀 | 具体 |
|---|---|---|
| 1 | **额度上限 2** | `MaxProviderRejectionRecoveriesPerRun = 2`（照 `MaxImageStripAttemptsPerRun` 的先例）。一个长 run 里可能先后撞上**两个不同**的 400，各修一次是合理的；额度用尽即抛，走原来的报错路径 |
| 2 | **报文指纹去重（主力拦截）** | 把报文归一化（去空白 / 标点 / **数字**）取前 120 字做指纹；重发后撞上**同一指纹** ⇒ 判定「改了也没用」⇒ 立刻抛出，**即使额度还有**。去数字是故意的：上游常把索引写进正文（`.messages[477]`），算进指纹会把「同一毛病在下一处复发」误判成新问题 |
| 3 | **必须有可替换的对象** | 本轮一条工具结果都没有 ⇒ 不进这个分支（坏数据是用户消息，我们没有权力替它删）⇒ 直接抛 |

**安全阀 2 与 1 的分工（写清楚免得以后有人以为 1 是硬拦截）**：真正保证「不对着同一个错反复烧」的是**指纹去重**；额度 2 只决定「最多能修几个不同的问题」。两者叠加后，**浪费的上界固定为「每个不同报文一次」，总数不超过 2**。

**安全阀 3 是关键**：它保证这条兜底**永远不会白花一次请求去试一个不可能的修复**。

### 4.3 代价，如实写在这里

认不出的 400（模型名不存在 / key 错 / 服务商内部 schema 变更）会**多花请求**才报出来：同一报文最多 1 次，不同报文最多 2 次。这是本需求**唯一**的代价，老大已知悉并接受（「根据你的推荐 开始推进」）。

对照 2026-10-27 那次撤掉 400 重试的账：当时的失控来自「同一请求重试 20 次、每次十几分钟」，本条把上界钉死在 2 次、且同一错不重复，不是同一类问题。

## 五、S-236 判据 10 红线的口径变更（必须记下来）

S-236 判据 10 原文：「无关 400（模型不存在 / 参数错 / 工具配对错 / 上下文超限）**不被**这条降级路径截走」。

**本条会改变这个口径** —— 配对错 / 图像错 / 超限之外的所有 400 **都会进本条兜底分支**。所以必须把差别写清楚，否则以后有人拿判据 10 来质疑：

| | 旧口径（S-236 判据 10） | 本条之后 |
|---|---|---|
| 谁被截走 | 只有图像 400 | 所有 400（图像/配对/超限之外） |
| 截走后做什么 | 剥图，静默重发 | **替换工具结果 + emit 事件 + 明确告知模型和用户**，没有静默 |
| 上限 | 2 | **2** + 指纹去重 + 必须有工具结果 |
| 最坏结果 | 无关 400 被误判成图像问题 | **多花一次请求**，然后照原样报错，绝不静默成功 |

**判据 10 的本意是「不许静默吞掉无关 400」。本条不吞 —— 它显式 emit 事件、显式告知模型、显式提示用户、显式记录日志。** 所以新口径与本意一致，与字面不同。

`AgentLoop.cs:464` 那两行（`SuppressImagesForModel || !ConversationHasImageBlocks ⇒ throw`）**一个字不动**。

## 六、判据（验收）

1. **400 被收集**：`ProviderRejectionErrors.IsRequestRejected` 认 `ProviderHttpException(400)`，**不认** 429 / 500 / 401 / 408，也不认没有 `ProviderHttpException` 的普通异常。
2. **告知模型**：重发前模型收到的对话里，本轮最后一条工具结果的 `Content` 已变成拒绝说明、`IsError = true`、**`ToolUseId` 与调用方一致**（配对未破）。
3. **不中断**：替换后重发成功 ⇒ run 继续跑完，`completed` 正常收尾，**不是** `loop_end(aborted)`。
4. **安全阀 1（额度）**：2 次不同报文的恢复额度用尽后撞上的 400 ⇒ 直接抛出，不进入第 3 次替换。
5. **安全阀 2（指纹）**：重发后撞上**同一指纹**的 400 ⇒ 抛出，不进入第二次替换（即使上限还有额度）。
6. **安全阀 3（无可替换对象）**：本轮没有任何工具结果时撞 400 ⇒ **不进入**本条分支，原样抛出。
7. **不抢前三条**：图像 400 仍走 S-261 分支、配对 400 仍走 `RepairToolPairing`、超限仍走错误驱动压缩。
8. **用户可见**：恢复发生时 emit `provider_request_rejected` 事件，渲染端出提示；同一会话合并，不刷屏。
9. **不污染历史**：替换只发生在 wire 副本，切回会话后原始工具结果**仍在**。

## 九、不做的事（说明边界，防止范围蔓延）

- **不猜报文里 `messages[N]` 索引去精确定位坏消息** —— 索引是上游数组下标，经过压缩 / 剥图 / 配对修复后与 UI 消息对不上，猜错会改坏用户历史。定位能力留作后续独立需求。
- **不动 400 的 retry 属性**（`ProviderRetryPolicy.IsRetryableStatus` 保持 `429 || >=500`）。
- **不做历史性脏数据的通用清理** —— 不知道坏在哪，猜不准就不猜。图像那条已由 S-261 专项覆盖。
