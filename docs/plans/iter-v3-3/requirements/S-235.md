# S-235：内置浏览器增加「清除浏览数据」入口

## 1. 原话 / 来源

> 2026-10-27 11:06 老大：

> 对了 登记一个需求到下个迭代，希望浏览器增加去除缓存操作，之前我就遇到过缓存去不掉，上个迭代好像还专门处理了些什么，现在更简单粗暴一点，增加一个缓存清除操作，让用户自己点。

补充（2026-10-27 11:0x）：「刷新是好的，刷新以后能看到是新内容，但手输地址栏跳转又是加载旧缓存」—— 这句话是本需求的判据，见 §3.4。

性质：**软件侧新功能 + 一处存量缺陷修复**。零后端改动、零 Worker 改动。

归属：**v3-iter-3（产品 1.0.3）** —— 老大明确「登记一个需求到下个迭代」。

编号：S-235（承接 `raw-requirements.md` §三「新号从 S-235 起」）。

「上个迭代专门处理过什么」= **S-220 浏览器硬刷新**。那次的结论是「加一条免缓存重载」，**没有清缓存的能力**。本需求是对 S-220 的正面补齐：S-220 解决「这一次要看到新的」，本需求解决「把陈旧的清掉」。

## 2. 现象

老大两次踩到，场景一致：

| 步骤 | 期望 | 实际 |
|---|---|---|
| 1. 本地起服务，改了代码（前端产物换了 hash / 页面结构变了） | 手输 `localhost:xxxx` 看到新内容 | **旧内容** ❌ |
| 2. 点刷新 | 新内容 | **新内容** ✅ |
| 3. 再手输同一个地址回车 | 保持新内容 | **又回旧内容** ❌ |
| 4. 反复刷新都不管用，只能重启应用 | 应用内能清 | **没有入口** ❌ |

矛盾的正是 2 和 3 同时成立：**刷新拿到了新内容，说明网络层能拿到新内容；手输地址又回旧内容，说明有一层缓存在刷新时被绕过、在导航时被命中。**

这不是「刷新不管用」，是「刷新这条路绕过了缓存，另一条路走进了缓存」。用户没有任何手段把那层缓存清掉 —— 这就是本需求的立点：**给一个显式的、粗颗粒的、用户自己按的清除入口**，不再跟缓存机制斗智。

## 3. 现状（2026-10-27 实读源码，Electron 43.2.0）

### 3.1 全库没有任何一处清过 Electron 缓存

`src/` 全树搜 `clearCache|clearStorageData|clearCodeCaches|clearHostResolverCache`，命中 **全部是 C# CodeGraph 的同名无关方法**（`CodeGraphReferenceResolver.ClearCaches()` / `CodeGraphProjectConfig.ClearCache()`，管的是代码索引缓存）。

⇒ **内置浏览器的 HTTP 缓存，从第一版到现在，一次都没被清过。** 这是本需求最硬的事实：不是「清了没效果」，是「压根没有这个动作」。

### 3.2 现成的两个 Cookie 按钮是死按钮（存量缺陷）

`src/main` 全树搜 `cookie`（不区分大小写）只有 **2 条命中**，且都在 `api-request-handler.ts` 的无关上下文里。

但渲染层这边是齐的：

| 位置 | 内容 |
|---|---|
| `lib/ipc/channels.ts:354` | `BROWSER_CLEAR_COOKIES: 'browser:clear-cookies'` |
| `lib/ipc/channels.ts:363` | `BROWSER_IMPORT_COOKIES: 'browser:import-cookies'` |
| `lib/ipc/messagepack-channel-routing.ts:122,125` | 两个通道都在路由白名单里 |
| `components/settings/AppPluginPanel.tsx:291-308` | `handleClearBrowserCookies` |
| `components/settings/AppPluginPanel.tsx:310-…` | `handleImportBrowserCookies` |
| `components/settings/AppPluginPanel.tsx:711-722` | 「清除 Cookie」按钮（`Trash2` 图标） |
| `components/settings/AppPluginPanel.tsx:695-710` | 「导入 Cookie」按钮（`DownloadCloud` 图标） |

**主进程侧零注册**。`src/main/ipc/misc-handlers.ts` 里 `browser:` 开头的只有两个：

- `:244-249` `'browser:emulation-status'`
- `:263-291` `'browser:set-device'`

⇒ 点「清除 Cookie」会 `invoke` 到一个不存在的通道，抛错进 `catch`（`:302-304`），toast 报「清除失败」。**两个按钮都是摆设。**

这与 S-204 是同一类病，但方向相反：S-204 是「端点有、渲染层不调」，这里是「渲染层调、主进程没接」。

### 3.3 `browser:emulation-status` 是 stub，把「复用浏览器数据」在运行时打回 false

`misc-handlers.ts:243-249`：

```ts
// -- Browser emulation status (stub -- returns defaults) --
registerMessagePackHandler<…>('browser:emulation-status', async () => {
  return { success: true, status: { reuseEnabled: false, userAgent: '' } }
})
```

渲染层照单全收（`BrowserPanel.tsx:101-102`）：

```ts
if (!cancelled && result.success) {
  setRuntimeBrowserUserDataReuseEnabled(result.status.reuseEnabled)   // ← 恒被写成 false
```

而设置默认值是 **true**（`stores/settings-store.ts:319`、`settings-store-migrate.ts:319` 兼容补默认），且 `webviewSessionProps` 拿它决定挂不挂 partition（`BrowserPanel.tsx:84-91`）：

```ts
...(runtimeBrowserUserDataReuseEnabled ? {} : { partition: BUILTIN_BROWSER_PARTITION }),
```

⇒ **用户在设置里开着「复用浏览器数据」，面板一挂载就被 stub 覆写成 `false`，实际走 `persist:wishfulclaw-browser` 分区。** 复用功能整体是死的。

这条**不在本需求修复范围**（另立，见 §6），但它直接决定了本需求的实现方式 —— 见 §4.2。

### 3.4 为什么「刷新好、手输地址坏」（机制推断，实施时需实测确认）

按 Electron / Chromium 的分层，两条路走的缓存层不同：

| 路径 | 走什么 | 结果 |
|---|---|---|
| `reloadIgnoringCache()`（S-220 的硬刷新） | 跳过 HTTP 缓存，强制回源 | 新内容 |
| 地址栏手输 → `loadURL()` 导航 | 正常查 HTTP 缓存；`Cache-Control` 未过期就直接用 | 旧内容 |

`BrowserPanel.tsx` 的 `reloadIgnoringCache` 就在这个文件里（S-220 落地），说明硬刷新只作用于 reload 这一条命令，导航不动。

**推断而非结论**：也可能叠加了 Service Worker / 字节码缓存，实施时用 §5 的判据实测分辨，不预设。

### 3.5 缓存实际落在哪

当前（3.3 生效下）是 `persist:wishfulclaw-browser` 分区，路径形如：

```
%APPDATA%\<appName>\Partitions\wishfulclaw-browser\Cache
```

用户既不知道这个路径，也不该知道。**这正是要给界面上按钮的理由**：让用户去翻 Chromium 的数据目录本来就不合理。

## 4. 修复方向

### 4.1 主通道：`browser:clear-cache`

| 项 | 设计 |
|---|---|
| 通道名 | `browser:clear-cache`（与既有 `browser:*` 命名一致） |
| 入参 | `{ webContentsId: number }` |
| 主进程 | `webContents.fromId(id)` → `.session` |
| 落地文件 | `src/main/ipc/misc-handlers.ts`（`browser:set-device` 隔壁，同文件已有 `fromId` 用法可循） |
| 渲染层 | `channels.ts` 加 `BROWSER_CLEAR_CACHE` + `messagepack-channel-routing.ts` 白名单同步 |

`webContentsId` 从 `webview.getWebContentsId()` 取。**这套模式项目内已有先例** —— `browser:set-device`（`misc-handlers.ts:256-291`）就是 `webContents.fromId(args.webContentsId)`，照抄结构即可，不引入新范式。

### 4.2 为什么是 `webContentsId`，不是「按设置判断清哪个 session」

因为 §3.3 那条 stub bug 让**设置值和实际 session 不一致**：设置里 `true`，运行时被写成 `false`，真身是 `persist:wishfulclaw-browser`。

任何「读设置 → 决定清哪个 session」的写法，在当前代码下都有 **50% 概率清错对象**：清了 default session，而 webview 挂在 partition 上 → 用户点了没反应，需求等于没做。

`webContents.fromId(id).session` 拿的是**那个 webview 真正在用的 session**，不管 §3.3 修没修、不管用户在设置里怎么选，结果永远对。这不是风格偏好，是当前代码状态下唯一正确的选择。

附带好处：将来 3.3 修好后，这份代码一个字都不用改。

### 4.3 清什么（Electron 43.2.0 签名已核）

```ts
// electron.d.ts 实测签名
clearCache(): Promise<void>                                    // 无参
clearCodeCaches(options: ClearCodeCachesOptions): Promise<void> // options 必填，urls?: string[]
clearData(options?: ClearDataOptions): Promise<void>            // dataTypes?: Array<'cache'|'cookies'|'indexedDB'|…>
clearStorageData(options?: ClearStorageDataOptions): Promise<void> // storages?: Array<'cookies'|'localstorage'|…>
```

| 层级 | 调用 | 是否清 | 理由 |
|---|---|---|---|
| HTTP 缓存 | `session.clearCache()` | ✅ **必清** | 本需求的正主，手输地址命中的就是它 |
| JS 字节码缓存 | `session.clearCodeCaches({})` | ✅ **必清** | 开发者场景的正主 —— 改了代码仍跑旧字节码，这才是「本地改了 N 版还加载旧结构」最直接的嫌疑。`urls` 省略 = 清全部 |
| 存储（localStorage / IndexedDB / SW） | `clearStorageData({...})` | ❌ **不清** | 会把所有站点的登录态和站点数据抹掉。这不是「清缓存」，是「重置浏览器」 |
| Cookie | `clearStorageData({storages:['cookies']})` | ⭕ 归 §4.5 | 已有独立按钮，语义不同，不混进「清缓存」 |
| DNS 缓存 | `clearHostResolverCache()` | ⚠ 见待确认 | 本地改 `hosts` 调试时有用，但与「页面内容旧」无关 |

备选：`session.clearData({ dataTypes: ['cache'] })`（43 已有，注释自称「more thorough than clearStorageData」）。**建议不换** —— `clearCache()` 语义单一、边界清楚，`clearData` 会连 shared dictionary cache 一起清（d.ts 明确写了），排查「到底清了啥」时更难界定。留作 S-235 失败时的 Plan B。

### 4.4 清完必须重载，否则用户看不到任何变化

清缓存是**后台动作**，不重载的话页面还是内存里那一份，用户体感「点了没反应」。所以：

```
clearCache → clearCodeCaches → webview.reloadIgnoringCache()
```

顺序不能反：先清后载才是「装新货再开箱」。

### 4.5 顺手修「清除 Cookie」按钮（同文件、同域，边际成本近零）

§3.2 那两个死按钮，**建议只修「清除 Cookie」**：

- 加 `browser:clear-cookies` handler，`session.clearStorageData({ storages: ['cookies'] })`
- 与 §4.1 同文件相邻，一次改完，不另开需求
- **「导入 Cookie」不碰** —— 那要读别的浏览器的 Cookies 库（SQLite + 平台解密），成本量级完全不同，另立（见 §6）

老大点头才做，不点头就只做 §4.1，死按钮留原样（反正现状也不会更坏）。

### 4.6 落点

**主推：工具栏按钮。** `components/layout/browser-toolbar.tsx` 现有一排 `ArrowLeft / ArrowRight / RefreshCw|Square / 地址栏 / Go / BrowserDevicePicker`。加一个 `Eraser`（或 `Trash2`，但设置页已用 `Trash2` 表 Cookie，为避免两处同图标不同义，**建议 `Eraser`**）。

风险：工具栏横排在窄面板下会挤。**实施时先量**：面板最小宽度下现有控件占用 + 新按钮宽度，超出就把按钮挪进设备选择器旁的溢出菜单。

**备选（若工具栏容不下）**：`BrowserDevicePicker` 左侧加一个「⋯」下拉，把「清除浏览数据」放进去。

### 4.7 反馈

点击到完成之间有 IO（`clearCache` 是异步的，大缓存可能几百 ms）。必须给三态：

| 状态 | 表现 |
|---|---|
| 进行中 | 按钮图标转圈 / `disabled`，防连点 |
| 成功 | 轻量提示（图标短暂变绿，或复用现有 toast 体系），同时页面已重载 |
| 失败 | 错误 toast，带 `error.message` |

`AppPluginPanel.tsx:291-308` 那套 `clearingCookies` + `toast.success/error` 就是项目里的现成写法，照抄。

## 5. 验收判据（老大要能自己点出来）

不改代码就能验：

1. **清得动**：本地起服务，页面放一个固定文案 → 改成新文案 → 手输地址回车，看到旧文案（复现）→ 点「清除浏览数据」→ 看到新文案 ✅
2. **只清缓存不清登录**：先在某站点登录 → 点清除 → **仍处于登录态** ✅（若掉登录 = 误用了 `clearStorageData` 全量，不合格）
3. **防连点**：连点三下不产生三次重载、不报错 ✅
4. **不误伤主界面**：清完主界面（聊天窗 / 设置页）状态不受影响 ✅
5. **两种 session 都对**：设置里「复用浏览器数据」开关**切到两种状态各验一次**，第 1 条都要成立 ✅（这条是对 §4.2 设计的直接验收）

## 6. 明确不在本需求内（另立，不在本次动手）

| 项 | 为什么不并 | 处置 |
|---|---|---|
| **§3.3 stub 打回复用开关** | 是独立 bug，涉及「主进程怎么拿到复用来源/UA」整条能力，不是加 handler 能了事 | 建议单独立一条，本迭代或下迭代定 |
| **「导入 Cookie」死按钮** | 要读其他浏览器的 Cookies 库（SQLite + 解密），成本与「清缓存」不是一个量级 | 建议单独立一条 |
| 清除范围可选（只清某站点 / 按时间） | 「简单粗暴」是老大原话，颗粒度不该在这里膨胀 | 不做 |
| 给模型暴露 `clear_cache` 工具动作 | `browser-native-ui.ts` 有模型侧的浏览器能力，让模型自己清缓存属于另一层设计 | 不做，除非老大要 |
| 自动清理策略（定时/退出清） | 同上，用户按需 | 不做 |

## 7. 代价与取舍

| 取舍 | 结论 | 理由 |
|---|---|---|
| 粗颗粒一键清 vs 精细选择 | **一键** | 老大原话「更简单粗暴一点」。精细选择把决策成本推给用户，而用户根本不知道 Chromium 分几层缓存 |
| 清完自动重载 vs 让用户自己刷 | **自动重载** | 不清不重载 = 用户看不出效果 = 需求白做 |
| 并进设置页 vs 工具栏 | **工具栏** | 这是「看到旧页面」时的即时反应，去设置页翻是打断。设置页那套是「配置」，这里是「动作」 |
| 顺手修 Cookie 按钮 | **待老大点头** | 同文件边际成本近零，但确实超出「清缓存」的字面范围 |

### 9.2 两处实施中定下的口径

| 口径 | 为什么 |
|---|---|
| **`clearingRef` 而不是只靠 `clearing` state 防连点** | `setClearing` 是异步的，同一帧连点三下后两次仍读到旧 state ⇒ 三次清缓存三次重载。ref 同步，是唯一可靠的闸（判据 3） |
| **清完必须 `reloadIgnoringCache()`，不能用普通 `reload()`** | 缓存刚清掉，普通 reload 若命中 304 或内存副本，用户看到的内容与清之前一样 ⇒ 动作看起来没发生。这是 §4.4 的落地方式 |
