## 1. 原话 / 来源

**2026-11-11 10:35 老大**：

> 我们现在的 tokens 往上显示的是 G，我希望参考通用方式。
>
> 在 AI 和大模型语境下，表示数量级有一套相对固定的缩写：**M = Million（百万）／B = Billion（十亿）／T = Trillion（万亿）**。1.016B 就是 10.16 亿。很多平台把 1,016M 换算成 1.016B，是因为数值达到十亿级后，用 B 更简洁，也是行业描述模型参数、Token 用量时的常见做法。
>
> **「G」在中文互联网语境里常被联想为 GB（存储容量）或「个」**。虽然某些非正式计数里有人用 G 代指十亿，但在 AI Token 统计中它没有 B 那样被广泛接受。把 Token 显示成 G，别人可能误解为存储大小，或者觉得这不是专业计量单位。
>
> **建议跟着大多数平台用 B 就行。** 如果面向的是中文普通用户，也可以考虑直接写「10.16 亿 Tokens」，这样最不容易产生歧义。

**溯到出处**：`G` 不是实现跑偏，而是 S-194 当时的**原始口径**就是 G ——

> 「……导致部分会话的统计已经到 1127.85M 这种数字了，是否应该怎么处理呢 **我在考虑增加 G 这些单位**」（老大，iter-v2-39 登记时）

S-194 按 SI 前缀（Giga = 1e9）实现 `k / M / G / T`。**本次是口径变更，不是缺陷修复** —— 记在这里，防止后人当 bug 去「修回去」。

## 2. 现象

token 计数进到十亿级后显示成带 `G` 后缀的串，例：

| 原始值 | 当前显示 | 期望显示 |
|---|---|---|
| `1_127_850_000` | `1.13G` | `1.13B` |
| `2_500_000_000` | `2.50G` | `2.50B` |
| `999_999_999` | `1.00G`（进位） | `1.00B` |
| `1e12` | `1.00T` | `1.00T`（**不变**） |

受影响的是**所有显示 token 数量的面**（上下文环、输入框计数器、子 Agent 卡、用量统计、用量明细表、运行时面板、bash 工具卡等），共 26 个调用点 —— 它们都走同一个 `formatTokens`，所以**一处改全生效**。

`src/renderer/src/lib/format-tokens.ts:17-22`：

```ts
const TOKEN_UNITS: ReadonlyArray<{ divisor: number; suffix: string }> = [
  { divisor: 1_000, suffix: 'k' },
  { divisor: 1_000_000, suffix: 'M' },
  { divisor: 1_000_000_000, suffix: 'G' },   // ← 只改这一行

```

`formatTokens`（`:49-61`）按这张表逐档试算，`formatScaledUnit`（`:29-33`）只管精度分档（`< 10` 两位 / `< 100` 一位 / `>= 100` 整数）。**进位逻辑（`999999` → `1.00M`）与后缀无关**，改字面量即可。

## 4. 根因

不是 bug。S-194 订口径时按 **SI 前缀** 选了 `G`（Giga），而 AI 行业描述参数与 token 用量通行 **`B`（Billion）**；两者数值同为 1e9，只差显示字母，但 `G` 在中文语境里会与 GB 混淆。**这是显示口径变更：`G` → `B`，量级与精度一概不动。**

## 5. 修复方向

| 方案 | 做法 | 评价 |
|---|---|---|
| **A 只换字母（推荐）** | `TOKEN_UNITS` 的 `'G'` 改 `'B'`；同步 3 处注释 + 4 处断言 | 一行实改。零逻辑风险、零布局风险（`B` 与 `G` 等宽等长）；与主流平台写法一致 |
| B `B` + 中文双轨 | 十亿级显示 `1.13B（10.16 亿）` | 信息更全，但把「括号补充」塞进每个用量格子，表格与环上会挤；且两套说法并存，用户反而会问「哪个是准的」 |
| C 全中文单位 | `1.13 十亿` / `10.16 亿` | 最不容易歧义，但 `k` / `M` 段也要跟着中文化才有体系，等于推翻 S-194 的全部断言与用户已习惯的读法 |

**我的建议是 A**。理由：`B` 是行业硬通货，`B` / `M` / `T` 一套系统才自洽；方案 B 的「括号」在设置页表格里会撑破单元格（`usage-detail-table.tsx` 是定宽列），而中文「亿」只对国内用户友好 —— 本产品用量面本来就混着英文单位 `k` / `M`。**若你要求面向纯中文用户，那就该整条阶梯一起中文化（方案 C），不是只在十亿级挂个括号。**

**待拍板**：是否要顺带把 `B` 段也纳入中文提示？我的倾向是不加，单一写法。默认按 A 执行。

## 7. 刻意不做

- **不改 `k` 的小写**（S-194 已定，改它要破一批断言与视觉一致性）。
- **不加中文单位双轨**（理由见 §5，方案 B 落选）。
- **不动 `formatScaledUnit` 的精度分档**（`< 10` 两位 / `< 100` 一位 / `>= 100` 整数）。
- **不动 `T` 及以上**：`T` 在 SI 与 AI 行业口径里同义（Trillion），无歧义。
- **不回溯改历史需求单与 changelog 里的 `G`**：那是当时的口径记录。
- **不动 C# 侧**：全仓 `.cs` 无 token 格式化实现。

> 实施后确认（2026-11-11 10:4x）：以上六条一条没破。`k` / `M` / `T` 三档、精度分档、进位逻辑、防御分支零改动，历史文档零改动。
