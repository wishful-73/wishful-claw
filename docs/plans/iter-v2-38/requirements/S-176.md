## 三、候选机理（**推断，未实测** —— 需老大给场景才能收窄）

按可疑度排：

1. **水位线激活但内容底读不到，于是视口被钉在留白区**（最可疑）
   - `:179` 判「水位线激活」，但内层 `:184-188` 要求 `realBottom > 0` 才切到 DOM 真值；`getRealContentBottom` 在**没有任何行挂载**时返回 0（`:164` `if (!content || content.children.length === 0) return 0`）
   - 此时 `bottom` 保持 `:178` 算出的 `ref.scrollHeight - ref.clientHeight` —— **那是含留白的底**
   - 而留白区里虚拟器的可见范围为空 ⇒ 没有行可渲染 ⇒ 下帧 `getRealContentBottom()` 仍是 0 ⇒ **越钉越空，自锁**
   - 对得上「高度超出聊天窗范围」「用户对着空白发呆」

2. **水位线未及时清零**
   - 清零挂在 `isSessionOutputting` 转假那一次 layout effect；而 `:643` 的 `if (pendingAskUserQuestion) return` 在它**之前** ⇒ 该轮漏掉后要等依赖变化才补做

3. **「高度超出聊天窗范围」指的是单块内容撑破视口**（而不是留白）
   - 另一条链：`CollapsibleHeightPanel` 展开态是 `height: auto`（`:138`，无上限），工具结果 / 思考块展开后可以远超视口
   - 若老大的现象是「看不到下半截、也滚不动」，查这里而不是水位线

## 四、已知硬约束（无论走哪条方案都不能违反）

1. **收 `min-height` = 制造 `scrollHeight` 骤减 = 浏览器 clamp `scrollTop` = 跳** —— iter-30 实测代价，写死在 `useMessageListScroll.ts:650-655` 与 `docs/plans/iter-v2-30/raw-requirements.md:426`。
2. 若要回收，**顺序**必须是「先把视口对齐到真实内容底，再撤 `min-height`」—— 代码里已有这份实现（`:691-699`），回收直接复用，不要另起一套。
3. **全局 `* { scroll-behavior: smooth }` 必须继续被 inline `scrollBehavior: 'auto'` 覆盖**（`VirtualListContent.tsx:135-137`）—— 这是 iter-30 认定的「真凶」，别碰。
4. 冷却锁（240 ms）与单调下界是 S-150 为治抖动加的，回收方案**不得与其打架**；要动，得给出「为什么这次不会变成拉锯」的推理。
