# S-271 失败的工具调用会从折叠块里跳出来 —— 三处判据不同步，所以「有时跳有时不跳」

> 归属：**本迭代**（v3-iter-4，刀 10）｜登记 2026-10-29 15:00｜实施 2026-10-29
> **状态：已交付 · 纯函数回归 12/12 全 PASS · 待真机验收。**
> 老大原话：「我们正常连续的工具调用 会折叠收起到工具调用下，但是如果某个工具调用报错或者失败了，就不会被折叠进去，感觉是偶然情况，并不是一定」。
> **不是偶然** —— 三条独立机制叠在一起，每条都能单独造成「有时候跳、有时候不跳」。见 §三。

## 一、现象

连续的工具调用（Read / Edit / Bash / MCP…）在聊天窗里收成一个折叠块，折叠头显示「工具调用 · N」。

其中某一次失败时，那个失败项**不在折叠块里面**，而是单独一张卡露在折叠块外面。老大以为是自己看错或者偶发，实际每次都能复现 —— 只是**不是每次都跳**，取决于下面 §三 的三个条件撞上哪个。

## 二、根因：这是刻意设计，不是渲染 bug

`force` 项露在折叠面板外是 S-225 §8 定的口径，代码里写得很明白：

| 位置 | 事实 |
|---|---|
| `execution-outline.ts:201-204` | `if (hasError \|\| status === 'pending_approval' \|\| requiresApproval) return 'attention'` —— 注释原文：「Errors and approval requests always need user attention regardless of tool type」 |
| `execution-outline.ts:227-238` | `getToolVisibility`：`ordinary` 白名单只有 `context` / `mcp` / `command` / `file-change` 四类，**`attention` 落进 else 分支 ⇒ `'force'`** |
| `render-density.ts:171-173` | `shouldPinOutsideCollapsedRun(collapsed, visibility)` ⇒ `collapsed && visibility === 'force'` |
| `content-renderer.tsx:319-337` | `pinnedTools` 从 `renderedTools` 里滤出 force 项 |
| `content-renderer.tsx:353-357` | `pinnedTools` 渲染在 `CollapsibleHeightPanel` **之前** —— 也就是折叠面板外面 |

`content-renderer.tsx:319-324` 的注释是这条设计的理由：

> S-225 §8：折叠态下 attention / force 项必须露在折叠面板之外 —— 档位不得藏错误。
> 否则「纯文本」档里一个失败的 Edit 会跟着面板一起沉下去，用户只看到「运行了 N 个工具」。

⇒ **想让失败项折进去，等于推翻 S-225 §8 的口径**，不是修一个 bug 那么简单。这一点必须在动码前拍板。

## 三、为什么「感觉偶然」—— 三条判据各自不同步

### ① `hasError` 有一个来源是「嗅探输出文本」，不是运行时标记

`execution-outline.ts:361-365` 四个来源：

```ts
const hasError =
  baseStatus === 'error' ||              // 运行时标记
  !!result?.isError ||                   // 运行时标记
  !!liveToolCall?.error ||               // 运行时标记
  hasStructuredOutputError(block.name, output)  // ← 嗅探
```

`hasStructuredOutputError`（`:166-179`）只在输出能解成**结构化 JSON** 且命中 `success === false` / 非空 `error` 字段 / 命令类 `exitCode !== 0` 时才算。

⇒ 工具失败了、但失败写在**纯文本**里（`File not found: ...`），且 `isError` 没置位 ⇒ `hasError = false` ⇒ 归类仍是 `context` / `command` ⇒ **折进去**。

⇒ 同一个工具失败两次，失败信息的形态不同（一次走结构化、一次走文本），表现就不同。这是老大感觉「偶然」的第一个来源。

### ② 取消（`canceled`）按工具种类分流

`execution-outline.ts:209-223` 的分支顺序决定了：

- 白名单工具（`Read` / `Edit` / `Bash` / MCP / 浏览器…）在 `:209-212` 就被归类了，**永远走不到 `:221`** ⇒ 取消的 Read 归类 `context` ⇒ **折进去**。
- 白名单外的工具（未知 / 第三方）走 `:220-223`：`status === 'canceled'` ⇒ `attention` ⇒ **跳出来**。

⇒ 同样是「取消」，一个折进去一个跳出来。

### ③ 换渲染档位，表现就变

`content-renderer.tsx:329-332`：`pinnedTools` 除了要求 `visibility === 'force'`，还要求满足以下任一：

```
processForm === 'card' || PROCESS_LINE_CARD_ONLY_TOOL_NAMES.has(name)
  || category === 'desktop' || category === 'interactive'
```

`processForm === 'card'` 只在**卡片档**成立。

⇒ **同一个失败项**：卡片档里跳出来成一张卡；**纯文本档（S-248）里留在面板内当红行**。

⇒ 老大在不同档位下看到不同结果 —— 这是第三个来源，也是最容易被当成「偶发」的一个。

## 四、方案

### A（推荐）：失败项留在 run 里，折叠头给失败信号

- `getToolCategory` 的 `hasError` 分支拆开：**只有 `pending_approval` / `requiresApproval` 判 `attention`**（真交互不能藏），`hasError` 不再单独决定 `force`。
- `ToolExecutionRun` 增加 `failedCount`，折叠头显示「工具调用 · N」+ 红色「· M 失败」徽章。
- 展开后失败项本身已是错误态（现有 `ToolBlockRenderer` 的错误渲染不用动）。
- 卡片档与纯文本档行为一致。

**代价**：折叠态下看不到失败详情，只剩徽章 —— 所以徽章必须常亮，且点开时自动定位到第一个失败项。

**理由**：老大要的是「连续别断裂」。错误可见性用徽章 + 定位保住，不靠把卡拎到外面。

### B：保持 pin，只统一判据

去掉 `hasStructuredOutputError` 的内容嗅探（只认运行时标记），并让白名单工具的 `canceled` 也判 `attention`。

**治的是「飘」，不治老大要的「别跳」。** 如果老大其实接受「失败就该跳出来」，选这个，改动面最小、不动 S-225 §8。

### C：pin 但降级成一行

失败项仍在面板外，但渲染成一行紧凑红提示（不是整张卡），点开才展开。视觉上连续感损失小一些。

**不建议**：多一套渲染形态，纯文本档本来就是行，两种「行」要再区分一次。

## 五、判据（验收）

1. **连续不断裂**：连续 5 次同类调用、第 3 次失败 ⇒ 仍是**一个**折叠块，折叠头计数为 5。
2. **失败有信号**：该折叠头显示失败徽章（数量 = 失败项数）；折叠态下不出现额外的独立失败卡。
3. **档位一致**：同一场景在卡片档 / 紧凑档 / 纯文本档下，折叠块数量与位置一致。
4. **真交互不藏**：`pending_approval` / `requiresApproval` / `INTERACTIVE_TOOL_NAMES`（答题 / 计划审批 / 目标确认）**仍然 pin 在折叠外** —— 这些一项都不许折。
5. **卡片型工具不藏**：子 agent（`TASK_TOOL_NAME`）/ 团队事件 / 生成图 / `visualize_show_widget` / 桌面截图仍 pin。
6. **error 与 canceled 一致**：同一个工具失败和取消，归类结果相同（不再按白名单分流）。
7. **不倒退 S-225 §8 的本意**：失败在折叠态**必须有可见信号**，不许退化成「只剩一个数字」。

**闸有效性反向验证**：把 `hasError` 判据临时注回 `attention` 分支 ⇒ 断言 3 变红（`actual ['t3'] / expected []`）；撤销后 12/12 恢复。已反向确认这条闸不是空转。

## 十、不做的事

- **不动 run 的切分边界**：`execution-outline.ts:406` 已经把 force 项 `push` 进同一个 `pendingRun.itemIds`，**边界本身是对的**，错的是渲染时把它拎出去。改边界是错的方向。
- **不藏错误**：任何方案下，失败在折叠态都要有可见信号。
- **不改 `ToolBlockRenderer` 的错误渲染**：失败项展开后长什么样不用变。
