## 一、假参数 `_options`

`src/renderer/src/lib/agent/session-scoped-agent-state.ts:119`

```ts
export function selectSessionScopedAgentState(
  state: AgentStore,
  sessionId: string | null | undefined,
  _options?: { mode?: string }      // ← 下划线已声明「不用」
): SessionScopedAgentSelection {
```

**4 个调用点全部传 `{ mode: 'coarse' }`，函数体一次没读**：

| 文件 | 行 |
|---|---|
| `components/chat/useMessageListData.ts` | 142 |
| `components/chat/MessageList.tsx` | 33 |
| `components/chat/StaticMessageTranscript.tsx` | 65 |
| `components/chat/SubAgentCard.tsx` | 241 |

**危害不是「多传个参数浪费 CPU」**，而是**撒谎**：读代码的人看到 `mode: 'coarse'`
会认为「这里传了粗粒度，所以拿到的是裁剪过的视图、会比较便宜」，于是照着这个假设
去加新调用点、去调性能。实际什么都没发生 —— 未来有人真要接「按模式裁剪」时，
会先发现「咦，早就在传了怎么没效果」，再花时间确认它是个空壳。

**修法**：删参数声明 + 删 4 处传参。若将来真需要按模式分化，那时连同实现一起加，
不留占位。

## 三、198 行缓存逻辑零覆盖

`npm test` 127/127 里**没有任何一条碰这个文件**。而它的正确性完全依赖一个
非显然前提：**zustand 用 `Object.is` 比对选择器返回值，所以源引用不动就必须
返回同一个对象引用**，否则订阅方无限重渲染（`:19~21` 注释写的就是这个）。

守这条线的只有一个 `CacheEntry` 的 6 个 `===` 比对。写错一个字段，
表现是「某个操作后整个消息列表卡死重建」—— 这类 bug 已被老大骂过好几次
（S-336 一系的内存/渲染问题），但没有测试兜底。

### 新增 `tests/session-scoped-agent-state/program.ts`

纯数据 + 纯函数，不碰 DOM / Electron，直接 esbuild 打包跑。用例：

| # | 场景 | 期望 |
|---|---|---|
| 1 | `sessionId` 为 `null` / `undefined` | 返回 `EMPTY_SELECTION` 同一引用 |
| 2 | 两个会话各有 sub-agent | 各自只看到自己的；`hasOrchestrationData` 都为真 |
| 3 | **同 state 连调两次** | 返回**同一对象引用**（`assert.strictEqual`） |
| 4 | 只换 `activeSubAgents` 引用（内容相同） | 引用失效，返回**新**对象（不能误判命中） |
| 5 | 只换 `runningSessions[sessionId]` 从 `running` → `completed` | 引用失效，`isSessionRunning` 由真变假 |
| 6 | `liveSessionId === sessionId` | 取 `pendingToolCalls` / `executedToolCalls` |
| 7 | `liveSessionId !== sessionId` 且无 `sessionToolCallsCache` | `toolCalls` 为 `EMPTY_TOOL_CALLS` 同一引用 |
| 8 | 会话数超过 `MAX_CACHED_SESSIONS`(32) | 缓存整表清空后仍返回正确值（不抛、不返回旧值） |
| 9 | `findSubAgentInSelection` | 优先级 活 → 死 → 历史；找不到返回 `null` |
| 10 | `resetSessionScopedAgentStateCache()` 后再调 | 返回**新**对象引用（缓存确实被清了） |

`package.json` 加脚本 `test:session-scoped-agent-state`，并按现有格式接进
`scripts/run-tests.mjs`。
