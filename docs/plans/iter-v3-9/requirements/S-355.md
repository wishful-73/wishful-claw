## 2. 现象

`src/main/channels/channel-media-source.ts` 是 S-352 刀 1 抽出来的统一读源入口（飞书 / 微信的 image / file / audio 全走它）。

| 行 | 问题 |
|---|---|
| `44` | `await fetch(value)` —— **无 `AbortSignal`、无 timeout**。URL 不响应时渠道服务一直挂着，没有任何回收路径 |
| `49` | `Buffer.from(await response.arrayBuffer())` —— **不校验 `content-length`、无大小上限**，全量进主进程堆 |
| `59` | `fs.readFileSync(value)` —— **同步读整个文件**，主进程事件循环阻塞 |

**放大效应**：微信侧 `uploadMedia`（`weixin-api.ts`）接着走 `encryptOutboundMedia` → `Buffer.concat([cipher.update(buffer), cipher.final()])`（`weixin-crypto.ts:25`），**再复制一整份**。一条 N 字节的媒体，峰值 2~3N。

**为什么能到很大**：`ChannelSendFile` 语义上就是「任意文件」，模型完全可能塞几百 MB 进去。

**安全侧（D-7）**：`readBinarySource` 对 `source` **不做任何沙箱校验**，且渠道会话内这批工具**免审批**：

- `ToolCallProcessor.Approval.cs:81-84` —— `IsChannelSession() && IsChannelFileTool()` ⇒ `return false`（不审批）
- `:125-128` —— 本迭代把 `ChannelSendAudio` 加进了 `IsChannelFileTool`
- 全仓 `Sandbox` 相关只剩 `SandboxElevationStore`（管的是 shell 越界申请），**路径校验不覆盖渠道工具**

组合后果：群里有个人说句话 → agent 在渠道会话内 → 调 `ChannelSendImage(source: "C:\\Users\\x\\.ssh\\id_rsa")` → 免审批 → 当图片发到群里。

## 3. 代码链路（2026-11-11 实读）

### 3.1 三个缺口在同一函数里

```
readBinarySource(source, fallbackName)
  ├─ 空串 → throw                      ✅
  ├─ /^https?:\/\// → fetch(value)     ❌ 无 timeout / 无大小上限
  │                    arrayBuffer()   ❌ 全量入堆
  └─ fs.existsSync + readFileSync      ❌ 同步阻塞 / 无大小上限
```

注意 `fs.existsSync` + `readFileSync` 是**两次系统调用且中间有竞态**（TOCTOU），但这不是本单重点。

### 3.2 调用面无校验

| 调用方 | 传进来的 `source` |
|---|---|
| `channel-feishu-handlers.ts` × 3 | `args.filePath`（MessagePack 直传，**无校验**） |
| `channel-weixin-handlers.ts` × 3 | 同上 |
| `executeFeishuChannelTool` / `executeWeixinChannelTool` | `String(args.filePath ?? '')` |
| `feishu-outbound-media.ts` / `weixin-outbound-media.ts` | `media.source` |

**从头到尾没有一处检查这个路径是否在允许的目录内。**

### 3.3 与 S-247 的关系（防止误读）

S-247（内存占用异常偏高）已于 2026-11-09 10:24 关闭，结论是「**不是泄漏，是每帧重做**」，生产构建 GC 在收。

**本单不是复活 S-247。** 本单是「某条具体代码路径对单次输入没有上界」，是可复现、可定量的**新增**问题，与「渲染每帧重做」是两件事。

## 4. 根因

**`channel-media-source.ts` 是从 `channel-handler-utils.ts` 原样搬家出来的（刀 1），搬的时候只关心「依赖方向」，没有重新审一遍「这个函数该不该有上界」。**

搬家本身是对的（避免 `channel-handler-utils → channel-manager → providers → 本文件 → channel-handler-utils` 的循环依赖，见文件头注释）。问题在于**搬家被当成纯重构**，于是原有的缺口一并继承，还被 new 的调用面（audio / 任意 URL）放大。

## 5. 修复方向

### 5.1 上界与超时（改 `channel-media-source.ts` 一处即可）

```ts
const MAX_MEDIA_BYTES = 50 * 1024 * 1024   // 与渠道平台上限对齐，具体值见 §9
const FETCH_TIMEOUT_MS = 60_000

// URL 分支
const res = await fetch(value, { signal: AbortSignal.timeout(FETCH_TIMEOUT_MS) })
const declared = Number(res.headers.get('content-length') ?? '0')
if (declared > MAX_MEDIA_BYTES) throw new Error(...)
// 流式读并累加，超限即 abort —— 不能只信 content-length（可能缺失或撒谎）

// 本地分支
const stat = await fs.promises.stat(value)
if (stat.size > MAX_MEDIA_BYTES) throw new Error(...)
const buffer = await fs.promises.readFile(value)   // 异步，不阻塞主进程
```

三个要点：

1. **不能只信 `content-length`** —— 可能缺失，也可能小于实际；
2. **`readFileSync` → `fs.promises.readFile`** —— 主进程阻塞是真卡顿的来源；
3. **超时用 `AbortSignal.timeout`** —— Node 18+ 原生，无需手写。

### 5.2 路径边界（D-7）

最低限度：**在 S-352 单据与本单里明确登记「渠道出站媒体的 `source` 不做路径边界校验」这个已知风险**，别让它默默变成「本来就该这样」。

再进一步（可选，工作量更大）：复用 `SandboxElevationStore` 的判据，对 `source` 做只读校验 —— 但要注意渠道会话弹不出审批框，越界时只能**拒**不能**申请**，用户体验上要给可读错误。

### 5.3 审批链（可选）

`Approval.cs:81-84` 的免审批是**既有设计**（渠道无法完成远程审批），不是缺陷。本单不推翻它，只把「免审批 + 无路径校验」这个组合的风险写明。

## 6. 代价与取舍

- **加上界**会拒掉合法的大文件（比如用户真想发一个 80 MB 的视频）。所以 `MAX_MEDIA_BYTES` 的取值要对齐**渠道平台自己的上限**（飞书文件上限、微信上限各不相同），而不是拍一个数。
- **异步替换同步**会让 `readBinarySource` 的语义从「同步抛错」变成「异步 reject」—— 所有调用点都是 `await`，无影响，但要核一遍。
- **路径边界校验**如果做得太严，会挡住「agent 把刚生成的图片发出去」这个主场景（生成目录可能在数据根之外）。所以要做**白名单**而不是**黑名单**。

- **不动入站媒体的下载链路**（`mediaRefs` 那条）—— 那是另一条线，本单只查出站。若入站也有同样缺口，另开单。

## 8. 验收

| 子项 | 验收方式 |
|---|---|
| 大小上限（本地） | 传一个 200 MB 文件 → 被拒 + 明确错误，主进程内存无尖峰 |
| 大小上限（URL） | 指向一个大文件 URL → 边读边判，超限即 abort，不把整个 body 读完 |
| 超时 | 指向一个不响应的 URL（如 `http://10.255.255.1/`）→ 60 s 内失败并回收，渠道服务不挂死 |
| 不阻塞 | 读 50 MB 文件期间，主进程 UI 不卡（可同时点开设置页验证） |
| 路径边界 | 若做了校验：`source` 指向用户目录外 → 被拒；若没做：S-352 / 本单有明确风险登记 |

## 10. 实施记录（2026-11-11，D-6）

### 10.1 上界与超时的取值依据

`MAX_OUTBOUND_MEDIA_BYTES = 30 MB`。

**为什么不是「飞书文件上限 / 微信上限」**：那些是平台规则，随平台版本变化，而本文件是两家共用的读源入口 —— 把平台值抄进来等于在底座里维护一份注定过期的副本。本护栏只回答一个技术问题：**一次读多少字节算失控**。30 MB 覆盖正常的文档 / 图片 / 短视频，又能把「模型塞进来一个 500 MB 文件」挡在主进程堆之外。

**按 kind 细分不做**：`readBinarySource` 不知道 `kind`，也不该知道 —— 那是渠道实现层的事。

### 10.2 三处改动

| 问题 | 改法 |
|---|---|
| URL 无超时 | `fetch(value, { signal: AbortSignal.timeout(60_000) })`；超时常量导出为 `OUTBOUND_MEDIA_FETCH_TIMEOUT_MS` |
| 无大小上限 | ① `content-length` 声明值先判；② 不信声明值 —— `response.body.getReader()` 边读边累加，超限即 `cancel()` 断连；③ 无 `body` 时（理论上不该有）退 `arrayBuffer()` 再判 |
| 本地同步读 | `fs.existsSync` + `readFileSync` → `fs.promises.stat` + `fs.promises.readFile`；`stat.size` 先判，读完再判一次（TOCTOU 兜底） |

顺带：`Not a file: <path>`（传目录）与 `Download URL returned an empty body` 两处可读错误，此前分别是「读到 EOF 得到 0 字节」和「EISDIR」。

### 10.3 测试

`tests/channel-media/program.ts` 新增 `runSourceCases()` 7 条：空串 / 不存在 / 非文件（目录）/ 正常读通 + 文件名推断 / 本地超限 / URL 声明值超限（只声明不真发，验证先看 header）/ URL 流式超限（本地起 `http` 服务实发 30 MB + 64 KB，验证边读边判）。

**超时未测**：跑一次要 60 s，不进常规套件；验收走 §8 的 `http://10.255.255.1/` 手工验证。
