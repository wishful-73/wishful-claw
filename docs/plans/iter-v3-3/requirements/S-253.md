# S-253：文件搜索失败只说一句「没有在运行」—— 该拉起的不拉起，该引导的不引导

> 老大 2026-10-28 11:14 登记，原话：
>
> 「我们快捷启动里面有个搜索文件，现在选择搜索文件进行搜索后，直接显示个软件没有运行就没有后文了，
> 没下载还是没安装，没启动应该是我们自动给他们拉起，没下载需要引导。这个方式不对」
>
> 性质：**交互缺陷 + 状态混淆**。不是"再加一句提示"，而是把「失败」拆成三种互斥情况，每种给出**可点的下一步**。

编号：S-253。归属 **v3-iter-3（产品 1.0.3）**，状态 **已完成（2026-10-28）**。

## 1. 现象

快捷启动 → 「搜索文件」→ 输入关键词 → 结果区只有一行灰字，**没有任何按钮、没有下一步**：

- `Everything 没有在运行，先启动它再搜`
- 或 `es.exe 启动失败，可能路径已失效（设置里可以重新检测）`

用户被丢在死胡同：不知道是我们没装、装了没起、起了没连上，也不知道点哪儿。

## 2. 现状链路（2026-10-28 实测代码）

### 2.1 主进程

`src/main/quick-launcher/file-search.ts:114` `executeFileQuery`：

```ts
const status = await getEsStatus()
if (!status.ready || !status.exePath) {
  return { ok: false, hits: [], failure: 'spawn-failed', error: 'es-not-ready' }
}
...
if (result.failure === 'not-running') {
  result = await startEverythingAndRetry(exePath, request, result)   // S-155 调整②：自动拉起 + 轮询重试
}
```

两个问题：

1. **「没装 / 没探到 es.exe」被折进 `spawn-failed`**（`error: 'es-not-ready'`），跟「路径失效」共用一句话。老大说的「没下载还是没安装」在这里就丢了信息。
2. `not-running` 已经有自动拉起（`startEverythingAndRetry`，S-155 已做），**但拉起失败/超时后回到渲染端时，跟"压根没尝试拉起"长得一模一样** —— 渲染端无法区分「我们试过了但没成」和「我们没试」。

### 2.2 探测侧

`src/main/quick-launcher/es-probe.ts:333`：本体路径没探到就如实回 `not-running`；轮询到预算耗尽仍回 `not-running`。
⇒ **「没安装」和「装了但没在跑」在 `EsFailure` 枚举里根本没有区分**（`types.ts:84`：`'not-running' | 'spawn-failed' | 'bad-output' | 'search-failed'`）。

### 2.3 渲染端

`src/renderer/src/lib/file-search-shared.ts:95` `fileSearchFailureText`：四个 `case` 全部 `return` 一段**静态字符串**。调用方拿到就画，没有动作位。

## 3. 要求

### 3.1 三种情况必须分开（判定口径）

| 情况 | 判定依据（现状可得） | 用户该看到 |
|---|---|---|
| A. 已装但没在跑 | 探到本体路径（`everythingExePath` 有值），`es` 报 exit 8 / IPC not found | 「Everything 没在运行，我们正在替你启动」→ 自动拉起（已有，保留）→ 成功就直接出结果 |
| B. 没安装 / 没探到 es.exe | `status.exePath` 为空、`error === 'es-not-ready'` | 引导下载 + 给下载落点，不是一句"启动失败" |
| C. A 拉起失败（超时） | `startEverythingAndRetry` 跑完仍 `not-running` | 「已尝试启动但没有成功」+ 「重试」按钮 + 一句排查提示（多半是安装损坏 / 权限） |
| D. 其它 | `bad-output` / `search-failed` | 维持现有文案，可加「重试」 |

### 3.2 交互落点

1. **A 走自动拉起，界面上给"进行中"态**（如 `正在启动 Everything…`），不要停在错误行。
2. **B 给可点动作**：一个「去下载」按钮（打开 Everything 官网下载页 / 官方 CLI 页）+ 一个「我已装好，重新检测」（调 `invalidateEsProbe()` 后重试本次搜索）。
3. **C 给「重试」按钮**，重跑本次查询，不用用户重开窗口、不用重新输入关键词。
4. 所有动作按钮都用现有设计语言（不是裸链接），失败文案本身**仍保留**，不要为好看把原因藏掉。

### 3.3 状态建模

建议给 `EsFailure` 增加一档（如 `'not-installed'`），把「没装」从 `spawn-failed` 里摘出来 —— 摘出来才能分别引导。
**只在主进程判定侧新增，不允许在渲染端靠字符串猜。**

## 4. 验收

1. 卸掉 Everything（或临时改名 `es.exe`）⇒ 搜索 → 出现**引导下载**，点「重新检测」后能恢复。
2. 装好 Everything 但进程退出 ⇒ 搜索 → 界面出现"正在启动"，随后**自动出结果**，用户不需要点任何东西。
3. 拉起失败（人为占住 IPC / 只读权限模拟）⇒ 出现「已尝试启动但没有成功」+「重试」按钮，点重试能再跑一次。
4. 三种情况文案互不相同，且都能从现象反推原因。
5. 空结果（搜到了但没有匹配）**不得**被当成失败 —— 现状已区分，改完不能退回去。

## 5. 不在范围

- 不做「内置 Everything 本体的自动安装」（安装第三方软件属于另一个决策）。
- 不动 `es.exe` 的探测优先级与排除规则（S-151 / S-155 已定）。
- 不改独立搜索窗的窗口参数、缓存与分页。

### 6.6 审查修补（2026-10-28 13:49，dev 实例只读审查后的三点反馈）

**① 真缺陷，已修 —— 过程态可能永久停住。**

### 6.8 审查修补第三轮（2026-10-28 15:05，dev 实例只读审查；反馈原文 `.wishful-claw/notes/review-feedback-round2.md`）

**缺陷，已修 —— `launchingEverything` 可能永久停在 `true`，且与空态同屏。**

渲染端只有**一个**写入点（`main.tsx` 的 `file-search:status` 监听），`runFirstPage` 开头不重置它。而主进程那条 `done` 推送会**静默消失**：`notifyFileSearchStatus` 在窗口销毁时提前 `return`，而 `safeSendMessagePackToWindow`（`window-ipc.ts`）另有三处返回 `false` 且不说话 —— 其中一处正是「reload 期间 `webContents` 还活着但 `mainFrame` 已经拆了」，**窗口首开与刚 reload 都撞得上**。返回值没人检查，于是 `done` 就这么没了。

后果：`searching` 收成 `false` 而 `launchingEverything` 卡在 `true` 时，`result-list.tsx` 的转圈块（`:87`）与空态（`:110`）**同屏并存** —— 用户看到「正在替你启动 Everything」和「输入关键词开始搜索」一起出现。

6.7 ① 补的 `try/finally` 方向对，但只覆盖「函数抛异常」，**没覆盖「推送本身送不到」** —— 后者不是异常，是静默返回 `false`。

修法两处：

1. `runFirstPage` 开头 `setLaunchingEverything(false)` —— 每次新查询都归零，丢失最多影响一次查询，不会永久卡住；
2. `result-list.tsx` 的 `showEmpty` 补 `&& !launchingEverything` —— 即使推送正常也避免同帧重叠（状态更新与推送到达本来就不在同一帧）。

### 6.9 审查修补第四轮（2026-10-28 15:37，dev 实例只读审查 `07c73ed0`+`4fc2dc41`）

**缺陷，已修 —— 6.8 的清零位置放错了侧，制造出启动提示抖动。**

6.8 把 `setLaunchingEverything(false)` 写在 `runFirstPage` 开头、token 检查之前，**无条件执行**。dev 按真实时序反算出的链条（逐条核实成立）：

- `esProbeCache` TTL **30 秒**（`es-probe.ts:62`），而 Everything 启动只需几秒 ⇒ 窗口期内每条 query 都命中缓存、都走 `not-running` 分支、各自重推一次 `starting-everything`（`file-search.ts:138`）；
- `EVERYTHING_AUTOSTART_COOLDOWN_MS = 10s` **只拦 spawn 不拦推送** —— `:352` 的判断在 `:138` 之后，推送在它前面；
- `enqueueEsSearch` 是**全局串行队列**（`es-probe.ts:214-219`），第一条查询在 while 里轮询最长 3 秒（`WAIT_MS=3000` / `POLL_MS=250`），第二条要排在它后面；
- 输入框防抖 **250ms**（`main.tsx:38`）。

于是：

| 时刻 | 事件 | `launchingEverything` | 界面 |
|---|---|---|---|
| T=0 | 查询#1 开始 | `false` | 搜索中... |
| T=+5 | 主进程推 `starting-everything` | `true` | 正在启动 Everything |
| **T=250** | **用户敲第二个字 → 查询#2，开头无条件清零** | **`false`** | **搜索中...** ← 启动态被抹掉 |
| T=250~3000 | #2 排队等 #1 跑完（串行队列） | `false` | 搜索中...（2.7 秒） |
| T≈3000 | #1 推 `done`；#2 开始跑，若仍未运行又推 `starting` | `true` | 正在启动 Everything |

`result-list.tsx:92-95` 与 `:106-108` 两块都是 `h-40` 居中、图标相同、只差文案 ⇒ 观感是文字在「正在启动 Everything」↔「搜索中...」之间反复跳。**6.8 之前没有这个问题**：启动态只由推送写入，整段启动稳定显示一次都不跳。

**根因**：把「兜底」放到了**状态生命周期的开头**。启动态的生命周期由一条 invoke 覆盖，起点清零等于「每次新查询都假装启动没发生」。

**改法**：挪到查询**结束**侧 —— `runFirstPage` 的 `finally`、token 检查之内。成立的前提已核：`startEverythingAndRetry` 在 `executeFileQuery` 里被 `await`，`done` 在它的 `finally` 发（`file-search.ts:145-148`），所以 **invoke 返回就意味着启动流程已结束**。在 `finally` 清零既修掉「推送丢失卡死」，又不会在启动进行中抹掉启动态。

### 6.10 真机验收发现的缺陷（2026-10-28 15:54，老大实测；**本轮审查验不出来，只有真机能撞上**）

**现象**：老大在 dev 实例里用文件搜索，界面报「已经替你启动过 Everything，但它没起来。多半是安装损坏，或它需要管理员权限才能索引。」

**核实结果：这句话三句全错。**

| 文案断言 | 实测事实 |
|---|---|
| 「但它没起来」 | Everything **正在跑**：PID 31688（用户会话）+ PID 6480（服务会话），StartTime **15:53:48** —— 正是我们拉起的 |
| 「多半是安装损坏」 | es.exe 当场实测 `exit=0`、**119ms** 返回 5 条结果、280 字节 |
| 「需要管理员权限」 | `Everything` 服务 `Status=Running` / `StartType=Automatic`，根本没缺权限 |

**根因两处，都在我这次写的代码里：**

**① 等待预算 3 秒太短（`es-probe.ts:74`）。** Everything 冷启动要读索引，这台机器上超过 3 秒。轮询到点仍未通 ⇒ 判定 `not-running` ⇒ 打上 `autostartAttempted`。而「索引还在读」和「进程起不来」在我的实现里是**同一个结果**，压根没分开。

**② 文案把三种成因揉成一句（`file-search-shared.ts:130-134`）。** 「慢 / 坏了 / 没权限」的处置方式完全不同（等 / 重装 / 提权），合成一句等于什么都没说 —— 而这恰恰是 S-253 本来要治的病：原来那句「软件没有运行」也是「什么都说了 = 什么都没说」。

**最讽刺的是，我们已经在 `:347-349` 探到了本体路径**（探不到会早退且不带 `autostartAttempted`）⇒ **exe 文件必然存在** ⇒ 从这个分支说出「安装损坏」在逻辑上就不成立。文案自我矛盾。

**改法两处：**

1. **`EVERYTHING_AUTOSTART_WAIT_MS` 3000 → 8000**。覆盖绝大多数冷启动，让情况压根不出提示。等待期间界面显示「正在启动 Everything」，是诚实的，不是干等。
2. **新增 `autostartFailed` 字段，把「慢」和「坏」分开**：
   - `spawn` 抛 `error`（UAC 拒绝 / 映像损坏 / 缺依赖）或进程**非 0 退出** ⇒ `autostartFailed = true`，轮询提前收手（等下去没意义），文案说「启动失败（多半被权限拦住或安装损坏）」+ `retry` + `redetect`；
   - 其余情况 ⇒ `autostartFailed = false`，文案说「**已经启动了，但索引还没读完**，等十几秒再搜一次」+ `retry`。
   - `-startup` 的官方语义是「正在运行就什么都不做」⇒ 已有实例时它**立刻以 0 退出**，这不是失败，所以判定必须收紧到 `code !== 0`。

**测试（此前 `fileSearchFailureView` 零测试覆盖，而它就是误报的现场）**：新增 8 条断言，钉「用户看得见的后果」而不是实现细节 —— 两种文案必须不同、没判 `autostartFailed` 时不许出现「损坏」、`actions` 精确匹配、以及遍历全部 `failure` 值确认「都有话可说 + 都有按钮可点」。`everything-search` 61 → **107 checks**。

> **变异验证**：把 `return result.autostartFailed` 改成 `return false`（即修前「两种情况一句话」的状态），立即 `AssertionError: 「索引还没读完」和「启动失败」必须是两句不同的话，不能合成一句`。还原后 107 全过。

**这轮说明一件事**：前三轮 dev 审查全是「按代码反算」，它能算出 381.5px、能推 250ms 时序，但**算不出「这台机器冷启动要几秒」**。3 秒这个数字是当初拍的，代码里读起来完全合理，只有真跑一次才知道不够。审查与真机验的不是同一层，缺一不可。
