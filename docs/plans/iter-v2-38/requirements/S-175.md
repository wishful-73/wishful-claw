⇒ 差分所需的三样东西里，**本地旧安装包 ✅、新包 + 新 blockmap ✅，唯一缺的就是服务器上的旧 blockmap**。

### 2.2　根因落点：`scripts/deploy.mjs` 的「只留当前版本」清理

`scripts/deploy.mjs:469-472`：

```sh
# 只留当前版本（老大 2026-09-23：官网不放历史版本；差分不需要旧包，回滚靠 GitHub Release）
sudo find '${CFG.downloadsDir}' -maxdepth 1 -type f \
  \( -name 'wishful-claw-*-setup.exe' -o -name 'wishful-claw-*-setup.exe.blockmap' \) \
  ! -name '*${version}*' -delete
```

**「差分不需要旧包」这句对 `.exe` 成立、对 `.blockmap` 不成立**（见 2.3 的链路）。0.2.37 发布时这条命令把 0.2.36 的两件一起删了，其中 blockmap 正是差分的必需输入。

### 2.3　差分链路（electron-updater 6.6.2 实读）

| 步 | 位置 | 说明 |
|---|---|---|
| 入口 | `NsisUpdater.js:47-51` | `disableDifferentialDownload` 未开 ⇒ 先试差分，返回 `true` 才回落全量 |
| 拼两份 blockmap URL | `AppUpdater.js:609` + `util.js:36-40` | 旧 = 新包 URL 里把版本号换成 `app.version` ⇒ `wishful-claw-0.2.36-setup.exe.blockmap` |
| **两份都必须下到** | `AppUpdater.js:638` | `Promise.all(blockmapFileUrls.map(downloadBlockMap))` —— 任一份 404 即抛 |
| 回落 | `AppUpdater.js:642-648` | `catch` ⇒ `log.error("Cannot download differentially, fallback to full download")` ⇒ `return true` ⇒ 全量下载 |
| 旧**安装包**从哪来 | `AppUpdater.js:628` + `DownloadedUpdateHelper.js:30` | `oldFile` = `<cacheDir>/installer.exe`，**本地**取，不从服务器下 |
| 谁写的 `installer.exe` | `app-builder-lib/templates/nsis/include/installer.nsh:93` | NSIS 安装器装机时自拷 `copyFile "$EXEPATH" "$LOCALAPPDATA\${APP_INSTALLER_STORE_FILE}"` |
| 名字怎么定的 | `NsisTarget.js:502` | `APP_INSTALLER_STORE_FILE = <updaterCacheDirName>\installer.exe` ⇒ `wishful-claw-updater\installer.exe` |

**结论**：旧 `.exe` 确实不需要（省 108 MB/版，清理合理）；旧 `.blockmap` **必须留**（实测 0.2.37 那份仅 **118,423 B**，0.2.36 那份 118,949 B —— 一个版本一百多 KB）。

`curl -s https://wishful-claw.work/downloads/latest.yml` 全文（356 B）：

## 三、修复方向

### 3.1　A：blockmap 保留最近 N 版（改 `scripts/deploy.mjs`）— ✅ 已实施

清理规则拆成两条：

- `.exe`：**只留当前版本**（现状不变，省空间）
- `.blockmap`：**保留最近 N 版**（按文件名版本号倒序，`N` 待裁，建议 3 ~ 5；单份 ~116 KB，5 版也就 600 KB）

为什么保留多版有意义：本地 `installer.exe` 是「**上一次装机用的那个包**」，不是「上一版」。用户若从 0.2.30 直接升到 0.2.38，差分要找的旧 blockmap 是 **0.2.30** 的 —— 只留一版照样 404。

> ⚠️ **`scripts/deploy.mjs` 不进版本控制**（`.gitignore:57` 的 `scripts/*`；`git log -- scripts/deploy.mjs` 为空，从未提交过 —— 文件头注释写明含服务器地址与密钥路径，不要提交）。
> ⇒ 改动只在本机生效，**口径已同步写进 `docs/release-workflow.md` §4.2**（进 git）✅。

**实施记录（2026-10-08）**：

- **裁定**：老大「blockmap 保留 5 个版本」⇒ N = **5**。
- **改法**：`CFG` 增 `blockmapKeepCount: 5`；清理段拆两条 —— `.exe` 仍只留当前版；`.blockmap` 用
  `find … -name 'wishful-claw-*-setup.exe.blockmap' | sort -V | head -n -5 | sudo xargs -r rm -f`
  保留最新 5 个（数量不足 5 时 `head` 输出为空，不会误删），并打印落位后的 blockmap 清单。
- **实测**（服务器 `/tmp` 造假数据）：7 个 blockmap（`0.2.9` / `0.2.10` / `0.2.33`~`0.2.37`）⇒ 保留
  `0.2.33`~`0.2.37` 五个，删掉 `0.2.9`、`0.2.10` —— **按版本序而非字典序**（`sort -V` 生效）；
  同目录 `.exe` 未被触碰；对真目录（当时 2 个 blockmap）干跑输出为空 ⇒ 不误删。
- **尚未验证**：整套 `installer` 动作实际发版跑一遍（等 38 发版时顺带验证）。

### 3.2　现象②的根治（更新说明的来源）— ✅ 定案：`latest.yml` 不带 `releaseNotes`，说明走官网独立 md

**先讲清「为什么切官网后说明就没了」**（这是本条实因，勘测时没说到位）—— 两个 provider 取说明的**管道不同**：

|  | 旧：GitHub 源 | 现：官网 generic 源 |
|---|---|---|
| 清单 | `latest.yml` | `latest.yml` |
| 说明来源 | 清单里没有 ⇒ **回头去 GitHub Releases 的 atom feed 抓 Release 正文**补上（`GitHubProvider.js:135-139` → `computeReleaseNotes()`） | **没有第二来源**，清单里没有就是空（`GenericProvider.js` 全文不含 `releaseNotes`） |

切源提交 `d8315a3c`（2026-09-23 15:25，S-129 收尾），`git tag --contains d8315a3c` = **v0.2.36 / v0.2.37**
⇒ **v0.2.35 及以前有说明（借的是 GitHub Release 的光），0.2.36 起没有了**。0.2.36 正是第一个官网源版本，老大恰好在它上面点检查更新，撞的就是切换点。
说明**并没有少写** —— `v0.2.36` 的 Release 正文 1333 字符、`v0.2.37` 1159 字符，内容都在，只是新管道不去取。

#### 定案（2026-10-08 老大裁定）

老大口径：**「跟 GitHub 上能保持一致；`latest.yml` 只保留版本 / 时间 / 地址这些，更新说明由另一个文档提供」**。

**三条事实**（本轮实读，非推断）：

1. **`latest.yml` 不带 `releaseNotes` 本来就是 electron-builder 的默认行为** —— 仓库无 `build/` 目录、未配 `releaseInfo`，工具**从来没产出过**这个字段。证据是现成的：`tests/latest-yml/program.ts` 拿 **0.2.35 的真实产物**当 fixture、逐字照抄，**里面就没有** `releaseNotes`（0.2.37 那份是手工救火塞进去的）。
   ⇒ 老大要的「只保留版本 / 时间 / 地址」= **什么都不用做**。
2. **官网下载页不看 `releaseNotes`** —— `website/src/lib/latest-yml.ts` 的 `parseReleaseManifest` 只取 `version` 与安装包文件名（注释即写「其余字段留给 updater」）。动这个字段对官网**零影响**。
3. **应用只从 `latest.yml` 读说明，没有第二来源** —— 链路唯一：`latest.yml.releaseNotes` → `info.releaseNotes` → `formatReleaseNotes`（`updater.ts:180`）→ payload → `UpdateReleaseNotes.tsx`。抽走就是空态「本次发布未提供更新说明。」

**方案：应用侧兜底**

```
latest.yml 有 releaseNotes  → 用（旧行为，一字不改）
没有                        → 去官网拉 release-notes-{version}.md
拉不到 / 版本对不上         → 落到空态「本次发布未提供更新说明。」
```

- **一个真源，喂两个发布面**：收尾那份 `.wishful-claw/notes/release-notes-v0.2.{N}.md` —— 一份给 `gh release create --notes-file`（GitHub Release 正文），一份传给官网（`/downloads/release-notes-{version}.md`）。**「跟 GitHub 保持一致」由此保证**，不是靠人工对齐两份文本。
- **文件名带版本号**（`release-notes-0.2.38.md`）：应用拿 `info.version` 直接拼 URL ⇒ **文件不在就是没说明，绝不会显示上一版的说明**。与 blockmap 那次同一类坑，宁缺勿错。
- **上传顺序**：notes md **先传**，`latest.yml` **后传**。
- **`electron-builder.yml` 零改动** —— 不喂 `releaseInfo`、不建 `build/`，清单自然干净。

**过渡期（绕不开，必须写进流程）**：已发出的 ≤ 0.2.37 客户端**只认清单内联**。若 0.2.38 的清单已抽干净，0.2.37 用户升 38 时**反而看不到说明 —— 比现在更差**。
⇒ **0.2.38 的 `latest.yml` 照旧带内联**，真正「干净」最早从 **0.2.39** 起。上面那条「有就用」的优先级正好让这次过渡零风险。

**实现细节（实施时定，助手有倾向）**：

- **官网根地址从哪来** —— 倾向**读包内 `resources/app-update.yml` 的 `url:`**（electron-builder 写的，更新源的唯一真源），一行正则取即可。**不要**在代码里再手写 `https://wishful-claw.work/downloads/`（多一个真源）。
- **更省的备选 A′**（本轮一并记下，供对比）：弹窗那块说明区**只放一个「查看更新说明」按钮**、点了开浏览器 —— **零主进程改动**，只加常量和按钮。**助手不推荐**：`UpdateReleaseNotes.tsx` 那块（`min-h-32` / `flex-1` / 独立滚动）本就是为内联渲染设计的，改成外链等于**砍功能**。

**⏳ 手工救火（2026-10-08，已完成）** —— 在根治方案落地前，把 0.2.37 的说明手工补进线上 `latest.yml`：

**缓存澄清（别再怀疑一遍）**：nginx 给 `/downloads/` 设了 `Cache-Control: max-age=604800`（7 天），看着吓人，但**两个消费方都主动绕过**：

### 3.4　现象③的根治（差分下载无进度）— ✅ 定案：关掉多区间（`useMultipleRangeRequest: false`）

**一句话**：electron-updater 在**多区间**差分路径上**根本不发 `download-progress`** —— 不是「渲染成未知」，是**根本没有数据**。

**机理**（实读 `node_modules/electron-updater/out`，6.6.2）：

- `differentialDownloader/DifferentialDownloader.js:105`：

  ```js
  if (!this.options.isUseMultipleRangeRequest && this.options.onProgress) {
  ```

  ⇒ **只有「不用多区间请求」时才创建** `ProgressDifferentialDownloadCallbackTransform`（旁注原文：`// TODO: Does not support multiple ranges (someone feel free to PR this!)`）；`:155` 再分叉，多区间走 `executeTasksUsingMultipleRangeRequests`。
- `total` / `transferred` / `bytesPerSecond` **三样都在那个不存在的 transform 里算**（每 1000 ms 推一次）⇒ **三样一起没有**，正是老大看到的三样。
- **为什么 GitHub 源时代没这毛病**：`providers/GitHubProvider.js:16` 把 `isUseMultipleRangeRequest` **硬编码成 `false`** ⇒ GitHub 源差分**有进度**。切 generic（官网）后走 `providerFactory.js:50`：

  ```js
  isUseMultipleRangeRequest: options.useMultipleRangeRequest !== false && isUrlProbablySupportMultiRangeRequests(options.url)
  ```

  我们**没传**该选项（`electron-builder.yml` 的 `publish` 只有 `provider` / `url`），而 `isUrlProbablySupportMultiRangeRequests(url) = !url.includes('s3.amazonaws.com')`（`providerFactory.js:11-13`）⇒ **官网 URL 判为支持多区间 ⇒ `true` ⇒ 进度被掐掉**。
- **为什么现在才暴露**：切官网后差分先因 blockmap 404 挂 → 回落**全量**（全量走**无条件创建**的 `ProgressCallbackTransform`）⇒ 机器 A 有进度；机器 B 补上 blockmap 后**差分真跑通**，才踩进这条路。⇒ **blockmap 补齐后，所有走差分的用户都看不到进度。**

**修法（一行）**：

| 路 | 做法 | 结论 |
|---|---|---|
| **打包期** | `electron-builder.yml` 的 `publish:` 段加 `useMultipleRangeRequest: false` | ✅ **已采用**（2026-10-08 老大拍板，见下） |
| 运行期 | `autoUpdater.setFeedURL({ provider: 'generic', url, useMultipleRangeRequest: false })` | ❌ 不用 —— 要把 URL 在代码里**再写一遍**，多一个真源（现状 `updater.ts:471` 只 `module.autoUpdater`，**没调** `setFeedURL`） |

打包期那条的落地链（实读）：`app-builder-lib/out/publish/PublishManager.js:193` 是 `{ ...publishConfigs[0], updaterCacheDirName }`（spread 保留额外键）→ generic 分支 `:416-424` 直接 `return options` → `:89` `writeFile(path.join(resourcesDir, "app-update.yml"), serializeToYaml(publishConfig))`。选项本身见 `builder-util-runtime/out/publishOptions.d.ts:175-177`（字段名精确拼写 `useMultipleRangeRequest`，注释自述「`url` 不含 s3.amazonaws.com 时默认 `true`」）。

**定案理由（2026-10-08 老大原话）**：「改成 false 确定了，**服务器带宽太小了**，加上现在为 true 还**导致进度显示 bug**」。

- **带宽是瓶颈** ⇒ 并行分片拿不到额外收益，顺序区间不吃亏 —— 这条否掉了原先「先量再定」的顾虑。
- **不修的代价更大**：进度 / 总量 / 速度三样全无，用户体感就是「下载中一片空白」。
- 顺带：关掉即**回到 GitHub 源时代的行为**（`GitHubProvider.js:16` 硬编码 `false`），0.2.35 及以前一直这么跑。
- **代价（据实记录，未实测）**：顺序区间 = 一个 range 下完再下一个（`DifferentialDownloader.js:202-213`，`response.once("end") → w(index)`），且**每 100 个区间故意歇 1 秒**（`:207-210`）。区间碎片多时会慢一截；真要量化，看服务器 nginx access log 的 range 条数与总耗时。

**实施记录（2026-10-08）**：`electron-builder.yml` 的 `publish:` 段已加该键（`useMultipleRangeRequest: false`）；`js-yaml` 解析复核 `publish.useMultipleRangeRequest` = boolean `false`，文件 no-BOM + 纯 CRLF。**该键随 publish 配置写进包内 `resources/app-update.yml`**（落地链见上）⇒ **待下一个构建（0.2.38）验证**。

**生效边界（重要）**：`app-update.yml` 是**打进安装包**的，运行时读的是用户本机那一份 ⇒ **救不了已发的 0.2.37**。0.2.37 → 0.2.38 这一跳照旧零进度；**从 0.2.38 起**才不带这毛病（前提是 38 打包时带上这一行）。
