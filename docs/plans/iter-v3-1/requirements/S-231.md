# S-231：运行时附加块由「前置」改为「后置」——修第三方服务端会话标题被 `<current_time>` 污染

## 1. 原话 / 来源

> 2026-10-26 14:24 老大：

> 2026-10-26 14:28 老大：

> 2026-10-26 14:42 老大：

> 2026-10-26 14:44 老大：

> 2026-10-26 14:44 老大：

性质：**请求报文形状修复**。不动机型、不动人格注入、不动渲染端。

## 2. 目标

一句话：**用户消息的运行时附加块（`<current_time>` / `<memory-recall>` / `<memory-update>`）从消息头部挪到尾部，让「取首条 user 消息做标题」的服务端截出来的是用户原话。**

## 3. 现状（2026-10-26 实查）

### 3.1 注入点：两层前置，标签打在消息最前面

| 顺序 | 位置 | 动作 |
|---|---|---|
| 1 | `AgentLoop.cs:259` | 每轮（iteration 循环之前）调 `InjectTransientPrefix(conversation, state)` |
| 2 | `AgentLoop.Helpers.cs:320-349` | 拼 `parts`：`PendingMemoryRecall` → `<memory-update>` → `<current_time>` |
| 3 | `AgentLoop.Helpers.cs:351-360` | `Text = parts.ToString() + msg.Text` —— **前置** |
| 4 | `AgentLoop.cs:357-360` | `iteration == 1` 时 `TryInjectMemoryRecallAsync(...)` |
| 5 | `AgentLoop.MemoryRecall.cs:112-116` | `Text = recallBlock + conversation[i].Text` —— **再前置一层** |

所以首条 user 消息的实际开头是：

```
<current_time>
2026-10-26 14:44 +08:00 (星期一)
</current_time>

用户原话……
```

（首轮若还触发召回，则最前面再叠一层 `<memory-recall>…</memory-recall>`。）

### 3.2 出站：`Text` 原样写进请求体

- `OpenAIChatRequestBuilder.cs:99-105`：`provider.systemPrompt` 先写一条 `role: system`

⇒ 标签原封不动到服务端，谁读首条 user 谁就吃到它。

| 代码 | 依赖什么 | 改后是否成立 |

### 3.4 我们自己的标题链路不受影响

## 4. 方案 A（已裁定）

### 4.1 改动清单

| # | 文件 | 改动 |
|---|---|---|
| 1 | `AgentLoop.Helpers.cs:351-360` | `Text = parts.ToString() + msg.Text` → `Text = 原话 + 分隔 + parts` |
| 2 | `AgentLoop.MemoryRecall.cs:112-116` | `Text = recallBlock + Text` → 追加到尾部 |
| 3 | `AgentLoop.Helpers.cs:313-316` | 注释订正：守卫用 `Contains` 的理由不再是「前置在 current_time 之前」 |
| 4 | `AgentLoop.MemoryRecall.cs:41-47` / `:109-110` / `:164-166` | 注释订正为「尾部附加块」 |
| 5 | `ConversationModels.cs:19-24` | `Text` 的注释由「前置了」改为「附加了」 |
| 6 | `OpenAIChatRequestBuilder.cs:143-148` / `AnthropicMessagesInputWriter.cs:125-128` | 注释同步 |

**只改拼接方向，不改块内容、不改标签名、不改注入时机。**

### 4.2 块间顺序

改造后消息结构（最后一条 user）：

```
用户原话

<memory-update>…</memory-update>

<current_time>2026-10-26 14:44 +08:00 (星期一)</current_time>

<memory-recall>…</memory-recall>
```

- `<memory-recall>` 由 `iteration == 1` 才注入，天然落在最后，符合「召回基于原话检索、附在尾部做参考」的语义
- `<current_time>` 与 `<memory-update>` 由 `InjectTransientPrefix` 一次性写定，此后不再变 ⇒ 前缀缓存不受影响

### 4.3 边界：空文本的消息

纯图片消息 `msg.Text` 可能为空。拼接必须判空，**不得产生开头的 `\n\n`**：

```
Text = string.IsNullOrWhiteSpace(msg.Text) ? blocks : msg.Text + "\n\n" + blocks
```

- 用 `IsNullOrWhiteSpace` 而非 `IsNullOrEmpty`：纯空格原话同样不能产生前导换行
- `blocks` = 各块拼装结果 `.TrimEnd()`（块自身自带尾随 `\n\n`，后置会在消息末尾留白行）
- 原话的尾部空白**保留**，只裁块
- 两处拼接点（`InjectTransientPrefix`、召回追加）共用一个 helper `AppendTransientBlock`，见 plan 步骤 1
- 注：纯图片消息出站时 `HasImageContent` 分支优先（`OpenAIChatRequestBuilder.cs:152-159` /
  `OpenAIResponsesInputWriter.cs:115-122`），整段 `Text` 被丢弃 ⇒ 这条判空锁的是**内存 `Text` 不变量**
  （`OriginalText`、压缩快照、后续轮次会读它），不是出站首字符

同理召回追加：`Text` 为空时直接赋 `recallBlock.TrimEnd()`。

### 4.4 注入块从不入库，无需迁移

`AgentLoop.cs:130-131` 同时持有 `GetConversation()`（活引用，注入改这份）与 `GetWireConversation()`
（入库来源，注入**不**改这份）⇒ 落库的 `messages.content` 从来不含 `<current_time>` / `<memory-*>`。

前置形状只活在**旧进程内存**里，重启即消失。⇒ **不存在「已落库的前置形状」**，不做数据迁移，
阶段六也不必抽查旧行。（原表述「已落库的历史行仍是前置形状」有误，2026-10-26 阶段三复审后订正。）

## 5. 影响面 / 风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | 模型对尾部块的响应退化（时间/召回信息靠后，注意力权重变化） | 阶段六真机对比同一问题在 OpenAI / Anthropic 两条路的回答是否仍带时间感知；这是本需求唯一非确定性风险 |
| 2 | 渲染端把标签露出来 | 渲染端全树 grep `current_time` 0 命中，历史从未显示过标签；且用户消息渲染走本地原文而非 `Text`。阶段一实施前再确认一次落库字段来源 |
| 3 | 前缀缓存命中率下降 | 尾部追加不触及历史消息字节，比前置更稳；首轮消息本身一变本来就会 miss 一次 |
| 4 | 压缩快照取错「用户原话」 | 走 `OriginalText` 优先，剥块为兜底，位置无关 |
| 5 | 召回块顺序变化影响召回质量 | 召回检索在注入前基于 `StripInjectedBlocks(userMessage)`，剥完只剩原话，与位置无关 |
| 6 | 渠道会话（`shared` scope）行为变化 | 该 scope 不注入 SOUL，但仍注入 `<current_time>`；一并后置，行为一致性更好 |

## 6. 范围外
