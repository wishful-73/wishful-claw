## 2. 症状与判据

| # | 现象 | 判据 |
|---|---|---|
| 1 | 会话里出现图像之后，某一轮起每轮都 400 | 换任意模型/渠道都 400（脏块在请求体里，与模型无关） |
| 2 | 400 报文点名 `.messages[N].image[0]` | N 是**历史**位置，不是本轮最新那条 ⇒ 脏块来自历史 |

| 5 | 报错后无法自愈 | 剥图重试没触发（文案不在 marker 表里），且 S-237 之后 400 不再盲目重试 |

## 3. 根因（2026-10-28 实读源码，逐处核到行）

### 3.1 主因：wire 组包**信任声明的 mediaType**，既不验真实字节、也不验上游白名单

三处独立实现，逻辑一字不差地重复：

| # | 文件 : 行 | 形态 |
|---|---|---|
| 1 | `OpenAIChatRequestBuilder.cs:273-281` `BuildBase64ImageUrl` | OpenAI chat（`image_url`） |
| 2 | `OpenAIResponsesInputWriter.cs:211-219` `BuildBase64ImageUrl` | OpenAI Responses（`input_image`） |
| 3 | `AnthropicMessagesInputWriter.cs:366-381` | Anthropic（`source.media_type`） |

三处的取法都是：

```csharp
var mediaType = JsonHelpers.GetString(source, "mediaType")
    ?? ProviderContentHelpers.DetectImageMediaTypeFromBase64(data)
    ?? "image/png";
```

两个漏洞叠在一起：

1. **declared 优先于事实。** 只要块里写了 `mediaType`，字节是什么完全不看。而 `ImageFileProbe.MediaTypeFor` 明确把 `.bmp` 认成 `image/bmp`（`ImageFileProbe.cs:25-38`，`FileReadTool.cs:99-103` 据此走 `ReadImage` 内联 base64）⇒ **agent 读一张 bmp，就会给上游发一张 `data:image/bmp;base64,...`**。OpenAI 系只收 png/jpeg/webp/gif，这条必 400。
2. **嗅探只是兜底，而且嗅不全。** `ProviderContentHelpers.DetectImageMediaTypeFromBase64`（`:22-42`）只认 png / jpeg / webp 的 base64 前缀：不认 **gif**（`R0lGOD`），也不认 bmp / tiff / svg / ico。嗅探不出就落 `?? "image/png"` —— **把任意脏字节贴上 png 标签发出去**，上游解码失败，报的还是同一句 unsupported image。

`??` 的顺序是这段代码的关键：它把「声明的正确性」当成了前提。声明来自扩展名、来自渠道侧探测、来自历史里落库的旧块 —— 每一环都可能错，而字节从不撒谎。

### 3.2 次因：这个 400 认不出来，也没有自愈路径

- `ImageInputErrors.Markers`（`ImageInputErrors.cs:24-44`）没有 `unsupported image` 这类文案 ⇒ 档 2 的剥图重试不触发。
- S-237 之后 `IsRetryableStatus` 收紧成 `429 / 5xx` ⇒ 400 连重试都不进，直接报错。
- 脏块还在 `SessionConversation` 里 ⇒ 下一轮照样带上 ⇒ **同一个 400 无限循环**，只有清历史能出来。

### 3.3 一句话

修复前：一张格式不被上游接受的图，代价是整个会话报废。
修复后：不该出门的图**在组包这一步就不出门**，且模型仍拿得到「读了哪个文件、多大、什么格式」的文字行。

## 4. 落点与改法

### 4.1 `ProviderContentHelpers.cs`：嗅探执行事实，白名单执行可行

1. 新增白名单常量（四家上游的共同底线）：

   ```csharp
   public static readonly IReadOnlySet<string> SupportedImageMediaTypes =
       new HashSet<string>(StringComparer.OrdinalIgnoreCase)
       { "image/png", "image/jpeg", "image/webp", "image/gif" };
   ```

2. `DetectImageMediaTypeFromBase64` 扩成**完整事实嗅探**（认得出 ≠ 上送）：

   | 前缀 | 结论 |
   |---|---|
   | `iVBORw0KGgo` | `image/png` |
   | `/9j/` | `image/jpeg` |
   | `UklGR` | `image/webp` |
   | `R0lGOD` | `image/gif`（**本次补上**） |
   | `Qk` | `image/bmp`（**本次补上**） |
   | `SUkq` / `TU0q` | `image/tiff`（**本次补上**） |
   | `PHN2Zy` / `PD94bWw` | `image/svg+xml`（**本次补上**） |
   | `AAABAA` | `image/x-icon`（**本次补上**） |

   后面五种嗅得出来但**不在白名单**，这正是要的效果：能把「错标」也拦下。

3. 新增唯一判定入口：

   ```csharp
   public static string? ResolveSupportedImageMediaType(string? imageBase64, string? declaredMediaType)
   ```

   判据顺序：
   1. 嗅探出真实类型 ⇒ **以嗅探为准**（声明与事实冲突时，事实赢）；
   2. 嗅探不出（极小/非常规字节）⇒ 才看 declared，归一小写、`image/jpg` → `image/jpeg`，且必须落在白名单内；
   3. 都不成立 ⇒ 返回 `null`，**调用方据此丢块**。

### 4.2 三处 wire 写入点统一收口

`BuildBase64ImageUrl` / Anthropic 的 `media_type` 全部改调 `ResolveSupportedImageMediaType`，返回 `null` 时跳过该块（现有 `if (string.IsNullOrWhiteSpace(imageUrl)) continue;` 就是那个出口），并 `WorkerLog.Warn` 记一条（带 mime 与截断后的字节前缀，便于判断是哪种脏图）。

丢块后模型不会瞎：`FileReadTool.ReadImage` 产出的 `[text("Read image: 路径 (尺寸, 格式)"), image]` 里那行文本本来就在，块被丢时它继续留着。

### 4.3 `FileReadTool.ReadImage`：入口侧不烧那一次往返

上游不收的格式（bmp / tiff / svg / ico），**不内联 base64**，直接返回一行文本：

```
Read image: <path> (<尺寸>, image/bmp). This format is not accepted by upstream model APIs
(png/jpeg/webp/gif only), so the pixels were not attached. Convert it to png/jpeg first if the
pixels are needed.
```

`ImageFileProbe.MediaTypeFor` **不动**（`.bmp → image/bmp` 是对的 —— 它回答的是「这是什么格式」，不是「上游要不要」）。判断放到 `ReadImage`，依据是 `ProviderContentHelpers.SupportedImageMediaTypes`。

## 6. 风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | **白名单误伤**：某家中转其实收 bmp，我们却拦了 | 拦下时记 Warn + 回文本说明，用户能看出「图没上去」而不是「莫名其妙报错」；白名单只写四家共同底线，不按单家放宽 |
| 2 | **丢块导致模型「看图看空」** | `ReadImage` 的 summary 文本行仍在，路径 + 尺寸 + 格式齐全，模型可据此让用户转格式 |
| 3 | 嗅探靠 base64 前缀，图片被重新编码后前缀变化 | 前缀是格式签名，重编码只会变成另一种**合法**格式的前缀（png/jpeg/webp/gif），仍在白名单；嗅不出才回落 declared |
| 4 | 三处 wire 收口漏一处 ⇒ 那条协议通道照样崩 | 逐处改完 grep `DetectImageMediaTypeFromBase64` 确认零残留调用（只留定义处） |
| 5 | 顺手把 `ImageInputErrors.Markers` 补上 `unsupported image` | **不做，见 §7** |

## 7. 不做什么（有意留手）

- **不把 `unsupported image` 塞进 `ImageInputErrors.Markers`。** 这是本次最需要写下来的判断：
  - `ImageInputErrors` 认的是「**这个模型不吃图像输入**」⇒ 命中后 `state.SuppressImagesForModel = true` **并且** `ImageVisionMemory.RememberUnsupported(provider, model)` **落盘永久记住**。
  - 「这张图的编码不对」是**一张图**的问题，不是**模型**的问题。把它塞进 marker 表，等于用一张脏图把一个 `(provider, model)` 永久标记成「不能看图」—— 此后该模型所有图都不发，比现缺陷更糟。
  - 结论：格式问题在**组包闸门**解决（本需求），能力问题留给 `ImageInputErrors`。两者不复用。
- **不做图像转码**（bmp → png）。转码要引图像编码依赖，AOT 体积与攻击面都不划算；而「读图」这件事用户完全可以让 agent 用 shell 转一下。
- **不动渲染端 `visual-context.ts`。** `mediaTypeFromPath` 的 `.svg → image/svg+xml` 与未知回落 `'image/png'` 确实也是脏源，但那个模块当前**全仓零调用方**（`applyRecentVisualContext` 无引用），改了不产生任何行为变化。
- **不动渠道侧的 mediaType 探测**（微信 / QQ / 飞书）。它们探出来什么就探什么，闸门在组包处统一兜。
- **不处理 URL 型 image 块**（`source.type === "url"`）。上游协议本身接受 http URL，问题不在这条路径上。
- **不改 `ImageFileProbe` 的格式表。** 它回答「这是什么格式」，`.bmp → image/bmp` 是正确答复；「上游要不要」是另一个维度的判断，放在 `ReadImage`。

落码期发现两处必须补的细节：

1. **前缀窗口 24 字符不够。** 48 字节解出来只到 `<?xml version="1.`，带 XML 声明的 svg 认不出来 ⇒ 会被当成「嗅不出」而回落 declared。改为 64 字符（48 字节），覆盖 `<?xml version="1.0"?><svg` 这段。
2. **「没有字节」不能回落 declared。** `ResolveSupportedImageMediaType(null, "image/png")` 原会返回 png —— 一个空块被贴上 png 送出去同样是 400。改为空数据直接 `null`。
3. **判据必须同源。** `HasImageBlock` / `HasToolImage` 一旦与闸门不同源，脏块会被判成「有图」⇒ 调用方走 parts 分支 ⇒ 写出只有 text 的 parts 数组 ⇒ 上游把 400 从「图不合法」换成「内容不合法」。两处都改为 `HasUsableImageBlock`。

### 8.5 补刀（2026-10-28，dev 实例实测反馈）

dev 实例拿真实图库跑了一遍：37 张 png + 5 张 jpg 正常，2 张 `.ico` **没进 ReadImage**，走的是普通文本分支。查 `ImageFileProbe.MediaTypeFor` 只有 6 个扩展名（`.png .jpg .jpeg .webp .gif .bmp`）—— `.ico` 不在表里，于是 `FileReadTool` 落到 `StreamReader(path, Encoding.UTF8).ReadLine()`，把二进制当 UTF-8 逐行读。

**这条不能靠「加白名单」解决**：白名单的口径是「上游收什么」，OpenAI 兼容协议只收 png/jpeg/webp/gif，把 ico 加进去就是把 400 请回来，正是本需求要消灭的东西。

真正的问题在 `MediaTypeFor` 的语义被混淆了 —— 它该回答「这是不是图像文件」，而不是「上游收不收」。修复前的后果是双输：模型看不到图（本来也看不到），还吃进一屏 `\x89PNG` 乱码占上下文，连「这是个 16x16 图标」都不知道。

改动：

| 文件 | 改动 |
|---|---|
| `ImageFileProbe.cs` | `MediaTypeFor` 补 `.ico → image/x-icon`、`.tif`/`.tiff → image/tiff`；`TryReadSize` 补 ICO 尺寸（首个目录项，宽高各 1 字节，**0 表示 256**）；注释写清「这张表是『是图像』，不是『上游收』」 |
| `FileReadTool.cs` | `Description` 同步：`.bmp/.tiff/.ico` 只描述不附像素，`.svg` 按文本读 |
| `ReadImageRegressionTests` | +13 条：`.ico/.ICO/.tif/.tiff` 映射、16x16 尺寸、**0 字节读成 256**、ico 读出来无 image 块 / 走 image 分支 / 报真实格式与尺寸 / 不被当文本解出替换字符 |

**`.svg` 刻意不列进表里。** 它是文本，让模型读源码比给一行「格式不接受」有用得多。同理 `KNOWN_IMAGE_EXTENSIONS`（主进程，管粘贴/拖拽）**不扩** —— 扩了只会多造一个上面传的脏源，闸门在组包处照样兜。

### 8.6 结案（2026-10-28 09:48，老大校正验收口径）

**本需求结案，且不需要造脏图会话做真机复验。** 老大原话：

> 基本都测过了，脏图会话没必要，主要是语法出现脏图会话，不出现脏图污染会话才是根本

（「语法」按上下文应为笔误，指「会生成/出现脏图的场景」。）

**验收点被校正为「源头不产生脏块」，不是「已脏的会话能救回来」。** 这个校正站得住，因为修法本身就是三道闸门：

| 闸门 | 位置 | 作用 |
|---|---|---|
| 1 | `ProviderContentHelpers.ResolveSupportedImageMediaType` | **嗅探优先**，声明只在嗅不出时作数且须在白名单内；空白 base64 直接返回 null |
| 2 | 三处 wire 组包（OpenAI Chat / OpenAI Responses / Anthropic Messages） | 走同一道 `HasUsableImageBlock`，收不了的块**直接丢弃**，不贴上假 `image/png` 标签发出去 |
| 3 | `FileReadTool.ReadImage` | 上游不收的格式**不内联像素**，只回一行元信息 |

脏块**没有生成路径** —— 不是「进去了再拦」，是「进不去」。所以 §8.4 那条「真机未验」不再是遗留项，而是**验收口径本身换了**。

**判据覆盖情况**：`ImageMediaGate` 37 条断言钉住三道闸门，`ReadImage` 51 条断言钉住入口格式分支。§5 第 2 条判据（脏块历史里后续每轮不再 400）现在退化为兜底 —— 闸门都堵住后，历史里不该再出现脏块可供测试。
