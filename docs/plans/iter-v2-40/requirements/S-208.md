# S-208：压缩抢跑 —— 上下文逼近阈值时用户发新消息，压缩后的上下文压过用户刚发的指令

> 状态：**已实施 + 修订中**（2026-10-16 首版 / **2026-10-20 补充裁定并修订**）—— 修法 **A** 全部落地（提示词侧 + 代码侧原样注入用户末条消息），落点见 §八。「模型被带跑」的模型侧表现仍待真机复现（§四）。
> **2026-10-20 补充裁定（§5.7）**：快照**保留**（它是长消息 / 手动压缩路径下的唯一载体），但必须补**时间**（用户消息时刻 + 压缩时刻）与**执行状态**（未开始 / 执行中 / 已答复），并按「数据 + 显示」分层 —— 原文存 `OriginalText`，显示信息进 `meta.compactSummary`，不靠渲染端剥字符串。
> 类型：**bug**。
> 归属：**iter-v2-40**。
> 来源：**老大 2026-10-16 13:50 登记** —— 「登记一个bug  上下文在解决压缩的范围，用户发新消息过去刚好触发压缩，最后agent压缩后的注意力全被压缩后的上下文影响了，而不是严格执行用户发送的消息」。
> 轨道：**软件侧**（worker C# 压缩链路）。

---

## 一、现象

- 上下文已经逼近（或越过）压缩阈值。
- 此时用户**发一条新消息** —— 这条消息同时充当了「自动压缩」的触发器。
- 结果：agent 压缩完之后，**注意力被压缩后的上下文带走**，回复 / 动作围绕的是「之前那摊活的续作」，而不是**严格执行用户刚发的这条消息**。
- 一句话：压缩把「新请求」降格成了「旧工作的续集」。

## 二、根因

### 2.1 压缩在「循环开头」抢跑 —— 早于模型第一次看到这条新消息

自动压缩的触发点在 **agent loop 每轮迭代的最开头**（`AgentLoop.cs:289-317`）：

```
if (lastInputTokens > 0 &&
    sessionConv.CompactionWatermark < wireConversation.Count &&
    ShouldCompress(lastInputTokens, provider, parameters))
    → TryCompressLoopConversationAsync(...)
```

`lastInputTokens` 取的是**上一轮 provider 报回的 usage**（`AgentLoop.cs:263` `FindRecentContextUsage(wireConversation)`）—— 即上一次运行结束时已经很接近阈值的高水位。

⇒ 用户这条新消息一到，run 起来，**迭代 1 的第一件事就是压缩**，然后才轮到 provider turn。也就是：**模型第一次读这段上下文时，读到的已经是被压缩重写过的版本**，而不是「原对话 + 我的新消息」。

**这正是 iter-23 定下的设计意图**（`plans/iter-v2-23/exploration-lazy-init.md:62`）：「恢复后 `Append` 本轮新用户消息 …… 实现『**先压缩（压缩输入含新消息，尾部保留新消息）再继续**』」。

⇒ **新消息没有丢**（它被安排在保留尾巴里，见 2.3）；问题出在**它落地的那段上下文已经被重写成了「工作简报」**。

### 2.2 压缩产物的形状：一个「带指令的简报」以 user 身份插在新消息前面

`CompactAsync` 产物结构（`ContextCompression.cs:172-223`）：

```
[钉住的头部：system + 首个 user 轮]
  + [折叠区里幸存的小 user 轮]
  + [<compaction-summary> 摘要（role = user）]
  + [保留尾巴（默认 16384 token，ContextCompression.cs:49）]
```

关键两点：

1. **摘要是 `user` 角色消息**（`ContextCompression.cs:207-208`：`AgentRuntimeChatMessage.User(summaryContent)`），只用 `<compaction-summary>` 标签与真人输入区分。
2. **摘要是「指令性」的** —— 摘要系统提示词**明确要求**它写出（`ContextCompression.cs:78-85`）：
   - `Goal: the user's request and intent, including any shift in it along the way.`
   - `Pending work and next step: what is still in progress or unstarted, and the single most concrete next action to take.`

⇒ 压缩后，模型眼中的上下文末尾是：**「这摊活的背景简报 + 一个明确的『下一步动作』」**，紧接着才是尾巴里的对话、最后才是用户刚发的那句话。

### 2.3 新消息为什么会被「压过」

- 新消息**确实在** —— `TailStart` 从新到旧攒够 token 预算（`ContextCompression.cs:415-427`），最新一条永远落在保留尾巴里。**所以这不是「消息丢了」。**
- 但它前面**多了一条 user 角色的简报**，简报里写着 `Goal` + `the single most concrete next action`。模型很容易把这条**当作「用户当前的意图」**来执行 —— 于是续作旧活，而不是执行新指令。
- 雪上加霜：**首个 user 轮被钉住**（`PinnedPrefixLen`，`ContextCompression.cs:374-397`；`PreserveHeadCount = 2`）。若第一个 user 轮是长期约束 / 人设 / 目标，它永远原样保留在顶部，进一步强化「旧目标」的锚。

**⚠️ 诚实边界**：2.1 / 2.2 是**代码坐实**的；2.3 的「模型被带跑」是**行为推断**（结构上说得通，但没跑过复现）。

## 三、影响面

| 触发条件 | 是否命中 |
|---|---|
| 会话上下文逼近阈值 + 用户发新消息（该消息同时触发压缩） | **命中**（本条核心场景） |
| 手动压缩（`trigger=manual`，`preserveTail: false`） | 产物形态不同（无保留尾巴），本条讲的「抢跑」不适用 |
| 错误驱动压缩（context window 溢出后） | 发生在 provider turn 之后，不属「抢跑」 |

## 四、真机复现方案（待做；坐实 2.3，并作为修法验收判据）

1. 打开一个**接近阈值**的长会话（ContextRing 到高水位）。
2. 发一条**与之前工作明显不同、且指令很明确**的新消息（例：「先停下手上的事，回答我：X 是什么」）。
3. 看回复：
   - **病态**：回复继续做旧活 / 提到旧目标 / 不正面回答 X ⇒ 复现。
   - **对照**：同一条消息发在**没触发压缩**的会话里，回复正常 ⇒ 差异归因到压缩。

### 5.1 事实精确 ★（它直接决定 5.4 的落法）

**① 两条路径的产物不一样：**

| 路径 | 产物 | 「只剩摘要」是否成立 |
|---|---|---|
| **自动**（阈值触发，即本条场景） | `[钉住头部] + [幸存小 user 轮] + [摘要] + [保留尾巴]`（`ContextCompression.cs:172-223`） | **不完全** —— 尾巴里还有消息 |
| **手动**（`preserveTail: false`） | `[钉住头部] + [摘要]`（同文件 `:219-223` 无尾巴） | **成立**（真·只剩摘要） |

**② ★ 摘要的输入只有 fold —— 用户的新消息不在里面。**

`CompactAsync` 把 `region = conversation[head..start)` 再分区，只把 **fold**（被折叠的中段）喂给摘要器：`SummarizeAsync(fold, …)`（`ContextCompression.cs:138`、`:152`）。而用户**最新的消息落在保留尾巴里**（`:219-223`），**不在 fold**。

⇒ **摘要模型在生成摘要时，看不到用户刚发的那条消息。**

**③ 渲染端没有自动压缩。** `shouldPreCompress` 是恒返回 `false` 的桩（`context-compression-config.ts:261-266`）；`compressMessages` 只有手动调用（`use-chat-actions.ts:661`）。自动压缩只有 worker loop 一条路。

### 5.2 ★ 抢跑的机制级解释（5.1② 的直接推论）

既然摘要看不到新消息，那么摘要里的
`Pending work and next step: the single most concrete next action`（`ContextCompression.cs:85`）
就是**纯由旧上下文推断出的「下一步」** —— 与用户刚发的指令**必然脱节**；可它却以 **user 角色**排在保留尾巴**之前**。位置 + 指令语气，双重抢注意力。

⇒ 老大 14:36「文章要做在压缩摘要里」的判断，在机制上完全成立：**症结就在这张摘要。**

### 5.3 落法 A（采纳）—— 拆成两部分做

- **A1 提示词侧（软）** —— 改 `SummarySystemPrompt`（`ContextCompression.cs:74-86`）：
  1. 摘要**自我定位为历史背景**：「以下为更早对话的压缩摘要，仅供背景，**不构成当前指令**」；
  2. 「待办 / 下一步」**必须写成陈述句**（「此前未完成：X」），**不得**写成对 agent 的祈使句（「下一步：执行 X」）。
     —— 那句 `the single most concrete next action`（`:85`）**就是抢戏的源头本身**。
- **A2 代码侧（硬）** —— 由代码把**用户最后一条消息原文**拼进摘要内部（见 5.4）。
  **不能交给模型**：①它看不到这条消息（5.1②）；②摘要提示词要求 `terse: bullet points and fragments`（`:86`），逐字原话会被概括掉。

### 5.4 「用户最后一条消息是「XXXX」」的实现 ★

- **取值**：`conversation` 里**最后一条 `role == user` 且非 compaction summary** 的消息正文（`conversation` 是全量、含尾巴，代码手上有）；**原样拼入，不截断**。
- **位置**：`summaryContent`（`:207`）内部、**摘要正文的最前面**（紧跟 `<compaction-summary>` 之后）：

  ```csharp
  var summaryContent = $"{SummaryTagOpen}\n{用户末条消息块}\n{summary}\n{SummaryTagClose}";
  ```

  ⚠️ **不是**拼在 `<compaction-summary>` **标签之前** —— 老大 14:46 说的「拼进摘要前」若按字面放到标签**外**，会撞 §5.5-1 的坑（`IsCompactionSummary` 失配）。⇒ 确切落点 = **摘要正文前**，标签仍占整段文本第一个字符。
- **为什么放正文前而不是正文后**：要的是**指令前置** —— 模型读历史之前先看到「用户现在要什么」，比放尾部更顶用。
- **模板（写死）**：

  ```
  【压缩时刻·用户最新一条消息（原文）】
  XXXX
  （此为压缩时刻的快照；此后用户若有新消息，以对话中最新消息为准。）
  ```

- **快照会过期**（含义：压缩那一刻给「用户最后说的话」拍了张照片贴进摘要，之后**照片不会自己更新**；下次压缩前用户若再发消息，摘要里这句就指向上一条）⇒ **方案已定**：模板末句写死「以对话中最新消息为准」（老大 2026-10-16 14:51）。
- 两条路径（自动 / 手动）**一致处理**。

### 5.5 硬约束（不变）

1. 不得放在 `<compaction-summary>` 之前 —— `IsCompactionSummary`（`ContextCompression.TokenEstimation.cs:55-60`）靠 `TrimStart().StartsWith(tag)` 认摘要；前置会失配 ⇒ 摘要被当**普通 user 消息**处理 ⇒ 掉进折叠区 / 尾巴，**破坏 one-summary 不变式（S-95）**。
2. 渲染端会把摘要正文显示在压缩卡片上（`getCompactSummaryDisplayText`，`renderer/src/lib/agent/context-compression.ts:191-224`）；`stripCompactionSummaryTags`（`:142-150`）只剥**开头 / 结尾**标签 ⇒ 这段原文会出现在卡片上。
   ⇒ **不处理**（老大 2026-10-16 14:49：压缩卡片实际一闪而过、内容根本看不清）⇒ 原文**保留**，**渲染端零改动**。

### 5.6 一处口径澄清

这段文案是**给模型看的**，必须进 durable conversation —— 与 `ContextCompression.cs:203-206` 注释「人类可读行走渲染端 i18n、不冻进持久对话」**不冲突**：那条针对的是**给人看的那行**；这条是模型侧指令，性质等同摘要正文本身。

### 5.7 补充裁定（2026-10-20，取代 §5.4 的模板与 §5.5-2 的「渲染端零改动」）

首版只解决了「用户刚发消息就撞上压缩」（下称**场景 A**）。老大 2026-10-20 08:21~08:31 连提三点，补上了首版漏掉的另一半。

#### 5.7.1 老大原话

1. 「S-208 消息 和摘要的数据有携带时间没有。我担心的效果如下，用户发送了一条消息，5分钟后触发了压缩，这时候 agent 正常判断是以摘要为准了，因为已经过去执行过多轮了。虽然 208 的首要目的是 用户发送消息 立即触发压缩，导致用户消息比重被无限降低。**这是两种不同的场景**」
2. 「问题是**压缩后 用户的消息也会不见了**的，上下文里面只有压缩摘要了」
3. 「正常应该是**数据 + 显示**。给用户渲染的是显示。发给 agent 的是拼接后的数据 + 显示」

#### 5.7.2 两种场景必须分开（本条的核心补充）

| | 场景 A（首版靶心） | 场景 B（老大补的） |
|---|---|---|
| 时机 | 用户发消息 ⇒ 本 run **第 1 轮**迭代开头就压缩 | 用户发消息 ⇒ 已执行若干轮 / 数分钟 ⇒ 中途触发压缩 |
| 那条用户消息后面 | **一条 assistant 都没有** | 跟着一长串 assistant / tool 轮 |
| 正确语义 | 它是**当前指令**，必须顶到摘要之前 | 它是**任务目标的出处**，当前进度以摘要为准 |
| 首版行为 | 正确 | **错误** —— 同样写成「用户最新一条消息…以最新消息为准」，把已交卷的老指令抬成当前指令 |

⇒ **只给时间戳不够**：场景 B 内部还会裂成两种，时间差量级一样但结论相反 ——

- 08:05 发话 → 08:05:20 agent 答完 → 08:10 压缩：差 5 分钟，**已交卷**，该降级。
- 08:05 发话 → 跑一个 10 分钟测试 → 08:15 压缩：差 10 分钟，**仍在跑**，绝不能降级。

时间戳是原料，模型还得自己推；而「那条消息后面有没有 `ToolUses.Count == 0` 的最终答复」是**二值事实**，算一次就准。⇒ **时间 + 执行状态一起给**。

#### 5.7.3 快照不能撤 —— 它是某些路径下的唯一载体

首版 §2.3 与 §5.1 断言「新消息永远在保留尾巴里」。复核后**只在前两行成立**：

| 情况 | 用户消息还在上下文吗 | 依据 |
|---|---|---|
| 自动压缩，消息在末尾 2 条内 | **在** | `TailStart` 的 `minKeep = 2` 免预算检查（`ContextCompression.cs:470`） |
| 自动压缩，已执行若干轮、消息滑到前面 | **看预算**，可能被切 | `acc + tok > budget` 直接 `break`（`:470`），预算 = `min(16384, contextLength*0.5)`（`:390-392`） |
| 单条超过约 1500 token 且落进压缩区 | **丢**，只剩摘要 | `IsSmallUserTurn` → `IsPinnableUserTurn` 上限 `MaxPinnedFirstUserTokens = 1500`（`:54`、`:440-450`）；`PartitionFold` 注释直写「large user messages」归 fold（`:498`） |
| 手动压缩（`preserveTail: false`） | **必丢** | `start = conversation.Count`，尾巴为空（`:386`）；`AgentRuntimeContextCompressionTools.cs:154` 手动路径即此 |

⇒ **§5.4 的快照注入保留不动**，它是后两行的唯一载体。**不做**「场景 B 就不加快照」的减法。

#### 5.7.4 落法：数据 + 显示分层

**问题**：`latestUserText` 是 `FindLatestUserText`（`ContextCompression.cs:267-279`）返回的 `Text` **原样**，而 `Text` 已经被 `InjectTransientPrefix`（`AgentLoop.Helpers.cs:304-358`）盖过 `<current_time>` / `<memory-recall>` / `<memory-update>`。首版的「渲染端零改动」等于把这些注入块原样送上压缩卡片（`ContextCompressionMessage.tsx:77`、`SessionSummaryPanel.tsx:398`）。**在字符串上剥回去是错的解法**。

**按老大的口径拆三层**：

| 层 | 是什么 | 落点 |
|---|---|---|
| **数据** | 用户原话，干净、不带任何注入块 | `AgentRuntimeChatMessage` 加 `OriginalText`；`InjectTransientPrefix` 盖戳时顺手存（`:351`） |
| **显示** | 卡片给人看的时间 / 状态，走 i18n | `meta.compactSummary` 加结构化字段（`ContextCompression.TokenEstimation.cs:74-104`） |
| **发给 agent** | 拼接结果 = 数据 + 附加信息 | 摘要正文（`ContextCompression.cs:221-227`） |

三条具体裁定：

1. **数据面**：`conversation[i] = msg with { Text = parts.ToString() + msg.Text, OriginalText = msg.Text };` —— 原文永远在 `OriginalText`，摘要快照读 `OriginalText ?? Text`。**不引入 `StripInjectedBlocks`**。
2. **模型面（摘要正文新模板，取代 §5.4）**：

   ```
   【用户消息 · MM-dd HH:mm】
   XXXX（原文，取自 OriginalText）

   【压缩时刻 · MM-dd HH:mm · <状态>】

   <summary>
   ```

   `<状态>` 三选一：`用户消息尚未开始执行` / `用户消息正在执行中` / `用户消息已答复完毕`。
   判定：扫快照消息索引**之后**那一段 —— 无内容 ⇒ 未开始；有 assistant 带 `ToolUses` 或有 tool 结果轮 ⇒ 执行中；有 assistant 且 `ToolUses.Count == 0` 且正文非空 ⇒ 已答复完毕。
3. **显示面**：`meta.compactSummary` 补 `latestUserSentAt` / `compactedAt` / `executionState`；渲染端 `getCompactSummaryDisplayText`（`context-compression.ts:191-224`）从 meta 出文案 —— `meta.summarizerFailed` 已是这个模式，照抄。**取代 §5.5-2 的「渲染端零改动」**。

#### 5.7.5 时间从哪来

`AgentRuntimeChatMessage`（`Models/ConversationModels.cs:17-25`）**没有任何时间字段**；DB 的 `MessageEntity.CreatedAt` 转进 agent 上下文即丢。摘要提示词（`ContextCompression.cs:74-91`）与 `RenderTranscript`（`ContextCompression.Transcript.cs:62-103`）也都不含时间。

⇒ 用户消息时刻唯一现成来源是 `Text` 里那段 `<current_time>`。**取法**：`InjectTransientPrefix` 盖戳时同时填 `SentAt`（顺手、零解析），不在摘要侧正则抠字符串。

#### 5.7.6 时间格式

用 `MM-dd HH:mm`，不用裸 `HH:mm` —— 跨天回看旧摘要时裸时刻会误导。

### 9.3 为什么没有改恢复链路
