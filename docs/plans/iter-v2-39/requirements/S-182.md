## 三、口径（2026-10-10 08:35 定）

**「下载次数」= 安装包被下载的总次数** —— 官网点击与应用内自动更新**都算**（老大 08:35：「我要的不是这个版本的下载，应用内自动更新这个也算上」⇒ 要的是**分发总量**，不是官网页面的点击量）；**检查更新（`latest.yml`）不算**。

- **计入**：`/downloads/wishful-claw-{版本}-setup.exe` 的请求，不论来自浏览器还是 `electron-updater`。
- **不计入**：`latest.yml`（检查更新）与 `*.blockmap`（差分辅助文件，非安装包本体）。

⚠️ **一个 URL 两类下载者、且请求形态完全不同** ⇒ 合并计数后，**必须先定义「怎么算一次」**（见 §四「计数规则」）。

| **应用内自动更新** | nginx `/downloads/` 日志 | 不变 |

⇒ **本需求的聚合脚本必须吃两个日志源**（`wishfulclaw-downloads.log` + `wishfulclaw-clicks.log`）；两源**完全正交、不重叠**（加速站点击只进 `clicks`，本站直链只进 `downloads`）⇒ **各自去重后相加即可**。

**中转页 `/go` 的 nginx 侧**（页面本身归 S-186，这里只给它的日志落点）：

```nginx
location = /go {
    access_log /var/log/nginx/wishfulclaw-clicks.log combined;
    try_files $uri.html =404;          # /go -> /go.html（与现有 /download 同款）
}
location ~ ^/(download|guide|changelog|go)/$ { return 301 /$1; }   # 尾斜杠规则补 go
```

**2026-10-10 10:38 定**：b 由「裸 `302`」改为**官网中转页**（老大原话见 `S-186.md` §六）—— **计数原理不变**（页面请求进 nginx 即计一次），但返回的是真实页面，能给用户兜底链接；两个日志源仍**正交、不重叠**。

**b 与 A 的分工不变**：A（服务器日志）仍承担**应用内自动更新**这一半；b 只补**官网点击**那一半 —— **本需求不是回到当初被否的「纯前端埋点」**。

## 四、方案候选（A 采用；B 经修订后**部分采用**）

### A（采用 · 主方案）服务器侧日志聚合 —— 承担「应用内自动更新」这一半

1. **nginx**：① 把 `/downloads/` 的 `access_log off;` 换成**独立日志**（如 `/var/log/nginx/wishfulclaw-downloads.log`）；② **给官网中转页 `/go` 配独立日志** `wishfulclaw-clicks.log`（＋尾斜杠 301 正则补 `go`，见 §三「口径修订」）；页面请求继续走 `access.log`。
2. 新增一个 `log_format`，带上 **`$http_range`** 与 `$http_x_forwarded_for`（如未来走 CDN）。
3. **服务器 cron 每日聚合** —— 在 14 天轮转窗口内把当日数据抽出来，落到 `/data/stats/`（按日 JSON），**长期累积**。
4. **查看**：本地加一条命令 `node scripts/site-stats.mjs`（SSH 拉取 + 打印报表）；**官网读同一份 JSON** —— **下载页显示下载次数，全站 footer 显示访问次数**。

#### 计数规则（关键 —— 决定数字对不对）

**不能用「无 `Range` 的首次请求」计数**：`electron-updater` 的**差分下载**只发带 `Range` 的段请求，可能**完全没有一次完整 GET** —— 那样会把自动更新全漏掉。

**采用：按 `客户端 IP + User-Agent + 文件名` 去重（窗口 1 小时）** —— 同一「IP-客户端-文件」在窗口内的所有请求（浏览器多线程、updater 分段）**只算 1 次**；跨窗口（隔天再下）算新的 1 次。

| 场景 | 实际请求形态 | 计数 |
|---|---|---|
| 浏览器点一次下载 | 1 个 GET | **1** |
| 浏览器多线程 / 断点续传 | 多个（含 `Range`） | **1**（同窗口去重） |
| `electron-updater` 全量 | 1 个 GET | **1** |
| `electron-updater` 差分 | 1 个 blockmap + N 个 `Range` | **1**（blockmap 不计） |

代价：NAT 出口（公司 / 校园网）同一小时内的多人下载会被并成 1 次 —— 可接受，UV 类指标都有此特性。

- 优点：数据真实（覆盖**应用内自动更新** + 走本站直链的下载 + 右键另存 / 复制直链）；页面与后台**一份数据源**；**不新增后端服务**（中转页的日志落在 nginx，页面里不用写上报代码）。
- 缺点：**官网点击改走加速站后数不到那一半**（由 B′ 补）⇒ **必须两源合并**；**只能从「改配置那天」起算，历史下载无法回溯**；配置改动在服务器侧，**不入版本库**（同 `scripts/deploy.mjs`），口径必须另找地方留档。

### B′（部分采用）官网点击统计 —— 只补「官网点击」这一半

- **加速站各项的 `href` 不直指第三方**，改为先到官网的**中转页** `/go?src=<源>&u=<GitHub直链>`；页面请求进 nginx 的 `clicks` 日志（**＝一次点击**），页面再 `location.replace()` 跳到加速站。⚠️ **中转页地址已于 2026-10-11 收紧为 `/go?src=<源名>`（去掉 `u`，目标改由页面读 `latest.yml` 自己拼）；计数口径不变** —— 详见 [`S-186.md`](S-186.md) §9.1。
- **中转页里不用写任何上报代码** —— 计数靠页面请求本身；跳转成败与我们无关。
- **不承担自动更新**（那一半仍由 A 数）⇒ **与 A 相加（各自去重后）才是完整的「下载次数」**。
- 原「B 前端埋点」被判作废的理由是「天生数不全」—— 那条理由针对的是「**用它单独承担整个下载统计**」；**改为只承担官网点击之后，该问题消失**。
- 相对原 B 方案更轻：**无新增后端与存储**（nginx 一条 location 即可）。
- 已知偏差：数的是「**点击**」，不是「加速站真实传输完成」（第三方不回报）。

### C 第三方统计（Umami 自建 / 百度统计 / GA）

- 只能拿「访问量」；下载量与自动更新仍要自己搞后端。
- Umami 要自己部署一套（Node + 库），对这台小服务器是负担。

## 六、影响面与风险

1. **改动位置**：`/etc/nginx/snippets/wishfulclaw-site.conf`（`/downloads/` 日志 + **`/go` 中转页的 location 与 `wishfulclaw-clicks.log`**）+ root crontab + `/data/stats/`（新建）+ 本地 `scripts/site-stats.mjs`（新建）。**全在服务器与脚本侧，主仓业务代码零改动**；前端那半（中转页本身 + 下载按钮改 `href`）归 **S-186**。
2. **不入版本库** ⇒ 必须像 `deploy.mjs` 那样**把口径与脚本留档在仓库文档里**（否则换机器即丢）。落点建议同 `docs/release-workflow.md` 或另立一份官网 SOP。
3. **日志体积**：只记请求行（不记字节），可忽略；且会被 logrotate 的 `*.log` 规则自动纳入轮转。
4. **历史数据缺口**：下载统计**从零开始**，没有过去的数据可补。
5. **不可与「升级成功率」混淆**：`latest.yml` 的请求数只是「检查更新」次数，**不代表升级成功**（后者要应用侧上报）。
6. **⚠️ 与 S-186 强依赖**（老大 2026-10-10 10:21 裁定后新增）：官网点击改走加速站 ⇒ 本需求**必须同时聚合 `wishfulclaw-downloads.log` 与 `wishfulclaw-clicks.log` 两源**。10:38 定为**官网中转页**方案后两源**正交、不重叠**（加速站点击只进 `clicks`，本站直链只进 `downloads`）⇒ **各自去重后相加即可**。⇒ **两条需求应一起收口**，刀序见 `plan.md` §三。
