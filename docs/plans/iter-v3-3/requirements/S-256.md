## 3. 现状链路（2026-10-28 实读代码）

### 3.1 四层批处理都在

| 层 | 现状 | 结论 |
|---|---|---|
| main | `AdaptiveEventBatcher` 33ms / 150ms 两档 + `maxBufferSize` 200 | S-135 成果，在 |
| store | `text_delta` / `thinking_delta` 进 `_pendingStreamDeltas`，rAF 合并后一次 `setState` | 在 |
| 渲染池 | `use-typewriter.ts`：步长 `getCatchupStep = ceil(pool / catchupFrames)`（agile K=2、elegant K=3）；帧间隔 `resolveFrameIntervalMs` 在池 > `pressurePoolSize` 时线性放宽到 `maxFrameIntervalMs` | 在 |
| 正文分块 | `useStreamingMarkdownBlocks`：按空行切「稳定块」，`MarkdownContent` 是 `React.memo`，稳定块稳定字符串跳过重解析，只重解析 tail | 在 |

⇒ 所以本次**不是**「每个 delta 一次 setState」那种老问题。

### 3.2 三条没兜住的口子

**(1) 单帧步长无上限 —— 制度性**

`src/renderer/src/hooks/use-typewriter.ts:64-66`：

```ts
export function getCatchupStep(poolSize: number, config: RenderPoolConfig): number {
  if (poolSize <= 0) return 0
  return Math.max(1, Math.ceil(poolSize / config.catchupFrames))
}
```

积压 100 000 字符 ⇒ 单帧喂 50 000 字符进解析器。而**测试把这个行为钉死了**，`tests/streaming-render-pool/program.ts:66-68`：

```ts
eq(getCatchupStep(1_000_000, config), Math.ceil(1_000_000 / config.catchupFrames),
   `${style}: a huge backlog is drained proportionally, not step-capped`)
```

⇒ 任何「加步长上限」的修法都必然要**改这条断言语义**，这是口径变更，不是 bug 修复。

**(2) 正文 tail 可能无限大 —— 分块失效的两种情况**

`useStreamingMarkdownBlocks` 只在「空行 + 下一行顶格」时切块（`use-streaming-markdown-blocks.ts:108-120`）。所以：

- 模型连续输出**没有空行的长段落** ⇒ 一个块都切不出来，tail = 全文累积
- **未闭合的 ` ``` ` fence / `$$` 数学块** ⇒ 整段都被当成未稳定，tail = 全文累积

两种情况下 `MarkdownContent` 每帧全量重解析 + 重建整棵 React 元素树 + DOM diff。老大给的样本正好是第一类。

**(3) 跑完那一下是全量重排**

`markdown-renderer.tsx:493`：非流式直接 `<MarkdownContent text={text} />` 一次性解析全篇。思考块同理 —— `ThinkingBlock.tsx:200-260`，`isThinking` 结束后把整段思考塞进 `<Markdown>` 全量解析。几万字的两条消息 ⇒ 收尾瞬间两记全量解析。

### 3.3 顺带确认的两件事

- **全仓零 `content-visibility` / `contain`**（grep 整仓无命中）⇒ 长消息的布局成本不会被浏览器跳过。
- 思考流**已经不走 markdown**（`ThinkingBlock.tsx:188-197` 流式中是纯文本 `{renderPool.text}` 直塞 DOM）⇒ 它的每帧成本是 **text node 替换 + 整段 reflow**，不是解析。S-149 写的「思考块重排整段长文本」这半句，对应的是这个 layout 成本，比 markdown 解析轻，但不是零。

## 4. 根因判断（标注可信度）

**已查证（代码层事实）**：上面 §3.2 三条口子、§3.3 两条、以及测试断言把「无步长上限」钉死。

**推断（未实测权重）**：本次触发的主因是 (1)+(2) 叠加 —— 巨长积压下每帧排掉半个池子，且 tail 因为无空行切不开整个重解析。**我没有在这台机器上抓到触发时的帧耗时数据**，权重排序需要实测确认，见 §5.1。

**「无法点击」的机制**：一次 rAF tick 里要串行做完 markdown 解析 → React commit → 浏览器 layout/paint。单帧一旦超过几十 ms 且连续不断，点击事件只能在渲染间隙排队 ⇒ 观感就是「像截图」。

## 5. 方案

### 5.1 第一阶段：先让数据说话（不做任何策略改动）

`src/renderer/src/lib/streaming-perf.ts` 已经有现成的四桶埋点（DEV 生效）：`longTask` / `rafGap` / `reactCommit` / `renderPool`，带 p95 / max 与阈值（`RENDER_POOL_P95_LIMIT_MS = 2` 等）。

用老大那段文本做压测样本，取三个数定主攻方向：`longTask` p95/max、单帧 `reactCommit` 耗时、`renderPool` 单帧 flush 耗时。**权重不由猜决定。**

### 5.2 候选修法（按我的建议排序）

| 候选 | 内容 | 治什么 | 代价 |
|---|---|---|---|
| **A. 单帧步长上限** | `getCatchupStep` 加 `maxStepChars`（量级 1000~2000），积压再大每帧也只吃这么多 | 直接压住单帧成本 | **要改 `streaming-render-pool` 的「无步长上限」断言**（口径变更，需老大拍板）；大积压时文本「追上来」变慢 |
| **B. tail 强制分段** | tail 超 N 字符且无空行可切时，按固定长度硬切（流式期间 markdown 可能有细微差异，跑完再全量重排一次） | 治 (2)，即老大这次的样本形态 | 流式期间列表/引用渲染可能闪一下 |
| **C. `content-visibility: auto`** | 给消息体 / 大块加 `contain-intrinsic-size` | 长消息滚动的 layout 成本 | 视口内那条治不了，只是廉价补充 |
| **D. 思考流截窗** | 流式期间只渲染最近 N 字符 | S-149 原话的方案 | 产品取舍：用户看不到前面的思考 |

**我的建议**：先 5.1 实测，然后 **A + B** 一起上（A 治单帧绝对成本，B 治分块失效），C 顺手加。D 先不做 —— 思考流现在是纯文本，不是解析瓶颈，砍掉可见内容不划算。

### 5.3 必须一起改的文档与断言

- `tests/streaming-render-pool/program.ts:66-68` 那条「一百万字符也按比例排干、不设步长上限」的断言，任何步长上限落地都要改成新契约；
- iter-v2-29 T-15「取消步长上限」的结论要么明确作废，要么改成「上限从 ∞ 收到 X」并写清理由（长思考追不上与卡死之间取谁）——**这条是口径，不是代码**。

## 6. 验收

**压测场景**（唯一凭据）：单条 assistant 消息，输出 ≥ 50 000 字符、无空行分隔的长段落（照老大给的样本形态），跑一次完整流式。

| 指标 | 门槛 |
|---|---|
| 流式期间 `longTask` p95 | 明显下降（基线待 5.1 实测后写死） |
| 流式期间点击「停止」响应 | ≤ 500ms |
| 用户可感知 | 页面不再出现「静止、点不动」 |
| 跑完那一次全量重排 | ≤ 1 次、不影响交互 |

门禁：`npm run typecheck` 0 错；`npm test` 不回归（步长上限落地后 `streaming-render-pool` 断言按新契约更新）。
