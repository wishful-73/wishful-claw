# S-177：渠道会话长时间空闲后，首条入站消息误报「Agent run was not started」

> 状态：**✅ 已实施**（2026-10-09）。方案由老大 09:36 裁定（入队改判 `return true`）、09:50「根据开发工作流推进」；计划见 [`../plan-s177/plan.md`](../plan-s177/plan.md)。归属 iter-v2-38（老大原话「38迭代 登记一个bug」）。
> 现象通道：**微信**（`weixin`）。飞书 / 钉钉是否同理**未验证** —— 三渠道共用同一条 `plugin:session-task` → `use-channel-auto-reply` 链路，按代码应同病，但**未实测**。

## 一、原话 / 来源

老大 2026-10-09 09:14：

> 「38迭代 登记一个bug 微信渠道上过10分钟或者几个小时或者几十个小时，首次发送消息 微信上报错Agent error: Agent run was not started，过一段时间后实际agent又回复微信消息回来了」

## 二、现象（拆三句）

1. **前置**：渠道会话距上次活动 **≥ 10 分钟**（老大另举几小时 / 几十小时）。
2. **触发**：此时该会话的**首条**入站消息。
3. **表现**：微信侧立刻收到 `Agent error: Agent run was not started`；**随后（一段时间后）agent 的正常回复又发到了微信**。

⇒ **关键矛盾：报「没启动」，实际启动了。** 这条矛盾是定位的锚点 —— 它把嫌疑范围直接锁到「返回值为假、但副作用为真」的分支上。

## 三、代码链路（实读）

### 3.1 文案产生点 —— 逐字命中

`src/renderer/src/hooks/use-channel-auto-reply.ts:299-308`：

```ts
    const started = await sendPromise
    if (!started) {
      throw new Error('Agent run was not started')
    }
    return true
  } catch (err) {
    activeAutoReplies.delete(sessionId)
    console.error('[ChannelAutoReply] sendMessage failed:', err)
    await sendChannelNotice(task, `Agent error: ${err instanceof Error ? err.message : String(err)}`)
    return false
  }
```

⇒ 微信那句 `Agent error: Agent run was not started` = `sendChannelNotice` 拼出来的，`err.message` 正是第 301 行那句。**铁证。**

### 3.2 `sendMessage` 的 `false` 有**四种**语义

`src/renderer/src/stores/chat-store/index.ts`：

| 分支 | 行 | 含义 | 会不会自己开跑 |
|---|---|---|---|
| 无 sessionId | `:236` | 参数问题 | 不会 |
| **会话被判忙** | `:268-272` | **已入队**，等前一个 run 结束派发 | **会** |
| Worker 拒绝 | `:487-508` | run 未启动（`result.started === false`） | 不会 |
| 异常 | `:514-529` | 抛错 | 不会 |

`:268-272` 原文：

```ts
      if (state.streamingMessages[sessionId]) {
        const { enqueuePendingSessionMessage } = await import('@renderer/hooks/use-chat-actions')
        enqueuePendingSessionMessage({ text: userText, sessionId, rawParams: params }, sessionId)
        return false
      }
```

### 3.3 「后来真的回复了」= 入队分支的必然结果

入队后由 `dispatchNextQueuedMessageForSession` 在**当前 run 结束**（`loop_end`，非 aborted / error）时派发 —— `index.ts:1743-1751`。

⇒ **只有「入队」这一条分支能同时满足「立即返回假」+「稍后真开跑」**。老大的现象因此**高度指向 `:268-272`**。

### 3.4 同类缺陷 iter-31 修过一次，渠道这条漏改

`docs/progress/v2-iter-31.md:89-91`（原文实读）：

> 三层根因：`sendMessage` 的 `false` 返回值被复用（入队也是 false）；派发侧把 `!started` 一律当失败，还撤渠道回执 + 标 `blocked`；Worker 侧把整份 JSON 信封交给 agent …
> 修法：派发侧调 `sendMessage` 前记队列长度、失败后**回查队列**判断到底是不是入队。

⇒ 那次修的是**会话任务派发侧**。`use-channel-auto-reply.ts:299-302` **至今没有这个回查** —— 同一个坑，另一条路。

### 3.5 报错时注册被注销（次生问题）

`use-channel-auto-reply.ts:305`：进入 catch 时 `activeAutoReplies.delete(sessionId)`。
⇒ 即便 run 随后真跑，**这条 auto-reply 的注册已经没了**。「回复怎么还能发回微信」需进一步勘测（候选：另经 `registerExternalChannelReply` 管道；或微信侧消息重投后走了新一轮）。

## 四、根因（**部分锁定，一条未定**）

**已锁定**：渠道派发侧把 `sendMessage` 的 `false` 一律当「未启动」，**不区分「已入队」** ⇒ 误报。这是**缺陷本体**。

**未定（卡住的关键）**：**为什么长时间空闲后 `streamingMessages[sessionId]` 仍有值？**

- `streamingMessages` 是**纯内存态**（`streaming-slice.ts:39` 初始 `{}`），不持久化。
- 正常清理点：`loop_end`（`index.ts:1651`）/ `error`（`index.ts:1875`）/ `setStreamingMessageId(sessionId, null)`（`streaming-slice.ts:53-54`）。
- ⇒ 残留意味着**上一轮 run 的终结事件没送达渲染端**。候选：系统休眠 / 唤醒后事件丢、Worker 侧异常退出、窗口重载。

**残留有两种成因，取证必须分清**（两者现象完全一样：假忙 → 入队 → 报错 → run 真结束后派发 → 回复）：

- **甲：终结事件丢了** —— run 其实早已结束，渲染端没收到 `loop_end` / `error`。
- **乙：终结事件还没发生** —— run 在 Worker 侧一直没结束（典型：某次 provider 请求挂住且无超时），渲染端据实显示「忙」。

**这一条必须靠日志定案，不靠猜**（见 §八 取证清单）。

### 4.3 Worker 侧已排除「结束却不通知」

实读 `AgentRuntimeTools.ExecuteRunAsync`（`src/runtime/WishfulClaw.Agent/AgentRuntimeTools.cs:273-325`）—— **每条退出路径都发终止事件**：

| 路径 | 终止事件 |
|---|---|
| 正常跑完 / 撞轮次上限 | `AgentLoop.cs:521` `EmitLoopEndAsync(loopEndReason)` |
| 取消（`OperationCanceledException`） | `:289` `EmitLoopEndAsync("aborted")` |
| 其它异常 | `:295-310` 先发 `error`，再 `EmitLoopEndAsync("error")` |

且 `finally`（`:312-324`）**无条件**清 `ActiveRuns` / `ActiveSessionRuns` / `RunSlots`。

⇒ 「Worker 侧 run 已结束却没通知」**不成立**。老大「会话是空闲的」这一观察与代码一致 ⇒ **run 确实早已结束**。

⇒ 残留只可能在**渲染端**：`loop_end` 已发出，但渲染端 `streamingMessages[sessionId]` 没被清。机制只剩两种 ——

1. 事件**没送达**渲染端（主进程转发丢 / 渲染端重载）；
2. 送达了但 **key 错位**：清理打在 `targetSessionId` 上，而它优先取 `envelope.sessionId`（`index.ts:665`）；若它 ≠ 写入时的 `sessionId`，`delete state.streamingMessages[targetSessionId]`（`:1651`）就删不到那一条。

### 4.4 「进队列」与「队列派发」共用同一个判据（**本次的关键约束**）

`dispatchNextQueuedMessageForSession`（`use-chat-actions.ts:865-875`）派发前先查 `hasActiveSessionRunForSession(sessionId)`，而后者（`:939-944`）**第一个看的就是 `streamingMessages[sessionId]`**。

⇒ **残留不清，排队的消息就永远派发不出去。** 这正好解释老大看到的「过一段时间才回复」—— 那就是残留被清掉的时刻。

⇒ **只做「甲」（不报错）等于把「报错」换成「静默卡住」，体感不会变好。甲必须与残留销账机制一起看才闭环。**

## 五、修复方向（**老大 2026-10-09 09:36 已裁定 —— 已实施，见 §九**）

老大原话：

> 「渠道发送消息，有运行中就进队列，这里返回 true，没有运行中就启动运行，这里也返回 true，而不是现在莫名其妙报错 Agent error: Agent run was not started」

⇒ **裁定方案：把「入队」从 `false` 挪进 `true`。** 即改 `src/renderer/src/stores/chat-store/index.ts:268-272`：

```ts
      if (state.streamingMessages[sessionId]) {
        const { enqueuePendingSessionMessage } = await import('@renderer/hooks/use-chat-actions')
        enqueuePendingSessionMessage({ text: userText, sessionId, rawParams: params }, sessionId)
        return false        // ← 改为 return true
      }
```

`sendMessage` 的新语义：**`true` = 已受理**（立刻跑 / 已排队）；**`false` = 未受理**（无 sessionId / Worker 拒绝 / 异常）。

### 5.2 残留不因本刀消失（**必须写清**）

本刀只治「误报」。§4.4 那条约束仍在：残留期间消息会**安静排队**，直到残留被清才派发 —— 与用户预期一致（消息会稍后回复），但**残留本身仍未销账**。

- 残留销账（原「丙」）**不在本刀范围**。
- 若要销账，候选是 `AgentRuntimeTools.HasActiveSessionRun(sessionId)`（worker 侧**现成**的只读判据，`ActiveSessionRuns.ContainsKey`，目前仅手动压缩在用）—— 给渲染端加一个只读 IPC 去核，比「空闲超时猜」可靠。**待老大另行裁定。**

### 5.3 顺带发现（不扩范围，仅记）

真失败（Worker 拒绝 / 异常）时，渠道路仍报硬编码的 `Agent run was not started`，**真因被吞**（例如 Worker 实际回的是 `Session already has an active agent run: …`）。是否改为透传 `result.error`，**待老大裁**。

## 六、代价与取舍

- **不能动** iter-30 BUG-A/B 的入队前置拦截（`:255-272`）—— 那修的是「跨会话派发撞 Worker 单会话单 run 锁致渲染端丢 run」，删了会复现丢流。
- **不能动** `setStreamingMessageId` 的「已有活跃 run 不覆盖」（`streaming-slice.ts:48-51`）—— 同理。
- 甲的代价：入队时渠道侧**不再立刻回执**（本来也不该回执错误），用户体感变为「消息稍后才有回复」—— 与正常排队一致。

## 七、刻意不做（边界）

- **改** `sendMessage` 的返回值语义（老大 09:36 裁定：入队从 `false` 挪进 `true`）—— 原写「不改」的边界**已被该裁定取代**。但仍**不**引入三态返回 / 新返回类型，也**不**动消费点的判据结构（只改一个 `return` 值 + 注释）。
- 不给微信单独写分支 —— 三个渠道共用同一链路，修就修链路。
- 不碰 Worker 侧的 run 互斥 / 会话恢复。

### 8.1 二分判据（拿到 ① 就能砍掉一半范围）

在 `~/.wishful-claw/logs/{日期}.log` 里搜 `agent run accepted runId=… sessionId=<该渠道会话>`：

- **一条都没有** ⇒ 渲染端就拦下了（`:268` 假忙入队），run 根本没发到 Worker ⇒ 问题在渲染端事件送达（甲）。
