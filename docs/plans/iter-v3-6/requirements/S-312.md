# S-312 · 窗口最小化被当成「用户把窗口拖窄」—— 左栏被误收，切回来还不恢复

> 状态：**✅ 已实施（2026-11-04），门禁通过，待真机验收**
> 登记：2026-11-04 13:41（老大口述）
> 实施：2026-11-04
> 来源：老大原话「窗体切换到其它窗体，再切回来，就感觉窗体进行了一次初始化，左侧面板我本来是展开的，再次进来后直接就收起了」
> 关联：S-306（Tauri 换壳，本条是在壳上测出来的，但**根因在渲染层，Electron 同样中招**）

## 一、现象

窗口切到别的应用再切回来，左侧面板（会话列表）原本是展开的，回来后就变成收起状态；应用其余部分看着正常，不像崩溃，更像「面板状态被重置了一次」。

## 二、根因

不是「状态被重置」，是**收侧判定被一次假读数触发，而且只触发一次，没人负责恢复**。

两件事叠在一起：

1. **窗口最小化 / 隐藏时，WebView2 会把视口报成一个占位尺寸**。本机实测：`1680×1072` → **`144×18`**，恢复时再报回 `1680×1072`。这个读数会让页面收到一次 `resize`。
2. **`MainLayout.tsx` 的 resize 监听只在「变窄」时跑判定**（这是 S-247 时有意为之：变宽不自动弹回，否则用户手动收掉的面板会被窗口拉伸反复掀开）。于是：

| 步骤 | 视口 | 判定 | 结果 |
|---|---|---|---|
| 最小化 | 1680 → **144** | 144 < 1680 ⇒ 变窄 ⇒ 跑 `enforceViewportWidthGuard()` | 聊天窗「只剩 144px」⇒ **收掉左侧栏** |
| 恢复 | 144 → 1680 | 变宽 ⇒ **不跑判定** | 左侧栏**回不来** |

**缺的不是恢复逻辑，是「这个读数根本不是用户操作」。** 用户从没把窗口拖到 144px 宽 —— 那是系统给的占位值。

## 三、影响面

- 用户每次最小化 / 切走再切回，左栏状态就丢一次，得手动点回来；
- 右栏同理（`enforceViewportWidthGuard` 两侧都判，`resolveViewportYield` 决定收哪一侧）；
- Electron 与 Tauri 共用同一份渲染层 ⇒ 两边都会中招，不是 Tauri 壳的问题。

## 四、修法

一处改动，`src/renderer/src/components/layout/MainLayout.tsx`：

```ts
const MIN_REAL_VIEWPORT_WIDTH = 480
...
if (width >= MIN_REAL_VIEWPORT_WIDTH && width < lastWidth) {
  useUIStore.getState().enforceViewportWidthGuard()
}
```

**阈值取 480 的依据**：壳自己的窗口下限是 **900**（`src/main/index.ts:116` `minWidth: 900`）/ **960**（`shell-tauri/src/main.rs:157` `min_inner_size(960, 640)`）。真实视口不可能低于窗口下限，480 已经是下限的一半，留足余量给未来调小下限的情况。占位读数（144）在这个阈值下直接跳过判定。

`lastWidth` 仍然照常更新 —— 跳过判定不等于跳过记录，否则恢复后的下一次真实拖动会拿占位值当基准、算不出「变窄」。

## 五、范围边界

- **不改**`enforceViewportWidthGuard` 与 `resolveViewportYield` 的判定逻辑（那条「变窄才收、变宽不自动弹回」的语义是对的）；
- **不做**面板状态持久化 —— 本次是「不该收的别收」，不是「收掉的要记住」；
- 不涉及中英语言包、不涉及主进程。

## 六、验收

1. 左栏展开 ⇒ 最小化 ⇒ 还原：左栏**仍然是展开的**；
2. 右栏打开 ⇒ 切到别的应用再切回：右栏**仍然打开**；
3. 真实把窗口从 1440 拖到 900：左栏**照旧被收掉**（判定没被削弱）；
4. 拖宽回 1440：左栏**不自动弹回**（既有语义不变，需要自己点开）。

## 七、工作量

单文件、约 10 行（含注释）。落点只有 `MainLayout.tsx` 的 resize 监听。
