## 2. 现象

本地启动 `http://localhost:xxxx` 开发服务器，改了页面、已迭代多个版本后：

| 动作 | 结果 |
|---|---|
| 工具栏刷新按钮 | 新内容 ✓（`reload()` 会重验证，本来就好使） |
| **地址栏手输（另一个）地址回车** | **旧内容 ✗** |
| 系统浏览器打开同一地址 | 新内容 ✓ |

⇒ 只有「命令式导航」这条路径会命中旧缓存。用户实际工作流是「手输地址 → 看到旧的 → 手动点一下刷新」，所以诉求落在**让刷新这一下彻底可靠**。

## 3. 代码链路

### 3.1 两条完全不同的导航路径

| 路径 | 入口 | 底层调用 |
|---|---|---|
| **命令式导航** | 地址栏回车 → `navigate()` → `requestBrowserNavigation()` → `navigationSeq + 1` → `nextCommittedUrl` 返回新地址 → `setCommittedUrl` → **`<webview src>` 属性变化** | Electron 内部 `loadURL` |
| **刷新** | 工具栏 `onReload`（`BrowserPanel.tsx:436`）→ `runWebviewCommand('refresh', wv => wv.reload())` | `reload()` |

`navigate`（`BrowserPanel.tsx:204-227`）：

```ts
if (isSameBrowserUrl(normalized, storedUrl)) {
  runWebviewCommand('navigate', (wv) => wv.reload())   // 同址：走 reload
  return
}
requestBrowserNavigation(normalized, sessionId, projectId)   // 换地址：写 url + navigationSeq
```

`requestBrowserNavigation`（`stores/ui-store-browser-slice.ts:66-79`）同步写两项：`{ url, navigationSeq + 1 }`。

### 3.2 `reload()` 与 `loadURL()` 的缓存语义不同

这是本缺陷的核心：

| | 导航类型 | 缓存行为 |
|---|---|---|
| `reload()` | **重新验证式** | 主资源带 `Cache-Control: max-age=0`（等价条件请求），强制向服务器确认 ⇒ 一定拿最新 |
| `loadURL()` / `src` 赋值 | **普通**导航 | 遵守服务器缓存头；服务器没给明确新鲜度头时走 **Chromium 启发式缓存**（`(now − Last-Modified) × 10%` 当新鲜期），新鲜期内根本不发请求 |

而 `reloadIgnoringCache()` 是第三档 —— 硬刷新，**连条件请求都不发，全部绕过缓存重新下载**。

### 3.3 本地服务器大多只给 `Last-Modified`，正好触发启发式缓存

`python -m http.server`、部分轻量 dev server、nginx 默认配置只返回 `Last-Modified`，不给 `Cache-Control` / `Expires` ⇒ 完全落进启发式缓存 ⇒ 改了文件也不请求。

这与实测吻合：`reload()` 重验证所以正常，`loadURL()` 命中启发式缓存所以旧。

### 3.4 缓存落在磁盘且跨重启保留

`shared/browser-plugin.ts:8`：

```ts
export const BUILTIN_BROWSER_PARTITION = 'persist:wishfulclaw-browser'
```

`BrowserPanel.tsx:84` 挂到 webview。`persist:` = 持久化分区，缓存落 `userData/Partitions/wishfulclaw-browser/`，**重启不清**。复用浏览器数据模式不给 partition ⇒ 落 default session，同样落盘。

⇒ 缓存进脏内容后重启软件也带不走 —— 这正是需要「硬刷新」兜底的原因。

### 3.5 无任何清缓存入口

全仓 `clearCache` / `clearStorageData` / `reloadIgnoringCache` **零命中**。工具栏只有 后退 / 前进 / 停止 / 刷新 / 地址栏，设置里没有「清除浏览数据」。

## 4. 根因

**缓存本身没坏，是「刷新」这个动作的力度不够。**

1. **路径不对齐** —— 刷新走 `reload()`（重验证），导航走 `loadURL()`（遵守缓存头甚至启发式缓存）。同一用户意图，两条路给出不同结果。
2. **本地服务器缺缓存头** —— 只给 `Last-Modified`，正好落进启发式缓存，使 `loadURL()` 在开发场景下几乎必然命中旧内容。
3. **没有硬刷新出口** —— 用户唯一能拿最新的手段是 `reload()`，但它只是重验证，遇到服务器回 304 或缓存策略更激进时就无能为力。

**关键判断：缓存本体要保留**（外部站点靠它提速）。缺的是给用户一个「我确定要最新的」的按钮 —— 也就是把刷新按钮升级成硬刷新。

## 5. 修复方向

### 5.1 主修（唯一）

`WebviewTag.reloadIgnoringCache(): void` 存在，注释即「Reloads the guest page and ignores cache」（`electron.d.ts:20073`），与 `reload()` 同签名同用法，**纯替换，零结构改动**：

```ts
// src/renderer/src/components/layout/BrowserPanel.tsx:436  改前
onReload={() => runWebviewCommand('refresh', (wv) => wv.reload())}
// 改后
onReload={() => runWebviewCommand('refresh', (wv) => wv.reloadIgnoringCache())}
```

一行。不新增依赖、不动状态机、不碰 main 进程。

### 5.3 边界：本次不治「手输地址」那一步

硬刷新只让**点刷新**一定拿到最新；**手输地址导航依然走 `loadURL`、依然可能命中缓存**。用户工作流仍是「手输地址 → 看到旧的 → 点一下刷新」。

若要让手输地址本身就不吃旧缓存，需要下面这些（**本轮不做**，留作后续）：

| 备选 | 做法 | 状态 |
|---|---|---|
| A · session 层按 host 注入 `no-cache` | main 进程注册 `webRequest.onBeforeSendHeaders`，对 loopback / 私有网段补 `Cache-Control: no-cache` | 备选，未采用 |
| B · `wv.loadURL(url, { extraHeaders })` | 换掉 `<webview src>` 驱动方式（`LoadURLOptions.extraHeaders` 可用，`electron.d.ts:21999`） | 备选，风险高于 A |
| C · 导航前 `session.clearCache()` | 每次导航清整个分区 | 不做，粗暴且误伤外部站点缓存 |
| D · 「清除浏览数据」入口 | 工具栏 / 设置 | 本轮不做 |

## 6. 代价与取舍

- **硬刷新会稍慢** —— 绕过缓存必然重新下载。只在用户**主动点刷新**时发生，不是常态路径，可接受。
- **外部站点点刷新也全量拉** —— 单按钮不区分本地/外部。要区分只能走备选 A 的 host 判定，本轮不做。这对日常浏览是可接受的代价（刷新本就是重载）。
- **持久分区不能改** —— 去了 `persist:` 会连登录态、localStorage 一起丢，代价远超收益。
- **不改自动重载路径** —— `:382` 与设备切换若一并硬刷新，会让每次挂载/切设备都全量拉，得不偿失。

## 7. 刻意不做

- **不做 per-host 缓存策略** —— 本轮只做「刷新按钮硬刷新」，session 层拦截（备选 A）不做。
- **不动 `committed-url.ts` 的状态机** —— 地址去重、站内跳转不重载这些逻辑来之不易，本次改动完全不涉及它。
- **不全局禁用 HTTP 缓存** —— 会让所有外部站点每次导航全量拉，明显变慢。
- **不在导航前 `clearCache()`** —— 见 §5.3 方案 C。
- **不改 `partition` 命名或去掉 `persist:`** —— 登录态与 localStorage 会一起丢。
- **不处理 Service Worker** —— 官网 `/website` 已核实无 SW：`package.json` 无 `vite-plugin-pwa`，源码无 `registerSW` / `workbox`（`ReleaseManifest` 是产品发布清单，与 Web App Manifest 无关）。
