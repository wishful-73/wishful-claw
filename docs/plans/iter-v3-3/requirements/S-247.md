## 2. 现象与判据

| # | 现象 | 现在能确认到什么程度 |
|---|---|---|
| 1 | 内存占用「奇高」 | **未量化**。没有具体 MB 数、没有进程名、没有出现时机 |

## 3. 现状勘测（2026-10-28 实读源码）

### 3.1 全仓没有内存观测

| 位置 | 现状 |
|---|---|
| Electron 主进程 | **零采样**。全树搜 `app.getAppMetrics` / `getProcessMemoryInfo` / `process.memoryUsage` **零命中** |
| 渲染进程 | 同上，零命中 |
| Worker（.NET） | 有 `worker/memory` 端点（`SystemModule.cs:18-19`，回 `SystemMemorySnapshot`：`ManagedBytes` / `HeapBytes` / `FragmentedBytes` / `WorkingSetBytes`），**但渲染端与主进程对它的调用是零** —— 纯死代码 |
| 日志 | `logs/YYYY-MM-DD.log` 里没有任何周期性资源行 |

也就是说：现在出现「内存奇高」，我们能拿到的唯一证据是任务管理器一张表，且**事后无法复盘**。

### 3.2 进程结构（决定「奇高」是哪个进程的事）

一次正常运行至少五个进程，任何一个涨都会让用户觉得「这软件吃内存」：

| 进程 | 说明 |
|---|---|
| 主进程 | Electron |
| 渲染进程 | 聊天窗 UI + 消息列表 |
| GPU 进程 | Chromium |
| Worker | `.NET` 运行时，跑 agent loop / 工具 / SQLite |
| 内置浏览器 webview | 有独立渲染进程，页面本身的内存不受我们控制 |

**所以第一步必须先分清「哪个进程高」** —— 渲染进程高和 Worker 高是完全不同的问题（见 §4）。

### 3.3 已经被我们抬高内存底数的既有设计（不是缺陷，但会被误读成缺陷）

- `MaxInlineImageBytes = 5 MB`（`FileReadTool.cs:42`）—— 单张图内联 base64 后字符串开销约 1.33 倍。
- 消息历史按窗口加载（`loadRecentSessionMessages` / `fetchOlderMessages`），窗口内消息常驻渲染层状态。
- 会话快照、`segments`、`toolCalls` 都挂在 store 上，切换会话时旧会话数据是否释放**未核**。
- Worker 侧 SQLite 连接池、`SessionConversation` 常驻内存。

这些是「正常占用」，用来说明一个判断：**用户说「没用什么东西」和进程说「占 800 MB」可以同时成立**，两者不矛盾。

## 4. 嫌疑方向（**推测，未验证**，按可查性排序）

| # | 方向 | 为什么怀疑 | 怎么证实 |
|---|---|---|---|
| 1 | 渲染进程：图片 base64 常驻 | 截过图、看过图的会话，`image` 块的 `data` 是完整 base64 字符串挂在 store 里；S-224 已把图落盘，但**历史回读时是否仍把 base64 提到内存**未核 | 采样渲染进程 RSS + 统计 store 里 image 块总字节 |
| 2 | Worker：托管堆涨上去不归还 | .NET 的 Working Set 在 GC 之后通常不立刻还给 OS；`Server GC` 开启时更明显 | 调 `worker/memory` 看 `ManagedBytes` 与 `WorkingSetBytes` 的差值随时间变化 |
| 3 | 会话切换未释放 | 每个会话的数据都在 store 上堆着，切得越多堆越多 | 连续切 10 个会话看 RSS 斜率 |
| 4 | 内置浏览器 webview | 页面自己吃内存，且我们不清缓存 | 只开浏览器不聊天，对比 RSS |
| 5 | GPU 进程 / 合成层 | 长消息列表 + 虚拟滚动 + 动画 | 对比有无动画时 GPU 进程内存 |
| 6 | 长会话 + 大量折叠块 | 执行过程折叠块 DOM 数量 | 长会话 vs 新会话对比 |

**这里刻意不写「大概就是 X」** —— 现在没有任何数据支撑任何一条，写死结论就是编。

## 5. 做法（分两步，先观测后修）

### 第一步：让它可观测（本需求的实质交付）

不要求用户做任何操作 —— 不埋点、不跑脚本、不看日志。软件自己做：

1. **递归启用 `worker/memory`**：那个端点已经写好了，缺的是调用方。
2. **主进程补采样**：`app.getAppMetrics()` 能一次拿到全部子进程（主 / 渲染 / GPU / utility）的 `workingSetSize`，比分别采样省事且口径一致。
3. **定时落日志**：低频（例如 5 分钟一次）追加一行到 `logs/YYYY-MM-DD.log`，格式固定为「时间 + 进程角色 + pid + working set（MB）+ 托管堆（MB，仅 Worker）」。低频是为了不污染日志，也不占 I/O。
4. **设置页诊断区可见**：用户在「设置 → 关于 / 诊断」能直接看到当前各进程内存，不用开任务管理器。这也是将来用户报「内存高」时唯一可靠的输入。
5. **阈值告警（可选，最后做）**：某进程越过阈值时日志打一条 Warn 并记录当时的关键上下文（会话数、消息数、图片块数），事后可复盘。

### 第二步：按数据定因，再改

拿到 §5.1 的数据后，回到 §4 表里逐条证伪。**在数据出来之前不改任何内存相关逻辑** —— 猜着改容易把一个正常占用当泄漏修掉，反而引入新问题。

## 6. 验收

1. 正常使用 1 小时后，日志里有完整的周期性资源行（主 / 渲染 / GPU / Worker 都有数）
2. 设置页能看到当前各进程内存，单位 MB，刷新不卡
3. 用户报「内存高」时，我们能从日志指出是哪个进程、什么时候开始涨、涨之前什么操作
4. 第一步落地后，「奇高」这个词可以被量化成具体数字（现在不能）

**注意：本需求第一阶段的验收不是「内存降下来了」** —— 是「看得到了」。降下来属于第二阶段，且依赖第一阶段的数据。

## 7. 不做什么

- **不做自动内存回收**（定时 `GC.Collect` / 主动 kill 渲染进程）。这是拿副作用换数字好看：.NET 强 GC 会卡、杀渲染进程会丢 UI 状态。等数据说真泄漏了再谈手段。
- **不做内存上限强制**（`--max-old-space-size` 之类）。先看清楚再设限，否则只是把崩溃提前。
- **不要求用户上手**：不写「请打开任务管理器记录」这种步骤 —— 老大 2026-10-27 17:14 明确否决过「让用户挂东西」的做法。
- **不在第一步就优化图片链路**。图片 base64 是嫌疑之一，但 S-224 刚动过落盘，先看它是不是真的常驻再改。
- **不动 `worker/memory` 的返回结构**，除非采样需求确认它少了字段。

## 10. 观测实锤：renderer 直接 OOM 崩溃、窗口白屏（2026-10-31）

**这一节把本条的性质改了。** 之前是「内存占用高、卡」，现在是「渲染进程崩掉、白屏、会话不可用」。§5 说的「先观测后修」，观测阶段到此结束 —— 数据已经足够，问题不再是「到底高不高」，是「高到直接把进程干死」。

### 10.1 时间线（dev 实例，`~/.wishful-claw-dev/logs/2026-10-31.log`）

| 时刻（+08） | 事件 | 证据 |
|---|---|---|
| 10:04:02 | 渲染进程 **3985.2 MB**（peak 4218.6 MB），越线告警 | `memory role=renderer type=Tab pid=31848 ws=3985.2MB peak=4218.6MB` + `[WARN] memory high … threshold=1536.0MB` |
| 10:11:18 | 渲染进程消失 | `Render process gone: killed (exit code: -1073741510)` |
| 10:22:07 | 重启，新渲染进程 pid 26340 | `Application started` |
| 10:27:08 | 1084.2 MB | 正常 |
| 10:32:08 | 1324.6 MB（peak 1607.6，**已越 1536 阈值**） | 半小时内从 1 GB 爬到越线 |
| 10:43:16 | **pid 变成 17516**、peak **4346.6 MB** | pid 变了 ⇒ 中间崩过一次又重建；峰值 4.3 GB |
| **10:47:55** | **渲染进程崩溃，之后再没起来** | `Render process gone: crashed (exit code: -36861)` |

**结果**：主进程与 Worker 都还活着（`23320` / `20648`），但窗口没有渲染进程 ⇒ **整窗白屏，用户完全没法用**。Electron 不会自动重建 renderer，只能重启应用。

### 10.1.1 触发点：**上下文压缩**，不是图片（2026-10-31 补查，老大补充「当时正在让它测试图片截图」）

先按「图片是主因」查了库，**假设被证伪**：

| 查的东西 | 结果 |
|---|---|
| 10:20 之后的消息 | assistant 6 条 / content **12 KB**；user 7 条 / content **8 KB**；system 1 条 |
| 含 `"type":"image"` 块的消息 | **0 条** |
| 含 `data:image/` 或 `"data":"` 的消息 | **0 条** |
| 全库含图片的消息 | **1 条，0.00 MB** |
| 崩溃前那个会话 `7-agqNb6NkCf7N1Soyf5K` 全会话 | 96 条 / content **0.08 MB** / meta **2.46 MB** |
| 全库最大单条 meta | `wc-agent-1793167187352-habwgj` = **746 KB** |

**把库和日志按时间戳对齐，压缩是唯一的时间关联点**：

```
10:38:58  [user]      查看最新迭代和需求文档，目前需要测试界面相关的一条龙 截图 预览查看这些
10:38:58  [assistant] 我先看这几条需求的验收口径，再一条龙实测…
10:43:14  [user]      <compaction-summary>            ← 上下文触发压缩
10:43:16  renderer    pid 变 17516，peak 4346.6 MB   ← 压缩后 2 秒
10:47:55  renderer    crashed                        ← 白屏
```

**两条硬结论**：

1. **不是图片数据的锅**。库里连一张图都没有 —— dev 在「刚读完需求文档、还没真正开始截图」就崩了。图片只是老大当时的**意图**，不是已发生的事实。
2. **4 GB 与 2.46 MB 差约 1700 倍** ⇒ 不是「数据大」，是**渲染端把这份数据放大了三个数量级**。压缩恰好是「整段历史折叠成摘要」的时刻 —— 消息列表要重建；若重建路径对每条消息的 `meta`（那个会话单条最大 **593 KB**）做深拷贝或重新解析，一次压缩就能把几 MB 放大成 GB 级瞬时驻留。

**这与 §4 嫌疑方向里「消息列表整表驻留 + 深拷贝」完全吻合**，且比原来更精确：**触发时机是压缩，不是「用得久」**。

**注意**：拆表（S-285 刀 11）**已经做了**，但按「零迁移」原则没搬走老数据 —— 崩溃那个会话正是老格式，meta 里仍完整带着 `segments` / `toolCalls` / `thinking`（单条最大 593 KB）。详见 §10.3 的实测表。

**待查（优化阶段第一步）**：压缩发生时渲染端对消息列表做了什么 —— 是否整表 `map` + 深拷贝 `meta`、是否每帧重建、有没有 `structuredClone` / `JSON.parse(JSON.stringify())`。这条能解释 1700 倍放大，也解释了「刚重启 1 GB、半小时到 4 GB」。

### 10.2 关键定性

1. **不是白屏 bug，是 OOM 崩溃的后果**。日志里没有任何 JS 异常、没有 `Maximum update depth exceeded`，只有内存越线 → 进程消失。10:47:55 崩的那一刻 worker 还在正常跑 agent（`context compression DIAG inputTokens=51403`）。
2. **不是偶发**。半小时内崩了两次（10:32→10:43 那次 pid 变化、10:47:55 这次），两次峰值都在 4 GB 量级。

### 10.4 ⚠️ S-285 拆表的盲区：**存储瘦了，IPC 还是胖的**（2026-10-31 12:2x 查代码发现）

这条直接决定「开新会话能不能测出问题」，也解释了「上了极简模式内存照样上 GB」。

**写侧确实剥了** —— `DbMessageParts.SplitMeta`（`:163`）把 meta 里的 `segments` / `toolCalls` 抽出来写进 parts，meta 落库变瘦。

**但读侧又合并回去了**，两条路都调 `MergePartsIntoMeta`：

| 调用方 | 用途 | 代码 |
|---|---|---|
| `SessionRestoreTools.AttachPartsToEntities`（`SessionRestoreTools.Wire.cs:40`） | **worker** 恢复/压缩读侧，重建 wire 给模型 | `entity.Meta = DbMessageParts.MergePartsIntoMeta(entity.Meta, parts)` |
| `DbMessageTools.ToRowsWithParts`（`DbMessageTools.cs`） | **渲染端**加载消息 | `rows[i].Meta = DbMessageParts.MergePartsIntoMeta(rows[i].Meta, parts)` |

而 `MergePartsIntoMeta`（`:422-494`）的输出：

- `:456` 写 `segments`（全部段，原样）
- `:473` 写 `toolCalls`（**从 tool_use 段重建**，字段完全重叠）
- 方法注释说「字段完全重叠，不再单独存一份」—— **那是说「库里不存两份」，输出仍然是两份**

**结论表**：

| 消息格式 | 库里 `meta` | 渲染端收到 |
|---|---|---|
| 老格式（parts 无行） | 胖（带 segments + toolCalls） | 胖（原样返回） |
| **新格式（parts 有行）** | **瘦** | **胖（读时合成，segments + toolCalls 各一份）** |

⇒ **渲染端拿到的数据量与老格式完全一致。** S-285 治的是「写入时整行 stringify 14 MB / 累计 2.07 GB 分配」（S-285 §二），**没有治「渲染端输入量」**。

**因此**：

1. **开新会话测不出来「和老数据有没有关系」** —— 新会话读出来一样胖。要复现 OOM，关键条件是**触发压缩**，不是「会话老不老」。
2. **§10.3 的「数据回填」优先级要降** —— 回填只能让**库里**变小，读侧不改造的话渲染端毫无改善。**先改读侧，回填才有意义。**
3. **真正该查的是渲染端怎么消费这份胖 meta** —— 拿到 `segments` + `toolCalls` 两份完整数据后，是否整表 `map`、是否深拷贝、是否每帧重建。这是 §10.1.1 里「2.46 MB → 4 GB、约 1700 倍」的放大器所在。

**改造方向的候选（待定，不是结论）**：渲染端加载路径不再走「合并回 meta」，直接下发 parts（渲染层本来就懂 `ContentSegment`，`types.ts` 的 `ContentSegment` 与 parts 的 `kind` 一一对应），把 `toolCalls` 由渲染层从 `tool_use` 段派生。这样 IPC 只传一份。**这条要评估渲染层改动面，别拍脑袋。**

**本迭代（v3-iter-5）不修**：改动面在渲染端数据结构，不是收尾期该动的。收尾后进 v3-iter-6 第一批。

**临时缓解**：撞到白屏只能重启应用；重启后渲染进程从 1 GB 重新起算，但半小时量级的重度使用会再撞一次 —— 所以缓解手段不是「多重启」，是少开长会话。

**根因**：我在探针文件顶部写了 `import { webFrame } from 'electron'`。渲染进程里 `'electron'` 不是运行时模块，vite 会把它当 **npm 包**打进浏览器侧（`node_modules/.vite/deps/electron.js`），那个包内部用了 `child_process` / `path` / `__dirname`，加载即抛错。而探针是在 `main.tsx:5` 被 import 的 —— **import 链在 `createRoot` 之前就断了，整个应用一行都不渲染**。

**修法**：`webFrame` 只能在 **preload** 里用（那里 electron 是真实模块）。改成：

- `src/preload/index.ts`：`import { webFrame } from 'electron'` + 暴露 `getResourceUsage(): Record<string, number> | null`
- `src/preload/index.d.ts`：补 `getResourceUsage?: () => Record<string, number> | null`
- `renderer-memory-probe.ts`：删掉 `import { webFrame } from 'electron'`，改调 `window.api?.getResourceUsage?.() ?? {}`

**教训（写给自己）**：渲染端**永远不要** `import ... from 'electron'`。需要主进程 / preload 能力时，一律走 `window.api` 或 `window.electron`。`typecheck` 抓不到这类错 —— 它是**运行时**才炸，而且炸在启动链最前面，表现为白屏而非报错弹窗。以后加任何渲染端探针/调试代码，先确认 import 清单里没有 `electron`。

## 16. 2026-10-31 19:0x 结案：找到了，是渲染链上三处「每帧全量重做」

§15 停在「716MB/26s 的分配源未定位」。这一段把它读完了，结论不是探针能测出来的东西 ——
是 `MessageList` 的转换层每帧把**整个消息数组**从头做了一遍，三处叠加。

### 16.1 分配链（一个 token 进来会发生什么）

```
appendTextDelta            // 原地改 msg.text，数组和对象引用都不换
  → zustand notify
  → useChatStore(useShallow(selectMessageListSession))
  → selectMessageListSession              // MessageList/utils.ts:498
  → convertChatMessagesToUnified          // MessageList/utils.ts:457
      ├─ getChatMessageConversionSignature → JSON.stringify(messages)   ← ①
      └─ messages.map(...)                 → buildChatMessageContent 每条重跑  ← ②
  → renderableMessages / rows 全量重建    → 每行新对象
  → MessageRow memo 比较器 prev.item === next.item 恒 false               ← ③
  → 12 行全部重渲染，每行里面的工具卡片全部重算
```

**①是内存大头，②是次大头，③是卡顿大头。** 三者串起来，一个 token 的代价是「序列化整个数组 +
重建 12 份 content blocks + 重渲染 12 行」—— 这就是 26 秒 716MB、CPU 打满、界面卡死的全部原因。

### 16.2 三处改动（均在 `src/renderer/src/components/chat/MessageList/utils.ts`）

**① `getChatMessageConversionSignature`：干掉 `JSON.stringify(messages)`**

原实现把 12 条消息整体序列化，每帧几十 KB 临时字符串，V8 分配完立刻丢弃 —— 堆峰值的主要来源。

换成逐条轻量签名 `getMessageSignature(msg)`：只取 `id` + `text.length` + 末字符 charCode +
`thinking.length` + `toolCalls.length` + `error.length` + `updatedAt`。

> 已知盲区：**等长替换**（长度相同、末字符也相同）会漏判。当前所有写入路径都不产生这种变更；
> 真出现时把末字符换成正文字符串 hash，**不要退回 stringify**。

**② `convertChatMessagesToUnified`：逐条复用转换结果**

原实现每次 `messages.map()` 全量重建 12 个 `UnifiedMessage`，每个都跑一遍
`buildChatMessageContent`（内部按 content block 拆工具卡片）。

新增模块级 `perMessageConversionCache`（`WeakMap<raw对象, {signature, converted}>`）。
store 原地改字段不换引用，所以命中后还要比 signature —— 没变就复用同一个 `UnifiedMessage` 对象，
变了才重跑。同时把单条转换逻辑抽成 `convertOneMessage`。

**③ `areMessageRowPropsEqual`：`prev.item === next.item` → 语义比较**

`renderableMessages` 每帧 `map` 成新对象，引用比较恒 false。新增 `areRenderableItemsEqual`，
按 kind 分派逐字段比（`message` / `summary` / `boundary` 比引用，标量比值）。
配合②，没变的消息 `item.message` 引用相同 ⇒ 只让真正在流式的那一行重渲染。

### 16.3 为什么不是之前猜的那些

| 曾经的怀疑 | 判定 |
|---|---|
| `Maximum update depth exceeded`（09:45 那条） | 是**症状**不是原因：每帧全量重建导致单帧耗时过长、被动触发嵌套更新。三处修完再观察 |
| `onRecoverableError` 没接上（§15.7 的 B 项） | 仍是废探针，已作废 |

| `CollapsibleHeightPanel` 冒泡 | 真缺陷但只影响抖动，已单独修（§15.5） |
| Blink 原生分配 635MB | 是①产生的临时字符串落到原生堆的账上，不是独立问题 |

|---|---|---|---|---|

| 19:07:35 | 120.2MB | 1987.6MB | 66.9MB | GC 回收，rss 只还 507MB |

这一轮是**纯文本流式、零工具调用**（日志里没有 tool 事件），30 秒 425MB。

### 17.3 根因：`charCodeAt` 强制 flatten ConsString（§16 ① 的副作用）

§16 ① 里我为了缩小「等长替换」盲区，给签名加了末字符：

```ts
const lastChar = text.length > 0 ? text.charCodeAt(text.length - 1) : 0   // ← 毒药
```

`msg.text` 是流式 `+=` 拼出来的 **ConsString（rope）**：

- `text.length` 是 O(1)，只读节点上的长度字段，不碰内容
- **`charCodeAt` 需要连续内存，会强制 V8 把整条 rope flatten 成 flat 字符串**

而每帧 `appendTextDelta` 都会 `flat + 新片段 → 新的 ConsString`，所以**下一帧又得重新 flatten**。
长回复 10 万字 ⇒ 每帧复制 200KB。

对齐实测：

- `RENDER_POOL_CONFIG.agile.frameIntervalMs = 32` ⇒ 约 31fps
- 32 秒 ≈ **1000 帧**
- 425MB ÷ 1000 ≈ **425KB/帧**

425KB ≈ **两次** 20 万字符全文操作。两次的来源：`charCodeAt`（我加的）+ `stripThinkTags`
（`content-renderer.tsx:430`，原有 —— 两个 `replace` 正则同样要 flatten）。

**这也是为什么这一轮（553MB）比上一轮（254MB）高：回复更长，flatten 更贵。**

### 17.4 本刀改动（`MessageList/utils.ts`）

`getMessageSignature` 去掉 `charCodeAt`，签名只留 O(1) 属性：

```
id : text.length : thinking.length : toolCalls.length : error.length : updatedAt
```

盲区从「等长替换」回到「等长替换（且 updatedAt 相同）」。流式是追加、`text.length` 必变，
历史加载会换 id，工具结果改 `toolCalls.length` —— 现有写入路径都不踩这个盲区。
函数注释里写死了一条禁令：**不要为缩小盲区在这里读文本内容（`charCodeAt` / `slice` / `includes`）**。

### 17.5 还剩什么（已知，未动）

`stripThinkTags` 每帧对整段文本跑两个正则，是**渲染必需**的一次全文 flatten ——
要显示就必须有连续字符串，这条降不到 0。预期效果：**425KB/帧 → 200KB/帧，砍一半**。

如果复测后仍然偏高，下一步是让 think 剥离只做一次（在 `convertOneMessage` 里算好塞进
`UnifiedMessage`，渲染层不再 strip），而不是继续在渲染层省。**先验证这一刀，别叠加。**
