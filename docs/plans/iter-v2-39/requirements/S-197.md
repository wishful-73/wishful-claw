## 二、现象

耗时**只在 run 结束后**才出现，且只出现在 assistant 消息的操作栏上：

`AssistantMessage/action-bar.tsx:61-65`：

```ts
// 时间戳只在这一轮跑完后才亮：流式期间显示的是「开始时间」，看着像已经完成。
const finishedAt = updatedAt ?? createdAt
// 耗时只在两个戳都齐、且结束晚于开始时才算（老消息没有 updatedAt）。
const elapsedMs =
  updatedAt != null && createdAt != null && updatedAt > createdAt ? updatedAt - createdAt : null
```

- `updatedAt` **只在 run 收尾时写入**（所以那行注释才说「流式期间显示的是开始时间」）⇒ 运行期间 `elapsedMs` 恒为 `null`，**整段时间一个字都不显示**。
- 运行期间唯一的进度反馈是输入框左上角的状态栏（`InputArea/composer-status-indicator.tsx:224-236`，`absolute left-5 top-2`，10px 单行），它只报「状态」，**不报时间**：

| 分支（`composer-status-indicator.tsx:93-202`） | 文案 |
|---|---|
| `isOptimizing` | Optimizing |
| `pendingImageReads > 0` | Loading media |
| 压缩中 / 压缩完 / 压缩失败 | `contextCompressionStatusLabel` |
| `pendingApprovalToolName` | Awaiting approval: {{tool}} |
| `sessionStatus === 'retrying'` | Retrying {{attempt}} |
| `isGeneratingImage` | Generating image |
| `activeToolName` | Running {{tool}} |
| `activeSubAgentCount > 0` | {{count}} sub-agents running |
| `isStreaming && 思考期` | Thinking |
| `isStreaming && 有文本` | Generating |
| `isStreaming`（兜底） | Waiting |
| 其余 | Ready |

⇒ 长任务跑十几分钟时，用户**全程看不到已经跑了多久**，只能等结束后回看。

---

## 三、目标

运行中（含思考 / 输出 / 跑工具 / 等审批 / 重试 / 子 Agent 期间）在**输入框左上角状态栏**追加一个**秒级走字**的耗时，且**与跑完后操作栏的耗时同口径、末值自然衔接** —— 让用户在跑的过程中就知道「这轮跑了多久」，而不是跑完才补看。

## 四、可行性评估（静态，2026-10-14）

**结论：可行。** 四个前提全部现成，不需要新增字段、不需要动协议、不需要动状态机。改动集中在 `composer-status-indicator.tsx` 一个文件。

### 4.1 起点时间戳 —— **已有**，不需要新增字段 ✅

流式 assistant 消息**在创建那一刻就带 `createdAt`**（`chat-store/index.ts:290-324`）：

```ts
const runId = `wc-agent-${now}-${Math.random().toString(36).slice(2, 8)}`
const userMessage: ChatMessage = { id: `user_${now}`, role: 'user', …, createdAt: now }
const assistantMessage: ChatMessage = {
  id: runId, role: 'assistant', text: '', thinking: '', isStreaming: true,
  createdAt: now                       // ← 起点在流式开始前就已落定
}
```

`chat-store/index.ts:332` 紧接着 `beginUserTurn(sessionId, userMessage, assistantMessage, assistantMessage.id)` —— **user 与 assistant 两条消息共用同一个 `now`**，所以「本条 assistant 消息的 `createdAt`」就是**这一轮 run 的起点**，不需要另找。

⇒ **运行中实时耗时 = `Date.now() − message.createdAt`。**

⇒ 跑完之后操作栏算的是 `updatedAt − createdAt`（`action-bar.tsx:64`）—— **同一个起点、同一个终点口径**。差别只是「终点」：运行中取 `Date.now()`，跑完取落库的 `updatedAt`。所以状态栏最后一个 tick 的数字，与随后操作栏亮出来的数字**天然接得上**，不会出现「走字 3m12s、一跑完跳成 3m18s」这种割裂。

### 4.2 取数路径 —— 组件**已经**拿着这条消息 ✅

状态栏早就通过 zustand 订阅了「当前会话的流式消息」（`composer-status-indicator.tsx:30-57`）：

```ts
const streamingMessageId = messagesOverride
  ? (streamingMessageIdOverride ?? null)
  : (s.streamingMessages[targetSessionId] ?? null)
const message = streamingMessageId ? messages?.find((item) => item.id === streamingMessageId) : undefined
```

⇒ **`message.createdAt` 就在手边**，只需把 `createdAt` 一并从 selector 带出来（现在只带了 `collectRuntimeOutputSnapshot(message)` 的结果）。**零新增订阅源、零新增 store action。**

### 4.3 tick —— 仓库有**同形**先例，照抄即可 ✅

`SubAgentCard.tsx:299-305` 就是「running 时起表、不 running 时清表」的写法：

```ts
const [now, setNow] = React.useState(tracked?.startedAt ?? 0)
React.useEffect(() => {
  if (!tracked?.isRunning) return
  setNow(Date.now())
  const timer = setInterval(() => setNow(Date.now()), 1000)
  return () => clearInterval(timer)      // ← 卸载 / 状态翻转即清，不泄漏
}, [tracked?.isRunning, tracked?.startedAt])
```

仓里 `setInterval(…, 1000)` 同款还有 `ThinkingBlock.tsx:86`、`ImageGeneratingLoader.tsx:139`、`SubAgentsPanel.tsx:291`、`goal-session-utils.tsx:166` 等 —— **这是本仓库的既有惯用法，不是新引入的模式**。

### 4.4 格式化 —— 直接复用现成函数 ✅

`lib/format-duration.ts` 的 `formatDurationMs(ms)` 已处理好 `ms / s / m / h` 阶梯（**且已经做过 `1h0m → 1h`、`1m0s → 1m` 这类去尾处理**），操作栏用的就是它（`action-bar.tsx:18`）。状态栏直接 import 同一个函数，**口径与观感天然一致**。

### 4.5 「运行中」怎么判 —— 判据就取「起点是否存在」✅（原「要放宽」的主张已证伪，见 §4.7）

> **订正（2026-10-14，实施前勘察）**：本节原先主张「计时器开关不能只挂 `isStreaming`，要放宽到 `sessionStatus / activeToolName / pendingApprovalToolName / activeSubAgentCount`」。**该主张被证伪**，实现改用收紧版；完整论证见 §4.7。

状态栏的 `isStreaming`（prop）由 `SessionConversationPane.tsx:39-41` 定义为 `Boolean(s.streamingMessages[resolvedSessionId])`；而组件 selector 取消息用的是 `s.streamingMessages[targetSessionId]`（`composer-status-indicator.tsx:39`）—— **同一份数据，两者恒等价**。

计时起点只能来自**当前流式 assistant 消息**的 `createdAt`，而这条消息正是由 `streamingMessages[sessionId]` 定位的。run 一结束该 id 即被删除（`chat-store/index.ts:1655`、`:1879`），**起点随之消失** ⇒ 那 6 个放宽条件对「算不算得出来」毫无影响。

⇒ **判据 = `startedAt != null`**（等价于 `isStreaming`），不需要任何新增订阅。

### 4.6 一句话

> **起点有了（`createdAt`）、消息对象有了、计时惯用法有了、格式化函数有了 —— 缺的只是一行「把 `Date.now()` 减出来」+ 一个 `setInterval`。** 这是一处纯派生显示，没有数据面风险。

### 4.7 订正：为什么「放宽判据」是多此一举（2026-10-14 实施前补勘）

§4.5 原来的推理是「`Running {{tool}}` / `Awaiting approval` / `Retrying` / `N sub-agents running` 这几条**分支判断里没写 `isStreaming`** ⇒ 它们可能在 `isStreaming === false` 时出现 ⇒ 只挂 `isStreaming` 会停表」。**代码事实没错，推论错了**，三条：

1. **`isStreaming` 就是「run 活着」的本源表达。** `SessionConversationPane.tsx:39-41` 把它定义为 `Boolean(s.streamingMessages[resolvedSessionId])`，与组件自己取消息用的 `s.streamingMessages[targetSessionId]`（`composer-status-indicator.tsx:39`）是同一份数据。**run 活着 ⟺ 这个 id 在 ⟺ `isStreaming` 为真。**
2. **起点唯一来源就是这条流式消息。** 计时要算 `now − startedAt`，而 `startedAt` 只能从 `streamingMessages[sessionId]` 指向的那条消息取（§4.2）。run 一结束该 id 即被删除（`chat-store/index.ts:1655`、`:1879`）—— **起点没了，放宽到 6 个条件也算不出数**。放宽对「能不能算」零影响。
3. **放宽反而逼出违规行为。** `activeToolName` / `pendingApprovalToolName` / `activeSubAgentCount` 这三个桶在 run 结束后**可能残留**（状态栏那几条分支刻意不检查 `isStreaming`，正是为了用它们兜住残留态、不让面板提前回 `Ready`）。把开关放宽到它们，等价于要求「run 结束后继续走表」——**直接违背裁定 ③「跑完不保留」**。

⇒ **实现判据收紧为**：`startedAt != null` **且** 非历史回放 **且** `now > startedAt`（首帧尚未 tick 的兜底）。

**顺带订正 §五-2 的一处措辞**：「整轮」被注成「含排队等待」，**注释是错的**。会话忙时 `sendMessage` 会在前置分支里**入队并直接 `return`**（`chat-store/index.ts:272-276`），**消息根本不创建** ⇒ `createdAt` 拿到的是**真正开跑时刻**，天然不含排队。所以「整轮」与「本轮」在本仓库**完全等价**，不存在分叉。

## 五、方案（待裁定）

**位置**：状态图标 + 文案之后，同一行追加耗时。两种形态待老大选：

| | **形态 A：拼进文案** | **形态 B：右侧独立一段** |
|---|---|---|
| 观感 | `Thinking · 12s` / `Running Read · 3m20s` | `Thinking` ……（右对齐）`12s` |
| 优点 | 改动最小（只动 `statusView.text` 的拼接）；与现有单行 truncate 天然兼容 | 时间不被长工具名挤掉（`Running {{tool}}` 的工具名可能很长） |
| 缺点 | 工具名极长时，**时间会被 `truncate` 先吃掉**（(:234 `truncate`)，恰恰是长任务更需要它） | 要改成两段布局（`justify-between` / 绝对定位），状态栏宽度也要再看 |

**我的建议：B** —— 理由是 `Running {{tool}}` 这条分支工具名可长可短，而**恰恰是跑工具最需要看时间**；A 在长工具名场景会把时间截掉，等于在最需要的地方失效。

**已裁定（老大 2026-10-14）**：

| # | 待定项 | 裁定 | 落地 |
|---|---|---|---|
| 1 | 形态 A / B？ | **B（右侧独立一段）** —— 按建议 | 状态文案后追加 `shrink-0` 的耗时段，长工具名被 truncate 时**耗时不被挤掉** |
| 2 | 口径：本轮 / 整轮？ | **整轮** | 二者在本仓库**等价**（排队中的消息不创建 ⇒ `createdAt` 即开跑时刻，见 §4.7）。实现 = `Date.now() − message.createdAt`，与操作栏 `updatedAt − createdAt` 同起点 |
| 3 | 跑完后是否保留？ | **不保留** —— 按建议 | `startedAt` 一消失即不渲染；不做「保留几秒」 |

## 六、边界与风险

1. **多会话并行**：状态栏只反映**当前会话**。非 live 会话走 `messagesOverride` 分支（`:36-39`，历史回放 / 只读态）—— **该分支必须不计时**（否则回看历史会话会看到「正在走表」的假象）。
2. **卸载 / 切换会话必须清表** —— 照 `SubAgentCard.tsx:304` 的 `return () => clearInterval(timer)` 写；`useEffect` 依赖里带上 `sessionId`，切会话即重挂。
3. **每秒 re-render**：只是重渲这一个 10px 的状态行（`:224-236`），与 `ThinkingBlock` / `SubAgentCard` 同级开销，**可接受**；但要注意别把 `now` 塞进那个大 `useMemo`（`:93-220`）的依赖里 —— 那会让整张 `statusView` 每秒重算（虽无副作用，但没必要）。**`now` 只在渲染层拼字符串即可。**
4. **`isRunning` 抖动**：工具切换 / 子 Agent 起停会造成 `isRunning` 短暂翻转 ⇒ 计时器反复挂清。因为起点取的是**消息的 `createdAt`（固定值）**而不是「表启动时刻」，**翻转不会丢时间**（重新起表后算出来的仍是 `now − createdAt`，连续无误）。这是本方案相对「累加计数」的关键优势。
5. **`createdAt` 缺失的兜底**：老消息 / 异常路径可能没有 `createdAt` ⇒ 取不到就不显示耗时（**宁可没有，不可报 0 或负数**），与操作栏 `elapsedMs === null` 的态度保持一致。
6. **压缩（S-196 同族）**：`adjustCompactArtifactTimestamps` 改写的是**压缩工件**的 `createdAt`，**不碰当前流式 assistant 消息** ⇒ 与本条**无交叉**。反过来，本条也**不去碰** S-196 改过的那套分段逻辑。
7. **i18n**：`Thinking · 12s` 这种「文案 + 时间」的拼接**不要塞进 i18n 键**（时间不是可翻译片段）；若要 A 形态，只对分隔符用常量。若需新增键，zh / en 必须同批。

## 七、刻意不做

1. **不改 `action-bar.tsx` 的完成态耗时算法** —— 它是对的（S-196 刚收口），本条只在**运行中**补一个显示。
2. **不动 run 状态机**（不给 `SessionExecutionStatus` 加 `startedAt`）—— 起点从消息 `createdAt` 拿就够了，**不给 store 加状态**是这条能保持「零风险」的前提。
3. **不显示「预计剩余时间 / 进度百分比」** —— 没有可靠的进度来源，硬做就是编。
4. **不在状态栏同时显示「本轮 + 整轮」两个耗时** —— 一个状态栏放不下，也没必要；单轮口径与操作栏一致即可。
5. **不做「超过 N 分钟变红 / 告警」** —— 那是另一个需求，本条只加走字。
