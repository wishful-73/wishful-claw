## 2. 边界（本号最容易被理解错的地方）

**基座只提供「采」，不提供「懂」。**

| 在基座 | 在插件项目 |
|---|---|
| 打开麦克风 / 系统声音，把音频变成**文件或流** | 切成多长的段、什么时候切 |
| 设备枚举与选择 | 把音频喂给哪个引擎 |
| 音量电平（可视化用） | 转写、说话人区分、纪要 |

⇒ 本号的成品是「**能拿到干净的 wav 文件**」，不包含任何 ASR 代码。

## 3. 现状（2026-10-27 实读源码）

### 3.1 全仓零录音实现

`getUserMedia` / `MediaRecorder` / `NAudio` / `WASAPI` / `desktopCapturer` 在 `src/main` 与 `src/renderer` **全部零命中**（唯一 `system-settings` 相关命中只是跳转系统设置页）。

⇒ 从零做。

### 3.2 两条采集路径必须分开

| 来源 | 实现 | 说明 |
|---|---|---|
| **麦克风** | 渲染端 `navigator.mediaDevices.getUserMedia` | Electron 原生支持；插件在自己的 webview 里**本来就能直接调**，基座提供的是「统一入口 + 设备选择 + 落盘工具」 |
| **系统内录**（会议对面的人） | **主进程** `desktopCapturer` + `setDisplayMediaRequestHandler` | ⚠️ **这是本号唯一不可替代的部分**：渲染端 `getDisplayMedia` 在 Windows 拿不到干净的 loopback 音频 |

### 3.3 必须实测的未知 —— **已实测完毕（2026-10-28，v3-iter-4 第 0 刀）**

原怀疑「Electron 在 Windows 上通过 `desktopCapturer` 拿系统音频时是否需要特殊处理、是否混入本程序自身播放」。实测结论（Electron 43.2.0 / Windows，探针见 `iter-v3-4/exploration_findings.md` §1.7）：

| 问题 | 结论 |
|---|---|
| 纯音频 `getDisplayMedia({audio:true})` | **不可用**，抛 `AbortError: Invalid capture constraints`。**必须先要 video，拿到后丢掉 video track** |
| `callback({ video, audio:'loopback' })` | **通**。静音基线 RMS=0；播放 440 Hz 时 RMS=0.0165、FFT 主频 445 Hz |
| 是否混入本程序自身播放 | **必然混入**。本程序自己播的 440 Hz 被完整采到 |
| loopback 实际参数 | **48 000 Hz / `channelCount: 1`（单声道）**，label `System audio` —— **不是**预想的 48 k stereo |
| 48 k → 16 k 重采样 | `OfflineAudioContext(1, 16000, 16000)` 渲染 1 s，输出长度精确 16000、RMS 非 0 ⇒ 无需新依赖 |
| `loopbackWithMute` | **未测**，语义存疑；当前口径用 `'loopback'` |

## 4. 落点

### 4.1 主进程

| 文件 | 内容 |
|---|---|
| 新增 `src/main/plugins/plugin-audio.ts` | 系统内录（`desktopCapturer` + `setDisplayMediaRequestHandler`）；设备枚举；音频流写入 wav |
| 新增 `src/main/ipc/plugin-audio-handlers.ts` | `plugin-audio:devices` / `start` / `stop` / `level`；事件 `plugin-audio:chunk` |

### 4.2 渲染端（给插件视图用的可选糖）

```ts
window.wishful.audio = {
  devices(): Promise<AudioDevice[]>          // 输入设备 + 系统声音源
  start(opts): Promise<{ sessionId }>        // { source: 'mic' | 'system' | 'both', deviceId? }
  stop(sessionId): Promise<{ wavPaths: string[] }>
  onLevel(cb: (level: number) => void): () => void
  onChunk(cb: (path: string) => void): () => void   // 分段落盘后回调
}
```

**分段策略归插件**：基座按插件给的 `segmentSeconds`（缺省 30 s）切，切完落一个 wav 并回调。

### 4.3 格式

- 16-bit PCM wav、单声道、**16 kHz**（QwenASR `--stdin` 原生格式；重采样由基座做，插件不操心）
- `both` 模式（麦克风 + 系统）先**混音成单轨**再落盘 —— 说话人区分靠 sherpa-onnx 事后分割，不靠双轨
- ⚠️ 实测 loopback 与麦克风**都已经是 48 000 Hz / 1 ch**，所以只需**重采样**，不需要声道下混。但实现必须按 `track.getSettings()` 动态取值，**不能写死单声道**（换机器 / 换驱动可能是 stereo）

## 5. 验收（不依赖任何插件）

用一个**测试页**（内部调试页即可）验证：

1. 列出本机输入设备（至少 1 个），可切换
2. 录音 10 s → 落出 wav → **用系统播放器能正常播放、听到自己的声音**
3. **系统内录**：播放一段网上的音频，同时录制 → 落出的 wav 里能听到那段音频（这是 Windows loopback 是否真的通的唯一判据）
4. `both` 模式：麦克风说话 + 系统放音，两者都在同一个 wav 里
5. 电平回调：说话时数值跳动，静音时接近 0
6. 分段：`segmentSeconds: 5` 录 17 s → 落出 4 个文件（5/5/5/2），相邻段无重叠、无丢帧
7. 中途停止：不产生损坏的超短文件；正在写的文件能被正常关闭

## 6. 风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | ~~Windows loopback 拿不到音频 / 拿到的是静音~~ | **已排除**（2026-10-28 实测通过，见 §3.3）。不需要 WASAPI 原生模块。**新风险转移为**：`getDisplayMedia` 必须带 video 才能拿到 audio ⇒ 实现上要「要 video 再丢」，别写成纯音频请求 |
| 2 | 系统内录混入本程序自身播放的声音（回声 / 双声） | **必然发生，已定为已知特性并接受**（老大 2026-10-28 17:57 拍定）。Windows loopback 无 per-process 排除 API；主场景是听会议 / 听别人说话，此时本程序不播放。真出现「边放音乐边转写」再单独立需求 |
| 3 | 采样率 / 声道转换出错导致 ASR 识别率暴跌 | 统一 16 kHz mono 16-bit 并写单测校验 wav 头 |
| 4 | 长时间录音文件过大（会议 1 小时 ≈ 110 MB） | 分段落盘（缺省 30 s）；基座不做拼接，由插件决定保留策略 |
| 5 | 麦克风权限被系统拒绝 | 明确报错文案 + 引导到 Windows 隐私设置 |

## 7. 不做什么

- **不做 ASR / 说话人区分 / 纪要** —— 全在插件项目
- **不做降噪 / 回声消除 / VAD（除了切段）**
- **不做「边录边转写」的管道** —— 那是插件把 wav 喂给引擎的事
- **不做录音文件管理界面** —— 文件交给插件，基座不管归档

### 8.2 两条实测约束落进代码注释

- **纯音频 `getDisplayMedia` 不可用** ⇒ `openStream` 里一定先要 video 再 `stop()` 掉 video track（并 `removeTrack`，不然画面会被持续抓取白烧 GPU）。
- **loopback 与麦克风实测都是 48 kHz / 1 ch**，但实现按 `track.getSettings()` 之后的实际值走 `AudioContext`，不写死单声道。
