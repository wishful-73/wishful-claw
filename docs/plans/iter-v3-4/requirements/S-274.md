## 三、根因：一道 `<= 1` 守卫被浏览器 clamp 穿透

代码里**自己写着**这条循环（`useMessageListScroll.ts:340-343`，2026 年那次修复留下的）：

```ts
// Already pinned: re-writing scrollTop would dispatch another scroll
// event, whose handler sets state and re-runs the auto-scroll layout
// effects — that cycle is what React reports as "Maximum update depth
// exceeded".
if (Math.abs(ref.scrollTop - bottom) <= 1) return
```

当时的解法是「已经钉底就别再写」。**这个判据有一处没算到**：

跟随目标 = `realBottom + gapTarget - clientHeight`，`gapTarget` 是**提前量**（`resolveGapTarget`，上限 `STREAMING_BOTTOM_FOLLOW_CHUNK` = 240px），**远大于内容容器底部 padding（十几到二十几 px）**。

虚拟列表尾部行未挂载的那一帧（长文本流式的常态），`scrollHeight` 撑不到这个目标 ⇒ 浏览器把写入值 **clamp 到 `maxScrollTop`**：写 1000 读回 760。

于是：

```
写 1000 → 读回 760 → |760 - 1000| = 240 > 1 → 守卫不成立 → 再写 → …
```

**自激链**：每帧写 `scrollTop` → 派发 `scroll` 事件 → `handleListScroll` → `syncBottomState` 里 `setIsAtBottom` → bottom-anchor `useLayoutEffect` 再跑 → `scrollToBottomImmediate` → 再写。撞满 React 的 50 层嵌套上限即报错。

三处写入点同在一条链上，判据一样漏：`:293` 悬空救援、`:320` 回收计划（`plan.scrollTop` 与跟随目标**同值**，最危险）、`:352` 跟随落位、`:866` 流式结束撤水位线。

## 四、为什么「长文本修复以后才开始」

三个需求各加一层，正好在此处撞车：

| 需求 | 那一层 | 后果 |
|---|---|---|
| **S-256**（2026-10-29 12:21） | 单帧步长封顶 1600 字符 | 流式期间每帧都在重渲染，时间被拉长到几十秒 |
| **S-233**（2026-10-27） | `tailMounted === false` 时 `observeGrowthOnly` 只升不降 | floor 与真实可滚范围脱钩 |
| **S-176 / S-150** | 提前量 `gapTarget`（最多 240px）+ 水位线 | 跟随目标常年超出 `scrollHeight` |

S-256 之前，长文本一帧吃完就静止，这个循环跑不了几轮；S-256 之后每帧都跑、跑几十秒，循环才够时间撞上限。

## 五、修法

**写超范围的 `scrollTop` 本身没有意义** —— 夹进可滚范围，写进去与读回来一致，守卫即恢复有效。可滚范围足够时是 no-op，观感完全不变。

- `scroll-watermark.ts` 新增纯函数 `clampScrollTop(value, scrollHeight, clientHeight)`（夹取 + 幂等 + 内容不满一屏返回 0）
- `useMessageListScroll.ts` 的 `clampScrollTop` 包成读 `listRef` 的 `useCallback`，四处写入点全部先夹；`:361` 的守卫**改为对夹取后的值比较**（这是关键，只夹写入不夹判据仍然无效）

## 六、闸

`tests/scroll-watermark/program.ts` **103 → 110 条**（+7），核心两条：

1. **复现**：未夹取的目标（640）读回来（400）与目标差 > 1 ⇒ 守卫失效
2. **修复**：夹取后写进去 == 读回来 ⇒ 守卫必然成立；且夹取幂等
3. 可滚范围内 no-op（提前量跟随不被夹掉）、负值夹到 0、内容不满一屏恒为 0

反向验证：把 `clampScrollTop` 退回 `return Math.max(0, value)`（等价于修复前的行为）⇒
`AssertionError: 超范围目标夹到 maxScrollTop（实际 640）`，撤销后 110/110 复绿。

## 七、真机验收清单

1. 让 dev 输出一段 5 万字以上的长文本（无空行长段落更佳）⇒ 流式期间不卡、内存稳定在几百 MB
2. 流式期间滚轮往上翻、再回底 ⇒ 无跳动、无「拽回」感
3. 流式期间尾部行滚出视口（快速上翻制造 `tailMounted=false`）⇒ 不出现持续重排
4. 长文本结束后接着跑工具调用 ⇒ 提前量留白仍按 gapTarget 收，非零
5. 窗口拉矮、右侧面板拖窄各重复一次第 1 项（`scrollHeight` 更紧张，最容易复现）
6. 看 dev 日志：不再出现 `Maximum update depth exceeded`，`memory type=Tab` 不再上万 MB
