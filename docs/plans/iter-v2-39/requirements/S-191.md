## 二、现象

- 子 Agent **异常退出**（非正常结束）后，面板 / 卡片状态**持续显示「工作中」**，而该子 Agent 实际早已停止运行。
- **现场样本**（2026-10-12 约 19:20–19:30）：主会话派出的两个后台实施子 Agent —— C# 侧 169.5s / 31 calls、渲染端 476.7s / 49 calls —— **活儿全部干完、改动落盘、报告也已回报主会话**，但二者在面板上的状态**仍显示「工作中」**，不随时间收敛。

## 三、静态定位（初步读码，**未实机**）

### 3.1 状态收敛是「单事件」驱动的

| 环节 | 位置 | 说明 |
|---|---|---|
| 文案判定 | `src/renderer/src/components/layout/SubAgentsPanel.tsx:66-77` | `isQueued` → Queued；**`isRunning` → Running（「工作中」）**；迭代上限 → Iteration limit reached；`aborted` → Aborted；否则 Completed |
| 状态收敛 | `src/renderer/src/stores/agent-store/slices/sub-agent-slice.ts:341` | 消费 `sub_agent_end` |
| 另一条链路 | `src/renderer/src/stores/chat-store/index.ts:852`、`chat-store/adapt-sub-agent-event.ts:55` | 同一 `sub_agent_end` 的卡片侧消费 |
| 事件发出（Worker） | `src/runtime/WishfulClaw.Agent/SubAgentExecutor.cs:209`（start）/ `:345`（end，**前台路径**）；`SubAgentExecutor.Background.cs:89 / :145 / :168`（**后台路径**三处） | |

⇒ **「工作中」= `isRunning === true`，而它只由 `sub_agent_end` 收敛。事件一旦没送达，`isRunning` 就永远停在 true —— 代码里没有任何超时 / 心跳兜底。**

### 3.2 事件可能丢在哪（待逐个证伪）

1. **Worker 侧异常出口** —— 前台路径 `SubAgentExecutor.cs:342` 的 `EmitAsync("sub_agent_end")` 位于 `try/catch/finally` **之后**；`catch` 已把异常吞成 `subAgentOutput` 文本，看似「必经」。但若 `EmitAsync` 自身抛错、或父 run 的 transport 已断（父 run 先结束 / 被中断），这一条就发不出去。
2. **进程级异常**（崩溃 / 被杀 / 重启）—— 任何事件都发不出，天然无兜底。
3. **渲染端持久化恢复** —— `src/renderer/src/stores/agent-store/sub-agent-persistence.ts` 会把崩溃前残留的记录原样恢复，`isRunning` 可能被一起带回来。
4. **两条链互相独立** —— 主进程侧的「后台子 Agent 完成唤醒」（`src/renderer/src/hooks/use-background-subagent-wakeup.ts`，同样消费 `sub_agent_end`）与**卡片状态收敛**是两条互不相干的链路。**本次现场正是「报告到了、卡片仍挂」的组合** ⇒ 至少存在「唤醒成功但卡片没收」的路径。

### 3.3 与相邻需求的边界

- 与 **S-178**（子 Agent 排队态可见：queued / dequeued 事件 + start 时序归位）、**S-180**（后台子 Agent「不要等」提示词与占位返回）**同属子 Agent 状态机区域**，本条是该区域的**遗留缺口**：前两条把「排队 → 启动」这一段收口了，**没有覆盖「异常退出 → 收敛」这一段**。

## 六、验证方式（待口径齐）

- **自动化**：难 —— 需要真实触发异常退出路径。若修复采用「Worker 侧异常出口必发 `sub_agent_end`」，可在 C# 侧对「异常 → 仍发 end」加断言；**进程级崩溃场景无法用单元测试覆盖**。
- **实机**：制造异常退出（杀 Worker / 中断父 run）⇒ 卡片应在**有限时间内**收敛为 `aborted` / `failed`，**不得永挂 Running**；刷新 / 重启后不得复活「工作中」。

## 七、修复方向（**未拍板**，待口径齐后进 plan）

| 候选 | 内容 | 评价 |
|---|---|---|
| **A** | Worker 侧把 `sub_agent_end` 收进 `finally`（覆盖所有异常出口），确保「异常退出」也发收敛事件 | **根因侧**修复；不解决进程崩溃 |
| **B** | 渲染端加超时 / 心跳兜底 —— 长时间无事件则标 `aborted` | **治标**；唯一能兜住「进程崩溃」的手段 |
| **C** | 主进程在收到 Worker `run end` / 断连时，**扫描并收敛该 run 名下所有未收敛的子 Agent 卡片** | **兜底侧**修复；覆盖面最广 |

**倾向 A + C**（事件会丢、进程会崩，单靠「必发事件」不够）。**最终方案待老大补 §五 信息后再定。**
