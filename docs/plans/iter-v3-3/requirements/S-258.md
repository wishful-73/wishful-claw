**归属**：v3-iter-3（产品 1.0.3）。编号 **S-258**。真机验收中发现。

**状态**：**已实施，待真机验收**（2026-10-28 16:1x）。

## 2. 现状（2026-10-28 实查）

### 2.1 「清空消息」三个入口，只有一个没确认

`clearSessionMessages`（`stores/chat-store/session-slice.ts:489`）落库删 messages 行，切走切回不再复活 —— 也就是说**删了就是删了**。

**2026-10-28 16:07 老大追问「右侧悬浮块也有这个操作，需要你确认一下是否有二次确认」⇒ 三入口逐一实查，结论如下：**

| 入口 | UI 位置 | 代码 | 有确认？ | 显示的动作名 |
|---|---|---|---|---|
| **右侧悬浮块**「更多」菜单 | 聊天窗**右上角竖排悬浮操作块**（`absolute right-3 top-3`，终端 / 文件夹 / 上下文 / ⋯）→ ⋯ → 最后一项 | `SessionConversationPane.tsx:305-308` `onClick={handleClearSession}` → `:109-123` | ✅ **有**，`confirm({ variant: 'destructive' })`，标题 `sidebar.clearSessionConfirmTitle`、描述带 `{{title}}` 且写明「无法恢复」 | 「**清空会话**」`sidebar.clearSession` |
| 左侧会话列表右键 | 左侧面板会话项右键菜单倒数第二项 | `workspace-sidebar-items.tsx:180-183` `handleClear` | ❌ **直接删** | 「**清空消息**」`sidebar.clearMessages` |
| 输入框上方删除按钮 | composer 工具条 | `clear-conversation-dialog.tsx:63-70`（`AlertDialogAction`） | ✅ 有 `AlertDialog` 二次确认 | 「**清空对话**」`chat.input.clearConversation` —— **但该入口当前不显示，见 §2.5** |

> 老大问的那一处（右侧悬浮块）**有**二次确认，且是三个入口里写得最规范的一个：`await confirm(...)`、`variant: 'destructive'`、描述里插了会话标题、确认后才落库。**唯一没确认的仍然是左侧右键那一个。**

### 2.2 同一个文件里，紧挨着的「删除会话」都有确认

`workspace-sidebar-items.tsx`：

- `handleDelete`（`:164-178`）= `await confirm({ title, description: '"{{title}}" and its message history will be permanently deleted. This cannot be undone.', variant: 'destructive' })` → 才 `deleteSession`
- `handleClear`（`:180-183`）= **直接 `clearSessionMessages(session.id)`** + 一条 `toast.success`

同一个右键菜单里，「删除会话」（连带删消息 + 删会话）有确认，「清空消息」（只删消息，同样不可逆）没有 —— **口径自相矛盾，而且保护强度跟破坏力倒挂**。

### 2.3 i18n key 已经现成

`locales/{zh,en}/layout.json` 的 `sidebar` 段里 S-204 已经加了：

- `clearSessionConfirmTitle`
- `clearSessionConfirmDesc`（带 `{{title}}` 插值）
- `clearSession` / `clearMessages` / `conversationCleared`

⇒ **纯组件改动，零新增文案、零新增机制。**

### 2.4 顺带查出的口径问题：同一个动作三处三个名字 —— **老大拍板统一**

| 位置 | 改前用户看到的字 | i18n key | 权威值 |
|---|---|---|---|
| 右侧悬浮块 ⋯ 菜单 | 清空**会话** | `sidebar.clearSession` | ✅ 保留这一份 |
| 左侧列表右键 | 清空**消息** | `sidebar.clearMessages` | ❌ 删，改引用上面 |
| composer 删除按钮（已隐藏） | 清空**对话** | `chat.input.clearConversation` | ❌ 删，改引用上面 |

> 2026-10-28 16:11 老大：「都统一成清空会话」。

三个词指同一个动作，行为完全一致（都走 `clearSessionMessages`，都保留标题与用量统计）。**做法是「合并成一份」而不是「三处改成一样的字」** —— 三份重复文案本身就是这次跑偏的原因，改值只能治一次，下次谁改一处又分叉。所以：

- 权威文案只留 `sidebar.clearSession`（zh「清空会话」/ en `Clear session`，en 原值 `Clear messages` 一并订正）
- `clear-conversation-dialog.tsx` 跨命名空间引用它（同文件 `:61` 早有 `t('action.cancel', { ns: 'common' })` 先例，不是新玩法）
- 两个冗余 key 从 zh/en 四份 JSON 里删除

### 2.5 composer 那个入口其实是关着的

`InputArea/index.tsx:453` 硬编码 `showInlineClearConversation={false}` ⇒ `ClearConversationDialog` 组件自 `:30` 起就 `return null`。也就是说**这个入口当前根本不渲染**，它那套 `AlertDialog` 与 `clearConfirmDesc` 文案是死代码。

不影响本需求处置（左侧照抄右侧悬浮块的写法即可），但要记一笔：将来若重新打开 composer 入口，别以为「已有确认」就万事大吉 —— 它确实有，但它现在不显示，**统一命名之后它的标题也该跟着换**。

### 2.6 另有一处死 key 被顺带改到

`layout.json` 里有**两个** `conversationCleared`：`:199` 在 `sidebar` 段（唯一被用，`workspace-sidebar-items.tsx:196`），`:435` 在 `layout.layout` 段（全树零引用，死 key）。两处值都改成了「会话已清空」/ `Session cleared` —— 死 key 那处改不改都不影响运行，一起改只是不想留一份字不一样的同名 key 在那儿误导下一个人。

## 3. 目标

1. 左侧右键「清空会话」点击后弹二次确认，`variant: 'destructive'`，文案含会话标题。
2. 取消则**什么都不发生**（不落库、不 toast）。
3. 确认后才走现有的 `clearSessionMessages` + `toast.success`。
4. **三处入口统一叫「清空会话」，且只有一份文案来源**（§2.4）。
