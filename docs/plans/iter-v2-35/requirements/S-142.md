## 一、现象

一轮 agent 回复渲染到最后，末尾多挂一个（通常很短的）思考流条。**v0.2.33 无此问题。**

**老大 09:33 订正关键口径**：思考流**并不是全是空的，只是大部分是空的**；从内容上看，**是同一段思考流被文本劈开了**（与 34 修的「文本被思考流/组件卡片劈开」同型，劈的对象反过来了）。

**真症状链（2026-09-23 12:43 补记）**：劈开的伤害不止「末尾多挂一条空思考」。`process-summary.ts` 的 `splitProcessAndFinal` **从末尾倒扫**、跳过 text / image 这类「最终输出」块，撞到第一个「过程类」item 就停（`items` 的顺序 = segments 顺序，见 `chat-message-blocks.ts`）。段被劈开时**末段是 thinking** ⇒ 倒扫第一项就停下 ⇒ `finalOutputStartIndex = items.length` ⇒ **整段正文被划进「执行过程」折叠收起**，用户看到的正文直接消失。

⇒ **验收标准**：① 同一轮段序恒为「思考 → 正文 → 工具卡」；② **折叠块里不许漏进正文** —— 正文必须留在最终输出区。

## 三、根因（初判）：S-135 batcher 的 drain 固定顺序重排了事件

> ⚠️ **本节结论已被 [§七](#七重开初版未生效改按-iteration-type-定位2026-09-23-1153) 推翻** —— 交错分片是上游两条独立流各自分片的自然产物，不是 batcher 重排。保留作追溯。

**引入者：iter-34 S-135**（`src/main/ipc/batcher/batcher-codec.ts`，注释自署「iter-34 S-135」）。

1. **上游真实顺序**（C# `OpenAIChatProvider.ProcessSseDataAsync:343-363`）：同一 chunk 先 emit `thinking_delta` 再 emit `text_delta`，跨 chunk 也按到达序 —— **顺序本身正确**。
2. batcher 攒批：`accumulateEvent` 把 `textDelta` / `thinkingDelta` 攒进**两个独立拼接串**（`batcher-codec.ts:39-44`）—— **到达顺序在这里丢失**。
3. `drainAccumulator`（`:64-82`）**固定顺序倒出：正文 → 思考 → 工具参数**（注释 `:61` 自书）。
4. 前端 store 忠实按收到序建段 ⇒ `[thinking1, text, thinking2]` ⇒ 思考流被劈。

**三个口径全部吻合**：

- 「同一段思考流被文本劈开」= drain 固定 text 在前；
- 「大部分是空的」= 劈出的第二段是思考尾巴，通常 1~4 字符；
- 「33 之前没有」= batcher 是 34 的 S-135 引入，33 之前事件直通、顺序保真。

**与 S-133 补完（`3366f8f1`）的关系**：S-133 补完修的是 text 分支的 `findLast` 谓词，它不是本案引入者 —— 本案数据里 text 并回是**正确行为**（正文本来就该连贯）。S-135 重排让「思考尾巴」以独立段出现在 text 之后，S-133 补完只是让这个结果得以呈现。**劈开的引入者判 S-135。**

## 四、修法（已裁定，老大 09:45 拍板：**丙案**）

> ⚠️ **初版方案，已被 [§七](#七重开初版未生效改按-iteration-type-定位2026-09-23-1153) 取代**。下面「丙案」描述的段边界事件仍是**现行机制的一部分**（`StreamSegmentBoundary` 一行未改、C# 继续发），但**「按边界决定续段还是开段」已被废弃** —— 段改为按 `(iteration, type)` 定位。本节其余内容（含「协议版本升 v2」等细化项）是当时的候选清单，**不作数**。

| 方案 | 做法 | 代价 |
|---|---|---|
| 甲 | batcher `accumulateEvent` kind 冲突先 flush | 改动小；前端「猜并回」逻辑仍在，劈开类问题还会换形态复发 |
| 乙 | accumulator 按到达顺序记片段数组 | 保序彻底，但仍是「拼串」思路 |
| **丙（裁定）** | **协议加段边界事件**：`thinking_start` / `thinking_end` / `text_start`，后端在 kind 切换处发；前端按边界决定「续段还是开段」，不再靠 `findLast` 猜 | 改动面大（wire protocol 升 v2 + C# 三处 provider/parser + 前端 store + batcher），但**治本** —— 劈开类问题从协议层绝根 |

**裁定理由（老大 09:42 提出思路「首段接收到的时候有没有类似标识，按标识拼接」）**：

- 现协议里 tool 有完整标识（`tool_use_streaming_start` → `tool_use_args_delta` → `tool_use_generated`）⇒ **工具卡从不劈**；text/thinking 只有裸 delta、无边界 ⇒ 劈开全发生在这两类。
- 上游边界信息存在：Anthropic SSE 有 `content_block_start/stop`（C# parser 收得到但未上传）；OpenAI 系边界隐含在 reasoning→content 字段切换处，后端 `ProcessSseDataAsync` 先 emit reasoning 再 emit content，切换点已知。
- **batcher 的甲方案作为丙的附带项**：边界事件走直通（控制类事件不打乱顺序），甲的冲突 flush 顺手做。

**Reasonix 对照（老大 09:45 要求查看）**：Reasonix（`D:\koda\DeepSeek-Reasonix-main-v2`，`internal/agent/agent.go:1345-1448`）**不存「段」** —— 流式期间 Reasoning/Text 分事件显示，落库时合成**消息级 2 字段**（Text 全文 + Reasoning 全文），渲染固定思考在上、正文在下。劈开问题结构上不存在，代价是**丢弃交错时序**（思考永远整块在正文前）。S-133 补完时已裁定「不抄 Reasonix」（放弃交错 = 换掉整个 segments 模型）。**参考结论**：Reasonix 靠「取消段」消灭劈开，丙案靠「显式段边界」消灭劈开 —— 同样的确定性，保住时序。核心教训：**边界必须是一等公民，不能靠猜**。

**实施范围（待开工细化）**：

1. `shared/agent-stream-protocol.ts`：新增 `thinking_start` / `thinking_end` / `text_start` 事件，协议版本升 v2（seq 丢包检测兼容性一并核）。
2. C# 侧：`AnthropicMessagesEventParser.cs`（有 `content_block_start/stop` 原料）、`OpenAIChatProvider.cs` / `OpenAIResponsesEventParser.cs`（kind 切换点补发边界）。
3. batcher：边界事件直通 + 冲突 flush。
4. 前端 `chat-store`：按边界建段/续段；`findLast` 谓词（S-133 hack）评估退役。
5. 兼容：历史数据（已落库的无边界 segments）渲染不受影响。

## 六、实施记录（2026-09-23 11:01）

> ⚠️ **该归因与修法已被 [§七](#七重开初版未生效改按-iteration-type-定位2026-09-23-1153) 推翻**，以下是实施当时的原记录，保留供追溯。其中**两处已失效**的具体说法：
>
> - 第 1 条末尾「老 worker + 新渲染端 = 退回旧行为，`findLast` 兜底仍在」—— §七 之后新渲染端不再依赖边界事件，**老 worker 也能正确分槽**。
> - 第 2 条「**没退役 `findLast`**：S-133 的合并语义保留」—— §七 已把 text 分支的 `findLast` 去掉（按 `(iteration, type)` 定位后不需要跨类型回找）。

**做出来的东西（丙案）**

1. **协议**（`src/shared/agent-stream-protocol.ts`）：新增 `text_start` / `thinking_start` / `thinking_end` 三个无载荷事件，登记进 `CHAT_STREAM_EVENTS`；**不进** `AGGREGATABLE_EVENT_TYPES` —— 它们是控制类事件，被攒批就会打乱顺序。
2. **C# emit 点**：
   - 新增 `StreamSegmentBoundary`（`src/runtime/WishfulClaw.Agent/StreamSegmentBoundary.cs`）：记着「当前开着哪类块」，返回该发的边界事件。两个入口 —— `BeforeDelta(kind)`（OpenAI 系：kind 由到达的 delta 字段推断）；`OpenBlock` / `CloseBlock(kind)`（Anthropic：块边界由协议显式给出）；`AtEnd()` 收尾关掉仍开着的思考块。
   - `AnthropicMessagesEventParser.cs`：`content_block_start` 按 `block.type` 发 `text_start` / `thinking_start`；`content_block_stop` 对 thinking 块发 `thinking_end`。块类型按 index 记在 `AnthropicParseState.BlockKinds`。
   - `OpenAIChatProvider.cs`：SSE 与 JSON 两条路径，reasoning → `thinking_delta`、content → `text_delta` **之前**发边界；响应结束（`message_end` 之前）发 `AtEnd()`。
   - `OpenAIResponsesEventParser.cs` + `OpenAIResponsesState.cs`：`response.reasoning_summary_text.*` / `response.output_text.delta` 之前发边界，响应结束发 `AtEnd()`。
   - 边界事件用 `AgentRuntimeTools.EmitAsync` 直发（不经 `EmitProjectedEventAsync`），避免「已投影输出」的重试语义被边界事件改写。
3. **batcher**（`batcher-codec.ts` / `adaptive-event-batcher.ts`）：段边界是控制类事件 ⇒ 走既有的「先 flush 再直通」路径（不加分支）；**附带把甲案做了** —— `accumulateEvent` 遇 kind 冲突（缓冲里已攒着另一类）返回 false，调用方先 flush 再直通。窗口内**同类才攒** ⇒ `drainAccumulator` 的固定倒出顺序**不可能**再重排到达顺序。这条是「后端漏发边界」时的兜底。
4. **前端**（`stores/chat-store/index.ts`）：三个 case + `closeOpenThinkingSegment()` 助手。
   - `thinking_start`：置 `msg.thinkingBlockPending`（**瞬时字段，不入库**）⇒ 下一个 thinking delta **必开新段**。只收到 start 没 delta 时**不产生空段** —— 那正是 142 的表象。
   - `thinking_end` / `text_start`：关掉当前思考段（`completedAt`）、清 pending。
   - **text 分支不动**：仍按 S-133 的 `findLast`（跨工具卡与思考块并回同 iteration 的 text 段）。S-133 的「正文本来就该连贯」是老大裁过的口径，`text_start` 不强制开新段。

**为什么这个改法除根**

成因不是「谁先来」，而是 **batcher 攒批丢了到达顺序**：上游 reasoning 的最后一小片与紧随其后的 content 落进同一个窗口，`drainAccumulator` 固定「正文 → 思考」倒出 ⇒ 思考尾巴被排到正文之后 ⇒ 前端只见裸 delta、无从判断「这是同一段思考」⇒ 开新段。边界事件（控制类）把每次 kind 切换变成一次 flush 屏障，窗口内不再混类 —— 顺序不可能被重排，前端也不必再猜。

## 七、重开：初版未生效，改按 `(iteration, type)` 定位（2026-09-23 11:53）

**初版（11:01 那刀）实测未生效。** 老大 11:31 实测 + dev 库取证（会话 `9JffXuOXIrsfqGLXRYy92`，msg `wc-agent-1790132806262-l7hszn`）：同一 iteration（三段 `iteration` 全为 `28`）里 `[53] thinking(116 字) → [54] text(3604 字) → [55] thinking(45481 字)`。两段思考**内容互不重复**（`[53]` 那 116 字在 `[55]` 里搜不到、全消息只出现 1 次），且六个 thinking 段长度之和 `86+104+17+139+116+45481 = 45943` 与消息的 thinking 总量自洽 ⇒ **同一段思考被正文劈开，不是重复投递。**

**初版为什么没用**：初版把上游宣告的块边界（`thinking_start`）当成「必须另开一段」的权威信号（`msg.thinkingBlockPending = true`）。但上游发的是**两条独立流的交错分片**（思考 1_1 / 正文 2_1 / 思考 1_2 …）—— 思考每被打断一次再来，都会再发一次 `thinking_start`，前端就再开一段。**边界信号本身没错，错的是「边界 ⇒ 新段」这个推论。**

**上游实测（11:52，直连 opencode.ai `deepseek-flash`，Node SSE 探针）**：`reasoning(23985 字) → content(5596 字)` 单次切换、切完不回头；短问答（113 / 3 字）同型。⇒ 交错分片是**流式分片的自然产物**，不是网关重排，也不是 batcher 重排（batcher 已由初版改成「窗口内同类才攒」）。**渲染端不能拿到达顺序当段的身份。**

**新修法（老大 11:48「按照 Reasonix 改下吧，根据类型来」）**

| 点 | 改动 |
|---|---|
| 段身份 | `(iteration, type)` —— 本轮 `thinking` / `text` 各一个槽，delta 一律追加进槽，槽不存在才建 |
| 建段落位 | 新增 `insertSegment()`：新段插进本 iteration 段组内按 kind 固定序（`thinking < text < tool_use`）的位置；同轮多个 `tool_use` 仍按到达序 |
| `text` 分支 | 去掉 S-133 的 `findLast` 跨类型回找（按类型定位后自然跨过一切） |
| `thinking` 分支 | 同上；续写时撤回 `completedAt`（正文/工具卡曾在中间把它标成完结） |
| `thinkingBlockPending` | **退休**（字段 + 三个事件分支的读/写全删）；`thinking_start` 不再有 case |
| `closeOpenThinkingSegment` | 改为只关**本 iteration** 的思考段（段不再只追加到尾，倒扫会撞上后续轮次） |
| `tool_use` 两处 `push` | 一并改走 `insertSegment` —— 段落位只此一个入口 |

**参照物（老大点名）**：`D:\koda\DeepSeek-Reasonix-main-v2` —— 消息模型 `HistoryMessage { content, reasoning, toolCalls[] }`（`desktop/frontend/src/lib/types.ts:295`），流式状态 `live = { text, reasoning, reasoningComplete }`，`text` / `reasoning` 两条 case **各 append 到自己的槽**（`useController.ts:542-551`），`reasoningComplete` 只在收到 text 时置位。它**根本没有按到达顺序建的段数组**，所以天然免疫交错。我们保留 segments（一个 run 跨多轮，需要轮内时序），但把段身份换成 `(iteration, type)` —— 等价于它的「按类型分槽」加一层 iteration 分组。
