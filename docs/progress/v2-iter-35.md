## S-141：历史会话重启后首次发消息被误触发压缩

现象：进旧会话发第一条消息就触发上下文压缩，而前端明明显示用量才 25K / 上限 180K。

- **定性经过**：初判「前端按模型窗口、后端按 200K 兜底，同一份上下文两套分母」（S-108 取值链）**被推翻** —— 老大实测 UI 自洽；真问题是**后端触发加载时拿的是整个会话原始历史（≈144K），而不是压缩快照之后的活跃上下文**。分子错，不是分母错；`inputTokens=144083 > trigger=144000` 只是加载 bug 的副作用。
- **修法**：首次加载剥掉压缩快照带入消息的旧 usage，分子只取增量消息的真实值。

## S-142：同一段思考流被正文劈开

现象：回合末尾多渲染一个空思考流；DB 里同一 iteration 出现多个 thinking 段（`116 字 → 3604 字正文 → 45481 字`），两段思考内容互不重复 ⇒ 同一段思考被劈开。

- **三轮定性**：
  1. 初判 S-133 补完 `3366f8f1` 的 `findLast` —— **推翻**（劈出的 thinking 段非空）；
  2. 次判 S-135 batcher 的 `drainAccumulator` 固定顺序重排 —— **推翻**（交错分片是上游两条独立流各自分片的自然产物，不是 batcher 重排）；
  3. **终判**：思考与正文是**两条独立流**，各自分片交错到达（直连探针实测 `reasoning(23985 字) → content(5596 字)` 单次切换、切完不回头）。初版把上游的 `thinking_start` 当成「必须另开一段」的权威信号，错在「边界 ⇒ 新段」这个推论。
- **修法（对齐 Reasonix 的「按类型分槽」）**：段身份由「到达顺序」改为 `(iteration, type)` —— 本轮 thinking / text 各一槽，`insertSegment()` 按 kind 固定序（thinking < text < tool_use）落位，`thinkingBlockPending` 退休。
- **劈开是竞态、不是必现**：正文分片插进思考的两个分片之间才劈，插不进去就不劈 —— 这就是「昨天测不出、今天集体中招」的原因。
- **验证（真实数据，非自证）**：扫 DB（`messages.meta.segments` 即段的时序骨架），判据「同一 iteration 内出现多个非空 thinking 段」—— packaged 0.2.34 库 9/23 当天 82 条消息**全命中**（82/82）；dev 修复版 5 条**全净**。尺子不瞎 + 修复有效。
- **收尾补强**：段定位逻辑抽成纯函数模块 `chat-store/stream-segments.ts`（store 与回归套件跑同一份代码）+ 新增 `tests/stream-segments`（20 断言）—— 重开那一刀当时**零覆盖**（全迭代唯一改了核心逻辑却没新增测试的刀）。
