# S-279 · 普通消息（`send_session_message`）发出去就没法回 —— 需要轻量回执

> 归属：**v3-iter-5**。登记 2026-10-30 08:19（老大一次给三条，本条是第 2 条）。
> 老大原话：「全局会话发送的常规消息也要有可以回复的方式，因为现在是渲染成卡片了，所以可以携带一些参数过去，项目下会话回复的时候只需要拿到卡片标识之类的就能直接回复，不需要操心那么多参数。」

## 一、现象

全局会话和项目会话之间有两种通信：

| 工具 | 有 dispatch 记录 | 能回执 |
|---|---|---|
| `send_work_request` | 有（`gd_xxx`） | 能，靠 `reply_global_dispatch({ dispatchId, report })` |
| `send_session_message` | **没有** | **不能** |

所以「问一句 / 催一下 / 确认个细节」这类**普通消息**，项目会话回不了。模型只有两个选择：把答案写在自己会话里（全局会话看不到），或者干脆用 `send_work_request` 硬包一层（凭空建一个 dispatch，污染任务板）。

## 二、根因

`AgentRuntimeProjectExecutor.cs:274-328` `SendSessionMessageAsync`：

```csharp
var content = RequireString(input, "content");     // 裸文本，原样投递
...
w.WriteString("sessionId", sessionId);
w.WriteString("content", content);                 // ← 没有任何标识
```

投递端（`lib/tools/project-send-message.ts`）再走 `chatStore.sendMessage()`，**完全模拟用户输入**。

结果：目标会话收到一条普通用户消息，**没有 id、没有来源、没有回执通道**。而 `reply_global_dispatch` 的 schema 里 `dispatchId` 是必填（`GlobalDispatchReplyToolProvider.cs:28-36`）—— 没有 id 就没法回。

`send_session_message` 现有唯一的「回传」能力是 `followUp`（`SendSessionMessageAsync:285-316`），但那是**定时追问**：`delayMs >= 1000` 后全局侧主动再问一次，方向是反的，救不了这个场景。

## 三、目标形态（老大已给口径）

1. 全局会话的普通消息也渲染成卡片（与 S-278 同一套组件，只是 `kind` 不同）；
2. 卡片**携带标识**，项目会话回执时**只给卡片标识 + 正文**，不用重复传 sessionId / projectId / 全局任务等一堆参数；
3. 回执自动回到全局会话对应卡片的下面。

## 四、实现方向

**核心决定：普通消息也建一条轻量 dispatch 记录**，复用现有表与状态机，`kind` 区分。

| 项 | work request | 普通消息（新增） |
|---|---|---|
| `kind` | `work_request` | `message` |
| id 前缀 | `gd_` | 建议 `gm_`（`g`lobal `m`essage），或统一 `gd_` + kind 区分 |
| 绑全局任务 | 必填 | 可选（允许「就地问一句」不绑任务） |
| 进任务板 | 是 | 是（但默认折叠，避免噪音） |
| 回执工具 | `reply_global_dispatch` | **同一个工具**，`status` 只允许 `completed`（普通消息没有「进行中」） |

**回执工具要不要拆成两个？** 我的建议是**不拆** —— 一个 `reply_global_dispatch({ dispatchId, report, status? })` 够用，模型只需要记住「收到带标识的消息 → 用这个 id 回」。拆两个工具只会增加模型选错的概率（S-270 的教训：出口越少越好）。

**但要改的是 schema 必填项**：现在 `status` 是可选的、`report` 必填。普通消息的回执建议允许 `report` 为空（只是「收到 / 好」），此时自动填「已确认」。

## 五、待确认

1. **轻量 dispatch 会不会污染任务板**：每句问答都进看板显然不行。建议默认 `hidden_from_board=true`，只有 `work_request` 上板。
2. **id 前缀**：`gm_` 与 `gd_` 两套，还是一套 `gd_` 靠 kind 分？我倾向前者 —— 前缀能一眼看出类型，排查日志时省事。
3. **是否允许「回执再回执」**（全局会话对项目会话的回执再回一句）：按现在的机制会无限套娃。建议**只允许一层**：派发 → 回执，回执本身不再触发回执通道。
4. 与 S-278 的**实现顺序**：本条依赖 S-278 的 meta 通道（卡片标识要落进消息）。建议**同迭代同刀做**，顺序是 S-278 打底 → 本条扩 `kind`。
5. 与 **S-280（自动回执）** 的关系：普通消息**要不要也自动回执**？我的建议是**要**，但状态只标 `completed_implicit` 且卡片上明确写「未显式回复，已按本轮输出自动归档」—— 不能把沉默伪装成回答。
