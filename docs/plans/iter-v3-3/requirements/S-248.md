## 2. 偏差在哪（机械原因）

### 2.1 现在的档位只有一根轴

`render-density.ts:36-53` 的 `ChatRenderDensityPolicy` 一共 8 个字段，**全是布尔**：

```ts
runCollapseWhileActive / runCollapseWhenDone / toolOutputOpen
thinkingOpenWhileActive / thinkingCollapseWhenDone
subAgentOpenWhileActive / subAgentCollapseWhenDone / fileChangeOpen
```

`text` 档（`:57-66`）把这 8 个全设成「收起」。结果是：**折叠态还是卡片态**。
一屏仍是多少个带 `rounded-md border` 的壳、每个带 `+1 -1` 徽标、带 chevron、点了还能展开输出区。

老大要的是**换形态**：壳整个不存在，过程降级成纯文本行，且点不动。

**结论：policy 缺一根「形态」轴。** 这是 S-225 没做到的根因，也是本需求的核心交付。

### 2.2 目标形态的参照物就在仓库里

`SubAgentCard.tsx:120-128` 的 `SubAgentStepList`，一步一行：

```
✓  修改 s219-concurrent-edit-test.md 文件
●  执行命令 npm test
○  查看 index.ts 文件
```

每行只有三样：**状态字符**（10px）+ **中文描述**（11px，truncate）+（待审批时两个按钮）。
无边框、无 chevron、无输出区、无 diff 块、无 hover 卡。

描述文案来自 `lib/agent/sub-agents/step-descriptions.ts:114` 的 `generateStepDescription`：
中文动词 + 关键参数，文件类只取 basename，命令类截到第一个 `&&` / `|`，超 40 字截断。
状态符号/配色来自同文件 `:155` / `:171`。

**这套东西直接复用，不另写。**

## 6. 档位可逆（硬要求）

老大 09:41：**「这个就只是渲染方式变了，如果用户这个时候切换渲染方式还是能又回到现在的模式的」**。

含义：text 档只影响**渲染**，不影响**数据**。切回紧凑 / 详情档，必须完整回到现有卡片形态，包括：

1. 工具输出内容、diff、截图 —— 仍在 store 里，切回来能展开
2. 折叠状态按新档位的 policy 重新派生（不是沿用 text 档的收起态）
3. 待审批状态不丢：text 档下降级的工具如果此时进了 `pending_approval`，要能立刻恢复成可操作卡片
4. 子 agent 的 StepList、右侧面板切回来仍可用

**风险点**：降级后卡片组件不 mount，卡内 `useEffect` / 局部 state 全部不存在。
所以降级路径**只允许依赖 props 与 store**，任何"卡内自己攒的状态"都不得成为唯一真源。
验收时必须专门验这一条（`§8` 第 3 项）。

## 7. 不做什么

- **不改 S-225 的三档定义与顺序**（`text` / `compact` / `detail`）。本需求只补形态轴，不动档位本身。
- **不动 `compact` 档的任何表现** —— 它是 1.0.1 线上等价形态，零变化。
- **不改折叠条组件**（`execution-process-block.tsx`）。
- **不在 text 档新增任何交互**（不新做"点一下看详情"的替代入口）。
- **不动后端 / worker / 数据库**。
- **不改 `render-density.ts` 里既有的 8 个布尔字段语义**，只新增形态轴。

1. **text 档视觉**：一轮执行后，过程中没有任何卡片边框、没有 chevron、没有徽标；只有

2. **text 档禁点**：工具行点不动，不弹右侧面板，不展开输出区
3. **档位可逆**（重点）：同一段历史，text → compact → detail → text 来回切换，

   截图在 text 档**仍按原卡片渲染且可交互**
5. **待审批不丢**：text 档下某工具进入 `pending_approval`，能正常授权/拒绝（不是被降级成一行字）
6. **报错可辨**：失败工具行为红字，状态字符为 `✗`
7. **compact 档零变化**：与 1.0.3 表现逐项一致

### 10.2 与需求的偏差（三处，都有据）

1. **错误在 text 档不再浮出折叠面板。** S-225 定的规则是「折叠态下 `visibility === 'force'` 的项提到面板外」，而 `error` 会被归类成 `attention` ⇒ `force`。到了 text 档就变成：一个失败的 Edit 仍是浮在外面的一张卡片，与老大 2026-10-28 09:40「错误丢了就丢了，文字行显示红色就行」直接冲突。收窄办法：text 档只有**仍然必须是卡片**的项（答题 / 子 agent / 团队 / 生成图 / widget / 桌面截图）才浮出，错误留在面板里当红行。`compact` / `detail` 一字未动。
2. **运行中也降级。** 命令类工具跑起来时输出流不可见 —— 这是 §5「不提供点开输出」的必然结果，不是漏做。要边跑边看输出就切 `compact`。
3. **§9.1 按「保留」落地**：行尾有耗时（`formatDurationMs`，仅实时态有 `startedAt/completedAt`）和文件变更的 `+N -N`（有落盘快照时用 `resolveEditSummaryDiff` 现算，其余工具不付这份代价）。
