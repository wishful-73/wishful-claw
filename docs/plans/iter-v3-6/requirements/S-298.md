> 交付内容：`applyAvailable` 空串守卫（同版本保留 / 换版本清空）+ 一次重试 + 按版本号落盘缓存；门禁 typecheck 0 错 / `npm test` 121/121 / `ci-checks` 91/91 / dotnet 两套 sln 各 0 警告 0 错误
> 登记：2026-11-01 19:52
> 来源：老大原话「点击检查更新，会出更新弹窗，里面的更新说明不稳定，二次点开弹窗就看不到更新说明了，也就是看到有更新点击开始下载，然后点后台下载，过一会儿再点开看进度，结果没有更新说明了。这个计入下个版本做，然后官网也登记上标记未做」
> 官网侧：**已随「官网反馈无限期搁置」一并搁置**（2026-11-01），本迭代只做软件内

## 一、现象

1. 点「检查更新」⇒ 弹窗出现，**有**更新说明；
2. 点「开始下载」，再点「后台下载」关掉弹窗；
3. 过一会儿再点开 ⇒ **更新说明没了**，只剩进度。

第一次能看见、第二次看不见 ⇒ 说明文案本身没问题，是**状态被丢了**。

## 二、渲染层先排除

`UpdateDialog.tsx:142` 是「有内容就渲染」，没有缓存或条件分支会把已拿到的说明藏起来。所以问题一定在**状态源头**。

## 三、两条候选链路（根因未确认，先取证再改）

### 候选 A（我倾向这条）：说明是「一次性 best-effort 拉取」，没有重试也没有缓存

- `latest.yml` 从 0.2.39 起**不带** `releaseNotes` ⇒ 说明**只能**从官网单独拉 `release-notes-<版本>.md`（`src/main/lib/release-notes.ts:106`）；
- `fetchReleaseNotes` 把**所有** miss 都吞成空串：404、空 body、重定向到别的文档、超时、网络错误（`:116-122`，注释明确写 "Returns ... an empty string for every kind of miss"）；
- `announceUpdateAvailable`（`updater.ts:231-254`）只拉**一次**，失败即 `''`；
- `applyReleaseNotes`（`updater-state.ts:197-203`）**拒写空串**，也**没有第二次机会**。

⇒ **那一次请求失败 = 本次更新周期内说明永远空。** 「有时有、有时没有」正好对上「不稳定」。

### 候选 B：下载中的状态跃迁顺手清了一个不相干的字段 —— **❌ 已排除（2026-11-02 复核）**

原推测：`applyNotAvailable()`（`updater-state.ts:205-211`）在 `downloadedVersion` 为空时**连 `releaseNotes` 一起清**，而下载中恰好 `downloadedVersion === null`，于是「下载中点开弹窗 → 重查 → 说明被清」。

**复核结论：链路走不通。** `LEGAL_TRANSITIONS`（`updater-state.ts:20-30`）里写的是：

```ts
downloading: ['downloaded', 'error']
```

**`downloading → idle` 不合法。** 而 `applyNotAvailable()` 第一行就是 `if (!transition('idle')) return false` —— 下载中调用它直接返回 false，**根本执行不到清 `releaseNotes` 那行**。

⇒ 这条候选是我登记时没验跃迁表就写下的，不成立。**但「不相干字段被清」这个隐患本身是真的**，只是触发点不在下载中，见 §3.3。

### 3.3 复核补全：真正的根因链（候选 A 的具体形态）

全文件扫 `releaseNotes` 的写入点，只有三处写、一处清：

| 位置 | 行为 |
|---|---|
| `updater-state.ts:107` | 初始 `''` |
| `:171` `applyAvailable()` | **无条件写入** `input.releaseNotes` |
| `:201` `applyReleaseNotes()` | 有守卫（空串拒写、版本不匹配拒写） |
| `:208` `applyNotAvailable()` | 清空 —— 但下载中走不到（§候选 B） |

问题在 `:171` **没有守卫**。配合 `updater.ts:426-458` 的 `update-available` 处理：

```
update-available 事件
  → formatReleaseNotes(info.releaseNotes)   // 0.2.39 起清单不带 ⇒ 恒为 ''
  → applyAvailable({ releaseNotes: '' })     // :171 无条件清零，旧说明丢失
  → announceUpdateAvailable()                // 异步补拉，成功才恢复
      → resolveReleaseNotes → fetchReleaseNotes
```

**每次检查更新都把说明清零，然后靠一次异步补拉赌回来。** 补拉是 `fetchReleaseNotes`（`lib/release-notes.ts:106-126`）：5 秒超时，404 / 空 body / 重定向 / 超时 / 网络错误**全吞成空串**，无重试、无缓存。

⇒ 老大原话「不稳定」的准确含义：**不是说明丢了，是每次都要重新拿一次，拿不到就空着。**

### 3.4 现象已停，但缺陷仍在（2026-11-02 09:24）

老大反馈：「目前 S-298 更新说明不稳定 这个问题实际更新时没有遇到了」。

**这跟代码缺陷是否消失是两件事**：

- **现象窗口窄**：要求 `update-available` 之后那次补拉失败（网络抖动 / 官网瞬时不可达 / 5 秒超时）。发布服务器稳定时，补拉基本都成功 ⇒ 看不到。
- **缺陷是客观的**：`applyAvailable` 仍无条件清零、`fetchReleaseNotes` 仍无重试无缓存。换台网络差的机器、或官网抖动一次，现象就回来。

对比 **S-265（裸 body 400）的撤销先例** —— 那条撤销是因为**改我们自己的代码没用**（上游不再返那种报文），取证窗口关着。本条不同：**改代码能根治，且改动极小**（两处守卫 + 一个落盘缓存）。

⇒ 建议**降级但不撤销**，理由与处置见 §5.3。

## 四、取证步骤

主进程日志里找 `Updater could not resolve release notes for`：

- **出现了** ⇒ 候选 A 成立，走 §5.1；
- **没出现** ⇒ 说明当初拉到了，是后来被清的，走 §5.2；
- 两条都可能同时存在 ⇒ 两条都修。

## 五、方案

### 5.1 `applyAvailable` 加「空串不覆盖」守卫（核心，治根）

`updater-state.ts:171` 现在是无条件 `releaseNotes: input.releaseNotes`。改成：

```
新说明非空                ⇒ 写入
新说明为空且版本没变      ⇒ 保留旧说明
新说明为空且版本变了      ⇒ 清空（旧版本的说明不能挂在新版本下）
```

**为什么这条是核心**：它把「每次检查都清零再赌补拉」变成「有就更新、没有就留着」。补拉从此是**增强**而不是**唯一来源**，网络抖一次不再把说明打没。

`applyReleaseNotes`（`:197-203`）的版本守卫逻辑照抄，别写第二套判断。

### 5.2 补拉加一次重试 + 落盘缓存（治网络抖动）

- 拉失败后**重试一次**（短退避 ~300ms），仍失败才留空；
- 拿到的说明按版本号**落盘缓存**（`app.getPath('userData')` 下一个小文件，键是版本），同版本直接读盘，不再依赖网络；
- 缓存带版本守卫：换版本号即作废，不许串版本 —— 复用 `applyReleaseNotes` 的守卫口径（`:199`），不另写。

⚠️ **注意重名**：本文件早先写的 `fillReleaseNotes` 是笔误，代码里没有这个函数，正确名字是 `applyReleaseNotes`。

### 5.3 处置建议：降级，不撤销

老大 11-02 09:24 反馈现象不再复现。建议：

| 选项 | 评价 |
|---|---|
| **降级为「顺手加固」，退出刀 1**（建议） | 缺陷客观存在（§3.4），但复现窗口窄、不挡任何人的路。改动只有两处守卫 + 一个缓存文件，**做别的刀顺路带上**，不单独占一刀 |
| 撤销 | **不建议**。S-265 能撤是因为改代码影响不了上游；这条改代码能根治，且改动极小 |
| 保持刀 1 | 不建议 —— 现象停了还占第一刀，挡后面八条 |

**最终归属由老大定。** 本文件只给建议。

## 六、验收判据

1. 断开网络 → 检查更新 → 说明为空（合理）；恢复网络 → 重新检查 ⇒ **说明出现**（不再需要等下一个版本周期）；
2. 有说明的状态下，走一遍「开始下载 → 后台下载 → 再点开」⇒ **说明仍在**；
3. **有说明的状态下再触发一次 `update-available`（清单仍不带说明）** ⇒ 说明**不被清零**（这是 §5.1 守卫的直接判据，也是原现象的核心场景）；
4. 版本号变化 ⇒ 旧版本的缓存说明**不被误用**，新版本说明为空就是空；
5. `npm test` 里 `updater` 相关套件全绿，且新增判据做**反向验证**：
   - 把 `applyAvailable` 的守卫改回「无条件写入」⇒ 判据 3 必须变红；
   - 把版本守卫去掉 ⇒ 判据 4 必须变红。

## 七、明确不做的事

- **不动 `latest.yml` 的「清单干净」口径** —— 0.2.39 起刻意不内联 `releaseNotes`，那是发布流程的决定，不在这条需求里翻案。
- **不在渲染层做兜底缓存** —— 状态源在主进程，渲染层存一份会引入「两个真相」。
- **不登记官网侧** —— 官网反馈看板已无限期搁置。
- **不动 `LEGAL_TRANSITIONS`** —— 候选 B 排除后，跃迁表无需改动；它是别处多条逻辑的护栏（`updater-state.ts:14-18` 注释），不该为本条放宽。
