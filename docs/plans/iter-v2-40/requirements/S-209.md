# S-209：只出思考、不出正文的回合被判死 —— run 报「no usable assistant output」

> 状态：**已实施**（2026-10-16，iter-v2-40 实施态）—— 形态由**本机日志实证**收敛（§三）；修法 = **判定收窄 + 发提醒催一轮 + 临时副本注入**，落点见 §八。§5.3（GLM 内置清单）**未做**，见 §八 末条。
> 类型：**bug**（provider 兼容性）。
> 归属：**iter-v2-40**。
> 来源：**老大 2026-10-16 15:54 登记** —— 「登记一个bug openai-chat returned no usable assistant output (stopReason=stop, textLength=0, toolCalls=0)  这是模型glm 5.3 flash返回的。一个结束 但是没有返回任何信息，我们好像没兼容上」
> 追加口径：**老大 15:58**「正常的模型发送结束会带上消息返回。这个模型不讲武德结束的时候不带消息，这个跟思考没关系啊，不是已经返回了结束么」；**18:07**「那这个只能用测试实例然后，使用对应模型测试一下了，就是如果不好重现就麻烦了」。
> 轨道：**软件侧**（worker C# 响应判定链 + provider 内置清单）。

## 一、现象

- provider 报告**结束**（`stopReason=stop`），但正文与工具调用皆空 ⇒ worker 抛：

  ```
  openai-chat returned no usable assistant output (stopReason=stop, textLength=0, toolCalls=0)
  ```

- 用户观感：模型思考了半天，然后甩一个报错说「没有输出」—— 明明有思考。老大因此定性「不讲武德」。

## 二、代码事实（判定链）

1. **判定不看 `reasoningContent`** —— `AgentLoop.Helpers.cs:246`：

   ```csharp
   if (!string.IsNullOrWhiteSpace(assistantText) || toolCalls.Count > 0) return;
   // 否则 → 日志 + throw ProviderEmptyResponseException
   ```

   `reasoningContent` 只进日志（`:245` `reasoningLength`），**不参与判定**。

2. **思考内容其实已经流给 UI 了** —— `OpenAIChatProvider.cs:353-365` 边流边发 `thinking_delta`。⇒ 用户**看得到**思考，然后才看到报错。这就是"不讲武德"观感的来源。

3. **`stopReason=stop` 可能是我们兜底填的** —— `:65` 默认 `"stop"`，仅当上游真给 `finish_reason` 才覆盖（`:393-396`）；`native_finish_reason` 只有 OpenRouter 给（`:398-403`）⇒ GLM 直连时 `nativeStopReason` 恒 `<none>`。

4. **重试是生效的** —— `ProviderRetryPolicy.cs:160-163` 捕获 `ProviderEmptyResponseException` 重试（`attempt=1/20`）。⇒ 用户最终看到的报错 = **重试耗尽**。

## 五、修法裁定（老大 2026-10-16 18:13：**给模型发一条提醒**）

> 老大原话：「我希望收到这种，给模型发送一个提醒可以么」

**为什么必须"发提醒"而不是简单放宽**：

`AgentLoop.cs:456-468` —— `ToolCalls.Count == 0` 时：emit `iteration_end` → `TryCloseMessageQueueIfEmpty()` 为真 ⇒ `completed = true`，**run 以「正常完成」结束**。
⇒ 单纯放宽判定 = **报错变成静默空回复**（留个思考块、没正文、run 还显示成功），且**重试机会也没了**。这不是老大要的。

### 5.1 定案：判定收窄 + 提醒重试

1. **判定收窄**（`AgentLoop.Helpers.cs:246`）—— 让「有输出」在正文 / 工具调用之外**再认一种情况**：`reasoningContent` 非空。目的**不是**放过它，而是让 **turn 能正常返回**，把处置权交给 loop（现在异常在 provider 层就抛了，loop 拿不到 turn）。
2. **loop 拦截**（`AgentLoop.cs:456` 之前）—— 检查「`ToolCalls.Count == 0` **且** 正文空 **且** 有思考」⇒ **发提醒 + 再跑一轮**。
3. **提醒就是一条注入内容**，告诉模型上一轮只出了思考、必须给正文或工具调用。
4. **轮次上限**：连续 **2** 次催仍空 ⇒ 停止催，按现有逻辑收尾。
5. **iter-29 链路不受影响**：`reasoningLength == 0` 的真·空流仍抛 `ProviderEmptyResponseException`，仍走 `ProviderRetryPolicy`（§三 的 0/16 那类）。

### 5.2 ★ 提醒的注入方式：走**临时副本**（不污染聊天窗、不落库）

现成通道（iter-30 S-44 建的）：`AgentLoop.SessionTodo.cs` 的 `InjectSessionTodo` 走**临时副本** —— `conversation` 一字不动，只为本次请求构造一个附加了内容的副本（当时是为了不废掉前缀缓存）。

⇒ **提醒沿用同一手法**：
- 构造 conversation 的临时副本，末尾追加一条 user 角色的提醒；
- **不写进 durable conversation**、**不落库**、**聊天窗看不见** —— 零 UI 影响、零历史污染；
- 「催一轮」只需它存在一轮，之后自然消失，语义正好。

**否决「追加真消息到 conversation」**：
- 会进 durable（落库）+ 会显示在聊天窗（多出一条"用户发言"，用户没说过）；
- 踩坑先例：iter-33 的 `<current_time>` 就是"注入进最后一条 user 消息"，结果污染了压缩摘要的身份判定（`IsCompactionSummary` 失配）。

**提醒文案**（给模型看，中文；措辞属工程细节，实施时定稿）：

> 你上一条回复只包含思考过程，没有给出任何正文或工具调用。请给出你对用户请求的回答（正文），或调用必要的工具继续推进。

❌ **不做**：把 `reasoningContent` 当正文显示 —— 思考 ≠ 回答，会污染 UI。

### 5.3 附带发现（独立缺陷，建议一并修）：GLM-5.3 清单与官方冲突

智谱官方 `docs.bigmodel.cn/cn/guide/models/text/glm-5.3` 实读（2026-10-16）：

- **「GLM-5.3 会始终启用思考功能……并不再支持禁用思考功能」**；迁移提示：「如果您的应用当前使用 `thinking.type: "disabled"`……**否则，请求将失败**。」
- `reasoning_effort` 三档 `low` / `high` / `max`，**默认 `max`**；最大输出 128K；思考走 `delta.reasoning_content`（已解析）。
- 注意：该模型 1M 上下文 / 128K 输出 —— 思考长到吃满输出上限的可能性**真实存在**（§三 有 `length` 样本）。

`src/renderer/src/stores/providers/bigmodel.ts`：

| 位置 | 现状 | 问题 |
|---|---|---|
| `glm-5.3` `:112-115` / `glm-5.3-flash` `:129-132` | `disabledBodyParams: { thinking: { type: 'disabled' } }` | ❌ 官方不支持 ⇒ **UI 关思考必然请求失败** |
| 两者 | 无 `defaultReasoningEffort` | ⚠️ 不发 `reasoning_effort` ⇒ 服务端默认 `max`（思考最长） |
| 两者 | 无 `maxOutputTokens`（`glm-5.2` `:141` 有 `131072`） | ⚠️ 128K 上限没带上 |

**推测**：不设 effort ⇒ 默认 `max` ⇒ 思考拉满 ⇒ 更容易只出思考不出正文。**修它可能顺带降低本条触发率**（但非根治）。
