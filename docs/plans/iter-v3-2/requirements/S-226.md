## 6. 接口契约

### 6.1 统一响应信封

```json
{ "code": 0, "msg": "ok", "data": null }
```

三字段固定，`data` 承载泛型。

**HTTP 状态码只表达「请求是否到达并被正确处理」，业务成败全看 `code`。**

| 层 | 负责 |
|---|---|
| HTTP 200 | 请求正常走完，**不论业务成败**（参数错、限流、业务拒绝一律 200） |
| HTTP 404 / 500 | 路由不存在 / 未捕获异常，**JSON 体仍是同一信封** |

> 理由：参考文档 §14 里「401 被改写」「4xx 被 `error_page` 换成 HTML」「前端拿 HTML 当 JSON 解析」
> 四行坑，全部源于「用 HTTP 状态码传业务语义」。切干净后这类问题从根上不存在。
> 前端只有一条判断路径：`code === 0`。

### 6.2 码表（分段，永不复用旧码）

| code | 含义 | 段位 |
|---|---|---|
| `0` | 成功 | — |
| `10001` | 参数缺失或格式不对 | `1xxxx` 公共 |
| `10002` | 请求体不是合法 JSON | 公共 |
| `10003` | 字段超长 | 公共 |
| `10004` | 触发蜜罐字段 | 公共 |
| `20001` | 反馈类型只能是 `bug` / `feature` | `2xxxx` 反馈 |
| `20002` | 提交过于频繁 | 反馈 |
| `20003` | 反馈不存在 | 反馈 |
| `30001` | 管理口令无效 | `3xxxx` 管理（**预留未用** —— 认证在 nginx，进程内无口令） |
| `90001` | 存储层失败 | `9xxxx` 兜底 |

码表落 `server/common/codes.mjs`，前端照抄一份常量。新模块开新段（心相 App 运营站点用 `4xxxx`）。

### 6.3 端点（对外 2 个 + 管理 4 个）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/feedback` | 提交。字段 `type` / `title` / `content` / `contact`(可选) / `page`(可选) / `product` / `website`(蜜罐) |
| `GET` | `/api/feedback` | 公开读。**只返回 `status in (todo, done)`**；`pending` / `rejected` 永不外露 |
| `GET` | `/admin/feedback/` | 管理页，**nginx basic auth 保护**（见 §9.3） |
| `GET` | `/admin/feedback/api/list` | 审核列表（可按 `status` 过滤，含 `pending`） |
| `POST` | `/admin/feedback/api/set` | 改状态，支持批量 + 任意方向回退 |
| `POST` | `/admin/feedback/api/note` | 写内部备注 |

**管理端点的 API 全部挂在管理页路径下**（`/admin/feedback/api/*`），nginx 一条
`location ^~ /admin/feedback/` 全兜住，页内 `fetch('api/list')` 用相对路径即可。

`/admin/feedback/*` 不做额外口令校验 —— 认证由 nginx basic auth 在反代前完成；进程只监听
`127.0.0.1`，绕过 nginx 直连不可达。

## 7. 数据

### 7.1 目录

```
/data/services/wishfulclaw-feedback/
  ├── feedback.db
  ├── feedback.db-wal
  ├── feedback.db-shm
  └── feedback.log
```

**必须在 `/data/sites/` 之外** —— `deploy site` 是整目录原子替换，放里面等于一次发布清库。

`/data/` 根下现有 6 项（`CoHeart.db` / `obsidian-vault` / `uploads` / `downloads` / `sites` / `stats`）
**全部不动**，新东西只往 `sites/`（静态产物）与 `services/`（有人守的服务）两个目录里长。

### 7.2 表结构（对齐 `CoHeart.db` 的 `前缀_表` + `IX_` 索引命名）

```sql
create table fb_entry (
  id             integer primary key autoincrement,
  product        text not null default 'wishfulclaw',
  type           text not null,                     -- 'bug' | 'feature'
  title          text not null,
  content        text not null,                     -- 纯文本，无 Markdown
  contact        text,                              -- 可空，永不公开
  page           text,
  status         text not null default 'pending',   -- pending | todo | done | rejected
  ip_hash        text,                              -- 防刷用，永不公开
  -- 审核留痕（以下四列永不公开）
  reviewed_at    text,                              -- 最后一次审核时间
  reviewed_by    text,                              -- 'assistant' | 'owner'
  review_note    text,                              -- 驳回理由 / 并入去向 / 修复版本
  requirement_id text,                              -- 转成迭代需求时填 'S-233'
  created_at     text not null,
  updated_at     text not null
);
create index IX_fb_entry_product_status_created
  on fb_entry(product, status, created_at desc);
```

`product` 字段是为以后铺路：心相 App 的反馈进同一张表，加一个过滤参数即可，不用迁移。

**`requirement_id` 打通「用户反馈 → 迭代需求」链路**：一年后问「首页那个按钮截断什么时候修好的」，
一条 join 就能答；首页「已做」也能直接标出修在哪个版本。可空，成本近零。

### 7.3 SQLite 两个必钉的坑

| 坑 | 处置 |
|---|---|
| WAL 下裸 `cp` 备份会丢未 checkpoint 的数据 | 备份一律 `sqlite3 feedback.db ".backup /data/backup/..."`，**禁止 `cp`** |
| 并发写 `SQLITE_BUSY` | `journal_mode=WAL` + `busy_timeout=5000`；单进程串行写；耗时操作不包在事务里 |

### 8.2 客户端两层封装

```ts
export interface ApiResult<T> { code: number; msg: string; data: T | null }

/** 底层：原样返回信封，调用方自己判 code */
export function apiRequest<T>(path: string, init?: RequestInit): Promise<ApiResult<T>>

/** 便捷层：code !== 0 抛 ApiError(code, msg)，成功直接给 data */
export function apiData<T>(path: string, init?: RequestInit): Promise<T>
```

列表接口用 `apiData<FbEntry[]>` 一行拿到数组；需要特判某个码时用 `apiRequest` 拿全貌。

## 9. 审核

### 9.1 双通道

| 通道 | 谁用 | 形态 |
|---|---|---|
| **管理页** | 老大 | `https://wishful-claw.work/admin/feedback/`，nginx basic auth 保护 |
| **CLI** | 我（老郑） | SSH 后 `curl 127.0.0.1:7860/admin/feedback/api/...`，复用 `scripts/deploy.mjs` 的 SSH 模式 |

两条通道打的是同一组端点，只是入口不同。

### 9.2 管理页

**单文件 HTML + `fetch`，无框架、无构建**，由服务进程直接返回（**不放进 `website/public/`** ——
`deploy site` 是整目录原子替换，放站点里迟早被顺手删掉，且它本不该混进对外产物）。

```
待审 3 · 待办 5 · 已做 12
[bug] 首页手机端按钮被截断
10-26 14:02 · /download
（正文，纯文本）
[驳回] [待办] [已做]     备注：______
```

- 顶部四个状态标签（待审 / 待办 / 已做 / 驳回）切列表，带计数
- 每条三个按钮改状态，点完即时生效（`fetch` 后局部刷新，不整页跳）
- 备注框写驳回理由 / 并入哪条 / 修在哪个版本，失焦即存
- 正文纯文本渲染（`white-space: pre-wrap`）

### 9.3 管理页保护（nginx）

```nginx
location ^~ /admin/feedback/ {
    auth_basic           "WishfulClaw Admin";
    auth_basic_user_file /data/services/wishfulclaw-feedback/.htpasswd;
    proxy_pass           http://127.0.0.1:7860;
}
```

**不做登录页 / 不做 session / 不做 token** —— basic auth 配一个极端尺寸的服务正合适。
`/admin/feedback` 之外的 `/admin/*` 一律不反代。

| 项 | 值 |
|---|---|
| 用户名 | **`alwy`**（老大 2026-10-26 17:17 指定，不用 `admin` 这种通用名） |
| 密码 | 部署时生成 24 位随机串，**只在会话里发给老大**，本地不落文件 |
| 存储 | `/data/services/wishfulclaw-feedback/.htpasswd`，`chmod 600` |
| 多账号 | htpasswd 天然支持多行，心相运营站点复用时直接加行 |

### 9.4 审核边界（谁判什么）

**老大不终审。我审，能做的直接做，拿不准的才找他。**

| 情况 | 我的动作 |
|---|---|
| 明显垃圾 / 广告 / 灌水 | 直接 `rejected`，不打扰老大 |
| 重复（与已有条目或已实施需求重复） | 直接 `rejected` + `review_note` 写明并入哪条 |
| 清楚可做的**小需求** / 明确的 bug | 直接 `todo` → 开工 → `done` |
| 大需求（改架构 / 动数据面 / 有产品取舍） | 标 `todo`，**报给老大讨论**，定了才动 |
| 说不清 / 信息不足 | **不动**，留 `pending`，攒几条一起报 |
| 拿不准该收还是该驳 | 留 `pending`，报老大 |

**「直接做」的上限（防旁路）**：反馈条目**不得成为绕过迭代流程的通道**。

- 我能直接做的：文案修正、错别字、失效链接、明显显示 bug、参数默认值
- 做完仍然走**正常迭代流程**：登记 S-xxx、落需求文档、一个需求一刀 commit、过门禁
- 必须找老大：新增接口 / 改数据面 / 改对外承诺 / 影响已发布版本行为 / 视觉决策 / 第三方对接

⇒「直接做」= 省掉「要不要做」这一次确认，**不是**跳过工作流。

### 9.5 审核节奏

不实时盯。**每轮迭代收尾时**顺手过一遍待审队列，按这个形态报给老大：

| # | 类型 | 标题 | 我的判断 |
|---|---|---|---|
| 12 | bug | 首页手机端按钮截断 | 已修（S-234），标 `done` |
| 13 | feature | 场景级快捷键自定义 | 大需求，等你定收不收 |
| 14 | feature | 「希望支持 xx」 | 信息不足，留 `pending` 等追问 |

### 9.6 CLI

| 命令 | 作用 |
|---|---|
| `feedback.mjs list [--status pending] [--json]` | 列表，默认只列待审 |
| `feedback.mjs set <id,id,...> <status>` | 改状态，**支持批量、支持任意方向回退** |
| `feedback.mjs note <id> "..."` | 写内部备注（永不公开） |
| `feedback.mjs stats` | 各状态计数 + 距上次审核新增多少条 |

### 9.7 状态机（四状态必须能互回退）

```
pending ──approve──→ todo ──done──→ done
   │                  │  ←──reopen─┘
   └──reject──→ rejected
                  └──重新打开──→ pending
```
