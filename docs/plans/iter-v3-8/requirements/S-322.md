## 三、代码链路（主仓实读，2026-11-05 15:02）

### 3.1 三个方法，没有闸

`src/runtime/WishfulClaw.Agent/SessionConversationManager.cs`（主仓 **73 行**）全文只有 `GetOrCreate` / `TryGet` / `Remove` / `ClearAll`。**没有闲置时间判据、没有容量上限。**

类注释写的是：

> Lives for the process lifetime; entries are removed on session switch or explicit clear.

**这句话是错的。**

### 3.2 `Remove` 到底在哪调

主仓 grep 全部调用点：

| 位置 | 场景 |
|---|---|
| `AgentRuntimeTools.cs:408` | `agent/clear-session`（**显式**清空） |
| `SubAgentExecutor.cs:172` / `SubAgentExecutor.Background.cs:206` | 子 agent 结束 |
| `GoalOrchestratorModels.cs:120` | goal 结束 |

**没有一处是「切换会话」或「闲置回收」。**

### 3.3 为什么这一条就够解释 GB 级

`SessionConversation.cs:22`：

```csharp
private List<JsonElement> _wireConversation = [];
```

常驻字段，而 `JsonElement` 持有底层 `JsonDocument` ⇒ 一张 600 KB 的截图 base64，会随会话**一个字节不少地留在堆上**。

私有仓核对后的定性（`SessionConversationManager.cs:9-16`）：

> 滞留条目的真实来源是「**发过消息**的会话」（会话前后端分离，纯切换不建条目）：每个发过消息的会话都留在这儿，带着「解析后对象 + wire JSON」两份；跑完不会自己消失，直到会话被删除。压缩只让**单个**会话变小，从不让**别的**会话退出 —— 所以多会话累加就是 GB 级，且永远不会自己掉。这就是 worker `ws` 只涨不降的结构性来源。

## 四、根因

**没有淘汰策略。** 一个「发过消息的会话」的完整 wire 副本（含全部历史图片 base64）会活到进程退出为止，只有删会话能释放它。

这不是「压缩没做好」—— 压缩的作用域是**单个**会话，所以它永远治不了「十几个会话各占一份」。

## 五、修复方向

`SessionConversationManager` 补两条闸，判据直接照私有仓已定型的设计：

| 闸 | 取值 | 为什么是这个值 |
|---|---|---|
| 闲置淘汰 | **2 小时** | 对齐真实痛点「已经空闲 2 小时了，那条会话还在占着」。太短会把「切回去继续聊」变成一次全量 DB restore |
| 常驻上限 | **8 条** | 闲置时间压不住「一天发了十几个会话」。桌面 Agent 的活跃上下文基本是「手头这一两个任务」，8 条够覆盖来回，超额按最久未访问砍 |

配套：`SessionConversation` 加 `Touch()` 记最后访问时刻。

**淘汰是安全的** —— `AgentLoop.cs:83-89` 的逻辑是「`MessageCount == 0` 就从 DB 懒恢复」，下次进这个会话会自动重建。

## 六、代价与取舍

| 取舍 | 说明 |
|---|---|
| 「切回去」偶发一次 DB restore | 2 小时内不触发；超时后首次进会话多一次 DB 读。**拿一次 IO 换几百 MB** |
| status bar 的 cache hit/miss 累积计数会归零 | `SessionConversation._sessCacheHit` 是**展示指标**，不影响功能。验收里要显式确认「归零不算 bug」，否则会被当成回归 |

## 七、验收

| # | 项 | 怎么验 |
|---|---|---|
| 1 | **有效性** | 开 3 个不同会话各发一条带图消息 → 删掉其中 2 个 → `worker/memory` 的 `managed` **必须回落**，不是只停止增长 |
| 2 | **闲置淘汰** | 会话 A 发消息 → 等 2h（或临时把常量调小验流程，**验完改回**）→ 再进 A，消息完整恢复、能继续对话 |
| 3 | **容量淘汰** | 连开 10 个会话各发一条 → 最久未访问的 2 个被淘汰 → 切回去能看到完整历史 |
| 4 | **计数归零不算 bug** | 淘汰后 `_sessCacheHit` 归零属预期，**不得**当成回归 |
| 5 | **零行为变化** | 压缩、落库剥离、脏图拦截（S-246）、subagent / goal 的 `Remove` 全部照旧 |
