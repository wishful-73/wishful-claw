# S-314 · 热记忆（MEMORY.md）变更后系统提示不重建 —— 提示里长期是过期快照

> 状态：**📋 已登记（2026-11-04 16:18），排下个迭代 v3-7，未开工**
> 来源：老大 2026-11-04 16:15 追问「如果热记忆文档变了，要不要重写读取？读取了那么我们的前缀就变了，缓存命中率下降，不读取，那跟我现在这个方式有什么区别，提示里面的热记忆都是过期的」
> 关联：**S-313 §6.6**（热记忆指针化）—— 本条是它的前置缺陷，指针化顺带把本条消解
> 级别：bug（不是优化）

## 一、现象

系统提示里的 `<memory scope="...">` 块，在同一个 worker 进程里**永远是首次构建时的快照**。记忆热写（`memory_append` / `memory_hot_write`）之后不会刷新。

老大 dev 实例常开一整天 ⇒ 提示里的热记忆就是一整天的旧状态。

## 二、三条证据（实测，非推测）

### 2.1 注释承诺过

`SystemPromptCache.cs:46-47`：

> MEMORY.md mtime rides along so memory hot-writes rebuild on the next session too.

### 2.2 实现没做到

`GetPersonaFingerprint`（`SystemPromptCache.cs:83-124`）只扫：

```csharp
<项目>/.wishful-claw/personas/<personaId>/*.md
```

而 MEMORY.md 不在这里 —— `MemoryPathResolver.GetMemoryFilePath`（`MemoryPathResolver.cs:75-76`）：

```csharp
public static string GetMemoryFilePath(string? scope) =>
    Path.Combine(ResolveRoot(scope), "MEMORY.md");
```

本地项目的 root 是 `<项目>/.wishful-claw/`（`:66` `WishfulClawDataDir.ProjectRoot(...)`）⇒ **MEMORY.md 在 `personas/<id>/` 之外，压根没进 `cacheKey`**。

### 2.3 没有别的失效路径

`SystemPromptCache.Invalidate` / `Clear` **全仓 0 处调用**，两个方法都是死代码。

⇒ `ComputeKey` 的实际输入（personaId / workingFolder / language / userRules / sshConnectionId / projectId / sessionMode / pluginId / externalChatId / sandbox / persona 四件套 mtime）里**没有任何一项跟 MEMORY.md 有关**。

## 三、影响

- **单会话内不刷新** —— 设计上算「可接受」（保前缀稳定）；
- **跨会话也不刷新** —— 这才是 bug。注释承诺的是「next session rebuild」，实际是「worker 重启才重建」；
- **用户侧表现** —— 昨天写进记忆的结论，今天在同一个常驻 worker 里新开会话仍然读不到，agent 表现成「忘事」。

## 四、为什么不是「加个 invalidation」就能修

MEMORY.md 坐在系统提示里，而系统提示是 prompt 的**最前面**。想让内容新，就得重算提示 ⇒ 前缀变 ⇒ 提供商的**前缀缓存全失效**（`SystemPromptCache.cs:9-13` 的设计目标就是「byte-stable across turns」）。

**「内容新」和「缓存命中」在「塞全文」这个结构下天然互斥。**

现状选了「缓存」牺牲「新鲜」，但因为证据 2.2 / 2.3，连「跨会话刷新」都没做到 ⇒ **两头都没占到**。这也是老大那句「不读取，那跟我现在这个方式有什么区别」的由来 —— 实际上比「不读」更差：既过期，又白占 6,000 字符预算。

## 五、修法方向（由 S-313 §6.6 定案）

正解不是加 invalidation（那只会让前缀频繁失效），而是把易变内容从**前缀**挪到**尾部**：

1. **系统提示只留一行路径指针** —— 字节恒定，前缀缓存不回退；
2. **写入即注入** —— 记忆是我们自己的工具写的，写的那一刻就知道变了；把更新后的内容作为**工具结果**带回上下文（尾部，不碰前缀，额外往返为零，因为写入本来就要一次调用）；
3. **会话开头召回一次** —— 复用现有 `<memory-recall>`（`AgentLoop.MemoryRecall.cs`，`AgentLoop.cs:557` 首次 API 调用后清除 transient 召回）；
4. agent 需要旧账时自己 `Read` MEMORY.md。

⇒ S-313 §6.6 落地后，本条**随之消失**（不再存在「提示里的热记忆」这个东西）。两条应一起改，本条作为 §6.6 的验收依据。

## 六、验收标准（真机，不走代码走查）

1. **跨会话可见** —— `memory_hot_write` 写入一条独有标记 → **不重启 worker** → 新开会话 → agent 必须能说出这条；
2. **前缀不回退** —— 同一会话内多次调用，系统提示字节**不随记忆变化而变**；
3. **无额外往返** —— 除写入那一次工具调用外，不新增每轮读取。

## 七、范围

- **不改** `MemoryPathResolver` 的 scope 判定（global / project / project:ssh）；
- **不改** 记忆存储表结构；
- 与 S-313 §6.6 同一刀或紧邻两刀，但**必须可独立回滚**（留「热记忆全文注入」的回退口子）。

## 八、不解决什么

**本条修好也治不了「全局 PM 忘事」。** 那是 scope 隔离：`BuildMemoryContext`（`PromptBuilder.cs:228-249`）里全局会话走 `global`、项目会话走 `project:{工作目录}`，**两份记忆库物理分离**，全局 PM 读不到项目会话写的记忆。跟塞不塞提示、过不过期无关。那条另有需求（2026-11-02 登记的「当前会话用户发言查询」同源）。
