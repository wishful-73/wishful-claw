# S-193：会话底部用量统计可重置（浮窗「更多」的「删除会话」改为「重置用量统计」）

> 状态：**已实施**（2026-10-13，`ad2ac62f`）；**口径齐**（10:51 老大拍板方案 **B**）；待审查 + 待验证。
> 类型：**体验优化** —— 补一个缺失的重置出口，同时把浮窗里代价过大的「删除会话」换掉。
> 归属：**iter-v2-39**（迭代定位 = bug 修复 + 体验优化 / 能力补充）。

## 二、现象

1. 产品方向是**尽量不换会话**，于是单会话的累计 token 会一直涨。输入框下方那排指标已经出现 `1127.85M` 这类数字（单位到 M 封顶，值无限增长）。
2. 会话列表与浮窗里**没有任何「把统计清零」的入口**。想清掉这个数字，唯一的办法是**删掉整个会话** —— 消息、任务、右侧面板 tab 全没了，代价与诉求完全不匹配。
3. 侧边栏右键确实有个「清空消息」，但那是清消息（另见 §3.2），不是清统计。
4. 浮窗「更多」里当前只有 `重命名` + `删除会话` 两项，而 `删除会话` 是个不可逆的重操作。

## 三、静态定位（读码，未实机）

### 3.1 底部统计的数据链

输入框下方那排指标 = **两个字段相加**（`components/chat/InputArea/runtime-status.tsx:101-109`）：

| 字段 | 来源 | 性质 |
|---|---|---|
| `session.sessionUsageTotals` | 内存里的实时累计（`message_end` 事件累加） | 内存态，好清 |
| `session.usageBaseline` | 加载会话时由 `dbGetSessionUsageStats()` 从 DB 聚合出来（`stores/chat-store/session-slice.ts:874`） | **DB 派生** |

DB 侧聚合链路：

- `stores/chat-store/db-helpers.ts:601` `dbGetSessionUsageStats()` → worker channel `db/messages-usage-stats`
- `src/runtime/WishfulClaw.Infrastructure/Db/DbMessageCompactTools.cs:56` `UsageStats()`：
  ```sql
  SELECT * FROM messages WHERE session_id = @sid AND role = 'assistant' AND usage IS NOT NULL
  ```

⇒ **只清内存无效**：切走会话再切回来（或重启）`usageBaseline` 又从 DB 聚合回来，数字复活。

### 3.2 现有两个「清」都清不掉统计

| 动作 | 位置 | 动统计吗 |
|---|---|---|
| `clearSessionMessages`（侧边栏「清空消息」） | `stores/chat-store/session-slice.ts:431-461` | ❌ 只改内存 messages / messageCount / totalTurns…，不碰 `usageBaseline` / `sessionUsageTotals` |
| `deleteSession`（浮窗「删除会话」） | `stores/chat-store/session-slice.ts:195-249` | ✅（连会话一起删 —— 「能清掉」但代价过大） |

### 3.3 浮窗菜单

`components/layout/SessionConversationPane.tsx:258-275`：`DropdownMenu` 里两项 —— `重命名`（`:265`）+ `删除会话`（`:270`，`className="text-destructive"`）；处理函数 `handleDelete` 在 `:85-101`，带 `confirm(...)` 二次确认 + `navigationToHome`。

### 3.4 加列范例（本方案要照抄的既有做法）

`DbClientCompactionSnapshotMigrations.cs:87-90` 给 `sessions` 加 `context_revision` 就是这么干的（additive、幂等）：

```csharp
if (!columns.Any(column => string.Equals(column.Name, "context_revision", StringComparison.OrdinalIgnoreCase)))
    ALTER TABLE sessions ADD COLUMN context_revision INTEGER NOT NULL DEFAULT 0;
```

## 四、根因

**从来没有「重置会话用量统计」这个能力。**

- 统计 = `usageBaseline`（DB 派生）+ `sessionUsageTotals`（内存），二者都没有重置出口；
- 唯一能清掉它的 `deleteSession` 顺带毁掉整个会话 ⇒ 用户不会用；
- 于是数字只能单调递增，`1127.85M` 就是这条路走到头的样子。

---

## 五、修复方向（方案对比 + 裁定）

| | 方案 A：清 `messages.usage` | **方案 B：`sessions.usage_stats_reset_at`** |
|---|---|---|
| 做法 | `UPDATE messages SET usage = NULL WHERE session_id = @sid` | 清空时写时间戳；聚合 SQL 加 `AND created_at > @resetAt` |
| 迁移 | 无 | 加一列（additive，照 `context_revision`） |
| **副作用** | **毁掉逐条消息的 usage** —— AI 消息下方的 token 摘要（`AssistantMessage/token-summary.tsx` 读 `message.usage`）一起消失，超出「清底部统计」的本意 | 无。消息 usage 全留，逐条摘要不受影响 |
| 可逆性 | 不可逆（数据没了） | 可逆（改回时间戳即恢复） |

**裁定（老大 2026-10-13 10:51）：「可以 按照 B 来改动，确实应该是重置用量统计」** ⇒ 执行 **B**，入口命名定为 **「重置用量统计」**。

### B 的落地清单

| 侧 | 改动 |
|---|---|
| C# | ① `sessions` 加 `usage_stats_reset_at INTEGER NOT NULL DEFAULT 0`（additive 迁移）② `UsageStats` 聚合按 reset 过滤 ③ `DbModule` 注册 `db/session-reset-usage-stats` |
| TS | `db-helpers.ts` 加 `dbResetSessionUsageStats()` wrapper。**实施时砍掉了原计划的「`Session` 加 `usageStatsResetAt?` + `dbGetSessionUsageStats` 带上 resetAt」** —— renderer 不需要知道起点时间戳：重置后重拉一次 `dbGetSessionUsageStats` 拿到的就是归零后的值，过滤在 C# 侧聚合里做，少碰一处跨端类型映射 |
| renderer | 重置动作：调新 channel + 清内存两字段 + 重新取一次 baseline |
| UI | `SessionConversationPane.tsx` 浮窗第二项替换为「重置用量统计」（带二次确认）；zh / en 文案 |

**不需要「跨端四处登记」** —— 那是给 agent 用的工具才要；`db/*` 走 WorkerRequest 通道，`DbModule` 注册一行即可。

## 六、代价与取舍

> 实施回填（2026-10-13，`ad2ac62f`；静态核对，实机待验证）。

- 代价 1：`sessions` 多一列 schema（additive，老库自动补，无回填成本）。
- 代价 2：**UI 上没有「撤销重置」入口** —— 重置后旧统计只能靠改库恢复。对用户等价于不可逆（技术可逆）。
- 为什么可接受：用户点这个动作时的语义就是「我不要这段统计了」，与他诉求一致。
- 取舍：不在重置时删 `messages.usage`，因此**DB 体积不变** —— 这是有意的，见 §七。

---

## 七、刻意不做

> 实施回填（2026-10-13，`ad2ac62f`；静态核对，实机待验证）。

1. **不删消息、不清 `messages.usage`** —— 老大 10:28 明确「不清理数据库内的」，本条只动统计。
2. **不动设置页的全局用量统计** —— 那套读的是独立的 `request_usage_logs`（`DbUsageLogQueryTools`），与 `messages.usage` 是两条线，C# 注释里明写互不影响。
3. **不动「上下文用量」环**（`InputArea/context-ring.tsx`）—— 它算的是当前上下文占多少，是**瞬时值**不是累计值。
4. **不删侧边栏右键的「删除会话」** —— 只是把浮窗里那个换掉；删除会话仍从列表右键走。
5. **不加 G 单位** —— 老大 10:25 提到「是否增加 G 这些单位」但**未拍板**（他 10:51 只确认了重置统计）。单位与三套格式化实现的合并**另行裁定**，不在本条范围内。

## 八、阶段五审查回填（2026-10-13）

> 审查人：**独立 subagent**（`code-reviewer`，64 次工具调用）。报告：`plan-s193/review_report.md`。
> **结论：❌ 1（已修）/ ⚠️ 3（1 条已修、2 条留裁定）+ 1 条文档回填 —— 可进验证态。**

- **❌-1（已修，根修）重置后底部不会归零** —— `dbGetSessionUsageStats` 因 `hasUsage = AssistantReplies > 0` 返回 `null`，renderer 落到 `runtime-status.tsx:110-114` 的兜底分支，把**驻留窗口（默认 15 轮）**的逐条 `usage` 相加 ⇒ 显示的不是 0，且重启后依旧。与验收判据 1 直接冲突。
  修法：`DbMessageCompactTools.cs` 把 `hasUsage` 改判为 `AssistantReplies > 0 || resetAt > 0`（「重置过的会话，0 也是有效结果」），**一条修覆盖重置 / 切会话重载 / 重启三条路径**；`session-slice.ts` 补 `ZERO_USAGE_BASELINE` 零值兜底，`usageBaseline` 不再置 `undefined`。
- **⚠️-1（已修）重置失败静默** —— 补 `console.warn('[DB] resetSessionUsageStats rejected by worker:', sessionId)`；toast 未加（store 层调 UI 不合分层，仓库 toast 都在组件层），留裁定。
- **⚠️-2（留裁定）`DbClient.EnsureColumn` 的 `catch {}` 吞异常**（`DbClient.cs:773-776`）—— 一旦 ALTER 静默失败，聚合会因 `no such column: usage_stats_reset_at` **整体抛错** ⇒ **全仓所有会话**的底部统计退化成兜底相加，且无日志。属通用迁移原语改动，超出本条范围。
- **⚠️-3（留裁定）无回归测试** —— `tests/**` 搜 `usage-stats|UsageStats|usage_stats|usageBaseline|sessionUsageTotals` **0 命中**；加套件会动 `package.json` 计数（69 → 70），属范围外新增。
- **文档回填（已做）** 端点名订正：`db/sessions-reset-usage-stats`（复数）→ **`db/session-reset-usage-stats`**（单数，与既有 `db/session-reset-conversation` / `db/session-status` 同风格）。
- **附带观察（不改）** `sessionCacheHit` / `sessionCacheMiss` 重置后不清（当前无 UI 读取这两个字段）；渠道 `/stats` 对被重置会话会报「0 tokens」而非「无数据」（语义更准）。
