# S-278 · 全局会话发给项目会话的消息是裸文本 —— 希望识别出来渲染成组件

> 归属：**v3-iter-5**。登记 2026-10-30 08:19（老大一次给三条，本条是第 1 条）。
> 老大原话：「全局会话发送消息给项目会话，这个消息我希望能识别并且渲染成组件，包括全局任务下发，项目下会话对全局任务回执。」

## 一、现象

项目会话的聊天窗里，收到全局会话派下来的活，看到的是**一条普通用户消息**，正文长这样：

```
[GLOBAL AGENT WORK REQUEST] dispatch_id=gd_3f8a… global_task_id=gt_91c2…

<指令正文>

This work request was dispatched by the global agent. Decide yourself how to execute it
(including whether to create your own temporary Todos). Any notes or briefs you write for it
belong in `.wishful-claw/notes/`, not loose in the project tree. When you finish, get blocked,
or need to ask the global agent a follow-up question, report back via the `use_capability`
tool: action="call", capability_id="builtin:reply_global_dispatch", and pass
{"dispatchId": "gd_3f8a…", "report": "...", "status": "in_progress | completed | blocked"}
inside `arguments`, so the global agent can track the outcome.
```

**给模型看的协议说明，用户全看得见。** 没有卡片、没有来源标识、没有状态，也没法从这条消息里点回全局任务。

## 二、根因：投递路径就是「模拟用户输入」，不携带任何结构化信息

`send_work_request`（`AgentRuntimeGlobalTaskExecutor.cs:226-235`）拼好那段文本后，走反向请求 `project/send-session-message`；渲染端 handler（`lib/tools/project-send-message.ts`）拿到 `{ sessionId, content, ... }`，直接 `chatStore.sendMessage()` —— 文件头注释自己写着 *fully simulating a user action*。

于是：

| 环节 | 现状 |
|---|---|
| 落库的 `messages` 行 | `role = 'user'`，纯文本，**无 meta** |
| 渲染端能用的信息 | 只有正文前缀字符串 `[GLOBAL AGENT WORK REQUEST]` |
| dispatch 记录 | 有（`global_task_dispatches` 表），但**和这条消息没有 id 级关联**（只有 dispatch 表里的 `sessionId`，从消息反查不到） |
| 回执 | 同样只是一条 `role = 'user'` 消息塞进全局会话 |

所以「识别」只能靠正则嗅探正文，和 S-208 之前的状态一样 —— 而 S-208 的结论恰恰是**结构化字段进 meta，别让渲染端解析正文**。这条现在还是老样子。

## 三、附带问题：同一段协议文本有两份实现，已经漂移

| 位置 | 措辞 |
|---|---|
| C# `AgentRuntimeGlobalTaskExecutor.cs:233-235` | 走 `use_capability` → `capability_id="builtin:reply_global_dispatch"` |
| 渲染端 `task-board-store.ts` `buildWorkRequestContent()` | 「call the `reply_global_dispatch` tool」（注释自称 *mirrors AgentRuntimeGlobalTaskExecutor*） |

同一个动作，一份告诉模型「用代理调」，一份告诉模型「直接调工具」。两份都还在用（任务板派发走渲染端那份，全局 agent 派发走 C# 那份）。这条不修，后面加 meta 会改两遍，而且模型行为不一致。

## 四、目标形态（待拍板）

**派发消息渲染成一张卡片**，卡片上有：

- 来源：「全局会话」标识 + 全局任务标题（可点击跳任务板）
- 正文：只有 `instruction`，**那段协议说明不再给用户看**（留给模型，走别的通道）
- 状态徽章：`待处理 / 进行中 / 已完成 / 阻塞 / 失败`，实时跟着 dispatch 记录变
- 回执摘要：项目会话回过什么，直接挂在卡片上

**回执消息**在全局会话里同样渲染成卡片（对应 S-279）。

## 五、实现方向（三条，请老大选）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 反向请求加 `meta`（`dispatchId` / `globalTaskId` / `kind` / `globalTaskTitle`），`sendMessage` 落库带 meta；渲染端按 `meta.dispatchId` 直接出卡片，正文只留 instruction。**协议说明单独走一条不进消息流的通道**（或拼进 wire 但不入库） | 要动 `send-session-message` 参数、`sendMessage` 签名、DB meta 写入；协议文本与展示文本要拆开 |
| B | 只做渲染端识别：正则嗅探 `[GLOBAL AGENT WORK REQUEST] dispatch_id=xxx` | 零后端改动，但①用户还是能看到那段英文；②协议文本随时可能变，嗅探脆；③拿不到全局任务标题 |
| C | 先只把协议说明从消息正文里摘掉，卡片下个迭代再做 | 治标，且摘掉后模型失去回执指引 |

**推荐 A**。理由：S-208 已经把「结构化字段进 meta、正文只给人看」定成口径了，这条是同一套东西的延续；而且 S-279 / S-280 都依赖 `dispatchId` 能从消息侧拿到，A 不顺带做，后两条只能靠嗅探。

## 六、待确认

1. **协议说明放哪**：拼进发给模型的 wire 但不落 `messages`？还是落进 `meta.modelHint` 由 wire 构建时读？后者更干净，但要确认 wire 构建处能拿到 meta。
2. 全局任务标题是**派发时快照**还是**渲染时 join**？建议快照（任务改名不该改历史消息的显示），但状态徽章必须实时 join。
3. 老消息（1.0.4 之前派发的）没有 meta，卡片识别不了 —— 接受「老的仍显示原文」，还是渲染时兜底嗅探一次？建议接受，不做兼容层。
