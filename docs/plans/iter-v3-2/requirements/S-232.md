# S-232：发送给模型前对密钥类敏感信息做本地脱敏

## 1. 原话 / 来源

> 2026-10-27 09:15 老大：

> 登记一个需求
> 方案一:在Agent代码里加"发送前在你Agent的代码中，找到即将把文件内容或工具输出拼进Prompt的那一步。在发送给模型API之前，插入一个过滤函数:
> ·检测敏感模式:用正则匹配常见的密钥格式(如sk-、AKIA、包含password=的字符串等)
> 替换为占位符:把匹配到的真实值替换成[REDACTED]或一个假占位符，然后再发给大模型。
> 参考现有工具:GemFilter就是干这个的，它提供了Agent的pre-send hook，能在提示词、工具输出进入模型上下文前进行本地过滤。你可以借鉴它的规则逻辑，或者直接在你的Agent里集成它的库。"

性质：**安全加固**。状态：**无限期搁置**（2026-10-27 09:19 老大裁定，见 §10）。

## 2. 交付口径的边界先说清

老大贴的这段是**通用建议**，不是针对本仓架构的方案。落地到我们这里是两件事：

| 建议里的说法 | 我们的实际情况 |
|---|---|
| 「找到即将把文件内容拼进 Prompt 的那**一步**」 | **不是一个点**，是三条独立管线：`OpenAIChatRequestBuilder.WriteMessages:91`、`OpenAIResponsesInputWriter`、`AnthropicMessagesInputWriter`，各有自己的写出逻辑 |
| 「插入一个过滤函数」 | 过滤放哪比过滤规则本身更难：出站全扫与存储时脱敏的取舍相反（§4） |
| 「直接集成它的库」 | 我们是 **C# / .NET**，`GemFilter` 若是 Python / JS 包则无法直接引用，最多借规则表 |

> ⚠️ **`GemFilter` 我不了解**：无法确认它是否存在、规则表是否公开、什么语言、许可证如何。
> 不做任何假设，需要老大给源码地址或确认来源，否则这块按「自研规则表」推进。

## 3. 现状（已实查）

### 3.1 出站咽喉与四类文本

三条管线各有一份 `WriteMessages`，进 prompt 的文本共四类：

| # | 来源 | 位置 | 举例 |
|---|---|---|---|
| 1 | 用户消息 | `OpenAIChatRequestBuilder.cs:160` | 用户粘贴的报错里带 key |
| 2 | 助手消息 | 同文件 `:174` | 模型自己复述的 key |
| 3 | 工具调用参数 | 同文件 `:194`（`toolUse.Input.GetRawText()`） | `Edit(old_string="API_KEY=sk-…")` |
| 4 | **工具结果** | 同文件 `:131` → `ProviderContentHelpers.ToolResultToString` | `ReadFile(".env")` 的返回 |

另有一处不在消息里但同样出站：**system prompt**（人格 + 环境）。

### 3.2 已有的脱敏，都是局部的

| 位置 | 覆盖 | 规则 | 盲区 |
|---|---|---|---|
| `AgentRuntimeTools.SanitizeExceptionMessage:452-473` | **只有异常消息文本** | 3 条：`Bearer x` / `?api_key=` 类 query / `key=value` 键值对 | `sk-` 裸前缀、`AKIA…`、私钥块、JWT 全都**不命中** |
| `CodeGraphPathSafety.IsConfigLeafNode`（#383） | 只有 codegraph 读源码 | 配置叶子（yaml/properties 的 constant）只给 key 不给 value | 只作用于 codegraph 的 `getCode` |
| `ProviderHttpHeaders` | 请求头日志 | 值整体 redacted | 不进 prompt，只影响 `request_debug` 事件 |

**结论：全仓没有 pre-send 全局脱敏。** 异常消息那一层是本需求的现成先例（规则可以直接扩），但它只管一条通路。

## 4. 核心矛盾：脱敏做在「出站」还是「写入」

这是本需求真正的技术分水岭，**必须先定这一条，否则规则表写了也没处挂**。

### 4.1 出站脱敏（老大引用的形态）

在三条 `WriteMessages` 前对整段 conversation 做一次投影。

- ✅ 存储与 DB 保留真值，用户自己回看历史仍能看到原文
- ❌ **每次请求全量扫历史** —— 与上一迭代 T-7 的裁定直接冲突（老大 2026-09-14 原话：「不接受每次 provider 请求前扫全量，历史会话消息多，不做热路径空跑」）
- ❌ **击穿前缀缓存** —— 脱敏改变字节，缓存命中率掉下来，长会话成本变高（代码里多处注释在护 prefix cache）
- ❌ 压缩快照 / 子 agent / 渠道会话各有自己的组装路径，容易漏

### 4.2 写入时脱敏（源头）

工具结果写回 `SessionConversation` 时一次脱敏，之后所有消费方看到的都是脱敏后的文本。

- ✅ 一次开销，无热路径扫描，不动 prefix cache
- ✅ 压缩、子 agent、渠道、出站投影**全部自动覆盖**，不需要每处再挂一遍
- ❌ **真值永久丢失**：DB 里也是脱敏后的文本，用户回看历史看不到自己的 key
- ❌ **模型再也拿不到真值** → 见 §4.3 的死锁

### 4.3 致命问题：不可逆会把「改配置」这类活干坏

一旦模型看到的是 `[REDACTED]`：

| 场景 | 后果 |
|---|---|
| 模型 `Edit(".env", old_string="API_KEY=[REDACTED]", new_string="API_KEY=sk-new…")` | `old_string` 在磁盘上**不存在** → 编辑失败（相对安全，报错而不是写坏） |
| 模型 `Write(".env", "API_KEY=[REDACTED]\n…")` | **直接把 placeholder 写进用户文件** → 配置损坏，这是最高风险 |
| 模型需要真值去调接口（帮用户测 webhook、解析 token） | 干不了 |
| 模型 `ReadFile(".env")` 想拿真值 | 读到的是脱敏后的 → **死锁，无路可走** |

### 4.4 三个候选，取舍摆在明面上

| 方案 | 做法 | 能干活？ | 复杂度 | 我的判断 |
|---|---|---|---|---|
| **A · 出站不可逆** | 三条 writer 前全扫，替换 `[REDACTED]` | ❌ 写场景会坏 | 中（热路径 + 缓存问题） | **不推荐单独做**，风险最高 |
| **B · 来源侧** | 只对「从外面拿进来」的内容脱敏：WebFetch / 网页阅读 / 第三方文档 / 网关抓包 | ✅ 本地文件与会话文本不受影响 | 低 | 可以做，但挡不住用户自己粘贴 |
| **C · 可逆占位** | 出站时真值 → `[[SECRET_1]]` 并存映射；工具参数回来时反向还原再执行 | ✅ | **高** | 唯一能同时满足「不泄露」和「能干活」 |

**我的建议：第一版走 B + A 的收窄版，C 单独立项评估。**

理由：C 的复杂度被低估了 —— 映射表生命周期（跨轮次怎么保持）、模型改写占位符后匹配失败、压缩后映射丢失、子 agent 与主会话共享、并发 turn。第一版就上 C，等于为了一个安全需求造一套新状态机。

收窄版 A 的具体口径（建议）：

1. **只脱敏工具结果（第 4 类）与外部抓取内容**，不动 user / assistant 文本与工具参数
2. 命中后**追加一行提示**告诉模型「此处内容已脱敏，真值需用户自行提供」，避免模型以为文件里就是 `[REDACTED]`
3. **全局开关，默认开**，允许用户关掉（有人就是要在自己的机器上用自己的 key 干活）
4. **对 `Write` / `Edit` 类工具做兜底防护**：参数里出现 `[REDACTED]` 时拒绝执行并回报模型（防 §4.3 第二种）

## 6. 规则表初稿（待评审，非最终）

| 类别 | 正则 |
|---|---|
| OpenAI / 通用 sk | `sk-[A-Za-z0-9_-]{16,}` |
| Anthropic | `sk-ant-[A-Za-z0-9_-]{16,}` |
| AWS Access Key | `AKIA[0-9A-Z]{16}` |
| AWS Secret | `(?i)aws_secret_access_key\s*[=:]\s*\S+` |
| GitHub | `gh[pousr]_[A-Za-z0-9]{20,}` / `github_pat_[A-Za-z0-9_]{20,}` |
| Slack | `xox[baprs]-[A-Za-z0-9-]{10,}` |
| Google API Key | `AIza[0-9A-Za-z_-]{35}` |
| JWT | `eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}` |
| 私钥块 | `-----BEGIN [A-Z ]*PRIVATE KEY-----[\s\S]*?-----END` |
| 键值对 | `(?i)(?:password|passwd|secret|token|api[_-]?key|access[_-]?key)\s*[=:]\s*["']?[^\s"'&,}]{6,}` |
| 连接串 | `(?i)(?:mysql|postgres|mongodb|redis)://[^\s:]+:[^\s@]+@` |

现成的 `SanitizeExceptionMessage` 三条规则应合并进同一张表，避免两套正则各管一段、长期漂移。

## 7. 风险

1. **不可逆破坏用户文件**（§4.3）—— 最高风险，必须有 §4.4 第 4 条的兜底防护。
2. **前缀缓存击穿** —— 走了出站方案就有；写入时方案没有。
3. **误报吞掉正常内容** —— base64 图片、长哈希、`token: 123456` 这类正常文本会被当成密钥。规则越激进误杀越多，反过来规则越保守越没用。需要用真实样本对拍。
4. **与压缩的交互** —— 压缩摘要若保留脱敏后文本，模型后续会更依赖摘要而不是原文，信息损失放大。
5. **记忆召回同样会带密钥** —— 用户存进记忆的 token 会经 `memory-recall` 尾部注入进 prompt，这条通路也要一起覆盖（S-231 刚改过这块的注入位置）。
6. **性能** —— 若走出站全扫，历史越长越慢；详见 §4.1。

## 8. 范围外

- 不做「我们自己的服务器不经手 key」的架构改造（我们本来就是用户直连服务商）。
- 不做 DB 加密、不做本地存储加密（另一条独立的安全需求）。
- 不改 `SanitizeExceptionMessage` 的对外行为（只把规则表合并，判定结果保持一致）。
