- **扩 `Read` 本体，不新增工具** —— 对 `.png/.jpg/.jpeg/.webp/.gif/.bmp` 走图像分支，产出

## 三、两处本轮定的细节（iter-35 写「实施时定」）

### ① 非 vision 降级的数据来源

方案要求「`supportsVision === false` 时降级」，但 C# 侧拿不到模型能力（只有渲染端 `provider-store` 知道）。
**定：由渲染端在 run 参数里盖章 `supportsVision`**，位置选在 `sendMessage` —— 它是通往 `agent/run` 的唯一门，
六个 run 参数透传点不必各自查一遍模型能力（当年 `provider.sessionId` 就是只在某条路径上生效才出的问题）。
查不到模型时返回 `true`（不降级）：**宁可把图送出去让上游报错，也不要静默吞掉像素让模型猜内容**。

### ② DB 侧不落 base64 是「结构上成立」，不是靠事后剥离

- `tool_call_result` 事件里的 `Result` 保持纯文本摘要（`Read image: <path> (800x600, image/png)`），
  **base64 只走 wire 的 `tool_result.content`**，不进事件、也就不进渲染端 `meta.toolCalls`。
- 会话恢复时 wire 的 tool_result 是从渲染端存的文本结果**在内存里合成**的（见 `SessionRestoreTools` 头注），
  所以跨轮/重启后的历史里没有 base64 —— 模型需要再看就重新 `Read`（幂等、便宜），与 §3.3 一致。
- 兜底：渲染端 `limitToolResultContent`（`stores/agent-store/utils/tool-call-utils.ts`）本就会把超限 base64
  剥成「只留 filePath 的精简 image 块」，两条路都通往同一个结果。

## 六、扩容：读取视频（2026-09-24 登记，同日实施）

- **登记来源**：老大 2026-09-24 10:31 原话「读取文件之前只能返回文本，之前扩容了可以读取图片，我现在需要继续扩容 读取视频，你给我调整一下那个需求」
- **状态**：✅ 已实施（iter-36 本刀，未 push）

### 6.1 目标

同一个 `Read`，喂视频文件时模型能**看到画面**（若干帧），而不是拿到一堆容器元数据或乱码。

### 6.2 现状勘测（2026-09-24 实测）

| 事实 | 证据 |
|---|---|
| `Read` 无视频分支 | `FileReadTool.cs:98-102` 只判图像扩展名，其余一律按 UTF-8 文本读 |
| 项目**没有任何**抽帧 / 解码依赖 | 全仓 grep `ffmpeg` / `ffprobe` / `extractFrame` / `MediaFoundation` → **命中 0** |
| 渲染端**已能解码并播放本地视频** | `preview/viewers/video-viewer.tsx:60` 走 `FS_READ_FILE_BINARY` → base64 → Blob → `<video>` |
| 但那条路**全量读进内存** | 同上。预览小文件尚可，**抽帧不能照抄**（长视频会把内存和 IPC 一起顶爆） |
| 「带图结果」通路已通 | S-145 已让 `ToolResult.ContentBlocks` 从 C# 一路写到 wire 的 `tool_result.content` |
| 「C# → 主进程 → 渲染端」反向通道已存在 | `src/main/ipc/reverse-handlers/`（`window-capture` / `image` / `terminal` / `cron`） |

**结论**：抽帧**只能落在渲染端** —— 主进程是 Node 没有 DOM，C# 侧没有解码器；而已有的反向通道 + `ContentBlocks` 通路意味着这件事**不需要引入任何新依赖**，用 Chromium 自带的解码能力就够。

### 6.3 方案（建议，待拍）

- **入口不变**：仍是 `Read`。模型零学习成本；`Description` 补一句「视频会给你若干关键帧」。
- **判定**：按扩展名，沿用 `video-viewer.tsx:14-29` 那张表（`.mp4` / `.webm` / `.mov` / `.m4v` / `.mkv` / `.avi` / `.ogv` / `.3gp` / `.mts` / `.m2ts`）。
- **抽帧**：`<video>` seek → `<canvas>.drawImage()` → `toDataURL('image/jpeg', 0.8)`。渲染端已有 `drawImage` 先例（`image-mask.ts:124`、`image-clipboard.ts:87`），链路是熟的。
- **产出**：`[text(说明 + 时间轴), image(帧1), image(帧2), …]`，每帧前挂一行定位文本（形如 `[frame 3/6 @ 00:12]`），让模型能把结论说回到时间点。
- **降级**：解不了码的容器 / 超体积上限 / 非 vision 模型 —— 三种都只回文本（路径 + 时长 + 分辨率 + 为什么没给帧），与 §3.3 的降级口径一致。

### 6.4 约束（我给的默认值，待拍）

| 项 | 默认 | 理由 |
|---|---|---|
| 帧数 | **6 帧**（首帧 + 均匀 5 帧） | 视频天然要多帧；6 帧是够看操作步骤、又不至于把上下文顶掉的密度 |
| 单帧尺寸 | 长边 ≤ **1280 px**，JPEG q = 0.8 | 够看清界面文字，单帧约 100–200 KB |
| 视频体积 | ≤ **200 MB** | 超限只回元数据 + 提示，不把大文件读进内存 |
| 时长 | 不设硬上限；> 10 分钟时采样间隔相应拉大 | |
| 音频 | **不做**转写 | 要 ASR，是另一条链，不塞进 `Read` |
| DB | 帧图**不落 base64** | 与 §3.2 同一套机制：只走 wire，事件里只留文本摘要 |

### 6.5 待老大裁定

1. **帧数 6** 够不够？录屏分析想看得更细就得加（加帧 = 加 token）。
2. 要不要 **`start` / `end` 参数**（只看视频里某一段）—— 我建议要，长录屏只关心一段是常态。
3. **体积上限 200 MB** 是否合适。

### 6.6 实施时需确认（技术风险，未验）

- **本地媒体能否进 `<video>`**：生产是 `loadFile`（`main/index.ts:182`，`file://` 源），dev 是 `http://localhost`（`main/index.ts:180`）—— dev 下 `file://` 子资源可能被 webSecurity 拦。若被拦，走自定义协议或主进程分片代理。
- **Chromium 实际可解码的容器**：`.avi`、部分 `.mkv` 大概率解不了 —— 实测后把不可解码的并入降级，别写成「支持」。
- **反向通道选型**：复用 `reverse-handlers` 加一条，还是把视频分支整体做成「渲染端执行型工具」（与 Desktop / Browser 同类）—— 实施时定，需求只锁行为。

### 6.7 实施记录（2026-09-24 同日落地）

> 上面 6.3–6.6 是**登记当天**写的方案与默认值，保留原样作对照；下面是**实际实施**的样子，差异单列在 6.8。

- **入口不变**：仍是 `Read`。`Description` 补一句「视频会被取样成若干帧返回」。
- **判定用一份共享清单**：原表从 `video-viewer.tsx` 提进 `src/renderer/src/lib/media-file-types.ts`（14 项，含 `.mpeg/.mpg/.3g2/.ogg`）；C# 侧 `VideoFileProbe.MediaTypes` 是等价的一份。跨语言没法共用代码，套件**逐项比对两侧**，任何一边改了另一边没跟就红。
- **抽帧落在渲染端**：C# 的 `Read` 通过 `ToolExecutionContext.VideoFrameExtractor` 把活交给 `AgentRuntimeVideoFrameExtraction`（反向请求方法 `vision/extract-video-frames`，与 `browser/tool-request` 同一条既有通道）。
- **分片读，不整文件读**：`fs:read-file-binary` 新增 `offset` / `length`（不传时行为与从前逐字一致），`planChunks` 按 4 MB 切片，拼 Blob → `objectURL` → `<video>`。
- **抽帧**：seek → `drawImage` → `toDataURL('image/jpeg', 0.8)`；seek 后若浏览器有 `requestVideoFrameCallback` 再等一帧落定（`seeked` 只保证位置变了，直接画可能画到上一帧）。
- **产出**：`[text(一行说明：分辨率、时长、帧时间点), image(帧1), …]`，帧按时间顺序。
- **降级四种，全部只回文本且必须说明原因**：非 vision 模型 / 本 run 没有抽帧通路 / 超体积上限（**抽帧前**就拒，不白搬文件） / 渲染端抽帧失败（原样带上它给的原因，并让模型别猜）。

### 6.8 实施值与登记默认值的差异

| 项 | 实施值 | 差异与理由 |
|---|---|---|
| 帧数 | **4 帧** | 登记写 6。4 帧够看一段片子的大意，token 省三分之一。**要改就是一个常量**（`VideoFileProbe.FrameCount`） |
| 单帧长边 | **768 px**，JPEG q=0.8 | 登记写 1280。768 已能看清界面文字，token 与 base64 体积都按面积降 |
| 视频体积 | **≤ 256 MB** | 登记写 200 MB |
| 每帧前的定位文本 | **没做**（只在总说明里列时间点） | 4 帧一图一条文本会把 tool_result 撑成两倍块数；时间点已在说明里，够模型说回时间轴 |
| `start` / `end` | **没做** | 新参数 + 新交互，等老大拍 —— 挂账见 6.10 |
| 时长 / 音频 / 不落 base64 | 一致 | — |

**帧块为什么故意不带 `filePath`**（与 §3.3 图像的做法相反）：图像带路径是为了让持久化把 base64 换成占位、重载时按路径 hydrate。帧的路径指向的是**视频**，重载时按路径读回来的是整段视频，`<img>` 会渲染成一个打不开的图。宁可让大帧在历史里落成 `[image data omitted, N base64 chars]` 这句文本，也不留一个指向视频的假图像引用。

### 6.9 登记时列的「实施时需确认」（已闭合）

- **本地媒体能否进 `<video>`** → 不经 `file://`：分片读进来拼 Blob，`createObjectURL` 的地址与页面同源，dev / 生产都不涉及 `file://` 子资源与 webSecurity。
- **canvas 污点** → 同源 blob 不产生污点，`toDataURL` 不会被 `SecurityError` 拦。这也是**不**用「自定义协议直连本地文件」的原因：跨源媒体把 canvas 污点化，而给一个能读任意本地路径的协议开 CORS 等于开一个本地文件读取口子。
- **Chromium 到底能解哪些容器** → 不猜：解不了就由 `<video>` 的 `error` 按 `MediaError.code` 给出原因（aborted / network / decode / unsupported），原样写进给模型的文本。所以 `.avi` / 部分 `.mkv` 认得出扩展名、但会在抽帧这一步降级成文本 —— 这是预期行为，不是 bug。
- **反向通道选型** → 复用既有 `agent/reverse-request`，不新做「渲染端执行型工具」。
