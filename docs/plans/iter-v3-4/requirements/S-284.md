## 二、现象（实测，会话 `9yXnLPAM00ea6qAXu6qPp`）

单条助手消息 `meta` **14,496 KB**，其中图片 base64 **13,238 KB**（6,619 KB × 2，`toolCalls` 与 `segments` 各一份同一张图）。

打开这一个会话：`db/messages-list-by-turns` 单次响应 **32.6 MB**，渲染进程 `ws=1477 MB peak=2328 MB`。

**图本来就在盘上** —— S-283 已经落了：`{dataRoot}/screenshots/{yyyy-MM}/{sha256前16}.png`。

## 四、根因

落盘了，但**没告诉剥离器文件在哪**。`stripImagePayloads` 的剥离条件从一开始就要求 `source.filePath`（S-224 定的，为的是「没有 filePath 的块一旦被剥，图就彻底没了」），这个安全条件是对的 —— 缺的是写入方没把 `filePath` 填进去。

## 五、方案

### 5.1 C#：两个 `Create*Content` 往 `source` 写 `filePath`

| 位置 | 改动 |
|---|---|
| `AgentRuntimeDesktopExecutor.Encoding.cs` `CreateScreenshotContent` | 函数开头 `var filePath = JsonHelpers.GetString(response, "filePath");`，image block 的 `source` 里加 `if (!string.IsNullOrEmpty(filePath)) writer.WriteString("filePath", filePath);`（签名不动 —— `response` 本来就在手上） |
| `AgentRuntimeDesktopExecutor.Encoding.cs` `CreateAppWindowCaptureContent` | `filePath` 已取好，`source` 里加同样一段 |

**`data` 一个字节都不少** —— 模型这一轮仍要看到图。剥的是**落库那份副本**，不是给模型的。

### 5.2 TS：剥离器认字符串化的 JSON

`output` 是 `"[{\"type\":\"image\",…}]"` 这种字符串（被上游 stringify 过一层），`stripNode` 现在遇到 string 直接原样返回。

改法：字符串先做**三道廉价判别**（长度 ≥ 32、首字符是 `[` 或 `{`、且包含 `&quot;image&quot;`），命中才尝试 `JSON.parse` → `stripNode` → `JSON.stringify`；解析失败原样返回。

判据用 `"image"` 而不是 `"base64"`：要剥的块靠 `type === 'image'` 认，字符串里出现 `"base64"` 反而可能是 thinking 正文在讨论 base64（实测库里就有）。判别错了的代价是白 parse 一次，成本可忽略。

**保持既有安全条件不变**：仍然是「四个都满足才剥」，只是现在能看见字符串里的块了。

### 5.3 渲染层：`filePath` 兜底成 `src`

剥掉 `data` 之后，重新打开会话时那条消息只剩 `filePath`，**必须能显示出来**。

| 位置 | 现状 | 改动 |
|---|---|---|
| `lib/tools/image-block-source.ts:25-28` `resolveImageBlockSource` | `src` 只认 `base64` 或 `url` | 加 filePath 兜底：`filePathToMediaUrl(filePath)`（`lib/local-media-url.ts:14`，`oc-media://local/<encoded>`） |
| `AssistantMessage/content-renderer.tsx:159` / `:484` | 内联拼 `data:` | 收敛到 `resolveImageBlockSource` 或各自补兜底 |
| `BrowserToolCard.tsx:173`、`DesktopActionToolCard.tsx:259`、`ToolCallCard/utils.ts:92` | 同上，各自一份 | 同上 |

`oc-media://` 白名单按扩展名、不限目录（S-283 已核），`screenshots/` 下的 `.png` 能直接显示。

### 5.4 内存里的消息不受影响

`stripImagePayloads` **返回深拷贝、不改原对象** —— 当前会话的 `msg` 里 `data` 还在，正在执行的这一轮照常显示。
只有**从库里重新加载**的消息才只有 `filePath`，走 5.3 的路径显示。

### 5.5 worker 上下文不受影响

上下文重放走 `session_compaction_snapshots.wire_conversation`（53 行，日志 `lazy-restore source=snapshot`），**不读 `messages.meta`**。所以剥掉库里的副本对模型侧零影响。

## 六、预期收益

| 指标 | 现在 | 剥完 |
|---|---|---|
| 单条 meta | 14,496 KB | **1,257 KB** |
| 首屏 32.6 MB | 32.6 MB | **约 6 MB** |
| 单次 upsert 的 stringify | 14.5 MB | **1.26 MB** |
| 148 次 upsert 总分配 | 2.07 GB | **186 MB** |

**实测（10-30，真库那条 `wc-agent-1793264773464-cz0mvm`）**：给 32 个 image 块补上 `filePath` 后跑 `stripImagePayloads`，

```
14.34 MB  →  1.41 MB     降幅 90.2%
image 块总数 32，仍带 data 的 0
```

产物里残留的 6 处 `iVBORw0KGgo` 与 2 处 `;base64,` **全在 thinking 文本里** —— 是模型自己讨论 base64 时引用的字面量，不是图片载荷，不该动。

剩下那 1.4 MB 是纯文本 output（836 KB）+ thinking 两份（272 KB）+ 结构开销 —— 归 **S-285（拆表）** 处理。

## 七、代价与取舍

1. **老消息不动。** 10-30 之前存进库的 meta 里 `source` 没有 `filePath`，剥离条件仍不满足 ⇒ 那些会话不会瘦下来。存量要治只能靠「按需回填」或迁移脚本，另立。
2. **图片显示多一次磁盘读。** 用 `data:` 时图在内存里，用 `oc-media://` 时每次渲染要读盘。文件很小（PNG 几十到几百 KB）且 Chromium 会缓存，实测感知不到。
3. **剥的是副本，写入路径静默生效。** 出问题时不会有报错 —— 只能靠「库里 meta 体积」来判断是否生效，验收时必须量字节。
4. **`stripNode` 增加一次 `JSON.parse` 尝试。** 只对「首字符像 JSON 且含 `"base64"`」的字符串做，绝大多数工具输出直接短路。

## 八、刻意不做

| 不做 | 为什么 |
|---|---|
| **不删 image block 本身** | 模型要用图，只是不给库里存副本。 |
| **不动 `data` 的写入时机** | C# 侧照旧内联返回，剥的是落库那次。 |
| **不做存量迁移** | 动老数据风险与收益不成比例（S-285 §七 同口径）。 |
| **不去重 `segments` 与 `toolCalls`** | 那是结构冗余，归 S-285；本条只处理 base64。 |
