## 2. 现象

模型调这些工具时**参数被静默丢弃**，得到空值：

- `FeishuSendImage` / `WeixinSendImage` —— `imagePath` 丢了 ⇒ `filePath` 是 `""` ⇒ 发图必失败
- `FeishuAtMember` —— `userIds` 丢了 ⇒ `@` 谁？⇒ 必失败
- `FeishuSendUrgent` —— `userIds` / `urgentTypes` 丢了 ⇒ 加急给谁、按什么方式？⇒ 必失败
- `FeishuBitableDeleteRecords` —— `recordIds` 丢了 ⇒ 删空
- `FeishuListChatMembers` —— `pageSize` 丢了 ⇒ 退默认值（不报错，数量不对）
- `ChannelSendAudio` —— `durationMs` schema 声明了但 `ResolveGenericRoute` 根本不往外写 ⇒ 静默丢弃（**刀 3 自己带进去的**）

前几条的错误信息是「路径为空」「user_ids 为空」这种，看着像模型没传参，实际是**我们读错了名字** —— 排错方向会被带偏。

## 3. 代码链路（2026-11-09 实读）

### 3.1 两套读取风格，只有一套有回落

`AgentRuntimeChannelPluginExecutor.cs` 里读入参有四个 helper，行为**不一样**：

| helper | 实现 | 能否读 camelCase schema |
|---|---|---|
| `R(call, name)` | `GetString(input, name)`，**name 含 `_` 时**再读 `ToCamelCase(name)` | ✅ |
| `WReq(w, call, out, in)` | 内部走 `R(call, in)` | ✅ |
| `WOpt(w, call, out, in)` | `GetString(input, in)` —— **精确** | ❌ |
| `WOptI(w, call, out, in)` | `GetIntNullable(input, in)` —— **精确** | ❌ |

`JsonHelpers`（`src/runtime/WishfulClaw.Core/Protocol/JsonHelpers.cs`）全部用 `element.TryGetProperty(name, out …)` —— **大小写敏感、精确匹配、没有任何回落**：`GetString`(:7) / `GetBool`(:16) / `GetIntNullable`(:55) / `GetStringArray`(:111)。

**`R()` 那个回落是唯一的安全网。** 它的规则是「name 里**有下划线**才转 camelCase」—— 所以 `R(call,"file_path")` 能读到 `file_path` 和 `filePath`，但 **`R(call,"file_path")` 读不到 `imagePath`**（`imagePath` 不是 `file_path` 的 camelCase 形态，是另一个词）。

### 3.2 谁给模型看 schema

`ChannelPluginToolProvider.cs`（261 行）注册 `ToolDefinitionPlaceholder`，带 `InputSchema` → 进 `ToolRegistry` → **这才是模型可见的工具定义**。

渲染端 `plugin-tools.ts` 那套 `ToolHandler.definition`（用 `file_path` 蛇形）是**死的**：`registerPluginTools()` 全仓**零调用**（只有定义和一行注释）。所以「两套 schema 打架」不是问题，问题只在 C# 这一侧。

> **订正记录（2026-11-09 13:xx，实施时打开 `ChannelPluginToolProvider.cs` 逐行核过）**：本表初次登记时是**从 executor 的读取代码反推** schema 应该长什么样，不是实读，三处记错 —— `FeishuAtMember` 写成 `userIds`/`text`/`atAll`（那是 executor 侧，schema 实际是 `userId` 单数 + `content`）、`FeishuSendUrgent` 写成 `urgentTypes`（schema 实际是 `urgentType` 单数）、`FeishuListChatMembers` 写成 schema 有 `pageSize`（实际没有、要补）。**教训：对照表里凡带「schema 属性」的列，必须打开 provider 逐行看，不能从对面推。**

> `FeishuSendUrgent` schema 的属性名是 `urgentType`（单数，字符串），executor 读的是 `urgent_types`（复数，**数组**）—— 这不只是名字对不上，**形状也对不上**，即使名字改对也得处理单值 → 数组。

## 4. 根因

**同一个「读入参」的动作有两套实现，其中一套（`R`）带了 camelCase 回落，另一套（`WOpt` / `WOptI` / 直接调 `JsonHelpers`）没带。**

`R()` 那个回落是后补的补丁，只补了必填字符串字段，没补可选字段、数字、数组、布尔。于是「后来新增的工具」只要用到可选/数组参数，**默认就是坏的** —— 而且不报错。

跟 S-352 §6.4 记的「同一件事有两份实现」是同一种病。

## 5. 修复方向

### 5.1 治根：一个归一化入口，所有读法走它

在 `AgentRuntimeChannelPluginExecutor.cs` 里加一个解析器，**先精确、再 camelCase、再 snake_case**，返回实际命中的属性名：

```csharp
// 语义：给定我们的规范名（camelCase），返回 input 里真正存在的那个 key
private static bool TryGetProp(JsonElement input, string name, out JsonElement value)
```

然后 `WOpt` / `WOptI` / 数组 / 布尔全部改走它。`R()` 也并进去，消掉那个「有下划线才回落」的特例。

### 5.2 schema 侧要不要也统一

两处 `imagePath` **改成 `filePath`** —— 跟 `FeishuSendFile` / `WeixinSendFile` / `ChannelSendImage` 对齐。理由：同一个语义（"本地文件路径"）在 11 个工具里出现，9 个叫 `filePath`、2 个叫 `imagePath`，**没有理由**。

`FeishuSendUrgent.urgentType` 单数 → 复数 `urgentTypes` 数组，跟 executor 对齐。

### 5.3 兼容性

只改 schema 的话，旧会话 / 缓存的 prompt 里可能还留着 `imagePath`。归一化入口（5.1）天然兼容旧名，所以**不用额外写兼容分支** —— 这是把 5.1 做掉的额外收益。

## 6. 代价与取舍

- **改动面**：`AgentRuntimeChannelPluginExecutor.cs`（helper 重写）+ `ChannelPluginToolProvider.cs`（三处 schema 改名）+ 可能同步 `plugin-tools.ts` 的死代码（要么删要么一起改，不能留两套说法）
- **风险**：`WOpt` / `WOptI` 是**所有**渠道工具共用的 helper，改错了整个飞书集成一起崩。所以必须逐工具回归，不能只看编译过
- **验证**：现有 `npm test` 130 条里**没有一条覆盖这个 executor** —— 这是它坏到现在没人发现的原因。要么补一条，要么真机逐工具过一遍

## 8. 实施记录（2026-11-09 13:xx，commit `ab2b2dbe`）

### 8.1 改了什么

**`JsonHelpers`（`WishfulClaw.Core/Protocol`）** —— 加四个「值已取出」的解析入口，并把原来四个 `Get*` 改成委托它们：

| 新增 | 说明 |
|---|---|
| `AsString(JsonElement)` | 非字符串返回 `null` |
| `AsBool(JsonElement, fallback)` | 走既有 `ParseBoolText`，容忍 `" FALSE "` |
| `AsIntNullable(JsonElement)` | 数字或数字文本 |
| `AsStringArray(JsonElement)` | JSON 数组或 `"a,b"` 文本，空串与空白元素丢弃 |

> 为什么先动这里：原来 `GetString` / `GetBool` / `GetIntNullable` / `GetStringArray` **各自把同一套「判 ValueKind 再取值」写了一遍**，四份实现、四条演化路径 —— 这本身就是 S-353 的同源病。抽出 `As*` 后只有一份，`Get*` 变成「定位 + 委托」。

**`AgentRuntimeChannelPluginExecutor`** —— 加 `TryGetProp` 作为**唯一读入口**：

```csharp
private static bool TryGetProp(JsonElement input, string name, out JsonElement value)
{
    if (input.ValueKind == JsonValueKind.Object)
    {
        if (input.TryGetProperty(name, out value)) return true;
        var alternate = name.Contains('_', StringComparison.Ordinal) ? ToCamelCase(name) : ToSnakeCase(name);
        if (input.TryGetProperty(alternate, out value)) return true;
    }
    value = default;
    return false;
}
```

配套：`R`（必填字符串，trim）/ `RArray` / `RBool` / `WOpt` / `WOptI` 全部改走它；新增 `ToSnakeCase`（原来只有 `ToCamelCase`，只会蛇→驼一个方向）。

**`ChannelPluginToolProvider`** —— schema 与 executor 对齐：

| 工具 | 改前 | 改后 |
|---|---|---|
| `FeishuSendImage` / `WeixinSendImage` | `imagePath` | `filePath`（与 `FeishuSendFile` / `WeixinSendFile` / `ChannelSendImage` 统一） |
| `FeishuAtMember` | `userId`（单数）/ `content` | `userIds`（数组）/ `text` / `atAll`（布尔，可选） |
| `FeishuSendUrgent` | `urgentType`（单值枚举） | `urgentTypes`（数组枚举） |
| `FeishuListChatMembers` | 只有 `chatId` | 补 `pageSize` / `pageToken` |

### 8.2 实施中发现的两处额外缺陷（一并收了）

1. **`BitableMut` 的 `if…else…;` 无条件尾巴**
   ```csharp
   if (call.Input.TryGetProperty(arrayName, out var arr)) arr.WriteTo(w); else w.WriteStartArray(); w.WriteEndArray();
   ```
   C# 里 `if (x) A; else B; C;` 的 `C` **无条件执行**。所以命中数组时会在对象内多写一个 `WriteEndArray` ⇒ `InvalidOperationException`。也就是说 `FeishuBitableCreateRecords` / `UpdateRecords` / `DeleteRecords` **只要真传了数组就会崩**（不只是读不到）。改成显式 `return`。
2. **`FeishuBitableListApps`** 的执行体是 `_ => { }` —— 一个字段都不写，schema 里那个 `pageSize` 永远送不到插件。改成 `WOptI(w, call, "page_size", "page_size")`。
