# S-280 · 全局任务的回执不能只靠 agent 自觉 —— 需要确定性的归档机制

> 归属：**v3-iter-5**。登记 2026-10-30 08:19（老大一次给三条，本条是第 3 条）。
> 状态：**✅ 已交付（v3-iter-5 刀 10，2026-10-31 00:10）**。实施记录见 §七。
> 老大原话：「全局会话下发的全局任务，有时候项目下会话做完以后不进行回执，这个需要不依赖 agent 本身做回执，得我们想想其它办法。」

## 一、现象

全局会话派活 → 项目会话干完了 → **dispatch 记录停在 `pending`，看板上永远「待处理」**。全局 agent 只能靠 `list_global_dispatches` 反复问，问了也看不到结果。

## 二、根因：回执是「一个工具调用」，模型可以选择不调

`reply_global_dispatch` 是可选的工具（`GlobalDispatchReplyToolProvider.cs:18-38`），调用与否完全看模型当轮的决定。它会漏，至少四个原因：

| 原因 | 说明 |
|---|---|
| **没看到** | 那段协议说明写在**消息正文**里，长会话一压缩就没了（S-275 / S-276 那条链路正在放大这个） |
| **忘了** | 活干得很长，收尾时注意力在结果上，不在「该调哪个工具」 |
| **不认为自己该调** | 指令里说的是「改某个文件」，它改完就完事，不觉得这算「汇报」 |
| **这轮不是在做这件事** | 会话被别人接着用了，`loop_end` 跟这个 dispatch 无关 |

**把「状态正确」押在模型的自觉上，本身就是设计缺陷。** 这和 S-267 / S-268 是同一类病：我们让「成功」依赖于一个可被跳过的步骤，然后假装它是确定行为。

## 三、可观测的事实（我们能拿到什么）

不依赖 agent 的前提，是承认**只有一件事是确定的**：会话跑完一轮会发 `loop_end` 事件。

| 事实 | 来源 | 可靠度 |
|---|---|---|
| dispatch 已投递 / 被拒 | `AgentRuntimeGlobalTaskExecutor.cs:247-270` 的 `deliveryResult` | 确定 |
| 目标会话开始跑一轮 | agent stream `loop_start` / 首条 `message_start` | 确定 |
| 目标会话跑完一轮 | agent stream `loop_end`（`use-channel-auto-reply.ts:477-528` 已在订阅同一事件） | 确定 |
| 这一轮**是不是在干这个 dispatch** | **没有直接信号** | ⚠️ 未知 |
| agent 显式回执 | `reply_global_dispatch` | 确定，但可缺席 |

**唯一缺的是第 4 行。** 方案要围绕它设计。

## 四、方案：三层归档，显式永远优先

### 第 1 层 · 投递态（已有，补状态名）

投递成功 → `delivered`；失败 → `failed`（已有 `MarkDispatchFailed`）。这一步不用改。

### 第 2 层 · 执行态（新增，事件驱动）

投递后盯住目标会话：

- 该会话 `loop_start` → dispatch 转 `in_progress`（**不再依赖 agent 说「开始了」**）
- 该会话 `loop_end` → 进入第 3 层归档

### 第 3 层 · 归档（新增，隐式 vs 显式）

| 情况 | 归档结果 | 卡片显示 |
|---|---|---|
| 本轮内 agent 调了 `reply_global_dispatch` | `completed`（**显式**） | 「已完成 · 已回复」 |
| 本轮结束但没调 | `completed_implicit` | 「本轮已结束 · **未显式回复**」+ 该轮最后一条 assistant 正文摘要 |
| 该轮正文里明确说卡住了（可选启发式） | `blocked` | 「阻塞」 |
| 投递后 N 分钟无 `loop_start` | `not_started` | 「目标会话没有启动」 |
| 投递后 N 小时仍无变化 | `stale` | 「长时间无动静」 |

**三条硬规矩：**

1. **显式覆盖隐式，反向不许** —— agent 后来补了 `reply_global_dispatch`，把 `completed_implicit` 升级成 `completed`，报告覆盖掉自动摘要。
2. **隐式不许伪装成完成** —— 卡片上必须能看出「这是自动归档、不是它回的话」。这一条是底线，跟 `S-267`「不许把坏数据包装成好东西」同一个原则。
3. **自动归档只写 dispatch 记录，不往全局会话塞消息** —— 否则全局 agent 会被系统消息刷屏，且分不清哪句是项目会话真的说的。全局 agent 通过 `list_global_dispatches` 读，或者由它在下一轮自己判断要不要追问。

## 五、第 4 行那个未知项怎么办（核心难点）

「这一轮是不是在干这个 dispatch」有三种判法，按可靠性排序：

| 判据 | 做法 | 代价 | 我的评价 |
|---|---|---|---|
| **强（推荐）** | S-278 的 meta 落库后，worker 每轮构建 wire 时能看到「本会话有未回执 dispatch（含 id、投递归属时间）」⇒ 写进系统提示的固定位置；同时渲染端归档时用「投递时间之后的该会话轮次」精确关联 | 要动 C# wire 构建 + 系统提示拼装 | 最准，且顺带解决「协议说明被压缩掉」的问题（挪出消息正文后不会再被压） |
| 中 | 渲染端自己算：dispatch 投递时间 → 该会话在该时间点之后的**第一个 `loop_end`** | 纯渲染层 | 撞上「会话当时正忙」就会误归档，可用但会有假阳性 |
| 弱 | 正则扫该轮正文有没有提到 dispatch / 任务标题 | 纯渲染层 | 太脆，不建议 |

**推荐强判据**，但它把 S-278 从「渲染美化」升级成了本组的**前置依赖**。实测数据点：老大观察到的「有时候不回执」正好对应「工作内容长、压缩发生、协议说明被折叠」那条链 —— 也就是说弱判据在这个场景下最不可靠。

**折中（可先落地的版本）**：先做中判据 + 三个约束收窄假阳性 —— ①只有 `loop_start` 发生在投递之后的轮次才算；②该会话同一时间只允许一个「待归档」dispatch，多个就按投递顺序串行归；③归档结果一律标 `implicit`，全局 agent 看到 `implicit` 默认应该复核而不是信。等 S-278 的 meta 到位再换成强判据。

## 六、待确认

1. **超时阈值**：`not_started` 与 `stale` 各给多久？建议 5 分钟 / 12 小时（都要能配）。
2. **启发式判 `blocked` 要不要做**：靠正文关键词（「做不到」「缺少」「报错」）判阻塞，误判代价是全局 agent 白跑一趟。**我倾向不做**，统一 `completed_implicit`，让全局 agent 读正文自己判断。
3. **归档后的通知**：完全不通知（靠 `list_global_dispatches` 轮询）还是发一个不打扰的事件让全局会话的看板徽章更新？建议只更新看板数据，不塞消息。
4. **项目会话连跑多轮**（一个 dispatch 需要好几轮）：第 2 层 `in_progress` 期间每轮 `loop_end` 都归档会把活截断。建议：**首轮结束后 `loop_end` 归档，但如果 agent 下次显式回执就覆盖**；或者**只在「本轮没有 trigger 新一轮」时才归档**（靠 `loop_end` 后是否紧接 `loop_start` 判断）。这条需要实测确认取舍。
5. **和 S-279 的关系**：普通消息也走同一套归档，状态只给 `completed_implicit` / `completed`，不给 `in_progress`。

## 七、实施记录（v3-iter-5 刀 10，2026-10-31）

### 7.1 落地位置

- **归档层**：`src/runtime/WishfulClaw.Infrastructure/Db/DispatchArchive.cs` —— `ArchiveImplicitCompletions(sessionId)`，**一个入口覆盖两张表**（`gd_` 任务派活 + `gm_` 消息派活）。放在 Infrastructure 而不是 Agent：它只依赖 DB 工具，放上层会逼着 Agent 反向引用。
- **触发点**：`src/runtime/WishfulClaw.Agent/AgentLoop.cs` 的 `EmitLoopEndAsync`，timeline 段旁；归档条数 `>0` 时 `WorkerLog.Info`。
- **状态判据**：全部走 S-279 抽出的 `DispatchStatusMachine`，**不复制第二份**。
- **新状态值**：`GlobalTaskDispatchStatusValues.CompletedImplicit = "completed_implicit"`。

### 7.2 三条硬规矩怎么落的

| 硬规矩 | 落地方式 |
|---|---|
| **显式永远覆盖隐式** | `IsTerminal` 与 `IsImplicitCompletion` **刻意分成两个函数**，注释写明「防止有人图省事把 completed_implicit 并进终态集合」 |
| **隐式必须标明「未显式回复」，不许伪装成完成** | `latest_report` 写 `DispatchArchive.ImplicitCompletionReport`（含「未显式回复」字样）；任务板徽章加 `completed_implicit`，配色**中性灰**而非绿色 |
| **自动归档只写 dispatch 记录，不塞消息** | 归档层只 `UPDATE` 两张派活表，不碰 `messages` |

### 7.3 顺手修掉的真缺陷

`ResolveExplicitReply(currentStatus, requestedStatus)` 原先把 `completed_implicit` 与 `pending` / `sent` 归为一类，**不带 `status` 的显式回执会返回 `acknowledged`** —— 一条「已经跑完、只是没回执」的记录，补交回执反而退回「刚确认收到」。这是**降级**，与「显式永远覆盖隐式」正好相反。

修法：`IsImplicitCompletion(currentStatus)` 单独一支，返回 `completed`。

反向验证：退回旧逻辑 ⇒ 3 条断言当场红。

### 7.4 一条被改掉的断言（不是实现）

初版回归写了 `completed_implicit cannot be cancelled`，跑出来红 —— `CanCancel` 的实现是「非终态即可取消」，而 `completed_implicit` 不是终态。

**结论是改断言、不动实现**：取消是**人的显式动作**，不会把「未回执」伪装成「已完成」；反过来禁掉取消，全局会话就会有一张「未显式回复」的卡片永久挂着，既清不掉也关不掉。

### 7.5 回归

`tests/WishfulClaw.DispatchRouterRegressionTests`（真 sqlite，非 mock）**72/72 通过**，覆盖：

- 归档一把覆盖两张表（`archived == 2`）
- 显式完成的记录**不被隐式覆盖**，且 `latest_report` 原样保留
- 空 / 空白 `sessionId` 安全返回 0（不扫全库）
- 幂等：重复归档返回 0、`completed_at` 只盖一次
- 别的会话不受影响
- 状态机纯函数：`IsTerminal` / `AcceptsExplicitReply` / `ResolveExplicitReply` / `ShouldMarkImplicitCompletion` / `CanCancel`
- 端到端：归档成隐式 → 裸回执 → `completed`，且隐式标记被显式正文替换
- agent 不得自己声明 `completed_implicit`（只有归档层可以）

### 7.6 已知未做

- §六 第 1~4 条待确认项（超时阈值 / `blocked` 启发式 / 归档通知 / 连跑多轮）**本刀均未实现**，按推荐口径取最保守值：不启发式判 `blocked`、不塞消息、不在 `in_progress` 期间归档。
- 「这一轮是不是在干这个 dispatch」仍用**中判据**（会话级 `loop_end` 归档），未上强判据 —— 强判据要动 C# wire 构建 + 系统提示拼装，属于下一刀的量。

## 八、真机验收（4 条，**尚未跑**）

本刀补登 —— 原需求单只有自动化回归（72/72），没有真机判据。归档层是**事件驱动**的（会话 `loop_end`），只有真跑一轮才可能触发，纯函数测不到「到底会不会被调」。

前置：dev 实例已启动，库 `~/.wishful-claw-dev/index.db`。

| # | 操作 | 判据（SQL） | 看错了说明什么 |
|---|---|---|---|
| 1 | 全局派一条任务（`gd_`）给某项目会话，**让它正常跑完但不要显式回执** | `SELECT status, latest_report FROM global_task_dispatches WHERE id='<id>'` ⇒ `status='completed_implicit'`，`latest_report` 带「未显式回复」标记 | 仍是 `in_progress` ⇒ 归档层没挂上 `loop_end`；`completed` ⇒ 被误判成显式完成 |
| 2 | 同一条记录，之后补一次显式回执 | `status='completed'`，`latest_report` 是**显式正文**（隐式标记被替换） | 还是 `completed_implicit` ⇒ `AcceptsExplicitReply` 判错，回执丢了 |
| 3 | 派一条**显式回执**的正常任务 | `status='completed'`，`completed_at` 只有一份 | 被隐式覆盖 ⇒ 第 3 层「显式永远优先」没做到 |
| 4 | 会话内跑一轮**与任何 dispatch 无关**的普通对话 | 该会话所有 dispatch 的 `status` 不变 | 有记录被归档 ⇒ 归档判据太宽，会误伤 |

**为什么必须真机**：归档触发点是 agent 循环结束事件（`AgentLoop.cs:721-733`），单元测试里是手动调 `DispatchArchive.ArchiveImplicitCompletions(sessionId)` 模拟的 —— 真实循环会不会走到那一行、`sessionId` 传得对不对，只有真跑能验。

**基线事实（2026-10-31 实测备份库）**：`global_task_dispatches` **7 行，全部 `completed`**，`completed_implicit` **零记录** —— 说明隐式路径从上线到现在**一次都没触发过**。这 4 条是真机首次验证。
