# S-285 · 助手消息的块结构拆出独立表 `message_parts` —— 工具调用改为追加写

> 归属：**移交 v3-iter-5**（2026-10-30 14:32 老大拍「拆表先登记」）。
> 前置：**S-284（剥 base64）**，以及可选的 segments 去重。

## 一、原话 / 来源

老大 2026-10-30 14:28：

> 「写库走的是 db/messages-upsert → 整行覆盖 meta。工具调用每完成一个就 upsert 一次，每次都把整条 meta 重新 stringify 再发过去。那条消息 148 次工具调用，于是 14 MB × 148。**那这个可以改一下么？再加一个表，新的助手消息都是另一个表？**」

14:29 补一句：「**只是讨论，而且最好能兼容老数据**」。

## 二、现象（实测，会话 `9yXnLPAM00ea6qAXu6qPp`）

单条助手消息 `wc-agent-1793264773464-cz0mvm`，`meta` **14,496 KB**：

| 构成 | 体量 |
|---|---|
| `toolCalls[].output` 里的图片 base64 | **6,619 KB** |
| `segments[].tool_use.output` 里的图片 base64（**同一张图的第二份**） | **6,619 KB** |
| `toolCalls` 纯文本 output | 415 KB |
| `segments[].text` | 421 KB |
| `thinking`（segments 内 + 顶层**各一份**） | 136 KB × 2 |

写入侧：`dbUpsertMessage` 在**每个工具调用完成边界**写一次 ⇒ 这条消息 **148 次 upsert**，每次都把整条 meta 重新 `JSON.stringify` + 过 IPC：

| 每步 | 单次 | ×148 |
|---|---|---|
| `JSON.stringify` 分配新串 | 14.5 MB | **2.07 GB** |
| IPC 传输 | 14.5 MB | **2.07 GB** |

日志佐证：`memory role=renderer ws=1477.2MB peak=2327.8MB`。

**注意：S-284（剥 base64）做完后仍有 1,257 KB**，这是本条存在的理由 —— 剩下的重量来自结构冗余与大段文本 output，不是图片。

## 三、根因

工具调用在语义上是**追加**的（第 N 个完成 → 多一条记录），而 `messages.meta` 是**整行覆盖**的。用覆盖语义去模拟追加，每次都要重算全部历史。

## 四、方案：新表 + 读时合并，**零迁移**

### 4.1 表结构

```sql
CREATE TABLE message_parts (
  message_id TEXT NOT NULL,
  seq        INTEGER NOT NULL,   -- 段序号，追加序
  kind       TEXT NOT NULL,      -- 'thinking' | 'text' | 'tool_use'
  payload    TEXT NOT NULL,      -- 该段 JSON
  created_at INTEGER NOT NULL,
  PRIMARY KEY (message_id, seq)
) WITHOUT ROWID;
```

加 `ON DELETE CASCADE` 挂在 `messages` 上，或沿用现有删除路径手工清 —— 需确认现有 `db/messages-clear` / `-delete` 的清理方式再定。

### 4.2 新老共存判据（一条消息内部不混）

| 情况 | 写入 | 读取 |
|---|---|---|
| `messages.meta` 里**已有** `toolCalls` / `segments` | 继续整行 upsert（老格式原样写回） | 与老代码完全一致 |
| 新消息（meta 里没有块结构） | 只往 `message_parts` 追加，主表 meta 留 `{thinking?}` 或 `null` | 主表 + `parts` 批量拼 |

**同一个会话里前半段老、后半段新没问题** —— 按 `message_id` 分开判断，互不影响。**不写迁移脚本、不加版本号列、不动任何历史行。**

### 4.3 读取侧

首屏那条查询（`turns: 5`）里追加一次：

```sql
SELECT message_id, seq, kind, payload FROM message_parts
WHERE message_id IN (…窗口内 28 个 id…)
ORDER BY message_id, seq
```

窗口大小由 `turns` 锁定，量固定。拼装发生在 `deserializeMessage` 之前，对外形状仍是 `{ toolCalls, segments, thinking }`，**渲染层零改动**。

### 4.4 状态变化怎么处理

工具状态会变（`running` → `completed`）。两个选项：

| 选项 | 做法 | 取舍 |
|---|---|---|
| **A（推荐）** | `seq` 按 toolCallId 占位固定，状态更新走 `INSERT OR REPLACE` 单行 | 单次仍是 2 KB 级；顺序稳定 |
| B | 每次状态变化追加新行，读时按 toolCallId 取最后一行 | 行数翻倍，读时要去重 |

## 五、代价与风险

1. **改的是数据模型，不是一处调用。** 要跟着动：`db/messages-list` / `-list-page` / `-list-by-turns` / `-list-locator` / `-search-content`、`DbMessageCompactTools`（压缩读全量 segments）、`deserializeMessage`、worker 侧重建上下文的读法。
2. **跨语言同步面扩大。** C# 写、TS 读、C# 再读（压缩/上下文重建）三处对同一份结构的理解必须一致 —— 这是本项目栽过的坑（S-276 四处轮次判据各写各的）。
3. **`-list-locator` 本来就是轻量的**，别顺手把它也改成 join，否则右侧 rail 会变慢。
4. **拆完收益依赖 S-284 先落地。** 在 14.5 MB 的基座上拆，只是把 2.07 GB 摊薄；在 1.26 MB 的基座上拆，才是干净的架构演进。

## 六、验收方向（实施时细化）

- 新消息的 `messages.meta` 不再含 `toolCalls` / `segments`；
- 老消息打开后行为**逐字节不变**（同一条消息拆前拆后渲染结果一致）；
- 148 次工具调用的消息，单次落库传输量 ≤ 4 KB；
- 首屏 `responseBytes` 不再随工具调用数线性增长。

## 七、刻意不做

| 不做 | 为什么 |
|---|---|
| **不迁移历史行** | 老大 14:29 明确「最好能兼容老数据」。读时合并已经满足，迁移脚本写错就毁库。 |
| **不改 `-list-locator`** | 它本来就不取 meta，动它只会拖慢右侧 rail。 |
| **不与 S-284 合并成一刀** | 一个是写入侧两行改动，一个是数据模型改造，风险量级差太远。 |
| **不做 JSON 分段拼接缓存** | 曾评估在 `serializeMessage` 里缓存 `stringify` 前缀，单次能从 14 MB 降到 2 KB。但拼出来的 JSON 与 `JSON.stringify` 有一字节差异就是脏数据，而这条路上已经有过「两处口径必须同步」的事故。拆表是更正的解法。 |
