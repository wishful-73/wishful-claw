# S-224：聊天图片落盘存储，DB 只存路径

## 1. 原话 / 来源

> 2026-10-24 09:19 老大：

> 我们的图片是直接入库的么，我以为是存储的地址呢

> 2026-10-24 09:24 老大：

> 嗯 新登记一条，我们可以把图片复制一份到我们的数据目录下，根据日期创建文件夹，参考QQ 微信这些聊天存储图片文件的方式

性质：**存储结构调整**（写入侧 + 入库形状），读取侧链路已现成。存量数据**不迁移**，见 §4.6。

## 2. 目标

一句话：**图片字节落盘到全局数据目录、按日期分桶，`messages` 表只存路径，不再存 base64。**

## 3. 现状（2026-10-24 实查）

### 3.1 用户上传：base64 原文直入 `messages.meta`

| 步骤 | 位置 | 行为 |
|---|---|---|
| 1. 读文件 | `renderer/src/lib/image-attachments.ts:247-257` | `FileReader.readAsDataURL()` → dataUrl，上限 20 MB（`:29`） |
| 2. 转块 | `image-attachments.ts:82-94` | `dataUrl.split(',', 2)[1]` 取**纯 base64**，`source.type = 'base64'` |
| 3. 拼消息 | `hooks/use-chat-actions.ts:214-237` | `[{type:'text'}, ...imageBlocks]` |
| 4. 落库 | `stores/chat-store/db-helpers.ts:134` | `if (msg.content) meta.content = msg.content` —— 整个块数组 JSON 化进 **`messages.meta`**（TEXT 列） |

`messages.content` 列只放文本（`db-helpers.ts:141`），所以查库时 `content` 列看着是干净的，图全在 `meta` 的 JSON 里。

### 3.2 工具产物：路径 + base64 双写

| 来源 | base64 | filePath | 落盘位置 |
|---|---|---|---|
| Read 读图 | ✅ `FileReadTool.cs:334-336` | ✅ `:339` | 读的就是原文件，不复制 |
| 浏览器截图 | ✅ | ✅ | `resolveGeneratedImagesDir()` |
| 桌面截图 | ✅ | ✅ | 同上（`window-capture-handler.ts:75-79`） |
| AI 生成图 | ✅ | ✅ | 同上 |
| 用户上传 | ✅ | ❌ | **不落盘** |
| 渠道入站 | ✅ | ❌ | **不落盘** |

工具产物是先落盘（`main/lib/image-persist.ts:65-80`）拿 `filePath`，再把同一份字节以 base64 回给前端；`image:persist-generated` 的返回值里两者都给（`misc-handlers.ts:327-331`）。所以工具产物的 DB 行里**两个字段各存一份 base64**（`meta.content` 与 `meta.segments` 都会序列化）。

### 3.3 渠道入站：与用户上传同一条线

QQ / 飞书 / 微信都是「解析层只带地址 → 即时下载成 base64 → 拼 `[text, image…]`」：

- `channels/providers/qq/download-media.ts:157`
- `channels/providers/feishu/feishu-service.ts:201`
- `channels/providers/weixin/weixin-service.ts:405`
- 汇合点 `hooks/use-channel-auto-reply.ts:259` `buildInboundUserContent(content, task.images)`

S-211 的设计就是把渠道图做成与聊天窗**同构**，好处是链路统一，代价是同一条路一起缺落盘。

### 3.4 S-145 承诺的「DB 侧剥离 base64」没有落地

`FileReadTool.cs:337-338` 的注释写着：

> 路径必须带：渲染端按它重新 hydrate 出图像（visual-context），DB 侧也按它把 base64 换成 `[image: <path> …]` 占位（S-145 §3.3）。

全仓 grep `.ts` + `.cs`，`[image:` 只出现在这一句注释里，**没有任何实现代码**。这条要在本需求里要么兑现，要么把注释改成事实。

### 3.5 读取侧两条路都现成，缺口只在写入侧

| 用途 | 位置 | 现状 |
|---|---|---|
| 渲染显示 | `use-image-display-src.ts:110-113` | `filePath` 有值 ⇒ 走 `oc-media` 协议流式读，不占 IPC 大包 |
| 下载/复制 | `ImagePreview.tsx:174-191` | 优先读 `filePath`，文件没了才回退 dataUrl |
| 历史重放补图 | `lib/agent/visual-context.ts:269-286` | 有 `filePath` 就 `FS_READ_FILE_BINARY` 读盘，读不到才降级为路径文本 |
| 编辑重发 | `image-attachments.ts:60-80` | 从块还原成 `ImageAttachment`，只认 base64 / url —— **`filePath` 这一支要补** |

⇒ 落盘之后读取侧基本不用动，只有「编辑历史消息重新发送」需要能从 `filePath` 还原出图。

## 4. 方案

### 4.1 落盘位置：全局数据目录，按月分桶

```
{dataRoot}/images/{yyyy-MM}/{sha256 前 16 位}.{ext}
例：~/.wishful-claw/images/2026-10/9f2c1a7b3e5d4c60.png
```

- **单层月目录**（`2026-10`），不再往下分层。一天一个目录一年 365 个，目录碎；月级一个目录几百到几千张，NTFS 无压力，跨天找图也方便
- `dataRoot` 即 `resolveDataDir()` —— dev 实例自动落 `~/.wishful-claw-dev/`，与生产天然隔离（S-223 定的机制，不额外做隔离）
- **不放项目工作区**：否则用户 `git status` 里会冒出图片文件；QQ / 微信也是客户端私有存储区，不散落在聊天对象目录
- 不复用 `image/`（工具产物的 `GENERATED_IMAGES_SUBDIR`）：那个目录按项目/全局三分，语义是「工具产出物」；聊天图片是「会话资产」，且要跨会话稳定可读

### 4.2 文件命名：内容哈希

- 文件名 = 内容 sha256 前 16 位 + 扩展名 ⇒ **同一张图重复发送天然去重**，也避免「编辑重发」堆多份
- 月目录按写入时刻的本地时间取 `yyyy-MM`
- 扩展名从 mediaType 推断，复用 `guessExtensionFromMimeType()`（`image-persist.ts:23-36`），不重复造

### 4.3 入库形状：去掉 `data`，补 `filePath`

`ImageBlock.source` 已有 `filePath` 字段（`renderer/src/lib/api/types.ts:108`），不需要扩契约：

```jsonc
// 现在
{ "type": "image", "source": { "type": "base64", "mediaType": "image/png", "data": "iVBORw0..." } }

// 目标
{ "type": "image", "source": { "type": "base64", "mediaType": "image/png", "filePath": "C:\\Users\\…\\images\\2026\\10\\24\\9f2c1a7b3e5d4c60.png" } }
```

`source.type` 保持 `'base64'`：发给模型前本来就要读回字节拼成真 base64，改成 `'url'` 会让三处 provider 写入器（OpenAI / Anthropic / Responses）走错分支。**`type` 是给模型看的，`filePath` 是给我们自己存和读的**，两者并存不冲突。

### 4.4 写盘时机与责任方

| 场景 | 入口 | 动作 |
|---|---|---|
| 用户上传 | 发送消息前，`use-chat-actions.ts:214` 之后 | 调新的 `image:persist-chat`（主进程算哈希、写盘、返回 filePath），拿到路径再拼块 |
| 渠道入站 | `use-channel-auto-reply.ts:259` 之前 | 同上，同一入口 |
| 工具产物 | 不变（已经落盘） | 只在**落库序列化时**剥掉 `source.data`，保留 `filePath` |

落库剥离集中在 `db-helpers.ts` 的 `serializeMessage()`（`:118-147`）：递归走一遍 content / segments / toolCalls，把 image 块的 `source.data` 删掉、`filePath` 留着。这样四个来源一起收口，不用逐个来源改。

### 4.5 失败降级：永不阻断发送

写盘失败（磁盘满 / 权限 / 超长路径）时：

1. 主进程返回 `{ error }`，不抛
2. 渲染端退回旧的 base64 内联行为，照常发送
3. 渲染端日志记一条 warning

宁可留一份历史包袱，也不能让用户发不出消息。**降级路径必须留着**，不做「写盘失败就拦截」。

### 4.6 存量数据：不迁移

- 已在 `messages.meta` 里的 base64 保持原样，渲染端两种形状都支持（`use-image-display-src.ts` 三支分支已覆盖）
- 不写一次性迁移脚本：要遍历所有 `meta`、逐块解码落盘、回写 JSON，中途失败会留下半迁移状态，风险远大于收益（老图仍能正常显示，只是继续占库）
- 若后续要瘦身，另立需求（可做「按需回填」：老图第一次被重放时顺手落盘并回写）

## 5. 范围外

- 存量 base64 迁移 / 按需回填（另立）
- 视频、音频、文档附件 —— 本次只做图片，其它类型目前也不落盘，一并另立
- 图片压缩 / 转码（原样存字节，不做有损处理）
- 缩略图生成（列表长图卡顿另议）
- `THIRD_PARTY_NOTICES` 与参考实现出处登记
- 历史 `[image: …]` 占位符方案 —— 本需求用 `filePath` 直接落字段，不引入占位字符串；`FileReadTool.cs:337-338` 那句注释要改写成实际行为

## 6. 风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | 图片被外部删除（用户清缓存、杀软误删）⇒ 历史消息图裂 | 渲染端已有「文件读不到回退 dataUrl」与「都没有就显示占位」两支；落盘后 dataUrl 没了 ⇒ 显示明确的「图片已失效」占位，不是空白 |
| 2 | 剥离 `source.data` 时漏掉 `meta.segments` 里的副本 | 剥离逻辑写在 `serializeMessage()` 单点，递归覆盖 content / segments / toolCalls；门禁加断言：序列化产物 JSON 内不含 `"data":"iVBOR` 之类的 base64 头 |
| 3 | 同一消息内多图并发写盘 | 主进程写盘加内容哈希锁（同哈希并发只写一份，与 S-219 路径锁同款思路） |
| 4 | 哈希碰撞 | sha256 前 16 位 = 64 bit，且先查目标文件存在才复用；碰撞概率忽略不计 |
| 5 | `filePath` 泄漏用户目录结构到模型上下文 | 发给模型前读回字节并**不带 filePath**（现有 `OpenAIChatRequestBuilder.cs:279` 只取 base64 部分，`filePath` 不过我捏造的字段名不入 payload —— 阶段一需实测确认三处写入器都不序列化 `source.filePath`） |
| 6 | SSH 远程项目：`filePath` 在本地、模型在读远端 | 本需求只保证本地可读；SSH 场景的聊天图仍是本地文件，按「本地字节 → base64 → 发模型」照旧成立，不依赖远端 |
| 7 | 打包版与 dev 实例各存一份，用户切实例看不见对方历史图 | 预期行为（S-223 同口径），不特殊处理 |

## 8. 实施记录

### 8.1 阶段一探索的两个额外发现（计划外）

**① `oc-media` 协议只有生成端、没有注册端。** `local-media-url.ts:10` 的注释声称协议注册在
`src/main/local-media-protocol.ts`，但该文件从未存在；全仓 `protocol.handle` /
`registerSchemesAsPrivileged` 均 0 处。此前所有图片块都带内联 base64，`useImageDisplaySrc`
第一支直接命中 data URL，`filePath` 分支从不执行，所以没人发现。**不补协议，剥离后历史图必然全裂**，
已纳入本次实施（步骤 1-2）。

**② `SessionRestoreTools` 从不读 `meta.content`。** `ConvertToWireMessage` 对用户消息只取
`messages.content` 纯文本列，冷启动/切会话后历史图片块本来就不进模型上下文。这是既有行为，
**本需求不修**（另立需求），但它意味着剥离 base64 不会造成「模型看不到历史图」的回归。

### 8.7 阶段五审查与修复（2026-10-26）

独立 subagent 审查结论 **❌1 / ⚠️11 / ℹ️7**，唯一阻断项是**落盘写非原子**：
`writeFileSync` 直写最终路径 + `existsSync` 短路，一旦写到一半被打断就留下 0 字节文件，
下次同图重发被短路固化，而落库那边已按 `filePath` 剥掉 base64 ⇒ **图永久损坏、不可自愈**。

| 类别 | 处置 |
|---|---|
| ❌1 非原子写 | 临时文件 + `rename`；短路条件改 `stat().isFile() && size > 0`；空 buffer 直接报错；顺手全改 `fs.promises` |
| ⚠️1 往返一致性没测住 | 测试改为直接 `import { filePathToMediaUrl }`，删掉本地复刻的编码模板 |
| ⚠️2 协议路径无形态约束 | 加 `isAbsolute` / 拒 `..` 段 / 拒两种 UNC 前缀，补 6 条断言 |
| ⚠️3 兜底读盘无上限 | 超 64 MB 返回 413 |
| ⚠️4 两份 hydrate 语义 | 抽模块级 `readBinaryFileViaIpc` |
| ⚠️5 编辑重发重传 base64 | 已有 `filePath` 直接短路 |
| ⚠️6 主进程同步 IO | 改 `fs.promises` |
| ⚠️7 同一 base64 解两遍 | 新增 `chatImageFileNameFromBuffer`，解一次既算哈希又写盘 |
| ⚠️8 自反断言 | 换成「带换行非规范 base64 ⇒ 文本不同字节相同」真用例 |
