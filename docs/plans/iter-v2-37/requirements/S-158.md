## 一、它是什么

渠道**「按工具逐个开关」**的查询接口 —— 设计意图是让用户把某个渠道下的个别工具（如微信的「发送图片」「发送文件」）单独关掉。

存储落在 `ChannelInstance.tools?: Record<string, boolean>`，注释原话「Per-tool enablement flags (missing = default enabled)」。

## 二、为什么判定为死配置（2026-09-29 实证）

链路三段，只有中间一段在位：

| 段 | 位置 | 状态 |
|---|---|---|
| 配置方（用户勾选） | 渲染端 | ❌ **零引用** —— `src/renderer` 搜 `toolEnabled` / `tool-enabled` 无命中 |
| 存储 + 查询 | 主进程（见「三、删除面」） | ✅ 三层壳齐全 |
| 调用方（执行前询问） | C# 运行时 | ❌ **零发起** —— `src/runtime` 搜 `tool-enabled` / `ToolEnabled` 无命中 |

⇒ `tools` 表恒为空 ⇒ `isChannelPluginToolEnabled` **恒返回 `true`** ⇒ 开关从不生效。

**旁证**：同一批死配置里的 `autoReply` / `streamingReply` / 四个 `allow*` 已在 iter-29 清理（`plugin-panel-global.tsx` 顶部注释留了说明），本条是漏网的一条。

**取舍理由**：渠道工具本来就少（微信 `send-image` / `send-file` 两个、其余渠道共用 `COMMON_PLUGIN_TOOLS`），不存在「用户要关掉个别工具」的真实诉求。留着只会让人以为它管着什么 —— 与 iter-29 删那批字段同一条理由。

### 三条边界提醒

- ⚠️ **别误删**：`channel-types.ts:27-28` 的 `ChannelDescriptor.tools?: string[]`（注释「Supported tool names for this plugin provider」）是**另一个字段** —— provider 支持的工具名清单，被 `channel-descriptors.ts` 大量使用。**保留。**
- ⚠️ **C# 侧无对应物**：`src/runtime` 无 `ToolEnabled` / `tools` 强类型字段（渠道配置走 `ChannelConfigStore` 的 JSON 透传）⇒ 本刀**纯 TS 侧**。
- ⚠️ **存量数据无需迁移**：老配置 JSON 里若已存在 `tools` 键，删字段后不再被读取，属无害残留（与 iter-29 删那批字段同一处理口径）。
