## 一、诉求

对话里生成的图片是**产物**，但它当前没有一个顺手的出口：用户想拿走一张图，只能先点开预览浮层再复制 / 下载。

参考项目 v2.4.0 的原话，症状与我们高度重合：

> 生成的图是产物，而它此前**没有任何出口** …… 用户要把一张图贴进别的应用，唯一的做法是求 Agent 调一次 `SaveImage` 落盘再自己去找，而他手上明明已经有一张图。

## 二、我们的现状（2026-09-29 实读）

### 2.1 出口能力**已经存在**，但只挂在预览浮层

`src/renderer/src/components/chat/ImagePreview.tsx`：

| 位置 | 内容 |
|---|---|
| `:249` | `handleCopy()` → 写剪贴板，带 `copied` 状态与成功 / 失败 toast |
| `:195` | `handleDownload()` → 下载；分三条路（`downloadLocalFileCopy` `:86` / `saveImageBase64` `:104` / `window.api.downloadImage` `:219`） |
| `:349` `:360` | UI 上两颗按钮：Copy（`Copy` / `Check` 图标切换）+ Download |

⇒ **能力不缺，缺的是「在卡片上就地可达」。**

### 2.2 生图卡片上没有任何出口

`src/renderer/src/components/chat/ImagePluginToolCard.tsx`（388 行）的动作面只有两项：

- `:195-231` 一个包住图片的 `<button>`（点击放大 / 进预览）
- `:286` 重试按钮 `<Button onClick={handleRetry}>`（失败重试）

**没有复制 / 下载 / 保存。** 用户必须先点图进预览，才能拿到出口。

### 2.3 没有「把对话里的图写进工作区」的能力

- 主进程全仓搜 `saveImage` / `save-image` ⇒ **零命中**
- 现有的 `window.api.downloadImage`（`ImagePreview.tsx:219`）落点是**用户手选的路径**，不是工作区
- ⇒ agent 说「把这张图存到 `assets/logo.png`」时**办不到**（`Write` 只写文本，把 base64 当文本写进去得到的是一个打不开的文件）

### 2.4 两条附带经验 —— 一条我们已符合，一条没有

| 经验（NextCoWork） | 我们的现状 | 结论 |
|---|---|---|
| 剪贴板写图**一律转 PNG**（webp 在 macOS 粘贴板上没有对应类型，用户会「粘出来是空的」） | `src/renderer/src/lib/utils/image-clipboard.ts:8` 注释即写明「系统剪贴板只认位图，所以经由 data URL / SVG 进来的内容都先转成 PNG 再写」；走 `CLIPBOARD_WRITE_IMAGE` 通道 → 主进程 `clipboard-enhancer.ts` | ✅ **已符合，无需改** |
| 存盘扩展名按**字节魔数**判，不按建议名 | `ImagePreview.tsx:38` `getDownloadExtension(imageSrc)` —— 按 **src 字符串**判 | ⚠️ **未符合** |

`getDownloadExtension` 按 src 判的后果与它们 v2.4.0 记的一致：**内容没错、名字撒谎**；部分看图工具按扩展名挑解码器，表现是「存下来的图打不开」，而没人会想到是文件名的问题。

## 三、修复方向（草案，待裁定）

| # | 方案 | 说明 |
|---|---|---|
| A | **卡片就地出口**：把 `ImagePreview` 的复制 / 下载抽成共用，生图卡片上每张图浮出一排动作 | 抄它们的做法：悬停**或键盘焦点**进来才显形（用 `group-focus-within`，不用 `group-focus-visible` —— 后者匹配的是容器自己获得焦点，而容器不可聚焦，键盘用户 Tab 到按钮时会停在看不见的状态上） |
| B | **`SaveImage` 工具**：新增 agent 工具，把对话里的图写进工作区 | 复用现有 `resolveImageBase64` 与通道校验；默认**不覆盖**，目标已存在时须显式 `overwrite: true`；不转格式、不进 diff / 撤销记录 |
| C | **扩展名改按字节魔数判** | 认不出来落 `.bin`，**不猜成 `.png`** —— 猜错的那个会被当成 PNG 去解，失败发生在用户双击它的时候 |

**我的倾向是 A + B + C 一起做**：A 解决「顺手拿走」，B 补上「agent 自己能落盘」，C 是 A / B 共同的正确性底座 —— 两条路都要落到磁盘上，扩展名判错在哪条路上都出错。

## 四、实施注意（从参考项目抄来的坑）

1. **按钮与图片必须是兄弟，不能是父子** —— 图片本身包在 `<button>` 里（键盘要能 Tab 到并回车放大），而按钮套按钮是**非法结构**：浏览器会把内层那个**弹到图片外面**，表现为「点复制却打开了灯箱」。
2. **取消不闪任何状态** —— 用户在系统保存对话框里按取消，不能标「已保存」或「失败」（给取消也标成功，是在说谎）。
3. **复制与下载的提示文案要能分辨对象** —— 同一张卡片里「已复制」若出现两次（一段文字 / 一张图），用户要能一眼分出是哪一个。

## 五、验证要求（实施时）

1. 断言精确比**送出去的载荷**，而不是「按钮在不在」：两颗按钮的文案与图标在两种状态下长得像，而**送错的那张图**（把第 1 张的字节送给第 2 张那颗按钮）在界面上看不出任何异常。
2. `npm run typecheck` 0 错误；`npm test` 全绿（基线 61/61）。
3. 手工：生成多张图 ⇒ 逐张复制 / 下载 ⇒ 粘出来 / 落盘内容与所选一致；`SaveImage` 目标已存在时**默认拒绝**，显式 `overwrite` 才覆盖。
