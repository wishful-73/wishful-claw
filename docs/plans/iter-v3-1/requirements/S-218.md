## 2. 目标

WorkBuddy（腾讯的 AI 工作 agent）**本身有可用的大模型**，但客户端不是每个人日常都愿意开。做法：把**用户自己 WorkBuddy 账号的模型**接进我们的 provider 体系，作为一个**可选服务商**。

**不是**「免费模型」，**不是**「白嫖」 —— 用的是**用户已有的 WorkBuddy 套餐额度**。用户没套餐就用不了（见 §3.3 `14018`）。

### 2.1 形态裁定：A 形态（2026-10-22 老大定）

| 形态 | 做法 | 结论 |
|---|---|---|
| **A** | .NET 侧新写 provider 实现 `ICompletionProvider`，代码内完成 OAuth、请求头签署、出站修补、SSE 解码 | **选这个** |
| B | 照 Astra-Gate 分层起本地 HTTP，暴露 OpenAI 兼容端点 | 否 |

A 形态的收益：不起服务、不占端口、无鉴权面、无进程生命周期问题。代价：**只能我们软件自己用**，外部客户端（Codex CLI / Claude Code）接不进来。老大要的正是 A。

### 3.2 鉴权：浏览器 OAuth 轮询

```
1. POST /v2/plugin/auth/state?platform=workbuddy
   头：X-No-Authorization / X-No-User-Id / X-No-Enterprise-Id / X-No-Department-Info = "true"
   → { state, authUrl }

2. authUrl 追加 ?version=2.0.0&loginSessionId=<32 位 hex>
   （version 是工作台登录页版本号，硬编码 2.0.0；loginSessionId 为 randomBytes(16).toString("hex")）

3. 用户在浏览器登录腾讯账号

4. 轮询 GET /v2/plugin/auth/token?state=<state>     重试 code 11217
   → { accessToken, refreshToken, expires, domain, ... }

5. 轮询 GET /v2/plugin/login/account?state=<state>   重试 code 12151
   头：Authorization: Bearer <access>、X-Domain
   → { uid, nickname, phoneNumber, type, enterpriseId }

6. 企业账号：GET /v2/plugin/accounts 挑出 enterpriseId
```

轮询 1 s / 次，超时 5 min。token 到期前 **60 s** 刷新。

**桌面登录态路线在本机不可用**：WorkBuddy **5.6+** 把 token 落成 `{$wbEncrypted: 1, envelope}`，只有 App 自己能解。本机 `last-launch.json` 版本 **5.8.4** ⇒ 必须让用户在浏览器登录一次。产品里要有独立的「连接 WorkBuddy 账号」入口。

### 3.3.1 四个会话 id 的生成规则（实读 `src/request.mjs:25-140`）

id 一律 **32 位 hex**。每进程生成一个随机 `SALT = randomBytes(16).toString("hex")`，再由它派生：

```
idFor(kind, key) = sha256(`${SALT}|${kind}|${key}`).digest("hex").slice(0, 32)
```

| 头 | 取值 |
|---|---|
| `X-Conversation-ID` | `idFor("conversation", convKey)`。`convKey` = `session:<会话 id>`（有）；否则 `first:<首条用户消息签名>`（所有后续轮次都重复它）；**两者都没有 ⇒ 该头不发** |
| `X-Conversation-Request-ID` | 有 `turnKey` ⇒ `idFor("turn", "<convKey>\|<turnKey>")`；否则新 `hex()` |
| `X-Conversation-Message-ID` | 新 `hex()` |
| `X-Request-ID` | 与 `X-Conversation-Message-ID` **同一个值** |

- `turnKey` = 从消息列表**末尾向前**找第一条「`role: user` 且尚未被回答」的消息，得 `u<索引>:<签名>`；找不到则空串。
- **签名**（`signatureOf`）= 文本部分原样拼接 + 每个非文本部分（图片、文件、工具结果之外的）追加 `[<type>:<sha256(JSON).slice(0,8)>]`。
- **不得编造 `X-Conversation-ID`** —— 参考实现的原话是「编造的会话 id 会把一个会话拆成多个」（体现在计费的用量明细里）。

### 3.4 出站修补（不做就 400）

WorkBuddy 不吃标准 OpenAI 拼写：

- `max_completion_tokens` → `max_tokens`
- `developer` message → `system`
- `tool_choice` 对象 → 字符串形式
- 无 `system` 首条时补一条 WorkBuddy 默认 system

**工具 schema 四种畸形修正**（不修报 400 `11133`）：

1. `parameters` 无 `type` / 为空 / 根部是 `anyOf` `oneOf` `allOf` ⇒ 合成 `object`，合并联合体字段
2. `pattern` 里的 `\0` → `\u0000`
3. tuple 的 `items`（数组）⇒ 收成任一兼容的单一 schema
4. 工具名含 `[A-Za-z0-9_-]` 之外的字符（`.` `:` `/` 空格 CJK）⇒ 发出去时替换为 `_`，模型回来的调用名**还原**

### 3.8 签到与额度

**签到**（两个 build 同路径）

| 用途 | 端点 | 返回 |
|---|---|---|
| 签到 | `POST /billing/meter/daily-checkin` | 首次 HTTP 200 `{code: 0, data: {credit, streak_days, is_streak_day}}` |
| 连签状态 | `POST /billing/meter/checkin-activity-status` | `{code: 0, data: {today_credit, streak_days}}` |

- **当天重复签到返回 HTTP 400 + `code 10001`** —— 判定看 `code`，**不看 HTTP status**（400 承载的是"已签"这个正常语义）。
- 参考实现带验证码分支：错误文案命中 `/captcha|验证码|人机|滑块/i` 时视为需要人工。**说明该端点有防自动化措施**，撞上即中止，不得重试。
- 签到走 `postMeter`，那套头**不含** `X-Agent-Type` —— 国际版签到是否需要该头**未验证**。

**额度**

| 账号类型 | 端点 | 读法 |
|---|---|---|
| 个人 | `/billing/meter/get-user-resource-summary` | 遍历 `Packages[]`，累加 `CycleTotalCapacity` / `CycleUsedCapacity`；`IsPaidUser` 判 Pro / Free |
| 企业 | `/billing/meter/get-enterprise-user-usage` | `limitNum` / `credit` / `cycleStartTime` / `cycleResetTime`（UTC+8）。企业账号的 resource summary **不列任何 package**，只能走这条 |

**配额数值的坑**：`CycleTotalCapacity` 等字段**有时是字符串 `"438.88"`，有时是数字**，参考实现对解析失败直接抛错。我们按「字符串或数字都吃」处理。

**套餐明细（可选，非本需求核心）**：`get-user-resource-paid-packages` / `get-user-resource-free-packages` 需要传 `PackageCodes`（形如 `TCACA_code_001_PqouKr6QWV`，硬编码 20 个），缺了报 `10001 "PackageCodes required"`。**这些 code 是参考实现从客户端里抄的，随时可能变** ⇒ 不纳入本期。

## 4. 根因 / 技术判断

不是缺陷，是新能力。技术判断如下：

**A 形态没有任何加密签名环节。**对比 Qoder（DPAPI 解密 + AES-256-GCM + COSY 签名 + 自定义 base64），这里只有 Bearer token + 十余个固定头 + 纯 JSON/字符串修补。**工作量约为 Qoder 的一半到三分之一。**

可直接挂现有 provider 层：`OpenAIChatProvider` / `ProviderCompletionService` / `ProviderRetryPolicy` / `ProviderStore`，无需自建传输层。`ProviderStore` 落 `~/.wishful-claw/ai-provider/`，支持自定义 `baseUrl` + key + 模型清单 —— 新增 provider 走同一套配置面。

**真正的成本不在代码，在风险口径**（§5）。

## 5. 风险与产品口径

老大 2026-10-22 09:12 定：「这个可以提醒风险呀」。落成三层，缺一层不算尽责：

### 5.1 接入前

「连接 WorkBuddy 账号」面板上**直接写死**，不得折叠隐藏：

- 这是**非官方接入**，用的是你自己账号的额度
- 腾讯有权判定异常并**限制账号**
- 需要**勾选确认**才能继续

### 5.2 服务商标识

服务商卡片 / 列表里带标记（如 `WorkBuddy` 名称后加「第三方」角标），与官方 API Key 服务商**视觉分开**。用户看到「免费」时必须同时看到「有风险」。

> 落点按 2026-10-22 09:23 纠正 —— 标记跟着**服务商**走，不散到模型上。用户添加这个服务商时看一次，比在模型列表里反复看到更合理。

### 5.3 出错时

| 情况 | 显示 |
|---|---|
| `11140` | 「你的 WorkBuddy 账号被腾讯限制了（判定为非正常调用），需要到 WorkBuddy App 内申诉后解除」 |
| `14018` | 「你的 WorkBuddy 账号没有可用的套餐额度。即使标注免费的模型，也要求账号有有效套餐」 |
| `unapproved channel` | 「WorkBuddy 拒绝了这个对话内容（判定为非授权客户端）。换一个会话或调整提示词后重试」 |

**不得显示成笼统的「请求失败」** —— 否则用户以为是我们的 bug，反复重试只会加重风控。

### 5.4 自保设计

**默认不自动路由到该服务商。**用户显式选择了才用。封号风险由用户自己承担选择，而不是我们悄悄用。

### 5.5 签到策略（2026-10-22 09:36 老大定）

> 原话：「定时 一天只点一次，失败了就用户手动点击 或者去软件那边点击」

三条规则：

| # | 规则 |
|---|---|
| 1 | **自动签到，一天只尝试一次**（按北京时间日期判重，本地记 `lastCheckinDate`） |
| 2 | **失败不重试**。不做「N 分钟后重试」—— 参考实现的 30 min 重试**明确不采用**，它是最像机器人的那段 |
| 3 | 失败后 **UI 显示原因 + 两个手动出口**：① 我们的「立即签到」按钮（用户主动点，不计入自动额度）②「去 WorkBuddy App 签到」 |

**失败原因要分开显示**（否则用户不知道该怎么办）：

| 命中 | 显示 |
|---|---|
| `/captcha\|验证码\|人机\|滑块/i` | 「WorkBuddy 要求人机验证，请打开 WorkBuddy App 签到」 |
| `14018` / 额度相关 | 「账号套餐异常，无法签到」 |
| `11140` / 账号限制 | 「账号已被限制，需到 WorkBuddy App 申诉」 |
| 网络 / 超时 | 「网络异常，可手动重试」 |
| `10001` | 不是失败 —— 显示「今日已签到 · 连签 N 天」 |

**定时时刻（已定，2026-10-22 16:09 老大口径）**：**每天北京时间 8:00 之后触发，再随机等几分钟发送**。

> 原话：「8点以后触发签到 随机个几分钟发送签到请求」

| 情形 | 行为 |
|---|---|
| app 在 8:00 前就开着 | 到 8:00 后随机等几分钟再发 |
| app 在 8:00 后才启动 | 启动后随机等几分钟再发 |
| 当天已签 | 直接跳过，不重复打接口 |
| 随机等待量 | **1~30 分钟内随机**（范围待老大确认，见 §8） |
| 随机后越过 24:00 | 顺延次日 8:00 后重新判定（边界兜底） |

- 判定与等待都按**固定 UTC+8** 算，不读本地时区。
- **每分钟 tick 检查** —— 本地行为，服务端看不见，但能自愈睡眠唤醒与时钟回拨。
- **失败不重试**，退位给用户手动（上行规则 2/3）。
- **设置里可关闭**。

**唯一的暴露面是签到请求发出的那一刻。** 所以随机量必须散开 —— 固定分钟数等于把窄窗口从 90 分钟压成 1 分钟，比原来更糟。

**方案判定链**（留档，免得后人把旧路捡回来）：

| 方案 | 结论 |
|---|---|
| **8:00 后随机几分钟** | **采用**（16:09 老大定） |
| ~~`00:30 + hash(日期) % 90`~~ | 撤销 —— 30 天挤同一窄窗口，规律即指纹 |
| ~~日期字符串当种子~~ | 撤销 —— 确定性算法，同一日期永远同一点，可被反推 |
| ~~跟随真实对话流量~~ | 不采用 —— 老大 16:09 给了更简单口径，不叠复杂度 |

## 6. 代价与取舍

**（规划态，实施后回填）**

- **封号风险不可兜底。**账号是用户的，被封我们赔不了。只能靠 §5 三层提示 + 不自动路由来降低"用户不知情"的概率。
- **自动签到也是风控暴露面。**即便一天一次不重试，它仍是「无对话内容的定时请求」，比正常聊天更容易被看出不是人。所以它必须默认随服务商连接启用、可在设置里关掉 —— **不做成不可关的后台行为**。
- **必须手动登录一次。**桌面登录态在 5.6+ 已加密不可读，「装好就能用」在这条服务商上不成立。
- **无套餐即不可用。**`14018` 决定了适用人群是「已有 WorkBuddy 套餐的用户」，不是所有人。
- **接口全部未公开。**全部端点无文档，随时可能变。失败态要做清楚，而不是硬猜。
- **双版共用一套代码，模型表与图片能力要分开**：国际版 GLM 系实际丢图（配置写支持但服务端过滤），须按 `^glm-` 标纯文本。

## 7. 刻意不做

**（规划态，实施后回填）**

- **不做签到失败重试。**一天一次，失败即退位给用户手动（§5.5）。
- **不做成长任务自动化**（社区那批项目做的）。签到接口本身参考实现就标注「未对真账号验证」，成长任务更是纯推测，不能当能力宣传。
- **不做套餐明细列表**（`get-user-resource-*-packages`）。要传 20 个硬编码 `PackageCodes`，那是从客户端抄的、随时会变。只显示汇总额度，不拆到每个包。
- **不读桌面登录态。**5.6+ 加密，解不了；强行做等于逆向加密 envelope，成本与风险都不值。
- **不起本地 HTTP 端点（B 形态）。**老大已定 A。
- **不做多账号池 / 会话粘性 / 熔断冷却。**那是「刷额度」的形态，与「复用用户自己的额度」定位不符。
- **不碰 Anthropic 旁路**（`/v1/messages`）。只有两个模型可用，主线已覆盖，无收益。
