# S-204：「清空会话」名不副实 —— 只清内存不删库，切走再切回消息与上下文全回来；并补浮窗入口

> 状态：**已实施，待收尾裁定**（2026-10-16 实施完成；`npm run typecheck` 0 错 / `npm test` 72/72；真机验收并入迭代阶段六）。
> 类型：**bug**（功能不生效）+ **体验优化**（补入口）。
> 归属：**iter-v2-40**。
> 来源：**老大 2026-10-15 08:20 登记** —— 「我需要在右侧浮窗 重置用量下也增加这个清空会话，并且完善这个清空会话，它就不只是重置用量了，它需要删掉当前会话所有的消息，因为当前存在一个bug 点击清空会话再来回切换会话，历史会话和上下文又回来了」。
> 轨道：**软件侧**（渲染层 store + 浮窗 UI）。

---

## 一、现象

**两个面。**

**① 「清空」当场看着生效，切走再切回就全回来。** 左侧面板会话右键「清空消息」（`workspace-sidebar-items.tsx:246-249`）点下去，当前视图消息确实清空了；但**切到别的会话再切回来**，历史消息原样重现，**上下文也跟着回来**（首次发送时 agent 仍然记得清空前的对话）。

**② 右侧浮窗缺入口。** 浮窗「更多」菜单（`SessionConversationPane.tsx:264-274`）里只有「重命名」+「重置用量统计」，没有清空会话。

## 二、根因

### 2.1 主根因：只清内存，没删库

渲染层的 `clearSessionMessages`（`session-slice.ts:477-507`）只做两件事：

1. **清渲染层内存** —— `messages = []` / `messageCount = 0` / `totalTurns = 0` / `isRuntimeResident = false` 等一组字段；
2. 调 **`agent/clear-session`** → worker 侧 `AgentRuntimeTools.ClearSession`（`AgentRuntimeTools.cs:346-357`）→ 仅 `SessionConversationManager.Remove(sessionId)`，**清的是 worker 内存里的会话上下文**。

**DB 里的 `messages` 行一条都没删。**

⇒ 两个后果，同一个根因：

- **消息回来**：切回时 `setActiveSession` → `loadRecentSessionMessages`（`session-slice.ts:~900`）调 `dbGetMessageCount` 拿到真实条数（非 0），**从 DB 原样拉回**。
- **上下文回来**：`session-slice.ts:966` 注释写明 worker 会话是**懒重建** —— 首次发送时 `agent/run` 从 DB 重建上下文。DB 没删 ⇒ 重建出来的还是清空前的历史。

### 2.2 为什么「切回来必重载」

清空后内存状态是 `isRuntimeResident = false` + `messages.length === 0`。而 `loadRecentSessionMessages` 的两条早退条件是：

```
if (session.isRuntimeResident) return                    // 不成立（已置 false）
if (session.messagesLoaded && session.messages.length > 0) return   // 不成立（length 为 0）
```

**两条都不成立 ⇒ 必然往下走重新加载。** 恰好命中「回来」的路径。

### 2.3 端点早就写好了，只是没接线

| 端点 | 实现 | 行为 | 渲染层调用方 |
|---|---|---|---|
| `db/messages-clear` | `DbMessageToolsMutations.cs:171-191` | 事务内 `DELETE FROM messages` + `DetachForSession`（解压缩快照指针）+ `message_count = 0` | **零调用** |
| `db/session-reset-conversation` | `DbSessionTools.cs:256-292` | 上述全部 + **`DELETE FROM tasks`** + **标题重置为 "New Conversation"** | 仅渠道插件 `/new`（`plugin-command-handlers.ts:231`） |

⇒ `db-helpers.ts:625` 的 `dbClearMessages`（封装的正是 `db/messages-clear`）**全仓无调用方 —— 死代码**。当初实现时漏接了这条线。

## 四、修法

### 4.1 store 补 DB 删除 + 防竞态（`session-slice.ts:477`）

`clearSessionMessages` 增加：

1. **补 DB 删除** —— 调 `dbClearMessages(sessionId)`（`db-helpers.ts:625` 已有，走 `db/messages-clear`）。
2. **in-flight guard** —— 模块级 `const clearingSessions = new Set<string>()`：进入时 `add`，DB 删除落定后 `delete`。
3. **失败不静默** —— worker 返回 `success = false` 时 `console.warn`，对齐 `resetSessionUsageStats:515` 的既有口径（其注释写明「这是用户刚点过的不可逆动作，至少要留下一条线索」）。

### 4.2 竞态 guard 的三个落点

下列三处入口开头各加 `if (clearingSessions.has(sessionId)) return`：

- `loadRecentSessionMessages`（`session-slice.ts:~900`）
- `fetchOlderMessages`（`session-slice.ts:978`）
- `loadMessageWindowAround`（`session-slice.ts:~1000`）

**为什么这样能治**：清空后「已加载就不重载」的早退不成立（见 §2.2）⇒ 必然重载。加 guard 后，**删除在途期间任何回读都被挡掉**，内存保持空态；删除落定后 DB 已干净，后续回读拿到空 —— 两头都对上。

**否决的两个备选方案**：

- **让 `clearSessionMessages` 变 `async`、调用方 `await`** —— 治不了「`await` 期间用户仍能切走」。
- **删除完成后回写内存** —— 用户若在窗口内切回来发了新消息，回写会把**新消息一起清掉**，比原缺陷更糟。

### 4.3 浮窗加入口（`SessionConversationPane.tsx:264-274`）

`DropdownMenuContent` 中「重置用量统计」**下面**加一项「清空会话」，带 `confirm`（destructive 变体）。**两项都保留。**

### 4.4 语言包

`locales/zh/layout.json` + `locales/en/layout.json` 增 `clearSession` / `clearSessionConfirmTitle` / `clearSessionConfirmDesc` 三条。

## 六、验收判据

6. 浮窗「更多」里「重命名 / 重置用量统计 / 清空会话」三项齐全，清空项带二次确认（裁定 2）。
7. 重启应用后消息仍为空（DB 已删，非内存态）。
8. 四道门禁全绿（`typecheck` / `npm test` / `dotnet build sln` / 官网 `build`）。

## 十、代价与取舍（实施后回填）

- **guard 是「挡回读」而非「等删除完成」**：清空是 fire-and-forget（调用方不 await），删除也在途不阻塞 UI —— 用户点完立刻看到消息清空，落库在后台完成。代价是**极短窗口内**若 DB 删除失败，内存与 DB 会不一致（内存空、DB 有），此时 `console.warn` 留痕、下次回读会把 DB 内容拉回。这是「不静默失败 + 不阻塞交互」的折中，与既有的 `resetSessionUsageStats` 同口径。
- **不回写内存**（见 §4.2 否决项）：删除完成后再 set 一次内存是错的 —— 用户若在窗口内切回来发了新消息，回写会把新消息一起清掉。
