# S-351 浏览器截图卡重开会话后只剩原文 JSON（图片块没长回来）

> 状态：✅ **已修复**（2026-11-09 09:3x）—— 新增 `lib/tools/tool-output-revive.ts`，在
> `buildToolCallRenderState` 统一出口归一化 `output`；新增 `tests/tool-output-revive` 17 条断言；
> `npm run typecheck` 三配置 0 错、`npm test -- --ts-only` **95/95**
> 性质：缺陷（显示层数据形态不一致）。中危 —— 图片是这个功能的全部价值。
> 归属：本迭代。

---

## 一、现象

追一条 `BrowserScreenshot` 的卡片，展开后是这一坨原文：

```json
[{"type":"image","source":{"type":"base64","mediaType":"image/png",
  "filePath":"D:\\claw\\wishful-claw\\.wishful-claw\\image\\1794186665198-4f7662f4.png"}},
 {"type":"text","text":"Screenshot captured: 575x1434px - https://example.com/"}]
```

页面里**没有预览图**，只有一个能「提交 JSON」的空卡片。

## 二、根因（一句 `Array.isArray` 拦掉两条路）

库里 `message_parts` 的那一行 `kind='tool_use'`，`payload.output` 是**字符串**：

```text
"output": "[{\"type\":\"image\",\"source\":{...}}]"
```

后端 DTO 的 `output` 一律是 `string`，数组被 `JSON.stringify` 掉再落库；而**实时链路**
（worker 推 `tool_call_result`）给的是**内联数组**。于是同一条工具调用在两种形态之间来回：

| 时点 | `output` 运行时类型 | 卡片取图片块 |
|---|---|---|
| 执行中 | `Array` | ✅ 有预览 |
| 重新加载会话 / 重启软件 | `string` | ❌ 无预览，退化成原文 JSON |

三张卡片一律用 `Array.isArray(output)` 取图 —— `BrowserToolCard.tsx:64`、
`ImagePluginToolCard.tsx:104`、`text-output.tsx:27`。字符串进来直接判死。

`S-294` 当年只修了桌面 / 窗口截图那一条（`splitDesktopToolBlocks` 自己 `decode`），
浏览器截图、图片插件卡、通用 `ImageOutputBlock` 全漏着 —— 同一个病，修了四分之一。

## 三、修法

不逐个卡片补 `decode`（那样每加一张卡就要再抄一遍判据），在**渲染态统一出口**归一：

`components/chat/AssistantMessage/utils.ts` → `buildToolCallRenderState`：

```ts
output: reviveImageBlocks(result?.content ?? liveToolCall?.output, decodeStructuredToolResult)
```

四个 `tool-block-renderer.tsx` 调用点共用这一个出口，历史与实时两条来源一起覆盖 ——
以后新加的卡片只要走 `buildToolCallRenderState`，自动就是对的。

`lib/tools/tool-output-revive.ts` 的判据刻意收得窄：

- 不是字符串 ⇒ 原样返回（实时那一份是数组，不碰）；
- 不以 `[` 开头 ⇒ 原样返回（省掉解码，TOON 分支也不必进）；
- 解出来不是数组 ⇒ 原样返回；
- **数组里没有任何 `image` 块 ⇒ 原样返回**。

最后一条是重点。`[1,2,3]` 这种普通文本输出恰好是合法 JSON 数组，若无脑当成块数组，
卡片会认定「我有结构化输出」而把原文藏起来 —— 结果是一张空白卡，比原来的 JSON 更难查。
收窄到「含图片块」既够用又不可误伤：无图的输出本来就不需要这个转换。

`decodeStructuredToolResult` 走参数注入而不是直接 `import`，理由同
`desktop-tool-blocks.ts` 头部注释：`tool-result-format` 顶部 import 了 zustand 的
`settings-store`，直接拖进纯函数会让 node 里跑不了回归测试。

## 四、为什么不是「修落库」或「修后端 DTO」

- **改后端 DTO 类型**：`output` 变 `object` 要动 wire 格式，模型请求侧也在用同一份
  数据，牵一发动全身；而且库里已有的老数据仍是字符串，照样得在前端兜。
- **改落库**：同上，且老会话不会自己变好。

读取侧归一化是唯一能**同时覆盖新老数据、且不碰 wire** 的位置。

## 五、回归防线

`tests/tool-output-revive/program.ts` —— 17 条断言，钉死五件事：

1. 内联数组原样过，且是**同一个引用**（不做无谓拷贝）；
2. 含 `image` 块的 JSON 字符串解成数组、`filePath` 带出（重开会话靠它走 `oc-media://`）；
3. 无 `image` 块的字符串（`[1,2,3]` / 纯 text 块 / 普通多行文本）**原样返回**；
4. 坏 JSON / 空串 / TOON 文本 / 对象 / `undefined` 均原样返回且不抛；
5. 解码器失效时不得凭空出图 —— 证明结果确实来自解码，不是输入本来就是这个形状。

## 六、遗留

`ImagePluginToolCard.tsx:104` 与 `text-output.tsx:27` 的 `Array.isArray(output)` 现在
**能正常工作**（出口已归一），但判据本身没变。不改是刻意的：它们本来就该只吃数组，
真正的一致性由出口保证。若将来有人绕过 `buildToolCallRenderState` 直接给卡片喂
`output`，这两处还会复发 —— 那时才值得抽公共判据。
