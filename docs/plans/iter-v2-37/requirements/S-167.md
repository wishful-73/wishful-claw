- **状态**：✅ **已实施**（本迭代第 1 刀，2026-09-30）—— 老大 08:35「当前这个 bug 排最前面推进」，见 §七

## 一、现象（知识库原文要点）

1. **多会话串台**：会话 A 配 M1、会话 B 配 M2；A 跑完转非活跃后，轮到 B 时 **B 实际用了 M1**。老大 09-29 18:49 原话「总是容易」。
2. **外部投递会顶掉手设模型（21:51 补）**：老大手动把某会话（凶兆 / novel）**切成付费模型**；随后从外部（**全局助理派工单**）给该会话发新消息，**该会话模型又被切回去了**（不再是老大设的付费模型）。
3. **反方向同样中招（老大 2026-09-30 08:25 补充）**：**项目下的会话回复全局任务进度**时，**全局助理自己的模型也没用上** —— 「不只是派工单的时候，还有项目下会话回复全局任务进度导致的全局助理的模型也没用上」。
4. **最终后果（老大 2026-09-30 08:27）**：三条，逐条都能在代码里找到对应物 ——
   - **「用户去项目会话下手切也切不回来」** —— 见 §3.3（机制已定位：**模型与思考参数对不上账**，切回来了某些场景也报错）
   - **「思考模式的配置也匹配不上」** —— 见 §3.4（**独立缺陷，已定死**）
   - **「模型显示跟实际使用对不上账」** —— 显示侧走 `resolveSessionModelSelection`（会话绑定），实际侧走全局 `activeModelId`，两边必然劈叉

**影响**：按任务配的模型策略失效 —— 「凶兆配免费模型、心相配主力模型」这种分工被打乱。**只要从外部给别的会话发消息，就会顶掉该会话的模型**。

## 二、正确的做法已经存在，只是投递路径没走它

**正常发送路径（UI 发消息）是对的** —— `src/renderer/src/hooks/use-chat-actions.ts:323`：

```
resolveSendModel(sessionId)
  → resolveSessionModelSelection({ session, providers, activeProviderId, activeModelId, ... })
  → 优先 source: 'session'（会话自己的 providerId / modelId）
```

该函数上方注释已明写这个坑修过一次：

> Session-bound model switches used to update only the UI while sends kept reading the global provider store, so requests went out with the stale global model.

## 三、根因（实读定死）

### 3.1 两个方向汇聚到同一个 handler

**这是同一条代码路径，而不是两个 bug**：

```
① 全局助理派工单（全局 → 项目会话）
   send_session_message（C# AgentRuntimeProjectExecutor.cs:257）
     → 反向请求 project/send-session-message
     ─┐
      │  ② 项目会话回复全局任务进度（项目 → 全局助理）
      │     reply_global_dispatch（C# AgentRuntimeGlobalDispatchReplyExecutor.cs）
      │       → 反向请求 project/send-session-message（:184-185，sessionMode: "global"）
      │
      └─→ 渲染端同一个入口
          src/renderer/src/lib/tools/project-send-message.ts
            handleProjectSendSessionMessage()
            ← 两条路径都在这里给模型定型，也都绕过 resolveSendModel
```

⇒ **修一处即覆盖两条方向**，这也是为什么现象 ① 与现象 ③ 是同一个病。

### 3.2 落点代码：绕过了 `resolveSendModel`，直接取全局

**`src/renderer/src/lib/tools/project-send-message.ts`：**

| 行 | 代码 | 问题 |
|---|---|---|
| `:167-168` | `const providerStore = useProviderStore.getState()`<br>`const targetProvider = providerStore.getActiveProvider()` | 取的是**全局当前激活 provider** |
| `:175` | `const modelId = providerStore.activeModelId \|\| targetProvider.defaultModel` | 取的是**全局当前激活模型** |
| `:183` | `buildProviderPayload(targetProvider, modelId, settings, …)` | ⇒ **payload 就此定型**，`targetSession.providerId` / `targetSession.modelId` **一次都没读** |

### 同族路径（同一病，建议一并收）

| 路径 | 文件:行 | 模型解析 | 读会话绑定？ |
|---|---|---|---|
| 正常发送（UI） | `use-chat-actions.ts:323` `resolveSendModel` | `resolveSessionModelSelection` | ✅ 对 |
| **派工单 / 回复全局**（同一 handler，两个方向） | `lib/tools/project-send-message.ts:168,175` | `getActiveProvider()` + `activeModelId` | ❌ **根因** |
| 后台子 agent 唤醒 | `hooks/use-background-subagent-wakeup.ts:82-83` | `getActiveProvider()` + `activeModelId \|\| defaultModel` | ❌ |
| 渠道自动回复 | `hooks/use-channel-auto-reply.ts:203,214` | `channelMeta?.providerId \|\| activeProviderId` + `channelMeta?.model \|\| activeModelId` | ⚠️ 只读 channel，不读会话 |
| 定时任务 | `lib/tools/cron-runtime.ts:77-99` `resolveProvider` | 全局回落 | ⚠️ |

**写会话绑定的调用者只有两处**（都在 `stores/chat-store/session-slice.ts:777/790/800/812`）：

- `components/chat/ModelSwitcher/utils.ts:100/134/149` —— **用户手动切换**
- `lib/tools/cron-runtime.ts:203` —— **新建**会话时设置（不是覆盖已有会话）

⇒ **投递路径不写 session**（`project-send-message.ts` 全文无 `setSessionModelManual` / `dbUpdateSession`）。

### 3.3 「手切也切不回来」—— 机制是「模型与思考参数对不上账」

**老大澄清（2026-09-30 08:33）**：

> 「手切切不回来是因为**模型和思考参数对不上账**，就算切回来了**有些场景下也报错**。是其中一种后果。」

⇒ **不是切换功能坏了**。切换本身是好的（见下），坏在**模型变了、思考参数没跟着变**：两者不是一套。

**事实面（切换与 UI 发送都是好的）**：

- `resolveSendModel` 的调用点是**全**的 —— `use-chat-actions.ts:119/382/441/638`（四条 UI 发送入口）+ `cron-runtime.ts:393`。
- 手动切换 store + DB **双写** —— `ModelSwitcher.tsx:535 selectModel(...)` → `setSessionModelManual`（`session-slice.ts:767-778`）。

**错配的确切机制（已定位到代码）**：思考档位按 **`providerId:modelId` 的 key** 存 ——

`settings-store-types.ts:360-361`：

```ts
if (!providerId || !modelId) return null
return `${providerId}:${modelId}`
```

而 `buildProviderPayload` 查这个 key，用的是**它自己手里那套 provider/model**（`provider-payload.ts:54-62`）：

```ts
resolveReasoningEffortForModel({ reasoningEffortByModel, providerId: provider.id, modelId, thinkingConfig })
```

⇒ **投递路径查的是「全局 provider:model」的档位；UI 显示的是「会话 provider:model」的档位。两个 key 不同 ⇒ 必然两套值。**

再叠加 §3.4 的 `thinkingEnabled: false` 硬编码 —— **一个字段按全局、一个字段被钉死**，拼出来的请求 UI 对不上账是必然；个别模型 / 服务商不接受这套组合时即报错。

**报错的可能来源（待实测，不猜死）**：

- 实际发出的是全局模型的 `reasoningEffort`（如 `high`），而会话模型不接受该档位
- 用了全局 provider 的 `apiKey` / `baseUrl` 去跑会话的任务（该 provider 恰好不可用即报错）
- `thinkingEnabled: false` 与仍带 `reasoningEffort` 的组合被上游拒

**取证**：抓一次投递轮次的请求体，把 `provider` 字段逐项与 UI 显示比对。

### 3.4 「思考模式也匹配不上」—— 独立缺陷：派工路径**硬编码关思考**

`project-send-message.ts:183`：

```ts
const provider = buildProviderPayload(targetProvider, modelId, settings, { thinkingEnabled: false })
```

而这个 option 是**故意**留给派工路径的 —— `lib/agent/provider-payload.ts:42-49` 原文：

> Force the thinking flag instead of deriving it from settings. The project dispatch path has always sent `false`; **keep it that way until someone decides otherwise**.

⇒ 三件事：

1. **这不是意外，是历史设计**（注释明说「等人拍板」）。
2. **后果**：外部投递的**每一轮都强制关思考** —— 就算模型换对了，思考档位也对不上。
3. **待核**：`reasoningEffort` 仍按模型的 `thinkingConfig` 计算（`provider-payload.ts:54-62` 只看 `thinkingConfig` 存不存在，**不看 `thinkingEnabled`**），两字段是否在 C# 侧被一致解释，**需要核实** —— 若不一致，会出现更隐蔽的错配。

### 老大裁定（2026-09-30 08:31）

> 「外界投递的消息，**必须用会话本身的设置**，不管是**思考**还是**模型**。」

⇒ **裁定 = 跟随会话设置**：`thinkingEnabled: false` 的硬编码**去掉**，改走 `buildProviderPayload` 的默认口径：

```ts
options?.thinkingEnabled ?? (settings.thinkingEnabled && !!thinkingConfig)
```

即「全局思考开关 **且** 该模型支持思考」—— 这正是 UI 上给用户看的同一套结果。

**这条同时定下一条设计准则**（比单个字段重要，写进实施与评审口径）：

> **外部投递不是特殊通道。它必须与「用户在该会话里自己发消息」走完全一致的设置解析。**

由此推出：§3.2 的模型取用与 §3.4 的思考档位**必须收敛到同一个解析入口**（`resolveSendModel` + `buildProviderPayload` 默认口径），**投递路径不允许自带任何 override**。

> 边界说明：本次裁定是「投递路径跟随会话既有设置」，**不是**新增「会话级思考开关」。若日后要做每个会话独立的思考档位，那是**另一个需求**。

## 四、待验证点（登记时必须分开）

> **现象 ③ 已把天平压向「本轮跑错模型」这一侧** —— 全局助理**自己有绑定却没用上**，说明病在「这一轮取模型的方式」，不是某个会话的库被改写。下面两点仍需实测钉死。

1. **「被切回去」是显示观感还是真写了库？** 代码层面未见写入（`project-send-message.ts` 全文无 `setSessionModelManual` / `dbUpdateSession`）⇒ 判定倾向「这一轮跑的就是全局 `activeModelId`」，消息上标的模型 ≠ 会话绑定。**取证法**：外部投递前后各查一次 DB `sessions.modelId`，看是否被改写。
2. **绑定是否被清空过？** `resolveSessionModelSelection` 的 `manual` 分支要求 `session.providerId` **与** `session.modelId` **同时非空**（`session-model-resolution.ts:107`）。若其中任一被清空（`session-slice.ts:812` 的 inherit 分支会写 `undefined`），会静默回落全局 —— 这会放大观感。

## 五、修复方向（建议）

1. **统一收口**：把 `resolveSendModel(sessionId)` 复用到 §三 表里全部 ❌/⚠️ 路径（`project-send-message` / `use-background-subagent-wakeup` / `use-channel-auto-reply` / `cron-runtime`）。`project-send-message.ts` 已从 `use-chat-actions` 导入 `getPendingSessionMessages`，加一个 `resolveSendModel` 导入即可，无循环依赖风险。
   - **在 `project-send-message.ts` 改一处即覆盖两个方向**（派工单 + 回复全局，§3.1）—— 该函数已从 store 里取出 `targetSession`（`:78-90`），直接喂给它即可。**全局 session 也走同一函数**：它的 `modelSelectionMode` 若是 `inherit`，`resolveSessionModelSelection` 自然回落全局（正确）；若是 `manual`，则用它自己的绑定（当前漏掉的就是这一种）。
2. **兜底优先级明确**：会话绑定 > channel 绑定 > 全局激活 > provider 默认。**外部投递不得以全局覆盖会话**。
3. **`sessionMode: 'global'` 那一支要看住**：它影响的是提示词与工具集（`AgentRunContextPolicy.cs:43,76`），**不应影响模型解析** —— 修的时候别把两者绑到一起。
4. 顺手核 §四.2：若确认有路径把 `providerId` / `modelId` 清空，一并修。
5. **§3.4 的 `thinkingEnabled: false`（裁定：跟随会话设置）** —— 去掉 `project-send-message.ts:183` 的第四参，走默认口径；**并同步改掉 `provider-payload.ts:42-49` 的注释** —— 原文「keep it that way until someone decides otherwise」此刻**已被拍板**，注释不改，下一轮又会被当成「故意设计」保回来。
6. **总纲（按 08:31 准则）** —— 不止「改一个取值」，而是**把投递路径拉回统一解析**：模型走 `resolveSendModel`、思考走 `buildProviderPayload` 默认口径，投递路径**不允许任何自带 override**。评审时按这条卡。

## 六、验证要求

1. 会话 A 配 M1（付费）、会话 B 配 M2（免费）→ 从 A 给 B 发消息（派工单），**B 用 M2**。
2. **反向**：项目会话 A 回复全局任务进度（`reply_global_dispatch`）→ **全局助理用它自己绑定的模型**（`inherit` 则回落全局，符合预期）。
3. 手动把 B 切到 Mx → 外部投递一轮后，DB `sessions.modelId` **仍是 Mx**，`ModelSwitcher` 显示 Mx。
4. 覆盖「会话无绑定（fresh）」→ 回落全局，符合预期。
5. **思考档位（按 08:31 裁定）**：会话开着思考 → 外部投递那一轮**实际带思考**，与 UI 显示一致；会话关思考、或该模型不支持思考 → 投递轮**也不带**。
6. `npm run typecheck` 0 错误；`npm test` 全绿（基线 61/61）。
