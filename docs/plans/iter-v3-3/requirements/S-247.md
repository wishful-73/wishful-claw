## 3. 现状勘测（2026-10-28 实读源码）

### 3.1 全仓没有内存观测

| 位置 | 现状 |
|---|---|
| Electron 主进程 | **零采样**。全树搜 `app.getAppMetrics` / `getProcessMemoryInfo` / `process.memoryUsage` **零命中** |
| 渲染进程 | 同上，零命中 |
| Worker（.NET） | 有 `worker/memory` 端点（`SystemModule.cs:18-19`，回 `SystemMemorySnapshot`：`ManagedBytes` / `HeapBytes` / `FragmentedBytes` / `WorkingSetBytes`），**但渲染端与主进程对它的调用是零** —— 纯死代码 |
| 日志 | `logs/YYYY-MM-DD.log` 里没有任何周期性资源行 |

也就是说：现在出现「内存奇高」，我们能拿到的唯一证据是任务管理器一张表，且**事后无法复盘**。

### 3.2 进程结构（决定「奇高」是哪个进程的事）

一次正常运行至少五个进程，任何一个涨都会让用户觉得「这软件吃内存」：

| 进程 | 说明 |
|---|---|
| 主进程 | Electron |
| 渲染进程 | 聊天窗 UI + 消息列表 |
| GPU 进程 | Chromium |
| Worker | `.NET` 运行时，跑 agent loop / 工具 / SQLite |
| 内置浏览器 webview | 有独立渲染进程，页面本身的内存不受我们控制 |

**所以第一步必须先分清「哪个进程高」** —— 渲染进程高和 Worker 高是完全不同的问题（见 §4）。

### 3.3 已经被我们抬高内存底数的既有设计（不是缺陷，但会被误读成缺陷）

- `MaxInlineImageBytes = 5 MB`（`FileReadTool.cs:42`）—— 单张图内联 base64 后字符串开销约 1.33 倍。
- 消息历史按窗口加载（`loadRecentSessionMessages` / `fetchOlderMessages`），窗口内消息常驻渲染层状态。
- 会话快照、`segments`、`toolCalls` 都挂在 store 上，切换会话时旧会话数据是否释放**未核**。
- Worker 侧 SQLite 连接池、`SessionConversation` 常驻内存。

这些是「正常占用」，用来说明一个判断：**用户说「没用什么东西」和进程说「占 800 MB」可以同时成立**，两者不矛盾。

## 4. 嫌疑方向（**推测，未验证**，按可查性排序）

| # | 方向 | 为什么怀疑 | 怎么证实 |
|---|---|---|---|
| 1 | 渲染进程：图片 base64 常驻 | 截过图、看过图的会话，`image` 块的 `data` 是完整 base64 字符串挂在 store 里；S-224 已把图落盘，但**历史回读时是否仍把 base64 提到内存**未核 | 采样渲染进程 RSS + 统计 store 里 image 块总字节 |
| 2 | Worker：托管堆涨上去不归还 | .NET 的 Working Set 在 GC 之后通常不立刻还给 OS；`Server GC` 开启时更明显 | 调 `worker/memory` 看 `ManagedBytes` 与 `WorkingSetBytes` 的差值随时间变化 |
| 3 | 会话切换未释放 | 每个会话的数据都在 store 上堆着，切得越多堆越多 | 连续切 10 个会话看 RSS 斜率 |
| 4 | 内置浏览器 webview | 页面自己吃内存，且我们不清缓存 | 只开浏览器不聊天，对比 RSS |
| 5 | GPU 进程 / 合成层 | 长消息列表 + 虚拟滚动 + 动画 | 对比有无动画时 GPU 进程内存 |
| 6 | 长会话 + 大量折叠块 | 执行过程折叠块 DOM 数量 | 长会话 vs 新会话对比 |

**这里刻意不写「大概就是 X」** —— 现在没有任何数据支撑任何一条，写死结论就是编。

## 5. 做法（分两步，先观测后修）

### 第一步：让它可观测（本需求的实质交付）

不要求用户做任何操作 —— 不埋点、不跑脚本、不看日志。软件自己做：

1. **递归启用 `worker/memory`**：那个端点已经写好了，缺的是调用方。
2. **主进程补采样**：`app.getAppMetrics()` 能一次拿到全部子进程（主 / 渲染 / GPU / utility）的 `workingSetSize`，比分别采样省事且口径一致。
3. **定时落日志**：低频（例如 5 分钟一次）追加一行到 `logs/YYYY-MM-DD.log`，格式固定为「时间 + 进程角色 + pid + working set（MB）+ 托管堆（MB，仅 Worker）」。低频是为了不污染日志，也不占 I/O。
4. **设置页诊断区可见**：用户在「设置 → 关于 / 诊断」能直接看到当前各进程内存，不用开任务管理器。这也是将来用户报「内存高」时唯一可靠的输入。
5. **阈值告警（可选，最后做）**：某进程越过阈值时日志打一条 Warn 并记录当时的关键上下文（会话数、消息数、图片块数），事后可复盘。

### 第二步：按数据定因，再改

拿到 §5.1 的数据后，回到 §4 表里逐条证伪。**在数据出来之前不改任何内存相关逻辑** —— 猜着改容易把一个正常占用当泄漏修掉，反而引入新问题。

## 6. 验收

1. 正常使用 1 小时后，日志里有完整的周期性资源行（主 / 渲染 / GPU / Worker 都有数）
2. 设置页能看到当前各进程内存，单位 MB，刷新不卡
3. 用户报「内存高」时，我们能从日志指出是哪个进程、什么时候开始涨、涨之前什么操作
4. 第一步落地后，「奇高」这个词可以被量化成具体数字（现在不能）

**注意：本需求第一阶段的验收不是「内存降下来了」** —— 是「看得到了」。降下来属于第二阶段，且依赖第一阶段的数据。

## 7. 不做什么

- **不做自动内存回收**（定时 `GC.Collect` / 主动 kill 渲染进程）。这是拿副作用换数字好看：.NET 强 GC 会卡、杀渲染进程会丢 UI 状态。等数据说真泄漏了再谈手段。
- **不做内存上限强制**（`--max-old-space-size` 之类）。先看清楚再设限，否则只是把崩溃提前。
- **不要求用户上手**：不写「请打开任务管理器记录」这种步骤 —— 老大 2026-10-27 17:14 明确否决过「让用户挂东西」的做法。
- **不在第一步就优化图片链路**。图片 base64 是嫌疑之一，但 S-224 刚动过落盘，先看它是不是真的常驻再改。
- **不动 `worker/memory` 的返回结构**，除非采样需求确认它少了字段。
