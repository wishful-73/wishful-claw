## 一、老大的原话与现场

> 「我让浏览器截图后去查看图片就跑错 400 并且后续无法继续，我希望请求 400 就把本轮请求给剥离，并且写入请求报错的提醒。」

真实场景：**内置浏览器截图 → agent 去查看这张图 → HTTP 400 → 此后整个会话每轮都 400，无法继续。**

上游原文（知识库留档）：

```
.messages[477].image[0]: You have uploaded an unsupported image ...
（仅收 webp / png / jpeg / gif）
```

两条落地要求：

1. **请求 400 就把本轮请求给剥离** —— 把导致 400 的东西从请求里剥掉，后续轮次不再带着它撞。
2. **并且写入请求报错的提醒** —— 聊天窗要留可见提示，不能静默。

**链路是通的，问题在「进不去」和「拦不住」。**

### 3.2 成因 A（识别）—— marker 表里没有上游那句原文

`ImageInputErrors.cs:24-44` 的 marker 只有：`image_url is only supported` / `image_url is not supported` / `image input is not supported` / `does not support image` / `unknown variant \`image_url\`` / `not a multimodal` / `不支持图片` 等。

**上游原文 `You have uploaded an unsupported image` 一条都匹配不上** —— 没有 `unsupported image` 这个形态。`does not support image` 是「否定 + 支持」，原文是「un**supported** image」，词形不同。

⇒ `IsImageUnsupportedError` 返回 **false** ⇒ 不进剥图分支 ⇒ 脏块每轮重发 ⇒ 会话钉死。

> 附带事实：`ProviderRetryPolicy.cs:246` 自 2026-10-27 起 `IsRetryableStatus` 已收紧为 `429 || >=500`，**400 不再重试**。所以现在的现场比知识库留档那次**更快死**：不再白烧 20 次往返，而是每轮立刻 400 失败 —— 但脏块依然永留，用户体感仍是「这个会话废了」。

### 3.3 成因 B（拦不住）—— `source.type === 'url'` 的 image 块绕过整道格式闸

S-246 的白名单闸只覆盖 **base64 形态**。url 形态被直接透传：

| 位置 | 代码行为 |
|---|---|
| `OpenAIChatRequestBuilder.cs:253-256` | `sourceType == "url" ? GetString(source,"url") : BuildBase64ImageUrl(source)` —— url 分支**不经** `ResolveSupportedImageMediaType` |
| `AnthropicMessagesInputWriter.cs:331-338` | `sourceType == "url"` + url 非空 ⇒ `writableBlocks.Add(block)`，**无格式校验** |
| `ProviderContentHelpers.cs:238-245` `HasUsableImageBlock` | url 非空即判「有可用图」⇒ 调用方走 parts 分支 |

而渲染端确实会注入 url 形态：

- `visual-context.ts:272` —— 历史 artifact 若是 `source.type === 'url'` 就 `cloneImageBlock` 原样注入，**不做格式判断**。
- 一张 `file:///` / `oc-media://` 的 url 图送到上游，必然换回 `unsupported image`。

⇒ 这是 S-246 闸门的**结构性盲点**：同一个语义（「这张图能不能出门」）存在两份判据，base64 那半有闸、url 那半没有。

### 3.4 浏览器截图链路本身是干净的（排除）

老大描述是「浏览器截图后去查看图片」，所以这条链路本身必须查干净：

| 环节 | 事实 |
|---|---|
| 采集 | `browser-native-ui.ts:231` `capturePage()` → `:236 toDataURL()`。Electron `NativeImage.toDataURL()` **恒输出 PNG** |
| 编码 | `extractBase64ImageData` 从 data URL 取 `mediaType='image/png'` |
| 落盘 | `IPC.IMAGE_PERSIST_GENERATED` → `image-persist.ts:56 guessExtensionFromMimeType` ⇒ `.png` |
| 产出块 | `browser-native-ui.ts:246-254` = `{ type:'base64', mediaType, data, filePath }` |

**⇒ 浏览器截图产出的是合法 PNG base64 块，走的是有闸的那条路，不会 400。** 600 万像素级的大图另有 `MaxInlineImageBytes` 拦（`FileReadTool.cs:208`）。

所以现场那张脏图**不是**截图本身，而是**历史里另一张 url 形态 / 非白名单格式的图**（成因 B），或截图被再次读回时走了 `visual-context.ts` 的 url 注入路径。**成因 B 是主要的、可确证的一条**；成因 A 是它没被自愈救回来的原因。

`visual-context.ts:103` 把 `.svg` 映射成 `image/svg+xml`、`:288` 未知扩展名回落 `'image/png'` —— 这两条是知识库已记的次要线索，属于同类问题的输入端，一并纳入判据（§六 判据 4）。

## 四、定案

### 4.1 剥离粒度 —— **只剥出问题的 image 块，不剥整轮、不删历史**

依据三条：

1. **信息量**：`FileReadTool` 产出的是 `[text("Read image: 路径 (尺寸, 类型)"), image]`，剥掉 image 后 text 仍在 —— 模型照旧知道读了哪个文件、多大、什么格式，与旧版「不支持视觉」的降级输出一致。
2. **红线**：`AgentLoop.ImageInput.cs:21-23` 写明只剥 wire 副本；`conversation` 是 `SessionConversation` 的活引用，在它上面删块等于改用户历史。**本条沿用，不动历史、不动 DB。**
3. **剥整轮会吃掉用户消息里的文字**，代价远大于收益。

### 4.2 识别口径 —— 两层，缺一不可

**第一层（结构化，零文案依赖，优先）：** 给 url 形态补上格式闸，与 base64 共用同一个判据 `ResolveSupportedImageMediaType`。这是**从源头掐掉 400**，比事后认文案硬。落地后 url 图若非白名单格式，在组包阶段就不出门。

**第二层（文案，兜底）：** marker 表补上真实存在的原文形态，至少包含：

- `unsupported image`（本次现场原文）
- `image format is not supported` / `unsupported image format`
- `invalid image` / `image is not valid`
- `only supports` + image 的组合（保守取全短语）

**S-236 判据 10 红线不破**：`AgentLoop.cs:464` 的两道闸原样保留 —— 本轮没有 image 块可剥、或本 run 已经剥过一次，一律原样抛出，绝不截走无关 400。新增 marker 越多，越依赖这两道闸兜底，**所以这两行不许动**。

### 4.3 重发与收口

沿用既有 `MaxImageStripAttemptsPerRun`：**剥一次、重发一次**。第二次仍撞同一个错 ⇒ 问题不在图上 ⇒ 原样抛出走正常报错，**不静默吞**。

### 4.4 提醒文案 —— 走 i18n，扩既有键不新造

`chat:assistantMessage.imageInputUnsupported` 现有的语义是「模型不吃图，已剥图重发」。本条把「图格式不被上游接受，已剥图重发」并进同一个提示，文案要让用户明白两件事：①那张图像没被模型看到；②会话仍然可用。`zh` / `en` 双语。

## 五、判据（验收）

1. **隔离复现**：把上游原文 `You have uploaded an unsupported image ... 仅收 webp/png/jpeg/gif` 灌进判据，`IsImageUnsupportedError` 必须返回 **true**（修复前为 false —— 这条断言就是本 bug 的回归锚点）。
2. **追溯**：脏块留在会话历史里，后续轮次**不再 400**（走剥图重发），会话可继续。
3. **红线不破**：无关 400（模型不存在 / 参数错 / 工具配对错 / 上下文超限）**不被**这条降级路径截走，仍走各自专项处置。
4. **url 形态闸门**：`source.type==='url'` 且格式非白名单的 image 块，在组包阶段被丢弃并 `WorkerLog.Warn`，与 base64 同源判据。
5. **提示可见**：剥图发生时聊天窗出现提示 toast，同一会话重复触发合并不刷屏。
6. **不污染历史**：剥图后切回会话，用户原消息里的图**仍在**（`AgentLoop.ImageInput.cs:21-23` 红线）。
