# S-212：QQ 渠道入站图片 —— 解析层丢掉了 `attachments[].url`，图片从未下载

> 状态：**已登记，待开工**（2026-10-20 老大登记，iter-v2-40）。
> 类型：**bug**（能力缺失）。
> 归属：**iter-v2-40**。S-211 的渠道拆分项（老大 10:10「所有渠道的都需要，可以不同渠道登记不同的需求」）。
> 来源：**老大 2026-10-20 10:07 / 10:10** —— 渠道入站图片不保留，所有渠道都要。
> 轨道：**软件侧**（QQ 渠道主进程）。

---

## 一、现象

QQ 渠道收到图片，Agent 只看到 `[User sent an image]`，图片内容完全拿不到。

## 二、根因

`src/main/channels/providers/qq/parse-ws-message.ts:57-69`：

```ts
function describeAttachments(attachments: unknown): string {
  const first = attachments[0] as { content_type?: string } | undefined
  const contentType = first?.content_type ?? ''
  if (contentType.startsWith('image/')) return '[User sent an image]'
  ...
}
```

**只读了 `content_type` 用来挑占位符文案，`attachments[0].url` 直接丢掉。** QQ 官方机器人 API 的附件里 `url` 就是可下载地址（带时效签名），拿到了就等于拿到了图。

`normalizeContent`（`:78-82`）把占位符当正文返回，`buildIncomingMessage`（`:84-88`）的放行条件里虽然有 `data.images?.length`，但**解析层从来不填 `images`** ⇒ 图片这条路径永远走不到下载。

对比微信（`weixin-service.ts:390-414`）和飞书（`feishu-service.ts:192-208`）：两者都在**服务层**下载成 base64 再塞进 `images`。QQ 缺的就是这一段，连「拿到 URL」这一步都没做。

## 三、修法（沿用微信 / 飞书的既有形状）

### 3.1 解析层保持纯同步，只把待下载的 URL 带出来

`parse-ws-message.ts` 是纯函数（同步、无 IO，能直接单测），**不要在里面 fetch**。加一个瞬态字段：

```ts
// channel-types.ts 的 ChannelIncomingMessageData
/** 入站媒体的待下载地址（解析层填，服务层下载后转 images / audio 并清空） */
mediaRefs?: Array<{ url: string; contentType?: string; fileName?: string }>
```

`describeAttachments` 拆成两件：①照旧给占位符文案 ②把 `attachments` 映射成 `mediaRefs`。`normalizeContent` 不变。

### 3.2 服务层下载

`qq-service.ts:364-372` 在 `this.emit('incoming_message', parsed)` **之前**：

```ts
parsed.images = await downloadImageRefs(parsed.mediaRefs)   // 失败保留占位符 + content 追加 'but download failed'
```

- 形状照抄 `weixin-service.ts:390-414`：成功 ⇒ `images = [{ base64, mediaType }]`；失败 ⇒ `console.warn` + 改文案，**不能让一条消息因为下载失败整条丢掉**。
- `mediaType` 用 `content_type`，缺失按字节嗅探兜底。
- **QQ 附件 URL 有时效**，下载必须即时发生在 emit 前，不能留着 later。

### 3.3 复用 S-211

服务层把 `images` 填好后，渲染端消费由 **S-211** 负责（`use-channel-auto-reply.ts` 拼 `ImageBlock`）。**本条不碰渲染端。**

## 四、非目标

- **不改 QQ 发送侧**（QQ `qq-api.ts` 目前只有文本发送，发图是另一件事）。
- **不做历史回补**（已被丢弃的消息 URL 早已过期）。
- **不动 `buildIncomingMessage` 的放行条件**（它本来就已经认 `images`）。

## 五、待确认

1. **单条消息多附件**：QQ `attachments` 是数组，`describeAttachments` 现在只看 `[0]`。默认**全部下载**（最多取前 5 张，超出只留占位符并提示）。
2. **下载体积上限**：默认 10 MB，超出只留占位符（防止 base64 撑爆 WS 与 DB，与 S-211 §七 同一笔账）。

## 六、预计改动面

| 文件 | 改动 |

| `src/main/channels/channel-types.ts` | `ChannelIncomingMessageData` 加 `mediaRefs?` |
| `src/main/channels/providers/qq/parse-ws-message.ts` | `attachments` → `mediaRefs` |
| `src/main/channels/providers/qq/qq-service.ts` | emit 前下载 → 填 `images` |
| `tests/qq-attachments/`（新建） | 解析层单测（有 url / 无 url / 多附件 / 非图片） |

## 七、风险

- **QQ 附件 URL 带鉴权参数**，若服务端要求特定 UA / Referer，需要实测确认；失败必须降级成占位符 + `download failed` 文案，不能吞消息。
- **`mediaRefs` 是瞬态字段**，别让它进 DB（它只在主进程内活一次，渲染端拿不到也不需要）。
