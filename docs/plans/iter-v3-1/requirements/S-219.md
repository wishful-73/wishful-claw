# S-219：文件写入工具并发冲突（同 turn 多次编辑同一文件报 SharingViolation）

**2026-10-22 16:20**：

> 登记

来源：实际使用中撞到，非用户反馈。定性 **缺陷（工具健壮性）**，非体验优化。

## 2. 现象

同一个 assistant turn 内并发发出多个 `Edit` 调用、且都指向**同一个文件**时，只有第一个成功，其余返回：

```
Failed to edit file: IO_SharingViolation_File
```

- **无任何外部进程参与** —— 不是 VS Code 开着、不是同步盘、不是杀软。纯自己撞自己。
- 复现极其稳定：本轮改 `docs/plans/iter-v3-1/requirements/S-218.md` 时，一轮并发 4 个 `Edit`，**2 个失败**；后续几轮同类操作同样复现（累计 5 次）。
- 失败**不破坏文件**（现有内容是完整的，只是那条改动没落上），但调用方拿到 `success: false` 后只能重试，且**重试时机不可控**。

## 3. 代码链路

### 3.1 唯一的写入出口

`src/runtime/WishfulClaw.Agent/Tools/ToolHelpers.cs:141-168` `WriteAndFlushAsync`：

```csharp
await using var fs = new FileStream(
    path,
    FileMode.Create,
    FileAccess.Write,
    FileShare.Read,        // ← 关键：不允许别的写者
    bufferSize: 4096,
    useAsync: true);
```

`FileShare.Read` 的语义是「**我持写句柄期间，只允许别人以读方式打开，不允许写**」。第二个写者打开时即被 Windows 拒绝，映射到 `IOException`，`HResult` = `ERROR_SHARING_VIOLATION`（**32**），消息为 `IO_SharingViolation_File`。

### 3.2 共用的四个工具

`WriteAndFlushAsync` 是文件写入的唯一实现，四个工具全部经它：

| 工具 | 调用点 |
|---|---|
| `Edit` | `FileEditTool.cs:85` |
| `Write` | `FileWriteTool.cs:61` |
| 记忆热写 | `MemoryHotWriteTool.cs:63`、`:71` |
| Notebook 编辑 | `AgentRuntimeNotebookEditExecutor.cs:99` |

⇒ 缺陷面覆盖全部写类工具，不止 `Edit`。

### 3.3 读改写不是原子的

`FileEditTool.cs:55` 先 `File.ReadAllTextAsync` 读全文，`:75-77` 在内存里替换，`:85` 整体回写。读与写之间**没有任何锁**，也没有前置版本校验。

⇒ 即使把共享模式放宽让两个写者都进来，两个 Edit 也会各自基于**同一份原始内容**做替换，后者整文件覆盖前者 —— **前者改动静默消失**。

### 3.4 现状已核实的缺失

- **无按路径串行化**：全仓 `SemaphoreSlim` 有 4 处（`AgentRuntimeTools.cs:29` 等），**没有一处是文件路径锁**。
- **无共享冲突重试**：全仓无 `ERROR_SHARING_VIOLATION` / `SharingViolation` 相关处理；`GoalBackoffStrategy` / `ProviderRetryPolicy` 都是针对网络与限额，不能复用。
- **路径已规范化**：`ResolveFilePath`（`ToolHelpers.cs:63-79`）返回 `Path.GetFullPath` 绝对路径，可直接当锁 key 的原料。

## 4. 根因

三个因素叠加：

1. **写句柄独占** —— `FileShare.Read` 使同一文件的并发写必然被系统拒绝。
2. **工具栈允许同 turn 并发** —— 多个只读工具在同一轮并行是正确设计（读互不干扰），但写类工具被一并并行，没有任何约束。
3. **读改写非原子** —— 没有路径级互斥，并发写入即使不报错也会互相覆盖。

**关键判断：`FileShare.Read` 本身不是 bug，不要动它。** 它挡住的是「外部程序在我们写入时并发修改」这一类真实风险。要修的是「**我们自己内部没排队**」和「**外部占用时没有退避重试**」。

## 5. 修复方向

| 层次 | 做法 | 解决什么 |
|---|---|---|
| **① 按路径串行化**（主修） | `ToolHelpers` 内 `ConcurrentDictionary<string, SemaphoreSlim>`（key = 规范化绝对路径，`StringComparer.OrdinalIgnoreCase` —— Windows 不区分大小写），把 **读 → 改 → 写 整段**包进同一把锁 | 同 turn 并发 Edit 排队执行，第二个基于第一个的结果；**顺带修掉 3.3 的静默覆盖** |
| **② 共享冲突退避重试**（兜底） | 捕获 `IOException` 且 `HResult & 0xFFFF` ∈ {**32**, **33**} 时退避重试 50 / 100 / 200 / 400 ms，最多 4 次 | 真实外部占用：编辑器开着、OneDrive 同步、杀软扫描 |
| **③ 错误文案可读化** | 重试耗尽后返回「文件被其它程序占用……」，而不是直接抛 raw `IOException` message | 用户/模型能判断下一步该做什么 |

**锁的粒度**：`SemaphoreSlim(1,1)` 每路径一把，用 `GetOrAdd` 惰性创建。不需要清理 —— 进程生命周期内路径数量有上限（受沙箱约束），且条目本身极小。

**锁的范围**：从 `ReadAllTextAsync` 之前拿到，到 `Flush(true)` 之后释放。`AgentChangeTools.RecordChange`（`FileEditTool.cs:88-97`）**放在锁外** —— 它是内存记账，与文件内容无关，放在锁内只会拉长持锁时间。

**其它三处也要一起改**：`Write` / 记忆热写 / Notebook 编辑都经 `WriteAndFlushAsync`，但只有 `Edit` 有读改写的问题。`Write` 是整体覆盖，串行化后语义天然正确（后写胜出），重试层对三者都生效。

## 6. 代价与取舍

- **串行化会降低并发度** —— 多个 Edit 写同一文件时排队。但这是**必须**的：并行写同一文件本就无正确语义。
- **不影响真正的并行** —— 写不同文件时各拿各的锁，互不阻塞。这是本次设计的重点，没有用一把全局锁糊过去。
- **重试引入最长 750 ms 额外延迟**（50 + 100 + 200 + 400）—— 只在撞上外部占用时发生，正常路径零成本。
- **锁是进程内的** —— 跨进程（用户另开一个 WishfulClaw 实例、或外部编辑器）仍需靠退避重试兜。不追求跨进程文件锁（那是另一套复杂度，且会与外部程序抢锁）。
- **锁表不清理** —— `ConcurrentDictionary` 里的 `SemaphoreSlim` 条目随写入过的路径累积。受沙箱约束有上限，每项极小（一个信号量 + 一个字符串），进程生命周期内不需要清理。加清理反而要引入引用计数，得不偿失。

## 7. 刻意不做

- **不放宽 `FileShare.Read`** —— 改成 `ReadWrite` 会把「明确报错」变成「静默丢改动」，比现状更糟。**该判断已落到 `ToolHelpers.cs` 的代码注释里**，防后人顺手改。
- **不做全局单锁** —— 一把锁串行所有写入，会把「写不同文件」也拖成串行，白白损失并发。
- **不做跨进程文件锁**（`FileStream` 的 `FileShare.None` 独占 + 等待）—— 会与用户自己的编辑器打架，且 Windows 上不可靠。
- **不做读改写的前置内容哈希校验** —— 串行化已经保证进程内顺序，加校验属过度设计；跨进程场景由退避重试兜。
- **不改工具调度层**（让写类工具一律串行执行）—— 调度层不知道目标路径，粒度太粗，会误伤不同文件的并行写。
- **不改 `FileEditTool` 的行尾归一化与 BOM 探测** —— 只在其外层套锁与重试。

## 8. 验收

| 场景 | 步骤 | 期望 |
|---|---|---|
| 同文件并发 | 同一 turn 内并发 4 个 `Edit` 指向同一文件 | 4 个全部成功，**改动按发出顺序累加**，无丢失 |
