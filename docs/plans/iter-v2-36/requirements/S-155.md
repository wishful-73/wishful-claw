## 一、需求正文（做什么）

launcher 切「文件」模式后：

1. **输入即搜**：关键词变化 → 防抖 → 调 `es.exe` 取结果 → **在我们自己的面板里渲染列表**（图标 / 名称 / 所在目录 / 大小 / 修改时间）。
2. **键盘操作**：`↑↓` 选择、`Enter` 打开、`Ctrl+Enter`（或右键）在资源管理器中定位、`Esc` 清空 / 退出。
3. **空态 / 未就绪态**：查无结果显示「没有匹配的文件」；`es.exe` 或 Everything 缺席时走引导（§五）。
4. **文案改写**：S-151 遗留的「我们只是转发器」式心虚文案一并改掉（§六）。

**不做**：内容搜索（`content:`，见 §4.5）、mac / Linux、自建索引。

## 三、es.exe 官方参数核查

来源：**`es.exe -help` 实跑输出**（ES `1.1.0.38`，非记忆、非猜测）。

**取数配方（选定）**

```
es.exe -export-json <out.json> -utf8-bom -no-digit-grouping \
       -size -date-modified -extension -date-format 1 -n <N> <query>
```

| 参数 | 依据（官方 help 原文） |
|---|---|
| `-export-json <out.json>` | *Export to a file using the specified layout.* |
| `-utf8-bom` | *Store a UTF-8 byte order mark at the start of the exported file.* |
| `-size` | *Display options* → 出 `size` 列 |
| `-date-modified` | 同上 → 出 `date_modified` 列 |
| `-extension` | 同上 → 出 `extension` 列 |
| `-date-format 1` | *1=ISO-8601* ⇒ **直接拿 ISO 字符串，不必解 FILETIME** |
| `-n <num>` | *Specify the maximum number of results to find.* ⇒ 截断保护 |
| `-no-digit-grouping` | *Disable digit grouping (commas) for numbers.* ⇒ 防 `1,234` 污染 JSON |
| `-timeout <ms>` | *Wait up to … for the Everything database to load* ⇒ 首查时索引未加载完的兜底 |

**注意**：`-s` 在 es.exe 里是 **`Sort by full path`**，不是 S-151 的 `-search` 简写 —— 两个 exe 的参数表不同，别串（S-151 已把这条记成坑）。

**其它可用但本期不接的**：`-regex` / `-case` / `-whole-words` / `/a-d`（只文件）/ `/ad`（只目录）/ `-sort <name|size|date-modified|run-count|…>` / `-viewport-offset` + `-viewport-count`（分页）/ `-inc-run-count <file>`（**用一次 +1，可做「常用排前」**）/ `-get-result-count` / `-get-everything-version` / `-instance <name>`（多实例）。

**一个硬约束**：全参数表里**没有任何一项能启动 Everything 本体** ⇒ **es.exe 依赖 Everything 已在运行**。三路取数全都如此（索引在 Everything 内存里）。

## 四、本机实测（ES 1.1.0.38 × Everything 1.4.1.1032）

样本：老大本机 `D:\tools\Everything-1.4.1.1032.x64\`，ES 解压在 `.wishful-claw\tmp\es-probe\es\es.exe`（**262,312 字节**，zip 117,393 字节）。

### 4.1 JSON 结构（**字段真名已核**）

```json
[{"filename":"D:\\shared-file\\关于开展2026年民航…通知.pdf",
  "size":3970586,
  "date_modified":134295897306531411,
  "extension":"pdf"}]
```

- **`filename` 是完整路径**（不是裸文件名）；`size` 单位**字节**；`date_modified` 是 **FILETIME ticks**（100ns since 1601）⇒ 所以选 `-date-format 1` 绕开它。
- **名称 / 目录在 JS 里切**：实测 `-name -path-column` **没有**产出拆开的 `name` / `path`（t.json 里仍是 `filename` 全路径）⇒ 不靠 es.exe 拆列。
- 目录项路径**自带尾部反斜杠**（`…\.wishful-claw\`），规整时要认。

### 4.2 编码坑（必须钉死）

- **stdout 走控制台代码页（GBK / CP936）**：原始字节 `b9 a8 d2 ed` 按 GBK 解 = 「龚翼」；直接当 UTF-8 读**中文全变 `????`**。
- ⇒ **不读 stdout**，一律 `-export-json` + `-utf8-bom` 落文件再读，**读回时剥 `\uFEFF`**。

### 4.3 空结果

- 输出 **3 字节纯 BOM（`ef bb bf`）**，连 `[]` 都没有，**exit code 仍是 0**。（登记初版记的 `\uFEFF[]` 与实测不符，**2026-09-28 已订正**。）
- 要区分「无结果」与「出错」，用 **`-no-result-error`**：*Set the error level if no results are found*（实测无结果时 exit 9）。

### 4.4 耗时

- PowerShell `&` 直接调用：**平均 142.6 ms / 次**（含 PS 自身调用开销，Node `spawn` 应更低，**实施时用 Node 复测**）。
- Node `spawn` 复测（2026-09-28 实施期）：**~124–147 ms / 次**（含启动 es.exe + 建输出文件）。
- ⇒ 这个量级**必须防抖**，不能每敲一个字符调一次（§5.4）。

### 4.5 内容搜索（`content:`）—— 本期落不了

- 老大原话曾提「支持文件名 + 内容双模式」；Everything 的**内容索引是 1.5 才引入**的功能，老大装的是 **1.4.1.1032**。
- ⇒ 本期**只做文件名模式**；实施时用 `-get-everything-version` 判版本，**≥1.5 再谈内容模式**（另立需求）。
- （本条为**版本边界判断**，未在本机实测 `content:` 语法。）

## 五、落地方案

### 5.1 es.exe 探测（复用 S-151 骨架，另起一条链）

Everything 本体探测**保持不动**；`es.exe` 走**同款骨架**，八档：

`manual(设置页手动指定) → Everything 同目录 → 注册表 → 常见安装位 → PATH(where) → 程序目录 → 快捷方式 → 扫盘(仅「本机检测」触发)`

- 配置新增 `esExePath: string` + `esExePathAuto: boolean`（对齐 `everythingExePath` / `everythingExePathAuto`）。
- PE 版本校验必过：`ProductName` / `FileDescription` 含 `ES` 或 `Everything`（防选错）。S-151 已有 `isEverythingVersionInfoHit`，扩展复用。
- 实测样本位：`D:\tools\Everything-1.4.1.1032.x64\` 下**不一定**有 es.exe（官方向来分开下载）⇒ 「Everything 同目录」这档命中率存疑，但成本近零，留着。

### 5.2 取数（主进程）

新增纯函数模块（与 `everything-search.ts` 并列，不就地扩展 —— 见 §8.1）：

- `buildEsArgs(query, outFile, limit)` → `string[]`（§三 配方）
- `parseEsJson(raw)` → `FileHit[]`：剥 BOM → `JSON.parse` → 逐条派生 `name`（`basename`）、`dir`（`dirname`）、`isDir`（尾斜杠）、`size`、`mtime`、`ext`
- `FileHit = { fullPath, name, dir, isDir, size, mtime, ext }`

**临时文件**：落 `app.getPath('userData')` 下的固定 `es-search-out.json`；**串行队列**（后到者取消前一个未完成请求），避免并发写同一文件互踩。

**失败分类**（错误包装沿用 S-146 的口径，别把裸报文糊用户脸上）：

| 现象 | 判定 |
|---|---|
| spawn `ENOENT` | es.exe 路径失效 ⇒ 回探测 |
| exit 码 = `-no-result-error` 的值 | **无结果**，非错误 |
| 其它非 0 / 解析失败 | 报「文件搜索暂时不可用」+ 详情折叠 |

### 5.3 结果渲染（渲染端）

- 列表项：**文件图标**（`app.getFileIcon(path, {size:'small'})`，带 LRU 缓存，键 = 扩展名或路径）+ 名称（高亮命中）+ 目录（灰色，中段省略）+ 大小 + 修改时间。
- 键盘：`↑↓` / `Enter` 打开（`shell.openPath`）/ `Ctrl+Enter` 定位（`shell.showItemInFolder`）/ `Esc`。
- 上限 `-n 50`，列表可滚；底部一行小字「仅显示前 N 条」。
- **不做**：预览、右键菜单（除定位）、收藏、历史。

### 5.4 性能与防抖

- 输入防抖 **250ms**；每次请求带 **token**，回来时 token 过期就**丢弃**（防乱序回填）。
- 并发上限 **1**（§5.2 串行队列）。
- 单次查询硬超时 **2000ms**（`-timeout 1000` 给 es.exe 等索引加载 + 进程级 kill 兜底）。
- **不常驻**：不做长驻 es.exe 进程、不做文件系统 watcher。

### 5.5 降级矩阵

| Everything 本体 | es.exe | 文件模式表现 |
|---|---|---|
| ✅ | ✅ | **自渲染结果列表**（本期主体） |
| ✅ | ❌ | **投递式降级**：`spawn Everything.exe -search "<词>"`（S-151 现成能力，零新成本）+ 一行提示「装 ES 可在此直接看结果」 —— 见 §七 第 2 条 |
| ❌ | — | 引导页：**下载并安装 Everything** + **本机检测**（保持 S-151 现形态） |

## 六、文案改写（S-151 遗留病灶）

病根不是措辞，是**通篇解释「我们做了什么 / 没做什么」，而不是讲「用户能拿到什么」**。三处犯病原文：

**就绪态（面板）**

```
按回车用 Everything 搜索「x」
结果会显示在 Everything 窗口中          ← 把「我们只是转发器」写在脸上
D:\tools\Everything-1.4.1.1032.x64\...
```

**未就绪态**

> 「我们不做自己的文件索引 —— 装了 Everything 就直接把关键词交给它，搜索由它完成。」（自我辩解）
> 「……已经装了的话直接就绑上，**不需要你去找路径**。」（赔罪，「不麻烦你」重复两遍）
> 标题也先讲「缺什么」。

**设置页**：「由 Everything 完成搜索，我们不建自己的索引」。

**改法**（随结果自渲染一并做，「心虚感」与「结果跳出去」是同一个病）：

```
开启文件搜索
全盘文件名秒级出结果，支持通配符、正则、按大小 / 时间排序。
[本机检测]  [获取 Everything]
装过 Everything？点「本机检测」自动认出来。
```

设置页那句改成「**走 Everything 索引，不额外占磁盘**」—— 从辩解变卖点。

### 12.1 分类 0 条的根因：本机把「空格」当整文件名精确匹配

不是分类白名单错、不是 `ext:` 语法错、不是 IPC 版本错，是**空格**。老大本机 Everything 的
搜索设置把空格解释成「整文件名精确匹配」，而不是官方文档说的 AND。实测对照（2026-09-29，
`resources/es/es.exe`，`-get-result-count`）：

| 查询（旧拼法，带空格） | 命中 | 查询（新拼法，无空格 + 分组） | 命中 |
|---|---|---|---|
| `package ext:json` | **0** | `<package><ext:json>` | **11920** |
| `we chat` | **0** | `<we><chat>` | **360** |
| `package json ext:json` | **0** | `<package><json><ext:json>` | **11920** |
| `WeChat /ad` | **0** | `<WeChat><folder:>` | **47** |
| `数据库设计说明书 ext:doc;docx` | **0** | `<数据库设计说明书><ext:doc;docx>` | **2** |
| `WeChat Files`（完整目录名） | 2 | — | — |

所以**不能赌用户环境**：拼出来的查询串里一个空格都不留，关键词按空白拆词、每词各自 `<>`
分组后紧挨着拼，AND 语义交给 Everything 自己算。

顺带钉死两条同族事实：

- **单词分组与裸词等价**：`wechat` = 342 = `<wechat>` ⇒ 单关键词不存在「包了 `<>` 就变味」；
- **函数词分组与裸贴等价**：`<package>ext:json` = 11920 = `<package><ext:json>` ⇒ 选分组只是图一致
  （多词并列时裸贴的词会跟前面的组黏成一片）；但**自带尖括号的词必须原样放行**，包起来会破坏
  函数语法（`<size:>10mb>` 直接不成话）。

### 12.3 附带修复：首次开窗带词丢失（老大 11:14 报）

现象：原窗输入「周报」→ 选「搜索文件」→ 新窗输入框是空的。

根因不是参数没传过去，是**推的时机太早**：主进程在 `did-finish-load` 里推 `file-search:init`，而渲染端
`window.api.on` 只是 `ipcRenderer.on` 的封装，注册时机在 React 的 `useEffect` —— 晚于 `did-finish-load`，
消息直接丢。窗已经开着时反而正常（第二次点），因为那时监听早挂上了；这也解释了为什么 §11.3 手测那轮
没暴露。

修法：主进程加槽 `fileSearchInitialKeyword`，创建新窗时存词；渲染端挂载后主动 `invoke` 取一次（取完
清空）。**新窗不再走 `did-finish-load` 推送**（那一路必丢），已有窗仍走推送（收得到，推完清槽）。
新增通道 `file-search:take-initial-keyword`，`tests/ipc-msgpack-routing` 白名单已登记。
