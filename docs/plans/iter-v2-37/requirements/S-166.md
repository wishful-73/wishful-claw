## 一、诉求

现在的生图能力**强依赖一个单独配好的图像模型**；老大要的是「**通用的、当前模型就能调用**」的图片生成。

## 二、现状链路（2026-09-29 实读）

```
ImageGenerate 工具（模型侧）
  → AgentRuntimeImageGenerateExecutor.cs:42   反向请求 "image:generate"
  → src/main/ipc/reverse-handlers/image-reverse-handler.ts
  → POST {baseUrl}/images/generations          ← OpenAI Images API
```

`image-reverse-handler.ts` 的三个关键点：

| 行 | 内容 | 后果 |
|---|---|---|
| `:38` | `const model = (params.model as string) \|\| 'dall-e-3'` | **默认硬编码 DALL-E 3** |
| `:47-49` | 从 provider store 里找**第一个** `type === 'openai'` 且有 apiKey 的 provider | 只有 OpenAI **类型**的 provider 才会被选中 |
| `:51-56` | 找不到就直接失败：`No OpenAI-compatible provider with API key configured` | ⇒ **对话用 DeepSeek / 智谱 / Anthropic 的用户，生图直接不可用** |

⇒ 这就是「需要去配置专门的模型」的确切含义：**不是配一个图像模型，而是必须额外存在一个 OpenAI 类型的 provider**。

## 三、三条可能的路径（**方向待裁定**）

| # | 路径 | 做法 | 代价 / 风险 |
|---|---|---|---|
| A | **走当前对话模型的多模态输出** | 让模型在 chat completion 里直接吐图（Gemini `inlineData` / GPT-4o image output / 豆包·通义等），解析后入库 | **只有部分模型支持**；不支持的模型仍无图可出。需要 provider 侧解析图像输出块（我们目前只解析文本 / 思考 / 工具调用） |
| B | **不限定 OpenAI 类型，改用当前正在用的 provider** | `:47` 的筛选放宽到当前激活 provider（或其图像端点映射） | 现实是**多数 provider 的图像 API 端点与形状各不相同**（智谱 CogView / 豆包即梦 / 通义万相…），要逐个适配，工作量大且会持续漂 |
| C | **保留 images API 通路，但把端点做成「可自由配置」** | 用户可指定任意 OpenAI 兼容的图像端点（baseUrl + key + model） | 仍然是「要单独配」，**不满足老大诉求**，只能算现状改良 |

**A 与 B 不互斥**：A 是「模型自己会画」，B 是「模型让我们去调别人的画笔」。

### 老大裁定（2026-09-30 09:27）

> 我用 **DeepSeek v4.1 flash** 和 **glm 5.3 flash** 这些模型

⇒ **走 B**，并且问题 3 的答案是「**包含回落**」—— 一并实现。

**为什么 A 被否掉**：DeepSeek v4.1 flash / GLM-5.3 Flash 都是 **chat** 模型，chat completion 侧不产出图像块。A 的前提是「模型自己会画」，而这两个模型不会 —— 把图像输出解析写出来，对老大的日常链路依然是零收益。

**B 的实施口径**（即本条落地范围）：

1. 不再限定 `type === 'openai'`；
2. 优先用**当前激活 provider**：它声明了 `category === 'image'` 的模型就用它；没声明但 baseUrl host 在已知映射表里，用映射的模型名；
3. 激活 provider 给不出图像能力时，**回落到任何**声明了图像模型的 provider；
4. 都没有 ⇒ **明确报错**（§五.1），不给用户看原始 HTTP 报文。

## 四、实施注意

1. **不要动 S-162 的范围** —— 出口（卡片复制 / 下载 + `SaveImage`）与生图链路是两条独立的路，分别成刀。
2. 反向请求 `image:generate` 的入参里已有 `parameters`（`AgentRuntimeImageGenerateExecutor.cs:78`）；若走 A，需确认它是否携带**当前 provider / model 身份**（现在看起来不带，才会去 store 里自己找）。

## 六、实施记录（2026-09-30）

### 6.1 端点解析抽成纯模块

| 文件 | 改动 |
|---|---|
| `src/main/lib/image-endpoint.ts` | **新建**。`resolveImageEndpoint(providers, activeProviderId, requestedModel?)` / `summarizeApiError(raw)` / `KNOWN_IMAGE_MODELS` / `readString` |
| `src/main/ipc/reverse-handlers/image-reverse-handler.ts` | 删掉内联的解析与摘要函数改为 import；`type === 'openai'` 的筛选整段删除 |

抽模块的理由与 `generated-image-dir.ts` 一致：handler 的 import 链会拉到 `electron`（`ai-provider-store` → `data-dir` → `app`），**纯函数留在 handler 里就没法单测**。抽出后 `tests/image-endpoint` 直接 import，不需要 electron。

### 6.2 三条解析规则

按 §三 裁定，候选顺序是：**① 激活 provider**（`state.activeProviderId`，且 apiKey 非空）→ **② 其余任何 apiKey 非空的 provider**。

每个候选 provider 的模型名按 `声明的图像模型 → 显式请求的模型名 → host 映射表` 依次取；取不到就换下一个候选；全部取不到返回 `null`。

**映射表只写两条**：`open.bigmodel.cn → cogview-3-flash`、`api.openai.com → gpt-image-1`。刻意短 —— 猜一个不存在的模型名，比让用户显式声明一个图像模型更糟。

### 6.3 请求体按端点裁剪

`quality` / `style` / `n` 是 **OpenAI 专有字段**，兼容端点（智谱等）会拒收或误读。⇒ 只有 host 命中 `api.openai.com` 时才发全量 body，其余只发 `model` / `prompt` / `size`。

### 6.4 顺带修掉的一处真 bug：`count` 读不到

`AgentRuntimeImageGenerateExecutor.cs:71` 送出的键是 `count`，而 handler 读的是 `params.n` —— **`n` 永远是 undefined，张数永远是 1**。现在读 `count` 优先、`n` 兜底（老调用方）。

### 6.5 报错可读化

`summarizeApiError` 依次取 `error.message` → `error`（字符串）→ 顶层 `message`，都取不到回落原文；**HTML 错误页**（网关 502 之类）不原样透出，只说 `provider returned a non-JSON error page`；非 JSON 长文本截断到 300 字符。

找不到端点时的文案给可操作指引（去「设置 → 模型」加图像模型，或换服务商），不再说 `No OpenAI-compatible provider`。
