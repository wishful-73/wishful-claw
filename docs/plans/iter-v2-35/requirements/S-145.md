## 一、现象

让 agent 看工作目录里的本地图片时，agent 拿不到图像内容：`Read` 把 PNG 当文本读，返回二进制乱码。只有把图**作为附件贴进对话**（InputArea 图片附件 → base64 → user 消息 image block）模型才能看到。

**实测（2026-09-23 09:1x，本机）**：对 `website/img/p001.png` 调 Read，返回二进制乱码；最终改用 Windows 自带 OCR 才拿到图上文字。即「识别本地图」这件事当前只能靠用户贴图，agent 无路可走。

---

## 二、现状勘测（2026-09-23 11:2x）

### 2.1 Read 工具本体：纯文本，无图像分支

- 主 agent 的 `Read` = C# `FileReadTool`（`src/runtime/WishfulClaw.Agent/Tools/FileTools/FileReadTool.cs`），实现 `IToolExecutor`，用 `StreamReader(path, Encoding.UTF8)` 逐行读，返回 `ToolResult(string Content, bool IsError, string? Error)`（定义在 `WishfulClaw.Core/Tools/ToolTypes.cs:55`）。
- 图像文件被当 UTF-8 文本读，没有任何扩展名分派或二进制分支。
- 渲染端 `src/renderer/src/lib/tools/fs-tool.ts` 的 `readHandler` 只是 schema 占位：`execute: async () => nativeOnlyResult('Read')`（执行已迁 C# Native Worker）。

### 2.2 工具结果有两条形态，带图的一路只有「渲染端执行」的工具在用

| 形态 | 谁在用 | Content 类型 | 能带 image 块 |
|---|---|---|---|
| `ToolResult` | C# 内部工具（Read/Write/Grep/Glob/Memory…） | `string` | ❌ 不能 |
| `RendererToolResult` | 渲染端执行工具（Desktop / Browser / AskUser / ImageGenerate） | `JsonElement` | ✅ 能 |

`RendererToolResult` 定义在 `AgentRuntimeBrowserExecutor.cs:138`。`AgentRuntimeDesktopExecutor.CreateScreenshotContent` / `CreateAppWindowCaptureContent`（同文件 382-444 行）已经在产出 `[image(base64), text(说明)]` 的 content 数组。

### 2.3 图像真正被模型看到的通路：只有 user 消息

- **user 消息的 image block —— 三条线都完整支持**：
  - Anthropic：`AnthropicMessagesInputWriter.cs:164-171`（`user` 且无 tool results/uses 且含 image content 时走多模态写出）
  - OpenAI Chat：`OpenAIChatRequestBuilder.cs:253-274`（`image_url`，base64 → data URL）
  - OpenAI Responses：`OpenAIResponsesInputWriter.cs:195-207`（`input_image`）
- **tool_result 里的 image block —— Anthropic 会静默丢弃**：`AnthropicMessagesInputWriter.cs:187-193` 对非字符串 content 调 `ProviderContentHelpers.ToolResultToString`，而该方法（`ProviderContentHelpers.cs:46-71`）**只拼接 `text` 块，`image` 块直接丢弃**。
  - ⇒ 附带风险：现存 `DesktopScreenshot` / `CaptureAppWindow` 在 Anthropic 下的截图，很可能模型根本看不到。OpenAI 两条线是否保留 image 待实施时核（`OpenAIChatRequestBuilder` 图像收集范围需确认）。

### 2.4 前端已预留「Read 读图」，但从未接线

`src/renderer/src/lib/agent/visual-context.ts` 里已有：

- `VisualArtifactSourceKind` 含 `'read_image'`（第 14 行）；
- `sourceKindFromToolName`：`if (normalized === 'read') return 'read_image'`（第 105 行）；
- `hydrateImageForVision`：走 `fs:read-file-binary` 读 base64 → 组 image block（第 261-287 行）。

即「Read 读图」本来就是设计意图；只是 `Read` 从未产出 image block，这条分类成了走不到的死路径。

## 三、方案（已定稿）

### 3.1 主体：扩展 `Read` 本体，不新增工具

对图像扩展名（`.png/.jpg/.jpeg/.webp/.gif/.bmp`）走图像分支，产出与截图工具同形态的 content 数组：

```
[ text("Read image: <path> (<w>x<h>, image/png)"),
  image({ type: 'base64', mediaType, data, filePath }) ]
```

非图像文件走原有文本路径，行为不变。**不新增 `ReadImage` 一类独立工具** —— 对模型零学习成本，`Read` 就是 `Read`。

### 3.2 配套（必须一并做）：修 Anthropic `tool_result` 丢图

Anthropic API 的 `tool_result.content` 本身支持 image block，是这边写窄了：让 `AnthropicMessagesInputWriter` 对数组型 content 按 image block 写出，而不是无脑走 `ToolResultToString`。

**这条不修，新功能在 Anthropic 下无效**；同时它顺带修掉 `DesktopScreenshot` / `CaptureAppWindow` 在 Anthropic 下丢图的隐性 bug。

### 3.3 约束（已定）

| 项 | 口径 |
|---|---|
| 图像格式 | `.png` / `.jpg` / `.jpeg` / `.webp` / `.gif` / `.bmp` |
| 单图大小 | ≤ **5 MB**；超限只回「路径 + 尺寸 + mediaType + 超限提示」，不塞 base64 |
| 单次张数 | ≤ **4 张** |
| 非 vision 模型 | `supportsVision === false` 时降级为路径 + 提示文本，不产出 image block（文案参考 `visual-context.ts` 的降级写法） |
| 持久化 | **DB 侧剥离 base64**：segments 里只存 `[image: <path> <w>x<h> <mediaType>]` 占位；运行期历史保留 image 块供当轮发送。理由：否则每轮请求重发全历史图像，DB 与上下文双重膨胀。模型需要再看时重新 `Read` 即可（幂等、便宜）。实现细节（剥离点）实施时定 |

### 3.4 范围

- **本迭代做**：主 agent 的 `Read`；`sub_agent` 若与主 agent 共用 `FileReadTool` 则自动覆盖（实施时确认）。
- **本迭代不做（挂账）**：`pet` / `translate` 各自的独立 `Read`（渲染端各写各的）；SSH 远程图片（`ssh:fs:read-file-binary` 通道已存在，但先不接）。

## 五、验收

- **复现**：让 agent 对工作目录里的 png 调 `Read`。
- **验收**：agent `Read` 一张本地 png 后，能准确说出图上内容与版式（不是靠 OCR 猜字），且 Anthropic / OpenAI 两条线都成立。
- **回归**：非图像文件的 `Read` 行为不变；超 5 MB、超 4 张、非 vision 模型三种边界按 §3.3 降级；DB 里不出现 base64。
