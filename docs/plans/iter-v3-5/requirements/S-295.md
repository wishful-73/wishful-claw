## 一、这条需求真正要回答什么

老大看到的是一次**成功案例**：Astra Gate 从 Electron 迁到 Avalonia，内存 350 MB → 50 MB。想知道我们该不该也走这条路。

**但两个产品的形态差得太远，不能直接照搬结论。** 这份需求单的任务是把这个差距量出来，产出一份**带成本估算的评估报告**，让老大能拍板「迁 / 不迁 / 只迁一部分」，而不是凭一个别人的数字下决定。

**产出物是一份报告 + 一个可运行原型。** 评估完可能结论是「不迁」，那也是有效产出 —— 但原型必须真跑起来量出数字，不能只有推算。

## 二、参考对象：Astra Gate 是什么

`https://astra-gate.si/` —— **AIDotNet**（就是 OpenCowork / NextCoWork 的作者）的本地 AI 网关。MIT 开源，仓库 `239573049/Astra-Gate`。

它做的事：在 `127.0.0.1:17321` 起一个本机中转，把 OpenAI Chat / OpenAI Responses / Anthropic Messages / Gemini 四种协议解码成中间表示再重新编码，顺手做用量统计、费用入账、隐私护栏（密钥/邮箱/内网地址检测）。

**关键点：它的 UI 面很窄。** 官网原话「浏览器或桌面端打开，同一套液态玻璃界面」—— 控制台就是**概览、客户端开关、服务商配置、用量图表**这几页。没有聊天窗、没有 markdown 流式渲染、没有工具调用卡片、没有内置浏览器。

**这正是它能迁成功的前提。** 350 MB → 50 MB 的收益，是在「UI 复杂度接近零」的前提下拿到的。

## 三、我们的现状（2026-10-31 实测）

| 项 | 事实 |
|---|---|
| 桌面壳 | Electron `^43.2.0` + `electron-vite ^2.3.0` |
| 渲染层 | React，**874 个 `.ts` / `.tsx` 文件** |
| 主进程 | Node（`src/main`，含 IPC、协议注册、文件系统、渠道、更新器） |
| 预加载 | `src/preload`（IPC 桥） |
| 业务后端 | **C# / .NET worker，740 个 `.cs` 文件**（`src/runtime/WishfulClaw.sln`） |
| 内置浏览器 | **Electron `<webview>`**（Chromium 内核 + partition 隔离 + CDP 控制） |

**注意我们已经不是「纯 Electron 应用」** —— 业务逻辑本来就在 .NET worker 里，Electron 壳负责的是**窗口 + 渲染 + IPC + 浏览器宿主**。

这一点很重要：**迁移的收益空间比 Astra Gate 小，成本却比它大。** Astra Gate 迁完省掉的是「一整个 Node 后端 + Electron 壳」；我们迁完只省掉「Electron 壳」，.NET worker 本来就在。

## 四、四个硬约束（决定成本量级）

### 4.1 内置浏览器 —— 最大的拦路虎

我们用 Electron `<webview>`，agent 通过它做导航、截图、元素树抓取、执行脚本。这依赖 Chromium 的完整能力和 CDP。

Avalonia 侧的替代只有 **WebView2**（Windows）/ **WKWebView**（macOS）：
- WebView2 需要目标机安装 Edge WebView2 Runtime（Win10 早期版本可能没有）
- **CDP 控制能力不等价** —— Electron webview 暴露的调试协议、`session` / `partition` 隔离、`webContents` API 在 WebView2 上是另一套模型
- macOS 用 WKWebView 又是第三套 API ⇒ **跨平台要维护两套浏览器控制层**

`S-215`（浏览器工具）、`S-290`（截图经能力代理）、`S-294`（截图卡片）这一整条链都建立在现有 webview 语义上。

### 4.2 渲染层 874 个文件要重写

React + Tailwind + shadcn/Radix 的整套组件，在 Avalonia 里没有对等物。XAML 要重写：
- 流式 markdown 渲染（含代码块高亮、表格、mermaid）
- 工具调用卡片（几十种形状，`tool-block-renderer.tsx` 是路由中枢）
- 虚拟滚动消息列表（`useMessageListScroll.ts`，S-233 抖动问题还挂在那）
- 设置页、右侧面板、文件搜索、用量图表、i18n

**这不是「移植」，是「重做一遍」。**

### 4.3 内存问题的真因还没定

**这一点必须先说清楚，否则整个评估的前提是虚的。**

2026-10-31 实测（dev 库、真实会话）：

| 指标 | 数值 |
|---|---|
| JS 堆（稳定态） | **159 MB** |
| 消息数据总量（content + segments + toolCalls + meta） | **1.0 MB** |
| DOM 节点 | 1416，稳定 |
| 渲染进程工作集 | **1377 MB**，峰值 **2603 MB** |

**JS 堆 159 MB、数据 1 MB、DOM 稳定，而工作集 1.3 GB** —— 差的那 1.2 GB 在 JS 堆之外，最可能是**图片位图**（库里该会话 8 张 2520×1680 截图，满打满算 135 MB，除非被反复解码）。

**⇒ 也就是说，我们现在看到的 1.3 GB 很可能不是「Electron 的固有开销」，而是一个可以修的缺陷。** 在 S-247 把这条查清之前，拿 1.3 GB 去论证「必须迁 Avalonia」是不成立的。

**Astra Gate 的 350 MB 是「简单 UI 的 Electron 基线」，我们的 1.3 GB 是「简单 UI 基线 + 一个待修缺陷」。两者不可比。**

### 4.4 开发期与发布链全部要重做

`electron-vite`、`electron-builder`、增量更新（`blockmap` / `latest.yml`）、`oc-media://` 自定义协议、单实例锁、更新器、证书签名 —— 这一整套在 Avalonia 侧要换成另一套（MSIX / Velopack / 自研），**发布流程文档要重写一遍**。

## 六、值得单独看的一条中间路线

**「Avalonia 壳 + WebView2 跑现有 React 渲染层」** —— 这条路线省掉 Electron 主进程和 Chromium 打包体积，但保留 874 个文件的 React 代码不重写。

**它的可行性取决于 §4.1 和 §4.3**：如果内存大头是 Chromium 渲染进程本身（而不是 Electron 的 Node 侧），那换壳也省不掉，这条路线直接出局；反之它可能是性价比最高的选择。

## 七、我的初步判断（写在这里供老大参考，不是结论）

**倾向：不建议整体迁移，但值得做 §五 的评估。**

理由三条：

1. **收益空间小** —— 业务逻辑已在 .NET worker，Electron 壳省掉的那部分，不是我们内存的大头。

**如果 S-247 修完仍在 500 MB 以上且确实影响使用，那 §六 那条中间路线值得认真做原型。**

### 10.3 实测结果（本机，1440×900，每阶段 12 秒）

**空窗口**是这条需求的唯一关键数：

| 口径 | 工作集 | 私有字节 |
|---|---|---|
| Debug，框架依赖，GPU | 197.7 MB | 132.6 MB |
| Release，框架依赖，GPU | 187.4 MB | 128.7 MB |
| Release，NativeAOT，GPU | 156.2 MB | 122.6 MB |
| Release，框架依赖，软件渲染 | **96.9 MB** | **43.7 MB** |

加内容后的增量：流式文本 +32 MB（400 行上限、每 40 ms 一行）；一张 2520×1680 图 +14 MB。

### 10.4 结论

**Astra Gate 的 50 MB 能复现 —— 但只在「软件渲染 + 私有字节」这一种口径下（43.7 MB）。** 换到「GPU 加速 + 工作集」，同一份代码是 187 MB。

而 S-247 已实测：我们 Electron 生产构建的 renderer 稳态高水位是 **150~200 MB**，跑完能还 311 MB。**Avalonia 空壳的 156~187 MB 与它同量级** —— 也就是说，874 个渲染层文件重写成 XAML 之后，内存最乐观是持平。

⇒ **不建议迁移。** §六 那条中间路线（Avalonia 壳 + WebView2）同样不划算：WebView2 内核就是 Chromium，内存与 Electron renderer 同量级，还要重写一整套 IPC 与浏览器控制层。

**这条需求的结论是「不迁」，且是量出来的，不是推算的。** 评估报告不再单独出文件 —— §十 就是结论，`experiments/avalonia-shell/README.md` 是完整数据与复现步骤。

## 十一、完整场景实测与方案复核（2026-11-02 追加）

老大追问两件事：① 要完整界面的数，不要空窗口；② 框架依赖能不能 AOT。两条都在下面用实测回答，**§10.4 的结论因此修正（不是推翻，是精确化）**。

### 11.1 空窗口为什么不够

§10.3 的四个数只说明**壳的基线**，说明不了「换壳能不能治内存」。我们真实聊天窗的渲染成本大头在**单条消息内部**（markdown 正文、代码块、工具卡、图片），不在窗口本身。空窗口 156 MB 与「完整聊天界面」可能是两回事，必须分开量。

### 11.2 完整聊天场景的实现

新增 `ChatScenario.cs` + `ChatMessage.cs`，`--stage chat --messages N [--stream]`：

| 维度 | 取值 | 依据 |
|---|---|---|
| 单条助手消息 | 4~6 段正文，每段 100~260 字 | 对齐真实助手回复密度 |
| 代码块 | 30% 概率 | 真实占比 |
| 工具卡 | 60% 概率 | 真实占比 |
| 图片 | 每 7 条一张 840×560 | 走「PNG 落盘 → 解码 → 显示」，不跳过解码 |
| 列表 | `ItemsControl` + `VirtualizingStackPanel` + 外层 `ScrollViewer` | 对齐我们 Electron 侧的虚拟列表，否则比出来的数虚高 |
| 段落更新 | `ObservableCollection` 增量追加 | 流式只渲染新段落，不重建整条消息 |

**一处失败记录**：最初用 `ListBox` + `SelectionMode.None`，编译报 `CS0117: "SelectionMode"未包含"None"的定义`。Avalonia 11 的 `SelectionMode` 只有 `Single/Multiple/Toggle/AlwaysSelected`。改用 `ItemsControl` + 显式虚拟化面板，成本模型也更贴近我们自己的实现。

### 11.3 完整场景实测（本机 1440×900，稳态取最后三分之一采样中位数）

| 场景 | 工作集 | 峰值 | 私有字节 | 托管堆 | 线程 | 句柄 |
|---|---|---|---|---|---|---|
| **AOT · 200 条静态** | **154.0** | 165.6 | 118.3 | 5.3 | 40 | 596 |
| **AOT · 200 条流式** | **213.6** | 217.6 | 177.0 | 32.9 | 41 | 599 |
| JIT · 200 条静态 | 200.4 | 220.2 | 129.1 | 7.4 | 50 | 705 |
| JIT · 200 条流式 | 261.6 | 269.4 | 185.9 | 31.9 | 47 | 706 |
| JIT · 500 条静态（45 秒） | 190.0 | 208.3 | 125.6 | 5.7 | 50 | 706 |

三个关键读数：

1. **AOT 静态 154.0 ≈ AOT 空窗口 156.2** —— 完整聊天界面几乎不额外占内存，虚拟化把「消息有多少」和「内存有多大」彻底隔开。
2. **500 条比 200 条还低 10 MB**（190.0 vs 200.4）—— 常驻内存与历史条数无关，这组数是直接证据。
3. **流式才真花钱**：+60 MB（154.0 → 213.6），托管堆 5.3 → 32.9。增量渲染的中间态成本在这里，这也是 S-247「每帧重做」同源的成本。

### 11.4 三种发布形态的体积（`win-x64` 实测）

| 形态 | 运行时体积 | 文件数 | 用户机器要求 |
|---|---|---|---|
| 框架依赖 | 23.2 MB | 32 | 要装 .NET 10 Desktop Runtime（约 60 MB） |
| self-contained JIT | 99.7 MB | 218 | 无 |
| **self-contained AOT** | **32.0 MB** | **4** | 无 |

AOT 四件套：`WishfulClaw.AvaloniaProbe.exe` 16.07 MB + `libSkiaSharp.dll` 8.98 + `av_libglesv2.dll` 5.17 + `libHarfBuzzSharp.dll` 1.72。压缩后 **12.6 MB**（模拟安装包量级，已实测）。

> 口径提醒：早先量到「框架依赖 124.8 MB」是**错的** —— 没指定 `-r win-x64` 时 publish 会把各平台原生库全带上。指定 RID 后是 23.2 MB。这条记下来，别重复踩。

### 11.5 NETSDK1102：Avalonia 支持 AOT，但「框架依赖 + AOT」不能叠加

老大质疑「框架依赖应该也能 AOT」。实测 `--self-contained false -p:PublishAot=true`：

```
error NETSDK1102: 所选发布配置不支持优化程序集的大小。请确保你发布的是独立应用。
```

**Avalonia 完全支持 NativeAOT，§11.3 那两行 AOT 数据就是 AOT 版跑出来的。** 不能组合的是「框架依赖」这个**部署模式** —— AOT 产物按定义就不依赖 .NET 运行时，它自己必然是 self-contained。不是能力问题，是概念冲突。

**AOT 的真成本在代码 AOT 友好性，不在编译能不能过。** 原型上已踩一次：`MemoryProbe.FormatReport` 原本用 `JsonSerializer.Serialize`，AOT 下踩 IL2026 反射裁剪，报告写不出来，改手写字符串拼接才通。真要迁，Agent worker 侧还好（`InfrastructureJsonContext` 已用 source generator），Avalonia UI 层要确认全程编译绑定、不碰动态反射。

### 11.6 WebView2 实测：它就是 Chromium，25 个进程

老大查到「方式一：Avalonia 壳 + WebView2 加载 React 前端」。本机 WebView2 运行时在跑，直接量（运行时版本 `133.0.3065.92` / `145.0.3800.82`）：

| 角色 | 各进程工作集 | 数量 |
|---|---|---|
| browser(main) | 118.6 / 108.4 / 107.2 / 55.9 | 4 |
| renderer | 76.4 / 62.0 / 41.0 / 37.7 / 37.2 | 5 |
| gpu-process | 51.9 / 42.1 / 42.0 / 19.0 | 4 |
| utility | 35.0 / 32.8 / 32.7 / 19.3 / 18.3 / 17.5 / 17.3 / 5.8 | 8 |
| crashpad-handler | 11.8 / 8.8 / 8.5 / 8.4 | 4 |
| **合计（多宿主叠加）** | **1015.5 MB** | **25** |

> **口径必须写明**：1015.5 MB 是**多个宿主应用叠加**的合计，不是单实例。按最大一组进程估算单实例约 **290 MB**（browser 118.6 + renderer 76.4 + gpu 51.9 + utility 35），**这个 290 是推算，不是实测**。要精确值得单独起一个 WebView2 宿主来量。

**结论不变且更硬**：WebView2 的进程模型与 Electron 一模一样（browser/renderer/gpu/utility/crashpad 一个不少）。方式一只省掉 Electron 主进程那 220 MB，代价是引入 Avalonia 壳 154 MB。

### 11.9 结论修正

§10.4 的「不建议迁移」**维持**，但理由要换成下面三条（原来那条「成本大」不是重点）：

1. **内存缺陷与壳无关。** 那个涨到 2G 的会话是压缩卡片超长文本一次布局炸的，纯数据层 + 渲染策略问题。换任何壳，只要还渲染那几万字，照样炸。S-247 也已定性「不是泄漏，是每帧重做」—— 都是我们自己的代码。
2. **修完缺陷后换壳收益会缩水。** Electron renderer 主窗口 389.7 MB 里有多少是缺陷撑起来的，现在不知道。修好可能降到 300 上下，那时换壳的 60% 收益变成 30% 左右。
3. **纯 XAML 的 60% 是理论值，现实是 35%（A′）。** 因为消息正文逃不掉 WebView2。为了 35% 去重写 15.2 万行，且要先自建 Markdown 渲染器 / 终端 / Mermaid —— 投入产出不成立。

**体积这条账是干净的**：108.5 MB → 12.6 MB，砍 88%。但体积不是我们现在的痛点，内存才是。

## 十二、A′ 最小样张：airspace 前置已通过（2026-11-03）

### 12.1 为什么先验这一件

§11.10 那个垂直切片的**真正卡点不是内存，是 airspace**。经典 WPF + WebView2 的死结是：WebView2 是独立的 HWND 子窗口，永远压在父窗口的绘制内容之上，WPF 画不出东西盖住它。我们的聊天窗恰恰是把输入框状态条、浮动按钮、通知卡片**全部叠在正文之上**。这一条不成立，A′ 的设计就得整体推翻，后面的内存量了也白量。

所以先做最小样张，只回答一个问题：**Avalonia 的 XAML 能不能盖住 WebView2？**

### 12.2 样张

落点 `experiments/webview-airspace/`，刻意不进任何 sln / tsconfig / ci-checks（规矩同 `experiments/avalonia-shell`）。

| 文件 | 内容 |
|---|---|
| `WishfulClaw.WebViewAirspace.csproj` | `net10.0`，`Microsoft.Web.WebView2 1.0.*`，`ApplicationManifest=app.manifest`，`UseSystemDrawing=true` |
| `WebViewHost.cs` | `internal sealed class WebViewHost : NativeControlHost`，用 `CoreWebView2Environment.CreateCoreWebView2ControllerAsync` + `System.Drawing.Rectangle` 把 WebView2 子窗口贴到 NativeControlHost 的 HWND |
| `MainWindow.cs` | 三块 XAML 浮层（左上卡片 / 顶部通栏 `#3B82F6` alpha 235 / 右下卡片）叠在 WebView2 之上 |
| `content.html` | 棋盘格背景，便于看出被遮挡的边界 |
| `app.manifest` | `dpiAware/pmon` + `permonitorv2` + `supportedOS` |

### 12.3 结论：三块浮层全部盖住 ✅

截图实测，左上、顶部通栏、右下三块 XAML 浮层**全部正确显示在 WebView2 内容之上**，棋盘格被压住的部分没有透出来。

**airspace 问题在 Avalonia 的 `NativeControlHost` 场景下不成立。** 原因是 Avalonia 的子窗口托管走 dumb window（`WS_EX_NOREDIRECTIONBITMAP` 一路），Avalonia 自己的渲染走 DirectComposition，能与子窗口正确合成层级 —— 这正是 `NativeControlHost` 被设计出来的用途（原生内容在下面，Avalonia 内容可以盖在上面）。

### 12.4 与 Zephium 的对照（重要）

zephium 的 `stage.rs` 明确弃用了 child window 做覆盖，改用**顶层分层窗口**（`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` + `WS_POPUP`），注释写「layered child windows have broken input and spotty ULW support」。

**这个坑 Avalonia 帮我们绕掉了** —— 我们的样张用的就是 child window，浮层覆盖正常。所以 Zephium 那套 88 KB 的 stage 代码不是我们必须照抄的路径。

但两者不能直接类比：Zephium 是 wry 裸 HWND（没有 compositor 参与），我们是有 Avalonia 合成层。**Tauri 线要单独验这一条**（见 S-306），不能拿这个结论套过去。

### 12.5 还剩什么没验

`dotnet build` 0 错误、窗口正常、浮层覆盖通过 —— 但这只证明「能盖住」，不等于「能当生产外壳」。待验清单：

1. 内存基线（空页 / 载入真实 React 页 / 5 分钟是否回落）
2. 输入链路：浮层不吃穿透、未覆盖区鼠标滚轮键盘正常、**中文 IME** 候选框（子窗口 + 外壳的经典坑）
3. 尺寸 / DPI：改窗口大小时 WebView2 是否跟随、跨不同 DPI 显示器是否模糊
4. 多 WebView2 实例（我们内置浏览器面板需要 ≥2 个同时活着）
5. 落地代价：React 侧与原生外壳的通信边界（菜单、拖拽区、快捷键、剪贴板、文件对话框）

**各项均已派子代理实测，数据回来后补进 §十三。**
