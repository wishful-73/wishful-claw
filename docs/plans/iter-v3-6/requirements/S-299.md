# S-299 · 定时任务被 15 轮掐断 —— 默认改成不限，轮次留作手动设置

> 状态：**📋 已登记，待排刀（v3-iter-6）**
> 登记：2026-11-01 20:11
> 来源：老大原话「确实是定时任务触发的，不过我不太想要定时啊，做任务到一半停住了，我还不知道原因」+「我希望默认是不限，可以手动设置轮次。现在是默认 15 实际我其实没有去改」
> 定性：**不是「上限太低」，是「用轮次当护栏」这个设计本身错了。** 见 §三

## 一、这条需求真正要改什么

老大撞到的是：一个定时任务跑到一半停住，桌面通知只说「达到迭代上限」，不说停在第几轮、跑了多久、最后在干什么。

两件事要分开：

1. **默认值错了** —— 主聊天 `maxIterations: 0 = 不限`，定时任务却硬性兜 15 轮。用户没动过这个设置，却因此被掐断。
2. **归因说不清** —— 掐断时只给一个结果，不给上下文。

老大的口径很明确：**默认不限，轮次留成手动可设的选项**。不做「换个更大的默认值」，那是同一个错误换个数字。

## 二、现状证据（2026-11-01 实读）

### 2.1 三处硬编码，最后一处会把「不限」翻译成 15

| # | 位置 | 代码 | 后果 |
|---|---|---|---|
| 1 | `src/main/ipc/reverse-handlers/cron/db.ts:36` | `maxIterations: job.maxIterations ?? 15` | 建任务时落库默认 15 |
| 2 | `cron/db.ts:71` | `Number(row.max_iterations ?? row.maxIterations ?? 15)` | 读库再兜一次 |
| 3 | `cron/handlers.ts:61` | `(params.maxIterations as number \| undefined) ?? 15` | 创建入口兜 |
| 4 | `cron/scheduling.ts:153` | `maxIterations: job.maxIterations ?? 15` | 派发时兜 |
| 5 | `DbCronTools.cs:312` | `GetInt(parameters, "maxIterations", 15)` | agent 建任务时兜 |
| 6 | **`cron-runtime.ts:428`** | `runEvent.maxIterations && runEvent.maxIterations > 0 ? runEvent.maxIterations : 15` | **⚠️ 用户填 0 ⇒ 被改成 15** |
| 7 | **`cron-runtime.ts:504`** | 同上（sidecar 后台路径） | **⚠️ 同上** |

**第 6、7 两处是这次改动的关键。** 它们把「0 = 不限」的语义**反向**解释成「0 = 没填 = 15」。所以只在 UI 上把默认值改成 0 是没用的 —— 填 0 会被这两行改成 15，看起来「改了但没生效」。

### 2.2 UI 上这个字段没有任何说明

`src/renderer/src/components/automation/CronJobFormDialog.tsx:365-376`：

```
<Input type="number" min={1} className="w-20" value={values.maxIterations} ... />
```

- `min={1}` ⇒ **用户连 0 都填不进去**，想「不限」都没有入口；
- 标签只有 `t('automation.maxIterations')`，**没有一句说明**这数字是什么、撞了会怎样；
- 默认值 `15` 出现在 `CronJobFormDialog.tsx:63/88/182`、`AutomationTaskFormDialog.tsx:331`、`cron-job-view.ts:83` 五处。

**⇒ 老大「我还不知道原因」不是他的问题，界面上确实一个字都没说。**

### 2.3 主聊天是另一套语义

`src/renderer/src/hooks/use-chat-actions.ts:284`：`maxIterations: 0, // 0 = unlimited, agent runs until no more tool calls`

`AgentLoop.cs:271`：`var requestedMaxIterations = JsonHelpers.GetInt(parameters, "maxIterations", 0); // 0 = unlimited`
`AgentLoop.cs:280`：`var hasIterationLimit = requestedMaxIterations > 0 && !isSubAgentRun;`

**同一款软件，聊天不限、定时 15。** 用户没法预期这个差异。

### 2.4 撞上限后的提示（`AgentLoop.cs:746` / `run-end-label.ts:100-104`）

| 出口 | 文案 |
|---|---|
| 桌面通知（`AgentLoop.cs:746`） | `达到迭代上限` |
| 消息正文（`run-end-label.ts:103`） | `这一轮到了迭代上限，停在这里` |

两句都是**只有结果没有上下文**：不说第几轮、跑了多久、卡在哪个工具上。

## 三、根因：轮次不是护栏

15 这个数字纯属猜的，而且**跟任务复杂度没有比例关系**：

- 一轮可能 1 秒（读一个文件、列个目录）；
- 一轮可能 3 分钟（长上下文推理、跑一次构建）。

**同样 15 轮，可能是 20 秒，也可能是 45 分钟。** 拿它当「防止后台任务跑飞烧钱」的护栏，既防不住（每轮都贵的话 15 轮照样烧穿），也误伤（每轮都便宜的话 100 轮也无所谓）。

真正该管的是**时长**，不是轮次。

顺带一条脆弱点（本需求**不修**，只记）：`AgentLoop.cs:662`

```csharp
var loopEndReason = state.StopReason ?? (completed ? Completed : MaxIterations);
```

「不是正常跑完」一律记成 `max_iterations`。目前外层 `for` 只有三处 `break`（`:309` / `:610` / `:621`），三处都设了 `completed = true`，所以暂时不误报 —— 但这条链靠人工纪律撑着，以后谁加一条退出路径忘了标记 `completed`，任意异常收尾都会报成「迭代上限」。**这正是「我们明明没上限却报上限」的唯一可能来源**，值得单独立条（见 §六）。

## 四、方案

### 4.1 默认不限（老大已拍板）

- UI 默认值 `15` → **`0`**，`min={1}` → **`min={0}`**；
- 框下加一行说明：「留空或 0 = 不限轮次」；
- 五处默认值（§2.2）统一走一个常量，不再各写各的。

### 4.2 把「0 = 不限」贯通到 worker（**关键**）

`cron-runtime.ts:428` / `:504` 改成：

```
maxIterations: typeof runEvent.maxIterations === 'number' && runEvent.maxIterations > 0
  ? runEvent.maxIterations
  : 0
```

`0` 传进 `AgentLoop` 后走 `hasIterationLimit = false`，即真正的无限轮次。

主进程侧 `?? 15` 那四处（§2.1 的 1~5）同样改成 `?? 0`，否则「读库兜 15」会把新默认值又抹掉。

### 4.3 撞上限时说清上下文（这条可以单独一刀）

文案从「达到迭代上限」改成带数据的：

```
已跑 15 轮（42 分钟），最后一步：编辑 src/xxx.ts
```

需要的数据（轮次、累计耗时、最后一个工具名）在 `AgentLoop` 侧都是现成的，走 `runEnd` 的 `params` 带出去，渲染端拼。**不改 `RunEndLabelDescriptor` 的形状**，只加 `params`。

### 4.4 时长护栏 —— 我的建议，但**不在这条需求里做**

老大的原话只要「默认不限 + 手动设置」，没要时长护栏。我倾向单独登记一条：定时任务默认 60 分钟软上限，到了**先通知再继续**（不是掐断）。**这条等老大点头再立**，不夹带进 S-299。

## 五、验收判据

1. 新建定时任务，不改任何设置 ⇒ 落库 `max_iterations = 0`；
2. 该任务跑到第 20 轮、第 30 轮不被掐断（造一个需要 20+ 轮的任务实测）；
3. 手动把轮次设成 5 ⇒ 第 5 轮正常停下，且提示里带「5 轮」和耗时；
4. 手动填 0 ⇒ **仍然是不限**（回归 §2.1 第 6、7 两处的反向解释）；
5. 旧任务（库里已是 15）不受影响 —— 不回填、不改历史数据，用户自己改才变；
6. 主聊天行为零变化（`maxIterations: 0` 路径不动）。

## 六、明确不做的事

- **不改 `AgentLoop.cs:662` 的归因逻辑** —— 那是独立一条（`completed` 反推退出原因），改动在 worker 核心循环，风险与这条不同级，**另立需求**。
- **不做时长护栏** —— 见 §4.4，等点头。
- **不回填历史任务的 15** —— 老数据保持原样，只改新建默认值。
- **不动 `SubAgentDefinition` 的 `MaxTurns`** —— 它早在 S-132 就降级成「提醒点」了，与这条无关。
