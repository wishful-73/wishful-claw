## 一、来源

## 二、现象：11.98 MB 走完全链路，落地的只有 2.7 KB

私有仓实测（`docs/analysis-2026-11-05-round2.md` §7）：

```
request_debug payload 11,983,135 字符 → 渲染层实际驻留 2,695 字符
```

比例 **0.02%**。

## 三、为什么是 99.97% 白推 —— 渲染层自己写着上限

`src/renderer/src/stores/debug-store.ts:20-22`：

```ts
export const MAX_DEBUG_BODY_CHARS = 2_000;
export const MAX_RESIDENT_DEBUG_BODY_CHARS = 4_000;
```

**渲染层拿到就截到 4 KB。** 也就是说 worker 侧生成的那 11.98 MB 字符串，除了前 2~4 KB，全部在到达后 1 毫秒内被扔掉 —— 但它已经走完了：

`JsonSerializer.Serialize(body)` → MessagePack 编码 → pipe 传输 → base64（前端）→ 再解析成 JSON

一轮对话 × 每次重试 × 每条消息（assistant/tool 各一次）= 这条链路跑的次数远比「一轮一次」多。

## 四、代码链路（主仓实读）

`src/runtime/WishfulClaw.Agent/OpenAIChatProvider.cs:46-55`：

```csharp
var payload = JsonSerializer.Serialize(request);
events.OnRequestDebug?.Invoke(new RequestDebugEvent(... payload ...));
```

同样结构在另外两个 provider（`AnthropicChatProvider` / `GeminiChatProvider`）各有一份，**三处同构**。

## 五、修复方向

**在 worker 侧按渲染层真实需要的上限先裁一刀，结构化地裁。**

不是简单 `Substring` —— 要保留「结构完整 + 大字段占位」：

| 字段 | 处理 |
|---|---|
| `messages[].content` 里的 image / 超长 text | 换成 `[omitted: image/png 612KB]` 之类的占位符 |
| 请求头 / model / 参数 | 原样保留（这些是排查 400 真正需要的） |
| 总长 | 收敛到 4 KB 量级附近（对齐 `MAX_RESIDENT_DEBUG_BODY_CHARS`） |

私有仓的 `RequestDebugBodyTrimmer.cs` + `RequestBuildAllocationRegressionTests` / `RequestDebugTrimRegressionTests` 可直接参考移植（**注意：那边是从主仓全量搬出去的，中间两边已漂移，别整文件覆盖，按点核**）。
