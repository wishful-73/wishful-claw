## 二、现象

同一套「provider → HTTP 头」的规则，在主链里被**手抄了 5 遍**，每份的覆盖面还不一样：

| # | 位置 | User-Agent | organization / project | requestOverrides | opencode session | debug 版 |
|---|---|---|---|---|---|---|
| 1 | `OpenAIChatHeaders.cs:12-34` `ApplyHeaders` | ✅ | ✅ | ✅ | ✅（门禁 `providerBuiltinId == "opencode-go"`） | ✅ `:36-53` |
| 2 | `AnthropicMessagesProvider.cs:211-213` | ✅ | ❌ | ✅ | ❌ | ✅ `:235-237` |
| 3 | `OpenAIResponsesProvider.cs:233-249` | ✅ | ✅ | ✅ | ❌ | ✅ `:259-265` |
| 4 | `ContextCompression.cs:624-625`（anthropic 摘要） | ✅ | ❌ | ✅ | ❌ | ❌ |
| 5 | `ContextCompression.cs:769-777`（openai 摘要） | ✅ | ❌ | ✅ | ✅ | ❌ |

差异不是「协议本来就不一样」，而是**抄漏**：

- `ContextCompression` 两处都没有 `organization` / `project` —— 走 OpenAI 摘要时，配了组织的账号拿不到组织计费/路由。
- `AnthropicMessagesProvider` 与 `OpenAIResponsesProvider` 没有 opencode session 门禁 —— 对这两条协议而言目前无害（opencode-go 是 openai-chat 协议），但规则散着就迟早会对不上。
- 注释里已经留了痕：`ContextCompression.cs:622-623` 与 `:766-768` 都写着「Mirror the live-turn header chain」—— 抄的意图是明确的，只是没抄全。

## 四、根因

**没有单一头链定义点。** `ProviderHttpHeaders` 诞生前，主链每加一个 provider 协议就复制一遍头部装配；复制时按「这条协议现在需要什么」裁剪，而不是按「provider 配置有什么就该带什么」。结果是配置项与生效路径之间出现隐性缺口 —— 同一个 provider 配置，走 chat 生效、走自动压缩摘要不生效。

S-171 建 `ProviderHttpHeaders` 时**故意只收敛辅助通道**，主链原样不动：主链改动面大（4 个文件 + debug 版 + 每条的协议差异），跟辅助通道补头链是两件事，混在一刀里没法单独验证。这就是本需求单独登记的原因。

## 五、修复方向

把上表 5 处（+ 3 份 debug 版）收敛到 `ProviderHttpHeaders`，让它成为**唯一**的头链定义点：

1. `ProviderHttpHeaders` 补齐 debug 版：`ApplyOpenAiChatDebug(dictionary, provider, sessionId)` / `ApplyAnthropicDebug(dictionary, provider)` —— 语义与现有 `ApplyOpenAiChat` / `ApplyAnthropic` 一一对应。
2. 主链 5 处改为调用该类的对应方法，删掉各自的头部装配代码。
3. 收敛时**按「超集」对齐**：`organization` / `project` 与 opencode session 门禁统一进 `ApplyOpenAiChat`，各调用点不再自行裁剪。协议差异（Bearer vs `x-api-key` vs `anthropic-version`）留在调用点 —— 那是鉴权，不是 provider 配置。
4. `ProviderTestService` 是否一并收敛，实施时再定（见「七」）。

**前置依赖**：无。S-171 的 `ProviderHttpHeaders` 已就位，本需求是它的自然延伸。

## 六、代价与取舍

（登记时的预期，实施后回填）

- **主链是热路径**，4 个文件 5 处 + 3 份 debug，改错一处就是「聊天能发、压缩摘要 403」这类只在特定路径复现的问题 ⇒ 必须靠回归套件兜住：`tests/WishfulClaw.ProviderHeaderRegressionTests` 现有 `AssertHeaders` 系列断言直接打在 `OpenAIChatProvider.ApplyHeaders` 上，收敛后断言**应保持全绿不改** —— 这是收敛没改行为的证据。
- 收敛后行为**有意变化**的点：`ContextCompression` 两处开始带 `organization` / `project`（此前丢）。这属于修漏，需在验证里明确「压缩摘要请求头 = 聊天请求头」。

## 七、刻意不做

- **不动 `ProviderTestService`** —— 它发的是连接测试，用固定 session id（`ConnectionTestSessionId`），语义是「验证配置可用」而不是「像一轮真实对话」。且 `tests/WishfulClaw.ProviderHeaderRegressionTests/Program.cs:57-85` 有 4 条断言钉着它。要不要并入是独立判断，本需求不裹进来。
- **不改协议差异部分** —— `Authorization: Bearer` / `x-api-key` / `anthropic-version` / `Content-Type` 留在各 provider，不进 `ProviderHttpHeaders`。S-171 的类注释已写明「Auth headers stay with the caller」。
- **不给辅助通道加 debug** —— 辅助通道不发 `request_debug` 事件（S-171 已定），本次不为它补。

## 八、验证要求（实施时）

1. `npm run typecheck` 0 错误；`npm test` 全绿（C# 16 套含 `ProviderHeader`）。
2. `ProviderHeader` 套件**不因收敛而改断言**：现有 `AssertHeaders` 系列（8 + 1 + 4 条）必须原样通过 —— 证明行为等价。
