## 二、A：判据（写进 `AGENTS.md` 分层条款）

```
/src/runtime/WishfulClaw.Agent/ 下不得出现 SQL 字面量。
禁止形态："SELECT  "INSERT  "UPDATE  "DELETE  "CREATE TABLE（含 @" / $@" 前缀，
以及 DbService.MultiLine("SELECT …。SQL 只允许出现在 Infrastructure/Db/。
```

**机器复核命令**（大小写敏感，别用 `-match`）：

```
Get-ChildItem -Recurse -File -Path src\runtime\WishfulClaw.Agent -Include *.cs |
  Select-String -CaseSensitive -Pattern '"(SELECT |INSERT INTO |UPDATE [a-z_]+ SET |DELETE FROM |CREATE TABLE |CREATE INDEX )'
```

命中数必须是 **0**。

> 注意第一条：**`-match` / `Select-String` 默认不区分大小写**，会把工具描述里的 `multi-select questions` 当命中（假阳性），同时把真命中混在一起。S-328 §0.1 记的就是这个坑 —— 第一次扫出 32 处，用 `-cmatch` 才是 30 处。

### 3.2 薄化时最容易犯的错

| 错 | 后果 | 怎么防 |
|---|---|---|
| **假设两份 SQL 一样，直接换成调新方法** | 两份很可能**不一样** —— 端点的 `SELECT` 列常比 Agent 层多（带渲染端要的字段）、参数校验逻辑在端点里 | **逐字段 diff**：把两份 SQL 的列清单并排列出来，差异逐条判定「是遗漏还是有意」。有意的差异 ⇒ 新方法加参数，不是删列 |
| 端点里的 `WorkerResponse` 错误码被吞 | 端点约定 `{ ok: false, error: "..." }`，新方法抛异常就变了协议 | 端点**保留自己的 try/catch 与错误组装**，只把「查/写」那一句换掉 |
| 一次性改 34 个 | 一个行为回归要翻 34 个文件 | **按表分组 commit**，每组跑一遍该表的真机路径 |
| 忘记改完再复扫 | §二 的命中数必须回到 0，但 Db 层新增的方法也可能漏写 | 收尾跑一次全仓：`src/runtime/` 全目录按表名扫 SQL 字面量，每张表只许**一处** |

### 3.3 分批可以是「未做完就停」

S-328 §三 第 3 步允许分批：**端点暂时不动也不影响正确性**。但停下来的必须：

1. 在 `plan.md` 写明「哪张表的端点还没薄化」
2. 在本单 §五 剩余项表里登记
3. **不能默默留着** —— 默默留着就等于「同一份 SQL 存在两处」这个事实没人知道

### 6.3 逐字段 diff 结论（§3.2 第 1 条的工时在这）

**判定为「等价」才换**，四处一致：

1. `tasks` INSERT —— 端点 14 列、`DbTaskStore.Insert` 14 列，**列序完全相同**，只是参数别名不同（`@sid` vs `@sessionId`）。可空列端点写 `(object?)x ?? DBNull.Value`，`DbService.Param` 内部已做同样处理。
2. `tasks` UPDATE —— 端点 9 列、`UpdateRow` 9 列完全相同（含 `updated_at` 不在 WHERE、不含 `session_id`/`plan_id`/`sort_order`/`created_at`）。
3. `plans` INSERT —— 端点 9 列、`DbPlanStore.Insert` 9 列完全相同，三处 NULL 处理也一致。
4. `messages` `ReadRows` —— `role is null && !paged` 分支与 `ListForRestore(db, sid, null)` 逐字节等价。

**判定为「有意差异」明确保留**（写进代码注释，不是遗漏）：

| 处 | 为什么不合并 |
|---|---|
| `DbTaskTools.Update` 的 `SELECT * FROM tasks WHERE id = @id` | 端点入参只有 `id`，而 `DbTaskStore.GetById(db, taskId, sessionId)` **强制**带 session 过滤（任务 id 是模型给的，不当键信任）。合并就得给 Store 加一个不带 session 过滤的重载，等于把 S-328 立的防线拆掉 |
| `DbPlanTools.List` 的 `SELECT * FROM plans ORDER BY updated_at DESC` | 全表列表，`DbPlanStore` 五方法里没有「全部计划」这个语义，加进去只是把 SQL 搬一次、没有消重对象 |
| `DbPlanTools.Update` 的 UPDATE（含 `file_path` / `content` / `spec_json`） | `DbPlanStore.UpdateStatus` **刻意**只改 title + status + updated_at（正文创建时写一次、状态流转从不重发，全行更新会把库里正文覆盖成调用方手里那份）。端点这条路是给「用户改计划正文」用的，两者不是同一件事 |
