### 5.4 分档取值口径

官方对 8 个模型按 token 数分档（Grok 4.7/4.6 的 200K、GPT 6 Luna 与 GPT 5.6 Luna 的 272K、Claude Haiku 5.5 的 100K、Qwen3.7 Plus 的 256K），DeepSeek 四款按**时段**分档（Peak / Off-Peak）。

我方 `inputPrice` / `outputPrice` / `cacheHitPrice` 是**单值字段**，装不下一组。**裁定（老大 2026-10-08 09:42）**：一律取**最高档**。

- token 分档 ⇒ 取高上下文档（如 Grok 4.7 取 >200K 的 4 / 12 / 1）
- 时段分档 ⇒ 取 Peak 档（如 DeepSeek V4 Pro 取 1.32 / 3.96 / 0.044）

既有惯例与此一致（`qwen3.7-plus` 原就取 >256K 档），本次把 `gpt-5.6-luna` 从低档对齐到高档。

## 六、代价与取舍

**核心风险：改了 preset，已物化（已启用 / 已填 key）的 OpenCode Go 用户拿不到新清单。**

机制同 S-170：`provider-materialization.ts` 的 `reconcileProviders` **原样保留已持久化记录**，preset 改动只在 `isUnownedBuiltin` 为真的记录上经 `resetProviderToPreset` 生效。

⇒

- **未启用过的用户** ⇒ 打开 AI 服务商管理页时退回投影 ⇒ **拿到 31 条新清单** ✓
- **已启用 OpenCode Go 的用户** ⇒ 记录保留 ⇒ **仍是 27 条旧清单**（且 `ox-alpha-free` 这类已下线的模型仍会列在界面上）✗

**裁定：不写迁移代码。** 与 S-170 一致 —— 已配置用户不管，只改内置虚拟投影。

**单值价格必然失真**：分档模型取高档 ⇒ 成本估算**偏保守（偏贵）**。这是单值字段的固有代价，本次不引入分档数据结构。

## 八、待验证点

**`shared.thinkingConfig` 里的 `thinking` 字段对所有模型是否都会被 Go 网关拒。**

v9 的 GLM 修正基于一个实测事实：Go 网关是 Go 写的 OpenAI 兼容层，严格解码，**不认 `thinking` 字段** —— 开着思考时注入 `{ thinking: { type: 'enabled' } }` 直接 HTTP 400 `json: unknown field "thinking"`。

但 `shared` 至今仍带这个字段，被 **kimi 系 / mimo 系 / longcat 系 / hy3 / hy4-preview / space-bunny / deepseek 系 / minimax 系 / qwen 系** 全部继承（GLM 四款是唯一例外）。本次新增的 4 条（`mimo-v2.6-flash` / `mimo-v2.6-pro` / `hy4-preview` / `space-bunny`）同样继承。

**两种可能**，本次无法区分，需实测：

1. 网关对所有模型统一严格解码 ⇒ 这些模型开思考**都会 400**（v9 只修了老大当时用的 GLM，问题面比想象大）
2. 网关按模型路由到不同上游、字段透传策略不同 ⇒ 只有 GLM 那条路径严格

⇒ 真机验证时**用 `space-bunny` 或 `hy4-preview` 开思考发一轮**，看是否 400。若复现，单开一条需求统一处理 `shared`。
