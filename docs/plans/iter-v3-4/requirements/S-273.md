## 一、为什么要单开一条

S-272 的第二段（相对坐标 + 网格 + 窗口枚举）能把误差从「几百像素」压到「几十像素」，但**压不到零**。整条链路上有两段天生不可控：

1. **模型看到的图不是原图** —— 各家 API 都会对输入图做缩放（长边上限 1568 / 2048 不等），模型数的像素与 PNG 像素没有固定比例。
2. **视觉定位本身有误差** —— 一个 24×24 的图标，在缩过的图上只占 8 个像素，模型报的坐标落在图标外是常态。

而 UI Automation 把这两个问题**同时消掉**：元素的位置由操作系统直接给出，精确到像素，不需要任何视觉估计。

## 二、可行性（已核）

| 事实 | 依据 |
|---|---|
| Chromium / Electron 会把 DOM 的可访问性树暴露给 Windows UIA | Chromium 的 accessibility 子系统（`--force-renderer-accessibility` 或检测到 AT 客户端时自动开启） |
| Electron 有开关 | `app.setAccessibilitySupportEnabled(true)` —— 需要核实我们的主进程是否已开 |
| .NET 侧可用 | `System.Windows.Automation`（托管，老 API）或 `CsWin32` 直接调 `IUIAutomation` COM |
| 我们自己的页面完全可点 | 按钮 / 输入框 / 列表项在 Electron 里都有 `ControlType` + `Name`，`InvokePattern` 或 `SetFocus` + 坐标点击都能用 |

**关键约束**：第三方原生应用（微信、QQ、老式 Win32 程序）的 UIA 覆盖度参差 —— 有的只有窗口级，有的连窗口都拿不到。所以本条**只作为增强路径**，不能替代 S-272 的坐标路径。

## 三、方案

**新增 `DesktopQueryElements`（读）**

输入：`window`（标题关键字，可选）、`maxDepth`（默认 6）、`filter`（可选：`ControlType` 名单）。
输出：元素树，每项 `{ name, controlType, automationId, rect, enabled, patterns: ['Invoke','Value','Toggle'] }`，`rect` 标注坐标系（物理像素，与 S-272 对齐）。

**扩展 `DesktopClick`（写）**

新增可选形态：
```
DesktopClick({ window: "Wishful Claw", element: "发送" })
DesktopClick({ window: "Wishful Claw", element: "发送", controlType: "Button", index: 0 })
```
不传 `x`/`y` 时走「查元素 → 取 `rect` 中心 → 原有鼠标点击」。**不做** `InvokePattern` 直接调用（绕过鼠标会漏掉 hover 态、hover 才出现的菜单；点击坐标更接近真实用户）。

**扩展 `DesktopType`**

新增 `element` 参数：先 `SetFocus` 到该元素再输入。免掉「先点一下输入框」这一步。

**失败要明确**

元素找不到 ⇒ `isError: true`，报文里列出**最接近的 N 个元素名**（编辑距离），让模型一次改对，而不是反复试坐标。

## 四、待查（开工前）

1. 我们的主进程有没有 `app.setAccessibilitySupportEnabled(true)`；没开的话，开了对内存 / 性能的影响（Chromium 开启 A11y 会构建完整树）。
2. Electron 里 DOM 节点到 UIA 元素的 `Name` 映射：`aria-label` / 文本内容 / `title` 哪个优先 —— 决定模型该用什么词找按钮。
3. `IUIAutomation` 在 .NET AOT 下的 COM 互操作可行性（项目是 AOT 发布，`System.Windows.Automation` 依赖 WPF 程序集，未必能用；可能必须走 `CsWin32`）。
4. 混合 DPI 下 `IUIAutomationElement.CurrentBoundingRectangle` 给的是物理像素还是被虚拟化的值 —— 与 S-272 的坐标系必须对齐，否则又是一次坐标系混用。

## 五、判据

1. 我们自己的窗口：`DesktopQueryElements` 能列出聊天输入框、发送按钮、左侧栏会话项的名字与矩形。
2. `DesktopClick({ window, element })` 一次点中，**不需要**先截图。
3. 元素不存在时 `isError: true` 且报文含候选名（不返回假成功 —— 这是 S-267 / S-268 的同一底线）。
4. 第三方应用（微信 / 记事本）能找到窗口级元素；找不到时明确说「该应用不提供可访问性信息，请改用坐标点击」。
5. 不支持 UIA 的进程上，`x`/`y` 老路径行为完全不变。

## 六、不做的事

- 不替代 S-272 —— 两条路径并存，由模型自己选。
- 不做「视觉元素检测」（在截图上跑 OCR / 目标检测）—— 那是另一个量级的工作，且解决不了精度。
- 不碰 `DesktopScreenshot` 的返回格式。

## 八、卡住待拍板（v3-iter-5 刀 8）

**停在这里，不实施。** 原方案（`DesktopQueryElements` 走 `IUIAutomation`）撞上两个硬约束：

1. 待查 3 —— AOT 手写 COM vtable，风险与收益倒挂；
2. 待查 2 —— 为了让我们自己的窗口可查就得开全局可访问性，而这正是上一个迭代花整轮压下去的内存问题。

而且**原始诉求的场景本来就不需要 UIA**：老大提这条的原话是「让 dev 实例点自己的页面进行测试」—— 那是**我们自己的 Electron 窗口**，而自家窗口有一条精准得多、零 AOT 风险的路：主进程已经拿得到 `webContents`，挂 CDP 取 `Accessibility.getFullAXTree` 就是操作系统级的精确矩形，不用开全局 a11y 开关（`Accessibility.enable` 按需触发）。

**两个候选方案的对比（待老大拍板，不自行决定）**

| | 段 A：自家窗口走 CDP AXTree | 段 B：第三方应用 |
|---|---|---|
| 做法 | 主进程 `webContents.debugger` → `Accessibility.getFullAXTree`，元素名与矩形直接来自 Chromium | 先 `EnumChildWindows` + `GetWindowText`（Win32 控件级），UIA 全量留后 |
| 覆盖 | 只有我们自己（以及任何 Electron/Chromium 窗口） | 记事本这类 Win32 控件有效；微信/UWP 基本拿不到 |
| 成本 | 纯 TS，一个 IPC 方法，零 C# 改动 | 纯 TS，与 `desktop-screenshot.ts` 同一处落地 |
| 风险 | `debugger.attach` 与 DevTools 冲突（同时只能一个客户端）；需真机验证按需开 a11y 树 | 枚举深度与元素数量在上千级，要限深度和条数 |

**需要老大定的三件事**：

1. S-273 是否按上述拆成段 A / 段 B —— 还是干脆**砍掉**，承认 S-272 的相对坐标 + 网格 + 窗口枚举已经把「点自己的页面」压到够用。
2. 若做段 A：接受「只覆盖 Chromium 系窗口」这个边界吗（第三方应用仍走坐标）。
3. 若做段 B：`EnumChildWindows` 拿到的中文控件名在 Electron 窗口里是空的，要不要为此**同时**开 `setAccessibilitySupportEnabled` —— 即是否愿意付出待查 2 的内存代价。

## 九、AOT 到底撞的是什么（v3-iter-5 补刀，实测定性）

§八 把「AOT 下不可用」当结论写下了，但那句话**不够具体**，不能作为方案依据。这一节把它测到底。

### 9.1 三样硬事实

**① 打包版真的走 NativeAOT** —— 不是「配置里写了 AOT」这种推断：

| 证据 | 值 |
|---|---|
| `resources/worker/` 目录 | 共 3 项：`WishfulClaw.Worker.exe` 23 578 112 B、`e_sqlite3.dll` 1 978 880 B、`codegraph-worker/` |
| 托管 DLL 数量 | **0**（唯一的 dll 是原生 sqlite） |
| 判据 | self-contained 非 AOT 会产出上百个托管 DLL；单 exe + 零托管 DLL ⇒ 确认 ILC 产物 |

**② 编译配置**：

- `src/runtime/WishfulClaw.Worker/WishfulClaw.Worker.csproj`：`net11.0`、`PublishAot true`（:12）、`StripSymbols true`、`IlcOptimizationPreference Speed`、`JsonSerializerIsReflectionEnabledByDefault false`
- `scripts/publish-aot-worker.mjs:43-47`：`dotnet publish ... -c Release -r win-x64 --self-contained true -o resources/worker`
- `src/runtime/global.json`：SDK 钉 `11.0.100-preview.7.26381.103`
- **没有** `TrimMode` / `IlcArg` 自定义 —— 即用的是 `PublishAot` 隐含的全量剪裁默认值

**③ 报错原文**（探针 `.wishful-claw/notes/aot-probe/`，不进仓）

三层实测，每层都是**真跑**出来的：

| 层 | 做法 | 结果 |
|---|---|---|
| L1 | `PublishAot=true` + `UseWPF=true` | build 阶段即失败：`error NETSDK1168: 启用剪裁时，不支持或不推荐使用 WPF。`（`Microsoft.NET.RuntimeIdentifierInference.targets(309,5)`） |
| L2 | 去掉 `UseWPF`，改 `<FrameworkReference Include="Microsoft.WindowsDesktop.App" />` | build 通过；**publish 时 ILC 崩**：`System.NotSupportedException: error : C++/CLI is not supported: '...\microsoft.windowsdesktop.app.runtime.win-x64\11.0.0-preview.7.26381.103\runtimes\win-x64\lib\net11.0\DirectWriteForwarder.dll'`，挂在 `Code generation failed for method '[PresentationCore]ModuleInitializer.Initialize()'` 上，收尾 `error MSB3073`（ilc 退出码 1）。另有 `UIAutomationTypes` / `UIAutomationClient` 各一条 `warning IL2104` |
| L3 | 不引框架，按 `HintPath` 单引 `UIAutomationClient.dll` + `UIAutomationTypes.dll` | **publish 成功**（只剩两条 `IL2104`）；但 **exe 一跑就崩**：`System.InvalidProgramException: Non-blittable parameter types are invalid for UnmanagedCallersOnly methods.`（`Internal.Runtime.TypeLoaderExceptionHelper`），退出码 `-1073740791` |

### 9.2 定性 —— 不是三选一里的任何一个

§四 待查 3 和 §八 猜的是「`System.Windows.Automation` 在 AOT 下不可用」；老大问的是「是 UIA 不可用，还是 `ComWrappers` / COM interop 被 trimming 掉，还是 `Marshal.GetTypeFromCLSID` 被裁」。

**实测答案：三个都不是。**

| 猜测 | 实测 |
|---|---|
| `System.Windows.Automation` 本身 AOT 不可用 | 不准确。L3 证明**能编过**，编译期不拦它 |
| `ComWrappers` / COM interop 被 trimming 掉 | 不是。`IL2104` 只是剪裁**警告**，不是它导致失败 |
| `Marshal.GetTypeFromCLSID` 被裁 | 不是。探针里根本没用它，照样炸 |

真因是两条**独立的**、都在编译器/运行时能力边界上：

1. **WindowsDesktop 框架整体不可 AOT** —— 拦路的是 `PresentationCore` 里的 `DirectWriteForwarder.dll`，一个 **C++/CLI 混合程序集**，ILC 明确不支持（`C++/CLI is not supported`）。所以只要引整个 `Microsoft.WindowsDesktop.App`，`ModuleInitializer` 一跑就死。
2. **就算把框架剥到只剩两个 UIA 托管 DLL 骗过 ILC，运行时仍然死** —— UIA 内部有带**非 blittable 参数**的 `[UnmanagedCallersOnly]` 方法，AOT 下这种签名非法（`InvalidProgramException`）。

**结论：AOT worker 进程内使用 `System.Windows.Automation`，三条路全断。** 不是配置没调对，是能力边界。调 `TrimMode` / 加 `IlcArg` / 关剪裁都救不了 —— 关剪裁等于放弃 AOT，那是另一个量级的决定。

### 9.3 方案（三条，全都不碰 AOT 配置）

**方案 A —— UIA 走独立 out-of-process 辅助进程（推荐）**

新建 `src/runtime/WishfulClaw.UiaBridge/`，一个**独立的普通 exe**：`PublishAot=false` + `UseWPF=true`，照常 `using System.Windows.Automation`。worker 通过 stdio 传 JSON 进、JSON 出，一问一答。

| 维度 | 说明 |
|---|---|
| 拿得到 | 完整 UIA 树：`Name` / `ControlType` / `AutomationId` / `BoundingRectangle` / `IsEnabled` / 支持的 Pattern（Invoke、Value、Toggle、SelectionItem）；控件级定位与点击 |
| 拿不到 | 无（这是保留度最高的方案） |
| 对现有构建的侵入 | 新增一个 publish 目标 + 一条 `publish-aot-worker.mjs` 之后的拷贝步骤；打包体积涨（self-contained 约 +60~80 MB，可改 framework-dependent 压到几 MB，代价是要求目标机装 .NET 运行时 —— 不可接受，故仍需 self-contained 或做裁剪） |
| 代价 | 多一个进程、多一层 IPC、进程生命周期要管（超时、僵尸进程、并发） |
| 风险 | 低。UIA 跑在非 AOT 进程里是它本来该待的地方，不存在编译或运行时边界问题 |

**方案 B —— 放弃 UIA，用已交付的 `DesktopListWindows` + 截图 + 坐标点击**

不新增任何依赖，零构建侵入。S-272（刀 7）已经给了相对坐标、网格、窗口枚举。

| 维度 | 说明 |
|---|---|
| 拿得到 | 窗口标题、位置、尺寸；截图上的像素级视觉信息 |
| 拿不到 | 窗口内控件树、控件可点击性、控件级精确定位 |
| 对现有构建的侵入 | 零 |
| 代价 | 解决不了原始诉求「它不知道怎么去点击坐标」—— 只能靠视觉猜，猜不准就还是错 |
| 保留度 | 低（窗口级，非控件级） |

**方案 C —— 主进程 TS 侧直接调 COM（不新增进程，也不碰 AOT）**

桌面操作本来就在主进程 TS 侧执行（`native-agent-runtime.ts:147-180`），而主进程是 Electron，**不是 AOT**。用 `koffi` 绑 `UIAutomationCore.dll` 的 `CUIAutomation` COM 接口。

| 维度 | 说明 |
|---|---|
| 拿得到 | 与方案 A 同等的完整 UIA 树 |
| 拿不到 | 无 |
| 对现有构建的侵入 | 新增一个原生模块依赖（`koffi`），Electron 版本升级时要重编 |
| 代价 | TS 侧手写 COM interop 体量大；每个 COM 指针必须手动 `Release`，漏一个就是泄漏 —— 而我们上一轮刚被内存问题折腾过一整轮 |
| 风险 | 中高。原生模块 + 手写 vtable，调试成本高 |

### 9.4 我的建议

**选 A。** 三条里只有 A 同时满足「保留度完整」和「风险确定可控」：UIA 在非 AOT 进程里是它的正常用法，不存在边界问题；代价是确定的一个进程 + 一段 IPC，不是不确定的运行时崩溃。C 的保留度一样但风险高一档，且踩的正是我们刚花整轮压下去的内存泄漏那条线。B 保留度太低，救不了原始诉求。

**但在动手前仍需老大定两件事**（§八 那两条依然有效，现在多了一层背景）：

1. 段 A / 段 B 的拆分要不要保留 —— 自家 Electron 窗口走 CDP `Accessibility.getFullAXTree` 仍然是**最省**的路（纯 TS、零新进程、零 AOT 风险），UIA 只为第三方应用准备。若接受「自家窗口走 CDP、第三方走方案 A」，总成本比纯方案 A 更低。
2. 方案 A 的体积代价（约 +60~80 MB）能不能接受。若不接受，退方案 B。

**本节只做查证，未改一行主仓代码、未改任何 AOT 配置。** 探针工程在 `.wishful-claw/notes/aot-probe/`（已 gitignore），保留供复现。

## 十、段 A 实施结果（v3-iter-4 · 刀 8 · 2026-10-30）

### 10.1 落地路径

| 层 | 文件 | 做什么 |
|---|---|---|
| 纯逻辑 | `src/main/lib/ax-elements.ts`（新） | `collectAxElements` 拉树 + 换算 + 过滤；`CdpSession` 是**注入**的，不 import electron ⇒ 能写回归 |
| 主进程接线 | `src/main/ipc/desktop-elements.ts`（新） | 拿 `getMainWindow()` → `debugger.attach('1.3')` → `DOM.enable` → 拉树 → `finally` detach |
| 分发 | `src/main/ipc/native-agent-runtime.ts` | 桌面方法集合 + `case DESKTOP_QUERY_ELEMENTS` |
| C# 工具 | `AgentRuntimeDesktopExecutor` | `DesktopQueryElements` → 反向请求 `desktop:query:elements`，**整段转发主进程报文**（不重新拼，避免两处口径分叉） |
| 工具定义 | `DesktopToolProvider` | schema：`expect` / `nameFilter` / `roles` / `maxDepth` / `maxElements` |
| 中文名 | `locales/{zh,en}/chat.json` | 「查找界面元素」/「Query Elements」，两处（label + title）各一份 |

### 10.2 `Accessibility.enable` / `disable` 成对

**`disable` 放在 `finally`**，异常路径也收；`disable` 自己失败被 try/catch 吞掉，**不许掩盖原始异常**（否则模型看到的是「disable 失败」而不是「树没拉到」，排查方向直接跑偏）。

回归断言（`tests/desktop-ax-elements`，假 CDP session 记录调用序列）：

| 断言 | 钉住什么 |
|---|---|
| `enable` 恰好一次、`disable` 恰好一次（正常路径） | 不多开不多关 |
| `enable` < `getFullAXTree` < `disable` | 顺序不能乱 |
| 取树抛错时 `disable` 仍被调用一次 | **本条核心**：开了不关会让 Chromium 一直维护完整 a11y 树，正是 v3-iter-4 刚压下去的内存问题 |
| 取树抛 + `disable` 也抛 ⇒ 抛出的是**原始**异常 | disable 不掩盖真因 |
| `disable` 失败但树拿到了 ⇒ 结果照常返回 | 收尾失败不该让数据丢失 |

### 10.3 坐标系与 S-272 的对齐结论

换算链：`DOM.getBoxModel` 的 **CSS 像素（相对视口）** → 除 `zoomFactor` 得 DIP → 加 `getContentBounds()` 原点 → 乘 `scaleFactor` 得**屏幕物理像素**，与 `DesktopClick` / `DesktopScreenshot` 同一套帧。

**对齐到什么程度（如实说，不假装）**：

- 窗口在**主屏**时：与 S-272 完全一致（同一个 `scaleFactor`、同一套 DIP→物理换算）。
- 窗口在**副屏且两块屏缩放不同**时：`getContentBounds()` 是 DIP、乘的是窗口所在那块屏的 `scaleFactor`，而 S-272 的截图参照系用主屏 —— **会有偏差**。这条写进返回报文的 `frameNote`，并在测试里钉住换算公式本身（`scaleFactor=0` / `zoomFactor=0` 退化成 1，不除零）。
- 页面缩放（Ctrl+=）已处理：`zoomFactor` 单独参与换算，否则元素矩形会整体偏小。

### 10.4 只覆盖自家窗口（派单硬约束）

拿不到窗口 / 拿不到 `webContents` / 窗口最小化 / 调试会话已被占用 —— 四种情况全部 `success: false` + 明确报文，**不猜、不降级成假成功**。报文里点名 `DesktopListWindows` + 相对坐标，让模型一次换对路。
