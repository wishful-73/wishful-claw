# S-259：右侧面板跨会话串扰 —— 别人执行工具，当前窗口莫名展开且空白

**性质**：真缺陷。状态被拆成两半、生命周期不一致：**「开没开」是全局单值，「开的是谁的」是 per-session**。

**归属**：v3-iter-3（产品 1.0.3）。编号 **S-259**。真机验收中发现。

**状态**：**已完成 · 真机验收通过**（2026-10-28 17:40，6 改 2 新；17:02 真机六条全过）：判据收口为 `isRightPanelScopeActive`，四个调用点统一问它；新增套件 `tests/right-panel-scope`（19 断言）。实施口径与偏差见 §7。

## 1. 原话 / 来源

> 2026-10-28 16:01 老大：

> 「我在全局会话在沟通，然后全局会话给项目下会话发送了任务，项目下会话在执行过程中需要查看右侧浏览器这些，结果全局会话的右侧面板突然展开了，但是实际什么都没有打开显示，等我点击去项目下会话的时候 反而右侧面板又收起来了。」

三个现象连起来看是一个根因的三个断面：

1. 当前看着 A 会话，**B 会话**执行工具 ⇒ **A 的**右侧面板自己展开；
2. 展开后**空白**，什么内容都没有；
3. 切到 B 会话 ⇒ 面板**反而收起**。

## 2. 机制（2026-10-28 实查，四段代码闭环）

### 2.1 「开没开」是全局单值

`stores/ui-store.ts:134`：`rightPanelOpen: false` —— 一个 **boolean**，整个应用一份，不带 sessionId。

### 2.2 「开的是谁的」是 per-session 作用域

`stores/right-panel-scope.ts:22-28`：tab 的归属桶 = `rightPanelTabScopeId(tab.sessionId)`；`GLOBAL_TAB_SCOPE_ID = 'global'` 是「无会话」桶。

⇒ 同一个面板里，**开关**不分区、**内容**分区。这是矛盾的源头。

### 2.3 B 会话的工具调用能直接改全局开关

`lib/tools/browser-native-ui.ts:92`：

```ts
useUIStore.getState().openBrowserTab(url, ctx.sessionId)
```

→ `ui-store-browser-slice.ts:31-32` → `ensureBrowserTab`（`ui-store.ts:516-568`）：

```ts
const resolvedSessionId = resolveRightPanelSessionId(state, sessionId)  // = B
const tabId = scopedRightPanelTabId('browser', resolvedSessionId)       // tab 记在 B 名下
...
return {
  rightPanelTabs,
  ...activateRightPanelTab(state, resolvedSessionId, tabId),  // 激活项记在 B 桶
  rightPanelOpen: true,                                       // ← 全局开关，不分会话
  ...browserStatePatch
}
```

⇒ **现象 1 成立**：B 的工具调用把 A 屏幕上那个全局 `rightPanelOpen` 掀开了。

同类落点还有 `lib/agent/teams/register.ts:52` 与 `team-native-ui.ts:45`（`ui.setRightPanelOpen(true)`），机制一样。

### 2.4 渲染端只画「当前会话」的 tab ⇒ 空白

`components/layout/RightPanel.tsx:58-61`：

```ts
const panelScopeId = rightPanelTabScopeId(panelSessionId)   // = A（当前在看的）
const scopedTabs = rightPanelTabs.filter((tab) => rightPanelTabScope(tab) === panelScopeId)
```

而面板的开关不参与过滤：`RightPanel.tsx:118` `const activeTab = rightPanelOpen ? selectedTab : undefined`。

⇒ **现象 2 成立**：A 的 scope 里一个 tab 都没有（`scopedTabs = []`），面板却开着 ⇒ 宽度撑开、内容空白。

### 2.5 切会话时无条件收面板 ⇒ 现象 3

`stores/ui-store.ts:179` `prepareSessionSwitch`，其后半段（`:196-213`）：

```ts
return {
  rightPanelOpen: false,          // ← 无条件收起
  rightPanelTabs: browserTabs,    // 只保留 browser tab
  ...
}
```

⇒ **现象 3 成立**：老大切到 B 的瞬间 `prepareSessionSwitch` 跑了一次，把刚被莫名其妙打开的面板收掉。**而且 B 自己的 browser tab 明明在**（`:197` 特意保留了），只是开关被关了 —— 用户得再手动点一次才看得到。

## 3. 根因一句话

**开关是全局的，内容是分区的，而「别人的操作」能改全局开关、却改不动当前视图的内容** —— 于是打开了别人的东西、显示在自己脸上、一片空白，切过去又被切会话逻辑关掉。

## 3.5 附：多会话浏览器并存能力（2026-10-28 16:20 老大追问「同时两个会话都要用浏览器，都能活着吗」）

**能，而且本来就是这么设计的。** 五处证据：

| 机制 | 位置 |
|---|---|
| 每会话一个固定 tab id | `ui-store.ts:522` `scopedRightPanelTabId('browser', sessionId)` |
| 每会话一份 webview ref | `ui-store-browser-slice.ts:37` `browserWebviewRefsBySession[key]` |
| **全部同时挂载**（只切可见性） | `RightPanel.tsx:281-296`，注释原话「不会因为当前会话变化而卸载原会话的 webview」 |
| 工具按会话精确定位 | `browser-webview-helpers.ts:19-21` `getBrowserWebviewRef(ctx.sessionId)` |
| 后台建 tab 不抢 UI | `ui-store.ts:556-561` background 分支 |

⇒ **进程层与 ref 层早已 per-session；真正共享的只有存储层**（`partition` 全局一份）。所以「两个会话同时跑浏览器工具」不会互相踩 webview —— 会踩的是 **cookie / localStorage**（同一 partition）。存储隔离是独立话题，见 §4.4 与 S-260 §8。

同一条能力边界下还有 S-260（常驻上限 2 + 满了告诉 agent）：**上限是资源治理，不是能力阉割** —— 两个会话仍可同时活着，只是不许无限开。

## 4. 定案：通道早就有了，只差一个判断（2026-10-28 16:20 勘测结论）

原先列的 A/B/C 三候选是**在不知道 `background` 通道已存在**的前提下写的。实查之后推翻：**`ensureBrowserTab` 本来就有 background 分支**，agent 侧只是没走它。

### 4.1 证据

`ui-store.ts:556-567`：

```ts
if (options?.background) {
  return { rightPanelTabs, ...browserStatePatch }   // ← 不动 rightPanelOpen
}
return {
  rightPanelTabs,
  ...activateRightPanelTab(state, resolvedSessionId, tabId),
  rightPanelOpen: true,                              // ← 只有非 background 才掀开
  ...browserStatePatch
}
```

而两个调用点分道扬镳：

| 调用点 | 传 background？ | 结果 |
|---|---|---|
| `browser-webview-helpers.ts:105`（`ensureAttachedWebview` 自愈重启） | ✅ `{ background: true }` | 正确，注释写明「without stealing the UI」 |
| **`browser-native-ui.ts:92`（`executeBrowserNavigate` 的 goto）** | ❌ **没传** | 掀开全局开关 ⇒ 现象 1、2 |

`browser-native-ui.ts:91` 的原注释是「Reveal the browser panel so the user can see the page being loaded」—— **在前台会话里这是对的**（用户就该看见它导航），在后台会话里就变成了「抢别人的屏」。

### 4.2 修法

判据不用新写，`browser-session-helpers.ts` 有现成的 `isActiveBrowserScope(state, scope)`：

```ts
const state = useUIStore.getState()
const scope = resolvePanelScope(state, ctx.sessionId)
const foreground = isActiveBrowserScope(state, scope)
state.openBrowserTab(url, ctx.sessionId, undefined, foreground ? undefined : { background: true })
```

**前台照旧掀开（保持原体验），后台静默建 tab。** 零新机制、零状态迁移、零 UI 改动。

> ⚠️ **实施时没有照抄上面这段**：`isActiveBrowserScope` 用的是 `getBrowserScopeKey`（sessionId **+ projectId** 两维），而 tab 归属桶只看 sessionId —— 判据与桶不同源会出新坑。实际改为在 `right-panel-scope.ts` 新写 `isRightPanelScopeActive`，理由见 §7.1。

### 4.3 同源的第二处：团队面板

`rightPanelOpen: true` 在 agent 侧还有两个调用点，机制一模一样：

| 位置 | 触发 | 是否同一根因 |
|---|---|---|
| `lib/agent/teams/register.ts:52` | `team_start` 事件 ⇒ `setRightPanelOpen(true)` + `setRightPanelTab('team')` | ✅ 是。后台会话起团队，当前会话的面板被掀开 |
| `lib/agent/teams/team-native-ui.ts:45` | `snapshot` 且 `openPanel === true` | ✅ 是 |

老大这次报的是浏览器，但这两处会让「后台会话起团队」也出现同样的抢屏。**一并修**（判据同一个函数），改法一致。

⚠️ `register.ts:47` 的 `sessionId` 会 fallback 到 `activeSessionId`（`event.sessionId ?? activeSessionId`）—— 即「没有 sessionId 时按当前会话算」，这种情况应视为**前台**，不能因为拿不到 id 就静默。

### 4.4 剩下两条候选怎么处理

| 原方案 | 处置 |
|---|---|
| **A. 开关也按 scope 存** | **排 v3-iter-4**。这才是根治（开关与内容同源），但 `rightPanelOpen` 有持久化（`ui-store.ts:126` `rightOpen`），改 map 要处理存量迁移，收尾阶段不动 |
| **C. 无 tab 自动收起** | **不做单独的兜底**。它是「治标 + 掩盖」：用户看不出「其实是别人开的」。A 落地后它自然成立（A 之后这种状态不可能出现） |

**`prepareSessionSwitch`（`ui-store.ts:196-213`）的无条件 `rightPanelOpen: false`**：本轮**不动**。它的语义是「切会话收面板」，虽在现象 3 里表现别扭（收掉的是 B 自己 legit 的 tab），但那是**期望问题不是错**，且改它会把「切会话该不该自动展开」这个产品问题一起卷进来 —— 留给 A 一起定。

## 5. 验收

**（需双会话：A = 全局会话，B = 项目下会话）**

1. 看着 A，B 的 agent 调 `BrowserNavigate` goto ⇒ **A 的面板不展开、不闪空白**（现象 1、2 消失）
2. B 的浏览器 tab 照常创建、页面照常加载、后续 `BrowserClick` / `BrowserSnapshot` 等工具照常工作 —— **修的是可见性，不是能力**
3. 切到 B ⇒ B 的 browser tab 存在（现象 3 的「收起来」本轮保留不动，见 §4.4）
4. **在 A 里自己**调浏览器工具 ⇒ 面板照常展开（前台路径不能被锁死）
5. 后台会话起团队 ⇒ 当前会话的 team 面板不被掀开（§4.3 两处）
6. 两个会话各自开过浏览器后来回切 ⇒ 各自看到自己的页面，不串

## 7. 实施记录（2026-10-28 17:40）

### 7.1 判据为什么是新写的，不是复用 `isActiveBrowserScope`

§4.2 当时给的是「把 `isActiveBrowserScope` 塞进 `browser-native-ui.ts` 就完了」。落地时发现两把尺子量的不是同一件事：

| | 作用域由什么决定 | 用在哪 |
|---|---|---|
| `rightPanelTabScopeId`（`right-panel-scope.ts:22`） | **只看 sessionId**，为空落 `'global'` 桶 | tab 归属、激活项、`RightPanel` 的内容过滤 |
| `getBrowserScopeKey(resolvePanelScope(...))` | sessionId **+ projectId** 两维 | 浏览器别名/cookie 别名等存储侧 |

面板开不开，取决于「内容层会不会把那个 tab 画出来」，而内容层用的是**前者**。用后者当判据，会在「同一会话、projectId 一侧拿不到」的边界上判出「你在别的 scope」——面板该掀不掀。**判据必须与桶同源**，所以收口在 `right-panel-scope.ts`，照桶的维度比。

### 7.2 改动清单（6 改 2 新）

| 文件 | 改动 |
|---|---|
| `stores/right-panel-scope.ts` | 新增 `isRightPanelScopeActive(state, sessionId)`：两边都过 `resolveRightPanelSessionId` + `rightPanelTabScopeId` 后比较。注释写明「判据刻意只此一处」 |
| `stores/ui-store.ts` | `ensureBrowserTab` 在 `options.background` 分支**之后**再拦一刀：非当前作用域同样只返回 `{ rightPanelTabs, ...browserStatePatch }` —— 不置 `rightPanelOpen`、不改激活 tab。这样即便调用方忘了传 `background` 也不会抢屏 |
| `lib/tools/browser-native-ui.ts` | 调用本身没改，只换注释：面板掀不掀由 store 判，这一层不要自己再判 |
| `lib/agent/teams/register.ts` | `team_start` 分支：`if (isRightPanelScopeActive(ui, sessionId))` 才 `setRightPanelOpen(true)` + `setRightPanelTab('team')` |
| `lib/agent/teams/team-native-ui.ts` | `record.openPanel === true` 分支同上，同一判据 |
| `package.json` | 新增 `test:right-panel-scope` |
| `tests/right-panel-scope/program.ts` | **新**，19 断言：桶归一 / 前台允许 / 后台拒绝 / 空 sessionId 与空白串按前台 / 全局作用域 / 回落链 / `hasRightPanelTabsInScope` |
| `tests/right-panel-scope/stubs/chat-store.ts` | **新**，真实 chat-store 拉 IPC 与数据库层，Electron 外跑不起来 |

护栏放在 **store** 而不是四个调用点，是这次唯一的设计取舍：调用点会继续长（新工具、新事件），判据只写一遍才不漏 —— 这正是 `right-panel-scope.ts` 文件头注释自己说的那句话。

### 7.3 测试为什么值得单独钉

`isRightPanelScopeActive` 是纯函数、只有两个入参，看着「一眼就对」。但它是**四处的唯一开关**：谁把它改成恒 `true`（比如为了修「前台不展开了」而图省事），四处会同时退化回这个 bug，而 UI 上表现为「偶发空白面板」，几乎不可能靠真机验收稳定复现。所以用断言把边界钉住，包括最容易被顺手优化掉的**空白串必须按前台处理**（`'   '` 若不过 `trim`，会落进 `''` 这个假会话桶）。

### 7.4 明确没做的（沿用 §4.4，未变）

- `prepareSessionSwitch` 的无条件 `rightPanelOpen: false` —— 不动。切到 B 时面板仍会收起（现象 3 保留），这是期望问题，与 A 一起定。
- **A（开关也按 scope 存）** —— 排 v3-iter-4。它才是根治，但 `rightPanelOpen` 有持久化键 `rightOpen`，改 map 要处理存量迁移，收尾阶段不动。
- **C（无 tab 自动收起）** —— 不做兜底。A 落地后这种状态不可能出现。

### 7.5 早退分支**刻意不激活 tab**（2026-10-28 dev 第四轮追问后的定性）

dev 指出：`ensureBrowserTab` 的非当前作用域分支只写了 `rightPanelTabs` 与 browser 状态，**没调 `activateRightPanelTab`** ⇒ 用户切过去时，`RightPanel.tsx` 的 `?? tabs[0]` 会回落到第一个 tab，刚被 agent 打开的那个浏览器 tab 在、但没被选中。问这是漏写还是刻意。

**是刻意，不是漏写。** 取舍如下：

- `rightPanelActiveTabIds` 是 per-scope 的，写进去**不影响当前视图**（用户此刻在别的会话），所以技术上随手就能加上；
- 但它会覆盖**用户在那个会话里自己选过的 tab**。用户在 B 里手动切到任务面板，B 的 agent 后台导航一次就被弹回浏览器 —— 一次两次能忍，连着跑十次就是「面板自己乱跳」，正是本条要消灭的那类体验；
- 代价是可以接受的：切到 B 时浏览器 tab 明明在 tab 栏上（新建的那个），点一下就到位。

要「切过去自动选中刚打开的那个」，就得另加状态区分「用户选的激活项」与「agent 想要的激活项」，为这点收益加一个字段不值当。**所以 `ui-store.ts:576` 上面已补注释写明这个取舍**，免得下一个人当成漏写又「修」回去。

### 7.7 真机验收通过（2026-10-28 17:02）

§5 六条全部通过。**六条里最关键的是第 1 条与第 6 条**：前者是这条需求存在的理由（B 在后台跑浏览器工具，A 的面板纹丝不动），后者是它不能矫枉过正的反向约束（A 自己用浏览器要照常展开）—— 只验前者会把「全局锁死不展开」误判成修好了。

§7.5 那个「刻意不激活 tab」的取舍，真机确认可接受：切到 B 时浏览器 tab 在 tab 栏上，点一下到位。

**这条的经验**：登记时给的三条候选（A 开关按 scope 存 / B 加事件通道 / C 只在调用点判断）**全部作废**，因为 `options.background` 通道本来就存在、只是没人传。教训不是「勘测不够」，而是**先搜「有没有现成的」，再设计「该加什么」** —— 这条需求如果不先翻 `ui-store.ts:556-567`，光按登记的三选一会写出一整套新机制。
