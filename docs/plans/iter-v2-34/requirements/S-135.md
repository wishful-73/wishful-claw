# S-135 · 流式渲染降级：渲染量过大时主动降频

- 2026-09-22：**老大提出**（原话：「点击后过了几分钟，页面渲染直接卡住了，然后过来一会儿 停止生效了」→「不是子代理的停止按钮，就是主会话上的停止按钮，感觉是渲染本身卡住了，或者被执行占用了 导致停止按钮的事件没有及时到」→「没有出现未响应，但是页面上所有的都像是截图了一样不动了」→「『工具执行快、模型快 ⇒ 渲染量大 ⇒ 卡住』，幸福的烦恼 这个能想个办法么，比如，发现同时要渲染的东西太多了，那么就暂停一些不重要的进行中渲染。至少不能给人一种卡住了的感觉」→ 13:46「可以 立吧」）。

**现象（老大真机实测）**：任务跑得快（工具快 + 模型快）⇒ 单位时间渲染量过大 ⇒ **整页像截图一样静止**；主会话「停止」按钮点下去要几分钟才生效。**系统未报「未响应」** ⇒ 不是崩溃，是渲染队列堵死。

**定性（老大）**：「幸福的烦恼」—— 快是真快，问题是别让人以为卡死了。底线：**不能给人一种卡住了的感觉**。

**现状勘测（2026-09-22）**：

- `src/main/ipc/agent-stream-handler.ts` **全文 17 行**，C# worker 的 `agent/stream` 事件**原样逐条广播**给所有渲染窗口（`agent:stream`），**零聚合、零节流、零背压**。
- 全仓无自适应批处理设施：`*batch*` / `*throttle*` / `*adaptive*` 只命中 `session-todo-batch.ts` 与 `components/chat/MessageList/VirtualListContent.tsx`，**与流事件无关**。

**参考实现（OpenCowork `src/main/ipc/adaptive-event-batcher.ts`，实测 853 行）**：

- 配置：`foregroundFlushMs: 33`（约 30fps）、`backgroundFlushMs: 150`、`maxBufferSize: 200`、`idleTimeoutMs: 200`。
- 按 `runId` 维护累加器，聚合 `textDelta` / `thinkingDelta` / `toolArgsDelta`，控制类事件走 `pendingControl` 直通；`AGGREGATABLE_EVENT_TYPES` 白名单决定哪些事件可合批。
- **前台 / 后台两档刷新率** —— 窗口失焦或退到后台时降频，把主线程让给真正需要即时反馈的场景。
