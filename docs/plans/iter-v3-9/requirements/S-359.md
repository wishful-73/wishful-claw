### 2.1 第二层：服务商选对了，模型还是停用的

修掉服务商层之后，默认落到 `xiaomi-coding`（小米套餐，`provider.enabled = true`），但模型仍不对（11:20 实测）：

```jsonc

// provider-xiaomi-coding.json 的 models
```

根子换到了 `pickDefaultModel`：

```ts
provider.models.find((m) => m.id === provider.defaultModel) ??   // ← 第一档不看 enabled
provider.models.find((m) => m.enabled && ...) ??
provider.models.find((m) => m.enabled) ??

```

`mimo-v2.5-pro` 正是 preset 的 `defaultModel`，第一档直接命中 —— **用户把 preset 默认模型关掉，每次启动都被拨回来**。同一症状下沉一层：服务商对了，模型还是停用的。

## 3. 代码链路

### 3.1 引入点（v1.0.8 之前没有这段）

`7fc9647a` 在 `ensureBuiltinPresets()` 里新增：

```ts
const activeExists = (id) => !!id && nextProviders.some((p) => p.id === id)
if (!activeExists(activeId) && nextProviders.length > 0) {
  const picked =
    nextProviders.find((p) => p.requiresApiKey === false || !!p.apiKey) ?? nextProviders[0]
  updates.activeProviderId = picked.id
}
```

**diff 原文**：`provider-store-helpers.ts` 删掉旧的 `const activeId = updates.activeProviderId ?? state.activeProviderId`，换成 `let activeId = state.activeProviderId`。旧逻辑只有一条兜底 —— 无 active 时取 `providers[0]`（openai）。**几十个版本都没有这条挑选，所以「以前一直没有」成立。**

### 3.2 为什么必然落到 Ollama

| 环节 | 事实 |
|---|---|
| 内置投影默认值 | `provider-materialization.ts:64` `enabled: preset.defaultEnabled ?? false` —— **所有内置初始都是 false** |
| Ollama 免 key | `stores/providers/ollama.ts:18` `requiresApiKey: false` |
| 数组顺序 | `stores/providers/index.ts:43-` openai → anthropic → google → deepseek → openrouter → **ollama（第 6 位）**；前五家没 key 就到它 |
| 判定 | `requiresApiKey === false` 命中 ⇒ `find` 停在 Ollama |
| 写盘 | 选中结果落进 `index.json`，下次启动 `activeExists` 恒 true ⇒ **再也不重挑，永久钉死** |

### 3.3 判据分裂（这才是根）

**横幅侧本来就是对的**（`components/chat/InputArea/use-input-area-selectors.ts:218-225`）：

```ts
// "no usable configured provider exists at all" ... scan every enabled provider
s.providers.some((p) => p.enabled && (p.requiresApiKey === false || !!p.apiKey))
```

**store 侧五处全不看 `enabled`**：

| 位置 | 用途 |
|---|---|
| `provider-store-helpers.ts:238` | 启动时拨正悬空 `activeProviderId`（**今回中招点**） |
| `provider-store.ts:45` | `getActiveProvider()` 运行时回落 |
| `provider-store.ts:84` | `deleteProvider` 先塞 `providers[0]` |
| `provider-store.ts:89-92` | `deleteProvider` 再用「免 key 或有 key」覆盖 |
| `provider-store.ts:39` | `if (!activeProviderId) return providers[0]` |

⇒ 横幅说「你有五家能用的，不提示」，store 却塞给它一个停用的 Ollama。**两套标准在同一个仓库里打架。**

## 4. 根因

**判据搬错了场景。** `requiresApiKey === false || !!apiKey` 原本是 `deleteProvider` 的补救（`e0dc4ae3`：删掉当前服务商后别显示过期的「无 key」横幅），语义是「找一家能发请求的」。`7fc9647a` 把它复制到**启动迁移**时没有重新审：

- `enabled` = 用户的启用意图，是**硬门槛**，不是加分项；
- `requiresApiKey === false` 只说明「不用填 key」，**不说明「能用」**（本地推理要进程在跑、要拉过模型）。

## 5. 修复方向

**统一成一份判据，放在纯模块里**（`provider-materialization.ts`，可被 plain-node 测试直接覆盖）：

```ts
export function isProviderUsable(p) {
  if (!p || p.enabled !== true) return false
  if ((p.authMode ?? 'apiKey') !== 'apiKey') return false
  if (!(p.requiresApiKey === false || (p.apiKey ?? '').trim().length > 0)) return false
  return p.models.some((m) => m.enabled)          // 模型层也是硬门槛
}

export function pickDefaultModel(p) {
  return (
    p.models.find((m) => m.id === p.defaultModel && m.enabled) ??       // defaultModel 只是提示
    p.models.find((m) => m.enabled && (!m.category || m.category === 'chat')) ??
    p.models.find((m) => m.enabled)
    // 没有 models[0] 兜底：一个都没启用就返回 undefined
  )
}

export function pickActiveProvider(providers) {
  return providers.find(isProviderUsable) ?? null
}

export function resolveActiveProvider(providers, currentActiveId) {
  // 当前可用 ⇒ 不动；否则重挑；一家都没启用 ⇒ 返回 null
}
```

- **`enabled` 在服务商层和模型层都是硬门槛**，先筛再挑，不做分级降级。
- **`defaultModel` 降级为提示值**：只在该模型 `enabled` 时才采用。用户关掉它，就不能被拨回来。
- **空集合 = 不选**：`activeProviderId = null`。`send-model-resolution.ts:72` 已有 `if (!provider) return null`，调用方吃得下；横幅（判据同上）会亮「未配置 API Key，点击此处打开设置」。**不需要新造空状态。**

### 5.1 迁移是必须的（光改判据不够）

老盘里 `activeProviderId` 已经指着 Ollama，`activeExists` 恒真 ⇒ 改完判据也不会重挑。所以 `resolveActiveProvider` 把「存在」升级成「存在 **且可用**」：**悬空 / 停用 / 无凭据 / 无启用模型，任一都不算有效**。

`activeModelId` 同样要迁移：它可能指向 provider 里已停用的模型（本次小米套餐就是）。`ensureBuiltinPresets` 里改为「当前模型不存在 **或未启用** ⇒ 重挑」，而不是只在为空时才补。

## 6. 代价与取舍

| 代价 | 为什么可接受 |
|---|---|
| 用户停用正在用的服务商后，active 会自动换一家（或置空） | 停用了本来就不该继续在用；旧行为是「继续指着停用的那家，直到发请求失败」 |
| 首次安装（全部 `enabled: false`）⇒ 不选任何服务商 | 这正是要的：横幅引导配置，而不是塞一个必失败的服务商。`getActiveProvider()` 的调用方都已处理 `null` |
| 一处判据改了七处调用面 | 流动性最大的是 `getActiveProvider` / `isProviderAvailableForModelSelection`（9 处 UI 引用）。判据统一后它们行为只会更严，不会放宽 |
| 服务商下所有模型都停用时，它不再被自动选中 | 选中了也发不出去；这与「服务商停用时不选」是同一条原则下沉一层 |
| `activeModelId` 指向的模型被停用后会重挑 | 否则每次启动都被 `defaultModel` 拨回停用模型 —— 正是 11:20 实测的小米套餐症状 |

## 7. 刻意不做

- **不按模型「数量」过滤，但按模型「启用状态」过滤**：`models.length > 0` 不是判据（Ollama 拉到模型之前列表为空是正常的）；`models.some(m => m.enabled)` 才是 —— 这正是 11:20 老大指出的第二层。
- **不动 `isProviderAuthReady`**：它不含 `enabled` 的语义仍被 `ProviderModelsSection` 用（判断「这个 provider 的 key 填了没」），不能合并。
- **不改 `addCustomProvider` 的 `activeProviderId ?? provider.id`**：新建的自定义服务商本身就是 `enabled: true`，不在本次病灶上。
- **不动 `activeFastProviderId` / `activeImageProviderId` 等平行字段**：本次只报 active provider；同类问题若出现另开单。
- **不补真实渠道调用**（钉钉 / Discord 等）—— 与 S-352 线无关。
