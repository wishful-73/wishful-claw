# S-294 · 桌面截图 / 窗口截图的卡片点开后应是图片预览，而不是 JSON

> 状态：**✅ 已实施（2026-10-31 13:5x），待真机验收**
> 登记：2026-10-31 13:2x
> 来源：老大真机测试原话「还有窗口截图和桌面截图都没用图片预览，卡片输出的内容毫无营养，我希望卡片点开后是图片预览」
> 拍板：2026-10-31 13:36 老大「先修吧」⇒ 本迭代做

## 一、现象

| 工具 | 卡片点开后看到什么 | 应该看到什么 |
|---|---|---|
| `DesktopScreenshot`（桌面截图） | 极简档下基本是空的 / 或裸 JSON | **图片预览** |
| `CaptureAppWindow`（窗口截图） | **纯 JSON 文本**，一张图都没有 | **图片预览** |

老大 2026-10-29 还报过一次更早的形态：「极简档展开这张卡，只看到『输入 `{"require_active_window": false}`』」—— 那次修了（见 §三.3），但**图还是没出来**。

## 二、根因（两条，各自独立）

### 2.1 窗口截图压根没路由到图片卡片

`src/renderer/src/components/chat/AssistantMessage/tool-block-renderer.tsx:321-328` 的路由 if：

```tsx
if (
  block.name === DESKTOP_SCREENSHOT_TOOL_NAME ||
  block.name === DESKTOP_LIST_WINDOWS_TOOL_NAME ||
  block.name === DESKTOP_CLICK_TOOL_NAME ||
  block.name === DESKTOP_TYPE_TOOL_NAME ||
  block.name === DESKTOP_SCROLL_TOOL_NAME ||
  block.name === DESKTOP_WAIT_TOOL_NAME
) { ... <DesktopActionToolCard ... /> }
```

**`CaptureAppWindow` 不在这 6 个里面**，于是掉进通用 `ToolCallCard` ⇒ 输出按 JSON 文本渲染。

全仓核对：`CaptureAppWindow` 只出现在两处渲染端文件里 ——
- `locales/zh/chat.json:661` / `locales/en/chat.json:661`（只是工具名翻译「窗口截图」）
- 无任何路由 / 卡片引用

**而它返回的内容形状和 `DesktopScreenshot` 一模一样**：`AgentRuntimeDesktopExecutor.Encoding.cs:174` 的 `CreateAppWindowCaptureContent` 同样产出 `[{type:'image', source:{base64, filePath}}, {type:'text', text}]`。**数据是现成的，只是没人接。**

### 2.2 桌面截图的图片区只在 `output` 是数组时才出现 —— **已实测确认根因**

老大补充现象（2026-10-31 13:3x）：「桌面截图卡片右侧显示的是 `?x?`，点开卡片折叠内容屁都没有」。

**这两个症状是同一个判据的两个后果。** `src/renderer/src/components/chat/DesktopActionToolCard.tsx:99-108`：

```tsx
const { images, notes } = useMemo(() => {
  if (!Array.isArray(output)) {
    return { images: [] as ImageBlock[], notes: [] as TextBlock[] }
  }
  ...
}, [output])
```

- `?x?` ← `:119-120` 的 `notes[0]?.text.match(/(\d+)x(\d+)/)`，`notes` 空 ⇒ 回落 `'?'`
- 点开空白 ← `images` 空 ⇒ `:253` 的图片区整块不渲染

**实测证据（dev 库 `message_parts`，2026-10-31 13:3x 查）**：

```
toolName=DesktopScreenshot  typeof output = string
前 160 字: [{"type":"image","source":{"type":"base64","mediaType":"image/png",
           "filePath":"D:\\claw\\wishful-claw\\s268-test-no-ext.png"}},
           {"type":"text","text":"Captured d...
```

**`output` 在库里存的是 JSON 字符串，内容是数组的序列化形式。** 所以：

1. `Array.isArray(output)` === `false`
2. ⇒ `images` / `notes` 双空
3. ⇒ `?x?` + 点开空白

**不是数据丢了，是没人 parse。** 注意字符串里的 `source` 已经没有 `data` 字段、只剩 `filePath` —— 这是 S-284 剥 base64 的预期行为，渲染端本来就该走 `resolveImageBlockSource` 从 `filePath` 取图。

> ⚠️ 该会话是老格式（`messages.meta` 里 `segments: 0 段`），`output` 来自 `message_parts` 的 tool_use payload。**新格式同样如此** —— parts 的 payload 里 `output` 本身就是 string（同批 `Bash` / `Read` 的 output 也都是 string）。**这是全工具一致的形状，不是截图特例。**

### 2.3 顺带记一下：input JSON 已经收进详情档了

同文件 `:113-114`：

```tsx
const { density } = useDensityPolicy()
const showRawInput = density === 'detail'
```

这是 2026-10-29 那次反馈的修法。**极简 / 紧凑档不会再显示原始入参** —— 老大这次说的「内容毫无营养」，指的应该是 §2.1 那个走通用卡片的窗口截图，以及 §2.2 图片区没出来的桌面截图。

## 三、修法（方向，不是结论）

1. **窗口截图补路由**（确定要做，成本极低）：把 `CaptureAppWindow` 加进 `tool-block-renderer.tsx:321-328` 那个 if。
   - 注意 `DesktopActionToolCard` 内部的 `summary` 分支（`:116-140`）是按工具名分派的，`CaptureAppWindow` 需要补一个分支，否则标题行会走 fallback。
   - ~~i18n 键 `toolCall.desktop.screenshot.names.CaptureAppWindow` 已存在~~ —— **订正（实施时查证）**：没有这个键，`toolCall.desktop` 下只有 7 个工具的 `title`。真正存在的是 **`permission.toolLabels.CaptureAppWindow`**（zh「窗口截图」/ en「Capture Window」），`resolveToolDisplayName` 走的就是它，所以标题行靠 `defaultValue` 兜底即可，**不用补 title 键**。详见 §7.3。
   - 老大原话「紧凑模式下都还是纯文本 没有卡片」⇒ 这条**在紧凑档同样成立**，不是极简档专属。
2. **`output` 字符串化**（已确认，§2.2）：在 `DesktopActionToolCard` 里对字符串 output 做一次结构化解析再判数组。
   - **复用现成解码器，不要写第三份 parse**。`lib/tools/tool-result-format.ts:36 decodeStructuredToolResult(text)` 正是干这个的，且 `:57-59 isStructuredToolResult` **认数组**（`Array.isArray(value) || ...`）⇒ 截图那种 `[{type:'image'},{type:'text'}]` 能被它原样解出来。
   - **不能用裸 `JSON.parse`**：`toolResultFormat` 设置项可切 `toon`（`:15 getCurrentToolResultFormat`），此时 output 是 TOON 字符串，`JSON.parse` 直接抛。`decodeStructuredToolResult` 两条路都试（`:41` JSON → `:48` TOON），是唯一正确入口。
   - 判据放宽后 `images` / `notes` / `jsonOutput` 三处同时受益 —— `?x?` 一并修好。
   - ⚠️ 顺带要看的：`DesktopActionToolCard` 自己的 `parseStructuredOutput` 是不是和 `decodeStructuredToolResult` 重复。**若重复，这轮统一到后者**，别留两个入口（S-276「四处判据各写各的」就是前车之鉴）。
3. **卡片主体顺序**：老大要的是「点开 = 图片预览」。当前顺序是 图片 → 原始入参（仅详情档）→ JSON 输出 → 文字备注。图片已经排第一，符合诉求；剩下的问题是它**根本没渲染出来**（§2.1 / §2.2），不是顺序问题。

### 7.2 判据为什么抽成纯函数 + 解码器注入

`DesktopActionToolCard` 里的 `useMemo` 是组件内部逻辑，测不了。抽成 `splitDesktopToolBlocks(output, decode)` 就能钉死。

**解码器做成参数而不是直接 import**：`tool-result-format.ts:9` 顶部 import 了 `useSettingsStore`（zustand），一旦被纯函数 import，node 里就 import 不了这个模块，回归测试只能退化成「测判据、测不到真实形状」—— 这正是 S-276 踩过的坑（`trimMessagesToRecentTurns` 从 store 搬到 `turn-window.ts` 就是同一个原因）。

生产侧传 `decodeStructuredToolResult`（JSON / TOON 两条路都试），测试侧传裸 `JSON.parse` 包装。**裸 `JSON.parse` 绝不能当生产解码器** —— 设置项 `toolResultFormat='toon'` 时 output 是 TOON 字符串，裸 parse 直接抛。

### 7.3 `CaptureAppWindow` 为什么不进 `AppPluginToolName`

后端 `AgentRuntimeDesktopExecutor.cs:22-26` 的注释写明：它借用桌面 transport 只是因为「主体是本应用自己的窗口」，**它不在桌面控制插件的 `toolNames` 里**（`types.ts:102-108` 只有 6 个）。所以它不是 app-plugin 工具，只给渲染层当路由判据。

`permission.toolLabels.CaptureAppWindow` = 「窗口截图」**早就存在**（zh/en 都有），所以标题行走 `resolveToolDisplayName` 兜底就能出中文，**不用补 `toolCall.desktop.CaptureAppWindow.title`**。

### 7.4 极简档为什么仍然是一行

`PROCESS_LINE_CARD_ONLY_TOOL_NAMES`（`tool-block-renderer.tsx:54-60`）里**桌面截图故意不在**，这是 2026-10-29 15:46 老大定的口径：「极简模式还是个卡片，卡片内容对我来说没什么意义」。`CaptureAppWindow` 同样不加 —— 极简档一行「窗口截图」，紧凑 / 详情档才出卡片。

老大这次报的是「**紧凑模式下**都还是纯文本」，所以本次修的是紧凑档起的行为，**没有推翻 10-29 那条极简档口径**。
