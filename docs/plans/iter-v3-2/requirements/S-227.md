# S-227：官网「它能干什么」板块改为 banner 切换（去掉 tab）

## 1. 原话 / 来源

> 2026-10-26 10:12 老大：

> 登记一个官网需求，这个也是放入下一个迭代。就是当前「它能干什么」板块改成 banner 方式切换，而不是现在 tab —— 实际上又加了 banner 切换的方式。

性质：**官网侧交互重构**，零软件改动，可单独发。

## 2. 现状（2026-10-26 实查 `website/src/sections/features.tsx`）

### 2.1 布局

左侧 `176px` 竖排 tab 列表（宽屏 `lg:grid-cols-[minmax(0,176px)_minmax(0,1fr)]`），
窄屏退化为横向滚动 tab；右侧 `role="tabpanel"` 只渲染**当前一条**（描述 + 真机截图占位）。

面板比例 `PANEL_ASPECT = '2520 / 1608'`，与真机截图同比例，切换时不跳高。

### 2.2 三种切换方式已并存

点击 tab、hover 切换（`HOVER_DELAY_MS = 90` 防抖）、自动轮播（`AUTOPLAY_MS = 3500`）。

轮播三个刹车：鼠标在区块内 / 键盘焦点在区块内 / 区块不在视口（IntersectionObserver `threshold: 0.4`）；
`prefers-reduced-motion: reduce` 时不自转。

### 2.3 键盘支持

roving tabindex（选中项 `tabIndex=0`，其余 `-1`）+ 方向键上下/左右移动焦点。

### 2.4 历史约束（文件头注释，2026-09-23 老大原话）

1. 画面要占满整行（排三列细节全糊）
2. 九条竖排会把区块撑到六千像素 ⇒ 用选项卡
3. 要自动轮播
4. 要 hover 切换且点击保留

条目数：`features.items` 共 **8 条**（2026-10-26 复核订正 —— 原文写「9 条」是沿用 2026-09-23 的口径，
当时含「桌面控制」一条，后于 `site.ts:225` 删除，实际只剩 8 条）。

## 3. 需求意图（2026-10-26 10:14 老大拍板：取 A · 替换）

| 方案 | 判断 |
|---|---|
| **A · 替换** | ✅ 已定：左侧 tab 列表**整个去掉**，板块只剩 banner 切换（大图 / 大卡片滑动），tab 不再对外可见 |
| B · 并存 | ❌ 否决：tab 保留 + 另加一层 banner 轮播 |
| C · 换皮 | ❌ 否决：左列表改成 banner 式大卡片，切换方式不动 |

> 否决 B / C 的理由：目标形态只保留**一种**切换 UI，不做 tab 与 banner 并存的两套。
> 因此 `features.tsx` 里的 `role="tablist" / tab / tabpanel` 语义与左侧 `176px` 栏都要一并拆掉，
> 不是在其上叠加。hover 切换随 tab 删除**自然消失**（文案已定，不再问）。

## 4. 形态定稿（2026-10-26 17:08 老大拍板）

**目标形态 = 电商首页那种单张大图 + 标题浮层叠在图上。**

| 项 | 定稿 |
|---|---|
| 形态 | 单张全宽大图，标题 + 描述做成浮层叠在图上（不额外占高） |
| 自动轮播 | **保留 3.5s**，现有三个刹车（鼠标在区块内 / 键盘焦点在区块内 / 不在视口）直接搬 |
| 8 条怎么组织 | **不分组，一屏一条，靠轮播看全** —— 分页会把高度撑起来，撞 2026-09-23 那条「别撑到六千像素」 |
| 箭头 / 指示点 | **都有**：左右箭头 hover 才出现；指示点常驻底部 |
| 375px 窄屏 | **图缩到整宽，文字挪到图下方** —— 2520×1608 缩到 375 宽细节不可辨，浮层会糊成一坨 |

**hover 切换随 tab 删除自然消失**（不再作为输入源）。

## 5. 风险

1. **高度膨胀**：banner 单条全宽 + 8 条内容，比现在「单面板 + 小 tab」更容易把板块拉长，
   与 2026-09-23 那条「别撑到六千像素」的约束冲突。
2. **输入源打架**：banner 会有箭头 / 指示点 / 手势 / 自动轮播多套输入，共存时必须定优先级 ——
   手动操作要先抢过自动轮播并**重置计时**，否则用户刚点到第 5 张，3.5s 一到就被翻走。
3. **无障碍退化**：现有 `tablist / tab / tabpanel` 语义是完整的；改成 carousel 要换成
   `aria-roledescription="carousel"` + `aria-live` 控制，**不能只换视觉不管语义**，
   否则键盘和读屏用户拿不到当前是第几张。
4. **首屏性能**：现在只渲染当前一条的图；banner 若预载多张 2520×1608 真机图会明显拖慢首屏。
5. **与 S-221 的联动**：右侧悬浮导航锚点指向 `#features`，板块结构调整后要确认锚点仍准。

## 6. 代价与取舍

**这一节是防止后人当 bug 修回去的。**

| 取舍 | 牺牲了什么 | 为什么认 |
|---|---|---|
| **hover 切换彻底消失** | 原来鼠标扫过左侧 tab 就换面板，现在是「点箭头 / 点指示点 / 等轮播」 | tab 拆掉后没有任何可 hover 的落点；在 banner 上做 hover 切页是反直觉的（鼠标一飘过就翻页，比 tab 更难控制）。老大 10:14 取「A · 替换」时就接受了这个 |
| **`aria-live` 不启用**，改用「活动 slide 的 `aria-label` + 其余 `aria-hidden`」静默切换 | 需求 §5.3 原本写「`aria-roledescription="carousel"` + `aria-live` 控制」；读屏用户不会被告知「第 3 张到了」，要自己 Tab 进容器再按方向键 | 8 条 × 3.5s 自动轮播会把读屏搅成连续播报，比不播报更糟。**这是对需求原文的偏离，记在这里，不藏着** |
| **竖版 `wechat.png`（1226×1263）被 `object-cover` 裁掉上下** | 舞台钉死 2520/1608 才不跳高，竖图在横框里只能露中间一条，微信对话的头尾看不到 | 8 张里只有这 1 张竖版。为它单开 `object-contain` 会在左右各留 38% 底色，比裁切更难看 |
| **页面净增约 +90px**（1440 视口估算） | 单面板 780px → banner 870px | 指示点那一行 + 图区无 tab 栏的差价。占「别撑到六千像素」预算约 1.5%，可接受 |
| **点击箭头 / 指示点后焦点留在按钮上** | 键盘用户按 Tab 会从那个按钮继续走，而不是回到容器 | 保留浏览器默认焦点行为，不自作主张 `blur()` |

## 7. 刻意不做

- **不改 `site.ts` 的条目文案** —— 文案归 S-205 那一轨，本轮只动渲染。
- **不分组、不分页** —— 分页会多出一行页签、把区块撑高，撞 2026-09-23 那条「别撑到六千像素」。
- **不预载全部 8 张图** —— 合计约 1.2 MB，首屏只加载第 1 张，第 2 张在进入视口 1.5s 后预取。
- **不引第三方轮播库**（swiper / embla）—— 整站零依赖是既有约定（现有交互全是手写）。
- **不做手势拖动** —— 触屏靠箭头与指示点，拖动要处理阈值、回弹、与轮播抢事件，本迭代不值这个复杂度。
- **不改其它板块交互** —— advantages / quick-start / faq / value-ladder 一律不动。
- **不动 `section-rail.tsx` 的锚点逻辑** —— 它只吃 `#features` 是否存在，板块内部结构怎么改都不影响。
- **不改下载页 / 指引页** —— 它们没有 features 板块。
