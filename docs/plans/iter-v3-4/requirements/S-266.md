## 一、为什么 S-264 之后还有漏的

S-264 把判据换成「按真实签名判」，四档分流落地后，`foo.png` 里装 html / 半截数据 /
非图像内容这批被拦住了。但签名判据有一处天生够不着：

**签名位于文件开头，而截断发生在文件末尾。**

下载到一半的截图、被中断的保存、拷贝到一半的 U 盘文件 —— 头 8 字节完全合法
（`\x89PNG\r\n\x1a\n` 该在的位置一个字节不差），于是：

| 关卡 | 结果 |
|---|---|
| 档 4「签名认不出」 | **放行** —— 签名明明是合法的 |
| 档 2「扩展名骗人」 | 无需纠正（扩展名和内容一致） |
| 档 3「白名单」 | **放行** —— png 本来就在白名单 |
| 档 1 | **内联 base64 送上游** ⇒ 400 `invalid image` |

然后那个坏块留在历史里，每轮请求重发一次。**和 S-246 是同一个现场**，
只是触发条件从「格式不收」换成了「数据不全」。

老大说的「脏图」，在 S-264 里被定义成「文件头不符合任何已知格式」；
本条要补的是另一半：「**头符合，但身体没长全**」。

## 二、判据为什么不能用「解码试试」

最直觉的方案是「能解码就是好图，解不了就是脏图」。不采用，理由与 `ImageFileProbe`
类注释 `:12-14` 记的同一条：为这件事引入完整解码器不划算。

| 格式 | 真解码要什么 | 代价 |
|---|---|---|
| PNG | inflate（zlib）+ 逐行反滤波 | 一套 DEFLATE 实现 |
| JPEG | 熵解码（Huffman）+ 反量化 + IDCT | 一套 JPEG 解码器 |
| GIF | LZW | 另一套 |
| WebP | VP8 / VP8L | 再来一套 |

AOT 体积和攻击面都远超「别把坏图发上去」这个需求的量级。

## 三、定案：只看容器尾部结束标记

关键事实：**这四种容器都在文件末尾有一个固定的结束标记**，而截断恰恰会把它切掉。
所以只用常数级 I/O 就能抓住绝大多数截断 —— 读头几十字节 + 读尾 64 字节，不解码。

| 格式 | 结束标记 | 判据 | 之后容忍追加 |
|---|---|---|---|
| PNG | IEND 块（12 字节定值 `00 00 00 00 IEND AE 42 60 82`） | 尾部窗口内命中 | 16 字节 |
| JPEG | EOI（`FF D9`） | 尾部窗口内命中 | 32 字节 |
| GIF | trailer（`0x3B`） | 尾部窗口内命中 | 2 字节 |
| WebP | RIFF 头声明的长度（偏移 4，uint32 LE） | `8 + declared <= 文件长度` | 不适用 |
| BMP / TIFF / ICO | —— | **不判（返回完整）** | —— |

三处设计说明：

1. **从后往前找最后一个命中**：压缩数据里可能恰好出现同样的字节序列，只有最后一个才是真标记。
2. **容忍尾部追加**：某些相机 / 编辑器会在标记后追加私有数据。PNG 留 16 字节、JPEG 留 32 字节
   （缩略图 / 水印 / MPF 最常见）、GIF 收紧到 2 字节 —— GIF 的 trailer 是**单字节**，
   容忍放宽就会撞上压缩数据里的普通 `0x3B`，那是白白放过脏图。
3. **BMP / TIFF / ICO 不判**：它们本来就不内联像素（档 3 处理），坏不坏都不影响 wire。

代价不对称，所以宁可宽松也不要误杀：**漏检**的代价是上游 400 一次（S-262 会告知自愈），
**误杀**的代价是模型彻底看不到一张好图。

## 四、交付内容

| 层 | 位置 | 改动 |
|---|---|---|
| 探测层 | `ImageFileProbe.HasCompleteContainer` | 新增，四种容器尾部校验 |
| 工具层 | `FileReadTool.ReadImage` | 新增**第五档**：容器不完整 ⇒ `IsError: true`，不产生 image 块 |
| 测试 | `WishfulClaw.ReadImageRegressionTests` | +30 断言；新增真 PNG 编码器（stored deflate + CRC32 + Adler-32） |

第五档排在「超限」之后、内联之前：超过内联上限的图无论完整与否都不会出门，
报「太大」比报「坏了」更有行动指引（让用户重新给一张小的）。

**判定失败时不抛异常**：`HasCompleteContainer` 读不到文件就返回 `true`（不拦）。
这一层是「别把明显的坏图发上去」，不是安全边界；判定本身出错时，
上游 400 仍有 S-261 / S-262 的自愈与告知兜底。

## 五、判据（验收）

1. **截断即失败**：完整 PNG 砍掉末尾 12 字节 IEND ⇒ `IsError: true`，无 image 块，
   文案含 `end marker is missing`。
2. **不与「认不出」混淆**：同一文件的失败文案**不含** `signature not recognized` ——
   它是「头好身体不全」，不是「认不出这是什么」。
3. **头可读不足以放行**：该截断文件 `TryReadSize` 仍返回 `24x12`（这正是它以前能溜过去的原因）。
4. **JPEG / GIF 同判**：砍掉 EOI / trailer 同样判失败、同样无 image 块。
5. **0 字节即失败**：空文件不得以任何形式放行。
6. **完整的不许误伤**：完整 PNG / GIF / WebP 照常内联。
7. **尾部追加不误伤**：IEND 后补 8 字节私有数据仍算完整、仍内联。
8. **既有行为不回归**：S-246（bmp / ico 文本降级）、S-236（非 vision 模型照常附图）、
   超限降级、文本路径、文件不存在 —— 原断言全部不变。

## 七、与其它需求的关系

- **S-264**：签名判据与四档分流**原样保留**，本条是它的第五档，不替代、不修改前四档。
- **S-246**：白名单闸不动。本条新增的失败档排在白名单之后，bmp / ico 仍走各自既有分支。
- **S-236**：非 vision 模型照常附图的行为不变 —— 本条只按「文件是否完整」判，不看模型能力。
- **S-261 / S-262**：本层拦不住的情况（尾窗口内恰好撞上标记字节）仍由它们兜底，
  两层的职责不重叠。

## 八、不做的事

- **不做图像解码 / 转码**（理由见 §二）。
- **不做全文件 CRC 校验**：PNG 每个 chunk 都有 CRC32，全量算能检出「长度对但内容坏」，
  但那是 O(文件大小) 且要先走完 chunk 链；截断已经占了现场的绝大多数，先解决它。
- **不把失败降级成「只回路径」**：截断的图本来就没有可用像素。让模型以为「看过但没收获」
  比直接说「这张图是坏的，去重新弄一张」更糟。
