> 归属：**本迭代**（v3-iter-4，刀 **10**）｜登记 2026-10-29 13:56｜14:03 老大拍板「这些需要进本迭代」，当天下午交付
> **状态：已交付 · 刀 10（`9e593749`）+ 补正（`eb1817ac`）+ 补正之二（`7212dbc5`）· `test:tool-labels-coverage` 12/12 · 待真机验收。**
> 交付口径：中文表最终 **124 条**（TS 侧 61 + C# 侧 62，zh/en 对齐）、统一出口 `lib/tools/tool-display-name.ts`、渲染点七个（含输入框状态栏）、闸扫两侧常量反查表。
> 来源：老大 2026-10-29 13:56 原话 —— 「我们的工具一开始大部分都是从 OpenCowork 迁移过来的，在聊天窗显示的时候能看到工具对应的中文，是搜索或者读取，但是我们后续其实处理了很多的新工具，这些工具都是直接显示英文名称，看着就不舒服，很多用户也看不懂」。

## 一、现象

同一个聊天窗里两种观感混在一起：

| 工具 | 现在显示 | 用户感受 |
| --- | --- | --- |
| `Read` / `Grep` / `Glob` | 读取文件 / 搜索文件内容 / 查找文件 | 正常 |
| `BrowserNavigate` / `DesktopClick` / `codegraph_explore` | **原文英文** | 「看不懂」「像命令行」 |
| `create_goal` / `get_goal` / `RequestSandboxElevation` | **原文英文** | 同上 |

⇒ 越是后续新做的功能（浏览器、桌面控制、代码图谱、目标、沙箱授权），越像半成品。

## 二、根因（已核，两层）

### 2.1 中文标签表停在迁移期那批

`src/renderer/src/locales/zh/chat.json:612` 的 `permission.toolLabels` **只有 23 项**，清一色是 OpenCowork 带过来的老工具：

```
Read Write Edit Bash LS Glob Grep Delete Skill
TodoTaskCreate / Get / Update / List
TaskCreate / Get / Update / List
memory_hot_read / memory_hot_write / memory_search / memory_append / memory_update
discover_tools
```

之后每个迭代新增的工具（浏览器全家、桌面全家、codegraph 全家、目标全家、`AskUserQuestion`、`SubmitPlanReview`、`Notify`、`RequestSandboxElevation`、`PowerShell`、`WebFetch`、`WebSearch`、`ImageGenerate`、`visualize_show_widget`、`SaveImage`、`NotebookEdit`、`SavePlan`、`use_capability`、`CronRuns`、`SubAgentStatus` ……）**一个都没补**。

### 2.2 缺了不会报错，所以一直没人发现

`ToolCallCard/index.tsx:160-166`：

```ts
isMcpTool(name)
  ? formatMcpToolDisplayName(name)
  : t(`permission.toolLabels.${name}`, { defaultValue: name })
```

`defaultValue: name` —— key 不存在就静默回退成英文原名。**没有告警、没有兜底文案、没有测试**，于是「漏登记」这件事永远沉默。

⇒ 这不是某次忘了一条，是**机制上就没有防漏**。

## 四、方案（建议三件一起做，缺一件就还会漏）

### 4.1 补齐已知工具的中文标签

按族分组补进 `zh/chat.json` 与 `en/chat.json` 的 `permission.toolLabels`：

| 族 | 例子（中文） |
| --- | --- |
| 文件 | `NotebookEdit` 编辑笔记本、`SavePlan` 保存计划 |
| 命令 | `PowerShell` 执行 PowerShell 命令 |
| 网页 | `WebFetch` 读取网页、`WebSearch` 搜索网页 |
| 浏览器 | `BrowserNavigate` 打开网址、`BrowserGetContent` 读取页面内容、`BrowserClick` 点击页面、`BrowserType` 输入文本、`BrowserScroll` 滚动页面、`BrowserScreenshot` 页面截图、`BrowserSnapshot` 页面快照、`BrowserSetDevice` 切换设备 |
| 桌面 | `DesktopScreenshot` 桌面截图、`DesktopClick` 桌面点击、`DesktopType` 桌面输入、`DesktopScroll` 桌面滚动、`DesktopWait` 等待、`CaptureAppWindow` 窗口截图 |
| 代码图谱 | `codegraph_explore` 代码图谱探索 …… |
| 目标 | `create_goal` 新建目标、`get_goal` 查看目标、`update_goal` 更新目标、`update_goal_progress` 更新目标进度 |
| 交互 | `AskUserQuestion` 向你确认、`SubmitPlanReview` 提交计划待确认、`Notify` 提醒、`RequestSandboxElevation` 申请关闭沙箱 |
| 其它 | `ImageGenerate` 生成图片、`visualize_show_widget` 生成可视化、`SaveImage` 保存图片、`use_capability` 调用能力、`CronRuns` 定时任务记录、`SubAgentStatus` 子任务状态、`SubAgentDetail` 子任务详情 |

**en 侧同步**（不能留 `BrowserNavigate` 这种 camelCase，改成 `Open URL` / `Desktop click` 之类）。

### 4.2 统一出口 + 兜底

新增一个纯函数（建议 `lib/tools/tool-display-name.ts`）：

```ts
resolveToolDisplayName(name, t): string
```

顺序：① `toolLabels` 命中 → 用它；② `codegraph_*` → 「代码图谱 · <动作>」；③ `mcp__srv__tool` → 现有 `formatMcpToolDisplayName`；④ 插件工具 → manifest 显示名；⑤ **全都不中 → 结构化兜底**（例如 `浏览器工具` / `工具 · <原名>`），**绝不再裸回退英文 camelCase**。

然后把 §3.2 的四处渲染点全部改成走它 —— 这是「补表也治不了」的那半边。

### 4.3 防漏回归（**本条是这条需求的重点**）

新建 `tests/tool-labels-coverage`：

1. 扫描渲染层所有工具名常量与分类集合（`execution-outline.ts` 的 `INTERACTIVE_TOOL_NAMES` / `HIDDEN_TOOL_NAMES` / `FILE_CHANGE_TOOL_NAMES` / `COMMAND_TOOL_NAMES`，`browser-tool-names.ts`、`codesign`… 以及各 `*_TOOL_NAME` 常量）；
2. 断言每个名字在 `zh` 与 `en` 的 `toolLabels` 里都有条目；
3. 断言 `zh` 条目**不含 ASCII 字母开头**（防「Read 文件」这种半中文半英文混排，`PowerShell` 这类专有名词单独白名单）。

⇒ 以后新增工具忘了补中文，`npm test` 直接红。**这条比补 30 个 key 更值钱。**

## 五、不做 / 边界

- **不改工具名本身**：`name` 是协议字段，进请求体、进历史消息，改了模型就不认了。只改显示层。
- **不动 `messages.meta`**：纯显示层改造，历史会话不需要迁移。
- **不追求把插件工具名穷举进表**：走 4.2 的兜底。
- **不动 `tool-call-summary.ts` 的摘要**：那是「这一步干了什么」（查看 xxx 文件），与「工具叫什么」是两件事，本次只治后者。

## 六、验收

1. 聊天窗里 **不再出现裸 camelCase 英文工具名**（浏览器 / 桌面 / codegraph / 目标 / 交互类逐个点开看）。
2. 纯文本档（S-248）的行渲染、文件变更卡标题、浏览器卡、桌面卡、codegraph 卡**五处**都显示中文。
3. `codegraph_explore` 这类带前缀的显示成「代码图谱 · 探索」这种可读形态。
4. MCP 工具与插件工具的显示不回退成 `mcp__xxx__yyy` 原文。
5. 切 `en` 语言时同样不出现 camelCase。
6. `npm test` 含新的 coverage 套件并通过；`npm run typecheck` 0 错。

## 七、需要老大拍的两处

1. **兜底文案口径**：全都不中的工具，是显示「工具 · 原名」还是「未知工具」+ 原名（后者更诚实但更难看）。我建议**「工具 · 原名」**。
2. **`en` 侧要不要也友好化**：现在是 camelCase 原文（`BrowserNavigate`）。我建议**一起改**成 `Open URL` 这类 —— 英文用户看 camelCase 同样难受，而且改一次省得以后再动。

`resolveProxyStatusName()` 的唯一职责是**把 `use_capability` 拆回它代理的真实工具**（`builtin:Read` → `Read`、`mcp-tool:server/tool` → `mcp__server__tool`），给状态面用的。它的注释写得很清楚 —— 状态面要显示「具体是哪个能力」而不是卡片身份 `Skill`。

**但它对非代理工具原样返回**（`if (!isUseCapabilityTool(name)) return name`）。于是：

- 卡片（`ToolCallCard`）、折叠条（`execution-outline`）、文件变更行（`FileChangeCard`）、纯文本行（`ProcessTextLine`）、桌面卡、浏览器卡、codegraph 卡 —— 刀 10 全部接上了 `resolveToolDisplayName`；
- **状态栏这两处没接** ⇒ 平时跑工具时显示的是 `BrowserNavigate`、`FileEdit`、`DesktopScreenshot` 原文。§3.1 / §3.2 的影响面清单当时是按「渲染工具卡的组件」列的，状态栏不在这个心智模型里，所以漏了。

这恰好印证 §2.2 的判断：**缺了不会报错，所以一直没人发现**。防漏测试扫的是「代码里声明的工具名有没有中文表」，扫不到「某个显示点没查表」—— 这是判据的固有盲区。

#### 改法：新出口 `resolveStatusToolName()`，顺序不能反

`src/renderer/src/lib/tools/tool-display-name.ts` 新增：

```ts
export function resolveStatusToolName(name, input, t): string | null {
  const resolved = resolveProxyStatusName(name, input)   // ① 先拆能力代理
  if (!resolved) return null
  if (resolved.startsWith('skill:')) return resolved     // 能力 id，翻不动
  return resolveToolDisplayName(resolved, t)             // ② 再过统一出口
}
```

- **顺序不能反**：先代理再查表。反过来 `use_capability` 会被查成「调用能力」，用户永远看不到真实工具。
- `skill:<id>` 保持原样 —— 它是能力 id 不是工具名，与接这条之前的显示一致（记入挂账，见下）。
- 两个组件里 selector 只取**原始** `name` + `input`（新增 `activeToolInput` / `pendingApprovalToolInput` 两个字段，`!showStatus` 分支同步补 `undefined`），中文名在组件 `useMemo` 里算 —— 因为 `t` 在组件作用域，且能力代理要等 args 到齐。

#### 测试加固（11 → 12 条）

新增两条断言，**直接钉 `resolveStatusToolName`**：

1. `状态栏工具名也走统一出口（非代理工具不再露英文）` —— `Read` → 读取文件、`BrowserNavigate` → 打开网址、`DesktopScreenshot` → 桌面截图、`RequestSandboxElevation` → 申请关闭沙箱、未知工具 → 「工具 · 原名」、`null` → `null`。

#### 挂账

- `skill:<id>` 显示成 `skill:commit`。它不是英文工具名（是能力 id，`commit` 翻不动），但这串冒号分隔的形状在状态栏里也不好看。要做的话得定口径：`技能 · commit`？或者走 `Skill` 标签 + 参数。等老大定。
- 同类风险：以后新增任何「显示当前在跑什么工具」的界面，都必须走 `resolveStatusToolName` / `resolveToolDisplayName`。这条已写进「开发规范 —— 新增工具」那一节（见 §8.7）。
