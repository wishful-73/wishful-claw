# S-178：子 Agent 并发上限的「排队态」不可见 —— 5 个 Task 卡片全显示「工作中」

> 状态：**📝 已登记，待老大裁定**（2026-10-09 11:06）。**根因已实读定位**（见 §三、§四），**未开工、未改一行代码**。归属 iter-v2-38（老大原话「记录一个新的bug」）。
> 本需求是**纯 UI 表达缺陷**：并发限制**实际生效**，但界面无法区分「真在跑」与「在排队」。

## 一、原话 / 来源

老大 2026-10-09 11:06（随 S-176 真机验收一并给出）：

> 「然后记录一个新的bug 就是我本身当前软件设置的是 并行执行2个子agent 实际上你同时运行过5个，状态都是显示工作中，没有等待中，但是只有两个能展开看具体情况，所以我有点错乱，设置并行到底是什么情况」

## 二、现象（拆四句）

1. **设置**：「子 Agent 并发上限」= **2**（`maxConcurrentSubAgents`，UI 默认值也是 2）。
2. **实际**：同屏出现过 **5 个**子 Agent 卡片。
3. **状态**：5 张卡片**全部**显示「工作中」，**没有一张**显示「等待中」。
4. **反差**：**只有 2 个能展开**看具体情况。

⇒ **关键矛盾：卡片说「5 个都在工作」，但只有 2 个有内容可看。** 这条矛盾是定位锚点 —— 它把嫌疑范围锁到「卡片状态与真实执行脱钩」上，而不是「限制器失效」。

> 「5 个」这个数**尚未坐实是「真跑了 5 个」还是「建了 5 张卡」** —— 老大的判据是「看到 5 个卡片」。按 §四 的根因，**后者是必然**。见 §五待确认。

## 三、代码链路（实读）

### 3.1 设置确实一路传到了执行侧（**不是摆设**）

| 环节 | 位置 | 说明 |
|---|---|---|
| UI | `components/settings/RuntimePanel.tsx:434-459` | 「子 Agent 并发上限」，`1~8`，默认 2 |
| 落库 | `stores/settings-store-types.ts` | `DEFAULT_MAX_CONCURRENT_SUB_AGENTS = 2`，`clamp` 到 `1~8` |
| 下发 | `App.tsx:155-161` | 变化时 → `agent/configure-runtime` |
| 接收 | `AgentRuntimeTools.cs:117-120` | `SubAgentConcurrencyLimiter.Configure(...)` |
| 闸门 | `SubAgentConcurrencyLimiter.cs` | 进程级 **FIFO 信号量**，容量 = 设置值 |

三个执行点**都**取闸门：

| 路径 | 位置 |
|---|---|
| 前台 Task | `SubAgentExecutor.cs:138` |
| 后台子 Agent | `SubAgentExecutor.Background.cs:53` |
| Goal 子 Agent | `Goal/GoalSubAgentExecutor.cs:50` |

### 3.2 闸门实现是对的

`SubAgentConcurrencyLimiter.cs`：`_running < _max && _queue.Count == 0` 才放行，否则入 `_queue` 等 `Pump()`。**同时真正在跑的 ≤ 2**。

⇒ 「只有 2 个能展开」**正是限制生效的旁证**（只有拿到 lease 的才有内容流）。

### 3.3 **致命处**：`sub_agent_start` 在闸门**之前**无条件发出

`SubAgentExecutor.cs:74-93`（**顺序即证据**）：

```csharp
// Emit sub_agent_start event to parent's stream
await AgentRuntimeTools.EmitAsync(
    parentState, context,
    new AgentRuntimeStreamEvent("sub_agent_start", ...));   // ← :75-81，先发

if (isBackground) { return await ExecuteBackgroundAsync(...); }        // :83
return await ExecuteForegroundAsync(...);                              // :90
//                                    ↓ 闸门在这之后
// ExecuteForegroundAsync :138  using var concurrencyLease = await SubAgentConcurrencyLimiter.AcquireAsync(...)
```

⇒ 每个 Task 调用**先点亮卡片**，**再去排队**。

### 3.4 渲染端的「Queued」是一整套**死代码**

C# 侧 emit 的子 Agent 事件**全名单**（`SubAgentExecutor.cs` / `SubAgentExecutor.Background.cs` / `SubAgentRunCollector.cs`）：

`sub_agent_start` · `sub_agent_end` · `sub_agent_text_delta` · `sub_agent_thinking_delta` · `sub_agent_thinking_encrypted` · `sub_agent_tool_use_streaming_start` · `sub_agent_tool_use_args_delta` · `sub_agent_tool_use_generated` · `sub_agent_tool_call` · `sub_agent_tool_result_message` · `sub_agent_iteration` · `sub_agent_message_end` · `sub_agent_image_generated` · `sub_agent_image_error` · `sub_agent_report_update`

**没有 `sub_agent_queued`，也没有 `sub_agent_dequeued`。**

而渲染端**早就备好了**这两个事件的完整处理链：

| 位置 | 内容 |
|---|---|
| `lib/agent/sub-agents/types.ts:100,106` | 事件类型定义 |
| `stores/agent-store/slices/sub-agent-slice.ts:52,96` | reducer（置 `isQueued`） |
| `components/chat/SubAgentCard.tsx:257,322,418,449` | `isQueued` 态 + 「Queued」文案 + 琥珀色边框 |
| `components/layout/SubAgentsPanel.tsx:18,66` | 面板内「Queued」状态 |

⇒ **生产端从不发这两个事件 ⇒ 这套 UI 永远不会亮。** 渲染端无从得知谁在排队，5 张卡片只能全停在 `sub_agent_start` 给的「工作中」。

## 四、根因（两句话）

1. **`sub_agent_start` 发早了**：它在取闸门**之前**无条件下发，等于「卡片点亮」≠「真的在跑」。
2. **排队信息从未回传**：C# 侧不发 `sub_agent_queued`/`dequeued`，渲染端那套「等待中」是死代码 ⇒ 排队的 N 个被伪装成「工作中」。

**合起来**：并发限制**真生效**（只跑 2 个），但**界面把「排队」显示成「工作中」**，于是 5 张卡看起来像 5 个都在跑。

## 五、待确认 / 待老大裁定

| # | 问题 | 说明 |
|---|---|---|
| 1 | **「5 个」的口径** | 是「5 张卡片」（UI 谎报，必然）还是「真的并发了 5 个」（限制失效）？判据：当时**有几个在持续输出内容**。若只有 2 个，就是前者。**请老大确认，或给一次复现的卡片数 + 能展开数** |
| 2 | **5 从哪来** | `maxParallelToolCalls`（「最大并行工具数」，**默认 3**）管的是「单轮内并行执行几个工具」，与子 Agent 并发是**两层**。5 个 Task 是否同轮并发发出、是否受 `maxParallelToolCalls` 约束、是否含后台（fire-and-forget）模式 —— **未验证** |
| 3 | **排队态要展示，还是根本不排队？** | 三种产品取向：① 亮出「等待中」（Queued UI 现成）；② 排队卡不建、只在真跑时建卡；③ 干脆超限直接拒绝 |
| 4 | **是否纳入 38** | 38 已在收尾边缘；本条可并入收尾刀，或另起迭代 |

## 六、候选修法（**均未实施，待裁定**）

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲 · 亮出排队态** | C# 在 `AcquireAsync` **前后** emit `sub_agent_queued` / `sub_agent_dequeued`；渲染端那套 UI 直接复用 | 需在 `SubAgentExecutor` 三处执行点各加一对事件；`GoalSubAgentExecutor` 要单独处理 |
| **乙 · `start` 挪到拿到 lease 之后** | 卡片「点亮」即「真在跑」；排队期间不建卡或建为待命 | 会动 `BackgroundSubAgentRegistry.Register` 的时序与后台模式语义（后台是 fire-and-forget，不能等闸门） |
| **丙 · 甲 + 乙** | 排队期间显示「等待中」，拿到 lease 转「工作中」 | 最贴合直觉，工作量最大 |

**助手倾向 丙**，但**乙**对后台模式有语义风险（后台子 Agent 若被闸门挡住，「立即返回」的承诺会破），需先定后台模式的排队期望。

## 七、影响面

- **纯 UI/可观测性缺陷**：不影响任务正确性（限制器工作正常），影响**用户对系统的信任与可控感**（老大原话「我有点错乱」）。
- 连带暴露：`maxParallelToolCalls` 与 `maxConcurrentSubAgents` 两个设置**语义相邻、措辞相近**，容易误解为同一件事。是否需要在 UI 文案上做区分，可在本需求一并考虑。
