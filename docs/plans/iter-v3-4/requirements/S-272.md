# S-272 · 桌面坐标算不出来 —— 截图不给参照系，模型只能对着图瞎猜

> 归属：**跨迭代**。第一段（元数据 + DPI 判定）**本迭代交付**；第二段（相对坐标 / 网格 / 窗口枚举）**移交 v3-iter-5**。
> 登记 2026-10-29 15:53。
> 来源：老大 2026-10-29 15:53「我今天尝试让 dev 实例点击自己的页面进行测试，它先进行了桌面截图，然后后面是点击，最后进行的窗口截图，遇到一个问题就是它不知道怎么去点击坐标」。15:55 补一句「我希望的是做全，如果复杂的话可以先登记，然后下个迭代去推进」。
> 与 **S-268** 同族不同点：S-268 是「工具说成功但其实没做」，本条是「工具说成功了、其实做偏了」—— 报告都是成功，错在坐标。

## 一、现象

dev 实例的一次完整尝试，三步工具调用：

| 步骤 | 工具 | 结果 |
|---|---|---|
| 1 | `DesktopScreenshot` | 成功，返回整屏 PNG |
| 2 | `DesktopClick` | 成功（坐标是猜的） |
| 3 | `CaptureAppWindow` | 成功，返回窗口 PNG |

三步都没报错，但点的地方不对。**它卡住的不是「点了没反应」，是「没有依据去算 x/y」**。

## 二、代码齐证（已核）

| # | 位置 | 事实 |
|---|---|---|
| ① | `AgentRuntimeDesktopExecutor.Encoding.cs:69-99`（`CreateAppWindowCaptureContent`） | 文本只写 `Captured the Wishful Claw window (WxH)` —— **没有窗口在屏幕上的位置**。dev 最后一步拿到的是这张图，可它无从把「窗口内看到的位置」换算成屏幕坐标 |
| ② | `src/main/ipc/desktop-control.ts:145-154` vs `Encoding.cs:54-55` | 主进程**算了** `originX` / `originY` / `displayCount`，C# 编码时只用了 `width` / `height` ⇒ 前两项丢在半路。多屏、负坐标屏时模型不知道这张图对应哪块 |
| ③ | `AgentRuntimeDesktopExecutor.cs:87-111`（`ExecuteScreenshotAsync`） | 请求体是 `CreateJsonObject(_ => { })`，从图里拿不到任何参照（缩放比、显示器清单、光标位置） |
| ④ | `Tools/Providers/DesktopToolProvider.cs:41-42` | 描述写 `Absolute X coordinate` —— **没说是哪个坐标系**。模型看到的是 API 端处理过的图（可能被缩放过），它按眼里的像素报数，天然偏 |
| ⑤ | `src/main/ipc/desktop-control.ts:109-120`（`isPointInsideDesktop`） | 拿 `display.bounds`（**DIP / 逻辑像素**）去校验传入坐标。而 robotjs 的 `SetCursorPos` 要 **物理像素**（Electron 主进程 per-monitor DPI aware）。缩放 150% 的屏、1920×1080 逻辑，物理是 2880×1620 ⇒ 坐标 `(2000, 800)` 完全合法却被判「outside the desktop bounds」直接拒掉。**右半边、下半边点不动** |
| ⑥ | `docs/plans/iter-v2-23/plan-aux-window-placement/plan.md:28` | 项目里**早就写过**这条规矩：「bridge 上报的原生坐标统一标注为 screen-physical；进入 Electron 定位前转 DIP……未直接混用 Windows 物理像素」。⑤ 违反了它，只是当年只约束了辅助窗口那条线 |

⑤ 与「模型算不准」是两回事：前者是硬拦截，后者是精度问题。两者叠在一起，dev 自己分不清是「我算错了」还是「工具拒了」。

## 三、四层原因，层层叠加

1. **没有参照系**（缺 ①②③）—— 画面是活的，但没告诉模型这张图对应屏幕的哪块矩形。
2. **像素不对等**（缺 ④）—— 模型看的图已经被上游缩过，它数的像素不是 PNG 的像素。
3. **搜索空间是整屏**（缺 ⑤ 之外的结构）—— 2560×1440 里找一个按钮，人眼也做不到。
4. **校验层坐标系不一致**（⑤）—— 合法的点被拒，且报错文本让人以为是坐标写错。

## 四、方案分两段

### 第一段 · 本迭代交付（元数据 + 判定修复）

**A. 把坐标系说清楚**

- `captureDesktopScreenshot()` 的返回补 `scaleFactor` + `displays: [{ id, bounds, scaleFactor, primary }]`。
- `CreateScreenshotContent` 的文本行补全，形如：
  `Captured desktop screenshot 2880x1620 (origin 0,0, scale 1.5) across 2 display(s). Click coordinates are pixels in this image.`
- `window:capture-self` 的返回补 `bounds`（`win.getContentBounds()`，DIP）+ `scaleFactor`。
- `CreateAppWindowCaptureContent` 的文本行补窗口矩形，形如：
  `Captured the Wishful Claw window at (320, 180), 1600x900 DIP (scale 1.5, so screen pixels are 2400x1350 from origin 480,270).`
- `DesktopToolProvider` 三个工具的坐标描述改成「以最近一次截图的原点为参照，单位是截图返回的像素」。
- `DesktopScreenshot` 的 `delayMs` 之外**不加参数**（加参数属于第二段）。

**F. 修 ⑤ 的坐标系混用**

`isPointInsideDesktop` 改成按**物理像素**边界校验：优先 `screen.dipToScreenRect(null, display.bounds)`（Electron 43 运行时可用，类型未声明 ⇒ 能力检测）；不可用时按 `bounds × scaleFactor` 回退。报错文本带上边界，方便诊断：
`Coordinate (2000, 800) is outside the desktop bounds (0,0)–(2880,1620).`

**为什么不顺手把 A 做成参数化截图**：本迭代已进入收尾，随机化面越小越好。A 只加字段、只改文案，不动调用形态。

### 第二段 · 移交 v3-iter-5

**B. 相对坐标（根治 ④）**

`DesktopClick({ x: 0.62, y: 0.28 })` —— 0~1 小数表示「在最近一次截图里的相对位置」，主进程按那张图的尺寸换算绝对坐标。图被上游怎么缩放都不影响。整数仍按绝对像素解释，向后兼容。

**C. 截图可选网格**

`DesktopScreenshot({ grid: true })` 在主进程侧往 PNG 上画淡灰网格（每 200px 一条，边缘标刻度）。模型读刻度比目测距离准一个量级。**默认关**，只在实际要点击时开。

**D. 窗口枚举 + 按窗口截图**

- 新增 `DesktopListWindows` → 所有可见顶层窗口的 `title / class / rect`（Win32 `EnumWindows` + `GetWindowRect`，坐标标注物理还是 DIP 要写死）。
- `DesktopScreenshot({ window: "<标题关键字>" })` → 只截该窗口，并回报它的屏幕矩形。

把搜索空间从整屏缩到一个窗口，模型能直接算「窗口原点 + 窗口内偏移」。

## 五、待查（第二段开工前）

1. `screen.dipToScreenRect` 在当前 Electron 版本是否真的存在（`docs/plans/iter-v2-23` 记它「类型未声明、运行时可用」），缺失时 `bounds × scaleFactor` 在**混合 DPI 多屏**下偏多少。
2. `desktopCapturer` 的 `thumbnailSize` 在超高分辨率（4K×2）下会不会被系统截断到上限 —— 若会，截图就不是「物理像素」而是「被压过的物理像素」，B 方案的相对坐标正好能兜住。
3. `capturePage()` 返回的 `getSize()` 到底是 DIP 还是物理像素（需要真机确认，混合 DPI 下两者差 1.5 倍）。
4. `EnumWindows` 在 elevated 进程里的可见性（管理员权限窗口枚举不到普通窗口的反向情况）。

## 六、判据

**第一段（本迭代）**

1. `DesktopScreenshot` 的返回文本含 `origin`、`scale`、`displayCount`，且 origin 与主屏 `bounds.x/y` 一致。
2. 150% 缩放的屏上，坐标 `(width*0.9, height*0.9)`（物理像素）**不再**报 outside。
3. 真越界（超出所有屏并集）仍然拒绝，且报错文本带边界数值。
4. `CaptureAppWindow` 的返回文本含窗口左上角坐标与 DIP/物理两套尺寸。
5. `DesktopScreenshot` 不传任何新参数时，行为与改前**完全一致**（除文本行）。
6. 100% 缩放单屏下，改动前后可点击区域一致（回归：别把校验改松到能点到屏幕外）。

**第二段（下迭代）**

7. 相对坐标：同一张图，`{x:0.5, y:0.5}` 与 `{x: width/2, y: height/2}` 落点相同（容差 2px）。
8. 网格图：启用 `grid` 后，返回图里能找到刻度数字，且原图内容不被遮挡到不可用。
9. 按窗口截图：返回的矩形与 `DesktopListWindows` 里同名窗口的 `rect` 一致。
10. 全链路真机：让 agent 自己「截屏 → 找到聊天输入框 → 点进去 → 输入一句话」，一次成功，不回退重试。

## 七、不做的事

- **不做坐标点击的「自动纠偏」**（点空之后自动在附近重试）—— 会掩盖真实定位错误，而且对用户是意外输入。
- 不改 robotjs 调用方式（`SetCursorPos` 语义就是物理像素，改它要全链路换坐标系）。
- 不与 S-273（UIA）合并 —— 那是「不算坐标」，路径完全不同。
- 第一段**不加** `grid` / `window` / 相对坐标参数，留到第二段。
