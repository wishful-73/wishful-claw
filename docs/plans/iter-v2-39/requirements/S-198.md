## 三、问题

### 3.1 数据层面 —— 链接作废

`src/renderer/src/stores/providers/opencode-go.ts` 的 `homepage` 仍指向 `https://opencode.ai/go?ref=PWHP4P4E29`。

### 3.2 机制层面 —— **就算改了 preset，老用户也看不到**（这才是真 bug）

`reconcileProviders` 的既有口径是「**已物化的内置 provider 记录完全不动**，id 也不动（R-9.2：已物化的用户自己管理）」。而 `homepage` 对内置 provider **恰恰是只读展示字段**：

`src/renderer/src/components/settings/provider/ProviderConfigPanel.tsx`：

- `:126-138` —— `provider.builtinId && provider.homepage` ⇒ 渲染成**链接**（点击走 `shell:openExternal`），**没有输入框**；
- `:146-148` —— 只有**自定义** provider 才渲染 `homepage` 输入框。

⇒ **用户根本改不了这个字段**，但物化记录里存着旧值、且永远不参与重投影 ⇒ **官方一旦换地址，所有已配置过该 provider 的老用户永远看不到新地址**（除非删了重配）。

⇒ 这正是 `provider-materialization.ts:100` 新注释点破的那句：*「`upgradeProviderFromPreset` is dead code, so without this line an official-site link change would never reach users who had already configured the provider.」*

## 五、为什么这么改（取舍）

- **只放开 `homepage` 一个字段，而不是放开整条记录。** R-9.2 那句「已物化的用户自己管理」保护的是 `apiKey` / `baseUrl` / 模型开关等**用户可编辑**字段 —— 那些**绝不能**被 preset 覆盖。`homepage` 是**唯一**同时满足「用户改不了（§3.2）+ 纯展示 + 会随官方变动」三个条件的字段，单独放行它是最小面积的修法。
- **不引入「preset 版本比对」迁移。** 虽然 `version` 已升到 11，但本仓没有「按 version 触发迁移」的机制；本方案改成**每次重投影都刷新 `homepage`**，幂等、零新增状态、零迁移代码。
- **`apiKeyUrl` 不动** —— 它没变，且不在本次口径内。

## 六、影响面与风险

- **影响**：仅**内置** provider 的 `homepage` 显示值。自定义 provider 走后面的 `customProviders` 分支（`:140` 之后），**完全不受影响**。
- **风险**：若某内置 provider 的用户**故意**想保留旧 homepage —— 做不到（UI 不给改，§3.2），所以不存在「覆盖了用户的意愿」这种情况。**无数据风险**（纯显示字段，不落库变更）。
- **与 S-169 的关系**：`S-169.md` §七 已提前记了一句「39 迭代订正」；**本条是那件事的归属登记**，S-169 处加指路引用即可（不改动 S-169 的实质结论）。

## 七、刻意不做

1. **不引入 provider preset 的通用迁移框架**（version 比对 / 迁移脚本）—— 为一个只读字段不值当。
2. **不放开除 `homepage` 外的任何字段**（尤其 `apiKey` / `baseUrl` / 模型开关）—— 那会踩穿 R-9.2。
3. **不在推荐位加「返利披露」** —— 返利已取消，该议题（iter-31 未决项）自然作废，不再做。
4. **不顺手动其它 provider 的 `homepage`** —— 本次只 opencode-go 一家的数据变了。
