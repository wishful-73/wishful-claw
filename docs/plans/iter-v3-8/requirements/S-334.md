## 二、必须先看懂的三个细节（改错了不会编译错，只会行为错）

### 2.1 三条 UPDATE 在**同一个 try** 里 —— 失败是连锁的

```
try {
    UPDATE goal_plans  …   // ① 抛异常
    UPDATE goal_tasks  …   // ② 不执行
    UPDATE goal_execution_runs …  // ③ 不执行
} catch (Exception ex) { ReportFailure(nameof(AbortSubtree), ex); }   // 不重抛
```

方法注释自称 **best-effort**，但实际上**不是各自尽力** —— ① 失败就全停。

抽方法时最容易被「顺手优化」成「三条各自 try / 或包一个事务」，两种都**改变语义**：

| 改法 | 变成什么 | 判定 |
|---|---|---|
| 包一个事务 | 全成或全不成 | **不是新行为，但也不是现状** —— 现状是「可能只更新了 plans」 |
| 三条各自 try | 更尽力（② ③ 会继续） | **也不是现状** |
| 照抄同一个 try | 与现状一致 | ✅ **本单只做这个** |

真心想改成事务，**另开单并单独验证**（S-328 §四已写死不顺便改语义）。

### 2.2 三处条件不一致，**不是笔误**

| 表 | 条件 |
|---|---|
| `goal_plans` | `goal_id` **+ `session_id`** + 状态不在 4 个终态里 |
| `goal_tasks` | `goal_id` **+ `session_id`** + 状态不在 **3** 个终态里（没有 `superseded`） |
| `goal_execution_runs` | **只有 `goal_id`**，无 `session_id`；且条件是 `status = @executing` |

`goal_plans` 的 4 个终态含 `superseded`、`goal_tasks` 的 3 个不含 —— 因为 task 没有 superseded 状态。`execution_runs` 不带 `session_id` 是因为 run 表按 goal 唯一。

**搬的时候逐条照抄，不要抽出「共用 where」。**

### 2.3 状态值来自两个常量类

`GoalPlanStatusValues`（plans / tasks 共用）与 `GoalExecutionAttemptStatusValues`（runs 独用）。抽进 Db 层后这两个引用要么一起搬、要么留在 Agent 层当参数传 —— **后者更好**（Db 层不该依赖 Agent 层的领域枚举）。

## 五、交付形状

```
public static int AbortNonTerminalPlans(DbClient db, string goalId, string sessionId, string abortedStatus, string[] terminalStatuses, long nowMs)
public static int AbortNonTerminalTasks(DbClient db, string goalId, string sessionId, string abortedStatus, string[] terminalStatuses, long nowMs)
public static int MarkExecutingRunsInterrupted(DbClient db, string goalId, string executingStatus, string interruptedStatus, long nowMs)
```

三个方法**各自独立**，连锁语义由 Agent 层那个 try 维持 —— 这样 Db 层不带「谁失败谁不执行」的知识，责任划分才对。返回值是影响行数，方便真机验证时打日志。

### 6.2 一个比登记时更乐观的发现：这块线已经接了一半

§二 说「缺的是把 Entity + Mapper + 连接粘起来的那层」，S-335 / S-328 都是从零补那层。**`goal_*` 不是** —— `DbGoalExecutionRunTools` 早就双形态并存：

```
public static WorkerResponse InsertRun(JsonElement parameters)              // 端点
public static string          InsertRun(string goalId, string? planId, …)   // 表访问   ← 已有
```

`InsertRun(goalId, …)` / `FinishRun(attemptId, …)` 早在 `AbortSubtree` 和 `GoalOrchestratorAdaptive` 里被当函数调用了。所以本单**不是新造出口，是照既有形状补齐剩下三个** —— 比 S-335 那刀还顺手：连「该长什么样」都不用设计，照着 `FinishRun` 抄。

全族里 `goal_*` 是唯一「线接了一半」的地方。S-336 要薄化的正是同一批文件的另一半（端点那半），所以本单做完，`goal_*` 就自然收敛成「端点 + 表访问」双层的标准形。

### 6.3 一个刻意的形状分歧：新方法带 `DbService db` 首参

同文件其余表访问方法（`ListPlans(goalId, sessionId)`、`UpdatePlanStatus(planId, …)`）**不收 db**，内部自己 `DbClient.EnsureInitialized(); var db = DbClient.GetClient();`。

三个新方法反过来收 `db`，理由：

1. 调用点 `AbortSubtree` 第一行就有 `var db = DbClient.GetClient(parameters);` —— 传进去，省一次静态查
2. 与 S-335 / S-328 立的样板一致（首参 `DbService`），后代照哪个抄都不误导
3. 静态全局少一次依赖，测试更好打桩

于是同一个文件里两种形状并存。**这是有意的**，别再统一 —— 把既有的 20 多个方法改成收 db 首参，是本族以外的大重构，`git blame` 全毁、还容易漏参数。

- ⚠️ **订正 §五 交付形状**：`AbortNonTerminalPlans(DbClient db, …)` 里的 `DbClient` 是笔误，实际类型是 **`DbService`**（`DbClient` 是取连接的那个静态类，不是连接本身）。照单据直接抄会编译不过 —— 这个错还算好，编译期就拦住。

### 6.4 终态集合改成参数传（`IReadOnlyList<string>`）

§五 写 `string[] terminalStatuses`，实测用 `IReadOnlyList<string>` 更合适：调用点传的是 `new[] { … }`，数组天然满足；而 Db 层只读不写，用窄接口表达意图。

SQL 用动态占位符 `@t0…@tN` 拼 `IN (...)`：**拼的是占位符名，不是值**，没有注入面。plans 传 4 个、tasks 传 3 个，数量由调用方决定，Db 层不知道也不需要知道 `superseded` 只有 plan 有。

### 6.5 保住的四条语义（本次唯一允许的做法）

| 语义 | 怎么保的 |
|---|---|
| 三条更新在**同一个 try** 里，顺序 plans → tasks → runs | 一个 `try` 包三次调用，中间不放任何其它语句 |
| 不包事务 | 三次独立 `db.Execute`，无 `ExecuteInTransaction` |
| 失败连锁（① 抛出则 ②③ 不执行） | 就是「同一个 try」的自然结果，没有额外代码 |
| 三处 where 条件各自不同 | 三个方法三份 SQL，没有抽「共用 where」 |

代码里留了一条⚠️注释把「包事务 / 拆三个 try 都不属于这次搬 SQL、要另开单验证」写死，避免下一个人顺手优化。
