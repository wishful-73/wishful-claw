# S-339  同名文件大小写重名（`error-boundary.tsx` / `ErrorBoundary.tsx`）

> 登记：2026-11-06 09:5x，欠账普查（老大：「再找找还有没有欠账」）。
> 状态：**✅ 已完成（2026-11-06 10:2x，刀 30 / commit `78663ed2`）**。
> 归属：本迭代已修（一分钟的活，但拖着就是跨平台隐患）。

## 一、证据

`src/renderer/src/components/` 下同时存在两份：

| 文件 | 行数 | 字节 | 被引用 |
|---|---|---|---|
| `error-boundary.tsx` | 48 | 1,466 | **0 处** |
| `ErrorBoundary.tsx` | 35 | 1,035 | `App.tsx:9` import、`:241` / `:261` 使用 |

`git ls-files src/renderer/src/components | Select-String 'oundary'` 输出：

```
src/renderer/src/components/ErrorBoundary.tsx
src/renderer/src/components/error-boundary.tsx
```

**两份都在 git 索引里**，不是本地残留。

全仓 `-cmatch 'error-boundary'` 命中 **0** —— 小写那份没有任何 import，纯死文件。

## 二、为什么必须修

Windows（NTFS）/ macOS（APFS）默认**大小写不敏感**，两个文件能共存，所以本地跑得通；Linux（ext4）区分大小写。这造成三个坑：

1. **改了 A 实际改了 B**：大小写不敏感系统上 `open('components/error-boundary.tsx')` 命中的可能是 `ErrorBoundary.tsx`，编辑器「保存成功」但改的是错那份
2. **路径写法换一个大小写就换文件**：`App.tsx` 现在写 `@renderer/components/ErrorBoundary`，哪天有人手改成小写，在 Windows 上行为不变、在 Linux 上指向死文件 → 构建失败
3. **CI / 新机器 clone**：git 会把两份都落盘，在大小写不敏感系统上后写的那份覆盖先写的，谁赢不确定

现在只是**运气好**没出事。

## 三、修法

删掉没被引用的那份，**保留 `ErrorBoundary.tsx`**（零功能变化、不动任何 import）：

```powershell
git rm -f src/renderer/src/components/error-boundary.tsx
```

**不要**反过来保留小写那份改名 —— 那要改 `App.tsx` 的 import，多一次改动面。

## 六、实施记录（2026-11-06 10:2x，刀 30）

### 6.1 动手前又补了两道确认

§四 验收里没有这一条，但删文件前值得多做一次 —— 「零引用」和「导出的类型名也没被别处具名导入」是两件事：

```
小写 error-boundary.tsx  :12  export class ErrorBoundary extends Component<ErrorBoundaryProps, ErrorBoundaryState>
大写 ErrorBoundary.tsx   :12  export class ErrorBoundary extends Component<Props, State>

全仓 -cmatch 'components/error-boundary'          命中 0
```
