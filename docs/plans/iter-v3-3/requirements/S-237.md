性质：**软件侧缺陷**。不是「缺功能」，是「一个状态码被当成两种语义用」。
归属：**v3-iter-3（产品 1.0.3）**。
编号：**S-237**（原预留号让出，见 `raw-requirements.md` §三）。

**讨论过程留档（避免下轮重现）**：我先后把需求读成「400 但 body 里有正常内容，当成功吃下」和「不改分类、直接改退避曲线」—— 两者都不是老大的意思。老大要的是**给 400 分类**：限流类 → 重试，真错误类 → 报错。

## 2. 现象

部分 AI 服务商在**限流**时返回 **HTTP 400** 而不是 **429**。典型场景：

> 实际规则是「一分钟 10 个请求」，超了就回 400。

后果是两种完全不同的语义被同一个状态码承载：

| 上游真实原因 | 返回 | 该怎么做 |
|---|---|---|
| 触发限流（等一下就能过） | 400 | **等一会儿重试** |
| 参数错 / 模型名不存在 / 请求体非法 | 400 | **立即报错**，重试一万次也一样 |

现在代码对 400 一视同仁 —— 全部重试。这让第二类白烧请求，也让用户等了两分钟才看到一句含糊的报错。

## 3. 现状（2026-10-27 实读源码）

### 3.1 400 一律重试，默认烧 10 次

`ProviderRetryPolicy.cs:223-231`：

```cs
private static bool IsRetryableStatus(int statusCode)
{
    // 400 is intentionally retryable: several providers misbehave and
    // return 400 for transient conditions (overload, hidden rate limits,
    // momentary context hiccups) that succeed on retry. User-confirmed
    // design (audit M30 retracted 2026-08-28) — do not tighten this
    // back to "429/5xx only" without a product decision.
    return statusCode is 400 or 429 || statusCode >= 500;
}
```

**这段注释就是本需求的历史来源** —— 当初正是因为「有服务商把限流报成 400」，才把 400 拉进重试范围。本需求要做的，正是注释里要求的那个「product decision」：**不是收紧回 429/5xx-only，而是把 400 拆成两类**。

代价量级：

| 常量 | 值 | 位置 |
|---|---|---|
| `DefaultMaxRetryAttempts` | **10** | `:59` |
| `BaseDelayMs` | 500 | `:67` |
| `MaxBackoffMs` | 15 000 | `:68` |
| `MaxRetryAfterMs` | 60 000 | `:69` |

⇒ 一个真 400（比如模型名写错）会被完整重播 **10 次**，每次带全上下文，指数退避打完约 1~2 分钟，最后才把原始 400 抛给用户。

### 3.2 分流所需的两个信息，现在都拿不到（拿不全）

`ProviderHttpException`（`:20-48`）只存两个字段：

```cs
public int StatusCode { get; }        // :33
public TimeSpan? RetryAfter { get; }  // :35
```

| 分类判据 | 现在能拿到吗 |
|---|---|
| `Retry-After` | ✅ 能。`CreateAsync:47` 无条件取 `response.Headers.RetryAfter?.Delta`，不看状态码 |
| `x-ratelimit-*` 系列响应头 | ❌ **不能**。整个类没有 header 集合字段，构造时只取了 `RetryAfter` 一个 |
| 响应体原文 | ⚠️ **只能从 `Message` 字符串里抠**。`:27` 把 body 拼进了 Message：`$"{providerName} request failed HTTP {(int)statusCode}: {responseBody}"`，没有独立字段 |

⇒ 要做 header 判据，得给异常加字段；要做 body 判据，得让 body 独立成属性（现在只能靠字符串切分，脆）。

### 3.3 三个 provider 各自抛，形态一致

| Provider | 抛点 |
|---|---|
| OpenAI Chat（含所有 OpenAI 兼容中转） | `OpenAIChatProvider.cs:220-226` |
| OpenAI Responses | `OpenAIResponsesProvider.cs:152-156` |
| Anthropic Messages | `AnthropicMessagesProvider.cs:77-83` |

三处都是同一个形状：`if (!response.IsSuccessStatusCode) throw await ProviderHttpException.CreateAsync(...)`。

⇒ **分类逻辑只要落在 `ProviderHttpException` / `ProviderRetryPolicy` 这一层，三家自动都覆盖**，不必改三个文件。这是本需求改动面可控的关键。

### 3.4 顺带发现：`SlowRetryThreshold` 是死代码

```cs
private const int SlowRetryThreshold = 10;       // :65
private const int DefaultMaxRetryAttempts = 10;  // :59

if (attempt > SlowRetryThreshold) return SlowRetryDelayMs;  // :253  ← 永不成立
```

重试条件是 `retryAttempt < maxAttempts`、`attempt = retryAttempt + 1` ⇒ **attempt 最大就是 10**，`attempt > 10` 在默认配置下永远为假。

`:60-64` 那段注释写的意图：

> Retries beyond this attempt use a fixed 60s interval — by then the provider is rate-limiting at its own pace (per-minute quota), so exponential backoff adds nothing but user-visible dead time.

**这段「限流最该生效」的逻辑，默认配置下走不到。** 只有用户手动把 `requestMaxRetries` 设成 0（无限）或 > 10 才活。

**本需求是否动它 —— 见 §8 ⑤。** 它跟「限流走重试」直接相关（限流窗口是一分钟的话，头几次 500ms/1s/2s 的重试纯属白撞），但老大只要求做分类分流，我没有擅自把它算进来。

## 4. 修复方向

### 4.1 分类器落点：照抄 `ToolPairingErrors` 的范式

项目里已有三处「专项 400 → 特殊处置」，本需求是第四处，不引入新范式：

| 现成范式 | 位置 | 干什么 |
|---|---|---|
| `ContextCompression.IsContextWindowExceededError` | `AgentLoop.cs:386` | 上下文超限 → 压缩后重发 |
| `ToolPairingErrors.IsToolPairingError` | `AgentLoop.cs:426`、`ProviderRetryPolicy.cs:137` | 工具配对错 → 先修配对再重发 |
| （S-236 待做）`ImageInputErrors` | 同上两处 | 图像不支持 → 剥图重发 |

新增 `src/runtime/WishfulClaw.Agent/ProviderErrorClassification.cs`（或沿用 `XxxErrors` 命名），**结构照抄 `ToolPairingErrors`**（遍历 `InnerException` 链 + `Markers` 数组 + `Contains(OrdinalIgnoreCase)`）。

前置改动：`ProviderHttpException` 补两个字段
- `IReadOnlyDictionary<string,string> Headers`（或至少 `RateLimitRemaining` / `RateLimitReset` 两个值）
- `string ResponseBody`（从 Message 里拆出来，Message 保持现有格式不动，避免影响日志）

### 4.2 判据（2026-10-27 修订：原「三层猜测」被实测推翻，改为 code 优先）

> **修订原因**：§9.2 / §9.3 实测证明商汤那个渠道 **响应头里没有任何 `x-ratelimit-*`、也没有 `Retry-After`（限流的 429 也没有，只有 `X-Request-Id`）**，原判据 ①② 在该渠道彻底失效；语义放在 body 的 `code` + `type` 里。原文案表继续留着当兜底，但主判据换成 code/type。

**① 主判据 · body 的 `error.code` / `error.type`**（2026-10-27 实测校准，见 §9.3）

```cs
// 限流（实测两种都出现过）
code == 8                      // gRPC RESOURCE_EXHAUSTED，"rpm exhausted"
code == "429003"               // 业务码，"inference exceeds tpm/rpm limit"
type 含 "rate_limit" / "quota_exceeded"   // rate_limit_error / quota_exceeded_error
→ 限流，重试

// 真错误（实测）
code == 3 (INVALID_ARGUMENT) / 5 (NOT_FOUND) / 16 (UNAUTHENTICATED)
type 含 "invalid_request" / "not_found" / "unauthenticated"
→ 真错误，不重试

// 其它
→ 真错误，不重试（老大 11:49 定的兜底）
```

齐头并进看 `code` 与 `type` 两个字段，任一命中即可 —— 因为同一个渠道上两种限流只给了其中一个明确（`code:"8"` 有 type，`code:"429003"` 有 type，但谁也不保证下次两者都给）。

**⚠️ 修订记录（别退回去）**：上一版本写的是「只认 `code == 8`」。实测发现限流还有 `code:"429003"` 这一种，只认 8 会漏掉一半限流、把它当真错误立即报错。**「只认 8」已被推翻。**

**② 兜底 · body 文案**（`code` / `type` 都给不出来时）

```cs
// 限流类
"rate_limit", "rate limit", "too many requests", "请求过于频繁",
"频率限制", "并发数过高", "tpm", "rpm", "throttl", "resource_exhausted"
// 真错误类（重试无用）
"invalid_request", "unknown model", "model not found", "does not exist",
"malformed", "invalid api key", "insufficient_quota", "余额不足", "额度"
```

**③ 已被否决的两层（留档，别再捡回来）**

| 原判据 | 为什么废 |
|---|---|
| `x-ratelimit-remaining: 0` 之类的 header | 商汤渠道实测**一个都没有**：真 400 只有 `X-Request-Id`，限流的 429 也只有 `X-Request-Id` |
| `Retry-After` 存在即限流 | 同上 —— **限流的 429 响应里也没有 `Retry-After`**（§9.3 实测）。已在 `CreateAsync:47` 取到就用于算延迟，不参与分类，保持现状 |

### 4.3 分流：改一处，两个分支

现在 `ProviderRetryPolicy.cs:131-139` 的 when 条件第一项是 `IsRetryableStatus(ex.StatusCode)`。改为按分类结果判定：

```
限流类 400（任一层判据命中）  → 重试（沿用现有退避，或按 §8 ⑤ 走慢速路径）
429 / 5xx                    → 重试（不变）
真错误类 400（文案命中）      → 不重试，立即抛给上层
认不出的 400                  → 不重试，立即抛给上层  ← 老大 2026-10-27 11:49 定
```

**「认不出」的判定**：§4.2 三层判据**全不命中** 且 body 文案也没命中真错误类。

**这是一次有意的行为回退，必须写清代价。**

改动前：400 一律重试 10 次，所以「限流但文案认不出」的渠道**靠重试还有机会救回来**。
改动后：同样情况**第一次就报错**，用户看到 `request failed HTTP 400: {...}` 原文。

老大权衡的是：

| | 改动前（一律重试） | 改动后（认不出就报错） |
|---|---|---|
| 限流且认出 | 重试 ✓ | 重试 ✓ |
| 真 400 | **白烧 10 次请求，等 1~2 分钟才见错** | 立即报错 ✓ |
| 限流但认不出 | 靠重试救回 ✓ | **第一次失败** ✗ |
| 用户能否马上看到真实原因 | 否（被重试淹没） | 是 ✓ |

选报错的实质是：**宁可偶尔错杀，也不让用户白等两分钟、白付十次请求的钱。** 错杀时用户至少看得到原始 400 内容，能自己判断该重发还是该改配置。

**缓解手段（都记在这里，别实施时忘）：**
1. `Markers` / header 判据尽量写全，尤其是 §8 ④ 的报文到手后
2. §4.5 的可读性改动从「可选」升为「建议做」—— 认不出时报错是常事，报错文案得让人看懂
3. 上线后盯「真 400 立即失败 → 用户立刻成功重发」这个模式，它说明该补文案了

`IsRetryableStatus` 的注释要同步改写 —— 它现在写着「do not tighten without a product decision」，本需求就是那个 decision，注释得留下这个变更理由，不能直接删。

### 4.4 统计口径：**不动**

老大 11:46 明确：

> 还有请求失败只要不是200都计入，这个不需要去调整

⇒ `LogRequestAttempt`（`:119`、`:146`）的记账逻辑一行不改，限流的 400 仍照常计入请求失败。**这是老大明确划掉的边界，实施时不要「顺手优化」。**

### 4.5 用户可见面（见 §8 ⑥）

识别出限流后，`request_retry` 流事件的 `Reason` 现在固定是 `$"HTTP {ex.StatusCode}"`（`:152`），可以给限流单列一个 reason（如 `rate-limited`），让聊天窗显示「服务商限流，正在等待」而不是「HTTP 400」。**不影响功能，只影响可读性，等老大点名。**

### 9.2 商汤日日新实证（2026-10-27，老大点名「商汤有 400 实际是 429」后补做）

日志筛不到，改为对 `https://token.sensenova.cn/v1`（配置里唯一一条商汤渠道，`builtinId: sensenova`，key 在 `config.json`）做**低风险探测**：只发确定会失败的请求（参数非法 / 模型不存在 / 畸形 JSON），不跑推理、不耗额度、不并发。

**探测结果（响应体原文照抄，key 不外泄）：**

| 探测 | HTTP | body |
|---|---|---|
| 无效 key | **401** | `{"error": {"code": 16, "message": "Forbidden"}}` |
| 模型不存在 | **404** | `{"error":{"message":"model is not found","type":"not_found_error","code":"5"}}` |
| `max_tokens: -5` | **400** | `{"error":{"message":"field MaxTokens invalid, should be in [1, 384000]","type":"invalid_request_error","param":"max_tokens","code":"3"}}` |
| `temperature: 99` | **400** | `{"error":{"message":"field Temperature invalid, should be in [0.0, 2.0)","type":"invalid_request_error","param":"temperature","code":"3"}}` |
| `role: "wizard"` | **400** | `{"error":{"message":"field Messages[0].Role invalid, should be in one of: …","type":"invalid_request_error","param":"messages[0].role","code":"3"}}` |

| 畸形 JSON | **400** | `{"error":{"message":"invalid arguments","type":"invalid_request_error","code":"3"}}` |

**三条硬结论：**

1. **这个渠道的语义全在 body 的 `code` 字段里，而它是 gRPC 状态码。** 实测三个点与 gRPC 标准一一对上：`16` = UNAUTHENTICATED、`5` = NOT_FOUND、`3` = INVALID_ARGUMENT。配套的 `type`（`invalid_request_error` / `not_found_error`）只是人读的别名。
2. **五种互不相同的真错误，全部压成 `HTTP 400 + code:"3"`。** ⇒ 老大说的「400 实际是 429」，机制就是**限流（gRPC `8` = RESOURCE_EXHAUSTED）同样被压进 HTTP 400**，只是 `code` 不同。这也解释了为什么这个渠道的 400 看起来「时好时坏」—— 两个语义共用一个状态码。
3. **响应头里既没有 `x-ratelimit-*`，也没有 `Retry-After`**（每次都只有 `X-Request-Id`）⇒ **§4.2 原设计的判据 ①（限流 header）与判据 ②（Retry-After）对这个渠道完全无效**，原方案在本渠道上一条都用不上。

**⇒ 判据重写（见 §4.2 修订）。** 原「猜文案」那套对商汤是纯猜，现在有了确定性判据：**读 body 的 `code`**。

| 轮次 | HTTP | body |
|---|---|---|
| 串行 6 次（几乎无间隔） | **429** ×3 | `{"error":{"message":"inference exceeds tpm/rpm limit","type":"rate_limit_error","code":"429003"}}` |
| 同上 | 200 ×3 | ok |
| 同上 | **429** ×1 | `{"error":{"message":"rpm exhausted","type":"quota_exceeded_error","code":"8"}}` |
| **并发 10 个** | **429** ×9 | `{"error":{"message":"rpm exhausted","type":"quota_exceeded_error","code":"8"}}` |
| 同上 | 200 ×1 | ok |

**四条实测结论（前两条推翻了 §4.2 修订版的部分设计，正文已同步改）：**

1. **`code:"8"` = 限流，推断得到证实。** gRPC RESOURCE_EXHAUSTED 在这个渠道上确实用于限流，配套 `type:"quota_exceeded_error"`、`message:"rpm exhausted"`。
2. **但限流不止一种码**：还有 `code:"429003"` + `type:"rate_limit_error"`（`message:"inference exceeds tpm/rpm limit"`）。这是**业务码不是 gRPC 码**，且位数不同。⇒ §4.2 原来「只认 8」**会漏掉这一半**，必须同时认 `type` 与业务码。
3. **这个接入点限流时返回的是 `HTTP 429`，不是 400** —— 实测 13 次限流全是 429。老大说的「400 实际是 429」**在 `token.sensenova.cn`（token plan 网关）上复现不出来**。
4. **但需求本身反而更站得住**：`429003` 这个码的设计本身就说明「429 语义被塞进业务码、与 HTTP 状态码解耦」。真 400 是 `code:"3"`、限流是 `code:"8"`/`"429003"` —— **同一个接口上，语义全在 body，HTTP 状态码不是判据**。换成官方接入点或更早版本，被包成 HTTP 400 完全合理。
5. **RPM 额度极低**：串行第 0 次、第 3 次就 429，说明这个免费套餐的每分钟额度已经很小。**这解释了为什么老大对这个渠道的限流印象这么深。**

### 9.4 一个反向收获：别把 `code` 判据泛化到所有渠道

`code` 字段 OpenAI 官方也用，但那儿是**字符串业务码**（`invalid_api_key` / `insufficient_quota`），不是 gRPC 数字。若把「code 是数字」当通用判据，别的渠道只要回了个数字 code 就会被误判。

⇒ 只在 **`code` 能解析成整数** 时按 gRPC 语义判，且**只认 `8` 为限流**（其余整数值一律当真错误）；非数字 code 走文案兜底。这条纪律写进 §4.2 修订版。
