# S-264 · 脏图源头治理 —— 宁可标读图失败，也不把脏图送上上游

> 归属：v3-iter-4（产品 1.0.4）｜登记 2026-10-29 09:32
> **状态：待开工（刀 1e）。**
> 来源：老大 2026-10-29 09:30 原话「读图工具如果读到没有图，可以直接标读图失败么？而不是把脏图丢上去」；09:32「根据你的推荐来 登记然后按照工作流推进吧」。

## 一、老大的原话与提出问题

## 三、勘察结论（2026-10-29，读码定案）

### 3.1 魔数判据其实全都写好了，结论被三处丢掉

| 位置 | 现有判据 | 结论怎么用了 |
|---|---|---|
| `ImageFileProbe.MediaTypeFor`（`:36-50`） | 纯看扩展名 | `.png` ⇒ `image/png`，**不管文件里装的是什么** |
| `ImageFileProbe.TryReadSize`（`:55-86`） | **读文件头做魔数校验**（PNG 签名 / JPEG `FF D8` / GIF87a / BMP `BM` / WEBP） | 只用来取尺寸；`false` 只写「size unavailable」，**图像照旧 base64 送出去**（类注释 `:15` 明写） |
| `ProviderContentHelpers.ResolveSupportedImageMediaType`（`:193-209`） | **嗅探 + 白名单** | 嗅探认不出时**回落信任声明的格式** |

第三处是真正的漏水口：

```csharp
var detected = DetectImageMediaTypeFromBase64(imageBase64);
if (detected is not null)
    return SupportedImageMediaTypes.Contains(detected) ? detected : null;   // 认得出 ⇒ 按嗅探收口

var declared = NormalizeDeclaredMediaType(declaredMediaType);
return declared is not null && SupportedImageMediaTypes.Contains(declared) ? declared : null;
//      ↑ 认不出 ⇒ 信任声明 —— 脏图 100% 从这里出门
```

**「脏图」的定义就是「文件头不符合任何已知格式」，也就是 `DetectImageMediaTypeFromBase64` 返回 `null` 的那批。** 而这一刻代码选择信任声明，于是：损坏文件 / 半截写入 / 非图像内容（html、文本、二进制）全部被贴上 `image/png` 标签送上上游 ⇒ 400 `unsupported image`。

### 3.2 `DetectImageMediaTypeFromBase64` 认哪些格式（决定收严安全不安全）

png / jpeg / webp / gif / bmp / tiff / x-icon 七种二进制签名 + svg（文本嗅探，`DetectTextImageFormat:130-154`）。

⇒ 「认不出」剩下的是：**损坏 / 半截 / 非图内容 / AVIF・HEIC・JXL 等未列格式**。后一类的上游白名单本来也不收，所以**丢它是对的，不是误杀**。

### 3.3 工具层：`ReadImage` 只看扩展名，不看内容

`FileReadTool.ReadImage`（`:187-219`）的闸门是 `ProviderContentHelpers.SupportedImageMediaTypes.Contains(mediaType)` —— 判的是 `MediaTypeFor` 按**扩展名**推断出的 `mediaType`，**不是真实内容**。所以 `foo.png` 里装着 svg / html / 半截数据，轻松过闸。

## 四、定案

### 4.1 判据必须拆四档，不是「没图就失败」

| # | 真实内容 | 现状 | 应该 |
|---|---|---|---|
| 1 | 有效 png/jpeg/webp/gif，扩展名也对 | 正常发出 | 不变 |
| 2 | 有效 jpeg，但文件名叫 `foo.png` | 按 png 发出 ⇒ 上游可能 400 | **纠正成真实格式后发出**，不判失败 |
| 3 | 有效 bmp / tiff / ico | 已有文本降级（S-246 做的） | 保持 |
| 4 | **认不出**（损坏 / 非图 / 半截） | **base64 发出 ⇒ 400** | **标读图失败，不附像素** |

第 2 档单独说：**扩展名骗人是常见情况**（用户截图后手动改名），正确做法是按真实格式发，不是判失败 —— 否则「读图失败」就成了误报。

第 4 档才是老大说的「标读图失败」：`IsError: true` + 一句能指导行动的文本（哪个文件、为什么读不了、可以怎么办）。

### 4.2 三层一起改，缺一层就漏

| 层 | 位置 | 动作 | 不做的后果 |
|---|---|---|---|
| **工具层** | `ImageFileProbe` + `FileReadTool.ReadImage` | 加签名探测（**复用** `ProviderContentHelpers` 的判据，不新写一套）；`ReadImage` 按 §4.1 四档分流 | 脏图仍从 `Read` 出门 |
| **组包层** | `ProviderContentHelpers.ResolveSupportedImageMediaType:193-209` | **去掉回落**：嗅探认不出 ⇒ 返回 `null`（丢块 + `WorkerLog.Warn`） | 微信渠道 / 历史回放 / 视频抽帧三条线照旧漏（真实日志 10/18 条在微信会话） |
| **记忆层** | `AgentLoop.cs:470-476` 剥图分支 | **脏图触发的剥图不写 `ImageVisionMemory`** | 一张脏图把能看图的模型**永久**标成「不吃图」，不可逆（见 §4.3） |

**只收紧组包层也不行**：丢块是静默的，`FileReadTool` 那行文本「Read image: x.png (800x600, image/png)」还在，**模型会以为自己看过了** —— 比看不到更坏。所以工具层必须同时把「读图失败」说出口。

### 4.3 记忆层这个缺陷要单独说清（它是真缺陷，不是优化）

`ImageVisionMemory` 是**落盘永久**的（`image-vision-unsupported.json`，跟随数据目录），通读 `ImageVisionMemory.cs` 全文只有 `IsKnownUnsupported` / `RememberUnsupported` / `GetRememberedAt` 三个方法 —— **没有清除、没有 TTL、没有 UI 入口**。

而 `unsupported image`（S-261 加的 marker）与「模型不吃图」共用**同一个 catch 块**（`AgentLoop.cs:453-492`），那块里无条件执行 `RememberUnsupported`。两种语义被合并了：

| 报文 | 真实含义 | 该不该永久记 |
|---|---|---|
| `image input is not supported` | 模型没视觉能力 | **该** |
| `You have uploaded an unsupported image` | 这张图坏了 | **不该** |

后果推演：用户发一张 svg ⇒ 400 ⇒ 剥图（本轮正常）⇒ `deepseek-v4.1-flash` 被写进 json ⇒ 之后发正常 png 截图也**永远**被剥 ⇒ 想恢复只能手动删文件。

老大自己的现场就是反证：「我截图发消息，实际上是能识图的，结果它自己读取就不行了」—— 同一个模型，视觉能力明明有。

**S-236 档 2 的动机是「不让本地表替模型决定能不能看图」，现在变成「让一张脏图替模型决定以后永远不能看图」—— 反向复发。**

### 4.4 两个坑，实施时不许踩

**坑一：不能拿 `TryReadSize` 返回 false 当脏图判据。**
它只读 4 KB 找 JPEG 的 SOF 段，类注释自己承认「SOF 可能排在 EXIF 之后」（`:19`）。一张带大 EXIF 的合法 JPEG 会被误杀成脏图。判据**只判签名**，直接复用 `DetectImageMediaTypeFromBase64` 的字节版逻辑。

**坑二：`AgentLoop.cs:464` 的两道闸（S-236 判据 10 红线）一个字不许动。**
本轮只改「剥图后再不写记忆」和「丢块时补可见文本」，不碰那两道闸的判定。

## 五、判据（验收）

1. **签名纠正**：`foo.png` 内容实际是 JPEG ⇒ `ReadImage` 按 `image/jpeg` 发出（不是失败、不是 png）。
2. **认不出即失败**：`foo.png` 内容是 html / 半截损坏数据 ⇒ `ReadImage` 返回 `IsError: true` 的文本结果，**不产生 image 块**。
3. **组包层不回落**：`ResolveSupportedImageMediaType(脏 base64, "image/png")` 返回 **null**（修复前返回 `image/png`）。
4. **白名单格式不误杀**：有效 png / jpeg / webp / gif 四种，`ResolveSupportedImageMediaType` 全部返回 `detected`。
5. **bmp / tiff / ico 不误伤**：仍走既有文本降级，行为与 S-246 一致。
6. **脏图不写记忆**：剥图由「脏图」触发（`unsupported image`）时，`ImageVisionMemory.IsKnownUnsupported` 仍为 false；由「模型不吃图」（`image input is not supported`）触发时照旧写入。
7. **红线不破**：`AgentLoop.cs:464` 两道闸原样保留；无关 400 不被剥图路径截走。

## 八、不做的事

- **不做图像转码**（脏图 ⇒ 自动转 png）。`ImageFileProbe` 类注释 `:12-14` 明确记着「为这一行说明引入一个图像解码依赖，AOT 体积和攻击面都不划算」，本条沿用。
- **不动用户历史**：组包层丢块只作用在 wire 副本，与 `AgentLoop.ImageInput.cs:21-23` 红线一致。
- **不给 `ImageVisionMemory` 加 UI 清除入口**（那是另一件事，需要老大单独定 UI 落点）；本条只保证「不对脏图写记忆」，因而不产生新的错误记录。
