# S-316  内置服务商的请求头仍是 C# 硬编码，没走 `requestOverrides.headers`

> 登记：2026-11-05 10:30。来源：老大口述（见 §一）。
> 状态：**待开工**。
> 关联：S-317 是同一次口述的另一半（前端「编辑态 / 已保存态」），**故意拆开**——本条动 C# header 链，S-317 是纯前端，风险不同源，回滚粒度也不同。

## 一、原始诉求

> 登记一个需求 或者说是调整。本身我们很多 ai 服务商是有自定义请求头的，然后我们页面也有进行配置的方式。但是内置的 ai 服务商很多还是代码上硬编码，而不是通过自定义请求头数据的形式配置。以及页面的自定义请求头没有编辑形态和保存后形态的区别，导致用户编辑了请求头以后不知道是否保存了

后半句归 S-317。本条只解决「硬编码 ⇒ 数据」。

## 二、现状摸排（代码事实，2026-11-05）

### 2.1 数据化通道早就存在，而且支持模板

| 环节 | 位置 |
|---|---|
| 存储字段 | `provider.requestOverrides.headers: Record<string, string>` |
| UI 编辑器 | `src/renderer/src/components/settings/provider/RequestHeadersEditor.tsx` |
| 父级落库 | `ProviderConfigPanel.tsx:81-85` `handleHeadersChange` → `updateProvider` |
| 生效点 | `ProviderRequestOverrides.ApplyHttpHeaderOverrides`（`ProviderRequestOverrides.cs:61-92`） |
| 调用方 | `ProviderHttpHeaders.ApplyOpenAiChat`（`:58`）/ `ApplyAnthropic`（`:67`），即 chat / responses / anthropic / 压缩摘要 / 辅助单发**全部路径**共用 |

两个容易忽略但关键的性质：

1. **模板替换已经有**：`ResolveHeaderTemplate(value, sessionId, model)`（`ProviderRequestOverrides.cs:126-134`）认 `{{sessionId}}` / `{{ model }}`（带空格也认），`sessionId` 与 `model` 本来就从 `provider` 顶层取（`:74-75`）。
2. **覆盖语义已正确**：`ApplyHttpHeaderOverrides` 先 `request.Headers.Remove(name)` 再 `TryAddWithoutValidation`（`:89-90`），用户配的值**覆盖**而非追加。
3. **空值自动跳过**：解析结果 `Length == 0` 就 `continue`（`:85-88`）⇒ 变量为空时不发空头。这条在第 3.1 节会被直接用上。

### 2.2 真正走这条通道的预设只有 3 个

| 预设 | 带的头 |
|---|---|
| `codex-oauth.ts` | `openai-beta` / `originator` / `session_id` / `conversation_id` |
| `copilot-oauth.ts` | `Copilot-Integration-Id` / `editor-version` / `editor-plugin-version` |
| `workbuddy.ts` | 国内 / 国际两版都走 `staticHeaders()` |

`src/renderer/src/stores/providers/` 下 42 个文件，其余 38 个零 `requestOverrides.headers`。

### 2.3 C# 侧仍硬编码的 provider 头

全部集中在 `src/runtime/WishfulClaw.Agent/ProviderHttpHeaders.cs`：

| 头 | 出处 | 值来源 | 用户可见可改 | 判定 |
|---|---|---|---|---|
| `x-opencode-session` | `ApplyOpenCodeSession` `:172-182` | 运行时 `sessionId`；`IsOpenCodeGo`（`:199-205`）按 `providerBuiltinId == 'opencode-go'` 判定 | 否 | **该搬** |
| `OpenAI-Organization` | `ApplyOpenAiChat` `:49-52` | `provider.organization` 字段 | 否 | **该搬** |
| `OpenAI-Project` | `ApplyOpenAiChat` `:53-56` | `provider.project` 字段 | 否 | **该搬** |
| `X-User-Id` / `X-Domain` / `X-Enterprise-Id` / `X-Tenant-Id` | `ApplyOAuthAccount` `:120-140` | `provider.oauthAccount.{uid,domain,enterpriseId}`，登录态，动态值 | 否 | **不搬**，见 §四 |
| `User-Agent` | `ApiUserAgent.Apply` | `provider.userAgent` 字段 + `ApiUserAgent` 独立链路 | 否 | **不搬**，见 §四 |

**「无 UI 入口」是实测结论**：全仓搜 `organization` / `userAgent` 在 `src/renderer/src` 下的命中，全部属于内置浏览器的 UA / 记忆组织面板，`provider.organization` / `provider.project` / `provider.userAgent` **没有任何输入框**。也就是说这三个字段现在用户根本填不了——预设里不写就等于永远为空。

### 2.4 顺带查出的缺陷：`ApplyOAuthAccount` 会把用户配置追加成双值

`ApplyOpenAiChat` 的执行顺序（`:45-62`）：

```
1. ApiUserAgent.Apply
2. OpenAI-Organization / OpenAI-Project        ← 无 Contains 检查
3. ApplyHttpHeaderOverrides                    ← Remove 后 Add（覆盖）
4. ApplyOAuthAccount                           ← 无 Contains 检查
5. ApplyOpenCodeSession                        ← 有 Contains 检查（:176）
```

第 4 步跑在第 3 步之后。`HttpRequestHeaders.TryAddWithoutValidation` 在头已存在时是**追加第二个值**，不是替换 ⇒ 用户在 UI 里配了 `X-User-Id: abc`，实发头是 `X-User-Id: abc, <登录 uid>`。

`ApplyOpenCodeSession` 之所以没这个毛病，纯粹是它自己查了 `Contains`（`:176`）。同一个文件里两条路径两种写法，本身就是漏。

## 三、方案

### 3.1 模板变量扩到「provider 顶层任意标量」

`sessionId` / `model` 本来就是从 `provider` 取的，所以扩成「按名取 provider 顶层字符串字段」成本极低，且不破坏现有两个变量：

- 新增 `{{organization}}` → `provider.organization`
- 新增 `{{project}}` → `provider.project`
- 不引入完整 JSON path 语法，只做顶层标量按名取 —— 够用、可预测、一处实现

值为空的变量解析成空串，走既有 `Length == 0` 分支 ⇒ **不发空头**。这一条让预设可以无条件声明这三个头，用户没填就自然消失。

### 3.2 三条头搬进预设，C# 只留兜底

| 预设 | 新增 |
|---|---|
| `opencode-go.ts` | `requestOverrides.headers: { 'x-opencode-session': '{{sessionId}}' }` |
| OpenAI 协议系预设（`openai.ts` 等） | `'OpenAI-Organization': '{{organization}}'`、`'OpenAI-Project': '{{project}}'` |

C# 侧同步改：

- `ApplyOAuthAccount` / `ApplyOAuthAccountDebug` 加 `Contains` 检查（与 `ApplyOpenCodeSession` 对齐）—— 修 §2.4 的双值缺陷
- `OpenAI-Organization` / `OpenAI-Project` 的注入同样加 `Contains` 检查 —— 让「用户配了就以用户为准」在这三条上一并成立
- **不删** C# 兜底路径

### 3.3 老数据兼容：为什么兜底必须留着

`AddProviderDialog` 是从预设**拷贝快照**生成 provider 记录的，已存在的 provider **不会重读预设**。所以：

| 场景 | 结果 |
|---|---|
| 新装 / 新建的 provider | 预设带头 ⇒ UI 里看得见、改得动 |
| 老 provider（记录里没有这份头） | C# 兜底照旧生效，**行为零变化** |
| 老 provider + 用户手动加过同名头 | `Contains` 检查生效 ⇒ 用户值优先，不再双值 |

删掉兜底 = 老用户升级即丢 `x-opencode-session`（opencode-go 直接不可用）和 `OpenAI-Organization`（组织计费走错）。

## 四、明确不做（写清理由，防反复）

| 项 | 不做理由 |
|---|---|
| `X-User-Id` / `X-Domain` / `X-Enterprise-Id` / `X-Tenant-Id` 数据化 | 值来自登录态 `oauthAccount`，是**运行时动态身份**不是配置。写进预设等于写死；让用户改它只会让 WorkBuddy 按别人的账号作答。本条只修它「追加双值」的缺陷 |
| `User-Agent` 并入 `requestOverrides.headers` | 已有独立字段 `provider.userAgent` + `ApiUserAgent` 完整链路（含 `Ensure` 兜底、debug 镜像）。并入等于两套机制并存 |
| 协议必需头（`Authorization` / `x-api-key` / `anthropic-version` / `anthropic-beta` / `Content-Type` / `service_tier`） | 与协议请求体结构绑定，不是「服务商身份 / 路由」信息，放开只会制造 400。`RequestHeadersEditor` 的 `RESERVED_HEADERS`（`:12-20`）本来就拦着 |
| 给 `organization` / `project` 单独加输入框 | 搬进请求头表后已经可见可改，再加一层输入是两套入口 |

## 五、验收

1. 新建 opencode-go provider ⇒ 「额外请求头」里能看到 `x-opencode-session`，值是 `{{sessionId}}`
2. 同一会话跑两轮，看 `request_debug` 事件 ⇒ `x-opencode-session` 是真实 session id，不是字面量 `{{sessionId}}`
3. 老 provider（记录里没有该头）⇒ 行为与改动前一致，请求仍带 session 头
4. UI 里手动配 `X-User-Id: abc` ⇒ `request_debug` 里只有 `abc`，不是 `abc, <登录 uid>`
5. 用户没填 `organization` ⇒ 请求里**不出现** `OpenAI-Organization`（空值不发）
6. 门禁三条：`npm run typecheck`（三配置）、`npm test`、`dotnet build`（两套 sln，`-t:Rebuild`）

## 六、风险

- 动的是 header 链核心（所有服务商的 chat / responses / anthropic / 压缩 / 辅助全走这里）。改完必须逐条核对 `ApplyOpenAiChat` 与 `ApplyOpenAiChatDebug` 的**顺序一致性**，debug 态与实际发出去的头必须同序同值（debug 的值打码）
- `ResolveHeaderTemplate` 签名变化会牵动 `ApplyHttpHeaderOverrides` / `ApplyDebugHeaderOverrides` 两个调用点，`shouldSkip` 参数不动
- 不新增任何 UI ⇒ S-317 完成后这 3 个头才能在界面上被顺畅编辑，两条一起验才完整
