# 开发工作流

> 本文件由 WishfulClaw 在新建项目时自动放入 `.wishful-claw/workflow/`，是**通用**规范，不含任何特定仓库的信息。
>
> **是否遵循由项目根目录的 `AGENTS.md` 决定。** 想用就在 `AGENTS.md` 里写一句「本项目按迭代流程走，开工前先读 `.wishful-claw/workflow/dev-workflow.md`」；不想用就删掉本文件。没被指派时，agent 不会读它，它也就不占上下文。

## 一、为什么按迭代走

按迭代推进不是为了形式，是为了三件具体的事：

1. **能回滚** —— 一次迭代是一个可独立回滚的单位，出问题不会牵连上一个月的工作；
2. **能追溯** —— 半年后有人问「当时为什么这么做」，答案在需求单里，不在某个人的记忆里；
3. **能并行** —— 需求先登记、再排期、再实施，讨论和动手分开，不会边聊边改得一地鸡毛。

需求少的时候会觉得这套流程重。**收益出现在第 20 个需求之后** —— 那时已经没人记得清「这个字段为什么是这个语义」。

## 二、目录结构

全部产出都在项目的 `.wishful-claw/workflow/` 下，**不进用户源码树**：

```text
.wishful-claw/
└── workflow/
    ├── dev-workflow.md          ← 本文件
    ├── iter-001/
    │   ├── plan.md              ← 本轮做什么、按什么顺序做
    │   ├── changelog.md         ← 每个决定 + 为什么
    │   └── requirements/
    │       ├── S-001.md
    │       └── S-002.md
    └── templates/               ← 骨架，复制出去改
        ├── plan.md
        ├── changelog.md
        └── requirement.md
```

迭代目录名用 `iter-NNN`（三位补零，项目内递增）。跨项目协作时在前面加版本前缀也行，比如 `iter-v2-007` —— 只要全项目一致。

## 三、一轮迭代的生命周期

```text
拆迭代 → 登记需求 → 排刀序 → 逐刀实施 → 验收 → 收尾
```

### 3.1 拆迭代

一轮迭代**只装一个目标**。装不下的进下一轮，不要「顺便也做了」。

`plan.md` 里必须写清三样：

| 内容 | 为什么必须写 |
|---|---|
| 本轮目标（一句话） | 判断「做完没做完」的唯一依据 |
| 需求清单（编号 + 一句摘要） | 防止实施中漏项、防止范围悄悄扩大 |
| 刀序（先做什么、后做什么、为什么这个顺序） | 顺序错了会返工。有依赖的先做底座 |

### 3.2 登记需求

**先登记，再动手。** 讨论阶段只出方案和 diff 预览，不改代码、不提交 —— 除非明确说了「动手」。

每份需求单 `requirements/S-NNN.md` 至少要有：

1. **现象** —— 用户看到了什么。不要写「优化XX模块」这种说了等于没说的；
2. **根因** —— 定位到文件与行号。没定位到就写「未定位，需取证」，不要编；
3. **影响面** —— 谁会受影响，有没有兼容负担；
4. **修法** —— 打算改哪几个文件、改成什么样；
5. **验收判据** —— 怎么算做完了。**能实测就写实测方法**，不能实测要写明为什么；
6. **不做什么** —— 明确划出边界，防止实施时顺手扩张。

编号分配：扫一遍 `requirements/` 取现有最大号 +1。**不要维护计数器文件** —— 目录本身就是真相来源。并发登记撞号了，以文件存在为准重取一次。

### 3.3 排刀序

一刀 = 一次可独立提交、可独立回滚的改动。

排刀序的三条硬规矩：

- **风险不同源的，不许合成一刀。** 改「新增文件」和改「已有代码的行为」是两件事，效果混在一起就分不清是谁带来的；
- **能独立回滚的排前面。** 越早发现不对越好撤；
- **底座先于上层。** 要新增通道的，先把通道打通，再让人去用。

### 3.4 实施

一刀做完就提交一刀，提交信息写清需求编号。规矩：

| 规矩 | 说明 |
|---|---|
| 一次一刀 | 不要「反正都在改，一起提交了」。混在一起的提交没法单独回滚 |
| 校验不通过不前进 | 编译错、测试红、类型检查报错 —— 停下来修，不要攒着 |
| 不边讨论边改 | 说清楚了再动手；动手时发现方案有误，停下报告 |
| 不悄悄扩大范围 | 顺手发现的小 bug 记下来，攒进收尾那一刀，或者立新需求 |
| 非代码改动攒着 | 文档订正、口径补充这些攒着一起提，不要一次一提交 |

### 3.5 验收

**自己证明不了的事不要自己签收。** 分两类：

- **自动化能证明的**（编译、测试、类型检查）—— 跑一遍，把数字记进单据；
- **只有人眼能证明的**（界面、交互、手感）—— 明确标「待真机验收」，不要写「已通过」。

真实的验收清单要能照着做：装 / 停 / 卸、点哪个按钮、期望看到什么。写「用户体验良好」是废话。

### 3.6 收尾

收尾不是「差不多就这样吧」，是逐项结账：

1. 需求单状态全部更新到与事实一致（**这是最容易欠账的地方**）；
2. `plan.md` 里每条需求标注落地情况；
3. 未做的、延后的、挂账的，明确移交下一轮，别留在当前轮；
4. 跑一遍全量门禁，把结果记进 `changelog.md`；
5. 提交收尾一刀。

## 四、`changelog.md` 怎么用

它是**裁定流水**，不是日记。只记「做了什么决定 + 为什么」，一条一行到三行。

```md
- 18:20 **热记忆改成指针式**。原方案要改前缀预算，风险太大 ⇒ 改成系统提示只提路径，
  读不读交给 AGENTS.md。理由：改前缀会影响缓存命中率，而且不可独立回滚。
```

值得记的：

- 方案 A 和 B 之间选了 A，为什么；
- 某个做法试过不行，为什么不行（**这条最值钱**，防止后人重蹈）；
- 口径变更（原来这么算，现在那么算）。

不值得记的：

- 改了哪个文件（git 里有）；
- 一次性注意到的小细节。

## 五、文档纪律

| 项 | 规矩 |
|---|---|
| 文件大小 | 单文件 ≤ 500 行、≤ 60 KB。超了就拆 |
| 编码 | UTF-8 无 BOM |
| 换行 | 统一 LF 或 CRLF，一个项目内一致 |
| 格式 | 中英文之间加空格；代码块标语言；表格对齐 |
| 状态 | 状态行永远与事实一致。做完的标完成，没做的写「未做」，不要让读者猜 |

**状态行欠账是这套流程最大的敌人。** 一份写着「已实施」其实没做的单据，比没有单据更害人。

## 六、什么时候可以不按这套走

这些情况下别硬套流程，直接干：

- 改一个错别字、调一个边距；
- 一次性排查（查完就结束，不产生后续工作）；
- 用户明确说「先随便试试」。

判断标准：**这件工作是否会产生「以后需要解释为什么这么做」的结论**。会，就走流程；不会，就直接做。
