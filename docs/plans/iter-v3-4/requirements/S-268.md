# S-268 · `DesktopScreenshot` 的 `path` 参数完全无效 —— 描述含糊、行为缺失

> 归属：**下一迭代**（v3-iter-5）｜登记 2026-10-29 10:40
> **状态：待开工（本轮只登记，不实施）。**
> 来源：dev 实例第 6 轮审查（`.wishful-claw/notes/review-feedback-round6.md` §三 缺陷 B）。
> 与 **S-267** 同一类缺陷：**工具报告成功，实际没做成**。但那边是诊断缺失，这边是**参数没实现**。

## 一、现象

| 观察 | 结果 |
|---|---|
| 工具描述 | `Capture a full desktop screenshot and return it to the agent.` —— **没有承诺 `path`** |
| 对比 `CaptureAppWindow` 描述 | 明确写 `Pass path to write the PNG to disk; without it you receive the image but nothing is saved` |
| 实测：`DesktopScreenshot` 传 `path` | 全盘搜 `shot-desktop*` **零命中**，图只回到上下文，没落盘 |

## 二、代码佐证（已核）

| 位置 | 事实 |
|---|---|
| `AgentRuntimeDesktopExecutor.cs:98-100`（`ExecuteScreenshotAsync`） | `CreateJsonObject(_ => { })` —— **空请求体**，`input` 里除了 `delayMs` 一个字段都没读，`path` 从未出现 |
| `AgentRuntimeDesktopExecutor.cs:126-138`（`ExecuteAppWindowCaptureAsync`） | 认真解析 `path`：`GetString(input, "path")` → 相对路径按 `workingFolder` 拼绝对 → 写进 `targetPath`，还留了注释说明为什么必须在 worker 侧解析（主进程 cwd 是程序目录） |

⇒ **两个工具的调用姿势长得一样，行为差一半。**

## 三、为什么这是缺陷而不是「功能没做」

模型不会先读描述再决定传不传 —— 它看到 `CaptureAppWindow` 这么用能成，自然照搬到 `DesktopScreenshot`。然后：

> 传了 `path` ⇒ 工具报成功 ⇒ 模型以为存了 ⇒ 下一轮去 Read 那个文件 ⇒ 文件不存在。

比直接报错更糟：**报错模型会换招，假成功让它继续往下走**。

## 四、两个选项（实施时二选一）

**A. 补上 `path` 支持**（倾向）
照 `ExecuteAppWindowCaptureAsync` 的形状抄：worker 侧解析 → 写进 `targetPath` → 主进程落盘。附带把描述改成与 `CaptureAppWindow` 对齐。

**B. 描述里明写「不支持落盘」**
成本近乎零，但模型仍会在需要落盘时无处可去 —— 而「截图存下来」是高频需求（做文档、做对比图）。

⇒ **建议 A**。理由：`CaptureAppWindow` 那套已经写好且带注释说明坑在哪，抄一遍成本很低；而 B 只是把「做不到」说出来，没解决需求。

## 五、待查（开工前）

- `src/main/ipc/desktop-control.ts:122` `captureDesktopScreenshot()` 是否已经支持接收 targetPath（`window:capture-self` 那条是支持的，桌面截图那条未必）。
- `DesktopScreenshotResult`（`desktop-control.ts:16`）有没有 `filePath` 字段。
- 落盘路径要不要过沙箱审批（`CaptureAppWindow` 有没有过）。

## 六、判据（验收，留给实施时钉）

1. 传 `path` ⇒ 文件真的存在，且内容与返回的图一致。
2. 不传 `path` ⇒ 行为与修复前一致（只回图，不落盘）。
3. 描述与 `CaptureAppWindow` 口径对齐。
4. 相对路径按会话 `workingFolder` 解析，不是主进程 cwd。

## 七、不做的事

- 不顺手改 `CaptureAppWindow` —— 它是对的。
- 不与 S-267 合并 —— 那条已在本迭代交付（渲染端截图诊断），本条在 worker + 主进程，改动面零交集。

## 八、实施记录（v3-iter-5 刀 6）

### 8.1 开工前先把 §五 三项查清（结论与登记时不同）

| 待查项 | 实际 |
|---|---|
| `captureDesktopScreenshot()` 支不支持 targetPath | **不支持**，但它下游的 `persistImageBuffer`（`src/main/lib/image-persist.ts:59`）**早就支持 `targetPath`** —— 只差一个参数透传 |
| `DesktopScreenshotResult` 有没有 `filePath` | **有**。S-283 已经给它补了默认落盘（数据目录 + 内容哈希命名），所以本条不再是「截图不落盘」，只是「落不到模型要的位置」 |
| 落盘要不要过沙箱审批 | **不用**。`CaptureAppWindow` 走同一条 `persistImageBuffer`，从来没经过审批；本条保持一致，不新增一条只有截图才有的关卡 |

⇒ 改动比登记时估的小：**要补的是「用户指定位置」这一路，不是补落盘**。

### 8.2 三处改动

1. **C# 侧抽函数**：`AgentRuntimeDesktopExecutor.ResolveCaptureTargetPath(requestedPath, workingFolder)`（`internal static`），原来在 `ExecuteAppWindowCaptureAsync` 里写死的那 8 行搬出来，两个 capture 方法共用。worker 侧解析的理由不变（主进程 cwd 是程序目录）。
2. **主进程透传**：`captureDesktopScreenshot(targetPath?: string)` → `persistImageBuffer({ targetPath, defaultDir, fileName })`；`native-agent-runtime.ts` 的 `desktop:screenshot:capture` 分支从 `params.targetPath` 取。
3. **描述 + schema**：`DesktopToolProvider.cs` 的 `DesktopScreenshot` 加 `path` 入参，文案与 `CaptureAppWindow` 口径对齐（"Pass `path` only to choose a different location"）；`delayMs` 补上「Capped at 5000」—— 代码里本来就有 clamp，描述里一直没说。

### 8.3 实施中撞到一个真边界

`ResolveCaptureTargetPath` 第一版用 `string.IsNullOrEmpty`：`path = "   "` 不是空串 ⇒ 走到 `Path.Combine(baseDir, "   ")` ⇒ Windows 把尾部空格吃掉 ⇒ **解析结果等于工作目录本身**，于是「工作目录」被当成目标文件路径。

测试第 10 条当场红。改用 `IsNullOrWhiteSpace`。

调用点其实已经 `.Trim()` 过，现实中撞不到 —— 但这正是「判据写在自己身上」的价值：以后谁新加调用点忘了 Trim，函数自己扛住。

### 8.4 新增门禁 `tests/WishfulClaw.CaptureTargetPathRegressionTests`（14 断言）

| # | 断言 |
|---|---|
| 1 | 相对路径解析到**会话工作目录**下（不是进程 cwd） |
| 2 | 只有文件名 ⇒ 落在工作目录根 |
| 3 | `../outside.png` 规范化成绝对路径（不许原样带出去） |
| 4/5 | 无 / 纯空白 workingFolder ⇒ 退回进程 cwd，仍是绝对路径 |
| 6/7 | 绝对路径原样采信；**中文路径**不被转走（真机数据目录就在中文用户名下） |
| 8~11 | `null` / 空串 / 纯空白 ⇒ `null`，绝不回落到工作目录本身 |

**反向验证两次**：① `baseDir` 写死 `Environment.CurrentDirectory`（缺陷原形）⇒ 红 `相对路径必须解析到会话工作目录下`；② `IsNullOrWhiteSpace` 退回 `IsNullOrEmpty` ⇒ 红 `纯空白必须返回 null`。两次都改回并复绿。
