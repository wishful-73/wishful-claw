# S-260：内置浏览器保活池 —— 上限 2 个会话，满了要明确告诉 agent

**性质**：资源治理 + 可观测反馈。不是「限制功能」，是「给常驻资源划上限，且让 agent 知道边界在哪」。

**归属**：**v3-iter-4（产品 1.0.4）**。登记于 v3-iter-3（1.0.3），随 S-247 内存治理同批。

**编号**：S-260。

## 1. 原话 / 来源

> 2026-10-28 16:22 老大（回答「保活上限定几个」）：

> 「有两个活着就行了，要是能提示 agent 已经有两个是最好的」

两条要求：
1. **常驻上限 = 2**：同时「活着」的会话浏览器最多两个，不是无限。
2. **满了必须告诉 agent**，不许静默处理。

## 2. 为什么「提示 agent」是这条的核心，不是附加项

现在的行为是**全量保活、无上限**：

- `RightPanel.tsx:281-296` 把所有会话的 browser tab **全部挂载**，只切 `opacity` / `z-index`
- `ensureRightPanelTabs`（`right-panel-tab-factories.ts:9-13`）就是 `tabs ?? []` —— **零上限**
- 每个 webview = 一个独立 renderer 进程（量级 80~150 MB/个，需实测校准）

加上上限之后，新问题立刻出现：**满了怎么办？**

| 做法 | 后果 |
|---|---|
| 静默 LRU 淘汰最老的 | **可能正在被杀掉的那个会话，它的 agent 正在跑浏览器任务** —— 工具调到一半 webview 没了，报「Browser view is not attached」，agent 完全不知道为什么，只能无脑重试 |
| 静默拒绝（抛一句「无法打开」） | agent 不知道该等、该换方案、还是该请用户介入，大概率反复重试同一件事 |
| **拒绝 + 说清楚谁占着、占的什么页面** | agent 能转述给用户、能自己决定等一会儿再试、或者改用别的工具 |

⇒ **上限和反馈必须一起做**，只做上限会比现在更难用。

## 3. 当前是否有「谁在用」的信息可依

**有一半，缺的正是「正在被 agent 使用」这个标记。**

| 信息 | 现状 | 位置 |
|---|---|---|
| 每会话浏览器状态（url / 标题 / deviceMode） | ✅ 有 | `browserStatesBySession`（`ui-store-interface.ts`） |
| 每会话 webview ref | ✅ 有 | `browserWebviewRefsBySession` |
| 当前展示的是哪个 scope | ✅ 有现成判定 | `isActiveBrowserScope(state, scope)`（`browser-session-helpers.ts`） |
| 面板开没开 | ✅ 有 | `rightPanelOpen` |
| **某个会话的浏览器是否正被 agent 调用中** | ❌ **没有** | 需要新增 pin 标记 |
| 最后访问时间 | ❌ 没有 | tab 上的 `createdAt` 只能算创建时间 |

⇒ S-260 要新增的最小状态：`browserLeasesBySession: Record<scopeKey, number>`（ref 计数），工具调用进入时 +1、`finally` 时 −1；以及 `lastAccessAt`。

## 4. 设计

### 4.1 保活池

`BROWSER_KEEPALIVE_LIMIT = 2`。池 = 当前**挂载了 `BrowserPanel`** 的会话（不是 tab 数量 —— 每会话最多一个 browser tab，`scopedRightPanelTabId('browser', sessionId)` 保证了这点）。

### 4.2 淘汰顺序（从最可牺牲到最不可牺牲）

| 级 | 条件 | 可淘汰？ |
|---|---|---|
| 0 | **当前展示的会话**（`isRightPanelScopeActive` 为真 —— 与 S-259 同一判据，见 §5） | ❌ 绝不 |
| 0 | **agent 正持有 lease**（`browserLeasesBySession > 0`） | ❌ 绝不 |
| 1 | 不可见 + 无 lease + 空闲最久 | ✅ 优先 |
| 2 | 不可见 + 无 lease（较新） | ✅ 其次 |
| 3 | 面板关着但曾是当前会话 | ✅ 再次 |

淘汰动作 = 卸载该会话的 `BrowserPanel`（webview 随之销毁）+ `setBrowserWebviewRef(null)` 清理 ref。**URL 留在 `browserStatesBySession` 里，不丢。**

### 4.3 一个都不许动时 —— 这才是「提示 agent」

返回结构化错误（沿用 `browser-native-ui.ts` 现有约定：execute* 抛错 → `handleNativeBrowserToolRequest` 的 catch 转 `{ content, isError: true, error }`，agent loop 继续），文案必须带足信息：

```
浏览器常驻已达上限（2 个会话）。当前占用的会话：
- 「修复登录 bug」 https://app.example.com/login （2 分钟前活跃，正在被该会话的 agent 使用）
- 「抓取价格数据」 https://shop.example.com/list （15 分钟前活跃）
请先让其中一个会话结束浏览器任务，或请用户关闭它的浏览器面板后重试。
```

要点：
- **列出占用者**（会话标题 + 当前 URL + 活跃时间 + 是否正在被用）
- 给出**可执行的下一步**（等 / 让用户关 / 换工具）
- 用 `isError: true` 而非静默成功 —— 让 agent 的状态机看得见

### 4.4 空闲回收（自动，不打扰）

不可见 + 无 lease + 空闲超过 `BROWSER_IDLE_EVICT_MS`（建议 5 分钟）⇒ 自动销毁，不提示。这条保证「两个会话开着但都没在动」时内存自己降下来 —— 也正是 S-247 想要的。

### 4.5 重新拉起（已有自愈路径，直接复用）

`browser-webview-helpers.ts:90-113` `ensureAttachedWebview` 已经实现「webview 不在了就用 `browserStatesBySession` 里的 URL 后台重开」，且带 `{ background: true }` 不抢 UI。**淘汰后重进这条路即可，不需要新写恢复逻辑。**

**但「透明恢复」这四个字要拆开说清楚**（2026-10-28 dev 审查追问「组件都卸载了，`waitForWebview` 那 10 秒里 agent 拿到的是什么」—— 实查结论如下）：

| 问题 | 答案 |
|---|---|
| 下一次工具调用会**报错**吗 | **不会**。`ensureAttachedWebview` 走自愈分支：读 `storedUrl` → `openBrowserTab(..., { background: true })` → `waitForWebview` 等挂载 → `waitForLoad` 等加载完 |
| 页面状态还在吗 | **不在**。是**重新加载**，不是「原进程复活」—— SPA 的运行时状态（填了一半的表单、滚动位置、DOM 状态）全丢，回到「刚从 URL 打开」的初始态 |
| 耗时呢 | 变长：`waitForWebview` 5 秒窗口（浏览器工具路径传的是 10 秒，`browser-native-ui.ts`）+ `waitForLoad` 30 秒窗口。agent 看到的是「这个工具慢了一次」，不是「失败了一次」 |
| 有什么前提不能破 | ① 淘汰**只卸载组件、不清 `browserStatesBySession`**（`url` 一丢，自愈分支会直接抛 `Use BrowserNavigate first`，那就真成失败了 —— §4.2 最后那句就是这条约束）；② 淘汰**不动 `rightPanelTabs`**，tab 留在列表里，否则下次挂载不上 |

⇒ **§4.3 的溢出文案不必写「可能先失败一次」**（它不会失败）。但**冷启动那条文案（如果要做）要写「会重新打开页面」**，因为对用户来说可感知的差别就是「页面刷新了一下，我刚才填的没了」。如果被淘汰时会话正有 POST 在途，重复提交是真实风险 —— 这也是一条**不该在 agent 正在发请求时淘汰**的理由，与「有 lease 不动」同级（§4.2 级 0）。

## 5. 与 S-259 的分工（别混）

| | 修什么 | 迭代 |
|---|---|---|
| **S-259** | **归属**：后台会话的工具调用不许改当前视图的开关（`rightPanelOpen` 全局单值错配） | v3-iter-3（1.0.3） |
| **S-260** | **容量 + 反馈**：常驻上限 2、满了告诉 agent、空闲自动回收 | v3-iter-4（1.0.4） |

**顺序**：S-259 必须先在。否则 S-260 把上限压到 2 之后，后台会话的每次导航仍会掀开用户面前的面板 —— 界面行为会更难解释（「它明明没开第三个，为什么我的面板自己跳」）。

**判据复用**：S-260 判「这个会话是不是主力/在不在前台」时，一律用 S-259 收口的 `isRightPanelScopeActive`（`right-panel-scope.ts`，只看 sessionId，与 tab 归属桶同源），**不要**改用 `isActiveBrowserScope`（它多比 projectId）。两把尺子换着用会在 projectId 一侧拿不到的边界上判错 —— S-259 实施时已经踩过一次，见 `S-259.md` §7.1。

## 6. 与 S-247 的关系

S-247 是「内存占用异常偏高」的**观测**需求（先让内存说话）。S-260 是这次观测里**最确定的一条可疑源**：

- 全量保活 + 零上限 ⇒ 开过浏览器的会话越多，常驻 renderer 进程越多
- 这条可直接验证：连开 5 个会话各开一个网页，用 S-247 的采样看进程数与 RSS

⇒ 建议 S-247 的采样先落，S-260 用它的数据定 `BROWSER_KEEPALIVE_LIMIT` 与 `BROWSER_IDLE_EVICT_MS` 是否合适（2 和 5 分钟是当前判断，非实测）。

## 7. 验收

1. 连开 3 个会话的浏览器 ⇒ **只有 2 个 webview 挂载**，第 3 个在打开时触发淘汰或拒绝
2. 第 3 个会话的 agent 调浏览器工具且无可淘汰对象 ⇒ **收到结构化错误，含两个占用者的标题/URL/活跃时间**，且 agent 能把它转述给用户
3. **正在被 agent 使用的会话绝不被回收** —— 让 A 会话跑一个长浏览器任务，同时在 B/C 来回切，A 的 webview 全程不消失
4. **当前展示的会话绝不被回收**
5. 被淘汰的会话再进 ⇒ 自动用原 URL 后台重开（不抢 UI、不需要用户重新输地址）
6. 两个会话都不可见且空闲 5 分钟 ⇒ 自动回收，内存下降（用 S-247 的采样读数验证）
7. 用户手动关掉某会话浏览器面板 ⇒ 立即释放一个名额

## 8. 风险

- **回收时机与 agent 长任务冲突**：靠 lease 计数兜，但 lease 只在工具调用期间持有 —— **两次工具调用之间的空档（agent 在思考）也会被判定为空闲**。所以优先淘汰级 1 必须用「空闲最久」而非「不在调用中」，且 `BROWSER_IDLE_EVICT_MS` 不宜过短（5 分钟起步）。
- **`partition` 不随销毁释放**：webview 销毁不删 cookie/cache，这是 S-260 之外的独立话题（每会话隔离存储，见 S-259 §4 层 3 的讨论记录）。
