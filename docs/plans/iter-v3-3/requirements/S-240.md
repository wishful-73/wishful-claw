## 2. 目标

让 `extension.json` 能声明「我要一个**用户可点的视图**」和「我有一批**需要下载的资产**」，并把视图入口自动渲染到导轨上 —— **主程序不认识具体功能。**

本号只做**声明与入口**，不做窗口（S-241）、不做下载（S-242）。

## 3. 现状（2026-10-27 实读源码）

### 3.1 manifest 已有 80%，缺 `views` / `assets`

`src/shared/extension-types.ts` 的 `ExtensionManifest` 已支持 `tools` / `renderers` / `components` / `mcpServers` / `configSchema` / `permissions` / 聚合资源（`skills` / `agents` / `commands`）—— **没有 `views`，也没有 `assets`。**

`components` / `renderers` 是 `type: 'html'` 的**聊天窗内卡片**，不是独立功能页。

### 3.2 C# 侧是 manifest 的第二份模型

`src/runtime/WishfulClaw.Agent/Modules/Extensions/ExtensionModels.cs:20` `NativeExtensionManifest` —— 与 TS 侧**同一份数据的两个模型**，改一边必须改另一边，否则解析层丢字段。

配套：`ExtensionManifestReader.cs`（读盘）/ `ExtensionManifestNormalizer.cs`（归一）/ `ExtensionManifestStore.cs`（存取）。

### 3.3 导轨入口是硬编码三项，不是 manifest 驱动

`src/renderer/src/components/layout/WorkspaceSidebar.tsx:215-219`：

```ts
const extensionItems = [
  { id: 'draw', ... },
  { id: 'automation', ... },
  { id: 'taskboard', ... }
]
```

⇒ 现有「Extensions」是**固定下拉三项**（Draw / Automation / TaskBoard），**与 extension manifest 完全无关**。插件视图要新增一路来源，不能指望复用。

### 3.4 安装链路已通

`extension-handlers.ts` 已有 `extension:install-from-folder` / `update` / `remove` / `open-folder` / `read-asset` / `storage-*`。本号不动安装，只动清单与入口。

### 4.2 归一化输出是白名单 —— 两条必须守住的纪律

`extension/list` 返回的不是插件原文件，而是 `NormalizeManifestNode` **重建**的 `JsonObject`。没显式写出来的字段，渲染端永远看不见 —— 不报错、不 Warn，表现为「插件装了、入口不出来」。

| # | 纪律 | 违反后的表现 |
|---|---|---|
| 1 | `views` / `assets` 必须显式写进返回的 `manifest` 节点；`Count > 0` 才写，空数组不写（老插件线格式零变化） | 渲染端 `manifest.views` 恒为 `undefined`，入口永远不出现 |
| 2 | 「tools / views 至少一项」的校验必须**抛错**，不能静默放过 | `ListExtensionsCore` 的 catch 只 `Warn` 后 `continue` ⇒ 插件静默消失，用户装了看不见 |

### 4.1 `assets` 只声明 id，URL 归主程序（2026-10-27 14:17~14:19 老大定）

> 14:17「这个可以我们内置下载么，我的意思是从哪里下载，用户只需要点击下载就行，以及知道有这个功能」
> 14:19「插件我们可以内置一批目录，用户在这个插件上点击启用并下载，相当于我们帮他找到了路径这些，当然**路径过期那是以后的事情**了」

```json
"assets": [
  { "id": "asr/qwen3-asr-0.6b", "optional": false }
]
```

**插件里不出现任何 URL / 体积 / 哈希。** 那张表由主程序内置，见 [S-242](S-242.md) §4.1。

理由（不是洁癖，是三条实的）：

| # | 理由 |
|---|---|
| 1 | **换源 / 下架 / 国内分流**都只需改主程序表，不用改插件、不用让插件项目跟着发版 |
| 2 | URL 散在插件里，用户看到的是插件给的地址 —— **投毒面在插件侧**；收归主程序后只有一个可审计入口 |
| 3 | 客户端要能**在用户点下载之前**报出体积（489 MB？1.2 GB？）与用途。这个信息插件给不了，只有主程序表里有 |

`id` 是全程序唯一的资产键（带命名空间前缀 `asr/…`），**主程序表里查不到就明确报「未知资产」**，不静默跳过。

## 5. 验收

1. 装一个假插件（`extension.json` 只声明 1 个 `views`，无 assets、无 tools）
2. 启用后，导轨「Extensions」下拉出现该项，顺序符合 `nav.order`
3. 点它 → 提示「窗口能力未就绪」（不崩溃、不白屏）
4. 停用该插件 → 入口消失
5. 卸载 → 入口消失且无残留
6. 老插件（无 `views`）行为零变化（Draw / Automation / TaskBoard 仍在）

### 5.1 自动化部分已落地（2026-10-28，v3-iter-4 第 1 刀）

`tests/WishfulClaw.ExtensionManifestRegressionTests`（已进 `tests/WishfulClaw.Tests.sln`，`npm test` 收录为 `ExtensionManifest`，**13 条断言**）。

它刻意走渲染端真实那条路 —— `ExtensionManifestStore.List` → `ListExtensionsCore` → `ReadNormalizedManifestNode`。另一条 `ExtensionManifestReader` 的 C# 模型路径 `List` 根本不走，测了也证明不了渲染端能看见。数据目录用 `WISHFULCLAW_DATA_DIR` 指到临时目录，不碰本机数据。

| 断言 | 对应验收项 |
|---|---|
| 纯视图插件（无 `tools`）能被列出，`tools` 归一化为空数组 | 1 |
| `views[0]` 的 `entry` / `title` / `mode: window` / `nav.order` 原样保留 | 2 |
| `assets[].id` + `optional` 归一化正确 | —— |
| 老插件（有 `tools` 无 `views`）不凭空多出 `views` 字段 | 6 |
| `entry: "../../evil.html"` 的插件被拒，日志实测为 `entry must stay inside the extension directory` | 风险 2 |
| 既无 `tools` 又无 `views` 的插件被拒，日志实测为 `extension must define at least one tool or view` | §4.2 纪律 2 |

**仍待真机验：3 / 4 / 5** —— 点入口的提示、停用后入口消失、卸载无残留，都是 UI 行为，自动化覆盖不到。

## 6. 风险

| # | 风险 | 处置 |
|---|---|---|
| 1 | **两份模型漂移**（TS + C#） | 同一刀内改两边；**已落地**：`ExtensionManifest` 回归套件断言 `views` / `assets` 是否真的出现在归一化后的 JSON 输出里 |
| 2 | `views[].entry` 路径越界（`../../` 读到插件目录外） | 归一阶段强校验：解析后 `Path.GetFullPath` 必须仍在插件根内（`ExtensionManifestReader.ValidateManifestEntry`，归一化器与强类型读取共用）；**已落地**：`../../evil.html` 一条断言 |
| 3 | 入口来源混用（硬编码 + manifest）会让侧栏逻辑变脏 | 硬编码三项保留原地不动，manifest 视图**追加**在下方，**不改原有结构** |
| 4 | 插件写了主程序表里没有的 `asset id` | **明确报「未知资产」**并计入插件诊断，不静默忽略 —— 静默会变成「界面正常但功能就是不能跑」，最难查 |

## 7. 不做什么

- **不做窗口** —— 归 S-241
- **不做下载** —— 归 S-242
- **不做 `mode: 'panel'`**（主区内嵌）—— 老大 14:00 定「先只做 window」，panel 要动 `activeNavItem` 那套陈旧路由，本迭代不碰
- **不改内置四插件**（image / browser / desktop-control / codegraph）—— 是否改 manifest 驱动另议
- **不做插件市场 / 签名**
