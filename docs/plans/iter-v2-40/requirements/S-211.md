## 一、现象（老大实测数据）

- 微信渠道发图，Agent 完全拿不到图片内容，只收到一句 `[User sent an image]`。
- sqlite 直查 `index.db`：

| 消息 id | content | content 长度 | meta 长度 |
| --- | --- | --- | --- |
| `user_1792461192647` | `[User sent an image]` | 20 | **0** |
| `user_1792461638808` | `[User sent an image]` | 20 | **0** |

- 按消息 id 全域搜文件（`.wishful-claw` / 微信接收目录 / Temp / Downloads / C 盘用户区 / F 盘工作区）—— **全空，没有落盘**。
- 能力侧：channel 相关 5 个能力**全是发送侧**（`ChannelSendFile` / `ChannelSendImage` / `PluginListGroups` / `PluginReplyMessage` / `PluginSendMessage`），**没有「取入站附件」的能力**。
- 全库搜 `sent an image` 历史**仅这两条** ⇒ 无法判定是回归还是从未实现。**静态查完的答案是「从未实现」**（见 §2）。

## 二、根因（已钉死）

### 2.1 断点在渲染端：图片 base64 带到了、但没人消费

上游其实是**好的**，微信确实下载了图片：

- `src/main/channels/providers/weixin/weixin-service.ts:390-414` —— `api.downloadInboundImage(...)` 拿到 buffer，转 base64 放进 `images: [{ base64, mediaType }]`，随 `ChannelIncomingMessageData` 发出；下载失败才改写 content 为 `[User sent an image but download failed: …]`。
- `src/main/channels/auto-reply.ts:251-257` —— task payload 里 `content` 是占位符，**`images: data.images` 一并带上**，发给渲染进程。
- `src/renderer/src/hooks/use-channel-auto-reply.ts:255-258`：

```ts
const sendPromise = useChatStore.getState().sendMessage({
  provider,
  messages: [{ role: 'user', content }],   // ← content 是字符串占位符
  ...
```

**`task.images` 全文件只出现在第 48 行的类型声明里，从未被读取。** 图片在这一步被彻底丢掉 —— 所以 DB 里 `content` 是占位符、`meta` 长度为 0（图片块压根没进消息对象）。

而聊天窗发图走的是另一条路：`ImageBlock { type:'image', source:{ type:'base64', mediaType, data } }`（`lib/api/types.ts:100-112`）拼进 content 数组，所以「聊天窗能用、渠道不能用」——**不是渠道下载的问题，是一条通道没接上**。

### 2.2 八个渠道的入站现状（10:10 全量核查）

**有入站实现的只有 4 个渠道**（其余 4 个连 `incoming_message` 都不发）：

| 渠道 | 入站 | 图片现状 | 位置 |
| --- | --- | --- | --- |
| 微信 | ✅ | **已下载 base64**，带在 `images` 上；失败改占位符文案 | `weixin-service.ts:390-414` |
| 飞书 | ✅ | **已下载 base64**，带在 `images` 上；失败改占位符文案 | `feishu-service.ts:192-208 / 277` |
| QQ | ✅ | **从未下载** —— `describeAttachments` 只读 `content_type` 判类型，`attachments[].url` 被丢掉，只留占位符 | `qq/parse-ws-message.ts:57-69` |
| 钉钉 | ✅ | **连消息都丢** —— 只读 `payload.text.content`，从不看 `msgtype`，图片消息解析出空字符串后在 `dingtalk-service.ts:178` `if (!content) return` 直接丢弃 | `dingtalk-service.ts:160-178` |
| Discord / Telegram / 企业微信 / WhatsApp | ❌ | 纯发送桩（`discord-service.ts` 之类只有 `sendMessage` / `getGroupMessages` 空实现），**没有入站链路** | — |

⇒ **微信 / 飞书只差渲染端这一处消费**（本条 S-211 解决）；**QQ 差解析层补下载**（S-212）；**钉钉差解析层补媒体消息**（S-213）；**另外 4 个渠道的图片问题是伪命题**，它们连文本入站都没有。

⇒ 微信 / 飞书**只差渲染端这一处消费**；QQ 需要补下载。

### 2.3 落库行为（决定了「落盘」是否必须）

`db-helpers.ts:128-146`：`content` 列只存 `msg.text`，**数组块整体 JSON 进 `meta` 列**（`:134` `meta.content = msg.content`）。读回时 `:169` `if (Array.isArray(meta.content)) msg.content = meta.content`。

⇒ 修好之后 base64 会整块进 `meta` 列：**能持久化、刷新能看见图，但每张图会把 DB 撑大**（base64 比原图大 ~33%）。这是老大给的「修复方向 ①收到图片落盘」要衡量的账。

## 三、修复方向

### 3.1 主修（对症）：把 `task.images` 拼成 `ImageBlock` 交给 `sendMessage`

`use-channel-auto-reply.ts:255` 改成：

```ts
const contentBlocks = buildUserContent(content, task.images)   // 纯函数，见 3.3
messages: [{ role: 'user', content: contentBlocks }]
```

- 无图时仍传字符串，**行为零变化**；
- 有图时传 `[{ type:'text', text: content }, { type:'image', source:{ type:'base64', mediaType, data } }]`，与聊天窗同构 ⇒ 模型侧、渲染侧、落库侧全部走既有链路，**不需要新造任何东西**。

### 3.2 可选增强（老大给的「落盘 + 记路径」/「暴露取附件能力」）

这两条**不解决本 bug**（本 bug 是图片压根没进消息），它是「避免 base64 撑 DB」和「让 Agent 能主动再取」的优化，建议单独排：

- 落盘：`userData/channel-attachments/{sessionId}/{messageId}.png`，`ImageBlock` 用 `source:{ type:'url', url:'file:///…' }` 或仍走 base64 + `meta` 只记路径。
- 取附件能力：给 Agent 一个 `ChannelFetchAttachment(messageId)`，用于历史消息里图片已被清理的场景。

**本需求只做主修**，可选增强另行登记（除非老大要一并做）。

### 3.3 纯函数 + 单测

`buildUserContent(text, images)` 抽成不 import IPC 的纯函数（`lib/channels/inbound-content.ts`），node 侧直接覆盖：无图 → 字符串原样；一张图 → 两块的数组；多张 → 按序；`mediaType` 缺失 → 兜底 `image/png`。

## 四、非目标

- **不回补历史**：DB 里那两条只有占位符，图片字节在内存里已销毁，**不可恢复**。
- **不改发送侧能力**：`ChannelSendImage` 等 5 个能力不动。
- **不动 `downloadInboundImage` 实现**：下载已是好的（失败分支也有明确文案）。
- **不做音频同断点的完整修复**：`audio` 字段在 task payload 里同样是死负载（`handleSessionTask` 未消费），但微信语音走 `voice_item.text`（已转文字），实际影响面待评估 —— **登记在 §六 第 3 问，本轮默认不动**。

## 五、决策点（**已处置，`91fbbd7f`**）

1. **base64 直入 `meta` 是否可接受**（每张图 ≈ 原图 ×1.33，长期会话 DB 会涨）。**已按默认实施**：本轮走现链路、不落盘，DB 膨胀记 tech-debt；要落盘则换 `source.type = 'url'` + 补落盘工具，单独立项。
2. **QQ 是否一并补下载** —— **已定：拆 S-212 单做**（老大 10:10「可以不同渠道登记不同的需求」），本条不碰 QQ 解析层。**S-212 已实施 `49a27335`。**
3. **音频是否一并处理**（`task.audio` 同为死负载，飞书语音下载后 renderer 未消费）。**本轮未动** —— 等确认现实触发面后再立。**仍挂账。**

## 七、风险

- **`content` 变成数组后的下游**：`extractTextFromContent`（`use-channel-auto-reply.ts:398-406`）已能处理数组，但渠道侧若还有别处按字符串处理用户消息，要一并查。
- **会话标题**：渠道会话标题可能截取 `content` 字符串，数组要取 text 块。
- **大图**：渠道图片未做尺寸/字节上限，base64 进 WS 与 DB 都可能很大，必要时加「超过 N MB 只留占位符 + 提示」的护栏（默认不加，先看实测）。
