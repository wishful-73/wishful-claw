# S-309 · 工具调用没有兜底超时 —— 一次调用挂住，整个 agent 回合冻结 16 小时

> 状态：**✅ 已实施（核心 §4.2 + 11-04 的 P1 误杀修复），门禁通过，待真机验收；§4.3 / §4.4 未做，见文末**
> 登记：2026-11-04 13:25
> 实施：2026-11-04（见文末「§实施记录」）
> 来源：老大 2026-11-04 13:25 原话「你这个行为我个人认为是 bug 需要登记 bug」
> 触发场景：2026-11-04 13:25 之前，生产实例（老大正在用的这个会话）从 11-03 21:16 起**静默冻结约 16 小时**
> 关联：S-308（执行体缺停止手段，同源：执行体既停不掉、也不超时）

## 一、现象

### 1.1 时间线（全部取自会话与日志实录，无推测）

| 时刻 | 事实 |
|---|---|
| 11-03 21:09 | 老大派任务：自查 Tauri 壳缺口，明确「主动手」 |
| 11-03 21:15:05 | worker 启动，pipe 连通，主窗口创建 —— **壳运行正常** |
| 11-03 21:16:09 | 一个新 `WishfulClaw.Worker` 被拉起（此后成为孤儿进程） |
| 11-03 21:16 ~ 21:20 | 我在跑「清孤儿进程 / 核代码完整性」的排查命令；其中 2 条返回，2 条被 `interrupted`，**随后整个回合再无任何输出** |
| 11-04 13:25 | 老大发现卡住，发消息「你这是被一个命令卡了16小时啊」，会话才恢复 |

**16 小时里：没有报错、没有超时提示、没有中断、CPU 与网络都不该有负载。用户侧完全无法分辨「卡死了」还是「在思考」。**

### 1.2 卡住的是一条普通命令，不是重活

被挂住的两条，内容是：

```text
Stop-Process -Id <pid> -Force; Start-Sleep -Milliseconds 800; Get-Process ...
Select-String -Path shell-tauri\src\main.rs -Pattern ...
```

**都是毫秒级就能跑完的东西。** 也就是说：不是「命令太重跑不完」，而是「调用发出去了、结果永远不回来」。

## 二、根因：两层，第二层才是要修的那层

### 2.1 第一层（近因）：某一次工具调用的响应没有回到调用方

具体卡在哪个调用、为什么没回，**当前无法定论**，需要单独取证（见 §4.1）。可疑面有三个，都要查，不预设结论：

| 可疑点 | 为什么可疑 |
|---|---|
| `Get-Process` / `Stop-Process` 在目标进程句柄上阻塞 | Windows 上枚举进程句柄本身就可能卡；两次被挂的命令**都涉及进程操作** |
| 子进程 stdout/stderr 满管道后写端阻塞 | 长命令输出没被消费时，父进程 `wait` 永远不返回 —— 这是最经典的一类「假死」 |
| 工具调用链路上没有整体超时 | §2.2 |

**我没能给出确切结论，就不写确切结论。** 这一层必须先拿到实证，否则任何「修复」都是猜。

### 2.2 第二层（真缺陷）：**任何一次工具调用都没有兜底超时**

这一层不依赖 §2.1 的结论 —— 不管近因是什么，**它都不该演变成 16 小时冻结**。

对照来看，本项目在别处是有超时的，唯独 agent 这一侧缺：

| 位置 | 有没有超时 | 证据 |
|---|---|---|
| Rust 壳 → worker 的请求 | ✅ 有（默认 180 s，可传参覆盖） | `worker.rs:42` `DEFAULT_TIMEOUT: Duration = Duration::from_secs(180)` |
| worker → 渲染端的反向请求 | ✅ 有（壳侧 150 s 独立兜底） | `shell-tauri/src/reverse.rs` `RESPONSE_TIMEOUT` |
| **agent 调用工具 → 拿到结果** | ❌ **无** | 见下 |

现状是：工具执行这一侧只在**工具自己实现的代码里**各自设超时（比如 shell 工具可能有自己的 timeout），**调用方（agent loop）没有一层统一的「到点必回」**。一旦某个工具实现漏了、或者卡在了实现之外的环节（进程管理、管道读写、IPC），**外层无从感知，只能干等**。

⇒ **这是设计缺陷，不是某个工具的 bug。** 缺的是「不管工具内部发生什么，调用方都要在有限时间内拿到一个结果或一个明确的失败」。

### 2.3 第三层（放大因素）：用户侧看不到「卡在哪」

即使有了 §2.2 的超时，如果界面在等待期间还是显示「思考中」，用户依然只能靠猜。

现在的观感问题：

- 工具卡住 ⇒ 界面停在最后一条工具卡上，**不显示「已耗时」**，也没有「这条调用是不是异常」的判断
- 没有「正在等待：`Bash`，已 12 分钟」这类信息
- 「停止」按钮在这种状态下**是否真的能中断卡住的调用，未验证**（很可能不能 —— 因为中断靠的是取消 token，而卡住的线程根本没在检查 token）
- **子 agent 那一路连进度都看不到**：`SubAgentStatus` 在子 agent 运行期间恒报 `0 calls / 0 iterations`（进度只在整轮跑完之后写一次），于是「在跑但看不见」会被误判成「没启动」。这条已于 2026-11-04 单独修掉，见 [S-311](S-311.md)。

## 三、影响面

| 场景 | 后果 |
|---|---|
| 普通单次工具调用挂住 | 整个回合冻结，用户以为在思考，实际什么都没发生 |
| 挂住时用户发新消息 | 会话已冻结，新消息也进不来（本次即如此，16 小时里我根本没收到任何消息） |
| 挂住时用户点「停止」 | **未验证能否生效**，很可能不生效 —— 卡住的位置不在取消检查点上 |
| 长时间挂住后恢复 | 一次性涌入大量陈旧上下文，容易引发后续判断错乱（本次恢复后我第一反应是继续跑命令排查，而这恰是用户明令禁止的） |
| 费用 | 挂住期间虽无 token 消耗，但**用户的工作被硬生生截断 16 小时** |

**最后一条是本需求真正的成本 —— 不是钱，是用户的时间。**

## 四、方案

### 4.1 先取证，别先修

要定位 §2.1 的近因，**必须有不依赖「重跑现场」的手段**（老大已明确不接受「挂探针 + 复现」这种路子，也不该为一次偶发冻结去污染代码）。可行的取证方向：

1. **现有日志是否够（零成本，先做这条）**：查工具调用有没有「开始 / 结束」两条日志配成对。**只有开始、没有结束，就是最直接的证据**，且不需要新增任何代码。反过来，如果现在的日志连配对都没有 —— 说明它本来就不足以取证，那这条日志得跟 §4.2 一起补。
2. **调用栈快照**：冻结发生时，从外部（非注入代码）抓一次 agent 侧线程栈 —— 是阻塞在 `Read`、`WaitForExit`、还是 `WaitOne`，一眼就能区分
3. **命令级最小复现**：在**独立进程**里跑 `Get-Process` / `Stop-Process` 组合，看是否偶发不返回（不进主仓代码）

### 4.2 外层竞速超时（核心，与 §4.1 的结论无关，可以先做）

在 **agent 调用工具的那一层**加一道 race，**不改任何工具实现**：

```text
发出调用  ─┬─ 工具返回   → 正常继续
           └─ 计时器到点 → 立刻把「工具 X 执行超时」作为失败结果交给模型
                          → 回合继续，用户能继续干活
```

**语义必须先说清：超时是「放弃等待」，不是「取消执行」。**

这一点决定了本需求的边界 —— 它**不需要执行体配合**，所以能独立于 S-308 成立。卡住的后台执行体仍然挂着，那是资源洁癖问题（S-308 的活）；用户能感知的故障（回合冻结）在这里就被切断了。

#### 4.2.1 必须分档，不能一刀切

| 调用类型 | 上限 | 超时后怎么算 |
|---|---|---|
| 读 / 查 / 列 / 搜索 | 60 s | 失败 |
| shell、终端命令 | 600 s（工具自带默认）+ 30 s 外层宽限 = **630 s** | 失败 |
| 构建 / 安装 / 下载 | 1200 s | 失败（AOT 构建本身分钟级，不能按普通命令算） |
| **提问类**（ask-user） | **300 s** | **「用户暂离」，不是失败** —— 见 §4.2.4 |
| **审批类**（工具审批、沙箱申请） | **300 s** | **未获批准**（安全默认拒绝）—— 见 §4.2.4 |
| **计划评审** | **300 s** | **待确认**（不自动通过）—— 见 §4.2.4 |
| **background 子 agent** | **豁免** | 它的设计目标就是活得比父 run 长 |

**等人也要有时限。** agent 不该因为用户离开键盘就整体停摆 —— 但要区分「可以绕过去」和「不许绕过去」，见 §4.2.4。

#### 4.2.2 三条配套，缺一条就会误杀

1. **工具自带超时优先**：工具可声明自己的上限，外层取 `max(工具声明, 档位默认)`。长任务不必为了绕过超时去改代码，外层又兜住了「工具压根没声明」和「声明了但不生效」两种情况。
2. **收口必须在调用方，不在工具实现里**：工具会一直加，谁漏谁就是下一个黑洞。放在调用方，新工具自动继承。
3. **超时结果必须显式**：
   - 回给模型的是**明确的失败**，不是空结果 —— 空结果会让模型以为「这工具返回了空」，然后接着瞎编
   - 落一条日志，带工具名、实际耗时、上限值（同时也是取证材料）
   - UI 上那次调用显示「超时，已等 N s」，不是成功、不是空白

   —— 但「等人」这三档的超时**不是失败**，见 §4.2.4。

#### 4.2.3 两个实现坑，提前钉住

**① 过期结果不能回灌（最容易写漏、最难在测试里发现）**

超时放弃之后，那个卡住的调用**可能几分钟后又返回了**。必须有一个「已放弃」标记，让它回来的结果被丢弃 —— 否则模型会收到同一调用的两条结果，上下文直接错乱。

**② 超时不等于清理**

放弃等待之后就结束，**不在本需求里回收执行体**。硬要在这里顺手回收，就等于把 S-308 的取消句柄问题拖进来，边界立刻糊掉。等 S-308 修好，这里再顺手接上。

#### 4.2.4 「用户暂离」——等人超时的语义（老大 2026-11-04 13:32 口径）

老大原话：

> 提问等待5分钟，5分钟不回答，识别用户不在导致超时，进行其它操作。而不是默认失败之类的

⇒ **等人超时不是失败，是「用户暂离」这个明确状态。** agent 拿到它之后应该去干别的，不是整轮判死。

但三类「等人」的后果完全不同，**必须分开处理，不能一刀切成「继续」**：

| 类别 | 超时语义 | agent 该怎么做 | agent **不许**怎么做 |
|---|---|---|---|
| **提问**（ask-user） | `user-away`，**不是失败** | 继续执行不依赖该答案的部分；稍后可再问 | 不许反复重问刷屏（同一问题重问 ≤ 2 次，间隔 ≥ 5 分钟） |
| **计划评审**（plan/review） | `pending-confirmation`，**不自动通过** | 可先做**不依赖计划确认**的部分，或停在这里等 | 不许把「没确认」当成「默认同意」 |
| **审批**（工具审批、沙箱申请） | `not-approved`，**安全默认拒绝** | 放弃该操作，如实告知未获批准 | **绝不许绕路** —— 不许换工具、换参数、换路径去达成同一目的 |

**最后一行是安全底线，不能松。** 超时放行、或者 agent 换条道偷偷把事办了，都是比「冻结」更严重的事故。

其余要点：

- **问题本身不销毁**：ask-user 超时只是 agent 不等了，**问题卡片仍在会话里**。用户回来照样能回答，答案依然有效（作为后续上下文补进）
- **回给模型的话要可执行**，不能只写「超时」。要写成类似：

  > 用户暂未响应（已等 5 分钟）。请继续执行不依赖该答案的部分；稍后可用同一问题再问一次。已完成的部分不要重做。

- **回来要有交代**：用户离开期间攒下的未回答问题 / 未审批项，回来时应能看到「有 N 项在等你」，而不是散落在聊天记录里被淹没
- 用户主动点了「停止」的，走取消，**不算暂离**（两者在 UI 与日志里要能区分）

### 4.3 UI 侧：让「在等」和「卡住」可区分

- 执行中的工具显示**已耗时**
- 单条工具超过阈值（比如 2 分钟）时，卡上给一个**「可能已卡住」的弱提示**，不是弹窗、不改布局
- 停止按钮在这种状态下要有明确反馈（点了之后是否真的停了）

### 4.4 本次会话的特殊情况要一并处理

本次冻结期间，**新消息完全进不来**，直到冻结解除才一次性到达。这意味着「卡住」时用户连「提醒一下」都做不到。

⇒ 至少要保证：**工具卡住不影响会话接收新消息**。用户能发出来、能看到自己发出去了，「卡住」就变成了一个可沟通的问题，而不是一个黑洞。

## 五、范围边界

- **不改**各工具自己的超时实现（§4.2 是外层兜底，两者并存，不互相替代）
- **不动** worker ↔ 壳的既有超时值（180 s / 150 s 是另一条链路，本次不碰）
- **不在主仓加探针取代码**（老大已明确反对；取证走 §4.1 的外部手段）
- **不在本需求里清理后台残留执行体** —— 那是 S-308 的活，本需求只负责「不冻结」
- **不与 S-308 合并**：308 改的是 worker 侧可触达的取消句柄（执行体停得掉、状态如实），309 改的是 agent 侧的放弃等待（调用方不再傻等）。两条线改的位置、验收判据都不同，捆在一起会互相拖累
- 不涉及内存 / 渲染性能（那是 S-247 那条线）

## 六、验收

1. 人为让一次工具调用不返回（在**独立进程**里模拟，不进主仓），**调用方在设定上限内必须拿到失败结果**，回合继续，不冻结。
2. **调用方侧不留悬挂等待**：反复触发 20 次，等待表 / 计时器 / 句柄不持续上涨。
   —— 注意本需求**不要求**那个被放弃的执行体消失（那是 S-308 的验收项），只要求「等待」这一侧干净。
3. **过期结果被丢弃**：让一个被判定超时的调用在之后才返回，**模型不得收到第二条结果**，上下文不错乱。
4. UI 上该次调用显示为超时（不是成功、也不是空白），并带耗时。
5. 工具卡住期间，**用户发新消息能立刻收到**。
6. **等人超时语义正确**：
   - ask-user 5 分钟无响应 → 返回「用户暂离」，**agent 继续干别的、不判失败**；问题卡片仍在，用户回来能答、答案仍有效
   - 审批类 5 分钟无响应 → **未获批准**，且 agent **不换道绕行**（换工具/换参数达成同一目的 = 验收不通过）
   - 计划评审 5 分钟无响应 → **不自动通过**
   - 用户主动点「停止」与「暂离」在 UI 与日志中**可区分**
7. 正常工具调用的行为、耗时统计、既有 UI **零变化**。

## 七、工作量

| 部分 | 估计 | 说明 |
|---|---|---|
| §4.1 第 1 条：查日志有没有开始/结束配对 | **近乎零成本** | 不碰代码，可能直接定案 |
| §4.2 调用层竞速超时 + 分档 + 「用户暂离」语义 | 中 | 核心；含「过期结果丢弃」、审批不绕路 |
| §4.3 UI 耗时 / 弱提示 / 停止反馈 | 小 | 与现有工具卡样式一致，不加弹窗 |
| §4.4 卡住时仍可收消息 | 中 | 取决于阻塞点在哪，可能要等 §4.1 定论 |
| §4.1 其余取证（栈快照 / 独立复现） | 小 | 仅当第 1 条不足以定案时才做 |

**排刀建议**：

1. **先跑 §4.1 第 1 条**（查日志配对）—— 零成本，且可能直接定案
2. **再做 §4.2**（放弃等待 + 分档 + 豁免）—— 这条做完，16 小时冻结这类事故就断了根，与 §4.1 的结论无关
3. §4.3 紧随 §4.2（超时了要看得见，否则等于没超时）
4. §4.4 视阻塞点是否在收消息路径上，可能需要拆到后续

**本需求独立成刀，不与 S-308 合并** —— 两者改的位置、验收判据都不同（见 §五）。

**「构建 / 安装 / 下载 1200 s」没有按命令文本去猜**。从命令字符串判断「这是构建还是普通命令」猜错的两种代价都不小（误杀正常长任务 / 漏掉真卡死），改由 §4.2.2 第 1 条落实：工具在自己的入参里声明 `timeout`（毫秒），外层取 `max(声明, 档位默认)`。

> **2026-11-04 订正（dev 实测发现 P1）**：上面这段原本还写了一句「Shell 工具默认就声明了 600 s，所以 shell 档实际是 600 s，不会误杀」——**这句话是错的**，而且当时的实现与它自相矛盾。`ShellExecuteTool.DefaultTimeoutMs = 600_000` 只是 C# 类内常量，而 `MaxWithDeclared` 读的是**入参 JSON** 里的 `timeout` 字段；模型自主调用时通常不传这个参数，于是 `GetInt` 返回 0、直接回落到档位 180 s。实测后果：第一次调 Bash 就在第 180 秒被中断，日志 `limitMs=180000`；`dotnet build` / `npm run build` 这类本迭代门禁命令一过 3 分钟就被判超时，工具还在跑、结果被丢弃，模型收到「已放弃」后可能重跑一遍。
>
> 修法：`DefaultTimeoutMs` 改 `public const`，`ToolCallTimeout.ShellLimit` 直接引用它（不留第二个魔法数字），并新增 `GraceMs = 30_000` —— 外层比工具晚一步，让工具先报自己的 exitCode 124，外层只兜「工具压根没返回」。测试同步改成钉 `630 s`，并新增一条「shell 档不得低于工具自带超时」的断言防再犯。

### 语义落实

- **超时 = 放弃等待**，不取消执行。`RaceAsync` 到点即返回，卡住的执行体照旧挂着 —— 那是 S-308 的边界，这里不回收。
- **过期结果丢弃**：放弃后给那个 task 挂 `OnlyOnFaulted` 续接吞异常（否则变成 UnobservedTaskException），它的返回值不回灌给任何人。
- **用户取消 ≠ 超时**：竞速里先 `ThrowIfCancellationRequested()` 再报超时，两者在 UI 与日志可区分。
- **超时结果显式**：回给模型的是带标记的失败文本（`[TOOL TIMEOUT]` / `[USER AWAY]` / `[NOT APPROVED]` / `[PENDING CONFIRMATION]`），不是空结果。
- **日志取证**：`agent tool timeout runId=… tool=… kind=… limitMs=… elapsedMs=…`，工具名、实际耗时、上限一条齐 —— 也是 §4.1 第 1 条「开始/结束配对」缺的那个「结束」。
- **审批超时不放行**：300 s 没人回答 ⇒ 按「未获批准」走，文案明确禁止换工具/换参数绕路。
