# S-286 · 桌面截图的尺寸摘要取自 base64 —— 极简档显示 `8×5`

> 归属：**移交 v3-iter-5**（2026-10-30 15:09 老大登记：「这些下个迭代处理」）。
> 状态：**✅ 已修** —— v3-iter-5 刀 3（2026-10-30 21:2x），记录见 §八。
> 定性：**真 bug，已实测复现**。

## 一、原话 / 来源

老大 2026-10-30 15:09：

> 「现在图片预览 限制了高宽 我点开图片查看看不到放大版本，其次**截图这个 8×5 是什么意思呢，感觉也是有问题的**，然后中途有显示保存失败，这些下个迭代处理。」

附界面截图（极简档过程行）：

```
✓ 桌面截图  8×5
```

## 二、现象

同一时刻真实截图是 **2520×1680**（1680×1120 的屏 @ scale 1.5），过程行却显示 `8×5`。
同一条消息**落库后重开该会话，显示是对的** —— 只错在当轮。

## 三、根因（已实测）

调用链：

```
execution-outline.ts:387   inputSummary(block.name, input, outputAsString(output))
  → tool-call-summary.ts:253-257   summarizeDesktopAction
```

```ts
const size = outputText?.match(/(\d+)\s*[x×]\s*(\d+)/)
return size ? `${size[1]}×${size[2]}` : 'desktop'
```

`outputAsString`（`execution-outline.ts:155-162`）对**字符串** output 原样返回。而桌面截图的
output 正是一段**字符串化的 content 数组**，image 块排在最前：

```json
[{"type":"image","source":{"type":"base64","mediaType":"image/png",
  "data":"iVBORw0KG…（约 658 KB base64）","filePath":"…"}},
 {"type":"text","text":"Captured desktop screenshot 2520x1680 (origin 0,0, scale 1.5) …"}]
```

正则取**第一个**命中 ⇒ 先撞上 base64 里的随机字节。

实测（`~/.wishful-claw-dev/screenshots/2026-10/3ad69753123f60ce.png`，493,695 字节 → base64 658,260 字符）：

```
[纯 base64] 首个命中: 8x5        ← 就是页面上那个数
```

**`8×5` 不是任何尺寸，是 base64 字符流的巧合。** 换一张图就变成别的数字，所以看起来「像偶发」。

**为什么重开就对了**：S-284 之后落库副本里 `data` 被剥掉，image 块只剩 `filePath`，
正则自然落到 text 块 ⇒ `2520×1680`。老大看到的 `8×5` 出现在当轮 —— 渲染层手里那份还带 data。

## 四、方案

### 4.1 主修：把正则锚住文案（`tool-call-summary.ts`）

```ts
const size = outputText?.match(/Captured desktop screenshot\s+(\d+)\s*x\s*(\d+)/)
```

那句文案由 C# `DescribeScreenshot` 拼（`AgentRuntimeDesktopExecutor.Encoding.cs:89`），
开头永远是这几个词；S-283 之前的老格式（`Captured desktop screenshot 1920x1080 across …`）同样命中。

### 4.2 补刀：`outputAsString` 对大结构化串直接短路

同类误判不止桌面截图 —— **任何** output 是「字符串化 JSON + 内含 base64」的工具都会中招
（`BrowserScreenshot`、`ImageGenerate` 等）。在 `outputAsString` 加一条**零解析**的廉价判据：

```
typeof output === 'string' && output.length > 4096 && (output.startsWith('[{') || output.startsWith('{"'))
  ⇒ 返回 undefined
```

摘要拿不到就回退到工具名，比显示一个假尺寸强。**不做 JSON.parse** —— `inputSummary` 是
渲染热路径（`ToolCallGroup` / `ToolCallCard` / `execution-outline` 三处都调），
6 MB 串 parse 一次 30–60 ms，每帧跑不起。

> 4.2 只对**桌面截图**无效（它正需要那段 text），所以 4.1 必须一起做：先按 4.2 短路，
> 短路掉的串由 4.1 的锚定正则单独负责不了 —— 因此实际顺序是
> **`summarizeDesktopAction` 直接吃原串、用锚定正则**，4.2 的短路放在**其余工具**的兜底分支上。

## 五、代价与风险

- 改动面：`tool-call-summary.ts` 一个函数 + `execution-outline.ts` 一条判据，**不动数据结构、不动 C#**。
- **文案同步风险**：`Captured desktop screenshot` 这句在 C# 里拼。改文案必须同步渲染层锚点 ——
  这正是 S-276「四处轮次判据各写各的」栽过的坑，实施时在两边都留注释指向对方。
- `tests/` 里目前**没有** `inputSummary` 的套件（需实施时确认），按惯例补一个纯函数套件：
  给定「字符串化 content 数组 + 已知尺寸」断言摘要 = `2520×1680`，并加一条「base64 里含
  `8x5` 也不许命中」的守卫断言。

## 六、验收方向

1. 极简档跑一次桌面截图 → 过程行显示 `2520×1680`（当屏真实值），不是三位数。
2. 连跑 5 次，尺寸稳定不变。
3. 老会话（落库、data 已剥）打开后显示与今天一致。
4. `BrowserScreenshot` / `ImageGenerate` 的摘要不再出现随机 `数字×数字`。

## 七、刻意不做

| 不做 | 为什么 |
|---|---|
| 不改 C# 那句文案 | 它同时是给模型的坐标参照系（原话在 `DescribeScreenshot` 的注释里），措辞服务于模型理解，不为渲染层摘要让步。 |
| 不在渲染层解 base64 量真实像素 | 图上早就有 `filePath`，读 PNG 头（IHDR 前 24 字节）比解 658 KB base64 便宜两个量级。真要做也归 S-288。 |
| 不把尺寸从 output 里抠掉只显示工具名 | 极简档「一行说清发生了什么」是 S-248 定的口径，尺寸是有用信息。 |

## 八、实施记录（v3-iter-5 刀 3）

### 4.1 主修（`tool-call-summary.ts`）

裸正则换成锚定：

```ts
const size = outputText?.match(/Captured desktop screenshot\s+(\d+)\s*x\s*(\d+)/i)
```

加了 `/i` —— 文案由 C# 拼，大小写不该决定解析成败。base64 字符集不含空格，这个短语不可能藏在 `data` 里，锚定即安全。需求单 §五 的「文案同步风险」已按 S-276 的教训写进代码注释，指名 C# 那边是 `AgentRuntimeDesktopExecutor.Encoding.cs`。

### 4.2 补刀（`execution-outline.ts`）

新增 **摘要专用** 的 `outputTextForSummary(name, output)`，**没有动 `outputAsString` 本身** —— 这一点和需求单的字面写法有偏差，理由如下。

`outputAsString` 有两个调用点：`hasStructuredOutputError`（要拿原串 `decodeStructuredToolResult` 找 `success: false` / `exitCode !== 0`）和 `inputSummary`（只要一段像人话的预览）。若在 `outputAsString` 里短路，等于**顺手废掉结构化错误嗅探** —— 那是 S-262 一线留下的判据。所以短路只加在摘要这一条路上。

两处豁免，代码里都写了「别顺手统一掉」：

| 豁免 | 为什么 |
|---|---|
| `DesktopScreenshot` | 尺寸就写在那段 text 里，必须拿原串（由 4.1 的锚定正则负责取对） |
| `Bash` / `Shell` / `PowerShell` | 输出本身就是结构化 JSON（`{"exitCode":0,…}`），摘要要从中取退出码与首行错误，短路等于丢信息 |

判据保持**零解析**：`长度 > 4096` + `开头是 [{ 或 {"` + `含 "base64"`。没用需求单原写的两条件，多加了 `"base64"` 这一条 —— 否则任何 4 KB 以上的普通 JSON 输出都会被短路，误伤面比收益大。仍然不做 `JSON.parse`（`inputSummary` 在渲染热路径）。

**老实说一句**：4.2 对**现有分支没有可观察效果** —— 读 output 的三个分支里，桌面截图和命令行都豁免了，`LS` 的输出是文件名列表。它是给「将来新增一个读 output 的工具摘要」留的护栏。注释里已写明，不冒充成修了什么。

### 新增门禁 `tests/tool-call-summary`（11 断言）

进 `npm test` 的 tsTests。`tool-call-summary` 本身是纯函数，但它为 `coerceAskUserQuestions` 引了 `ask-user-tool`，后者拖着 `locales`（vite 专有的 `import.meta.glob`）⇒ node 下加载即炸。照 `tests/tool-run-folding` 的先例加 `stubs/ask-user-tool.ts` 顶掉，不动被测模块。

覆盖：

1. **真机同形**（核心）—— base64 里带 `8x5` 诱饵，真实尺寸 `2520×1680` ⇒ 必须取 `2520×1680`；
2. **诱饵在首位** —— 塞 `9x7-1x2-3x4-5x6`，裸正则必然先命中，结果仍须 `1920×1080`；
3. 老格式（`… across 2 display(s).`）同样解析；
4. 大小写不敏感；
5. **缺锚点文案必须回退 `desktop`**，不许拿无关数字充数；
6/7. 空 / 未提供 output ⇒ `desktop`；文案内外都有数字时取文案紧跟的那个；
8/9. 邻居分支（`DesktopClick`、`Bash`）没被波及 —— 含一条「Bash 输出里的 `8x5` 不许被渲染成尺寸样式」。

**反向验证**：把锚定正则改回裸 `(\d+)\s*[x×]\s*(\d+)` ⇒ 第 1 条当场红（`桌面截图摘要必须取文案里的 2520×1680，不能被 base64 里的 8x5 带跑`），撤销后复绿。
