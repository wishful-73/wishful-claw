## 一、勘测结论：知识库记的三个「触发候选」都不是触发项

登记的候选是「嵌套两层子目录 / 中文文件名 / 下划线文件名」。读判定代码（`Tools/PathBoundary.cs`）后：

`IsInsideAnyRoot` 全程只做**一次规范化 + 前缀比较**，没有任何按文件名/字符集/层数分支的逻辑：

```csharp
var target = Normalize(resolvedPath);            // Path.GetFullPath + TrimEndingDirectorySeparator
if (string.Equals(target, normalizedRoot, comparison)) return true;              // 根本身
if (target.StartsWith(normalizedRoot, comparison) &&
    target[normalizedRoot.Length] == Path.DirectorySeparatorChar) return true;   // 子目录（边界明确）
```

⇒ 中文、下划线、十层子目录都走同一条「前缀命中」路径，**不可能**因为文件名或层数被拦。

已把三个候选逐条固化成断言（新增 `WishfulClaw.SandboxPathRegressionTests`，14 断言）：
根自身 / 两层子目录 / 中文名+下划线 / 大小写 / 同前缀兄弟目录（`工作目录备份` 必须被拒）/ 父目录必须被拒 / 空根集合放行 / 相对路径挂工作目录 / 越界绝对路径必拒 / 关掉沙箱全放行 / 越界文案同时含路径与允许根。

## 二、真正的触发机制：`workingFolder` 漏传 = 整个项目目录变成越界

`workingFolder` 由**渲染端每个 run 组装点各自透传**，而 Worker 侧有**两处**依赖它：

| 用途 | 取值处 |
|---|---|
| 沙箱根集合（项目会话） | `PathBoundary.CollectProjectRoots` 读 `parameters.workingFolder` |
| 文件工具的路径基准 | `ToolCallProcessor` 读 `parameters.workingFolder` → `ToolExecutionContext.WorkingFolder` |

漏传一处 ⇒ 两者**同时落空**：roots 退化成「只有数据根」，相对路径也不再挂工作目录（`Path.GetFullPath` 落到进程 cwd = 应用目录）
⇒ 项目内的写入被判越界，而报错还在劝用户「把目录加进项目工作目录」——**他早就加了**。这与知识库描述的
「写工作目录下的深层子目录被拦、agent 反复重试后改走脚本」完全吻合；也解释了为什么它与文件名无关。

渲染端确实有三处漏了项目回退（同一个文件里主路径有，这三处没有）：

```ts
// use-chat-actions.ts（主路径，有回退）
const workingFolder = session.scope === 'project' ? session.workingFolder ?? project?.workingFolder ?? undefined : undefined
// 另外三处（plan 批准 / plan 驳回 / 退出 plan 模式），缺回退
const workingFolder = session.scope === 'project' ? session.workingFolder ?? undefined : undefined
```

## 三、修复（两侧都堵）

1. **C# 侧：路径基准与沙箱根集合共用同一个解析**（`PathBoundary.ResolveProjectWorkingFolder`）——
   run params 里有就用它；缺失时按 `projectId` **回查项目表**。`CollectProjectRoots` 与 `ToolCallProcessor` 都改用它。
   查不到（没 projectId / 查库失败）就返回 null，行为与从前一致（只有数据根），不会因为一次查询失败把工具打挂。
   > 这条是关键：让「漏传 workingFolder」不再能把项目目录整体判成越界，从机制上关掉 S-144 的成因。
2. **渲染端：三处补回退** `session.workingFolder ?? project?.workingFolder ?? undefined`，与主路径对齐。
