# S-255：顶部吸附条只认纯文本 —— 图片、粘贴内容块、选中文件块全丢

> 一句话：吸附条是 `R-10.5` 拍的「紧凑指示条」，实现却只取了 `text`，把图片和芯片类内容整块丢掉了；纯图片消息甚至落成空态。

**性质**：渲染层保真修复。零后端改动、零数据迁移、零 DB 变更。

**归属**：v3-iter-3（产品 1.0.3）。编号 **S-255**。

## 2. 目标

1. 吸附条呈现的内容**与聊天窗里那条消息一致**：图片看得见、粘贴块显示为芯片、选中文件显示为芯片、斜杠命令显示为芯片。
2. **不推翻 R-10.5**：仍旧是紧凑指示条，高度有上限（现在约两行文本），长粘贴**不展开**。
3. 纯图片消息不再落「空」态。
4. 点吸附条跳回消息本体（既有行为不回归），悬浮 `title` 给全文摘要但**不得露原始 XML 标签**。

## 3. 现状（2026-10-28 实查）

`src/renderer/src/components/chat/MessageList/useMessageListData.ts:402-413`：`pinnedTurnMessage` 从 `messages` 数组倒序取最后一条「非 team、非压缩摘要、非后台唤醒」的 user 消息，拿到的是**完整 `UnifiedMessage`** —— content 里的 text / image / pasted-block tag 一样不缺。

### 3.2 只取了 text，其余全丢

`src/renderer/src/components/chat/MessageList/VirtualListContent.tsx:103-109`：

`extractEditableUserMessageDraft`（`src/renderer/src/lib/image-attachments.ts`）返回 `{ text, images, command }`，这里**只用了 `.text`**。

### 3.3 四种内容各自的落空方式

| 内容 | 聊天窗（`UserMessage.tsx`） | 吸附条 |
|---|---|---|
| 图片 | `UserImageAttachmentView` 缩略图条（`UserMessage.tsx:179-192`） | **整块消失**；纯图片消息 `text === ''` ⇒ 落 `messageList.pinnedTurnEmpty` 空态 |
| 粘贴内容块 `<pasted-block>` | 芯片（`parseSelectFileText` 出 `pasted` 段，`SelectFileInlineText` 渲染） | `extractEditableText` **不处理 pasted 标签**（只剥 `<system-command>` 和 system reminders）⇒ 原始标签直接进 `line-clamp-2`，截成 `<pasted-block>{...}` 这种乱码样 |
| 选中文件 `<select-file>` | 文件芯片 | 同上，原样露标签 |
| 斜杠命令 | 命令芯片 | 被 `extractEditableText` 抽走（单独放进 `command`），吸附条根本不显示 |

### 3.4 现成原料（不需要新造解析器）

- `src/renderer/src/lib/select-file-tags.ts:250` `parseSelectFileText(text)` → `SelectFileTextSegment[]`，已能分出 `text | file | plugin | pasted` 四段；`pasted` 段自带 `label`（形如「粘贴 #1 · 120 行」）与 `pastedText`。
- 同文件 `:239` `expandPastedBlocks(text)` → 展开成正文（给 `title` 用）。
- `imageBlockToAttachment`（`src/renderer/src/lib/image-attachments.ts`）已把三种来源统一成**可直接渲染**的 `dataUrl`：base64 直出、只剩 `filePath` 的走 `oc-media` 协议 URL、`url` 直用 ⇒ 吸附条 `<img src={image.dataUrl}>` 就行，不需要额外 IPC 取图。

## 4. 根因

一句话：**吸附条把「一条用户消息」当成「一段文本」，而用户消息是 text + images + chips 的复合体。**

`R-10.5` 的意图（不占满窗口）被实现成了「只取 text」这个最省事的近似，于是复合体里的非文本部分静默蒸发。

## 5. 方案

### 5.1 预览数据改成复合结构

`VirtualListContent.tsx` 的 `pinnedPreviewText` 换成 `pinnedPreview`：

```ts
{
  text: string
  images: ImageAttachment[]
  chips: Array<{ kind: 'file' | 'plugin' | 'pasted'; label: string }>
  command: SystemCommandSnapshot | null
}
```

- `draft = extractEditableUserMessageDraft(content)` 拿 `text / images / command`
- `chips` = `parseSelectFileText(draft.text)` 里除 `text` 以外的段（取 `type` 与 `label`）
- `text` = 从 `draft.text` 里挖掉各段 `raw` 之后的纯文本（芯片不再重复以标签形式出现第二遍）
- **整块必须在一个 `useMemo` 里算完**：`imageBlockToAttachment` 每次调用都 `nanoid()` 生成新 id，放在 render 里逐帧调用会让 React key 每帧变化。

### 5.2 渲染布局（守住 R-10.5 的高度上限）

按钮内部改成竖向堆叠，总高仍按「约两行文本」封顶：

1. **图片行**：最多 3 张小缩略图 + `+N` 角标，`object-cover` 固定小尺寸（32px 级）。**不复用 `UserImageAttachmentView`** —— 它带着 hover 复制 / 预览 / 删除整套交互，而吸附条整体是「点击跳回」，内部不能再嵌可点区域。
2. **芯片行**：`pasted / file / plugin / command` 各一枚，超出折 `+N`；视觉上与聊天窗 `SelectFileInlineText` 对齐，能直接复用就复用。
3. **文本行**：`line-clamp-2`；`text` 为空则整段不占位。

### 5.3 空态与 title

- 空态判据从「`text` 为空」改成「`!hasEditableDraftContent(draft)` 且 `chips` 为空」⇒ 纯图片消息有内容，不再落空态。
- `title` 改成 `expandPastedBlocks(text)`（限长展开）+ 图片 / 文件计数，不露裸标签。

### 5.4 高度联动的坑

`VirtualListContent.tsx:113-127` 用 `ResizeObserver` 把吸附卡实测高度写进 `pinnedCardHeight`，给首条消息让位；`useLayoutEffect` 依赖数组是 `[pinnedPreviewText, isPinnedTurnOverlayVisible]` ⇒ 必须换成新 memo 的值，否则图片加载完成、高度变了却不会重新测量。

## 6. 验收

真机（dev 实例，1.0.3）：

1. 发一条**纯图片**，agent 执行中 ⇒ 吸附条显示缩略图（不是「空」）
2. 发一条**图片 + 文字** ⇒ 缩略图 + 两行文字都在
3. **粘贴 2000+ 字**长文本 ⇒ 吸附条出「粘贴 #1 · N 行」芯片，**不展开全文**，吸附条高度不超过约两行
4. 带 `<select-file>` **选中文件** ⇒ 文件芯片
5. 悬浮 `title` 不出现 `<pasted-block>` / `<select-file>` 原始标签
6. 点吸附条跳回消息本体（既有行为不回归）
7. **图片已落盘**（S-224，DB 里只剩 `filePath`）重新打开会话 ⇒ 吸附条缩略图仍然显示（走 `oc-media`）

### 7.2 为什么解析抽成独立 lib 文件

`PinnedTurnBar.tsx` 顶层要 import lucide-react / react-i18next / `cn`。把 `buildPinnedTurnPreview` 留在组件里，回归套件就得把整套 React 依赖打进 node bundle 才跑得动 —— 而这个函数**恰恰是不需要 DOM 就能验的那一半**。抽走后测试只链到 `select-file-tags` + `image-attachments`，既快又不脆。组件里只剩「怎么画」。

### 7.3 布局：一行媒体 + 两行文本（守住 R-10.5）

- **图片**最多 3 张，`size-7` + `object-cover` 小缩略图；**不复用 `UserImageAttachmentView`**（按 §5.2 的理由：它带 hover 复制 / 预览 / 删除，而吸附条整块是「点击跳回」，内嵌可点区域会和它抢事件）
- **芯片**最多 3 个（有缩略图时让到 2 个），一行封顶五个元素，多出来的折成 `+N` 徽章。顺序 = 命令 → 粘贴 → 文件 → 插件（保持消息里的出现序）
- 芯片配色与聊天窗对齐：命令绿 / 粘贴琥珀 / 文件蓝 / 插件紫；粘贴芯片的字数直接调 **S-257 的 `describePastedBlockLabel`**，两处文案不会再各写一套
- **文本** `line-clamp-2`，空则不占位
- 空态只在**真什么都没有**时出现（`hasContent === false`）—— 纯图片消息不再落「（图片/附件消息）」

### 7.4 四个实现细节

**① `title` 不再露裸标签。** 从 `draft.text`（含 `<pasted-block>` 标记）改成 `selectFileTextToPlainText(expandPastedBlocks(raw))` —— 粘贴恢复成原文、文件标签剥成路径文本，再叠命令名与「N 张图片」，超 400 字截断。§6 第 5 条验收就验这个。

**② `hasContent` 自己算，不调 `hasEditableDraftContent`。** 理由订正：`hasEditableDraftContent` 判的是 `draft.text.trim().length > 0`，而 `draft.text` 是**带原始标签**的字符串，所以「文本只有 `<select-file>` 标签」的消息它返回 **true**，并不会误判。两种判据实践上等价（新的只可能更严，且被 `chips.length` 补齐）。自算的真实好处是**不需要重复推导 draft**（`content` 已在手，直接解析能一次拿到 chips / images / command），省一趟转换。

**③ `useLayoutEffect` 的依赖换了口径。** 原来依赖 `pinnedPreviewText`（字符串），现在依赖 `pinnedTurnMessageId`。理由：高度重测只关心「ref 挂的元素换没换」和「overlay 显不显示」，而**内容高度本身有 ResizeObserver 兜着**（图片异步加载完自然触发）。用 id 比用整串预览文本更省，也避免长粘贴每帧比字符串。

**④ 媒体行槽位从「各 3 个」改成「共用 4 个」（审查补刀）。** 初版缩略图与芯片各给 3 个槽位，媒体行最宽约 410px；而容器是 `flex-nowrap + overflow-hidden`、子元素全 `shrink-0`，`+N` 徽章排在最后 ⇒ 窄窗口下**被裁掉的正是「还有内容」的唯一提示**，用户会以为看全了。改成 `selectPinnedMedia(images, chips)` 统一分配 4 个槽位（有图时图优先，芯片拿剩余），最宽约 290px；同时容器 `div` → `span`（`<button>` 里不允许 `<div>` 这种非 phrasing content）并加 `min-w-0`。

> **两处刻意与聊天窗不一致，验收时不要按「一致」判**：
> ① 文件芯片吸附条显示 **basename**（`f.md`），聊天窗显示归一化全路径 —— 吸附条只有一行、宽度金贵，basename 更省地方；
> ② 顺序是「媒体行 → 芯片行 → 文本行」，聊天窗是「命令卡 → 文本（内联芯片）→ 图片」。§5.2 规定这是新布局，非回归。
> 另：`+N` 是**图片与芯片合并计数**，5 图 + 5 芯片显示 `+5` 时看不出其中几张图，属一行只有几个坑位下的取舍。
