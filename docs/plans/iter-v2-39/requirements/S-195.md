## 二、现象

桌面工具（`DesktopClick` / `DesktopType` / `DesktopScroll` / `DesktopWait`）在会话里**每一张调用卡片都标红「失败」**，但展开后：

- 「输入」区正常；
- 「输出」区显示的是 `{"success":true,...}` 这类**成功数据**；
- 红色告警框里的「错误内容」，就是**整段 JSON 原文**。

⇒ 同一张卡片上「失败」与 `success: true` 自相矛盾。

**不中招的反例**：`DesktopScreenshot` / `CaptureAppWindow` 显示正常。区别在于它们返回的是**数组**（image + text block），命中 `typeof output !== 'string'` 提前返回，且卡片里**没有「输出」区**可看。

---

## 三、静态定位（读码 + 实机复现）

### 3.1 判定链

`src/renderer/src/components/chat/DesktopActionToolCard.tsx`：

```ts
const parsedError = error || parseErrorMessage(output) || canceledMessage          // :83
const hasError = status === 'error' || status === 'canceled' || Boolean(parsedError)   // :86
```

`hasError` 直接决定两处呈现：

| 位置 | 行 | 表现 |
|---|---|---|
| 子标题文案 | `:167-171` | `isRunning ? running : hasError ? failed : completed` |
| 红色告警框 | `:222-234` | 显示 `parsedError` 的内容 |

而「输出」区（`:268-277`）走的是另一条链（`parseStructuredOutput`），**不受 `hasError` 影响** —— 这就是「上面说失败、下面显示成功」的由来。

### 3.2 病灶

```ts
function parseErrorMessage(output: ToolResultContent | undefined): string | null {   // :45
  if (typeof output !== 'string') return null
  const parsed = decodeStructuredToolResult(output)
  if (parsed && !Array.isArray(parsed) && typeof parsed.error === 'string' && parsed.error.trim()) {
    return parsed.error
  }
  return output.trim() || null        // ← :51  兜底：任何非空输出都当错误
}
```

**最后一行是根因。** 成功路径返回的 JSON **对象**里没有 `error` 字段 ⇒ 第一个 `if` 不成立 ⇒ 落到 `return output.trim() || null` ⇒ 拿到**整段成功数据**（非空）⇒ `Boolean(parsedError)` 为真 ⇒ `hasError = true`。

### 3.3 实机复现（2026-10-13，主会话）

调用 `DesktopWait`（无副作用、不走审批），实际返回：

```json
{"success":true,"delayMs":300,"message":"Desktop wait completed after 300ms."}
```

按 §3.2 的逻辑走一遍：`JSON.parse` 成对象 → 无 `error` 字段 → 落兜底分支 → 返回值**非空** ⇒ 判定为错误。**与老大描述逐字吻合。**

### 3.4 同一份代码有三个副本（影响面比报告的大）

| 文件 | 行 | 对应工具 |
|---|---|---|
| `components/chat/DesktopActionToolCard.tsx` | `:45-52` | DesktopClick / Type / Scroll / Wait |
| `components/chat/BrowserToolCard.tsx` | `:62-69` | 浏览器工具 |
| `components/chat/ImagePluginToolCard.tsx` | `:52-59` | 图片生成工具 |

三处**逐字相同**（含同一个兜底行），且三处都各自有 `parsedError = error || parseErrorMessage(output) || canceledMessage` 的用法。

⚠️ **后两处是「同源高风险」，尚未实机确认**：是否中招取决于各自工具**成功时是否返回非空字符串**。若其成功输出是对象 JSON ⇒ 同样恒标失败。实施时**应一并核实**。

### 3.5 仓库里已有正确实现

`src/renderer/src/lib/tools/tool-result-format.ts:61-66`：

```ts
export function isStructuredToolErrorText(text: string): boolean {
  const parsed = decodeStructuredToolResult(text)
  if (!parsed || Array.isArray(parsed)) return false
  const keys = Object.keys(parsed)
  return keys.length === 1 && typeof parsed.error === 'string'
}
```

**只当对象「有且仅有 `error` 一个键」时才算错误** —— 这正是 `parseErrorMessage` 应有的语义，且已在仓库里（`C#` 侧 `EncodeError` 产出的也正是 `{"error": msg}` 单键对象）。

## 四、根因

**`parseErrorMessage` 的兜底分支把「非空的成功输出」与「错误」混为一谈。**

- 三个卡片的 `hasError` 都只做「`parsedError` 非空 ⇒ 是错误」这一层判断，**没有「这段输出到底是不是错误」的辨别**；
- 成功路径恰好返回**非空 JSON 字符串** ⇒ 必然踩中，且**每次必中**（不是偶发）；
- 返回数组的工具因 `typeof output !== 'string'` 提前返回而幸免 ⇒ 这才解释了「有的工具正常、有的恒失败」。

**来源**：三处文件头都标 `Ported from OpenCowork`，是移植带进来的老逻辑，**非本迭代新引入**。

---

## 五、修复方向（已裁定：**方案 A**）

| | **方案 A：删掉兜底**（采纳） | 方案 B：改用既有判定（否） |
|---|---|---|
| 做法 | 三处 `return output.trim() \|\| null` → `return null` | 三处改用 `isStructuredToolErrorText(output)` |
| 效果 | 非结构化的输出**一律不算错误** | 只认「纯 `error` 对象」 |
| 风险 | 若某工具真靠「纯文本输出」表达失败，改后不再由 output 触发标红 —— 但 `status === 'error'` 那一支仍然兜住（`:86`），且真出错时 `error` prop 通常有值（`:83` 最优先） | `keys.length === 1` 偏严：`{"error":"x","success":false}` 会**漏判**成成功 |

**采纳方案 A** —— 更简单，语义也更干净：**错误由 `status` 说，不由输出内容猜**。输出内容本来就可能是任意 JSON，拿它反推成败必然误伤。
方案 B 的出局理由（实施时确认）：`isStructuredToolErrorText` 要求「有且仅有 `error` 一个键」，而 C# 侧除 `EncodeError`（单键）外还会产出 `{"error":…,"success":false}` 这类多键错误体，用 B 会漏判。

实现要求：**三处一起改**，否则同类卡片行为不一致。

## 六、代价与取舍

**接受的代价**：非结构化输出里的失败信息不再单独标红。

若某个工具既返回非空纯文本、`status` 又不为 `error`（即「工具自己把失败编码进了正文」），改后这张卡片会显示「已完成」。判断这个代价值得，理由三条：

1. **成功路径是绝对多数**：`{"success":true,...}` 这类成功体必然踩中旧逻辑，**每次必中**；而「纯文本表达失败」在当前工具集里没有实例 —— 真失败走的是 `status === 'error'` + `error` prop，或 `{"error":…}` 结构体。
2. **旧逻辑不是「多标了」，是「恒标了」**：恒标失败会让用户彻底失去对红色告警的信任，真失败也被当噪音看，这比漏标更贵。
3. **真失败仍有两道兜底**：`status === 'error' / 'canceled'`（`:86`）与 `error` prop（`:83`，优先级最高）。

**不接受的代价**：漏判 `{"error":"x","success":false}` —— 这正是方案 B 出局的原因。

## 七、刻意不做

1. **不动 `decodeStructuredToolResult` / `isStructuredToolErrorText`** —— 它们是共用工具，被 30+ 处调用，改动面远超本 bug。
2. **不动 `status` 语义与 `canceledMessage` 分支** —— `status === 'error' / 'canceled'` 的判定是对的。
3. **不顺手统一三个卡片的其它重复代码** —— `parseStructuredOutput` 等也是三份拷贝，收敛属重构，与本 bug 无关，另行裁定。
4. **不动 `isBrowserToolName` 空壳**（`lib/app-plugin/browser-tool-names.ts`）—— 与 `isDesktopControlToolName` 同为空壳，但它的唯一消费点 `process-summary.ts:29` 已用 `item.name.startsWith('Browser')` 兜住，改它无行为收益，故留原样。
