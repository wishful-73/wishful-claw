# S-133 · 流式正文被思考块 / 工具组件从中间打断

- 2026-09-22：**老大提出**（原话：「前端渲染的时候，有时候输出的文本会被思考 或者 组件的渲染打断，也就是一段正常的文本渲染 中间突然插了一个组件的渲染。」）。
- **类型**：UI 渲染 / 流式时序；**间歇性**（「有时候」），非必现。

**现象（老大 2026-09-22 二次澄清，用他的原话）**：「文本输出到一大半，说准备调用工具，然后工具两个字还没输出出来，工具组件已经显示了。……是先有正文，然后调用工具的情况有问题，正常调用工具，后输出文本的是没有问题的。」即 —— **先出正文、再调工具**时，**同一段连贯正文被工具卡从中间截成两截**。

**方向性（老大实测，本需求的关键判据）**：

- ✅ **先调工具、后出文本 ⇒ 正常**：store 里 segments 长成 `[tool, text]`，渲染「卡 + 文本」，符合预期。
- ❌ **先出文本、再调工具 ⇒ 出问题**：store 里 segments 长成 `[text1_1, tool, text1_2]` —— `text1_1` / `text1_2` 是**同一段话**被工具调用劈成的两截。

> 这两种情形**互为镜像**，正是下面 `_flushStreamDeltas` 那个「追加还是新建」判据的两种输出 —— 所以「有时候」不是随机的，**取决于工具调用插在正文的哪个位置**。

**根因（第二版，修正前次误判）** —— ⚠️ 前次我把根因判给渲染层的 `splitProcessAndFinal`，**判错了**。老大 2026-09-22 的纠正点中要害：**内容形如 `[text1, tool]` 时就不该被劈开** —— 即**内容层**（store 组装 segment）本身就不该产出被劈开的数据，渲染层只是**放大**了它。

**真凶：`stores/chat-store/index.ts:2237-2249`（`_flushStreamDeltas` 的 text 分支）**

```ts
// Append to last text segment of current iteration, or create new
const lastSeg = msg.segments[msg.segments.length - 1]

if (lastSeg && lastSeg.type === 'text' && lastSeg.iteration === msg.currentIteration) {
  lastSeg.text = (lastSeg.text ?? '') + delta.text                                       // 追加
} else {
  msg.segments.push({ type: 'text', iteration: msg.currentIteration, text: delta.text })  // 新建
}
```

**判据太严 —— 只认「最后一个 segment 是 text」**。而工具卡会 `msg.segments.push({ type: 'tool_use', ... })` 插到**末尾** ⇒ 之后到达的 text delta 只能走 `else` **新建 segment**。

**流式时间线（同一次 LLM 响应 = 同一个 `iteration`）**：

| 步 | 事件 | `msg.segments` | 老大师到 |
|:--:|---|---|---|
| 1 | `text_delta` × N | `[text1_1]` | 正文在输出 |
| 2 | `tool_call_start` | `[text1_1, **tool_use**]` | 工具卡出现 |
| 3 | `text_delta`（续） | `[text1_1, tool_use, **text1_2**]` | **正文被劈开** ❌ |

**⇒ 与老大给的两种情形精确吻合（这才是真正的「镜像」）**：

- **先出文本、再调工具** ⇒ 步 3 走 `else` 新建 ⇒ `[text1_1, tool, text1_2]` ⇒ **劈开** ❌
- **先调工具、后出文本** ⇒ `[tool_use]` 收到 text delta ⇒ `lastSeg` 是 tool_use ⇒ 新建 ⇒ `[tool, text]` ⇒ **正常** ✅

**渲染层如何放大它**：`chat-message-blocks.ts:28-32` 把 `msg.segments` **原序**转成 blocks，再由 `splitProcessAndFinal`（`process-summary.ts:152-167`）**从尾部倒扫**切一刀 ⇒ `processItems = [text1_1, 卡]`、`finalItems = [text1_2]` ⇒ `text1_1` 留在卡上方、`text1_2` 掉到卡下方，**劈开被视觉放大**。⇒ **渲染层不用动**（对正确的 `[text1, tool]`，split 产出的「`text1` + 卡」本来就对）。

**已排除的两条**：

- **工具卡折叠吞文本**：`renderItems`（`index.tsx:370-393`）用 `i = run.endBlockIndex` 跳整段 run，但 `execution-outline.ts:394` 的 `endBlockIndex` 只更新到最后一个 tool_use，且 `:327-332` 遇 text / thinking 就 `closePendingRun()` 断开 run ⇒ run 区间内不含文本。**逻辑正确。**
- **正文打字机滞后**：`useStreamingRenderPool`（`hooks/use-typewriter.ts:68`）只被 `ThinkingBlock` 用；正文走 `StreamingMarkdownContent`（`markdown-renderer.tsx:455`）。**两者不是同一机制。**

**修法（待裁定）**：

- **A（推荐，治本）**：text delta 追加时**向前找**当前 `iteration` 内最近的 text segment；若它与末尾之间**只夹着 `tool_use`**（无 text / thinking 隔断），就**合并到它** ⇒ segments 保持 `[text1, tool]`，渲染为「正文 + 卡」。
- **B（治标）**：store 不动，改在 `splitProcessAndFinal` 里把同 `iteration` 的 text 合并渲染。⇒ 落库 / 复制 / 其它消费方**仍看到劈开的数据**。

我倾向 **A**：在**数据源头**消除劈开，且 `iteration` 判据能区分「同一响应内的碎片」与「跨轮次的独立文本」。

**⚠️ 一处需老大确认（决定 A 会不会误伤）**：老大认可的 **`[text1, tool, text2]`**，指的是哪一种？

- **(甲)** 第一轮说 `text1` + 调工具 ⇒ 工具跑完 ⇒ **第二轮**说 `text2` ⇒ 两者 `iteration` 不同 ⇒ **A 不会误伤** ✅
- **(乙)** **同一次响应**里模型主动分两段说（`text1 → 工具 → text2`）⇒ 同 `iteration` ⇒ A 会把它并成 `[text1, tool]`（**改变现状**）

若是 (乙)，则 A 需加附加判据（例如仅在「该工具仍 `running`、且 `text2` 紧跟 `text1` 到达」时才合并）—— 请老大定夺。
