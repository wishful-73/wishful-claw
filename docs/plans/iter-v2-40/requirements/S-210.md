# S-210：折叠块下方的总结写死成「任务暂告一段落」，该按真实结束情况显示

> 状态：**已实施**（首版 `7f58cb7c`；验证期按老大口径修正 —— **撤回正文回填**，2026-10-21）。
> 类型：**bug**（显示层给出与事实不符的总结）。
> 归属：**iter-v2-40**。
> 轨道：**软件侧**（渲染端为主；Worker 只补落库字段）。

---

## 一、原始需求（老大 2026-10-20 10:03 原话）

> 目前我们聊天窗 在用户终止执行或者 触发压缩后，之前的执行过程会折叠 并且显示一个固定值 任务暂告一段落 作为总结。这个我希望登记一个需求，能实际显示是用户取消执行，触发压缩等实际情况。

拆成三句：

1. **现状**：用户终止执行 / 触发压缩后，之前的执行过程会折叠 —— 这是既有行为，**不是要改的东西**；
2. **问题**：折叠块配的总结是**一个固定值**「任务暂告一段落」；
3. **要做**：换成**真实情况** —— 用户取消就说用户取消，压缩就说压缩。

一句话：**折叠行为不动，动的是那句总结。**

## 二、问题定位

### 2.1 固定文案只有一个

`content-renderer.tsx` 折叠块尾部，正文为空时兜底一句 i18n 文案：

```tsx
<p className="text-muted-foreground">
  {t('assistantMessage.executionPaused', { defaultValue: '任务暂告一段落' })}
</p>
```

不管这一轮是用户按了停止、模型报错、还是被压缩卡片劈开，**全都说同一句**。用户看到一个"平静收尾"的说法，实际可能是异常中断，信息是错的。

### 2.2 真实结束原因后端有，只是没落到消息上

`AgentLoop` 早就在收尾时发出 `loop_end`，`AgentLoopEndReasons` 五值齐全：

| `reason` | 含义 |
| --- | --- |
| `completed` | 正常跑完 |
| `user_cancelled` | 用户点了停止 |
| `aborted` | 其他中断（含压缩被取消、运行中被打断） |
| `max_iterations` | 到迭代上限 |
| `error` | 模型 / 链路报错（另带 `errorType`、`statusCode`） |

缺的是**渲染端把 `loop_end` 写进消息 `meta`、并据此选文案**这一步。

### 2.3 「压缩」不是结束原因，是分片位置

压缩不是 `loop_end` 的某个 reason —— 压缩成功后循环继续跑。它的表现是：**压缩卡片把一条 assistant 消息劈成两段折叠块**，前面那半截本来就没有收尾正文，于是落到那句固定文案上。

渲染项上带着分片信息（`renderable-chat-items.ts:22-29`）：

```ts
fragment?: {
  position: 'before' | 'after'
  operationId: string
  totalElapsedMs?: number
}
```

`position === 'before'` 就是被压缩劈出来的前半截 —— 这一轮**并没有结束**。

## 三、目标

折叠块下方按真实情况显示，四种形态分开：

| 实际情况 | 显示 |
| --- | --- |
| 正常跑完（`completed`） | **什么都不加** —— 正常结束本来就有正文 |
| 用户点了停止（`user_cancelled`） | 你中止了这一轮 |
| 其他中断（`aborted`） | 这一轮被中断了 |
| 到迭代上限（`max_iterations`） | 这一轮到了迭代上限，停在这里 |
| 模型 / 链路报错（`error`） | 按 `errorType` / 状态码细分，见下 |
| 被压缩劈开的前半截（`fragment.position === 'before'`） | 上下文已压缩，执行继续 |
| **压缩后继续执行、跑到一半用户中断**（两段折叠块） | **前半段「上下文已压缩，执行继续」/ 末段「你中止了这一轮」** —— 组合场景，见 §5.3 |
| 老消息（无 `runEnd`，也无分片） | 沿用「任务暂告一段落」兜底，不编原因 |

`error` 细分：

| 判据 | 显示 |
| --- | --- |
| `errorType === 'TimeoutException'` | 请求超时，这一轮中断了 |
| `errorType` ∈ HttpRequestException / SocketException / IOException / WebException / TaskCanceledException | 网络中断，这一轮没跑完 |
| `statusCode` 502 / 504 | 网络中断（502），这一轮没跑完 |
| `statusCode` 401 / 403 | 服务商拒绝请求（401） |
| `statusCode` 429 | 服务商限流（429） |
| `statusCode` ≥ 500 | 服务商返回错误（500） |
| 其他 `statusCode` | 请求被拒绝（4xx） |
| 无以上信息 | 出错中断，详见上方错误信息 |
| Worker 以后加了新 reason（未知值） | 这一轮已结束（原值）—— 照实报，不假装 |

## 四、非目标（**明确不做**）

- **不改折叠行为**：过程折叠是设计意图，照旧折叠。
- **不把过程里的文字提出来当正文**（首版做过，已撤）。理由见 §七。
- **不改 `AgentLoop` 的停止 / 压缩判定**。
- **子 agent 卡片不在范围内**（`SubAgentCard` 自带 `endReason` 三态显示）。

## 五、修法

### 5.1 结束原因落库

- `MessageRunEndMeta`（`lib/api/types.ts`）：`{ reason, errorType?, statusCode?, at? }`；
- 写入点：`stores/chat-store/index.ts` 的 `loop_end` 分支，在 final persist 之前写进目标 assistant 消息的 `meta.runEnd`；
- 落库零 schema 改动（`db-helpers.ts` 整体展开 / 还原 `meta`）。

### 5.2 原因 → 文案（纯函数）

- 新建 `lib/agent/run-end-label.ts`：`resolveRunEndLabel(runEnd)` 只做「数据 → i18n 键」映射，**不 import IPC、不 import i18n 实例**；
- `completed` 返回 `null` = 不该显示任何结束语；
- 缺失 / 未知返回 `null` / 兜底描述，由调用方决定怎么显示 —— **不编原因**。

### 5.3 压缩分片识别

- `renderable-chat-items.ts` 的 `fragment.position` 一路透传：`MessageItem.tsx` → `AssistantMessage` → `ContentRenderer`；
- 尾部提示里 `fragmentPosition === 'before'` 时显示「上下文已压缩，执行继续」，其余情况才走结束原因 / 老文案兜底。

**`runEnd` 只属于末段（2026-10-21 验证期补）**：压缩分片共用同一份 `meta.runEnd`（它记的是整条消息怎么收尾的），前半截读它就是错报 —— 老大实测：「正常执行 → 触发压缩 → 压缩后继续执行 → 跑到一半用户中断」时两段折叠块都显示「你中止了这一轮」，而前半截其实只是被压缩卡片截断了。

- 纯函数 `resolveFragmentRunEnd(runEnd, fragmentPosition)`（`run-end-label.ts`）：`fragmentPosition === 'before'` ⇒ 一律返回 `null`，其余原样返回；
- `AssistantMessage/index.tsx` 算一次，**折叠块提示与底部操作栏共用** —— 前半截的操作栏也不该亮出「结束时刻 + 耗时」，那同样是把末段的收尾安在了没结束的一段上。

### 5.4 渲染

`content-renderer.tsx` 折叠块之后：

- 有正文（`finalItems` 非空）⇒ 正常渲染，**不追加任何结束语**（`completed`）；
- 无正文 ⇒ 先看有无 `runEndText`（中断 / 报错 / 上限），有就显示真实原因；
- 无 `runEndText` 且是压缩前半截 ⇒ 「上下文已压缩，执行继续」；
- 以上都没有 ⇒ 老文案「任务暂告一段落」兜底。

`splitProcessAndFinal` **保持纯切分**，不做回填。

## 六、决策点（均已落地）

1. **`completed` 要不要留一句**（如「这一轮没写收尾文字，工具已执行完」）—— **不留**，老大 2026-10-21 口径：「正常结束都会有正文，根本不需要处理」。
2. **`aborted` 是否细分**「点停止」与「运行中插消息打断」—— **不细分**（后端同报 `aborted`，细分要改 Worker 侧 reason 值；另开需求）。
3. **压缩前半截的文案** —— 「上下文已压缩，执行继续」，点明这一轮没结束。
4. **老消息兜底** —— 保留「任务暂告一段落」，因为确实没有数据，不编。

## 七、首版走偏与修正（重要，别再犯）

### 7.1 首版怎么歪的

首版登记（2026-10-20 10:14 重查后）把问题重新定义成「**正文被折叠进过程块，外面只剩灰字**」，做了一轮实证：正式库最近 800 条 assistant 消息里会显示灰字的 83 条，**83 条全都有正文**。

数据的结论是「这些消息不是没说话，是话被折叠吞了」—— 于是修法变成 §5.1 **正文回填**：切完 `finalItems` 为空时，把尾部最后一段连续 `text` 提出来当正文。

**但这回答的不是老大问的问题。** 老大问的是「那句总结为什么是假的」，不是「正文去哪了」。

### 7.2 回填为什么站不住

原始登记 §2.1 自己列的三种典型尾部形态，全是「文字在前、工具在后」：

```
text, tool_use, tool_use
tool_use, tool_result, thinking
tool_result, tool_use, tool_result
```

按回填规则，会把**工具之前说的那句旧话**提到所有工具的下方 —— 顺序上凭空冒出一段"收尾"。执行中还更糟：尾部永远是刚发出的工具，`finalItems` 每帧为空 ⇒ 回填每帧触发 ⇒ 那段话被钉在渲染顺序最下方，后续工具、思考全叠在它上面（验证期实测当场暴露）。

### 7.3 最终口径（2026-10-21）

**撤回填，纯切分。** 老大原话：「正常结束都会有正文，根本不需要处理……如果是用户中断执行的，显示用户中断执行就行，如果是调用模型异常报错，显示报错就行，如果是压缩导致的，显示压缩。」

切完 `finalItems` 为空，说明这一轮本来就没说完 —— 那就据实说原因，不拿过程文字冒充正文。

### 7.4 教训

**登记需求时先照着原话拆句子，再去找技术解释。** 首版是先去找「哪里不对劲」，找到一个大问题就当成主因，把原话里真正的那句话（固定值该换掉）降级成附带项。数据是真的，方向是错的。

## 九、风险

- `tool_result` 不是渲染项（`index.tsx` 只对 `tool_use` 分组）—— 判断块类型要按 `normalizedContent`，别按 renderItem 种类；

- 未知 reason 照实报原值，避免新原因上线后界面静默。
