> - 门禁：`WishfulClaw.Infrastructure` / `WishfulClaw.Agent` 编译 0 警告 0 错误。

## 一、原话 / 来源

老大 2026-10-30 14:28：

> 「写库走的是 db/messages-upsert → 整行覆盖 meta。工具调用每完成一个就 upsert 一次，每次都把整条 meta 重新 stringify 再发过去。那条消息 148 次工具调用，于是 14 MB × 148。**那这个可以改一下么？再加一个表，新的助手消息都是另一个表？**」

14:29 补一句：「**只是讨论，而且最好能兼容老数据**」。

## 二、现象（实测，会话 `9yXnLPAM00ea6qAXu6qPp`）

单条助手消息 `wc-agent-1793264773464-cz0mvm`，`meta` **14,496 KB**：

| 构成 | 体量 |
|---|---|
| `toolCalls[].output` 里的图片 base64 | **6,619 KB** |
| `segments[].tool_use.output` 里的图片 base64（**同一张图的第二份**） | **6,619 KB** |
| `toolCalls` 纯文本 output | 415 KB |
| `segments[].text` | 421 KB |
| `thinking`（segments 内 + 顶层**各一份**） | 136 KB × 2 |

写入侧：`dbUpsertMessage` 在**每个工具调用完成边界**写一次 ⇒ 这条消息 **148 次 upsert**，每次都把整条 meta 重新 `JSON.stringify` + 过 IPC：

| 每步 | 单次 | ×148 |
|---|---|---|
| `JSON.stringify` 分配新串 | 14.5 MB | **2.07 GB** |
| IPC 传输 | 14.5 MB | **2.07 GB** |

日志佐证：`memory role=renderer ws=1477.2MB peak=2327.8MB`。

**注意：S-284（剥 base64）做完后仍有 1,257 KB**，这是本条存在的理由 —— 剩下的重量来自结构冗余与大段文本 output，不是图片。

## 三、根因

工具调用在语义上是**追加**的（第 N 个完成 → 多一条记录），而 `messages.meta` 是**整行覆盖**的。用覆盖语义去模拟追加，每次都要重算全部历史。

## 四、方案：新表 + 读时合并，**零迁移**

### 4.1 表结构

```sql
CREATE TABLE message_parts (
  message_id TEXT NOT NULL,
  seq        INTEGER NOT NULL,   -- 段序号，追加序
  kind       TEXT NOT NULL,      -- 'thinking' | 'text' | 'tool_use'
  payload    TEXT NOT NULL,      -- 该段 JSON
  created_at INTEGER NOT NULL,
  PRIMARY KEY (message_id, seq)
) WITHOUT ROWID;
```

加 `ON DELETE CASCADE` 挂在 `messages` 上，或沿用现有删除路径手工清 —— 需确认现有 `db/messages-clear` / `-delete` 的清理方式再定。

### 4.2 新老共存判据（一条消息内部不混）

| 情况 | 写入 | 读取 |
|---|---|---|
| `messages.meta` 里**已有** `toolCalls` / `segments` | 继续整行 upsert（老格式原样写回） | 与老代码完全一致 |
| 新消息（meta 里没有块结构） | 只往 `message_parts` 追加，主表 meta 留 `{thinking?}` 或 `null` | 主表 + `parts` 批量拼 |

**同一个会话里前半段老、后半段新没问题** —— 按 `message_id` 分开判断，互不影响。**不写迁移脚本、不加版本号列、不动任何历史行。**

### 4.3 读取侧

首屏那条查询（`turns: 5`）里追加一次：

```sql
SELECT message_id, seq, kind, payload FROM message_parts
WHERE message_id IN (…窗口内 28 个 id…)
ORDER BY message_id, seq
```

窗口大小由 `turns` 锁定，量固定。拼装发生在 `deserializeMessage` 之前，对外形状仍是 `{ toolCalls, segments, thinking }`，**渲染层零改动**。

### 4.4 状态变化怎么处理

工具状态会变（`running` → `completed`）。两个选项：

| 选项 | 做法 | 取舍 |
|---|---|---|
| **A（推荐）** | `seq` 按 toolCallId 占位固定，状态更新走 `INSERT OR REPLACE` 单行 | 单次仍是 2 KB 级；顺序稳定 |
| B | 每次状态变化追加新行，读时按 toolCallId 取最后一行 | 行数翻倍，读时要去重 |

## 五、代价与风险

1. **改的是数据模型，不是一处调用。** 要跟着动：`db/messages-list` / `-list-page` / `-list-by-turns` / `-list-locator` / `-search-content`、`DbMessageCompactTools`（压缩读全量 segments）、`deserializeMessage`、worker 侧重建上下文的读法。
2. **跨语言同步面扩大。** C# 写、TS 读、C# 再读（压缩/上下文重建）三处对同一份结构的理解必须一致 —— 这是本项目栽过的坑（S-276 四处轮次判据各写各的）。
3. **`-list-locator` 本来就是轻量的**，别顺手把它也改成 join，否则右侧 rail 会变慢。
4. **拆完收益依赖 S-284 先落地。** 在 14.5 MB 的基座上拆，只是把 2.07 GB 摊薄；在 1.26 MB 的基座上拆，才是干净的架构演进。

## 六、验收方向（实施时细化）

- 新消息的 `messages.meta` 不再含 `toolCalls` / `segments`；
- 老消息打开后行为**逐字节不变**（同一条消息拆前拆后渲染结果一致）；
- 148 次工具调用的消息，单次落库传输量 ≤ 4 KB；
- 首屏 `responseBytes` 不再随工具调用数线性增长。

## 七、刻意不做

| 不做 | 为什么 |
|---|---|
| **不迁移历史行** | 老大 14:29 明确「最好能兼容老数据」。读时合并已经满足，迁移脚本写错就毁库。 |
| **不改 `-list-locator`** | 它本来就不取 meta，动它只会拖慢右侧 rail。 |
| **不与 S-284 合并成一刀** | 一个是写入侧两行改动，一个是数据模型改造，风险量级差太远。 |
| **不做 JSON 分段拼接缓存** | 曾评估在 `serializeMessage` 里缓存 `stringify` 前缀，单次能从 14 MB 降到 2 KB。但拼出来的 JSON 与 `JSON.stringify` 有一字节差异就是脏数据，而这条路上已经有过「两处口径必须同步」的事故。拆表是更正的解法。 |

## 八、实施方案补齐（v3-iter-5，只写方案不动代码）

§四 给了表结构与共存判据，但缺工程细节。这一节把落地要答的问题逐条答完。

### 8.1 改哪几列 —— 一列都不改，纯新增表

**`messages` 表一个字不动**：不 ADD COLUMN、不改类型、不重建。整条需求落在新建的 `message_parts` 上。

现有 `messages` 表结构（`DbClient.Schema.cs:62-71`，实测）：

```sql
CREATE TABLE IF NOT EXISTS messages (
    id TEXT PRIMARY KEY NOT NULL,
    session_id TEXT NOT NULL,
    role TEXT NOT NULL,
    content TEXT NOT NULL DEFAULT '',
    meta TEXT,
    created_at INTEGER NOT NULL,
    usage TEXT,
    sort_order INTEGER NOT NULL DEFAULT 0
);
```

### 8.2 索引 —— 主键就是索引，不再加

| 项 | 决定 |
|---|---|
| 主键 | `PRIMARY KEY (message_id, seq)` + `WITHOUT ROWID` |
| 读侧查询 | `WHERE message_id IN (…窗口内 28 个 id…) ORDER BY message_id, seq` |
| 是否够用 | **够**。`WITHOUT ROWID` 表的行就存在主键 B-tree 里，`message_id` 等值 + `seq` 有序前缀扫描正好命中，不需要额外索引 |
| 不加 `session_id` 索引的理由 | 表里**不存** `session_id` —— 它由 `messages.session_id` 决定，重复存一份就是两份真相。读侧永远先有 message_id 列表（来自 `messages` 查询），再按 id 批量取 parts |

**顺带记一个既有事实，本条不动它**：`messages` 表**至今没有任何索引**（`DbClient.Schema.cs` 全文无 `ix_messages*`）。首屏 `turns: 5` 查询靠 `session_id` + `sort_order` 过滤，是全表扫。这是既有性能债，**不在本条范围内**，单独立项才动。

### 8.3 老数据怎么办 —— 零搬运，按 `message_id` 逐条判断

§4.2 的共存判据不改，这里补落点：

| 情况 | 判据（读的是这一行自己） | 写入目标 |
|---|---|---|
| 老消息 | `messages.meta` 里能解析出 `toolCalls` 或 `segments` | 继续整行 upsert（原样写回，一个字节不变） |
| 新消息 | `messages.meta` 里没有块结构 | 只写 `message_parts` |

**同一会话前半段老、后半段新是正常态**，不是边界情况 —— 判断粒度是 `message_id`，不是会话。

### 8.4 迁移类型 —— 纯增量，`CREATE TABLE IF NOT EXISTS`

沿用 `DbClient.Schema.cs` 现有写法，**老库启动自动建表**，零数据搬运、零 `ALTER`、零重建。

反向验证（写测试时必做）：把 `CREATE TABLE IF NOT EXISTS` 改成 `CREATE TABLE`，第二次启动**必须炸**。不炸说明测试根本没覆盖到「老库已有表」这个路径。

### 8.5 数据丢失风险点

| 风险点 | 具体是什么 | 怎么防 |
|---|---|---|
| **`ON DELETE CASCADE` 的真相** | §4.1 写「加 `ON DELETE CASCADE` 挂在 `messages` 上，或沿用现有删除路径手工清 —— 需确认」。**实测：`DbService.cs:35` 有 `PRAGMA foreign_keys = ON`，级联会真生效。** 但 `message_parts` 若真的加了 FK 指向 `messages.id`，则删除一条消息会**静默带走它的全部 parts** —— 一旦有 bug 误删 messages 行，parts 一起没，且不可恢复 | ① 先读 `DbMessageToolsMutations.cs` 的 `db/messages-clear` / `-delete` 两条删除路径，确认它们本来就手工清关联表；② **优先选手工清**（与现有 `sub_agent_runs` 等表的处理方式一致），不加 FK —— 多一步显式删除，比隐式级联更好排查 |
| **`WITHOUT ROWID` 的代价** | 该表不能再用 `rowid`，也不能用 `AUTOINCREMENT` | 本条不需要自增，`seq` 是业务序号，无影响 |
| **跨语言三处口径** | C# 写、TS 读、C# 再读（压缩 / 上下文重建）对同一份结构理解必须一致 | 与 S-276 同一教训（四处判据各写各的）。**`kind` 值域与 `payload` 形状必须只有一个定义源**，两侧各写一份常量并互相注释指名 |
| **状态更新的原子性** | §4.4 选 A（`INSERT OR REPLACE` 单行更新状态） | 单行 upsert 在 SQLite 里是原子的，但**并发两个工具同时完成时**要确认写的是不同 `seq`。`seq` 按 `toolCallId` 占位固定即天然隔离 |

### 8.6 回滚锚点 —— 能证明「修复前必红」的断言

写测试时必须先让它红，再让它绿。三条：

| # | 断言 | 修复前为什么必红 |
|---|---|---|
| 1 | 一条含 148 次工具调用的消息，`messages.meta` 里**不含** `toolCalls` / `segments` | 修复前 meta 就是整条 14 MB JSON，必然含 |
| 2 | 同一条消息的**单次落库传输量 ≤ 4 KB** | 修复前单次是 14.5 MB |
| 3 | 老格式消息读出来的 `{toolCalls, segments, thinking}` 与修复前**逐字节相同** | 这条是防回归，修复前后都应绿 —— 它红说明兼容层写坏了 |

### 8.7 影响面 —— 具体文件清单

**C# 写侧 / 读侧（`src/runtime/WishfulClaw.Infrastructure/Db/`，行数为实测）**

| 文件 | 行数 | 要动什么 |

| `DbMessageToolsMutations.cs` | 240 | upsert 分流（老格式原样写 / 新格式写 parts）；删除路径补清 parts |
| `DbMessageToolsQueries.cs` | 238 | 各 list 端点批量取 parts 并合并（`:35` 那条 `meta NOT LIKE '%compactSummary%'` 判据不动） |

## 九、实施结果（v3-iter-4 · 刀 11 · 2026-10-30）

### 9.1 与方案的三处偏差（都是查证后改的，不是偷工）

| # | 方案写的 | 实测是什么 | 实际怎么做 |
|---|---|---|---|
| 1 | `DbMessageCompactTools.cs` 必须同刀改掉（压缩读全量 segments） | `CompactSession`（`:22-46`）读的是 `messages.content` 纯文本列，再 `JsonDocument.Parse` 要求 Array ⇒ 对多数消息本来就是 no-op，**一次都不碰 `meta.segments`**。真正重建上下文的是 `SessionRestoreTools.Wire.cs`，读 `meta.toolCalls` 共 5 处 | **改 `SessionRestoreTools.Wire.cs`**，新增 `AttachPartsToEntities` 并在增量 / 完整恢复两个分支各调一次；`DbMessageCompactTools.cs` **不动**（改它是空转） |
| 2 | §8.1 引用 `messages.updated_at` 已有 | DDL（`DbClient.Schema.cs:62` 起）里没有 `updated_at`，是迁移补的列 | 按现有 Upsert 的写法照用，未新增迁移 |
| 3 | `seq` 可由段下标派生 | `stream-segments.ts:63` 有 `segments.splice(at, 0, seg)` ⇒ 下标会漂移 | `seq` 由**业务键**派生（`iteration` + `kind` + `toolCallId`），见 §9.2 |

### 9.2 parts 读写路径（一处定义、两处消费）

**写**（`DbMessageToolsMutations.cs` 的 `Upsert`）：

1. 先读该 `id` 现有行的 `meta`；
2. `DbMessageParts.HasBlockStructure(meta)` 分流：
   - **有**块结构（老格式）⇒ 整行原样写回，`message_parts` 一个字节不碰；
   - **无**块结构（新格式）⇒ 块结构剥进 parts，`messages.meta` 只留非块字段（`thinking` 顶层汇总、`error` 等）。
3. `seq` 编码（`DbMessageParts.EncodeSeq`）：`iteration` 主序 → `kind` 次序（thinking < text < tool_use，与渲染层 `SEGMENT_KIND_ORDER` 对齐）→ 并行工具用 ordinal。**同一 `toolCallId` 恒定映射同一 `seq`**，状态更新走 `INSERT OR REPLACE` 单行覆盖，永不追加。

**读**（两处，缺一就丢上下文）：

1. `DbMessageTools.cs` 的 `ToRowsWithParts` —— `ReadRows` / `ListByTurns` 返回前把 parts 合并回 `meta`，对外形状 `{toolCalls, segments, thinking}` **完全不变**，渲染层零改动；
2. `SessionRestoreTools.Wire.cs` 的 `AttachPartsToEntities` —— 压缩 / 恢复读侧。**漏这里的话 `SynthesizeToolResultsWireMessage` / `ReadToolCallIds` 读到空，工具结果整段丢**，压缩后上下文直接崩。

### 9.3 删除路径

`Clear`（整个会话）与 `Delete`（单条）都是**先清 parts 再删 messages 行** —— 顺序不能反，`Clear` 的子查询依赖 messages 行还在。刻意**不加 FK**：`PRAGMA foreign_keys = ON` 下隐式级联会静默带走 parts（§8.5）。

### 9.4 反向验证（§8.4 要求）

- 机制断言：`CREATE TABLE IF NOT EXISTS` 第二次执行安静通过，`CREATE TABLE` 第二次执行必抛（`guard_probe` 套件钉住）。
- **人工反向验证已做**：把 `DbClient.Schema.cs:85` 临时改成 `CREATE TABLE message_parts (`，套件当场红 —— `SQLite Error 1: 'table message_parts already exists'`；改回 `IF NOT EXISTS` 复绿。
- 一个坑记下来：**不能**从 `sqlite_master` 读回 DDL 再执行来验幂等 —— SQLite 存的是规范化文本，`IF NOT EXISTS` 已被剥掉，那样写必然常红。

### 9.5 回归套件 `tests/WishfulClaw.MessagePartsRegressionTests`

42 条断言，六组：

| 组 | 钉住什么 |
|---|---|
| 建表 | 表存在、列顺序、`WITHOUT ROWID` |
| 幂等 | `IF NOT EXISTS` 不是摆设（含反向） |
| `seq` 编码 | 同键恒定、段内序、跨轮不串、并行工具不撞 |
| 新格式写入 | meta 不含 `segments`/`toolCalls`、非块字段保留、parts 三行、读侧合并回来、**状态更新后行数不变** |
| 老格式 | 再次 upsert 后 `meta` **逐字节不变**、零 parts 行、读侧原样返回 |
| 删除 | 单条清、整会话清、无孤儿行 |

写测试时踩到的坑：S-276 之后 `ListByTurns` 只数**真实用户消息**，测试会话里没有 `role='user'` 行就取不到任何窗口 ⇒ 读侧断言必红。每个测试会话都要先种一条用户轮起点。

## 十、后续 / 已知隐患（2026-10-30 刀 11b 补刀时发现，**本迭代不处理**）

> 这一节是**文档留痕**，不是待办清单。两条都写在代码注释里了，但注释会随重构消失，需求单不会 —— 所以再写一遍。

### 10.1 `db/messages-update` 是死端点 —— 将来谁要启用，必须先做分流

`DbMessageToolsMutations.cs` 的 `Update` 方法（注册在 `DbModule.cs:52`）写 `meta` 是**整行覆盖**，且**完全不碰 `message_parts`**。

后果：新格式消息的块结构在 parts 里，而读侧 `MergePartsIntoMeta` 会用 parts 覆盖 meta 里的 `segments` / `toolCalls` ⇒ **通过这个端点写进 meta 的块结构会被静默吞掉**。不报错、不告警，写完读回来就是「没写进去」。

**当前是死端点**：全仓 grep `messages-update` 只有 `DbModule.cs:52` 那一行注册，渲染端零调用。

**将来启用时的硬要求**（代码注释 `DbMessageToolsMutations.cs:165-170` 已标，此处再记一遍）：必须改成与 `Upsert` **同一套分流** —— `HasBlockStructure` ⇒ 原样写 meta；否则 `SplitMeta` + `WriteParts`。**别直接拿它回写 `segments`。**

### 10.2 `clamp` + `INSERT OR REPLACE` 的组合会静默覆盖 —— 真正的防线不在本迭代

`EncodeSeq`（`DbMessageParts.cs:83`）的 `safeOrdinal = Math.Clamp(ordinal, 0, 99)`（`:86`），配合同表主键上的 `INSERT OR REPLACE`：**同一轮工具数超过 99 时，第 100 个之后全部撞同一个 seq，被后写的覆盖掉，段静默丢失。**

**这次是怎么发现的**：靠「实测一条消息有 148 次工具调用」才暴露 —— 148 − 100 = 48 段被吞。不是靠推理推出来的，是数出来的。**这意味着它是不可测的**：正常会话根本到不了 99，测试也造不出来，只有真实长跑会话才会踩到。

**已知的两处缓解（都不是根治）**：
- 缺 `iteration` 的老段改走 `EncodeFallbackSeq`（`:106`，负区间 `FallbackSeqBase = -1_000_000_000L`，`:112`）—— 解决了「老段与真实第 N 轮抢 ordinal」这一半问题，`PartsFromToolCalls` 已改走兜底（`:302`）。
- `:74-76` 的注释说明：clamp 到 99 是**保守取值**，不是编码硬边界；真要突破，把上限提到 799 即可，编码本身不用动。

**真正的防线（本迭代不做）**：**写入时检测 seq 冲突且 payload 不同 ⇒ 抛错或告警**，而不是让 `INSERT OR REPLACE` 静默盖掉。这是唯一能兜住「同轮工具数超 99」的机制，但它要动写入主路径、要新增冲突检测查询，**不在 v3-iter-5 收尾阶段做**。

**留一句给下个迭代**：现在这个隐患的暴露方式是「用户发现某段工具调用不见了」，而那时已经无从追查。要么做上面那条防线，要么把 clamp 上限抬到远大于任何现实轮次（如 799），二选一，别一直悬着。
