# S-317  自定义请求头编辑器没有「编辑态 / 已保存态」

> 登记：2026-11-05 10:30。来源：老大口述（见 §一）。
> 状态：**待开工**。
> 关联：与 S-316 同一次口述拆出。本条纯渲染层，不碰 C#，可独立回滚。

## 一、原始诉求

> 以及页面的自定义请求头没有编辑形态和保存后形态的区别，导致用户编辑了请求头以后不知道是否保存了

## 二、现状（代码事实）

### 2.1 每敲一个字符就保存一次，但界面零反馈

`RequestHeadersEditor.tsx`：

- `patchRow`（`:97-99`）→ `commit`（`:80-95`）→ `onChange(committed)`
- `commit` 里做三件事：`setRows` / 校验 / 调 `onChange`
- 父级 `ProviderConfigPanel.tsx:81-85` `handleHeadersChange` → `updateProvider(provider.id, { requestOverrides: {...} })`
- `updateProvider` 是 store 动作，即时写状态并落库

结论：**输入即保存**，用户每敲一个字符就是一次持久化。界面上没有「未保存」，没有「已保存」，也没有保存按钮。

### 2.2 同面板的其它字段有反馈，请求头没有

`ProviderConfigPanel.tsx` 里 API Key 走 `onFocus` 记原值 / `onBlur` 触发拉模型 / `toast` 提示（`:181-185`、`:63-77`），用户能感知到「生效了」。请求头这一段什么都不给——这是同一条口述里老大说「不知道是否保存了」的直接原因。

### 2.3 校验失败时的行为也反直觉

`commit` 遇到非法行会**跳过该行、把其余行照常提交**（`:84-92`：`continue` 后仍执行 `onChange(committed)`）。用户看到红字提示的同时，其它行已经悄悄存了。「有错就是没保存」才是符合直觉的语义。

## 三、方案：编辑 → 保存两态

1. 组件维护两份状态：`draft`（编辑中）与 `saved`（已提交）。**输入只改 `draft`**，不再调 `onChange`
2. 底部按钮行改成 `保存` / `取消`：
   - `保存` 仅在 `dirty` 且无校验错误时可用
   - `保存` ⇒ `onChange(draft)` + `toast.success` + `saved = draft`，状态回 clean
   - `取消` ⇒ `draft` 回滚为 `saved`
3. section 标题旁给状态文字：`dirty` 时显示 `未保存`，clean 时无标记（与现有 `badge={headerCount > 0 ? headerCount : null}` 并存，`badge` 显示条数）
4. **校验失败整体阻止保存**：任一行非法 ⇒ 该行红字 + `保存` 置灰，不再「跳过非法行存其余」
5. 切换 provider 时（`key={provider.id}` 重挂载）草稿丢弃

### 3.1 为什么不做「切走前确认」

`key={provider.id}` 是父级重挂载，React 层面拦不住，要拦得把 draft 提升到 store 或加 `useBlocker`，成本远大于收益。折中：`未保存` 状态文字足够显眼，用户看得见自己没保存——这正好也是老大要的「有编辑形态和保存后形态的区别」。

### 3.2 为什么只有这一段是两态，其它设置项仍即时保存

其它字段（apiKey / baseUrl / homepage / type / cacheTtl）都是**单值**，即时保存更顺手，且已有自己的反馈路径。请求头是**一组同构结构**，整组提交语义更清晰，而且「手滑改坏一个头立刻生效」的风险明显更高（一个错的 `User-Agent` 就能让服务商 403）。

两套规则只在这一个 section 里出现，不会让用户搞混——因为请求头这一段有明确的按钮，其它没有。

## 四、明确不做

| 项 | 不做理由 |
|---|---|
| 把 apiKey / baseUrl 等一并改成两态 | 超出本条范围，且会打断它们现有的事件链（apiKey 的 `onBlur` 还兼着拉模型） |
| 草稿存进 store / 持久化 | 草稿是临时态，落库反而制造「半保存」状态 |
| 加「恢复预设默认头」按钮 | 预设头与用户头现在混在同一张表里，无法区分来源。真要做得先给条目加 origin 字段，属于新需求 |

## 五、验收

1. 改任一行值 ⇒ section 出现 `未保存`，`保存` 可点
2. 点 `保存` ⇒ toast 成功提示，`未保存` 消失，请求头表变成展示态（输入框不再高亮编辑）
3. 点 `取消` ⇒ 值回到上次保存的样子，`未保存` 消失
4. 什么都没改 ⇒ `保存` 置灰
5. 把某个头名改成非法字符 ⇒ 该行红字，`保存` 置灰（其它行**不再**被偷偷提交）
6. 切到别的 provider 再切回来 ⇒ 看到的是上次**保存**的值，草稿不残留
7. 中英文案同步（`locales` 下 `provider.config.requestHeaders.*` 新增 key）
8. 门禁：`npm run typecheck`（web 配置）+ `npm test`

## 六、风险

- 组件由「受控即时提交」改成「内部草稿」，父级 `handleHeadersChange` 语义不变（仍接一个完整 headers 对象），不影响 S-316
- `ProviderConfigPanel` 里 `headerCount` 用的是 `provider.requestOverrides?.headers`（已保存值），改完后 badge 仍显示已保存条数——这是对的，无需改
- `CollapsibleSection` 折叠时组件不卸载（只是隐藏），草稿不会因折叠丢失

## 七、实施记录（2026-11-05，提交 `6e660276`）

### 7.1 改了什么

| 文件 | 改动 |
|---|---|
| `RequestHeadersEditor.tsx`（232 行） | `rows` 是草稿、`saved` 是已提交快照；`errors` 与 `dirty` **派生**而非 state（行改对了状态自然跟上，不会有一个「错误表落后于行」的窗口）；`保存` 在 `!dirty \|\| hasErrors` 时置灰；`取消` 把 `rows` 重置回 `saved`；`dirty` 时按钮行尾出「未保存」 |
| `locales/zh/settings.json`、`locales/en/settings.json` | 新增 `save` / `cancel` / `unsaved` / `saved`；`hint` 补 `{{organization}}` / `{{project}}`，并说明变量为空时整条头不发 |

`saveHeaders`（原 `commit`）拆成两个纯函数：`toHeaders(rows, errors)` 出对象、`sameHeaders(a, b)` 判脏。原来的 `commit` 一个函数里既改 state 又校验又调 `onChange`，是「校验失败还偷偷提交」的结构性原因 —— 把调 `onChange` 从校验路径里摘出来，这个 bug 就不可能复发。
