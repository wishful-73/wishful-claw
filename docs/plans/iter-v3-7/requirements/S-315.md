# S-315 · 连续工具调用时，工具 run 折叠块每个工具都开合一次

> 登记：2026-11-05 08:35（老大原话见 §一）
> 状态：✅ 已实施（2026-11-05，刀 4），**真机待验**
> 定位：优化项。老大判为「导致窗体抖动的来源之一」

## 一、现象（老大原话）

> 就是我们在执行过程中有个工具调用折叠块，如果有连续的工具调用会折叠起来。但是这个工具调用折叠块有个问题，就是有一个工具调用就展开，这个工具结束就收起，下一个工具调用继续展开。这个展开和收起的频率太高了。我希望收起的触发方式调整一下，需要直到渲染下一个输出或者思考，并且当前工具调用下没有执行中的工具了才收起

关键在最后一句：**收起的前提不是一个工具跑完了，而是「流程真的往前走了」**。

## 二、根因（代码事实，非推测）

### 2.1 开关就在一个三目里

`src/renderer/src/components/chat/render-density.ts:102-110`

```ts
export function deriveToolRunCollapsed(
  density: ChatRenderDensity,
  ordinaryCount: number,
  activeCount: number
): boolean {
  if (ordinaryCount <= 0) return false
  const policy = getDensityPolicy(density)
  return activeCount > 0 ? policy.runCollapseWhileActive : policy.runCollapseWhenDone
}
```

`activeCount` = run 内**当前在跑**的工具数（`execution-outline.ts:360` 收集 `isActive` 项，`:371` 写入 run）。
连续调用时它在 `1 → 0 → 1 → 0` 之间来回跳，于是每个工具开始时走 `runCollapseWhileActive`，结束时走 `runCollapseWhenDone`。

### 2.2 三档取值决定抖动只发生在紧凑档

`render-density.ts:55-89`

| 档位 | `runCollapseWhileActive` | `runCollapseWhenDone` | 结果 |
|---|---|---|---|
| `text` 纯文本 | `true` | `true` | 恒收起，**不抖**（过程层本来就不给看） |
| `compact` 紧凑（**默认档**） | `false` | `true` | **展开 → 收起 → 展开 …… 抖** |
| `detail` 详情 | `false` | `false` | 恒展开，**不抖** |

所以这条**只影响默认档**，而这恰好是绝大多数用户看到的那一档。

### 2.3 「done」这个判定本身是错的

`execution-outline.ts:345-390` 的 `closePendingRun()` 有两个完全不同的触发来源：

1. **循环里遇到非 `tool_use` / `tool_result` 块**（`execution-outline.ts:394-397`）—— 也就是**出现下一段文本或思考**，run 真的结束了；
2. **循环结束后兜底调用**（`execution-outline.ts:476`）—— 此时流可能还在继续，下一个工具随时会来。

两者都算 `defaultCollapsed` 的「done」，但它俩是一回事吗？不是。第 2 种情况下 run 根本没有结束，只是「这一刻没有工具在跑」。

`deriveToolRunCollapsed` 拿不到这个区别，只能用 `activeCount` 近似 —— 近似错了。

### 2.4 为什么以前没这么刺眼

`compact` 档的 policy 注释写着「与 1.0.1 线上行为等价」。也就是说这不是这次新引入的，是一直如此；只是过去工具串短、并发少，用户来不及看出开合。现在 agent 连续调用的密度上来了，抖动就浮出来了。

## 三、期望行为（老大定）

收起必须**同时**满足：

1. 该 run 之后已经渲染出下一段输出或思考（流程确实往前走了）；
2. 该 run 内没有任何执行中的工具。

只满足第 2 条、不满足第 1 条 ⇒ **保持展开**。

换句话说：一串连续工具在跑的过程中，折叠面板只展开一次，中间不再收放。

## 四、修法方向（开工时不照抄，以实测为准）

把「是否收起」的依据从 `activeCount` 换成 **run 是否封口（sealed）**：

- `sealed = true` 的情形：遇到非工具块而 close；或整条消息已结束（`!isStreaming`）。
- `sealed = false`：流式未结束时兜底 close，之后可能还有工具。
- 判定收敛成：`sealed ? policy.runCollapseWhenDone : policy.runCollapseWhileActive`。
- `activeCount > 0` 继续保留一个作用：**有执行中的工具时绝不收起**（守住 `text` 档「过程层一律收起」的语义不被这一步带偏）。
- 用户手动 toggle（`AssistantMessage/index.tsx:317-342` 的 `toolRunCollapseState`）优先级不变，不被下一帧弹回去。

改动面预估：`execution-outline.ts` 的 `closePendingRun` 加一个「为什么关闭」的参数 + `ToolExecutionRun` 加 `sealed` 字段 + `deriveToolRunCollapsed` 换判据。**不碰** `CollapsibleHeightPanel`、不碰三档 policy 的取值、不碰 `text` / `detail` 两档的实际表现。

## 五、验收（真机，dev 实例）

1. 默认（紧凑）档跑一串连续工具（≥3 个），**全程只展开一次**，中间不收起。
2. 工具串结束、正文出现 ⇒ 收起。
3. 工具串结束后又来一段思考或新工具 ⇒ 先收起，新 run 再展开（这是两次正常开合，不是抖动）。
4. 手动点开/收起仍然生效，且不会被下一帧弹回。
5. `text` / `detail` 两档行为与现在**完全一致**（回归，不许因为这条改变极简档藏过程、详情档全摊开的语义）。

## 六、边界

- **不解决 S-233**（消息列表整体抖动，另一条路径，仍挂账）。这条只处理「工具 run 折叠块自身的开合频率」。
- 不改三档的语义定义，不改动画时长/缓动。
- 不做「记住用户在每个 run 上的开合」这类状态持久化。

## 七、与 S-233 的关系

老大原话是「这个是导致窗体抖动的来源之一」—— 是**之一**，不是全部。修完这条之后 S-233 仍可能复现，两者不要混为一谈，也不要指望一条治两条。

## 八、实施记录（2026-11-05，刀 4）

### 8.1 改了什么

**判据换人**：`render-density.ts` 的 `deriveToolRunCollapsed` 第三参从 `activeCount: number` 改成 `sealed: boolean`。

```ts
return sealed ? policy.runCollapseWhenDone : policy.runCollapseWhileActive
```

**封口从哪来**：`execution-outline.ts` 的 `ToolExecutionRun` 新增 `sealed` 字段；`closePendingRun()` 改成 `closePendingRun(sealed: boolean)`，三个调用点按来源给值：

| 调用点 | 传值 | 理由 |
|---|---|---|
| 循环里遇到非 `tool_use` / `tool_result` 块 | `true` | 「下一段输出或思考来了」—— 唯一真正的封口信号 |
| 子 agent `Task` 卡前 | `false` | 只是让卡片站在正确位置，之后随时还有工具 |
| `boundaryAfter*` 强制分段 | `false` | 切开 ≠ 结束（且这两个参数全仓无人传，是死路径） |
| 循环结束后兜底 | `!isStreaming` | 流还在跑 ⇒ 未封口；流结束 ⇒ 这就是最后一段 |

**顺带拆文件**：`execution-outline.ts` 加完这些注解后到 **520 行**，顶穿 AGENTS.md 的 500 行硬线。把分类判据整块（工具名常量表、`is*ToolName`、`outputTextForSummary`、`hasStructuredOutputError`、`resolveToolStatus`、`getToolCategory`、`getToolVisibility`、`buildActiveSummary`）搬到新文件 **`execution-outline.classify.ts`（251 行）**，主文件回落到 **317 行**。对外入口用 `export { … } from` 原样转出，调用点零改动；类型留在主文件，新文件只做 `import type`，运行时无循环依赖。

### 8.2 为什么不是「加个冷却时间」

第一反应容易想到「收起前等 500ms，期间来了新工具就不收」。不采用：那只是把抖动拍扁成延迟，用户看到的是「闪一下再收」，并且定时器本身又是一份新状态。根因是**判据选错了变量**，换判据才是治本。
