## 三、本轮待勘（不预设结论）

1. **33ms 这档对「密集工具 + 快模型」够不够** —— 实测一次高吞吐 run 的单位时间事件量、flush 次数、渲染帧耗时。
2. **前台 / 后台分档是否真吃到** —— 分档只在窗口失焦时切 150ms，前台始终 33ms；若笔记本上测试时窗口一直在前台，等于只有一档。
3. **main 侧合批只解决跨进程消息量** —— 渲染端自身的瓶颈是否才是主因。历史证据指向这里是热点：`hooks/use-typewriter.ts` 的 `getCatchupStep`（`iter-v2-29/plan.md` T-15）、`iter-v2-30` S-31 记的「上游渲染池单帧增量」。
4. **「停止」延迟生效的机制** —— 是渲染队列堵死导致事件循环饿死，还是停止链路本身有异步等待。

## 七、勘测与实施（2026-09-24）

老大 14:13 口径：「渲染降级不一定能根治，有些电脑性能就在哪里」⇒ 目标定为**把主线程从固定帧频里解放出来**，并如实交代根治边界。

### 7.1 勘测：链路现状（三处批处理都已经在）

| 环节 | 现状 | 结论 |
|---|---|---|
| main 侧 | `AdaptiveEventBatcher`：可加事件按 run 攒，`flushMs` 33ms 或超 `maxBufferSize`(200) 即推；控制类事件先 flush 再直通（保序） | S-135 的成果，**在** |
| renderer 收包 | `agent-stream-receiver`：MessagePack 一次解多条信封，逐事件分发 | 无热活 |
| renderer store | `chat-store/index.ts`：`text_delta` / `thinking_delta` 进 `_pendingStreamDeltas`，**rAF 合并后一次 `setState`**；`tool_use_args_delta` **直接丢弃**（等 `tool_use_generated` 的全量入参） | 已批处理 |
| 显示层 | `useStreamingRenderPool`：rAF 32/36ms 一帧、`ceil(pool/K)` 排空；正文 markdown 按「已稳定块」memo，每帧只重解析尾巴；思考块是 `whitespace-pre-wrap` 纯文本 | 已降级 |

⇒ 「每个 delta 一次 setState」这条**两轮之前就治过了**，S-149 的症状不是它。

### 7.2 勘测：仍会占满主线程的是哪条

**帧频固定 + 单帧渲染成本随内容变大。** 池子（未渲染增量）一大，说明上游在爆发；此时
每一帧要干的活也跟着变重 —— 正文重解析 markdown、思考块重排整段长文本。固定 32ms 催帧
意味着主线程一帧接一帧被占满，点击 / 滚动 / 停止全部排队 ⇒ 与记录的现象吻合：**整页像
截图一样静止、系统不报未响应、停止按钮几分钟才生效**。

两条**不是**本轮落点，记清免得回头走错：

- 控制类事件（工具生命周期、段边界、循环起止）**逐个直通、不攒批** —— 那是 batcher 刻意保序的结果（7.1 第一行），不是漏批；
- `message_end` 每次造新 `messages` 数组 ⇒ 每轮 LLM 一次全量消息重渲染，量级远小于流式帧。

### 7.3 实施：帧间隔按池子压力自适应

`src/renderer/src/hooks/use-typewriter.ts`：

- `RenderPoolConfig` 增两个字段：`pressurePoolSize`（压力起算体积）、`maxFrameIntervalMs`（上限）；
- 新增纯函数 `resolveFrameIntervalMs(poolSize, config)`：`poolSize <= pressurePoolSize` 时返回
  基准 `frameIntervalMs`（**与改动前一字不差**）；超过则线性放宽，到 **4 倍**压力阈值时拉满；
- `tick()` 由「固定 `config.frameIntervalMs` 比较」改为「用 `resolveFrameIntervalMs(poolSize)`」。

取值：`agile` 32ms → 最多 64ms（压力起算 2000 字符）；`elegant` 36ms → 最多 72ms（1500 字符）。

**只放宽帧频，不动步长** —— 步长仍是 `ceil(pool/K)`，iter-29 T-15「取消步长上限、让长思考能追上」的结论原样保留（§二 那条不许当回退）。

### 7.4 能根治到什么程度（如实说）

- **能改善**：上游爆发时主线程不再被固定帧频连续榨干，点击 / 滚动 / 停止的响应窗口显著变大 —— 这正是「停止几分钟才生效」的直接对治；
- **不能保证根治**：池子拉到上限后，每帧的绝对渲染成本仍由**内容长度 × markdown 解析**决定。老电脑上「整页假死」的极端场景，本改动只把**触发门槛往后推**，没有消除。要真正消除得上「流式期间限制单帧渲染的文本量」（例如思考块只渲染最近 N 字符），那是产品取舍，**未做、等口径**；
- **未做**：main 侧档位（33ms / 150ms）未动 —— S-135 的「固定两档、不做自适应」口径保持；渲染池 `catchupFrames` 未动。
