## 2. 现象

`package.json` 里 **eslint / prettier / biome 一个都没有**，根目录无任何 lint 配置：

```
=== lint configs ===
(empty)

=== devDeps lint ===
(empty)
```

现有门禁只有三条：

| 门禁 | 管什么 | 不管什么 |
|---|---|---|
| `npm run typecheck`（node / web / test 三配置） | 类型 | 未使用变量、未使用 import、浮空 promise |
| `npm test`（130 个套件） | **已写用例** 的正确性 | 新增代码有没有用例（它统计的是用例数，不是覆盖率） |
| `dotnet build`（两套 sln `-t:Rebuild`） | C# 编译 | 同 typecheck 的那一类 |

**⇒ 「代码写了但没人调用」这一类问题，三道门禁全都不管。**

### 2.1 本轮的实证

这一轮审查找出来的 13 条里，至少 3 条是 lint 能自动抓的：

| 编号 | 问题 | 对应规则 |
|---|---|---|
| D-1 | `channel-media.ts` 全仓零 import | `import/no-unused-modules` 或自定义「导出零引用」检查 |
| D-8 | `FeishuMediaApi.downloadUrl` 零调用 | `no-unused-vars`（私有方法）/ `import/no-unused-modules` |
| D-10 | `PLUGIN_TOOL_DEFINITIONS` / `getDefaultPluginToolNamesForType` 零调用 | 同上 |

**这三条都是我人肉 grep 出来的。** 同一类问题每轮都要重查一遍，说明缺的是机制不是勤快。

### 2.2 为什么对这个项目尤其重要

- **1875 提交、约 18 万行 TS + 6.7 万行 C#**
- **接近 20 个迭代由 agent 自行开发**

人的直觉会累，agent 不会 —— 但 agent 会**一致地犯同一类错**（写完新模块忘了接线、改了声明忘了改读法，S-353 与本轮 D-1 是同一个模式的两次发作）。lint 恰好是「一致性检查」这个活里最便宜的一种。

## 3. 代码链路 / 现状盘点（2026-11-11 实读）

| 项 | 现状 |
|---|---|
| TS 文件数 | 1038（不含 `.d.ts`） |
| TS 行数 | 约 178,721 |
| 现有格式化约定 | `.editorconfig` 存在；无 prettier |
| 现有 tsconfig | `tsconfig.json` / `tsconfig.node.json` / `tsconfig.web.json` / `tsconfig.test.json` |
| 现有门禁脚本 | `scripts/ci-checks.mjs`（pre-push 钩子 + GitHub Actions 共用） |
| CI | `.github/workflows/ci.yml` —— 只跑 TS 侧，理由已在注释里写明（runner 没有 .NET 11 预览 SDK） |

`scripts/ci-checks.mjs` 已经把「typecheck + TS 测试」收在一个脚本里，本地钩子和 CI 共用一个判据 —— **lint 直接挂进去即可，不需要新造一条链路**。

## 4. 根因

**门禁是在「能跑起来」这个目标下长出来的，不是在「不出低级错」这个目标下长出来的。**

历史顺序是：先有 typecheck（保编译过）→ 再有测试（保行为对）→ 没有 lint（因为前两个已经能让版本发出去）。这在迭代早期是对的，但在「20 个迭代由 agent 写」的量级下，缺 lint 的边际成本开始明显。

## 5. 修复方向

### 5.1 分三步，不要一次上全量

**第一步：只报错、不改格式、不阻断**

- 选 `eslint` + `typescript-eslint`（生态最全，规则可逐条开关）；
- **不引入格式化规则**（省掉与 `.editorconfig` 的冲突，也避免一次性产生几万行 diff）；
- 先只开三条最保守的：`no-unused-vars`、`no-floating-promises`、`eqeqeq`；
- `npm run lint` 手动可跑，**先不进 pre-push 钩子**。

**第二步：统计基线，变成挂账**

- 跑一遍，把现有违规数落进 `docs/`（比如「当前 412 处 `no-unused-vars`」）；
- 定规则：**新增代码不得增加违规数**（可以是简单的「当前数 ≤ 基线数」比对，不需要逐行豁免）。

**第三步：接进门禁**

- 挂进 `scripts/ci-checks.mjs` 的 `STEPS`；
- 本地 pre-push 与 GitHub Actions 自动共用（这条链路已经有了，见 §3）。

### 5.2 可选：自定义「导出零引用」检查

`no-unused-vars` 管不到「导出了但没人 import」。这条要自己写，约 50 行 node 脚本：

```
扫 src/**/*.ts 的所有 export 名 → 全仓搜 import/require → 报零引用的
```

**注意误报**：入口文件、`preload` 暴露面、类型声明、被动态字符串拼出来的调用（比如 IPC 通道名）都会误报。所以这一步**只做提示，不做阻断**。

## 6. 代价与取舍

- **一次性上全量规则会导致几千条违规**，团队会直接关掉它。所以 §5.1 的「三步」不是保守，是**唯一能活下来的路径**。
- **`no-floating-promises` 需要类型信息**（`parserOptions.project`），会让 lint 变慢。1800 个文件大概 30~60 s，可接受但要知道。
- **格式化规则**（prettier）建议**永远不进**门禁 —— 它会和 `.editorconfig` 打架，且产生巨大 diff，与「只修该修的」纪律冲突。
- **C# 侧不在本单**：`dotnet build` 已有警告体系，且 S-320 的 `NU1903` 还挂着，此时加 C# 分析器会把信号淹没。

## 7. 刻意不做

- **不引入 prettier / biome 做格式化** —— 见 §6。
- **不做「违规数清零」的目标** —— 那不现实，会变成一次巨大的无关改动。
- **不在本迭代接进 pre-push** —— 先跑起来看基线，下一个迭代再决定。
- **不碰 C# 侧** —— 见 §6。

## 8. 验收

| 阶段 | 验收方式 |
|---|---|
| 第一步 | `npm run lint` 可跑通并输出违规列表；`package.json` 有该脚本 |
| 第二步 | `docs/` 下有一份基线数字 + 「新增不得增加」的判定脚本 |
| 第三步 | `node scripts/ci-checks.mjs` 里能看到 lint 步骤；故意写一个未使用变量，push 被挡住 |

## 9. 开放问题

1. **选 eslint 还是 biome？** eslint 生态全、规则可细调；biome 快、零配置但规则少。倾向 eslint（因为我们要的是**规则**，不是格式化）。
2. **基线数字定多少算合格？** 建议「当前数」为基线，只拦增量。
3. **要不要连 `.wishful-work-dev/` 之类的 scratch 目录一起 ignore？** 要。
