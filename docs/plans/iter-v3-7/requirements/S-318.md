## 四、必须处理的真缺陷：僵尸服务商记录

`provider-materialization.ts:177 reconcileProviders()` 的机制（实读）：

- `:198` 只遍历 **现存** `builtinProviderPresets` ⇒ preset 删掉后，该 `builtinId` 的单条记录**不再进内存列表**（自然清理，符合预期）
- 但 `:189-194` 会把同一 `builtinId` 的**第二、三条记录**收进 `extraBuiltinRecords`，`:224-229` 里

```ts
const preset = p.builtinId ? builtinProviderPresets.find(...) : undefined
providers.push(preset ? fillMissingProtocolFields(p, preset) : p)
```

`preset` 为 `undefined` ⇒ **原样 push 进列表**。

⇒ 删掉 preset 后，R-9.C.7 那句注释说的场景（「官方 + 中转」会有两三条同 preset 记录）会把 WorkBuddy 记录变成**列表里的僵尸服务商**：名字还在、能选中、`oauthConfig` 是记录里的旧快照，但刷新逻辑没了、重新授权入口没了，token 过期即死。

**处理方式**：`reconcileProviders` 增加显式剔除名单

```ts
const REMOVED_BUILTIN_IDS = new Set([
  'workbuddy', 'workbuddy-ai',          // A 段
  'codex-oauth', 'copilot-oauth', 'moonshot-coding'  // B 段
])
```

命中即**连 `extraBuiltinRecords` 一起丢弃**，不依赖「preset 不存在」这个隐式行为。

**配套校验**：`id` 落盘在会话（SQLite）/ 插件 / 定时任务 / 渠道 / 设置项里（`:200-205` 注释），剔除记录后这些引用会悬空。需确认回落路径：会话 `providerId` 失效时是否回落到全局激活 provider。**这一条要在实施前先验，验不通就得改成「保留记录但不显示」。**
