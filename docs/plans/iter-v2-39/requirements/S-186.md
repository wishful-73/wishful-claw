⚠️ 上表是**小文件（`latest.yml`）** 的探测；**开工时必须用真实 exe（113 MB）复测**，包含：能否下载 / 能否断点续传 / 实际速率 / `Content-Disposition` 是否透传。

### 真实安装包复测（2026-10-10 18:20，GET + `Range: 0-1048575`（1 MiB）+ Chrome UA，对 v0.2.38 的 `wishful-claw-0.2.38-setup.exe`）

|---|---|---|---|
| `https://ghproxy.net/` | **HTTP 206**，回 1 MiB | 131.8 KB/s | ✅ **可用** |

⇒ 下拉里 `gitproxy.click` 与 `ghproxy.homeboyc.cn` 均标注「当前不可用」（站点状态随时会变，保留但不推荐）。

## 六、与 S-182 的统计口径（**已裁定：b + c 都要**）

### 老大裁定（2026-10-10 10:21）

> 「b和c都要 你的推荐a违背了我做这个统计的目的」

⇒ **b（官网点击统计）+ c（下拉保留本站直链）两者都做**；
❌ **否定 a** —— 把口径缩成「只剩应用内更新」，**违背 S-182「统计真实分发量」的初衷**（助手的建议错在这里：拿「数字变小」换了省事）。

### 为什么 b + c 组合成立

S-182 当初否掉过「前端埋点」，理由是**它数不到应用内自动更新**。现在 b 成立，靠的是**分工**（且 10:38 后 b 已**不是**前端埋点，而是**官网中转页**）：

| 来源 | 由谁统计 |
|---|---|
| **官网点击**（不论选哪个加速源） | **b —— 官网中转页 `/go`**（页面请求进 `clicks` 日志，页面再跳加速站） |
| 官网点击选了**本站直链** | nginx `/downloads/` 日志（**不经 `/go`，与上一行正交**） |
| **应用内自动更新**（`electron-updater`） | nginx `/downloads/` 日志（**与 S-182 原设计一致**） |
| 检查更新（`latest.yml`） | **不计入**（S-182 原口径不变） |

⇒ b **只承担「官网点击」这一半**，自动更新那半仍由服务器数 —— **不是回到当初被否的「纯前端埋点」**（中转页方案下**不需要任何上报接口**，计数靠页面请求本身）。

### 中转页：**官网新增第四个入口 `/go`**（2026-10-10 10:38 定）

老大原话：

> 「我的想法是官网新建一个中转页面，点击下载先到我们中转页面，基于这个中转就可以记录下载次数了，然后中转再直接跳转到加速站去，这里是否成功就跟我们没关系了」

**做法**：加速站各项的 `href` 指向自己官网的 `/go`，**中转页记一次访问（＝一次下载点击）后自动跳转到加速站**。

**落点（4 处）**：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `website/go.html`（新建） | 照 `download.html` 骨架，改 title，引 `./src/go-main.tsx` |
| 2 | `website/src/go-main.tsx` + `go-page.tsx`（新建） | 读 query → 显示「正在前往下载…」+ 兜底链接 → `location.replace(target)` |
| 3 | `website/vite.config.ts` | `PAGES` 加 `'go'`；`rollupOptions.input` 加 `go: 'go.html'` |
| 4 | nginx（**归 S-182**） | 加 `location = /go` + **独立日志** `wishfulclaw-clicks.log`；尾斜杠 301 正则补 `go` |

```nginx
location = /go {
    access_log /var/log/nginx/wishfulclaw-clicks.log combined;
    try_files $uri.html =404;          # /go -> /go.html（与现有 /download 同款）
}
location ~ ^/(download|guide|changelog|go)/$ { return 301 /$1; }   # 补 go
```

**计数原理** —— **页面请求本身就被 nginx 记下，中转页里一行上报代码都不用写**：

- 点加速站项 ⇒ 浏览器请求 `GET /go?src=ghproxy.net&u=...` ⇒ 进 `clicks` 日志 ⇒ **计 1 次**；
- `combined` 格式的 `$request` **含 query string** ⇒ 聚合脚本能按 `src` 拆出**各加速站的点击量**；
- 跳转由页面里的 `location.replace()` 完成，**成败与我们无关**（老大原话）。

**与裸 `302` 的差别**：多一层页面 ⇒ 能显示「正在前往下载…」、能放**兜底链接**（自动跳转被拦时用户可手点），也不怕 `302` 失败变白屏。**计数口径完全一样。**

**细节（开工时定）**：

- `u` 参数用 `encodeURIComponent` 编码后传，页面 `decodeURIComponent` 还原（裸 `302` 方案里不敢编码，这里没这个顾虑）；
- 中转页跳转**不加人为延迟**（无感最好），兜底链接常驻；
- 中转页视觉从简：logo + 「正在前往下载…」+ 源名 + 兜底链接；
- 页面自身的 JS / CSS 资源请求**不计入**（聚合脚本只认 `$request` 精确匹配 `/go` 的那条）。

**偏差说明**：数的是「**点击**」（进了中转页），不是「加速站真实传输完成」—— 第三方不回报，这是能拿到的最接近分发的数。

### 去重规则（统一一套，覆盖三个来源）

沿用 S-182 已定的规则：**按 `客户端 IP + User-Agent + 文件名` 去重，窗口 1 小时**。

- 并掉**浏览器多线程 `Range`**（走本站直链的下载）；
- 并掉 **updater 分段**（应用内更新）；
- 代价不变：NAT 出口同小时的多人并成 1 次。

⚠️ **中转页方案下两个日志源完全正交、不重叠** —— 加速站点击只进 `clicks`，本站直链只进 `downloads` ⇒ **去重只在各自内部做，两源直接相加即可**。这是它相对「beacon 方案」的额外好处（beacon 会在本站直链上造成前后端重复记录）。

### 展示口径

- **页面上**：仍显示合并后的「已下载 N 次」= **官网点击 + 应用内更新**（两源正交，各自去重后相加）；
- **后台报表**：保留**分源明细**（`web_click` / `web_download_local` / `app_update` / `update_check`）。

### 范围边界

- **b 的落点分两半**：前端（`website/`，属 **S-186**）+ 服务器 nginx 那条 location 与日志聚合（属 **S-182**）。
- ⇒ **两条需求的刀序**：S-182 的聚合脚本要**按「两个日志源」设计**，因此**在 S-186 落地后一起收口**更稳。

## 八、已知限制（登记备查）

1. **应用内自动更新仍走 128 KB/s 的服务器** —— 差分下载通常远小于全量，可接受；但**差分失效回退全量时**，113 MB 仍要慢下。老大已明确不调整 ⇒ 记为已知限制。
2. **加速站是公益服务**，随时可能失效或限速（本次实测 4 中 2 已不可用）⇒ 多源下拉是唯一缓解手段，**但无法保证长期可用**。
3. 走第三方加速站意味着**下载请求经过第三方**（URL 只含版本号与文件名，无敏感信息）。
4. **b 数的是「点击」（进了中转页），不是「下载完成」** —— 走加速站那一段的传输量第三方不回报，这是能拿到的最接近分发的数。
