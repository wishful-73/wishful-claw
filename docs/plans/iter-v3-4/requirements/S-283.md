# S-283 · 桌面截图 / 窗口截图落盘返回路径，不再只留在内存里

> 归属：**本迭代 · 刀 15，已交付（2026-10-30 11:42，commit `3b6e02a9`）**（2026-10-30 11:36 老大拍板「根据开发工作流开始推进」）。
> 代码 + 自动化回归完成，真机 4 条待验。
> 登记 2026-10-30 11:29。

## 一、原话 / 来源

老大 2026-10-30 11:29：

> 「我们桌面截图 和窗口截图好像是返回的 base64，我希望是放到数据目录的临时文件里面，返回的是路径。」

与 **S-275**（压缩对图片失效）同一条链路，是它的**硬前置**。

## 二、现象

| 工具 | 落盘 | 返回形态 |
|---|---|---|
| `DesktopScreenshot` | **完全不落盘** | `image` block，`source.type = "base64"`，data 全量内联 |
| `CaptureAppWindow` | 有可选 `path` 参数，**给了才写盘** | **仍然内联 base64** + 文本行说落在哪 |

实测后果（S-275 §二）：一条 `DesktopScreenshot` 结果 **23~42 万字符**，单条估算 24 万 token，是压缩尾部预算（16384）的 15 倍。

更要紧的是**图一个字节都没留盘** —— 历史消息里的截图想再看，只能重新截；而桌面早不是当时的样子了。

## 三、代码链路

```
DesktopScreenshot
  C# AgentRuntimeDesktopExecutor.ExecuteScreenshotAsync        (:87-111)
  → IPC desktop:screenshot:capture
  → src/main/ipc/desktop-control.ts captureDesktopScreenshot   (:196-248)
  → 返回 { success, data: base64, width, height, originX/Y, scaleFactor, displays }
  → C# CreateScreenshotContent                                 (Encoding.cs :37-60)
  → 只写 {"type":"image","source":{"type":"base64","data":…}}

CaptureAppWindow
  C# ExecuteAppWindowCaptureAsync                              (:120-157)
  → IPC window:capture-self
  → src/main/ipc/reverse-handlers/window-capture-handler.ts    (:51-106)
  → 仅当 targetPath 非空才 persistImageBuffer
  → C# CreateAppWindowCaptureContent                           (Encoding.cs :132-159)
```

两处 `Describe*` 都只输出尺寸与坐标参照系，**路径要么没有、要么只进文字不进图**。

## 四、根因

落盘是「可选」而不是「默认」，且 `DesktopScreenshot` 连这个可选项都没有 —— 它压根没有 `path` 参数。截图只作为 base64 活在报文里，一次对话结束就没了。

## 五、修复方向（已选定 A）

| 层 | 做什么 | 模型能看图 | 省不省 wire | 结论 |
|---|---|---|---|---|
| **A（采纳）** | 落盘 + 路径写进文本行 + **image block 照旧保留** | ✅ | ❌ 本轮不省 | **采纳** |
| B | 落盘 + 只回路径，不传 image block | ❌ 要再 Read | ✅ 立刻省 | 否决 |
| C | 落盘 + 参数控制（`inline:false` 走 B） | 看调用方 | 看调用方 | 否决 |

**选 A 的理由**：老大 2026-10-26 明确否掉过 B 那个方向 ——

> 「不缺[定]模型到底能不能读图，可以先把图放给模型让它看，而不是通过配置就卡死了。」

而且 B 反而更贵：模型每次要对图做判断都得再 `Read` 一次，多一次往返 + 多传一次完整 base64。

**真正省 wire 的一刀在 S-275**：压缩时把 image block 换成 `[图片已省略：…路径…，可重新 Read 查看]`。那句「可重新 Read 查看」要成立，图必须先在盘上 —— 这就是本条是 S-275 硬前置的原因。

**目录与命名**（照抄 S-224 `chat-image-dir.ts` 的手法）：

```
{dataRoot}/screenshots/{yyyy-MM}/{sha256 前 16 位}.png
```

- **按内容哈希命名** ⇒ 同一帧重复捕获落到同一个文件，不涨盘；
- **按本地年月分目录** ⇒ UTC 会把月初月末的截图分错月份；
- **与 `images/` 分家** ⇒ 那边是用户资产（上传/渠道转发），这边是工具产物，量大、要能整体清。

渲染端**零改动**：`oc-media://` 白名单（`local-media-url.ts:22-36`）只按扩展名、不限目录，`.png` 落在哪都能显示。

## 七、代价与取舍（实施后回填）

**已知代价，是故意的：**

1. **本轮不省上下文。** wire 里的 base64 一分没少，S-275 的死循环照旧存在。本条只是把「以后能省」的前提铺好 —— 单看这一刀，内存与卡顿不会有任何改善。别指望它治卡。
2. **每张截图都落盘，即使没人再看。** 内容哈希只能去掉「完全一样」的重复，桌面每帧几乎都不同 ⇒ 一次认真操作会留下几十个 PNG。3000×2000 的 PNG 约 2~5 MB，一天重度使用几十到几百 MB 是可能的。
3. **落盘失败会静默降级。** `persistImageBuffer` 抛错会让整个截图工具报失败 —— 磁盘满 / 权限问题时，本来能看到的图也看不到了。没做「写盘失败仍然返回图」的降级。

## 八、刻意不做（实施后回填）

| 不做 | 为什么 |
|---|---|
| **不自动清理** | 保留期老大还没拍（30 天？总量封顶？）。而且清理必须跳过**当前会话引用过的路径**，否则压缩摘要里指向的图会被删成死链 —— 这不是加个定时器能糊过去的，见 §九。 |
| **不移除 base64**（方案 B） | 老大 10-26 的口径：先让模型看得见图。 |
| **不加 `inline` 开关**（方案 C） | 参数面一开就要两套测试，而默认值永远是 A ⇒ 实际用不到。 |
| **不裁剪 / 缩放 / 转码** | 图片尺寸优化是另一条线（S-275 §五 记着「估算把图片放大约 100 倍」），混进来改动面失控。 |
| **不改 `CaptureAppWindow` 的 `path` 参数** | 落盘变默认后，显式 `path` 仍有意义 —— 模型可以指定存放位置。 |

## 九、待办（移交后续）

**清理策略**（原 §五）仍未定，三个问题需要老大拍：

1. 保留期（建议 30 天）；
2. 是否按总量封顶（如 500 MB）；
3. **怎么判断「当前会话引用过的路径」** —— 这是真难点：压缩摘要里的路径散在 `meta` 与文本里，没有结构化索引。在解决它之前，任何自动清理都有删掉活引用的风险。
