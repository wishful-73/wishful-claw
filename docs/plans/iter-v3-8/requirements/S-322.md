## 三、代码链路（全部主仓实读，2026-11-05 15:00 ~ 15:04）

### 3.1 A 段｜根因：`SessionConversationManager` 永不淘汰

`src/runtime/WishfulClaw.Agent/SessionConversationManager.cs`（主仓 73 行）全文只有三个方法：`GetOrCreate` / `TryGet` / `Remove` / `ClearAll`。**没有任何闲置时间判据、没有容量上限。**

类注释写的是：

> Lives for the process lifetime; entries are removed on session switch or explicit clear.

**这句是错的。** 私有仓核对后（`SessionConversationManager.cs:9-16`）：

> 原注释写「entries are removed on session switch」，但全仓实测 `Remove` 只在**删会话**和 **subagent/goal 结束**两处调用 —— **普通切换会话不释放**。
> 滞留条目的真实来源是「**发过消息**的会话」：每个发过消息的会话都留在这儿，带着「解析后对象 + wire JSON」两份；跑完不会自己消失，直到会话被删除。
> 压缩只让**单个**会话变小，从不让**别的**会话退出 ⇒ 多会话累加就是 GB 级，且永远不会自己掉。这就是 worker `ws` 只涨不降的结构性来源。

主仓对应的 `Remove` 调用点（实读 grep，与私有仓描述一致）：

| 位置 | 场景 |
|---|---|
| `AgentRuntimeTools.cs:408` | `agent/clear-session`（显式清空） |
| `SubAgentExecutor.cs:172` / `.Background.cs:206` | 子 agent 结束 |
| `GoalOrchestratorModels.cs:120` | goal 结束 |

**没有任何一处是「切换会话」或「闲置回收」。**

`SessionConversation.cs:22` 的 `private List<JsonElement> _wireConversation = [];` 是**常驻字段**，而 `JsonElement` 持有底层 `JsonDocument` ⇒ 一张 600 KB 的截图 base64，会随会话**一个字节不少地留在堆上**，直到会话被删。

### 3.2 B 段｜`request_debug` 每轮白推十几 MB

`src/runtime/WishfulClaw.Agent/OpenAIChatProvider.cs:46-55`（实读）：


三个 provider 全一样：`OpenAIChatProvider.cs:49`、`AnthropicMessagesProvider.cs:54`、`OpenAIResponsesProvider.cs:217`。

**而渲染层根本不要它** —— 主仓 `src/renderer/src/stores/debug-store.ts:20-22` 自己写着上限：

```ts

const MAX_RESIDENT_DEBUG_BODY_CHARS = 4_000
```

`debug-store.ts:39-46` 还有 `stripBodyFields` / `stripInlineBody` 在非 dev 模式整个剥掉。

**也就是说：worker 每轮、每次重试都把完整 body 推出去，渲染层收到后 0.03% 留下、99.97% 立刻扔掉。** 中间要走 MessagePack 序列化 → named pipe → 壳重编码 → base64（×4/3）→ JSON → WebView 解回来。

私有仓实测（20 张截图会话）：`11,983,135 → 2,695 字符（0.02%）`，13 项断言全绿。

私有仓还查了一条「按需拉取」的退路 —— `agent/debug-body-read` 全仓只有 renderer 单方面调用，**worker 侧压根没有这个 method，`BodyRef` 也从没被赋过值** ⇒ 断链，不能指望它兜底。

### 3.3 C 段｜`StripDataUrlPrefix` 热路径整串复制

**`Trim()` 把 600 KB 整串复制一遍，只为看前 64 字符**（`:71` 的 `prefixChars = 64`）。而且 `:62` 上 `StripDataUrlPrefix` 内部已经 Trim 过一次，外面又 `.Trim()` 一次 ⇒ **两次**。

这条函数在组包热路径上**每张图跑两遍**：

### 3.4 B + C 三者叠加的实测放大倍数

私有仓的回归套件（`tests/WishfulClaw.RequestBuildAllocationRegressionTests`）口径，**注意 UTF-16 / UTF-8 的区别**：

## 四、根因

三条各自独立，共同构成「worker 用几个 GB」：

| # | 根因 | 性质 |
|---|---|---|
| **A** | `SessionConversationManager` 无闲置淘汰、无容量上限；`_wireConversation` 常驻 `JsonElement` 持有完整 base64 | **真泄漏**（只增不减，永不回收） |
| **B** | `request_debug` 每轮推完整 body，而渲染层上限 4 KB | **纯浪费**（99.97% 生成即丢弃） |
| **C** | `StripDataUrlPrefix` string 版在热路径整串复制，只用前 64 字符 | **纯浪费**（每图每轮 ×2 份 600 KB） |

A 决定「总量」，B / C 决定「峰值与 GC 频率」。**只治 B / C 不治 A，内存依然只涨不降** —— 这是过去几轮打转的原因。

## 五、修复方向

### A 段｜会话闲置淘汰（治根，优先）

`SessionConversationManager` 补两条闸，判据直接照私有仓已定型的设计：

| 闸 | 取值 | 为什么是这个值 |
|---|---|---|
| 闲置淘汰 | **2 小时** | 对齐真实痛点「已经空闲 2 小时了，那条会话还在占着」。太短会把「切回去继续聊」变成一次全量 DB restore |
| 常驻上限 | **8 条** | 闲置时间压不住「一天发了十几个会话」。桌面 Agent 的活跃上下文基本是「手头这一两个任务」，8 条够覆盖来回，超额按最久未访问砍 |

**淘汰是安全的**，因为 `AgentLoop.cs:83-89` 的逻辑是「`MessageCount == 0` 就从 DB 懒恢复」，下次进这个会话会自动重建。

**唯一会丢的**：`SessionConversation._sessCacheHit` 的累积计数（status bar 上的 cache hit/miss 展示）⇒ 展示指标，不影响功能。这一条必须在验收里显式确认「清了以后 cache 计数归零不算 bug」。

需要 `SessionConversation` 加 `Touch()`（最后访问时刻）。

### B 段｜`request_debug` 结构化裁剪

新增 `RequestDebugBodyTrimmer`，三个 provider 全部接入。

**必须是结构化裁剪，不能硬截断** —— 调试面板要 `JSON.parse` 这段 body，截断会把它变成非法 JSON，面板直接报错 ⇒ 等于用「看不见」换「不卡」，是退步。

- 解析 → 把超过 **8 KB** 的字符串值换成 `[omitted N chars]` → 重新序列化
- 阈值 8 KB：正常文本请求体远小于它，只有图片 / 文件载荷会触发
- 解析失败（body 不是合法 JSON）**退回硬截断**并留说明，不让面板以为是完整内容
- 短 body（≤ 8 KB）**走快速路径直接放行**，不为几十字节付一次解析 + 重新序列化

### C 段｜前缀剥离改 span

1. `ProviderContentHelpers` 新增 `StripDataUrlPrefixSpan(ReadOnlySpan<char>)`，**判据与 string 版逐字一致**（同 marker、同忽略大小写、同样只在命中时切），差别只是全程切片零分配
2. `DetectImageMediaTypeFromBase64` 改用它，`stackalloc char[take]` 处理 64 字符前缀
3. `ImageFileProbe.HasCompleteContainerInBase64` 改用它，`stackalloc` 解码头尾窗口（尾部 64 字节）
4. **保留 string 版不动** —— 三处真正要产 string 的调用点（`:408` / `:297` / `:221`）继续用它

## 六、代价与取舍

| 取舍 | 说明 |
|---|---|
| A 段会让「切回去」偶发一次 DB restore | 2 小时内不触发；超时后首次进会话多一次 DB 读。**这是拿一次 IO 换几百 MB** |
| B 段调试面板看不到完整 body | 但**本来就看不到** —— 渲染层上限 4 KB 已经在上游砍掉了。裁剪只是把「砍」提前到 worker，可视化效果一致 |
| C 段是纯性能改动 | 不改任何判据，可独立验证 |
| **两边已漂移** | 私有仓从主仓全量搬出后主仓仍有改动（S-284 等）。**禁止整文件覆盖**，必须按 §三 的实读位置逐点改。尤其 `ProviderContentHelpers.cs` 私有仓已到 479 行以上，主仓结构未必一致 |

## 七、刻意不做（都已实测证伪，别再花时间）

私有仓花了 11-04 一整天证伪的六条，主仓不要再走一遍：

| 别再试 | 实测 |
|---|---|
| 改 GC 模式降 worker | 默认本来就是 Workstation GC（空闲 13.9 MB / 10 线程）；`DOTNET_gcServer=0` 后 250.8 vs 252.0，纹丝不动 |
| 换 AOT 省那 212 MB | Debug×2 + AOT×1 三次独立启动，`managed` **一字不差** —— 那是**数据**不是 JIT。AOT 只省 23 MB 工作集 |
| dev 所以内存高，生产会好 | dev 176.5 vs prod 176.2 MB，差 0.3 MB |
| 换 Tauri 能降内存 | WebView2 就是 Chromium，占整树 **72%**。壳只省 55 vs 162 MB，省不掉渲染层 |
| `totalJSHeapSize` 涨了 = 泄漏 | 是 V8 **扩容**，GC 后会还（78 → 128 → 63） |
| 看任务管理器判泄漏 | 必须强制 GC 后看是否回落。私有仓自己一开始也误判成泄漏 |

另有一条**口径**要记：`payload.Length`（字符数）≠ 字节数。`.NET string` 是 UTF-16，每字符 2 字节，两个口径差整一倍 —— 私有仓就因为混用把「冗余拷贝有多严重」整体夸大了 100%。
