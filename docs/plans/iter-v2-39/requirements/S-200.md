## 一、现象（**已实测复现**，非推断）

| # | 调用 | 实际返回 |
|---|---|---|
| 1 | `Grep(pattern="package.json", path="D:\claw\wishful-claw\package.json")` | `Directory not found: D:\claw\wishful-claw\package.json` |
| 2 | `Glob(pattern="*.json", path="D:\claw\wishful-claw\package.json")` | `Directory not found: D:\claw\wishful-claw\package.json` |
| 3 | `LS(path="D:\claw\wishful-claw\package.json")` | `Directory not found: D:\claw\wishful-claw\package.json` |
| 4 | `Grep(pattern="\"version\"", path="D:\claw\wishful-claw\node_modules\@antfu", file_pattern="package.json")` | ✅ 正常：`install-pkg/package.json:4:   "version": "1.1.0",` —— **反证 `node_modules` 不是原因**（§2.1） |
| 5 | `Glob(pattern="package.json", path="D:\claw\wishful-claw\node_modules\@antfu")` | `No files found matching the pattern.`（而同目录下 `install-pkg/package.json` **确实存在**；改用 `Glob(pattern="**/package.json", path=<同目录>)` 则正常返回 `install-pkg\package.json`）—— **这是文档化的 pattern 语义，不是缺陷**，见 §5.1 |

> **登记过程订正（2026-10-14，动手前自查）**：本表初版把「`Glob` 传**文件**路径」记成返回 `No files found`。**那是我转录时写错了调用** —— 当时实际传的是**目录** `node_modules\@antfu`。已补测真实调用即现第 2 行：与 `Grep` / `LS` **同款** `Directory not found`。**教训（与 S-199 同源）**：登记表里每一行都要能对上一条**真实发生过的调用**，转录时别把参数凭印象改掉。

**伤害不在「搜不到」，在「不再试」**：`Directory not found` 把「这是文件」错报成「这路径不存在」⇒ 读到这句话的 agent 会（正确地）认为**自己路径写错了**，于是换路径重试或**直接放弃**该次搜索。这正是长期记忆里那条坑的由来，也是「同一处反复试错、浪费轮次」的来源。`FileTools` 的 `Read` 明明能读文件，`Grep` 却说「目录不存在」，两条工具链对同一个路径给出相反结论。

## 二、根因

`src/runtime/WishfulClaw.Agent/Tools/ToolHelpers.cs:82` 的 `ResolveSearchPath` 只做三件事：**默认值（空/`.` ⇒ 工作目录）+ 相对路径挂工作目录 + 沙箱边界**。它**不判别目标是文件还是目录**（函数名与注释都只承诺「解析搜索根」）。

三个消费者于是各自做同一句判断：

| 工具 | 位置 | 代码 |
|---|---|---|
| `Grep` | `SearchTools/GrepTool.cs:42-46` | `if (!Directory.Exists(root)) return new ToolResult($"Directory not found: {root}", true);` |
| `Glob` | `SearchTools/GlobTool.cs:79-85` | 同上（逐字相同的文案） |
| `LS` | `FileTools/FileListTool.cs:77-84` | 同上（`public string Name => "LS"`） |

`Directory.Exists(<真实存在的文件>)` 返回 `false` ⇒ 落进 err 分支。三个工具**共用一句不成立的文案**：路径存在，只是不是目录。

### 2.1 顺带订正一条**长期误记**（`node_modules` 不是问题）

长期记忆里把两件事记成了一件事：「`Grep` 对**具体文件**报 `Directory not found`」+「`Grep` 查 `node_modules/**` 不覆盖」。**后者不成立**，实测 #2 已证：

- `SearchFilter.DefaultExcludedDirs`（`SearchTools/SearchFilter.cs:20-29`）确实含 `node_modules`，但 `IsExcluded`（`:64-98`）比较的是**相对 `root` 的路径段**，且**跳过路径最后一段文件名**（`:78-82`）；
- ⇒ 当 `path` **直接指向某个包目录**（`node_modules/@antfu`）时，相对路径里**根本没有 `node_modules` 这一段** ⇒ **不排除、正常搜到**；
- ⇒ 当初那个现象的真因是**同一个「`path` 传了文件」**：agent 查依赖源码时，自然会把**具体那个源码文件**当 `path` 传进来（`node_modules/foo/index.js`），于是撞上 §二 的错误分支。

**「默认不搜 `node_modules`」是有意设计**（`:20-29` 的注释与 S-88 同源），**本条不动它**。

## 三、修法

**总原则：不动 `ResolveSearchPath`。** 它是共用解析函数（`Grep` / `Glob` / `LS` 之外的调用方也在用），把「文件 / 目录」语义塞进去会把**沙箱边界**与**目标类型**耦在一起。判别放在**各自消费者**里。

`File.Exists(<目录>)` 与 `Directory.Exists(<文件>)` 都返回 `false` ⇒ 判别是干净的二分：

| `Directory.Exists(root)` | `File.Exists(root)` | 语义 | 三工具应做的 |
|---|---|---|---|
| ✅ | ✗ | 目录 | **现行行为，一字不变** |
| ✗ | ✅ | 文件 | `Grep` 走**单文件模式**；`Glob` / `LS` 报「是文件，不是目录」 |
| ✗ | ✗ | 真不存在 | 报「路径不存在」（去掉误导的 `Directory` 字样） |

### 3.1 `Grep` —— 支持单文件（**本条的主要价值**）

`grep pattern file` 是标准动作，模型也习惯这么用。

- 判定为文件时：**只搜这一个文件**（绕过 `EnumerateSearchableFiles` 的目录枚举）；
- **展示基准取父目录**：`Path.GetRelativePath(root, root)` 会得到 `"."`（自相对），所以基准要用 `Path.GetDirectoryName(root)` ⇒ 输出形如 `package.json:12: …`（单文件场景下可读且够用）；
- **单文件模式下忽略 `file_pattern`**：调用方已经指名了文件，再拿 `*.ts` 去卡它是反直觉的（模型极可能带着一个陈旧的 `file_pattern` 进来 ⇒ 变成「明明有却报 No matches found」，二次伤害）。**该口径要写进工具 `Description`**，不靠猜。
- **二进制扩展名**：单文件模式下若扩展名落在既有的二进制清单里（`.png` / `.exe` …），返回**明确文案**而不是把二进制当文本读出来。实现上抽一个 `IsBinaryExtension(file)` 静态方法给两处共用（`GrepTool.cs:209-213` 现有清单即数据源）。

### 3.2 `Glob` —— **不加单文件模式**，只修文案

**决定**：`Glob` 判定为文件时报准确错误，**不**把它当单文件搜。三条理由：

1. **不发明语义** —— `Glob` 得拿到 pattern 才能干活，而 `MatchesGlob`（`GlobTool.cs:217`）匹配的是**相对 root 的路径**。把一个**目录树 pattern**（`**/*.json` / `src/**/*.tsx`）套到**单个文件**上，规则只能现编（只取 basename？还是也试全路径？）—— 编出来就是一个新的、没人验证过的语义。
2. **有现成替代** —— 调用方既然已经指名了文件，`Read` 能直接读、`Grep` 能直接搜；`Glob` 的职责是**在目录里找文件**。
3. **与 Unix 一致** —— `grep pattern file` 成立（`grep` 接受文件），而 glob 本质是**路径展开**、天生以目录为根。`Grep` 收文件、`Glob` / `LS` 不收，是**自然的不对称**，不是缺陷。

报错文案：

```
Not a directory: {root} is a file. Glob matches files under a directory — pass the directory, or use Read / Grep for a single file.
```

> 若日后要 `Glob` 也吃单文件，**另开一条** —— 前置条件是把「树 pattern 如何匹配单文件」定死。

### 3.3 `LS` —— **不加单文件模式**，只修文案

「列目录」就该要目录。文案：

```
Not a directory: {root} is a file. LS lists directory contents — pass a directory, or use Read / Grep for a single file.
```

### 3.4 三处共用的「真不存在」文案

现文案是 `Directory not found: {root}` —— **「Directory」这个词本身就在误导**（读的人会以为结论是「这路径不存在」）。三处统一改为：

```
Path not found: {root}
```

（措辞与既有的 `File not found: {path}`（`FileReadTool.cs:94` / `FileEditTool.cs:50`）同族，便于 grep 与日志聚合；`GrepTool` 的 `IsError` 语义不变。）

> **订正（2026-10-14，审查 ⚠️-3）**：本句初稿写的是「保留这个**已经在别处用过**的措辞」—— **该依据不成立**：`git grep "Path not found" ce182e52~1` 在父提交**零命中**。措辞本身没问题，但别按原句去「对齐既有措辞」。

## 四、验收判据

1. `Grep` 传**真实文件** ⇒ 返回该文件内的匹配，行前缀是**文件名**（不是 `."` / 空）。
2. `Grep` 传**不存在**的路径 ⇒ 文案说「路径不存在」，**不再出现 `Directory not found`**。
3. `Grep` 传真实文件 + **不匹配**的 `file_pattern` ⇒ **仍返回匹配**（单文件模式忽略 pattern）。
4. `Glob` 传**真实文件** ⇒ 报「是文件，不是目录」，**不再出现 `Directory not found`**。
5. `LS` 传真实文件 ⇒ 报「是文件，不是目录」，**不再说 not found**。
6. **回归护栏**：三个工具传**目录**的行为**一字不变**（含 `Grep` 的 `file_pattern` 过滤、`ShouldReportPatternRejected` 提示、`Glob` 的 `**/` 语义、`LS` 的条目上限）。
7. **回归护栏**：`Grep` 传 `path="node_modules"`（或其下包目录）**仍能搜到**（§2.1 的实测 #2 固化成断言）。
8. 门禁四绿：`npm run typecheck` 0 错 / `npm test` 不降 / `dotnet build src/runtime/WishfulClaw.sln` 0 警告 0 错误 / 官网 `npm run build` 0 错。

## 五、非目标

1. **不改 `SearchFilter` 的默认排除集合**（`node_modules` / `dist` / `obj` 默认不搜是**有意设计**）。
2. **不改 `ResolveSearchPath` / `EnsureInsideSandbox` / 沙箱判定**。
3. **不改 `Glob` 的 pattern 匹配语义**。见 §5.1。
4. **不新增工具、不改 TS 侧** —— 整条改动都在 C# 内置工具层。

### 5.1 登记时顺带坐实、但**不属于本条**的两处（防将来误当 bug）

- **`Glob(pattern="package.json", path=<某目录>)` 只匹配根层** ⇒ 实测 #5 返回 `No files found matching the pattern.`，而该目录下 `install-pkg/package.json` 确实存在。**这是文档化行为**：`GlobTool` 的 schema 示例全是 `**/*.cs` / `src/**/*.tsx` 这种带 `**/` 的形态，裸 `package.json` 只匹配根层。**不是缺陷**，故不修；若要改属**另一条需求**。
- **`FileListTool` / `GlobTool` 的报错分支与 `Grep` 逐字重复**（`Directory not found` 三处同源拷贝）⇒ 本条的文案改动**顺手把三处对齐**，但不做「错误文案统一化」的更大重构（那属于另一件事）。

## 六、与 S-195 的关系（**别照抄它的结论**）

S-195 / S-199 那一路是**渲染端**（卡片把成功误判为失败、空壳函数挡死卡片）。本条是**工具层**（C# 内置工具对路径的判别）。

两者只有一点相似：**都是「一句不成立的判断」造成的误导**。**S-195「改后行为变化仅限摘要文案」的结论对本条完全不适用** —— 本条的 §3.1 / §3.2 是**实打实的功能新增**（单文件目标），不是文案订正。
