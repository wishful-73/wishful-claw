## 一、现象（老大 09:52 订正后的口径）

**历史会话重启（软件重启）后，首次发送消息，后端触发压缩。**

- UI 显示上下文只用了 **25K 左右**；
- 上限 **180K**（200K − 20K，`effectiveWindow`）；
- **前端逻辑完全没有问题**——25K 对 180K，显示正确；
- **问题在后端**：重启后首次发送，后端触发**加载**，加载的数据量不对（≈144K，即**整个会话的原始历史**），而不是压缩快照后的活跃上下文（25K）。

> ⚠️ 初版勘测（08:42~09:22）把定性放在「后端分母按 200K 兜底、前端按模型窗口」（S-108 取值链）—— **该定性被老大 09:52 口径推翻**：前端 25K / 上限 180K 本身自洽，**分子（后端加载的上下文内容）才是问题**。144083 ≈ 全历史体量，不是「同一份上下文的两套分母」。

## 三、勘测结论（2026-09-23 09:54，代码 + DB 实证）

**老大推测的「加载了全历史」不成立——restore 确实走了快照；真凶是 token 估算虚高。**

- 08:27 那轮会话 = `YUWPQgpeb7rzuWNGusOiZ`（621 消息，rev 55）。
- **快照有效且被 restore 使用**：`48928cfe`（9/23 08:15 auto 压缩产物，`created_at=1790125305527`），wire 150 条 / 128,260 字符 ≈ **36.6K tokens**；快照后增量仅 2 条 / 568 字符 ⇒ restore 内容 ≈ **37K**。
- 但 08:27:10 首条 DIAG `inputTokens=144083` —— **比 restore 实际内容虚高 ~10.7 万 token**。
- 08:27:53 第二条 DIAG `inputTokens=23804` —— **压缩真的执行了**，把 150 条 wire 又折了一遍（`new_count` 再降），产物 23.8K ≈ UI 的 25K；此后正常增长。

**⇒ 定性：restore 后首条请求的 token 估算虚高（144083 vs 实际 ≈37K），虚报值撞上触发线 144000，触发了一次本不该发生的压缩**（把快照产物再折一遍）。不是「分母 200K 兜底」（S-108），也不是「加载全历史」。

**嫌疑代码**：`AgentLoop.cs:96-102` —— restore 后 `MarkCompactionWatermark`，注释自认「the compression gate is driven by the seeded token estimate (known behavior, harmless)」——**「seeded token estimate」就是虚高来源**，且代码注释已把该行为标记为 known，但「harmless」的判断在 144083 > 144000 这个实例上不成立（它真触发了压缩）。

### 根因定案（09:58，DB 实证闭环）

`FindRecentContextUsage`（`ConversationCodec.cs:139`）从 wire 倒序找最近一条 `usage.contextTokens>0` 的消息当 `lastInputTokens`（`AgentLoop.cs:263`）。压缩快照的 wire 保留了**压缩前**的 assistant 消息，其 `usage.contextTokens` 是当时的过期水位：

- DB 实证：快照 `48928cfe` wire index 148/150（倒数第 3 条）assistant `contextTokens=145306`（08:15 压缩前的真实水位），快照内 8 条带 usage 的消息 max=last=145306。
- restore 后 wire = 快照 150 条 + 新消息 ⇒ `FindRecentContextUsage` 找到 145306 ⇒ `lastInputTokens=145306`（**过期值；实际上下文仅 ≈37K**）。
- 新消息使 `wireConversation.Count(152) > CompactionWatermark(150)` ⇒ 压缩门放行 ⇒ `145306 ≥ 144000` ⇒ **触发本不该发生的压缩**（`AgentLoop.cs:290-292`）。
- 压缩把 150 条快照 wire 又折一遍 ⇒ 23.8K = UI 的 25K。
- 日志 144083 vs DB 145306 差 1223：量级吻合，微小差异来源未追（疑 restore 对 wire 的轻微处理），不影响定性。

**一句话根因：压缩快照保留了压缩前的 `usage.contextTokens`，重启 restore 后该过期水位被 `FindRecentContextUsage` 当成当前输入量，虚报撞线触发二次压缩。**

### 修复候选（讨论态，未拍板）

**老大 10:16 定见：`FindRecentContextUsage` 机制本身是对的——正常会话里 wire 末条 assistant 的 `usage.contextTokens` 就是当前累计上下文，可信。问题不在 restore，在压缩破坏了不变量。**

**不变量**：wire 末条 usage = 当前上下文水位。压缩把 wire 折小，但末条 usage 没刷新（仍是折叠前的 145306）——数字描述折叠前的内容，却挂在折叠后的 wire 里。restore 原样恢复，捞到错值。

### 定案（老大 10:28 / 10:30 订正）

**首次加载 = 最新快照 wire + 快照提交后的增量消息。两部分分开对待：**

- **快照 wire 里带进来的那批（老消息）**：usage 是**压缩前**冻结的，指标已过期 ⇒ **剥掉**。
- **增量消息**：usage 是快照**之后**真实跑出来的，描述的就是「快照内容 + 增量」这个当前上下文 ⇒ **保留**，分子取它是**对的**。
- 08:27 那次**增量 0 条** ⇒ 只能从快照里捞到压缩前的 144083。剥掉老消息 usage 后：增量 0 条 ⇒ 没有分子，不触发；有增量 ⇒ 分子即真实值。
- **老大 10:44 口径（增量 0 条这一点闭合）**：「基本不会出现压缩后就关了；压缩后不是置零了么，这跟触发过压缩有区别么。有增量 增量上有真实数据，没增量 不是置零了么」⇒ **0 增量 = 与「刚压缩完」同一状态**（都是等本轮真实 usage），不需要给快照额外存「压缩后水位」。**不新增字段、不动压缩侧。**

**修正早期错误表述**：这不是压缩、也不是「置 0 / 不播种」——加载侧只需把**过期的那部分 usage 排除掉**，新的照用。

**改法**：`SessionRestoreTools.RestoreFromDb` 快照分支 —— 载入 `snapshot.WireConversation` 后剥掉这批消息的 `usage`，增量消息原样保留。两条恢复入口（`agent/restore-session` endpoint + AgentLoop 懒加载）都走这里，改一处全覆盖。

### 探查验证（2026-09-23 10:40，拿今天真实数据跑 `ShouldCompress` 同一条判据）

判据：`trigger = min(180000×0.8, 180000−13000) = 144000`（与日志一致）。

| 场景 | 现状分子 | 修正后分子 | 判定 |
| --- | --- | --- | --- |
| 08:27 重启后首轮（`a36ffff1` + 增量 0 条） | wire[idx 132] = **144083** | **无**（快照消息 usage 已剥，增量没有） | 现状 WOULD COMPRESS → **修正后不触发 ✓** |
| 现在再重启（`48928cfe` + 增量 2 条） | wire[idx 151] = 144137 | 增量[idx 1] = **144137** | 修正后仍压缩——真实上下文确实 144K ✓ 不误伤 |

三条确认：① 08:27 那条误触发精准消除（现状分子落在快照内部 idx 132，剥掉后取不到）；② 增量行的 usage 确实会进 wire（第二场景 idx 151 即增量行），剥掉快照那份后 `FindRecentContextUsage` 天然只命中增量，**无需额外逻辑**；③ 真实超窗仍有 provider 报错触发的 errorDriven 压缩兜底。

- 影响面已确认：全仓只有 `ConversationCodec.FindRecentContextUsage`（分子）读 wire 里的 usage；UI 读 DB `messages.usage` 列，provider payload 由 `AgentRuntimeChatMessage` 重建（不含 usage）⇒ 剥掉不影响这两处。
- 附带好处：压缩持久化的快照 wire 以后也不再带旧 usage，从源头断掉复发。
- ~~丙「置 0」/ 丁「自己估」/ 戊「压缩时刷新末条 usage」~~ 全部作废。~~「跟自动压缩后续处理看齐」~~ 亦作废：首次加载不是压缩，两者不该套同一套。

## 四、08:27 实测：那次到底加载了什么（2026-09-23 10:30，DB + 日志实证）

**会话 = `YUWPQgpeb7rzuWNGusOiZ`**（08:27:10 起的第一条消息就是它；projectId `WlEXeF9v-1t3TSH9vKXj4`）。

- 08:26:34 应用重启（日志：renderer 重新初始化）→ 08:27:10 首条 run → DIAG `144083`。
- 当时该会话唯一有效快照 = **`a36ffff1`（09-22 19:49:25）**：orig 243 → new 134，wire 134 条 / 124,599 字符。
- **快照提交时间（19:49:25）→ 08:27:10 的增量 = 0 条消息** —— 会话昨晚 19:49 之后闲置，恢复内容就是这个快照 wire 本身。
- 恢复内容的体量标定：同会话快照 `48928cfe`（150 条 / 128,411 字符）在 09:01:45 压缩后，下一轮真实 DIAG = **36,191**（130,068 字符的 `a8e54a60` 对应 34,687）⇒ 同类 wire 约 **3.6 字符/token** ⇒ `a36ffff1` 恢复内容 ≈ **35K token**（与前端 25K 同档）。

**wire 的构成（这就是「加载之前的」的实体）**：

- 消息跨度 **09-19 16:15 → 09-22 19:49**，共 3 天。
- 组成：pinned prefix + **一整批小 user turn（idx 0~123，跨 3 天全在）** + **3 条 `<compaction-summary>`**（idx 81 / 95 / 125，即历史压缩摘要 + 当前摘要）+ 最近 tail。
- 单条最大：idx 119 = **88,666 字符**（占整个 wire 的 71%）。
- ⇒ 压缩后的 wire 并没有变「薄」：老摘要和老 user turn 一直留在 wire 里（`IsSmallUserTurn` 判定下它们算幸存者）。

**分子来源（数值完全相等）**：wire 里最后一条带 usage 的消息 = **idx 132（09-22 19:48:21）assistant，`contextTokens=144083`**，与 DIAG 数字**逐位相同**——它是 09-22 那次压缩**之前**的水位，冻结在消息上被带进了这次加载。

**快照的构成（老大 10:36 / 10:39 口径）**：快照就是**新压缩**的产物，没有「旧压缩」这一说；它按设计保留一部分**压缩前的消息**（小 user turn + 最近的 tail + 当轮新摘要）。首次加载加载的就是这个快照 —— 里面这些**压缩前的旧消息带着压缩前的 usage**（idx 132 = 144083），这才是分子取错的来源。压缩侧（含摘要留存规则）已改过，本案不动，只作参考。

⇒ 08:27 的压缩由**加载进来的历史消息自带的旧 usage**（144083）触发，而这次加载的真实内容只有 ≈35K。**不是加载了「全历史原始消息」，而是加载了「带旧 usage 的快照 wire」**——老大「加载之前的出了问题」的方向成立，问题载体就是快照 wire 里那条冻结的 usage。
