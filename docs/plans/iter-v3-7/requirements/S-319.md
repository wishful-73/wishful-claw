> 登记：2026-11-05 11:10（老大原话见 §一）

截图现场（生产实例，`wishful-work` 项目下会话）：

```
BuildSendableImageUrl 内部已经判断过 shape，所以这两处的前置检查变成多余。简化后还能少一次遍历。
```

三个工具之间**没有任何可见内容**，却各自成块。

## 二、根因（数据 + 代码事实）

### 2.1 分段判据只看类型，不看内容

`src/renderer/src/components/chat/execution-outline.ts:207-211`

```ts
if (!block || (block.type !== 'tool_use' && block.type !== 'tool_result')) {
  // 「下一段输出或思考来了」—— 唯一真正的封口信号（S-315）
  closePendingRun(true)
  continue
}
```

任何非工具块都会被当成「流程往前走了」，把当前工具 run 封口。这对**有内容的** text / thinking 是对的，对**空块**是错的 —— 空块既不渲染、也不构成语义边界。

### 2.2 空块是真实存在的，而且占比很高

模型在「这一轮不需要思考、直接调工具」时，`reasoning_content` 不是空串，而是**纯空格**。

生产库 `.wishful-claw\index.db` 实测（`node:sqlite` 只读打开，脚本 `.wishful-claw/notes/probe-blank-thinking.mjs`）：

| 范围 | thinking 总数 | trim 后为空 | 占比 |
|---|---|---|---|
| 截图那条消息 `wc-agent-1793845174941-f0xma7` | 272 | **181** | **66.5%** |
| 最近 200 条 assistant 消息 | 4073 | **1106** | **27.2%** |
| 其中 `text` 块 | 2699 | 0 | 0% |

空白 thinking 的原始内容只有三种形态：`" "` ×461、`"   "` ×3、`"    "` ×1 —— **全部是空格，没有一个空串**。

### 2.4 渲染层第二道闸也放行

`src/renderer/src/lib/agent/session-runtime-router.ts:199-200`

```ts

```

`stripThinkTagMarkers`（`think-tags.ts:12-14`）只去 `thinking` 标签，**不 trim**。

### 2.5 唯一判对的是显示层，所以用户完全看不到

`src/renderer/src/components/chat/ThinkingBlock.tsx:67,111`

```ts

```

`chat-message-blocks.ts:32` 的 `if (segType === 'thinking' && seg.thinking)` 同样被空格骗过（历史加载路径）。

**结论：一条看不见的空块，把工具链切开了。**

## 三、裁定过程（老大三次纠正，记录在此防跑偏）

### 3.1 「思考应该打断工具链」

老大定：「思考是应该打断工具链的。」

⇒ 否决「thinking 一律不切段」与「把 thinking 收进 run 里」两种方案。**分段判据本身不动**，只让真空块（trim 后为空）不参与判定。有明文的思考照旧封口。

### 3.2 「空思考不入库」这条路不成立

老大先问「空思考，不入库，其它操作照旧可以么」，随即自己发现矛盾：「既然有些需要回传，那不入库好像就不太行了。」

关键是两种「空思考」长得像、性质完全不同：

| | 空白 thinking | 加密思考 |
|---|---|---|
| 产生 | `appendRuntimeThinkingDelta` | `setRuntimeThinkingEncryptedContent`（`session-runtime-router.ts:305-311`） |
| 数据 | `{ thinking: ' ' }` | `{ thinking: '', encryptedContent: '…', encryptedContentProvider: 'anthropic' }` |
| 回传 | 无价值 | **必须回传**，否则推理连续性校验失败 |
| 入库 | 无所谓 | **必须入** |

按「thinking 内容为空」过滤入库，必然误杀加密思考。

⇒ **入库逻辑一个字不改。** 空白 thinking 的 block 压根没有 `encryptedContent`，在**源头**掐掉后它从未存在过，谈不上入库；加密思考走另一条路径，源头过滤碰不到它。

### 3.3 渲染层丢 `encryptedContent` 不算缺陷

助手曾报「`chat-message-blocks.ts:33` 从 segments 重建 block 时丢了 `encryptedContent`」。老大纠正：「chat-message-blocks.ts 显示的时候无所谓吧，我们消息是在后端直接回传的。」

实读确认成立：回传由 C# worker 直接从库取（`DbMessageParts.MergePartsIntoMeta` 把 parts 并回 meta，供后端重建上下文），渲染层只负责显示。**该条作废，不登记。**

⇒ 过滤判据反而更干净：**用户看不见的思考，就不该建块，也不该打断工具链。**

## 四、修法（三处，改动面极小）

### 4.1 源头：四处判空串 → 判空白

```csharp
// OpenAIChatProvider.cs:245
// OpenAIChatProvider.Sse.cs:175
- if (!string.IsNullOrEmpty(reasoning))
+ if (!string.IsNullOrWhiteSpace(reasoning))

// AnthropicMessagesEventParser.cs:167
- if (thinking.Length > 0)
+ if (!string.IsNullOrWhiteSpace(thinking))

// OpenAIResponsesEventParser.cs:61
- is { Length: > 0 } thinking
+ is { } thinking && !string.IsNullOrWhiteSpace(thinking)
```

影响面确认：`OpenAIChatProvider.cs:201` 是 `ReasoningContent: reasoningContent.Length > 0 ? … : null`，空白不累积 ⇒ 仍然是 `null`。DeepSeek 的 `reasoning_content` 回传不变。

### 4.2 渲染层第二道闸：trim 后再判

```ts
// session-runtime-router.ts:199-200
- if (!cleanedThinking) return
+ if (!cleanedThinking.trim()) return
```

### 4.3 读取侧：只认有明文的思考

```ts
// chat-message-blocks.ts:32（segments 分支）
- if (segType === 'thinking' && seg.thinking) {
+ if (segType === 'thinking' && String(seg.thinking ?? '').trim()) {

// chat-message-blocks.ts:62（老格式 fallback 分支）
- if (thinking) {
+ const legacyThinking = thinking ?? ''
+ if (legacyThinking.trim()) {
+   blocks.push({ type: 'thinking', thinking: legacyThinking })
  }
```

fallback 分支用局部变量而不是 `String(thinking ?? '').trim()` 内联判：判据改过之后 TS 不再收窄 `string | undefined`，而落库内容要保留**原文**（不 trim），所以拆成「判用 trim、存用原值」。

这条负责让**历史库里已有的 1106 个空白 thinking** 也不再切段。

### 4.4 明确不动

- `execution-outline.ts` 的分段判据（有内容的思考 / 输出照旧封口）
- 入库链路（`DbMessageParts.WriteParts` / `MergePartsIntoMeta`）
- 加密思考路径（`setRuntimeThinkingEncryptedContent`，`thinking: ''` 但带 `encryptedContent`）
- 加密思考的渲染层字段处理（不影响回传，见 §3.3）

## 五、验收

1. **新会话**：让 agent 连续调 ≥3 个工具且中间不输出正文 ⇒ 三个工具折叠成 **1 个**折叠块。
2. **新会话**：工具之间出现**真实思考**（有明文）⇒ 照旧切成两段（不能被本条改成一整块）。
3. **历史会话**：打开截图那条消息（`gyWRbcReJwsK0Spa3W3ff` / `wc-agent-1793845174941-f0xma7`）⇒ 那三块工具合并成 1 块。
4. **回归**：有明文的思考仍正常显示「已深度思考」，内容完整。
5. **回归**：Anthropic / OpenAI-Responses 的加密思考不显示、不切段、不影响回传（换该服务商通信正常）。

### 8.2 回归测试（新增，钉在渲染层）

`tests/tool-run-folding/program.ts` 新增「判据 8：S-319 空白思考不打断工具链」三条：

1. **现场复刻**：`text → tool_use → thinking(' ') → tool_use → thinking('   ') → tool_use → thinking(' ') → text`
   ⇒ 0 个 thinking 块、`runs.length === 1`、`totalItemCount === 3`（现场那三块合成一块）。
2. **判据没被改松**：两个工具之间夹**有明文**的思考 ⇒ 仍然 `runs.length === 2`。
3. **老格式 fallback**：`thinking: '   '` ⇒ 不建块；`thinking: '想一下。'` ⇒ 建 1 块。

**有效性实测**：临时把 `chat-message-blocks.ts` 的判据退回 `seg.thinking`，该套件立刻失败，报 `actual: 3, expected: 0` —— 精确复现现场的 3 个空白思考块；恢复修复后通过。说明这三条能真正抓住本缺陷，不是摆设。
