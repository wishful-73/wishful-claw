# S-152 微信渠道接入「正在输入」状态

- **登记日期**：2026-09-25
- **登记来源**：老大 11:45–11:52 讨论。起于「微信长时间收不到推送」的排查，收敛到本需求。
  原话（11:51）：「我希望的是微信渠道的时候 我们本身是流式输出，**如果开始接受文本流的时候就发送正在输出，文本流结束发送到微信的时候这个正在输入就结束**」；
  随后（11:52）：「消失就消失呗，不想搞太复杂了，**登记需求把 按照你刚刚说的方案**」。
- **分支**：`dev/v2-iter-36`
- **状态**：✅ 已实施（`3d9e55e3`，2026-09-26）

---

## 一、诉求

微信渠道的机器人目前**没有任何「正在输入」提示**：用户发完消息，只能干等到回复到达，中间没有任何反馈。

要的是：**机器人开始生成回复 → 微信里显示「正在输入」；回复真正发到微信 → 提示结束。**

---

## 二、现状勘测（实测，非推测）

### 2.1 渠道层完全没有 typing 能力位

全仓 grep `typing` / `Typing`，`src/main/channels/` 下**零命中**。具体：

- `MessagingChannelService`（`channel-types.ts:129`）**没有** typing 相关成员；
- `BasePluginService`（`base-plugin-service.ts:23`）的抽象方法只有 `sendMessage` / `replyMessage` /
  `getGroupMessages` / `listGroups` —— **没有** typing；
- `WeixinApi`（`weixin-api.ts`）**没有** `getconfig` / `sendtyping` 端点；
- 八个渠道服务（feishu / dingtalk / qq / wecom / telegram / discord / whatsapp / weixin）**无一实现**。

### 2.2 微信不走渠道流式

`plugin:stream:start|update|append|finish` 这套 IPC **已经存在**
（`ipc/channel-handlers/channel-plugin-stream-handlers.ts`），但**只有飞书和钉钉实现了 `supportsStreaming`**：

- `providers/dingtalk/dingtalk-service.ts:330`（需配 `cardTemplateId`）
- `providers/feishu/feishu-service.ts:70`

⇒ `auto-reply.ts:238` 的 `supportsStreaming` 对微信恒为 `false`，renderer 不走流式，
`plugin:stream:*` **对微信永远不会触发**。

**这是关键约束**：老大原话是「按流式边界开关」，但微信侧没有这条边界。要用它，
就得给微信实现 `supportsStreaming` —— 那会把**发送路径本身**改成 start/update/finish 反复改同一条消息，
而 iLink 支不支持消息更新**未经验证**。为一个 typing 冒这个风险不值得。

## 三、协议（来源：KodaClaw，仅作协议字典）

> 老大 11:47 口径：「kodaclaw**只是有这个输入中状态，其它不用抄**，
> kodaclaw 微信主动发消息有时候都回复不了，**bug 更多**」
> ⇒ 只取它的协议知识，实现方式一概不参考。

KodaClaw 有生产可用的实现，文档 `products/KodaClaw/docs/WECHAT_INTEGRATION.md` §3.4 / §3.5 / §11.8。

**typing 需要两步，不能直接调 sendtyping**（§11.8 原话）：

```
POST /ilink/bot/getconfig
Body: { ilink_user_id, context_token }
Resp: { ret, typing_ticket }

POST /ilink/bot/sendtyping
Body: { ilink_user_id, typing_ticket, status }     // 1 = 开始输入，2 = 取消
```

参考实现：

- `HttpWeChatApiClient.cs:151-169`（getconfig）/ `:171-185`（sendtyping）
- `WeChatConnector.cs:534-591`（组合流程）

**两点顺带核实**：

- `Content-Type` 必须不带 charset，否则 iLink 返回 **412**（`HttpWeChatApiClient.cs:142` 注释）。
  我们的 `buildHeaders`（`weixin-http.ts:20-40`）写死 `'application/json'`，**已符合**。
- **不抄 Reasonix**：它的 `sendTyping`（`internal/bot/weixin/weixin.go:623-665`）body 是
  `{ base_info, ilink_user_id, status, context_token }` —— **没有 `typing_ticket`**，
  与上面「不能直接调 sendtyping」矛盾，大概率无效实现。

## 四、改法（最小版）

### 4.1 边界改用主进程内现成的两个点

微信没有流式边界，但有另外两个点，**覆盖的区间与诉求完全一致**，且都在现有代码的必经之路上：

| 时刻 | 位置 | 动作 |
|---|---|---|
| agent 开跑（回复开始生成） | `channels/auto-reply.ts:264` 发出 `plugin:session-task` | `sendtyping(status=1)` |
| 回复发到微信 | `ipc/channel-handlers/channel-plugin-handlers.ts:118-121` 的 `SendChannelMessage` 成功后 | `sendtyping(status=2)` |

两点**均在主进程内，零 renderer 改动，不碰发送路径**。

### 4.2 改动清单（3 处）

1. **`weixin-api.ts`**：加 `getConfig` + `sendTyping` 两个方法（照 `getUpdates` 的 `postJson` 写法）。
2. **`weixin-service.ts`**：加 `startTyping(chatId)` / `stopTyping(chatId)`
   —— 内部先 `getconfig` 拿 `typing_ticket`，再发 `sendtyping`。
3. **两个调用点**各加一行（`auto-reply.ts:264` 前后 / `SendChannelMessage` 成功分支）。

### 4.3 硬约束

1. **失败一律降级**：`getconfig` 拿不到 ticket、或 `sendtyping` 报错 ⇒ 静默吞掉，
   **绝不阻断消息处理**（KodaClaw 同款思路，`WeChatConnector.cs:541-561`）。
2. **不缓存 `typing_ticket`**：每条消息重新 `getconfig`。token 一变 ticket 大概率失效，
   缓存是自找麻烦（KodaClaw 也不缓存）。

## 五、明确不做（本轮）

| 不做 | 理由 |
|---|---|
| **续发**（`status=1` 每 N 秒重打） | 老大 11:52：「消失就消失呗，不想搞太复杂了」⇒ 先打两发看效果 |
| `channel-types.ts` 加通用能力位 | 只有微信用，不暴露成跨渠道接口 |
| renderer 侧任何改动 | 边界全在主进程 |
| 给微信实现 `supportsStreaming` | 会改发送路径，iLink 是否支持消息更新未验证（见 §2.2） |
| 抄 KodaClaw 的续发循环 / 生命周期管理 | 它那套是为「全程显示」服务的，代价是定时器 + Map + 兜底；老大明确要简单 |

## 六、验收

1. 微信发一条消息 ⇒ **机器人开始生成时**，微信头像旁出现「正在输入」。
2. 回复送达 ⇒ 「正在输入」消失。
3. `getconfig` / `sendtyping` 任一步失败 ⇒ **消息照常回复**，用户无感（只是没有 typing）。

---

## 七、未验证点（如实）

1. **`status=1` 的时效多长**，以及**消息发出后它会不会自动消失** —— 代码判断不了，只能实测。
   这直接决定 §五 那个「不做续发」够不够：显示够久就收工；一闪就没则回头加续发。
2. **`getconfig` 这条路径我们从未调过** —— 虽然 KodaClaw 在生产跑着（说明端点可用），
   但**我们的 token / 账号形态**下是否同样可用，要实测确认。

## 九、独立审查结论（code-reviewer subagent，只读，未改任何文件）

**结论：可以安全上线** —— 不破坏、不拖慢任何既有消息收发路径，协议与参考实现逐一对齐。

确认无问题：

- 协议字段 / path / 请求头与 KodaClaw 一字不差（含「`Content-Type` 不带 charset，否则 iLink 返 412」那条坑）。
- 失败降级彻底：`startTyping` / `stopTyping` **永不 reject**，任何失败只 `console.warn`；调用点不 await、不改变返回值。
- 另外 7 个渠道（飞书 / 钉钉 / QQ / 企微 / Telegram / Discord / WhatsApp）**行为逐字节不变**（无同名方法，`?.` 全短路）。
- `errcode ?? ret ?? 0` 且强制要求 ticket 非空 ⇒ **只可能「少发」，不可能「误发」**。

提出待议项（**均未改动**，按纪律攒收尾刀）：

| # | 审查意见 | 裁定 |
|---|---|---|
| 1 | **无续期** —— 只发一次 `status=1`，长任务中指示器可能自己灭；KodaClaw 每 5s 续发 | 老大明确「消失就消失呗，不想搞太复杂了」⇒ **有意为之**，不算缺陷；但印证 §七.1 |
| 2 | **取消 / 异常路径不收尾** —— `stopTyping` 只挂发送成功处，用户取消本次运行指示器会挂住（KodaClaw 放在 `finally`） | **待真机**：会自行超时 ⇒ 短暂残留可接受；一直挂着 ⇒ 要补 |
| 3 | **stop 与 start 不成对** —— 唤醒消息（`isWakeup`）没点亮过也去 stop，多两次请求，且可能掐掉同 chat 并发 run 的指示器 | 潜伏路径（当前无调用方传 `isWakeup: true`）；补守卫很便宜，攒收尾刀 |
| 4 | **多段回复提前熄灭** —— 每个 `message_end` 都 flush 一次，第一段送达即 stop，后续还在跑 | 与 #1 同源，真机看表现 |
| 5 | `as unknown as` 双重断言，建议改为 `channel-types.ts` 的可选能力位 | **不采纳** —— 老大口径是只在微信加、不暴露成跨渠道契约（见 §五） |
| 6 | `void` 掉 promise 有未处理 rejection 的潜在风险 | 当前安全（服务层全包）；换 `.catch(() => {})` 更保险，攒收尾刀 |
| 7 | 图片 / 文件回复路径（不走 `sendChannelMessage`）不收 typing | 影响小（agent 回复基本都带文本） |

6. 用户取消本次运行后，指示器是立刻消失还是要等很久？
