## 一、现象（老大口述）

刚触发自动压缩 → 正在回复 / 输出流时 → 用户中断执行 → 重新发送新内容 → **又触发一次压缩**。

## 二、代码链路（2026-09-29 实读）

### 2.1 自动压缩的触发三条件

`AgentLoop.cs:263` 与 `:290-292`：

```csharp
var lastInputTokens = FindRecentContextUsage(wireConversation);   // ← 分子来源
...
if (lastInputTokens > 0 &&
    sessionConv.CompactionWatermark < wireConversation.Count &&    // ← 水位闸门
    ShouldCompress(lastInputTokens, provider, parameters))
```

- `FindRecentContextUsage`（`ConversationCodec.cs:139-158`）：**从尾部往前找第一条 `usage.contextTokens > 0`** 的消息，取它当分子。
- `ShouldCompress`（`AgentLoop.cs:669-708`）：`inputTokens >= min(ratioThreshold, bufferedThreshold)` 即触发。

### 2.2 压缩产物的构造 —— **旧 usage 原样带过来了**

`ContextCompression.cs` 的 `CompactAsync` 重建 `newWireConversation`，其中**三处直接复制压缩前的 wire 消息**：

| 位置 | 复制什么 | 带 usage？ |
|---|---|---|
| `:175-179` | pinned prefix（head） | ✅ 原样复制 |
| `:187-196` | region survivors | ✅ 原样复制 |
| `:209-214` | **summary（新造）** | ❌ 无 usage |
| `:217-221` | recent tail | ✅ 原样复制 |

⇒ 压缩后的对话里，**除 summary 外全部消息仍携带「压缩前那一刻」的 usage** —— 正是触发压缩的那个高值。

### 2.3 压缩落点

`AgentLoop.ContextCompression.cs:169-172`：

```csharp
sessionConv.Replace(newConversation, newWireConversation);
// S-95 D: the wire just shrank, so reset (not Max) the watermark — otherwise it
// stays parked at the pre-compression high and the gate never reopens.
sessionConv.ResetCompactionWatermark(newWireConversation.Count);
```

⇒ 水位被**重置到压缩后的新 count**（例：20）。**此后任何一条新消息都会让 `watermark < count` 成立。**

### 2.4 与 S-141 的对照

S-141（`788063e2`，2026-09-23）修的是**恢复路径** —— `SessionRestoreTools.cs:182-200`，`RestoreFromDb` 的快照分支逐条 `StripUsage`。提交信息原话：

> 快照 wire 里带的是折叠前那批消息，其 usage 报的是压缩前的 token 水位（实测 144083），而恢复后的上下文只有约 35K。FindRecentContextUsage 拿它当分子 ⇒ 重启后首轮就被误触发压缩。

**同一条病、不同的入口。** 全仓 `StripUsage` **只有 `SessionRestoreTools.cs:199` 一处调用** —— 运行中压缩这条路没做同样的剥离。

## 三、根因（逻辑闭合）

1. run N 触发自动压缩 ⇒ `sessionConv.Replace(...)`（新 wire 里旧 usage 仍在）⇒ `ResetCompactionWatermark(20)`
2. 本 run 内 `lastInputTokens = 0`（`AgentLoop.cs:315`，**内存变量**）⇒ **本 run 不会再压**
3. **用户在「正在回复 / 输出流」时中断** ⇒ 这一轮 provider turn 没走完、**没产出新 usage**（usage 在流末尾才到）⇒ 尾部那条**压缩前的高 usage 留在原地**，没人覆盖它
4. 用户重发新内容 ⇒ **新 run**：
   - `lastInputTokens = FindRecentContextUsage(wireConversation)` ⇒ **又取到那个高值**
   - `CompactionWatermark(20) < wireConversation.Count(21)` ⇒ 成立
   - `ShouldCompress(高值)` ⇒ 真 ⇒ **又压一次**

**为什么平时不暴露**：压缩后紧接着的那轮 provider turn 会把新 usage 追加到尾部（描述压缩后的真实上下文，低值），下一轮读数就正常。**只有「压缩刚完成 + 该轮被中断」这个组合**才让旧 usage 留在尾部 —— 正好是本次场景，也就解释了为什么它难被随手测出来。

## 四、修复方向（草案，待裁定）

| # | 方案 | 说明 |
|---|---|---|
| A | **与 S-141 对齐**：`ContextCompression.CompactAsync` 构造 `newWireConversation` 的三处复制（head / survivors / tail）逐条剥 `usage`；summary 本就无 | 治本，两条入口口径统一 |
| B | 把 `StripUsage` 从 `SessionRestoreTools` 的 private 提到 `ContextCompression`（internal），A 与 S-141 共用一份 | 配合 A，避免两份实现漂移 |
| C | 中断（`aborted`）时，若本轮发生过压缩，剥掉尾部残留 usage | 治标，不推荐 |

**我的倾向是 A + B**：压缩产物的语义就是「这是一段新上下文」，其 usage 理应由**压缩后的第一次 provider turn** 给出；把旧 usage 带进产物本身就不对 —— S-141 已经认定这一点，只是只修了一半。

### 老大裁定（2026-09-30 09:27）

原话：

> 这个是已经成功压缩后，用户中断后续执行，然后重新发言，这种应该能复用之前的压缩快照才对
