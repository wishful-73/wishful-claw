### D-3　飞书 audio 的注释在撒谎：「文件名强制 .opus」实际没做｜P1

**位置**：`src/main/channels/providers/feishu/feishu-outbound-media.ts:71-77`

```ts
// 飞书只认 opus；文件名强制 .opus，否则 uploadFile 的 file_type 与扩展名不一致
const { buffer } = await readBinarySource(media.source, 'audio.opus')
const fileName = media.fileName ?? resolveSourceFileName(media.source, 'audio.opus')
const fileKey = await api.media.uploadFile(buffer, fileName, 'opus')
```

**现象**：注释承诺「强制 .opus」，代码只在**推断不出名字时**用 `audio.opus` 兜底。传 `/tmp/x.mp3` 进来，`fileName` 就是 `x.mp3`，随后 `uploadFile(buf, 'x.mp3', 'opus')` —— 正是注释说要避免的「`file_type` 与扩展名不一致」。

**建议动作**（二选一）：
1. 真做强制：`fileName = path.basename(fileName, path.extname(fileName)) + '.opus'`；
2. 注释改成实话：飞书侧会拒，不做兜底。

**验收**：传 `.mp3` 到飞书 audio 分支，文件名要么变成 `.opus`，要么注释已改。

## 二、本迭代暴露、未收敛的既有问题

### D-6　`readBinarySource` 无上限、无超时、同步读｜P1（与内存线直接相关）

**位置**：`src/main/channels/channel-media-source.ts`

| 行 | 问题 |
|---|---|
| `44` | `await fetch(value)` —— **无 `AbortSignal`、无 timeout**。URL 卡住，渠道服务一直挂着 |
| `49` | `Buffer.from(await response.arrayBuffer())` —— **无 `content-length` 校验、无大小上限**，全量进主进程堆 |
| `59` | `fs.readFileSync(value)` —— **同步读整个文件**，主进程事件循环阻塞 |

**放大效应**：微信侧 `uploadMedia`（`weixin-api.ts`）接着 `encryptOutboundMedia` → `Buffer.concat([cipher.update(buffer), cipher.final()])`（`weixin-crypto.ts:25`），**再复制一份**。一条 N 字节媒体，峰值 2~3N。

**影响**：`ChannelSendFile` 语义上是「任意文件」，模型完全可能塞几百 MB。**这条与「卡炸 / 内存暴涨」是同一方向**，建议单开一条挂到内存线上，不要混在 S-352 里。

**建议动作**：加 `maxBytes`（建议 50 MB，与渠道平台上限对齐）、`AbortSignal.timeout(60_000)`、`fs.promises.readFile` 替同步读。

**验收**：传一个 200 MB 文件，应被拒并给出明确错误，主进程内存不出现尖峰。

### D-7　渠道文件工具零路径校验 + 渠道会话免审批｜既有，风险面被本迭代加宽

**链路**：
- `ToolCallProcessor.Approval.cs:81-84` —— 渠道会话 + `IsChannelFileTool` ⇒ **免审批直接执行**
- `:125-128` —— 本迭代把 `ChannelSendAudio` 加入 `IsChannelFileTool`
- `readBinarySource` 对 `source` **无任何沙箱校验**（全仓 `Sandbox` 相关只剩 `SandboxElevationStore`，管的是 shell 越界申请）

**组合后果**：群里有人说话 → agent 在渠道会话内 → 调 `ChannelSendImage(source: "C:\\Users\\x\\.ssh\\id_rsa")` → 免审批 → 当图片发到群里。

**性质**：免审批是既有设计（渠道弹不出审批框，只能这样），**不是本迭代引入**。但本迭代没有把它记成风险，反而多开了一个入口。

**建议动作**：最低限度在 S-352 单据里写明「渠道出站媒体的 `source` 不做路径边界校验，属已知风险」，别让它默默变成「本来就该这样」。再进一步可复用 `SandboxElevationStore` 的判据做只读校验。

**验收**：S-352 或本台账有明确风险登记；或真机验证 `source` 指向用户目录外时被拒。

## 三、项目级

### D-11　没有 lint｜P2，但是最大的工程缺口

**证据**：`package.json` 里 eslint / prettier / biome **一个都没有**，根目录无任何 lint 配置。

**影响**：这不是「少个工具」，是**一整类缺陷目前无法被机器发现** —— 未使用变量、未使用 import、漏写 `await`、`==` 与 `===`、浮空 promise。本轮 D-1（孤儿文件）、D-10（零调用导出）这种问题，一条 `no-unused-vars` 加一个「导出零引用」检查就能拦住，而现在全靠人肉 grep。

**为什么对本项目尤其重要**：1800+ 提交、约 18 万行 TS + 6.7 万行 C#，**接近 20 个迭代由 agent 自行开发**。人的直觉会累，agent 不会，但 agent 会**一致地犯同一类错**。

**建议动作**：先只上「不改变格式、只报错」的最小集（`no-unused-vars` / `no-floating-promises` / `eqeqeq`），跑一遍看基线数量，作为新迭代的挂账，不追求一次清零。
