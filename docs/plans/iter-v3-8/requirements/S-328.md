## 二、根因（不是「Agent 层偷懒」）—— S-333 ~ S-336 共用

`Db*Tools` 的方法签名是 `WorkerResponse (JsonElement)` —— 它的形状是**端点**（收请求、回 JSON），不是**表访问**（取/存强类型实体）。

实测证据（`DbProjectTools` / `DbSubAgentTools` 的公开方法清一色这个形状）：

```
public static WorkerResponse List(JsonElement parameters)
public static WorkerResponse Get(JsonElement parameters)
public static WorkerResponse ReadByToolUseId(JsonElement parameters)
…
```

**但根因不是「Agent 层拿不到强类型」—— 这个说法不准确，得改。** 强类型**映射**是有的，而且 Agent 层正在用：`Infrastructure/Db/EntityMappers.cs` 里的 `MapProject` / `MapSession`，`AgentRuntimeProjectExecutor` 直接 `db.Query(sql, EntityMappers.MapProject, …)`。

缺的是把两者粘起来的那一层：

| 有什么 | 在哪 | 缺什么 |
|---|---|---|
| 强类型 **Entity**（`ProjectEntity` / `SessionEntity` / `TaskEntity` …） | `Infrastructure/` | — |
| 强类型 **Mapper**（`EntityMappers.MapProject` …） | `Infrastructure/Db/EntityMappers.cs` | — |
| 裸 **连接 / 执行**（`DbClient.GetClient` / `db.Query` / `db.Execute`） | `Infrastructure/Db/DbClient*` | — |
| **表访问方法**（`List<ProjectEntity> ListProjects()` 这种把上面三者组好的） | **不存在** | ← 就是它 |

于是 Agent 层只能自己拼：`db.Query` + 手写 SQL + `EntityMappers.MapX` 三样在调用点现组装。每多一处业务就多一份 SQL 副本，也就多一处能写错的地方。

**同一段代码其实承认过这个方向**：`DbProjectTools.CreateEntity(JsonElement)` 返回 `ProjectEntity` —— 全层唯一一个绕过端点的口子，说明这想法有过，但只做了一个方法就停了。

**真正的病灶：`Infrastructure/Db/` 这一层混了两种职责** —— 表访问 + 端点组装，两类东西写在同一个类里，于是只有「端点」这一个出口对上层开放。这与 **S-326** 的 A2 判断完全一致（33 个 `Db*Tools`、8,204 行占该层 55%），是那次裁定的未尽面。

> 换个说法：**零件全在，就是没接线** —— 跟 S-327 那个结论是同一个味道。这也意味着本族的工作量比「从零建强类型出口」小：不需要新造 Entity、不需要新写 Mapper，只需要把已有的 SQL 原样挪进 Db 层、包成方法。

## 三、修复方向（三步，顺序不能换）—— S-333 ~ S-336 共用

1. **加**：在 `Infrastructure/Db/` 下为对应表抽强类型方法（`TaskRow Create(...)` / `TaskRow? Get(string id)` / `int UpdateStatus(...)` …）。SQL 从 Agent 层那几处**原样搬过来**，一行逻辑不改 —— 这是全族风险最低的部分。
2. **改**：Agent 层改为调强类型方法，`using` 指向 Db 层，删除手写 SQL 与连接管理。
3. **薄**（归 S-336）：对应的 `Db*Tools` 端点方法内部改调同一批强类型方法（**同一份 SQL 只能存在一处**）。可以分次做 —— 端点暂时不动也不影响正确性，但必须登记为剩余项。

### 硬判据（防回潮，归 S-336 落章程）

> `src/runtime/WishfulClaw.Agent/` 下**不得再出现** SQL 字面量：`"SELECT`、`"INSERT`、`"UPDATE`、`"DELETE`（含 `@"` 与 `$@"` 前缀，含 `DbService.MultiLine("…")` 里的第一个参数）。

## 四、坚决不做 —— S-333 ~ S-336 共用

| 不做 | 理由 |
|---|---|
| **把 `Db*Tools` 整体搬进 Agent** | 会让 Agent 直接压在表和 Entity 上 —— 耦合加深，不是减弱。S-326 已就这点裁过 |
| 重命名 / 合并这些 `.Db.cs` 文件 | 文件粒度是既有风格（主类 + `.Db.cs` 分部），改文件名会污染 `git blame` |
| 顺便改 SQL 语义（加索引、改排序、加 limit） | 只搬位置。语义变更要单独立项并单独验证 |
| 为「统一事务」重写连接管理 | 现有各处写法不同（有的自己开连接、有的复用），**逐处照抄**，先统一入口再谈统一事务 |

## 五、本单风险

| 风险 | 处置 |
|---|---|
| `tasks` 的 INSERT 带 8+ 列，`plans` 带 `spec_json` / `content` 两个大字段 | 搬之前把 `tasks` / `plans` 的 DDL 与现有 SELECT 列**逐个对齐**，差异就地记在案。`plans` 若走 `SELECT *`，强类型方法必须显式列全字段，不能漏 |
| `UPDATE tasks SET …` 是**部分列更新** | 不是 `UpdateStatus` 那种窄方法，抽的时候保持「传整行、只更这几列」的语义，别自作主张扩成整行覆盖。**⚠️ 本行登记时写错过**（原写「不含 status」），实际 `status` 在更新里，不含的是 `session_id`/`plan_id`/`sort_order`/`created_at` —— 订正见 §8.3 |
| 连接/事务边界 | 逐处照抄。两个 `.Db.cs` 都是 `db.Execute(conn, tx, …)` 或 `db.Execute(…)` 两种写法并存，搬的时候保持一致 |
| 这两个文件被 Agent 执行器热路径调用 | 搬完真机跑：建 plan → 建 task → 改 subject/description → 改 status → 归档 → 删除 |

### 8.2 与 S-335 同型：又一处「零件全在、没接线」

`EntityMappers.MapTask` / `MapPlan`、`TaskEntity` / `PlanEntity`、`DbClient.GetClient` 全都在，Agent 层原本就是 `db.Query(手写 SQL, EntityMappers.MapTask, …)` 三样在调用点现组装 —— 缺的确实只是 §二 说的那层胶水。所以这刀**没写一行新 SQL、没动一个字段映射**，纯搬位置。

### 8.3 三个「看着该顺手改、其实不能改」

1. **`UpdateRow` 只更 9 列**（subject / description / active_form / status / owner / blocks / blocked_by / metadata / updated_at），**不动 `session_id` / `plan_id` / `sort_order` / `created_at`**。task 不在会话或 plan 之间迁移；`sort_order` 是模型依赖的 todo 顺序，每次状态翻转重写它等于打乱顺序。
   - ⚠️ **订正 §五 表里的一句话**：登记写「`UPDATE tasks SET …` 是部分列更新（**不含 status**）」，实测 `:90` 是**包含** `status = @status` 的。真正不含的是上面那四个不可变列。照错描述去改，会把 status 从更新语句里删掉 —— 那个才是真 bug。
2. **`Insert` 用 `TaskEntity.Blocks` 原样文本**，不解析。解析成 `string[]` 是 `TaskWorkingRow` 的事（`ParseStringArray`），序列化回去是 `ToEntity` 的事（`SerializeStringArray`）。Store 一旦开始理解数组语义，就得跟 `AgentRuntimeTaskExecutor.Codec.cs` 那套（含 `RemoveTaskId` 的去重语义）纠缠，分层白做。
3. **`GetById` 的 session 过滤是查找的一部分**，不是可选参数。task id 来自模型输出、不可信，`WHERE id = @id AND session_id = @sessionId` 才是防跨会话越权的那道条件。`sessionId` 为空时直接返回 null —— 原来 `LoadTask` 的本地判断挪进 Store，语义不变。

### 8.4 `plans` 的 `SELECT *` 换显式列

`DbPlanStore.SelectColumns` 显式列全 9 个字段。`EntityMappers.MapPlan` 按列名读，`SELECT *` 与显式列对它无差别 —— 换的理由是 §五 风险表那条：「`plans` 若走 `SELECT *`，强类型方法必须显式列全字段」。差别在演进时：DDL 加一列，端点 `SELECT *` 会自动带出来，Store 不会 —— 漏了当场炸，比静默漂移好。

`plans` 不提供事务重载：五个操作都是单条语句，没有跨语句不变式要保。
