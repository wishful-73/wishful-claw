# S-263 · 侧栏一收起就白屏 —— hooks 被追加在 early return 之后（S-240 回归）

> 归属：v3-iter-4（产品 1.0.4）｜登记 2026-10-29 09:07
> **状态：代码已修复（2026-10-29，刀 1d）。** 自动化覆盖不到渲染端 hook 顺序，验收只能靠真机（见 §五）。
> 来源：老大 2026-10-29 09:02 指令「dev 我让它复现昨天 400 的过程 现在页面渲染已经炸了，你能看下 dev 的日志不」。

紧跟着一条 `ErrorBoundary caught: ...`，整棵侧栏被兜走 —— 用户看到的是侧栏白掉。

**触发条件：侧栏一收起（`leftSidebarOpen` 变成 false）就必崩**，与「复现 400」这件事本身无关。老大当时正在跑 400 复现，侧栏被收起，于是先撞上了这条。

顺带交代：当天全日志**零条 400**（`HTTP 400` / `provider_request_rejected` 均无命中），三条 ERROR 全是这条渲染崩溃加一条 `allowpopups` 属性警告。worker 侧最后一次心跳 `09:02:17 inputTokens=44938`（阈值 144000，远未触发压缩）⇒ 400 复现没走到。

## 二、根因

`WorkspaceSidebar.tsx` 的组件体里：

```tsx
// 修复前 192-195 行
// Collapsed state: completely hidden, use TitleBar button to expand
if (!leftSidebarOpen) {
  return null
}

// ……中间隔着一百多行……

// 修复前 222-248 行（S-240 追加）
const extensionInstances = useExtensionStore((s) => s.extensions)
const manifestViewItems = useMemo(() => { /* 插件视图入口 */ }, [extensionInstances, t])
```

**两个 hook 排在这个 early return 后面。** 于是同一个组件在两种状态下调用数量不同：

| `leftSidebarOpen` | 执行到哪 | hook 数 |
|---|---|---|
| `true` | 一路跑到底 | N + 2 |
| `false` | 193 行就 return null | N |

React 依靠「hook 调用顺序 + 数量恒定」维持 fiber 上的 hook 链表，数量一变就抛 `Rendered fewer hooks than expected`。这不是警告，是直接崩。

### 为什么 S-240 会踩上

S-240 的活是「已启用插件的 `views` 挂进左侧导轨下拉」。它把新逻辑**追加在文件末尾**（紧挨着 `extensionItems` 那个数组），而 `extensionItems` 本来就在 early return 之后 —— 结果两个 hook 一起落在了 `if (!leftSidebarOpen) return null` 的后面。

改的人只验证了「侧栏展开时插件入口出现」，没验证「侧栏收起时还不崩」——因为侧栏默认就是展开的，收起是个需要主动做的动作。

## 三、为什么前面的门禁全没抓到

| 门禁 | 为什么抓不到 |
|---|---|
| `npm run typecheck` | TS 只管类型，hook 调用顺序不属类型系统 |
| `npm test` 里的渲染端套件 | 全是纯函数 / store 层断言，不挂载 React 组件，跑不到组件体 |
| **项目没有 eslint** | 装了 `react-hooks/rules-of-hooks` 的话，这条 `useExtensionStore` 会被当场标红 —— 它正是为这个缺陷存在的规则。仓库里 `.eslintrc*` 与 `eslint.config.*` 均不存在，`package.json` 无 eslint 依赖、无 `lint` 脚本 |
| 真机验收清单 | S-240 的清单只列了「点入口提示 / 停用消失 / 卸载无残留」，没有「收起侧栏」这一条 |

⇒ 这条**只能靠运行时撞见**。所以补一条硬教训进 §四。

## 四、修法

### 4.1 动作：early return 后移，不是 hook 上移

两种改法都成立，选了后移：

| 方案 | 代价 |
|---|---|
| **hook 上移**（把 222-248 整段搬到 return 之前） | 要连注释一起搬，会打散「插件视图入口」小节，且新的 hook 位置离它服务的 `extensionItems` 越来越远 |
| **early return 后移**（本条采用） | 只挪一个块；`if (!leftSidebarOpen) return null` 的语义不变（still 挡住整棵渲染），只是排在全部 hook 之后 |

后移后的结构：

```tsx
const extensionInstances = useExtensionStore((s) => s.extensions)
const manifestViewItems = useMemo(/* … */, [extensionInstances, t])

// Collapsed state: completely hidden, use TitleBar button to expand
// ⚠️ 这句必须留在所有 hook 调用之后 ……
if (!leftSidebarOpen) {
  return null
}

const allExtensionItems = [ … ]   // 纯计算，留在 return 之后无害
```

`allExtensionItems` / `currentWidth` / `freeChatNavItem` 都是纯计算，收起时不执行正好省掉。

### 4.2 原位留警告注释

在 early return 上方写清「新增 hook 往上面放，不要往这之后加」，并写明本条编号与后果（整棵侧栏被 ErrorBoundary 兜走、页面白掉）。**下一个往文件末尾追加 hook 的人不会再踩。**

### 4.3 顺带补 500 行豁免头

文件原本 511 行、无豁免头（AGENTS.md 要求超 500 行标注）。S-240 加插件入口时就已经超了，一直没标。本次改动后 521 行，一并补上豁免头（依据：§大文件拆分 第 5 条第 3 类 —— 拆得动但代价显著大于收益；理由写进文件头）。

## 五、判据（验收）

自动化覆盖不到，全部靠真机：

1. **侧栏收起不崩** —— 点收起按钮，侧栏消失、聊天窗正常，无白屏、无 ErrorBoundary。
2. **反复收展 10 次** —— 不崩。这是复现本条最直接的动作。
3. **收起状态下有流式输出** —— 消息照常往外吐、不崩（收起时少执行的那两个 hook 不能影响别处）。
4. **插件入口仍在** —— 展开侧栏，已启用插件的 `views` 照常出现在导轨下拉，按 `nav.order` 排序。
5. **插件停用后入口消失** —— 停用一个插件，展开状态下其入口不再出现。

## 六、全仓同款扫描（2026-10-29）

项目没有 eslint，`rules-of-hooks` 用不上，所以按「同一缩进层级、遇函数边界即停」写了一次性判据扫 `src/renderer/src` 下全部 `.tsx`：

```
NO VIOLATIONS
```

扫描口径与局限，如实写在这里，免得以后有人把它当成「已保证」：

- 判据近似：`if (...)` 与 `return` 同缩进，然后往下找**同缩进**的 `use[A-Z]\w*(`；遇到缩进更小的 `}` / 函数边界即停。
- **不认嵌套函数里的 hook**（那本来就不是同一个组件体的 hook）—— 第一版按「return 之后出现任何 hook」判，误报两百多条，全部是跨函数的假阳性，所以收紧到同缩进。
- 局限：靠缩进近似作用域，本质上是文本匹配。**真要根治，应该装 `eslint-plugin-react-hooks` 把 `rules-of-hooks` 设成 error** —— 这条建议记在 §八。

## 八、不做的事（说明边界，防止范围蔓延）

- **不引入 eslint** —— 装 `eslint-plugin-react-hooks` 是更根本的解法，但那是工具链级别的决定（要新增依赖、配置、CI 门禁脚本），不在一个 bug 修复的范围里。**建议单独登记一条**，老大点头再做。
- **不动 `allowpopups` 警告** —— 同一份日志里还有 `Received true for a non-boolean attribute allowpopups`，来源是 `<webview allowpopups>` 在 React 里传了布尔值。它只是警告、不影响功能，与本条无关。
- **不顺手重构 `WorkspaceSidebar`** —— 虽然它 521 行、确实该拆，但拆是独立工程（见豁免头里写的代价），不在 bug 修复里夹带。
- **不补渲染端组件测试框架** —— 本条暴露的缺口（渲染端无自动化）值得单独讨论，但引入 jsdom + testing-library 是另一个决定。
