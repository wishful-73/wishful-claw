# S-304 · 流式响应中途断连零重试 —— 重试策略漏了 `HttpIOException` 这一类

> 状态：**✅ 已实施（v3-iter-6，待真机验收）**
> 登记：2026-11-02 15:50 ｜ 实施：2026-11-02 16:2x
> 来源：老大 2026-11-02 15:45「`net_http_invalid_response_premature_eof (ResponseEnded)` 这个报错是超时了么？超时我希望走重试呀」
> 裁定：老大 16:05「这些还是本迭代做，我希望的是报错了能重试……一旦发布任务，希望的是尽可能的保证任务完成」；16:06「报错了那一段就算中断报错呗，新的输出走新的呀」
> 关联：S-237（400 重试收紧）、S-291（回执翻历史）—— 同属「错误分类」这条线

## 一、现象

生产日志原文（`2026-11-02.log`，15:35:38）：

```text
[WARN] agent run failed runId=wc-agent-1793602557526-633g5c
       error=HttpIOException: net_http_invalid_response_premature_eof (ResponseEnded)
```

同一 run 的时间线：

| 时间 | 事件 |
|---|---|
| 15:12:13 | `agent tool output truncated tool=Bash originalBytes=69585 truncatedBytes=32767` ⇒ 已跑多轮工具 |
| 15:32:00 | `context compression DIAG: inputTokens=58253 ... -> skip (below trigger)` |
| **15:35:38** | **`ResponseEnded`，run failed** |
| 15:36:03 | 老大重发消息（新 run） |

**3 分 38 秒静默期间，零条 `request_retry` 日志。**

## 二、定性：不是超时

超时走的是另一条路，而且**已经在重试**：

| 超时类型 | 抛出位置 | 转成 |
|---|---|---|
| 首字节（响应头）超时 | `AgentRuntimeRequestTimeout.cs:69-77` catch `OperationCanceledException` | `TimeoutException` |
| 流空闲超时 | `AgentRuntimeRequestTimeout.cs:105-112` 同款 | `TimeoutException` |

`ProviderRetryPolicy.cs:101-130` catch `TimeoutException` → 指数退避重试，并发 `request_retry` 事件（`Reason: "timeout"`）。

`HttpIOException` 是 `ReadLineAsync` 读到**对端关闭连接**，不是 `OperationCanceledException`，不会被转成 `TimeoutException`。

`ResponseEnded` 的含义：响应流读到一半，对端关闭。同族还有 `InvalidResponse` / `HttpProtocolError`。

## 三、根因：`catch` 类型不匹配

三处网络重试入口全都只认 `HttpRequestException`：

| 位置 | 守卫条件 | 转成 |
|---|---|---|
| `OpenAIChatProvider.cs:92-107` | `!cancelled && assistantText.Length == 0 && reasoningContent.Length == 0 && toolCalls.Count == 0 && toolBuffers.Count == 0` | 502（可重试） |
| `AnthropicMessagesProvider.cs:126-139` | `!cancelled && parseState.AssistantText.Length == 0 && parseState.ToolCalls.Count == 0` | 502（可重试） |
| `ProviderCompletionService.cs:111-115` | 无（非流式，整包读） | 记 `lastError` 后重试 |

**`HttpIOException : IOException`，与 `HttpRequestException` 无继承关系**（.NET 8 引入；本项目 `net11.0`）。⇒ 三处一个都捕获不到。

全仓 `catch (IOException` 只有 6 处，全是文件 IO（写共享冲突 / 数据目录 / 媒体文件），**无一处覆盖网络流**。

**⇒ 连接中途断开时异常直接冒泡成 `agent run failed`。同属传输层故障，`HttpRequestException` 能重试、`HttpIOException` 不能 —— 这是实现漏了一类异常，不是设计选择。**

## 四、本次场景即使修了也不会重试（关键）

现有守卫是「**零输出才重试**」：一旦有正文 / 思考 / 工具调用，就不转 502 —— 因为重试会让模型从头再生成一遍，UI 上出现重复内容。

本次 run 从 15:12 前就在跑、已有多轮 Bash 工具调用 ⇒ UI 上早有大量输出 ⇒ **即使捕获了 `HttpIOException`，守卫也不会放行**。

所以老大「希望走重试」的诉求，在「已跑了二十分钟的中途断连」这个具体场景下，**不能靠加 catch 解决**。两件事要分开办。

## 五、方案（老大 16:06 已拍板，原 A/B/C 三选一作废）

老大原话：「感觉你想复杂了，报错了那一段就算中断报错呗，新的输出走新的呀」。

⇒ **不需要替换语义，也不需要新增交互态。** 中断的那一段就留在 UI 上，重试产生的新输出是新的段落。

这一点在架构上天然成立：`ProviderRetryPolicy.ExecuteAsync` 的循环体是**完整一次 provider 请求**（`Func<Task<...>>`），每次重试都会重跑整个方法 —— 新的 `StreamSegmentBoundary` 实例、新的 `assistantText`、新的 `text_start` 事件 ⇒ renderer 开新段落。**已有的半截内容不会被追加、也不会被改写。**

### 5.1 判定收进一个纯函数（三处共用）

新增 `ProviderRetryPolicy.IsRetryableTransportError(Exception)`：

```csharp
internal static bool IsRetryableTransportError(Exception ex) =>
    ex is HttpRequestException or HttpIOException;
```

三处调用点全部改用它：

| 位置 | 改动 |
|---|---|
| `OpenAIChatProvider.cs` | `catch (Exception ex) when (ProviderRetryPolicy.IsRetryableTransportError(ex) && !cancelled)` |
| `AnthropicMessagesProvider.cs` | 同上 |
| `ProviderCompletionService.cs` | `catch (Exception ex) when (ProviderRetryPolicy.IsRetryableTransportError(ex))` |

**为什么不各写各的 `ex is HttpRequestException or HttpIOException`**：正是因为三处各写各的，才会漏。收成一个函数后，将来加第三类传输故障只改一处。

### 5.2 去掉「零输出」守卫

两个流式 provider 原来的守卫要求正文 / 思考 / 工具调用全为空才重试。老大裁定后**整条守卫去掉**，只保留「用户取消不重试」。

理由：一个已经跑了二十分钟、做完多轮工具的 run，不能因为上游掉一次 socket 就整轮作废。半截输出留在界面上是可接受的代价。

**抛异常前先 `boundary.AtEnd()`**，把断流时仍开着的 thinking 块收尾，否则渲染端会一直显示它在流式输出。

### 5.3 不做

- **不加新事件**（比如 `stream_interrupted`）：`request_retry` 已经会让状态栏显示重试状态，段落本身靠新的 `text_start` 自然分开。加事件要动协议 + renderer + 落库，收益不匹配。
- **不做 UI 替换**（原方案 B）：工具可能已经执行过、副作用已发生，替换边界判不准。
- **不 catch 裸 `IOException`**：会误伤文件 IO / 管道 / 数据目录，必须精确到 `HttpIOException`。已写进测试防回归。
- **不为「中途断连」引入续写协议**：模型侧不支持，成本远超收益。

## 六、判据与实测

测试落在 `tests/WishfulClaw.ProviderHeaderRegressionTests/TransportRetryChecks.cs`（`npm test` 里跑）。

| 判据 | 结果 |
|---|---|
| `HttpIOException(ResponseEnded)` 判定为可重试 | ✅ |
| `HttpIOException(InvalidResponse)` 判定为可重试 | ✅ |
| `HttpRequestException` 仍判定为可重试（别在修的过程中丢掉） | ✅ |
| 带 inner exception 的 `HttpIOException` 仍可重试 | ✅ |
| 裸 `IOException` **不**可重试（防误伤文件 IO） | ✅ |
| `OperationCanceledException` **不**可重试（用户取消不是故障） | ✅ |
| `InvalidOperationException` **不**可重试 | ✅ |
| `HttpIOException` 不是 `HttpRequestException` 子类（根因固化） | ✅ |
| `HttpIOException` 是 `IOException` 子类 | ✅ |

**反向验证（已执行）**：把 `IsRetryableTransportError` 改回只认 `HttpRequestException` ⇒ 测试 `EXIT=1`，红的正是 `Assertion failed: ResponseEnded (the production failure) is retryable`。改回后 `EXIT=0`。

### 6.1 测不到的部分（如实记）

`OpenAIChatProvider.Http` / `AnthropicMessagesProvider.Http` 都是 `private static readonly HttpClient`，**不可注入**，所以没法用 mock handler 做「真的断一次流、看它有没有重试」的端到端单测。

单测能钉住的是**判定函数**（上表 9 条），端到端行为靠真机验收：

1. 跑一个长任务，中途断网 / 掐代理 ⇒ 期望状态栏出现「重试中」，随后继续输出；
2. 断流前的半截内容留在界面上，重试后的内容是新段落，不重复不覆盖；
3. 若断流时 thinking 块还开着 ⇒ 它会被收尾，不会一直转圈。

## 七、风险

- 去掉「零输出」守卫后，若上游持续「连上就断」，会按 `requestMaxRetries` 退避重试 —— 与 429 / 5xx 共用同一上限（默认 10），不会无限放大。
- 工具调用已完整生成但尚未执行时断流：旧卡片会留在界面上（不执行），重试后模型重新决策。属于「中断段落」的一部分，可接受。
- 若将来有人把判定放宽成 `catch (IOException)`，`TransportRetryChecks` 里那条「裸 IOException 不可重试」会先红。
