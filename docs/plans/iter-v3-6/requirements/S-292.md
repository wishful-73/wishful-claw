# S-292 渠道命令 `/compress` 是 no-op

> 登记：2026-11-01（v3-iter-5 移交时带过来，raw §1.3 已缩范围）
> 归属：**v3-iter-6 刀 4**
> 类型：缺陷（功能失效，且回假话）
> 状态：**✅ 代码完成 · 待真机验收**（2026-11-02）

## 一、现象

渠道（微信 / QQ 等）里发 `/compress`，机器人回「Context is already compact.」—— 用户以为压缩过了，实际一条消息都没动。

## 二、根因（读码事实）

| 入口 | 走哪条链 | 结果 |
|---|---|---|
| **界面「压缩会话」**（浮块 / ContextRing） | `compressSessionContext`（`use-chat-actions.ts:629`）→ IPC → worker `agent/compress-context` → `AgentRuntimeContextCompressionTools.CompressAsync` | ✅ 真压缩 |
| **渠道命令 `/compress`** | `handleCompress`（`plugin-command-handlers.ts:386`）→ `db/messages-compact-session` → `DbMessageCompactTools.CompactSession` | ❌ no-op |

`CompactSession` 里的 `TryCompactMessageContent` 要求 `content` 是 **JSON 数组**（`JsonDocument.Parse` 后 `ValueKind != Array` 直接 return null）。S-285 之后新消息的 `content` 是**纯文本** ⇒ 全部 `continue` ⇒ `compacted = 0` ⇒ 回一句假话。

## 三、决策：删命令（不做真压）

两条路都核过：

- **真压**：唯一真源在渲染层（`resolveSendModel` + `buildProviderPayload`）。main 进程虽有 `ai-provider:get` 与 `readPersistedProviderStore`，但把 payload 组装搬进 main = **双真源**，且渠道压缩是长耗时 LLM 调用、无进度反馈。
- **删命令**：`messages-compact-session` 的调用方**只有**这个命令和它自己的注册；`MessageCompactResult` 无测试覆盖。删掉不留死代码，用户侧也没有损失 —— 压缩在界面上有按钮，走的是真压缩。

⇒ **删命令，连带删掉无人调用的 DB 端点。**
