## 四、A2 · 原判「该不该迁出」是错问题 —— 真正的问题是漏了一次收口

### 4.1 原判

登记时写的是：

> 33 个 `Db*Tools` 8,204 行占 Infrastructure 55%，与 `AGENTS.md:59`「使 Tools / Modules 能迁出到 Agent 层」矛盾 ⇒ 二选一：改章程承认，或迁进 Agent

### 4.2 实读之后，结论反转

**那 33 个 `Db*Tools` 待在 Infrastructure 是对的。** 问题不在它们「太多了」，而在 **`memory_entries` 这条线没照它们的模式做**：

| 位置 | SQL 处数 | 干什么 |
|---|---|---|
| `Worker/Modules/MemoryModule.cs` | **8** | stats 两个 COUNT / append INSERT / update SELECT+UPDATE / demotion SELECT / batch-status UPDATE |
| `Worker/Modules/MemoryModule.Entries.cs` | **3** | `entries-by-status` 分页 / `entries` 分页 / `CountScope` |
| `Agent/Tools/MemoryTools/MemoryAppendTool.cs` | 1 | INSERT |
| `Agent/Tools/MemoryTools/MemoryUpdateTool.cs` | 2 | SELECT by id / UPDATE |
| `Workspace/Memory/MemoryFtsService.cs` | 2 | re-heat UPDATE / LIKE 回退 FROM |

而 Infrastructure 里关于这张表**只有** `Entities/MemoryEntryEntity.cs`（15 行）和 `EntityMappers.MapMemoryEntry` —— **没有 `DbMemoryTools`**。其他 33 张表都有访问器，唯独这张没有，于是 SQL 漏到上面三层各写一份。

### 4.3 逐字相同的证据

Worker `MemoryModule.cs:144-152` 与 Agent `MemoryAppendTool.cs:105-113`：

```csharp
"INSERT INTO memory_entries (scope, title, content, priority, status, created_at, updated_at) " +
"VALUES (@scope, @title, @content, @priority, @status, @ca, @ua)"
```

一字不差，连 7 个参数名都一样。Worker `:176-184` 与 Agent `:138-146` 的 UPDATE 同样一致。

### 4.4 仓库里已有同一条原则的先例

`MemoryTimeFilter.cs:8-10` 的注释写着：

> 两个消费方都要按 `updated_at` 收窄范围：记忆库列表与召回检索链。**它们必须共用同一份拼装 —— 各写一份必然漂移，而漂移的表现是「列表里翻得到的条目搜不到」，最难排查。**

**这条原则当时只落在了时间子句上，主体 SQL 一直没收。** 本条就是把它补完。

### 4.5 所以 `AGENTS.md:59` 那句是反的

> 「目的：解耦 Worker 对基础设施的直接依赖，**使 Tools / Modules 能迁出到 Agent 层**」

按 4.2 的结论，正确方向是**把访问代码收下来**，不是推上去。这句要改。

## 六、实施设计（C）

### 6.1 一个必须先解决的依赖约束

实测各层 `Microsoft.Data.Sqlite` 引用：

```
Infrastructure  YES
其余六层        -      ← 靠 ProjectReference 传递才拿得到类型
```

而 `MemoryTimeFilter`（产出 `SqliteParameter`，本质是 Db 层的东西）现在放在 **Workspace**。`DbMemoryTools` 在 Infrastructure 用不到它（方向反了）。

⇒ **先把 `MemoryTimeFilter.cs` 从 `Workspace/Memory/` 移到 `Infrastructure/Db/`**，namespace 改 `WishfulClaw.Infrastructure.Db`。Workspace 本来就引用 Infrastructure，两个现有消费方改 `using` 即可。

同理，DTO `MemoryEntryRow` / `MemoryDemotionCandidate` 在 **Workspace/Memory/AotMemoryResultTypes.cs**，Infrastructure 拿不到 ⇒ **`DbMemoryTools` 只进出 `MemoryEntryEntity`**，DTO 转换留在上层。反而更干净。

### 6.2 `DbMemoryTools` API

```csharp
namespace WishfulClaw.Infrastructure.Db;

public static class DbMemoryTools
{
    // 读
    public static MemoryEntryEntity? GetById(long id);
    public static int  CountByStatus(string? scope, params string[] statuses);
    public static List<MemoryEntryEntity> ListByStatus(string? scope, string[] statuses, int limit);
    public static List<MemoryEntryEntity> ListPaged(string? scope, MemoryTimeClause time, bool descending, int limit, int offset);
    public static int  CountPaged(string? scope, MemoryTimeClause time);
    /// <summary>降级候选：只读 id/scope/title/priority/status/updated_at，不读 content（避免整表大字段）。</summary>
    public static List<MemoryEntryEntity> ListDemotionCandidates(string? scope);

    // 写
    public static long Insert(MemoryEntryEntity entry);
    public static int  Update(MemoryEntryEntity entry);
    public static int  BatchSetStatus(IReadOnlyList<long> ids, string status, string? scope, bool touch);
    public static int  Reheat(IReadOnlyList<long> ids);
}
```

### 6.3 顺带修掉的东西

- **`scope` 子句改参数化**：原代码用 `$" AND scope = '{EscapeSql(scope)}'"` 拼字符串（4 处），URL 形式的 `project:` scope 里带引号也不会炸，但参数化是正确做法。收口时一并改成 `@scope`。
- **`EscapeSql` 随之删除**（`MemoryModule.cs:292`）。
- **两个 Agent 工具文件的格式已损坏**（几乎每行之间被插入空行，是之前某次编辑留下的），改造时顺手整理。

### 6.4 不纳入的部分

`MemoryFtsService.SearchAsync` 的 FTS 联查与 LIKE 回退**保留在 Workspace** —— 那是**检索**逻辑（trigram 分词、bm25、score 合成、阈值），不是行级 CRUD。硬塞进 `DbMemoryTools` 会把 FTS 知识搬进 Infrastructure。

`ReheatAsync` 的 UPDATE 属于行级状态变更 ⇒ **纳入**。
