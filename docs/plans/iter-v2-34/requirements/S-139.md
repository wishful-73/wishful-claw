# S-139 · 消息操作按钮组：清四条死链 + 「编辑」改为回填输入框

- 2026-09-22：**老大提出**。起因是 S-136 真机验收时我误判「重试 / 删除按钮也一并修好了」，老大当场纠正「**这两个没看到过**」，遂逐条取证。
- 同日 16:04 / 16:07 **老大两次纠口径**，把需求从「截断 + 重发」改成「**回填输入框**」。见本文第三节。

## 一、根因：TS → C# 迁移留下的孤儿 UI 契约

老大定性（2026-09-22 15:47 原话）：

> 以前我们是参考的 OpenCowork，最初是纯 TS + JS 的项目，所以很多链条都是那时候的。后来把运行时拆分到 C# 端了，所以就出现了这么多死链条。

具体到这一处：`MessageList` 的四个操作回调是 **OpenCowork 时代的 UI 契约**，迁移后主界面的壳换成了 `SessionConversationPane`，**新壳一个都没接**，旧契约连同它的下游实现一起悬空。

## 二、四条死链的取证（2026-09-22 实读）

**store 层零实现**：`retryAssistantMessage` / `deleteMessage` / `editUserMessage` / `continueToolExecution` 四个名字，全仓**只出现在 i18n 文案和 `action-bar` 自身的 JSX 里**，没有任何实现体。

### 2.3 `showContinue` 是三层全死（比另外三条多一层）

它看似有活逻辑，实测**没有一个环节是活的**：

1. `useMessageListData.ts:246-250` 真的算出 `continueAssistantMessageId`，并在 `:461` 导出 —— **但全仓零消费**（`MessageList.tsx` 用的是 `row.showContinue`，没碰它）。
2. 唯一消费它的 `buildChatRenderableMessageMetaFromAnalysis`（`transcript-utils.ts:292-301`）—— **零调用点**；包装 `buildChatRenderableMessageMeta`（`:364-374`）同样零调用点。
3. 渲染链实际走 `RenderableChatItem.showContinue`（`renderable-chat-items.ts:33`），该字段在 `:46 / :62 / :221 / :333 / :346 / :364` **全部硬编码 `false`**。

判定逻辑在 `MessageList/utils.ts:117-121`：会话空闲 + 尾部 assistant 的 `tool_use` 全有 `tool_result` ⇒ 打标。**语义**（i18n 原文）：让用户「使用已保存的工具结果在这条消息里继续，不会新增 AI 消息，也不会重新执行历史工具」—— **TS 时代「loop 会停在工具执行上」的产物**，搬到 C# 后 loop 自己跑到底，该状态基本不再产生。

**老大裁定（2026-09-22 15:54）**：「那这个没必要存在了。」

## 三、编辑的语义（老大两次纠口径后的定稿）

### 3.1 不是「截断 + 重发」

**老大 2026-09-22 16:02**：

> 编辑实际上我只是想把内容丢回输入框，可能跟你想的不太一样

我最初理解成「截断该消息及其后所有消息 → 自动重发」，方向反了。**正解：点一下 → 内容灌进底部输入框 → 用户自己改、自己发。不截断、不自动重发。**

### 3.2 通道是现成的：`pendingInsertText` / `pendingInsertImages`

**老大 16:04 提示**：

> 输入框本身是有这些东西的吧？首先消息可以在执行中发送，所以我们有消息队列，队列中的消息可以取回编辑，其次文件预览里面也有发送到对话

顺着找到通道（**我先前断言「没有外部写入通道」是错的**）：

```
stores/ui-store.ts:290-293            pendingInsertText / pendingInsertImages
        ↓（唯一消费点）
components/chat/InputArea/use-input-area-effects.ts:156-176
```

消费逻辑两段：文本 `replaceSelectionWithText(…)`（**插到光标处**），图片 `setAttachedImages(prev => [...prev, …])`（**追加**）。代码注释自己写着（`use-input-area-effects.ts:169-170`）：「`attachedImages` 是 InputArea 的局部 state，**除了这里没有别的外部写入通道**」。

**现成调用方 5 个**：

| 调用方 | 场景 |
|---|---|
| `use-queued-messages.ts:88-90` | **队列消息「取回」**（S-57） |
| `use-file-tree.ts:297` | 文件树「添加到会话」 |
| `preview-toolbar.tsx:160`（`onSendPathToChat`） | **预览「发送到聊天」** |
| `search-output.tsx:93 / :161 / :220`、`text-output.tsx:186` | 工具结果点文件名插入 |

### 3.3 三个定案（老大 16:07）

| # | 问题 | 定案 | 老大原话 |
|:--:|---|---|---|
| 1 | 追加还是覆盖 | **追加**（A 方案，照抄队列取回） | 「A」 |
| 2 | 原消息动不动 | **不动。不删原消息** | 「是重来的味道很重，但是不删除原消息，那是来时路」 |
| 3 | `UserMessage` 内联编辑态 | **整个删掉** | 「按『丢回输入框』，这套整个删掉」 |

⇒ **落草稿也不用管**：回填走 `replaceSelectionWithText` → `documentNodes` 变 → `finalSerializedText` 变 → 草稿保存 effect（`use-input-area-effects.ts:153-154`）自动接管，刷新后还在。

## 四、要做的三件事

### 4.1 删：重新生成 / 删除消息 / 继续执行（三条链全清）

含 `showContinue` 的判定位与数据字段。**受 `noUnusedLocals` / `noUnusedParameters` 所限（`@electron-toolkit/tsconfig` 两者均为 `true`），删 UI 必须删到源头，留不了残桩。**

### 4.2 删：`UserMessage` 的内联编辑态

现有一整套**就地编辑器**要整个移除（清单见 `plan-b4.md` 步骤 4）：

- state：`editing` / `editText` / `editSkillName` / `editImages`（`:95-101`）、`textareaRef` / `fileInputRef`（`:105-106`）
- 副作用：聚焦 effect（`:108-113`）、`loadSkills` effect（`:115-119`）
- 逻辑：`nextDraft` / `canSave`（`:121-129`）、`handleSave`（`:138-142`）、`handleCancel`（`:144-149`）、`handleKeyDown`（`:203-211`）、`addImages` / `removeImage`（`:213-223`）
- UI：`:251-330` 整块（命令提示条 + `UserSkillEditControl` + `textarea` + 图片编辑条 + 隐藏 file input + 三个按钮）
- 连带：`!editing` 判断（`:243 / :419 / :424 / :429`）、`:331` 的三元收敛
- **`UserSkillEditControl`**（`user-message-views.tsx:124` 定义）只有 `UserMessage.tsx:258` 一处使用 ⇒ 删完变**死组件**，一并删

### 4.3 接：编辑按钮 → 回填输入框

**接口定案：保留 `onEdit` 这条 prop 通道，上层负责灌 store。**

理由（**已实证**）：`MessageRow` 的四个使用方里有 **`ExportView.tsx:59` 和 `StaticMessageTranscript.tsx:106`** —— 导出视图与静态渲染**也会渲染到 `UserMessage`**。若改成组件内部直连 `useUIStore`，那两处导出/静态视图里也会冒出编辑按钮，是**行为错误**。

现有 `onEdit &&` 判断正是干这个的。所以：

- `UserMessage` 侧：`handleStartEdit` 改写成**只准备数据 + 调 `onEdit`**
- 上层：`SessionConversationPane` / `floating-chat-window` 各自提供 handler，往 `useUIStore` 灌（**输入框的拥有者来做回填，语义明确**）
- 不传 `onEdit` 的地方（导出 / 静态视图 / `ChatPage`）自然无按钮

**回填文本要带技能 / 命令前缀**，否则重发不等价。构造规则（对齐 `:72-76` 的 `copyText`）：

| 消息形态 | 回填文本 |
|---|---|
| 系统命令 | `/{command.name} {body}` |
| 技能 | `[Skill: {name}]\n{body}`（`serializeUserSkillDirective` 的格式，**不是** `/name`） |
| 普通 | 展开后的正文（`expandedText`，`<pasted-block>` 已还原） |

## 五、体量、依赖与独立发布性

- **体量**：中偏大。**约 18 个源文件 + 2 份 locale**。
- **依赖**：纯渲染层，**不碰 C# 运行时**，与 iter-34 其它需求无交叉。**不需要 `dbDeleteMessage` / `truncateMessagesFrom`**（不删消息）—— 这两条上一版设计要动的东西，现在**不碰**。
- **独立发布性**：独立成刀。建议**不并入收尾刀** —— 改动面大且是「删三条 + 删一套编辑器 + 接一个功能」的混合体，混进收尾刀看不出重点。
- **已知既有风险（非本需求引入）**：`pendingInsertText` 是**全局单例**，主窗与浮动聊天窗各有一个 `InputArea` 订阅它 ⇒ 两窗同时存在时，一次回填可能只有一个窗口收到。队列「取回」、文件树「添加到会话」**本来就有这个问题**，本需求只是复用同一条通道。

- **`subscribeInputDraftCache`（`input-drafts.ts:95-103`）零订阅者** —— 定义了草稿缓存广播机制，没人用。

两条均**记档，不并入**。是否清理由老大另定。
