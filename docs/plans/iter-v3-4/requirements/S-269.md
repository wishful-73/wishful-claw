# S-269 · 摘要请求被 429 拒绝，6 秒内重试三次全撞墙 —— 降级成「摘要器不可用」

> 归属：**v3-iter-4（1.0.4）本迭代**，插入为刀 **3b**（紧跟 S-242 之后）｜登记 2026-10-29 11:02
> **状态：已交付（2026-10-29）。** 实施内容见 §八；判据 1~4、7 的纯函数部分由 `tests/WishfulClaw.CompactionSnapshotRegressionTests/SummarizerRetryChecks.cs` 锁定（24 条断言），判据 5 的文案由渲染端照 `rate_limited` 分档，判据 1/6 的真机部分待老大验。
> 老大原话：「多次压缩的时候压缩失败了，摘要生成失败，已使用回退摘要 —— 这个是什么原因呢」。
> 根因已用生产实例日志坐实，**不是「摘要器坏了」，是我们没按上游要求的时间等**。

## 一、现场（生产实例日志原文）

`~/.wishful-claw/logs/` 里 10-28 20:31、10-29 09:25 / 10:08 / 10:24 / 10:42 五波，全是同一条：

```
context compression attempt failed attempt=1 budget=400000 overflow=False
error=InvalidOperationException: OpenAI summarization HTTP TooManyRequests:
{"error":{"type":"server_error","message":"Upstream request failed:
  [ttft_admission_refused] the cell is at capacity; retry shortly (after 29 s)"}}
context compression attempt failed attempt=2 budget=200000 ... (after 27 s)
context compression attempt failed attempt=3 budget=100000 ... (after 22 s)
context compression LLM summarization failed after all input budgets: ...
```

三件事一眼可读：

| 观察 | 含义 |
|---|---|
| `ttft_admission_refused` + `retry shortly (after N s)` | 上游是**容量准入拒绝**，N = 3~39 秒。它自己告诉了我们该等多久 |
| 三次尝试的写入时间 | 10:08:20 → 10:08:22 → 10:08:26，**整根重试链只活了 6 秒** |
| 三波之间隔 16~18 分钟 | 不是「重试不收敛」，是会话持续长回阈值后自然重触发（见 §三 第 3 条更正） |

⇒ 上游说「等 29 秒」，我们等了 1.5 秒。三次全落在同一个拒绝窗口里，等于**一次都没真正重试**。

## 二、代码佐证（已核行号）

| 位置 | 事实 |
|---|---|
| `ContextCompression.cs:547-605`（`SummarizeAsync`） | 重试循环，`SummaryMaxAttempts = 3` |
| `ContextCompression.cs:598-602` | 退避 = `SummaryRetryDelayMs(1500) * (1 << attempt)` ⇒ **1.5s / 3.0s** |
| `ContextCompression.cs:550` | `charBudget = 400_000 >> attempt` —— **无条件**递减，不管失败原因是限流还是输入超长 |
| `ContextCompression.cs:598-599` | 那个 `if` 只控制「要不要 sleep」，**不控制要不要 continue** ⇒ 三档预算总会跑完 |
| `ContextCompression.cs:846-850`（OpenAI）/ `:710-713`（Anthropic） | 非 2xx 抛 `InvalidOperationException`，状态码进字符串，**`Retry-After` 响应头直接丢掉** |
| `ProviderRetryPolicy.cs:20-49` | `ProviderHttpException` **早就带** `StatusCode` + `RetryAfter`，还配了 `CreateAsync(providerName, response, ct)` 一把抓 |
| `ProviderRetryPolicy.cs:227-247` | `IsRetryableStatus` 是 `internal`，判据成熟（429 / ≥500；400 已于 10-27 明确收回） |
| `ProviderRetryPolicy.cs:258-281` | `ComputeDelayMs` 是 **`private`**，honor `Retry-After` 但 `Math.Min(raMs, MaxBackoffMs)` 会**把它压到 15 s** |
| `ProviderCompletionService.cs:86-96` | 主链路同一个套路：`statusCode is 429 or 408 or >= 500` + honor `Retry-After` |

**结论：摘要请求是整条 provider 调用链里唯一一个绕开 `ProviderRetryPolicy` 的地方。** 它自建静态 `HttpClient`（`:50-55`）、自建退避、自丢响应头。

## 三、根因三条

1. **退避量级错了。** 上游给的是 3~39 秒的窗口，我们 1.5s / 3s 递进。3 次机会全部落在窗口内。
2. **429 不该砍输入预算。** 递减 400k → 200k → 100k 是为 context-window 超限设计的（`IsContextWindowExceededError`，`ContextCompression.Errors.cs:18`）。限流砍输入毫无意义，白扔两次机会 —— 而且砍完还不一定装得下需要摘要的内容。
3. **降级把「限流」翻译成「摘要器不可用」。** 三次失败 → `MechanicalFoldDigest`（零信息占位）→ 若没变小则 `TruncateMessages` + `summarizerFailed = true`（`AgentLoop.ContextCompression.cs:115-123`）→ 渲染端 `contextCompression.summarizerFailed` = 「摘要生成不可用，已使用回退摘要」（`locales/zh/agent.json:21`）。**用户拿到的结论是错的**：摘要器好好的，是渠道在限流，等 30 秒就能成。

> **⚠️ 对上一条消息的自我更正。** 我先前说「truncate 路径不打水印 ⇒ 几分钟重来一遍」，**这条读错了**：`AgentLoop.ContextCompression.cs:172` 的 `ResetCompactionWatermark(newWireConversation.Count)` 对「正常压缩」和「截断兜底」两条路径都执行，水印确实重置到截断后的长度。10:08 / 10:24 / 10:42 三波是会话在 135k~143k tokens 区间持续增长、反复顶到 144k 触发线，**不是水印缺陷**。所以本需求**不含**水印改动。

## 四、修法（A~E，五条同刀）

原则：**不造第二套退避，把摘要请求接回既有判据。**

**A. 摘要调用改抛 `ProviderHttpException`**
`CallOpenAISummary` / `CallAnthropicSummary` 的非 2xx 分支改成 `throw await ProviderHttpException.CreateAsync("OpenAI", response, ct)` —— 状态码与 `Retry-After` 一起带走，错误消息格式因此也统一（`... request failed HTTP 429: {...}`）。

**B. 复用既有重试判据，不自己拍**
`ProviderRetryPolicy.ComputeDelayMs` 从 `private` 提到 `internal`，并**加一个 `maxBackoffMs` 参数**（默认 `MaxBackoffMs`，摘要侧传 45_000）—— 否则 Retry-After 的 29 秒会被现有 `Math.Min(raMs, MaxBackoffMs)` 压成 15 秒，3 次机会不够覆盖。

**C. 摘要侧循环按失败类型分流**
- `ProviderHttpException` 且 `IsRetryableStatus` ⇒ 重试，**预算不递减**（原预算重发），退避 = `ComputeDelayMs(attempt, RetryAfter, 45_000)`
- `IsContextWindowExceededError` ⇒ 走现有递减预算路径，不 sleep（这是正确用法）
- 其它（真 400 / 空输出 / 解析失败）⇒ 直接抛，不重试
- 未识别出的 429（响应体里只有 `retry shortly (after N s)`、没有 `Retry-After` 头）⇒ **按 30 秒兜底**，别退回 1.5 秒

**D. 降级语义说人话**
`SummarizerFailed` 之外再带一个原因枚举（`rate_limited` / `timeout` / `context_overflow` / `other`），渲染端分档文案：
- `rate_limited` ⇒「服务商繁忙（限流），已用机械摘要降级，稍后会自动重试」
- `timeout` ⇒「摘要超时，已用机械摘要降级」
- 其余 ⇒ 保留现有文案

**E. 原因带出来**
`context_compressed` 事件的 `CompressionError` 填上游原文（截断到 200 字符）；日志侧沿用 `attempt failed` 那行即可。

## 五、判据（验收）

1. 造一个恒返 429 且带 `Retry-After: 3` 的 mock 端点 ⇒ 日志显示**第二次尝试确实等了 ≥3 秒**，不再 <1 秒连发。
2. 同一 429 场景下 `budget` 三次**保持一致**（400000 / 400000 / 400000），不再递减。
3. 真 400（`{"error":{"message":"unknown field \"thinking\""}}`）⇒ **一次都不重试**，直接抛。
4. `Retry-After: 29` ⇒ 实际等待落在 25~30 秒区间（不被 15 秒上限压掉）。
5. 429 三次全失败 ⇒ 渲染端显示「服务商繁忙（限流）…」，**不再**显示「摘要生成不可用」。
6. 正常压缩路径零回归：`SummarizerFailed=false` 时文案、快照、水印行为与现在完全一致。
7. `npm test` 新增套件覆盖判据 1~4 的纯函数部分（退避计算 / 重试分类 / 预算不递减）。

## 六、不做的事

- **不动 `IsRetryableStatus` 的 400 口径。** 10-27 已定「400 不盲目重试」，本条不改。
- **不动水印逻辑。** 见 §三 的更正。
- **不给摘要换模型 / 不加渠道切换。** 那是另一个需求（渠道降级），本条只修重试与语义。
- **不调 `SummaryMaxAttempts`。** 3 次配上正确退避足够覆盖 39 秒窗口；调到 10 次会让用户在一次压缩上干等十几分钟。

## 七、待查（开工前）

- `ProviderHttpException` 是 `InvalidOperationException` 子类，而 `SummarizeAsync:590` 的 `catch (Exception ex) when (ex is not OperationCanceledException)` 会接住它 ⇒ 分流改造要在这个 catch **之前**单独 catch 一次，别漏。

- Anthropic 分支的 429 响应体形态（`Overloaded` / `rate_limit_error`），确认 `CreateAsync` 拿得到 `Retry-After`。

### 8.3 测试

新建 `tests/WishfulClaw.CompactionSnapshotRegressionTests/SummarizerRetryChecks.cs`（`Program.cs` 里在 `UsageStripChecks.Run()` 之后调用），**24 条断言**锁定判据 2/3/4/7：

- 退避：29 s `Retry-After` 在摘要器上限下等满 29 s；同样输入走主 turn 仍压到 15 s（**判据 6 的一半**）；超大 `Retry-After` 先夹 60 s 再夹上限；无头指数退避 500-750 / 1000-1250 / 2000-2250；`Retry-After: 0` 不退化成连发；`attempt > 10` 走固定 60 s。
- 分类：429 → `WaitUpstream` + `rate_limited` + 带 `Retry-After`；**无头的 429 → 兜底 30 s**（线上 `ttft_admission_refused` 就是这个形态）；503 → `WaitUpstream` + `server_error`；真 400（`unknown field "thinking"`）→ `GiveUp` + `other` + 保留上游原文；`context_length_exceeded` → `ShrinkBudget` + `context_overflow`。
- **判据 2 的守卫**：`ShrinkBudget` 是唯一动输入的 action，因此断言「429 的 action 不是 `ShrinkBudget`」等价于「限流不砍预算」。
