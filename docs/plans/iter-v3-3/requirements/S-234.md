# S-234：更新弹窗的「更新说明」不稳定（二次打开变空白）

## 1. 原话 / 来源

> 2026-10-27 10:29 老大：

> 点击检查更新，会出更新弹窗，里面的更新说明不稳定，二次点开弹窗就看不到更新说明了，也就是看到有更新点击开始下载，然后点后台下载，过一会儿再点开看进度，结果没有更新说明了。

性质：**软件侧缺陷** —— 说明内容在两个数据源之间不一致，不是样式问题。零后端改动、零数据面改动。

归属：**v3-iter-3（产品 1.0.3）** —— 老大明确「这个计入下个版本做」。

编号：S-234（S-233 之后第一个新号）。

## 2. 现象

同一份更新、同一个版本号，**看不看得到说明取决于时机**：

| 步骤 | 期望 | 实际 |
|---|---|---|
| 1. 点「检查更新」→ 弹窗 | 有说明 | **有** ✅ |
| 2. 点「开始下载」→ 点「后台下载」→ 弹窗关闭 | —— | —— ✅ |
| 3. 过一会儿点顶栏图标再看进度 | 说明仍在，进度条在走 | **说明空白** ❌ |

「不稳定」的症状正是因为：说明在**事件**里有、在**状态**里没有。走到哪条路，就得到哪个结果。

## 3. 现状（2026-10-27 实读源码）

### 3.1 说明有两个来源，只有一路是完整的

`main/updater.ts:199-208` `resolveReleaseNotes()`：

1. **清单内联** —— `latest.yml` 的 `releaseNotes` 字段。本项目**从 0.2.39 起就不写这个字段**（`release-notes-<版本>.md` 单独发），所以常态是 `''`
2. **官网补拉** —— 内联为空时，异步去官网拉 `release-notes-<版本>.md`

⇒ 真实内容**只可能来自第 2 路**，而它是**异步**的。

### 3.2 状态源存进去的是第 1 路（空串）

`main/updater.ts:423-429`：

```ts
const releaseNotes = formatReleaseNotes(info.releaseNotes)   // ← 只取内联，常态 ''
...
updaterState().applyAvailable({ newVersion: version, releaseNotes, declaredInstallerSize })
```

`applyAvailable`（`updater-state.ts:160-182`）把 `releaseNotes` 写进 coordinator —— 写进去的是 `''`。

### 3.3 补拉的结果只进事件，从不回写状态

`main/updater.ts:220-237` `announceUpdateAvailable()`：

```ts
resolveReleaseNotes(version, inlineNotes)      // ← 补拉官网 md
  .then((releaseNotes) => {
    sendUpdateEvent('update:available', { ..., releaseNotes })   // ← 只推事件
  })
```

**没有任何一步把这个结果写回 coordinator。**

`getUpdateStatus()`（`updater.ts:614-620`）返回的就是 coordinator 快照：

```ts
return { success: true, ...updaterState().snapshot(), ...getAppDistributionInfo() }
```

⇒ **凡是从状态读，读到的永远是空串。**

## 4. 根因：一个病根，三条路径

**病根：`releaseNotes` 在 coordinator 里存的是「清单内联」的副本，而真正的正文在异步补拉里，结果只走事件、不回写状态。**

| # | 路径 | 位置 | 结果 |
|---|---|---|---|
| **P1** | 二次打开弹窗**先刷状态** | `App.tsx:82-88` `showUpdateDetails()` → `await updater.refreshStatus()` | `update:status` 拿回空串，`use-app-updater.ts:61-64` 用快照**整体替换**渲染端 state ⇒ 内存里那份有内容的说明被抹掉 |
| **P2** | 之后的「重查」救不回来 | `use-app-updater.ts:158-173` | `checkForUpdates` 更新 state 时**不动** `releaseNotes`，只保留 `previous` —— 而 previous 刚被 P1 抹空了 |
| **P3** | 下载完成后再检查，事件都不发 | `updater.ts:418-421` | `downloadedVersion === version` 时直接 `return`，`announceUpdateAvailable` 根本不执行 ⇒ 连"事件的第二次机会"都没有，说明**永久消失** |

P1 是必现路径（每次点顶栏图标都走），P2 让它无法自愈，P3 让下载完成后的情形彻底无解。

**这也解释了「不稳定」**：第 1 步能看到，是因为那时弹窗吃的是 `update:available` 事件 payload；此后每次重新打开都经 P1 走状态，于是空白。若期间后台巡检又发一次 `update-available` 事件，说明会"闪现"回来 —— 时序不同，表现就不同。

### 4.1 顺带发现的第四条泄漏（同族，一并处理）

`updater-state.ts:184-190` `applyNotAvailable()`：`downloadedVersion` 为空时会把 `releaseNotes` 清成 `''`。后台巡检撞上网抖或远端刚撤包，就会走到这里 —— 说明被清，而版本仍然在。

## 5. 方案

### 5.1 采用：补拉结果回写 coordinator（治 P1 / P2 / P3 三条）

- `updater-state.ts` 新增 `applyReleaseNotes(version: string, notes: string): boolean`：
  - 仅当 `state.availableVersion === version` 且 `notes` 非空时写入；
  - **不参与相位流转**（不改 phase、不 reset 进度），只补一个字段。
- `updater.ts` `announceUpdateAvailable` 的 `.then()` 里，在 `sendUpdateEvent` **之前**调用它。
- 版本不匹配就丢弃 —— 补拉慢于下一次检查时，不能把旧版本的说明盖到新版本头上。
- `applyNotAvailable` 的清空逻辑保留（那条是对的：没有可用版本时不该留残影），但要确认工程下发事件与状态同步。

**为什么这是"一处改治三条"**：P1 / P2 / P3 全都是「从状态读不到说明」的不同触发方式。状态补全了，三条自动消失，事件路径不用动。

### 5.2 否决：渲染端按版本缓存说明

否决理由：内存缓存活不过窗口重载（托盘点击、`Ctrl+R`、崩溃恢复后照样空白），等于把主进程该管的状态又抄一份到渲染端 —— 两份真源，下次还要再对一次。

## 6. 验收

必须在**打包版**上验（dev 下 updater 走桩，说明链路不成立）：

| # | 场景 | 期望 |
|---|---|---|
| V1 | 检查更新 → 弹窗 | 有说明 |
| V2 | 点后台下载 → 30 秒后点顶栏图标 | **有说明 + 进度在走** |
| V3 | 下载完成 → 再点顶栏图标 | **有说明 + "立即重启安装"** |
| V4 | 下载完成 → 手点「重新检查」 | 说明仍在，不回退到「发现新版本」 |
| V5 | 断网后点顶栏图标 | 不崩、不白屏；说明若拿不到，退化行为与这次改造前一致 |
| V6 | 窗口重载（Ctrl+R）后再开弹窗 | 说明仍在（证明是状态而非内存） |

## 7. 范围外

- **弹窗本身的排版与信息层级**（说明区高度、`UpdateReleaseNotes` 折叠展开）遇问题另立。
- **帧率 / 下载速度 / 差分更新**相关逻辑不动。
- 官网 `release-notes-<版本>.md` 的生成与上传流程不动 —— 本次只保证"已经拉到的那份"不再丢。
