## 2. 现象

准确报错原文（`FileReadTool.cs:188-192`）：

> `Read image: <path> (<尺寸>, <mediaType>). The current model is not marked as vision-capable, so the pixels were not attached.`

即：**Read 一个图片文件，没有返回图像，只返回一句「当前模型未标记为视觉能力」的说明。** 模型本身能看图（老大明确），是本地配置判它不能。

### 2.1 决定性的对照：同一条链上，截图能识图、Read 不能

2026-10-27 11:27 老大补充：

> 我现在遇到的就是我截图发消息，实际上是能识图的，结果它自己读取就不行了。

这一句把根因从「推断」变成「坐实」。同一个模型、同一个会话、同一份 `providers` store：

| 路径 | 结果 |
|---|---|
| 截图贴进输入框发消息 | **能识图** ✅ |
| 让它 Read 一个图片文件 | **拒图** ❌ |

两条路会得出相反的答案，只可能因为**它们用了两套不同的解析**。§3.2 给出对照代码 —— 这就是本 bug 的铁证。

### 2.2 三个特征

| 特征 | 说明 |
|---|---|
| **误判** | 模型实际支持图像输入，被判为不支持 |
| **静默** | 不报错、不中断，只是「像素没附上」。模型拿到一句说明继续干活，用户看不出少给了东西 |
| **「多次出现」** | 说明不是某个固定模型不对，而是判定链在某些组合下才出错。§3.2 的串号机制正是这种「看运气」 |

### 3.2 根因 A（主因）：两条路两套解析，Read 那条会跨 provider 串号

#### 对照（这就是 §2.1 那个症状的机械解释）

**贴图路径**（`components/chat/InputArea/use-input-area-selectors.ts:113-154`）—— 精确：

```ts
const providerId = fastConfig?.providerId ?? selection?.providerId ?? activeProviderId
const modelId = fastConfig?.model ?? selection?.modelId ?? activeModelId
const provider = providers.find((item: any) => item.id === providerId)   // ← 先按 provider 定位
if (!provider) return null
const model = provider.models.find((item: any) => item.id === modelId)   // ← 再在该 provider 内找
if (!model) return null
...
const supportsVision = modelSupportsVision(model, activeProvider.type)   // ← :153
```

**两层过滤**（provider.id → model.id），而且 `selection` 来自 `resolveSessionModelSelection`（`:122-126`），把 session 级选择、渠道 provider、fast 模式、auto 模式全解析过了。所以它能算对 —— **截图能识图**。

**Read 路径**（`stores/chat-store/index.ts:199-208`）—— 只有一层：

`resolveSessionSupportsVision`（`chat-store/index.ts:199-208`）：

```ts
async function resolveSessionSupportsVision(modelId: string | null): Promise<boolean> {
  if (!modelId) return true
  const { providers } = useProviderStore.getState()
  for (const provider of providers) {
    const model = provider.models?.find((item) => item.id === modelId)   // ← 只看 modelId
    if (model) return modelSupportsVision(model)                        // ← 第一个命中的赢了
  }
  return true
}
```

**它不知道这个会话用的是哪个 provider。** 只要两个 provider 有同名模型 id，取到谁全看 `providers` 数组顺序。

#### 两套解析的差异一览

| | 贴图路径 | Read 路径 |
|---|---|---|
| provider 定位 | `providers.find(p => p.id === providerId)` | **无** |
| model 定位 | 在**该** provider 的 models 里 find | 跨**所有** provider find |
| session 级解析 | `resolveSessionModelSelection`（含渠道 / fast / auto） | 无，只拿到 `workerParams.provider.model` 一个字符串 |
| 结果 | 准确 | 撞谁算谁 |

**同一个 `modelSupportsVision`（`provider-store.ts:375`），喂进去的 `model` 对象却不是同一个。** 这解释了 §2.1：截图走进上面那一列，Read 走进下面那一列。

这不是理论风险 —— 实测 `glm-5.3` 在 **4 个 provider** 里同名，而且标法有**三种**：

| provider | 文件:行 | `supportsVision` | 依据 |
|---|---|---|---|
| bigmodel（智谱官方） | `bigmodel.ts:106` | **false** | 显式写死 |
| opencode-go | `opencode-go.ts:17`（`shared`） | **false** | 显式写死 |
| workbuddy 国内版 | `workbuddy.ts:155` `toModels(CN_MODELS, () => true)` | **true** | 一律 true |
| workbuddy 国际版 | `workbuddy.ts:176` `toModels(AI_MODELS, (id) => !/^glm-/.test(id))` | **false** | 一刀切 |

⇒ **用户在 workbuddy 国内版下用 `glm-5.3`（该是 true），但 bigmodel 若也添加过且排在数组前面，拿到的是 bigmodel 那份 `false`** ⇒ Read 拒图。

这解释了「多次出现」：同一模型 id 在几个渠道间标法不一致，命中谁看运气；换模型/换渠道/调整 provider 顺序都可能让症状变。

**并且这个修复有现成钥匙**：`buildProviderPayload` 产出的 payload 里已经有 provider 身份 —— `id: provider.id`（`lib/agent/provider-payload.ts:87`）+ `providerId: provider.id`（`:94`）。`workerParams.provider` 里就带着，取用即可，无需新增字段。

`provider-payload.ts` 文件头注释（`:4-11`）恰好写明了这个设计的初衷：payload 以前在每个发送点 inline 构造，字段漏传屡次发生，所以收敛到一个构造点。**`supportsVision` 是这条收敛里漏网的一处** —— 它由 chat-store 单独盖章，绕开了那个构造点，连带把 provider 身份也丢了。

### 3.3 根因 B：workbuddy 国际版把整个 glm 系一刀切

`workbuddy.ts:64-66` 注释（原文）：

> `visionFor` 由调用方给：国际版的 GLM 系即使 `/v3/config` 写着 `supportsImages`，服务端也会把图滤掉（参考实现 `src_sites.mjs` `noImages: /^glm-/`，真账号实测），所以按 `^glm-` 标纯文本；国内版没有这条实测记录，一律按 config 的说法给 true。

问题在于国际版模型表（`workbuddy.ts:53-58`）**全部是 `glm-*`**：

```
glm-5.3 / glm-5.2 / glm-5.1 / glm-5v-turbo
```

⇒ `!/^glm-/.test(id)` 对整个国际版模型列表**全部返回 false**。其中 `glm-5v-turbo` 名字里的 `v` 就是 vision，被同一条正则连带打死。

另一头的国内版 `() => true` 是「一律放行」，与国际版「一律拒绝」都是同一类粗糙 —— 两头都没按模型实际能力分。

### 3.4 根因 C：自定义模型默认关掉视觉

`ModelFormDialog.tsx:70` `useState(false)`、`:106` `?? false`。

用户手动添加一个模型时，如果不动「支持视觉 / supportsVision」那个开关，结果就是 false。而**这个开关藏在模型编辑表单里**，用户不会有理由主动去想「我加的模型支不支持视觉」。

`ProviderModelsSection.tsx:73` 有 `if (model.supportsVision)` 的分支，说明 UI 上是有能力标记展示的 —— 但对误判这件事没有提示。

### 3.5 根因 D：`undefined` 与 `false` 被归一，与设计意图相反

`provider-store.ts:375-384`：

```ts
export function modelSupportsVision(model, providerType?): boolean {
  if (!model) return providerType === 'openai-images'
  const requestType = model.type ?? providerType
  return Boolean(
    model.supportsVision || model.category === 'image' || requestType === 'openai-images'
  )
}
```

`model.supportsVision` 是 `boolean | undefined`（`shared/types/provider.ts:289`）。**`undefined`（未标注）和 `false`（明确不支持）走同一条路。**

这与代码里三处明确的意图**直接矛盾**：

| 位置 | 原文 |
|---|---|
| `runtime/.../ToolTypes.cs:93-95` | 「默认 true = **不做降级**：拿不到模型能力信息时宁可照常送出图像块，也不要把图悄悄吞掉」 |
| `stores/chat-store/index.ts:197-198` | 「查不到模型就返回 true（**不降级**）：宁可把图送出去让上游报错，也不要静默吞掉像素让模型猜内容」 |
| `runtime/.../ToolTypes.cs:96` | `bool SupportsVision = true` |

三处都在说「不知道就放行」，唯独真正做判断的那一处是「不知道就拒绝」。**整条链的设计意图是「宁可多送」，实现在第二跳就翻转成「绝不送」。**

## 4. 修复方向

### 4.0 方向已定（老大 2026-10-27 11:21）

> 我的希望是，不确定模型到底能不能读图，可以先把图放给模型让它看，而不是通过配置就卡死了。

⇒ 主方案是**摘掉拦截**，不是「把配置改准」。

理由：配置永远追不上 —— 新模型、反代渠道、用户自定义模型、跨 provider 同名 id，每一种都能让标注失准。而这张本地表本来就不该决定「能不能看」，它最多决定「提示用户什么」。**让上游回答能不能看，比让一张会过期的表预言更可靠。**

### 4.1 要摘掉的三处拦截

| # | 位置 | 现在 | 改成 |
|---|---|---|---|
| 1 | `runtime/.../FileReadTool.cs:188` | `if (!supportsVision)` → 只回路径+尺寸 | 永远附像素 |
| 2 | `components/chat/InputArea/use-image-attachments.ts:111-114` | `supportsVision ? 收图 : []` → 图降级成文件引用 | 永远按图处理 |
| 3 | `lib/agent/visual-context.ts:364-366` | `supportsVision ? hydrate : []` | 永远 hydrate |

**摘法：渲染端不再往下传 `false`。** C# 侧 `SupportsVision` 默认值本来就是 `true`（`ToolTypes.cs:96`），`ToolDispatchRouter.cs:584` 的 `GetBool(..., true)` 也是 true —— 只要 `workerParams.supportsVision` 不再出现 `false`，第 1 处自动放行。第 2、3 处在渲染端，各拆一个三元判断。

### 4.2 档 2 定案（老大 2026-10-27 11:34：选档 2）

> 档2

即：**默认送图；上游明确说「不支持图像」时剥图重试；记住实测结果，下次不再浪费。**

#### 4.2.1 时序

```
① 请求带 image 块        → 上游 400
② 识别出「这是说图像输入不支持」   ← 保守匹配，见 4.2.3
③ 剥掉本轮所有 image 块（保留 text 段），立即重发，不让用户等
④ 重发成功 → 记住 (providerId:modelId) 不支持视觉 → 后续请求直接不带图
⑤ 重发仍失败 / 认不出是图像问题 → 正常抛错给用户看
```

#### 4.2.2 错误识别：照抄 `ToolPairingErrors` 的范式

项目里**已经有两处「专项 400 → 特殊处置」**，档 2 是第三处，不引入新范式：

| 现成范式 | 位置 | 干什么 |
|---|---|---|
| `ContextCompression.IsContextWindowExceededError` | `AgentLoop.cs:386` catch 链 | 上下文超限 → 触发压缩后重发 |
| `ToolPairingErrors.IsToolPairingError` | `AgentLoop.cs` catch 链 | 工具配对错 → 先修配对再重发 |

新增 `src/runtime/WishfulClaw.Agent/ImageInputErrors.cs`，**结构与 `ToolPairingErrors` 逐字照抄**（遍历 `InnerException` 链 + `Markers` 数组 + `Contains(OrdinalIgnoreCase)`）。

能按文案识别的前提已经具备：`ProviderHttpException` 的 Message 里**带着完整响应体**（`ProviderRetryPolicy.cs:27`）：

```cs
: base($"{providerName} request failed HTTP {(int)statusCode}: {responseBody}")
```

⇒ `Markers` 匹配的就是上游原文。

**`Markers` 候选**（实施时按真实报文补，宁缺毋滥）：

```cs
"does not support image",        // OpenAI 系常见
"image input is not supported",
"image_url is not supported",
"not a multimodal",
"does not support image input",  // Anthropic 系
"unsupported image",
"不支持图片", "不支持图像", "不支持多模态"
```

#### 4.2.3 判定必须保守 —— 这条比识别本身更重要

`ToolPairingErrors.cs:13-15` 的注释原话：

> 判定刻意保守：只认「明确在讲配对」的文案。其它 400 一律不匹配 —— 它们要继续走 `ProviderRetryPolicy` 的重试（**400 可重试是有意设计**，见 `ProviderRetryPolicy.IsRetryableStatus`），不能被这里截走。

同理，**绝不能写成「含图 + 400 就剥图重试」**：

- 会把参数错、模型不存在、配额错等 400 误判成图的问题
- 白烧一次请求（计费 + 延迟），还污染「记住」表 —— 把一个能读图的模型记成瞎的

所以：**认不出文案就退回报错**。这意味着档 2 的覆盖度受文案匹配限制，总有认不出的中转渠道 —— 那时用户看到 400 报错（明确、可查），仍好于现在静默吞图。

#### 4.2.4 剥图怎么剥（降级形态天然已有）

`FileReadTool.BuildImageContent` 产出的 content 是 **`[text(summary), image]`** 两段（`FileReadTool.cs:204`、`:320-338`），其中 `summary = "Read image: <path> (<宽x高>, <mediaType>)"`。

⇒ **剥掉 `type == "image"` 那一项，text 段还在。** 模型仍拿到「文件路径 + 尺寸 + mediaType」，信息量与现在「不支持视觉」时的降级输出一致（`FileReadTool.cs:191-192` 那条文案的形态）。

不用新造降级文案，也不用重新读文件。

#### 4.2.5 落地要改**两处**，少一处就不工作

这一点最容易漏，且漏了会表现成「文档说的没生效」。现有 tool-pairing 那条链就是两处的样板：

**第一处 · `ProviderRetryPolicy.cs:131-139` 加一条排除**

```cs
catch (ProviderHttpException ex) when (
    IsRetryableStatus(ex.StatusCode) &&
    !ContextCompression.IsContextWindowExceededError(ex) &&
    !ToolPairingErrors.IsToolPairingError(ex) &&      // ← 配对错交给 AgentLoop
    !ImageInputErrors.IsImageUnsupportedError(ex) &&  // ← 档 2 要加的就是这行
    (isUnlimited || retryAttempt < maxAttempts) &&
    !state.IsCancellationRequested)
```

为什么不加就废：`IsRetryableStatus(400)` 返回 **true**（注释明说「400 可重试是有意设计」），所以图像 400 现在会被 provider 层原样重试 N 次 —— 每次都带同一批图，每次都 400，纯烧钱烧延迟，最后才抛给上层。

`ProviderRetryPolicy.cs:134-136` 那段注释把道理写透了，逐字适用于档 2：

> 配对错不走这里：会话数据一个字没变，重试只会拿到同一个 400，白白烧掉几次往返。它交给 `AgentLoop` 的错误驱动分支 —— 先修配对，再重发同一请求，那一次重试才是有意义的。

**第二处 · `AgentLoop.cs:372` 外面加一条 catch 分支**

现有 catch 链已管 context-window（`:386`）和 tool-pairing（`:426`），档 2 在同一个位置加第三条，改 `conversation` / `wireConversation` 两个 list（剥 image 块）后 `continue` 重发。

为什么剥完能生效：`ExecuteAsync` 收的是 **delegate**（`ProviderRetryPolicy.cs:80-84`），每次重试都重新 `await execute()`，请求体按当时的 `conversation` 重新构造 ⇒ **剥完图再进循环，发出去的就是无图版本**。

#### 4.2.6 「记住」存哪

| 方案 | 评价 |
|---|---|
| **A. C# 进程内字典 + 本地持久化**（`ConcurrentDictionary<string,bool>`，key `providerId:modelId`，落一个轻量 json） | **推荐**。判定发生在 C#，记忆就放 C#，不引入跨端回写竞态。渲染端只读展示 |
| B. 回写到用户模型配置（`supportsVision = false`） | 用户看得见、能改；但**误判会改坏用户配置**，且要跨端事件往返。建议只做「提示」，不自动改 |

推荐 A + 渲染端一条只读提示：「该模型经实测不支持图像输入（日期）」。用户不信可手动改配置覆盖。

#### 4.2.7 与「不靠配置卡死」的关系（§4.0 那条方向的落脚点）

档 2 的「记住」**不是**回到配置预判 —— 区别在于：

| | 现在的配置 | 档 2 的记忆 |
|---|---|---|
| 来源 | 预设表 / 用户手填 | **真实请求撞出来的结果** |
| 首次行为 | 直接拒，不给模型看的机会 | **先给模型看** |
| 出错时 | 静默吞图 | 剥图重试，用户仍拿到回答 |

一句话：**配置不许替模型说「你不行」，只有上游真的说了才算。**

### 4.3 顺带修正：Read 的解析对齐贴图路径

**摘掉拦截后这条不再是「主修复」** —— 它不再决定 Read 能不能读图。但它仍要让 UI 说真话：

| 消费方 | 用途 |
|---|---|
| `components/chat/ModelSwitcher/model-info.tsx:27` | 模型信息里的视觉徽章 |
| `components/chat/InputArea/composer-editor-area.tsx:158` | 占位文案（「拖入图片」/「拖入文件」） |
| `components/chat/InputArea/use-input-area-selectors.ts:150-154` | 摘掉拦截后只剩提示用途 |

这些还在读 `modelSupportsVision`，而 `resolveSessionSupportsVision` 的串号问题会让**徽章显示与实际不符**（比如贴图能送，徽章却说不支持）。

修法：`workerParams.provider.id` / `.providerId` 已在 payload 里（`provider-payload.ts:87,94`），按它过滤即可；或更彻底 —— 直接复用贴图路径的 `resolveSessionModelSelection`，把第二套解析消灭掉。

### 4.4 原 B / C / D 在新方向下的去留

| 原方案 | 新方向下 |
|---|---|
| **B** 区分三态（`undefined` ≠ `false`） | **降为可选**。拦截摘掉后，未标注怎么处理不再影响功能，只影响徽章文案。不急 |
| **C** `ModelFormDialog` 默认值 | **仍建议做**。默认 `false` 会让用户以为模型不支持；改成「未标注」或按 id 特征预猜（`vision` / `-v` / `-vl` / `omni`） |
| **D** workbuddy `visionFor` 别一刀切 | **意义变了**：摘掉拦截后它不影响读图，只影响徽章。若 §8 🅲 确认「国际版服务端真会滤图」，那徽章标 false 反而是**对的**，D 不该改 |

## 5. 验收判据（无需改代码即可验）

| # | 场景 | 期望 |
|---|---|---|
| 1 | 截图贴进输入框发消息 → 让它描述图 | **能识图**。这是现状，作为回归基线：改完不许退化 |
| 2 | 让它 Read 一个 png | **能识图**，不再出现「not marked as vision-capable」 |
| 3 | 同一会话里先贴图、再让它 Read 同目录另一张图 | **两条路结论一致**，不再出现「贴图能看、Read 不能」。这条直接验 §3.2 的两套解析 |
| 4 | 同时添加 bigmodel 与 workbuddy，两边都有 `glm-5.3` → Read 图 | 仍能识图（不再受 provider 数组顺序影响） |
| 5 | 换真不支持视觉的纯文本模型 → 贴图 / Read | **自动剥图重试成功**，用户拿到回答，不看到 400；渲染端出现「该模型经实测不支持图像输入」提示 |
| 6 | 视频分支（`FileReadTool.cs:225-229`） | 与图片分支同一套逻辑 |
| 7 | 模型信息里的视觉徽章（若做 §4.3） | 与「实际能不能收图」一致，不再说假话 |
| 8 | 判据 5 撞过一次后，同一模型再贴图 | **不再发图**（记忆生效），无第二次 400 往返 |
| 9 | 把能读图的模型人为配成「不支持视觉」，再让它 Read 图 | **照常读图**（配置不再拦人），验「配置不许替模型说不行」 |
| 10 | 上游回一个与图像无关的 400（如模型 id 写错） | **不许**被 `ImageInputErrors` 截走；仍走原有重试 / 报错路径。验 §4.2.3 的保守判定 |

判据 8 / 10 是档 2 的两个关键防退化点：8 验「记忆真生效」，10 验「没把别的 400 误吞」。

## 6. 明确不在本需求内

| 项 | 为什么 |
|---|---|
| 删掉 `supportsVision` 配置字段本身 | 它仍要留着给 UI 徽章、也给用户手动覆盖档 2 的实测记忆。本需求只摘「它拦人」的那三处判断，不删字段 |
| 视觉能力自动探测（主动发测试图试上游） | 计费 + 可能被判定异常，不做。**注意与档 2 的区别**：档 2 是「被动撞上错误再降级」，不是主动探测 |
| 让模型自己声明能不能看图 | 拿不到图像时无法自证，无意义 |
| `visual-context.ts` 的注入策略（什么时候该补历史图） | 那是 `shouldInjectVisualContext` 的事，本需求只摘掉它上面那道 `supportsVision` 闸 |
