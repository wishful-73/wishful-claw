## 一、这条需求真正要回答什么

老大看到的是一次**成功案例**：Astra Gate 从 Electron 迁到 Avalonia，内存 350 MB → 50 MB。想知道我们该不该也走这条路。

**但两个产品的形态差得太远，不能直接照搬结论。** 这份需求单的任务是把这个差距量出来，产出一份**带成本估算的评估报告**，让老大能拍板「迁 / 不迁 / 只迁一部分」，而不是凭一个别人的数字下决定。

**产出物是一份报告 + 一个可运行原型。** 评估完可能结论是「不迁」，那也是有效产出 —— 但原型必须真跑起来量出数字，不能只有推算。

## 二、参考对象：Astra Gate 是什么

`https://astra-gate.si/` —— **AIDotNet**（就是 OpenCowork / NextCoWork 的作者）的本地 AI 网关。MIT 开源，仓库 `239573049/Astra-Gate`。

它做的事：在 `127.0.0.1:17321` 起一个本机中转，把 OpenAI Chat / OpenAI Responses / Anthropic Messages / Gemini 四种协议解码成中间表示再重新编码，顺手做用量统计、费用入账、隐私护栏（密钥/邮箱/内网地址检测）。

**关键点：它的 UI 面很窄。** 官网原话「浏览器或桌面端打开，同一套液态玻璃界面」—— 控制台就是**概览、客户端开关、服务商配置、用量图表**这几页。没有聊天窗、没有 markdown 流式渲染、没有工具调用卡片、没有内置浏览器。

**这正是它能迁成功的前提。** 350 MB → 50 MB 的收益，是在「UI 复杂度接近零」的前提下拿到的。

## 三、我们的现状（2026-10-31 实测）

| 项 | 事实 |
|---|---|
| 桌面壳 | Electron `^43.2.0` + `electron-vite ^2.3.0` |
| 渲染层 | React，**874 个 `.ts` / `.tsx` 文件** |
| 主进程 | Node（`src/main`，含 IPC、协议注册、文件系统、渠道、更新器） |
| 预加载 | `src/preload`（IPC 桥） |
| 业务后端 | **C# / .NET worker，740 个 `.cs` 文件**（`src/runtime/WishfulClaw.sln`） |
| 内置浏览器 | **Electron `<webview>`**（Chromium 内核 + partition 隔离 + CDP 控制） |

**注意我们已经不是「纯 Electron 应用」** —— 业务逻辑本来就在 .NET worker 里，Electron 壳负责的是**窗口 + 渲染 + IPC + 浏览器宿主**。

这一点很重要：**迁移的收益空间比 Astra Gate 小，成本却比它大。** Astra Gate 迁完省掉的是「一整个 Node 后端 + Electron 壳」；我们迁完只省掉「Electron 壳」，.NET worker 本来就在。

## 四、四个硬约束（决定成本量级）

### 4.1 内置浏览器 —— 最大的拦路虎

我们用 Electron `<webview>`，agent 通过它做导航、截图、元素树抓取、执行脚本。这依赖 Chromium 的完整能力和 CDP。

Avalonia 侧的替代只有 **WebView2**（Windows）/ **WKWebView**（macOS）：
- WebView2 需要目标机安装 Edge WebView2 Runtime（Win10 早期版本可能没有）
- **CDP 控制能力不等价** —— Electron webview 暴露的调试协议、`session` / `partition` 隔离、`webContents` API 在 WebView2 上是另一套模型
- macOS 用 WKWebView 又是第三套 API ⇒ **跨平台要维护两套浏览器控制层**

`S-215`（浏览器工具）、`S-290`（截图经能力代理）、`S-294`（截图卡片）这一整条链都建立在现有 webview 语义上。

### 4.2 渲染层 874 个文件要重写

React + Tailwind + shadcn/Radix 的整套组件，在 Avalonia 里没有对等物。XAML 要重写：
- 流式 markdown 渲染（含代码块高亮、表格、mermaid）
- 工具调用卡片（几十种形状，`tool-block-renderer.tsx` 是路由中枢）
- 虚拟滚动消息列表（`useMessageListScroll.ts`，S-233 抖动问题还挂在那）
- 设置页、右侧面板、文件搜索、用量图表、i18n

**这不是「移植」，是「重做一遍」。**

### 4.3 内存问题的真因还没定

**这一点必须先说清楚，否则整个评估的前提是虚的。**

2026-10-31 实测（dev 库、真实会话）：

| 指标 | 数值 |
|---|---|
| JS 堆（稳定态） | **159 MB** |
| 消息数据总量（content + segments + toolCalls + meta） | **1.0 MB** |
| DOM 节点 | 1416，稳定 |
| 渲染进程工作集 | **1377 MB**，峰值 **2603 MB** |

**JS 堆 159 MB、数据 1 MB、DOM 稳定，而工作集 1.3 GB** —— 差的那 1.2 GB 在 JS 堆之外，最可能是**图片位图**（库里该会话 8 张 2520×1680 截图，满打满算 135 MB，除非被反复解码）。

**⇒ 也就是说，我们现在看到的 1.3 GB 很可能不是「Electron 的固有开销」，而是一个可以修的缺陷。** 在 S-247 把这条查清之前，拿 1.3 GB 去论证「必须迁 Avalonia」是不成立的。

**Astra Gate 的 350 MB 是「简单 UI 的 Electron 基线」，我们的 1.3 GB 是「简单 UI 基线 + 一个待修缺陷」。两者不可比。**

### 4.4 开发期与发布链全部要重做

`electron-vite`、`electron-builder`、增量更新（`blockmap` / `latest.yml`）、`oc-media://` 自定义协议、单实例锁、更新器、证书签名 —— 这一整套在 Avalonia 侧要换成另一套（MSIX / Velopack / 自研），**发布流程文档要重写一遍**。

## 五、研究要回答的问题（报告大纲）

评估报告按这七条组织，每条都要给数据和结论：

1. **Astra Gate 的 50 MB 是怎么来的** —— 读它的源码与提交记录，确认省掉的是什么（Node 后端？Chromium 渲染进程？还是 UI 本身简单）。
2. **我们的 1.3 GB 到底是不是 Electron 的锅** —— 依赖 S-247 结论。若 S-247 修完降到 300 MB 量级，迁移的内存收益就要重算。
3. **Avalonia 侧能拿到的最低内存是多少** —— 做一个**最小可运行原型**（一个窗口 + 流式文本 + 一张图），实测常驻内存。不猜，量。
4. **内置浏览器的替代方案可行性** —— WebView2 在 Avalonia 里的 CDP/截图/元素树能力实测，对比现有 `<webview>`。
5. **渲染层重写的真实工作量** —— 按模块清点 874 个文件，给出人日估算（不要拍脑袋，按功能块拆）。
6. **双轨并行的代价** —— 老大说「electron 和 avalonia 都试一下」，要评估两套壳同时维护的成本，以及能否共用一个渲染层（例如 Avalonia 里嵌 WebView2 跑现有 React —— 那样省的是壳，不是渲染层）。
7. **明确的建议** —— 迁 / 不迁 / 只迁某部分，给理由和代价。

## 六、值得单独看的一条中间路线

**「Avalonia 壳 + WebView2 跑现有 React 渲染层」** —— 这条路线省掉 Electron 主进程和 Chromium 打包体积，但保留 874 个文件的 React 代码不重写。

**它的可行性取决于 §4.1 和 §4.3**：如果内存大头是 Chromium 渲染进程本身（而不是 Electron 的 Node 侧），那换壳也省不掉，这条路线直接出局；反之它可能是性价比最高的选择。

**报告必须单独回答这条。**

## 七、我的初步判断（写在这里供老大参考，不是结论）

**倾向：不建议整体迁移，但值得做 §五 的评估。**

理由三条：

1. **收益空间小** —— 业务逻辑已在 .NET worker，Electron 壳省掉的那部分，不是我们内存的大头。
2. **成本极大** —— 874 个渲染层文件 + 内置浏览器 + 整条发布链，周期按季度算，期间不能正常发版。
3. **前提未证实** —— 1.3 GB 很可能是 S-247 那个待修缺陷，不是 Electron 的固有开销。**先把 S-247 修完，再谈要不要迁。**

**如果 S-247 修完仍在 500 MB 以上且确实影响使用，那 §六 那条中间路线值得认真做原型。**

## 八、明确不做的事

- **不动主仓任何现有代码。** 原型放 §九 那个独立文件夹，**不接进 `electron-vite` / 任何 `.sln` / `ci-checks`**，现有构建与门禁的行为必须零变化。
- **不因为 Astra Gate 一个案例就下结论。** 它的 UI 复杂度跟我们没有可比性。
- **不承诺迁移。** 评估结论允许是「不迁」。
- **不动 S-247 的排查节奏。** 那条已收口（「每帧重做」，非泄漏），评估直接引用其结论。

### 10.2 原型落点与实现

`experiments/avalonia-shell/`，独立 `.csproj`，目标框架 **net10.0**（本机稳定版；不依赖仓库的 net11.0-preview，原型不该建在预览 SDK 上）。Avalonia 11.3.2。

| 文件 | 作用 |
|---|---|
| `Program.cs` | 入口；`--software` 切软件渲染 |
| `ProbeOptions.cs` | `--stage empty\|text\|image` / `--seconds` / `--report` / `--width` / `--height` |
| `MainWindow.axaml(.cs)` | 一个窗口 + 三态内容（空 / 流式追加文本 / 2520×1680 图） |
| `MemoryProbe.cs` | 每秒采样工作集 / 私有字节 / GC 托管堆 / 线程 / 句柄；稳态取最后三分之一的中位数 |
| `ScreenshotFixture.cs` | 手写 PNG 编码生成 2520×1680 测试图（不往仓库塞 12 MB 图片，也不引 `System.Drawing`） |

`.gitignore` 只排除它的 `bin/` `obj/` `publish-aot/` `.probe/`，源码入库。

### 10.3 实测结果（本机，1440×900，每阶段 12 秒）

**空窗口**是这条需求的唯一关键数：

| 口径 | 工作集 | 私有字节 |
|---|---|---|
| Debug，框架依赖，GPU | 197.7 MB | 132.6 MB |
| Release，框架依赖，GPU | 187.4 MB | 128.7 MB |
| Release，NativeAOT，GPU | 156.2 MB | 122.6 MB |
| Release，框架依赖，软件渲染 | **96.9 MB** | **43.7 MB** |

加内容后的增量：流式文本 +32 MB（400 行上限、每 40 ms 一行）；一张 2520×1680 图 +14 MB。

### 10.4 结论

**Astra Gate 的 50 MB 能复现 —— 但只在「软件渲染 + 私有字节」这一种口径下（43.7 MB）。** 换到「GPU 加速 + 工作集」，同一份代码是 187 MB。

而 S-247 已实测：我们 Electron 生产构建的 renderer 稳态高水位是 **150~200 MB**，跑完能还 311 MB。**Avalonia 空壳的 156~187 MB 与它同量级** —— 也就是说，874 个渲染层文件重写成 XAML 之后，内存最乐观是持平。

⇒ **不建议迁移。** §六 那条中间路线（Avalonia 壳 + WebView2）同样不划算：WebView2 内核就是 Chromium，内存与 Electron renderer 同量级，还要重写一整套 IPC 与浏览器控制层。

**这条需求的结论是「不迁」，且是量出来的，不是推算的。** 评估报告不再单独出文件 —— §十 就是结论，`experiments/avalonia-shell/README.md` 是完整数据与复现步骤。
