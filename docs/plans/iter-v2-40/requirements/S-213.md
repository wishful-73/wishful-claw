# S-213：钉钉渠道入站图片 —— 只解 `text.content`，图片消息连占位符都没有，整条被丢弃

> 状态：**已登记，待开工**（2026-10-20 老大登记，iter-v2-40）。
> 类型：**bug**（能力缺失，且比 QQ 更彻底：消息整个消失）。
> 归属：**iter-v2-40**。S-211 的渠道拆分项。
> 来源：**老大 2026-10-20 10:07 / 10:10** —— 渠道入站图片不保留，所有渠道都要。
> 轨道：**软件侧**（钉钉渠道主进程）。

---

## 一、现象

钉钉渠道收到图片 / 文件 / 富媒体消息，**聊天窗里什么都不会出现** —— 不是占位符，是整条消息被丢弃。

## 二、根因

### 2.1 解析只认 text

`dingtalk-service.ts:160-178`：

```ts
const parsed = JSON.parse(payload.text?.content ?? '{}')   // 只解 text
content = parsed.content ?? payload.text.content
...
content = content.trim()
if (!content) return                                       // ← 空就直接丢
```

图片消息（钉钉 Stream 回调里 `msgtype = 'picture'`）的载荷不在 `text.content` 里，而在：

- 新版：`msgtype: 'picture'` + `content: { downloadCode: '...' }`
- 老版：`msgtype: 'picture'` + `text.content: '{"downloadCode":"...","pictureDownloadCode":"..."}'`

**`msgtype` 在整个钉钉 provider 里从来没被读过**（`Select-String msgtype` 只有发送侧的 `:234`）。所以图片消息解析出空串 ⇒ `:178` `if (!content) return` ⇒ **静默丢弃**。

### 2.2 下载 API 完全没有

钉钉拿媒体要走 `POST https://api.dingtalk.com/v1.0/robot/messageFiles/download`（带 `downloadCode` + `robotCode`），返回一个临时下载地址再 GET。`dingtalk-api.ts`（270 行）里没有任何媒体相关方法 —— 只有发送。**与微信 / 飞书的差距就在这里。**

## 三、修法

### 3.1 解析层：认 `msgtype`，非文本消息也要产出消息

`dingtalk-service.ts:160-178` 改成按 `msgtype` 分派：

| `msgtype` | 处理 |
| --- | --- |
| `text` | 现状不变（含 @提及剥离） |
| `picture` | 取 `downloadCode`（`content.downloadCode` 优先，兜底解析 `text.content` 里的 `downloadCode`）⇒ 填占位符 `[User sent an image]` + `mediaRefs: [{ downloadCode, kind:'image' }]` |
| `file` | `fileName` + `downloadCode` ⇒ `[File: name]` + `mediaRefs: [{ kind:'file' }]` |
| `voice` | 现状钉钉语音是否已转文字需确认；未转则占位符 + `mediaRefs` |
| `richText` | 取文本段，图片段按 `picture` 处理 |
| 其它 | 占位符 `[User sent an attachment]`，**不再静默丢弃** |

`:178` 的 `if (!content) return` 必须挪到「所有已知类型都处理完」之后，只拦真正空的消息。

### 3.2 服务层：加下载

`dingtalk-api.ts` 新增：

```ts
async downloadMedia(downloadCode: string, robotCode: string): Promise<{
  buffer: Buffer; mediaType?: string; fileName?: string
}>
```

两步：①`v1.0/robot/messageFiles/download` 取 `downloadUrl` ②GET 拿字节。服务层照 `weixin-service.ts:390-414` 的形状转 base64 塞 `images`，失败保留占位符 + 追加 `download failed` 文案。

### 3.3 复用 S-211

`images` 填好后，渲染端消费由 **S-211** 统一负责。**本条不碰渲染端、不碰 `auto-reply.ts`。**

## 四、非目标

- **不改钉钉发送侧**（卡片流式发送等保持原样）。
- **不做历史回补**（`downloadCode` 有时效，早失效）。
- **不动 15 分钟陈旧过滤**（`:182-186`），那是另一条规则。

## 五、待确认

1. **钉钉应用是否必须申请媒体下载权限**（`qyapi` 时代要，新版 robot 接口一般随机器人凭证可下载）。**实施前先用手上的凭证实测一次 download 接口**，通了再写代码 —— 别写完发现权限没开。
2. **`robotCode` 来源**：`payload.chatbotRobotCode` / 实例配置里的 `robotCode` 哪个为准，实测确认。
3. **语音消息**：钉钉语音是否已自带文字（`recognition` 字段）。有文字就用文字，没有再下载音频。

## 七、风险

- **静默丢弃是真 bug 不只是图片问题**：任何非文本消息（文件、卡片、语音、富文本）今天都消失。修法必须保证「未知类型也产出占位符」，否则换个类型还是同样现象。
- **下载权限未开**会让整条链路停在第一步，必须先实测再实施（§五.1）。
- **`downloadCode` 时效**：必须 emit 前即时下载，不能排队延后。
