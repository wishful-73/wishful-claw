## 一、事实

同一个会话（当天 00:50 开始用，17:31 最后一条）：

| 指标 | 实测 |
|---|---|
| `session_compaction_snapshots` 快照数 | **21** |
| `messages` 表里压缩摘要卡 | **20**（`role=user` + `meta.compactSummary`） |
| 对应压缩边界 | **20**（`role=system`，内容空） |
| 压缩卡占全部消息 | 20 / 141 ≈ **14%** |
| 29 日最后一小时的压缩 | 16:40~17:31 共 **9 次** |

每次压缩都往 `messages` **插一对新行**（边界 + 摘要），**旧的从不删除**。渲染端 `renderable-chat-items.ts:255-395` 把每一对渲染成一张折叠卡（标题「任务暂告一段落」）。

跑一天的会话 = 20 张卡；跑一周呢。

## 二、这不是「设计如此」的那部分

- wire 侧**是对的**：`TailStart` 遇到旧摘要一律折进折叠区（`ContextCompression.cs:565-569`，「one-summary invariant」），所以**发给模型的上下文里只有一份摘要**。
- 错的是**持久化与渲染**：每次压缩都往 UI 的消息流里追加一张卡，且没有任何清理策略。

也就是说：模型看到 1 份摘要，用户看到 20 张卡。

## 三、为什么以前不是问题

S-95 之前摘要只活在 wire，不落 `messages`。S-208（2026-10-20）把压缩时刻/用户消息时刻/进度都写进 `meta`，卡片才成为「有内容的可渲染对象」。以前压缩偶发（一天 1~2 次），现在被 **S-275** 变成循环，问题才显形。

## 四、待拍板的口径（三种，互斥）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A · 只留最近一对** | 新压缩落库时，把上一对卡的可见性标记为「已被吸收」（不删行，加 `superseded_by`），渲染端只展开最新一对，旧的合并成一行「先前还有 N 次压缩」 | 历史可溯、渲染干净 | 要加字段（schema 迁移） |
| **B · 删旧行** | 新压缩落库时删掉上一对 `messages` 行 | 不改 schema | **破坏溯源**，快照表还在但消息流断了，且删行会动 `sort_order` 与分页游标 |
| **C · 不动数据，渲染端合并** | 库里照旧攒，渲染时把连续 N 张卡压成一张「压缩 N 次」 | 零迁移、纯渲染层 | 窗口仍被卡占名额（S-276 的根），且分页边界更绕 |

**我的建议是 A**，但它需要加列 —— 而 **S-276 §七-2 也正好需要加 `is_artifact` 列**。两条一起做，一次迁移解决两个判据，比现在用 `meta LIKE '%compactSummary%'` 扫 JSON 干净得多。

如果老大不想现在动 schema，**退一步做 C**，等 v3-iter-6 再上列。

## 五、不做什么

- **不删 `session_compaction_snapshots`** —— 那是完整回溯（含每次压缩前的原始 wire），是排查这类问题的唯一证据链。本条只动 `messages` 里的展示行。
- **不改压缩触发阈值** —— 那是 S-275 的活。

## 六、验收方式

不是真机截图，是**数据层断言**：让一个会话连续触发 5 次压缩，检查
1. `messages` 里可见摘要卡 ≤ 2（A 方案）或渲染出来的卡 ≤ 2（C 方案）；
2. `session_compaction_snapshots` 仍是 5 条（溯源不丢）；
3. wire 里仍只有 1 份摘要（不能把 one-summary invariant 弄坏）。

### 7.0 先解决一个矛盾：S-276 当时否决了加列

S-276 实施时明确选了「走 `meta LIKE`，**不加** `is_artifact` 列」，理由写在 `DbMessageToolsQueries.cs:28`：

> 走 `meta LIKE` 而不是加 `is_artifact` 列：加列要迁移旧库，收益不抵风险

**S-277 要推翻这条结论，得说清为什么这次划算：**

| | S-276 当时的场景 | S-277 的场景 |
|---|---|---|
| 要加几列 | 1 列（`is_artifact`），只为区分「是不是压缩卡」 | 2 列（`is_artifact` + `superseded_by`），既要区分身份，又要标记「已被后续压缩吸收」 |
| 判据能替代吗 | 能 —— `meta LIKE '%compactSummary%'` 已经够用，加列只是「更干净」 | **不能** —— `superseded_by` 是新语义，`meta` 里根本没有这个信息，不落列就只能每次压缩时回写整条 `meta`（又是 S-285 那个 14 MB 覆盖写的老问题） |
| 老数据 | 不用回填也能工作 | **必须回填**，否则现存 20 张卡全是 `is_artifact = 0`，A 方案直接失效 |
| 收益 | 判据从「扫 JSON」变成「查列」 | 同上，且换来 `superseded_by` 这个**新能力**，不是单纯优化 |

**结论：S-276 的「收益不抵风险」在它那个只有 1 列的场景成立；本条要 2 列且第二列是新语义，风险已经绕不开。** 该推翻，但要在 `DbMessageToolsQueries.cs:28` 那条注释上同步改口径，不能留一句和代码相反的注释。

### 7.1 改哪几列

`messages` 表新增两列（现有结构见 `DbClient.Schema.cs:62-71`，实测无索引）：

| 列 | 类型 | 默认值 | 用途 |
|---|---|---|---|
| `is_artifact` | `INTEGER NOT NULL DEFAULT 0` | `0` | `1` = 这是压缩产物（边界行与摘要卡），不是真实用户/助手消息 |
| `superseded_by` | `TEXT` | `NULL` | 产生该卡的那次压缩的 `snapshot_id`。**可见性判据 = `NULL` 或等于本会话最新 `snapshot_id`**（详见 §7.3.5 语义修正） |

**`is_artifact` 是常量默认值** —— SQLite 的 `ALTER TABLE ADD COLUMN` 对 `NOT NULL DEFAULT <常量>` 是支持的，不需要重建表。`superseded_by` 可空，更没限制。

### 7.2 索引 —— 不加

| 候选 | 结论 |
|---|---|
| `ix_messages_is_artifact` | **不加**。基数只有 0/1 两个值，索引选择性极差，SQLite 大概率直接忽略它走全表扫 |
| `ix_messages_superseded_by` | **不加**。查询模式是「按 session 取窗口内的消息」，不是「按 snapshot_id 反查」，没有等值查询需求 |
| 顺带：`ix_messages_session_sort` | **本条不加**。`messages` 至今零索引是既有债（首屏 `turns: 5` 靠 `session_id` + `sort_order` 全表扫），但加索引是性能优化，不是本条要解决的数据累积问题 —— 混进来会扩大回滚面 |

#### 7.3.0 探针实测：为什么不能靠 `created_at` 关联

| # | 实测 | 结果 |
|---|---|---|
| 1 | `sqlite_version()` | **3.53.3** —— JSON1 编译进来了 |
| 2 | `json_extract('{"a":7}','$.a')` | `7` |
| 3 | `json_extract('[{"id":"cb-x"},{"id":"cs-y"}]','$[0].id')` | `cb-x`（数组下标可用） |
| 4 | `json_extract(NULL,'$[0].id')` | 空，**不抛异常** |
| 5 | 子查询 `json_extract(compact_artifacts,'$[0].id') = messages.id` 做 JOIN | 4 条 link 全中 |
| 6 | 同形状 `UPDATE ... SET superseded_by = (子查询)` | touched 2 行，符合预期 |

**关键结论：`created_at` 不能当关联键。** 快照表的 `created_at` 写入值是 `Math.Max(now, boundary.CreatedAt + 1)`，而摘要卡的 `createdAt` 是 `compactedAt` —— **两者本来就不相等**，还带一个「至少 +1 秒」的偏移。按 `created_at` 配对必然配错或配空。

**改按 `session_compaction_snapshots.compact_artifacts` 里的卡 id 精确关联**（JSON 形状 `[{"id":"<boundary>"},{"id":"<summary>"}]`）。探针第 5 条证明这条路通，且是精确等值，不依赖时间。

#### 7.3.1 回填四步（顺序不许变）

顺序固定：**断列存在 → 标 artifact → 标 superseded → 计数比对**。任何一步失败即整体 `ROLLBACK`，不留半成品。

```sql
-- 步骤 0：前置断言 —— 两列必须都在。缺一列说明补列迁移没跑成功，
-- 此时继续执行就是往不存在的列里写，直接 return 不执行后续任何一条。
SELECT COUNT(*) FROM pragma_table_info('messages')
WHERE name IN ('is_artifact', 'superseded_by');
-- 结果必须 = 2。!= 2 ⇒ 记日志 + 直接 return（不抛，不让启动失败）
```

```sql
-- 步骤 1a：标记摘要卡
-- 判据与 DbMessageToolsQueries.cs:35 完全一致，不许另立标准（S-276 四处判据各写各的教训）
UPDATE messages
SET is_artifact = 1
WHERE role = 'user'
  AND meta IS NOT NULL
  AND meta LIKE '%compactSummary%';
```

```sql
-- 步骤 1b：标记边界行（与 1a 成对，必须一起标）
-- 只标 1a 不标 1b ⇒ 一对卡只标一半，渲染端合并逻辑错位
UPDATE messages
SET is_artifact = 1
WHERE role = 'system'
  AND content = ''
  AND meta IS NOT NULL
  AND meta LIKE '%compactBoundary%';
```

```sql
-- 步骤 2：把「已被后续压缩吸收」的卡标上 snapshot_id
--
-- 关联键 = compact_artifacts 里的卡 id（精确等值），不是 created_at（见 §7.3.0）
-- 排除项 = 每个会话「当前可见的那一对」= 该会话最新快照所包含的两个 id
--   「最新快照」的三级 tie-break：created_at DESC → version DESC → snapshot_id ASC
--   最后一级是主键，保证同 created_at 同 version 时结果唯一确定，不随行序漂
UPDATE messages
SET superseded_by = (
    SELECT s.snapshot_id
    FROM session_compaction_snapshots s
    WHERE s.session_id = messages.session_id
      AND (json_extract(s.compact_artifacts, '$[0].id') = messages.id
        OR json_extract(s.compact_artifacts, '$[1].id') = messages.id)
    ORDER BY s.created_at DESC, s.version DESC, s.snapshot_id ASC
    LIMIT 1
)
WHERE is_artifact = 1
  AND id NOT IN (
      SELECT json_extract(s2.compact_artifacts, '$[0].id')
      FROM session_compaction_snapshots s2
      WHERE s2.snapshot_id = (
          SELECT s3.snapshot_id FROM session_compaction_snapshots s3
          WHERE s3.session_id = s2.session_id
          ORDER BY s3.created_at DESC, s3.version DESC, s3.snapshot_id ASC
          LIMIT 1)
      UNION
      SELECT json_extract(s2.compact_artifacts, '$[1].id')
      FROM session_compaction_snapshots s2
      WHERE s2.snapshot_id = (
          SELECT s3.snapshot_id FROM session_compaction_snapshots s3
          WHERE s3.session_id = s2.session_id
          ORDER BY s3.created_at DESC, s3.version DESC, s3.snapshot_id ASC
          LIMIT 1)
  );
```

```sql
-- 步骤 3：计数比对，不符即 ROLLBACK
-- 期望值 = 步骤 1a 命中数 + 步骤 1b 命中数（执行前先各自 SELECT COUNT(*) 记下来）
SELECT COUNT(*) FROM messages WHERE is_artifact = 1;
-- 另查：每个会话 superseded_by IS NULL 的卡必须恰好 2 行（1 对）
-- 老库里没有快照的会话会全部保持 NULL —— 这是设计内的保守行为，见下
SELECT session_id, COUNT(*) FROM messages
WHERE is_artifact = 1 AND superseded_by IS NULL
GROUP BY session_id;
```

#### 7.3.2 三条边界规则（写死，实施时不许自行放宽）

| 场景 | 行为 | 理由 |
|---|---|---|
| 会话有卡、但**没有任何快照**（快照被删 / 老数据早于快照机制） | 步骤 2 的子查询取不到 `snapshot_id` ⇒ 全部保持 `NULL` ⇒ 渲染端照旧全显示 | §7.5「宁可多显示一张卡，不许写悬空值」。少隐藏是显示冗余，误隐藏是真话消失 |
| 同一 `created_at` 撞车 | 三级 tie-break 的 `snapshot_id ASC` 兜底，结果唯一 | 回填是不可逆写操作，结果必须确定性 |
| 快照的 `compact_artifacts` 不是合法 JSON | `json_extract` 返回 `NULL`（探针 #4 已证不抛）⇒ 该快照配不上任何卡 ⇒ 相关卡保持 `NULL` | 不因为一条脏快照炸掉整次迁移 |

#### 7.3.3 幂等性

四条 SQL 全部是 `UPDATE ... SET <常量>` 或 `SET ... = (确定性子查询)`，**跑第二遍结果完全一致**：

- 1a / 1b：已 `= 1` 的行再 `SET 1`，无变化
- 2：已 `= 'snapX'` 的行，子查询重算仍是 `'snapX'`（tie-break 确定）⇒ 无变化
- 无需 `WHERE is_artifact = 0` 之类的一次性开关 —— **但要在迁移里记一个 `PRAGMA user_version` 或等价的已跑标记**，避免每次启动白扫全表（20 张卡的库无所谓，将来几万行的库就有所谓了）

**步骤 1 的判据必须复用 `DbMessageToolsQueries.cs:35` 那一句，不许重写。** 两处判据各写各的正是 S-276 栽过的坑。

#### 7.3.5 完整 SQL 实测结果 + 一处语义修正

上面四条 SQL **逐字**跑过一遍（真 `Microsoft.Data.Sqlite`、`:memory:`、真实列形状含 `version`），不是推演：

| 检查项 | 实测 | 结论 |
|---|---|---|
| 步骤 1a 命中 | 6（5 张 s1 摘要卡 + 1 张 s2 摘要卡） | ✓ |
| 步骤 1b 命中 | 6（5 条 s1 边界行 + 1 条 s2 边界行） | ✓ |
| 步骤 2 命中 | 10 | ✓ |
| 5 次压缩的会话 | 前 8 行有 `snapshot_id`，最后 2 行 `NULL` | ✓ 只剩最新一对可见 |
| **无快照的会话**（模拟快照被删） | 两行全 `NULL` | ✓ 保守行为，全部照旧显示 |
| **污染探针**（真实用户消息 `content` 含 `compactSummary` 字样、`meta` 为 NULL） | `is_artifact = 0` | ✓ 回填范围没写宽 |
| 幂等（四条 SQL 跑第二遍） | 全表 `id:superseded_by` 串**逐字相同** | ✓ |
| tie-break（两快照 `created_at` 与 `version` 全相同） | 结果唯一，`snapshot_id ASC` 兜底 | ✓ 确定性成立 |

**语义修正（探针跑出来才看见的）：**

`superseded_by` 这个列名读起来像「被谁吸收」，但步骤 2 的 `SET` 子查询里带 `json_extract(...) = messages.id` 过滤，实际存进去的是**这张卡自己所属的那次压缩**。举例：`s3-b1` 属于 `snapZ`，它被标成 `superseded_by = 'snapZ'` —— 不是「吸收它的那个快照」，是「产生它的那个快照」。

**功能上不影响**（非 NULL 且不等于最新 ⇒ 不可见；NULL ⇒ 可见），但**读判据必须按下面这条写，不能写成「非 NULL 即不可见」**：

```sql
-- 渲染端 / 压缩读历史时判断「这张卡还该不该显示」
-- 正确判据：NULL（无快照可考）或 等于本会话最新快照 ⇒ 可见
-- 错误判据：superseded_by IS NOT NULL ⇒ 不可见   ← 会把无快照会话的卡全隐藏
WHERE is_artifact = 0
   OR superseded_by IS NULL
   OR superseded_by = (SELECT s.snapshot_id FROM session_compaction_snapshots s
                       WHERE s.session_id = messages.session_id
                       ORDER BY s.created_at DESC, s.version DESC, s.snapshot_id ASC LIMIT 1)
```

**列名不改**（老大在派单里已用 `superseded_by` 这个名字），但上面这条判据和这段说明必须在实施时一起落到代码注释里，否则下一个读代码的人一定会按列名想当然写成 `IS NOT NULL`。

### 7.4 迁移类型 —— 纯增量补列 + 一次性回填

**不重建表，不搬数据。** 沿用现有机制 `DbClient.Migrations.cs:199-218` 的 `EnsureColumn`（`PRAGMA table_info` 检查 → 缺了才 `ALTER TABLE ADD COLUMN`），先例见 `DbClientCompactionSnapshotMigrations.cs:84-90`（`sessions` 补过两列）。

执行顺序必须是：**先补列 → 再回填**。反了就是往不存在的列里写。

### 7.5 数据丢失 / 数据污染风险点

| 风险点 | 具体是什么 | 怎么防 |
|---|---|---|
| **`EnsureColumn` 吞异常** | `DbClient.Migrations.cs:214-217` 是 `catch { /* ignore */ }` —— 补列失败**静默通过**，然后回填 SQL 直接报错或写空 | 回填前先断言列存在（`PRAGMA table_info` 再查一次），不存在就**明确跳过回填并记日志**，不许闷头跑 |
| **回填 `UPDATE` 范围写错** | `meta LIKE '%compactSummary%'` 少一个 `%`、或漏掉 `role = 'user'` 条件，会把**真实用户消息**标成 artifact ⇒ 首屏窗口里真话消失（S-276 刚修好的那个症状原样复发） | 回填前先 `SELECT COUNT(*)` 打印命中行数，与预期（现存 20 对）比对；**测试里造一条含 `compactSummary` 字样的真实消息**，断言它不被标记 |
| **`superseded_by` 指向不存在的快照** | 回填时若快照表里找不到对应 `snapshot_id`，会留下悬空引用 | 回填的 `SET` 值只从 `session_compaction_snapshots` 实际存在的 `snapshot_id` 里取；取不到就留 `NULL`（宁可多显示一张卡，不许写悬空值） |
| **一对卡只标一半** | 只标 `role = 'user'` 的摘要卡，漏了 `role = 'system'` 的边界行 | 两条 `UPDATE` 都写，测试断言「每张卡的边界行与摘要行 `is_artifact` 一致」 |
| **`PRAGMA foreign_keys = ON` 的连带影响** | `DbService.cs:35` 已开外键。若有人顺手给 `superseded_by` 加 FK 约束到快照表，删快照时会连带失败 | **`superseded_by` 不加 FK 约束**，当普通文本列用 |

## 十、撤销裁定（2026-11-01 20:43）

> 老大原话：「之前一屏显示一大堆摘要，那是本身我们程序报错导致的压缩不到位，跟显示一毛钱关系都没有，这个不做」

### 10.1 撤销的直接理由

原需求把「一屏一大堆摘要卡」定性成**显示层缺陷**，方向就错了：

- 那一屏卡的真实来源是**压缩触发异常**（压缩不到位 ⇒ 反复重压 ⇒ 一屏全是卡）；
- **S-276 修完窗口判定后，首屏已不会被卡挤占**（`DbMessageToolsQueries.cs:34-35` 的 `RealUserTurnPredicate`，四处 SQL 统一用）；
- 剩下的「上滚能看到历史卡」是**历史事实的正确呈现**，不是缺陷。

### 10.2 复核掉的其余三条危害

撤销前逐条核对，全部不成立：

| 原说法 | 实测 |
|---|---|
| 首屏满屏卡 | **已修**（S-276，`840d99e9`） |
| 模型上下文被污染 | **从来不是问题** —— wire 侧一直有 one-summary invariant（`ContextCompression.cs:565-569`） |
| 库越攒越大、拖久回填越慢 | 20 行 / 141 行。一天 20 次 × 一年 ≈ 7000 行，SQLite 无感。**「在增长」不等于「在恶化」** |

### 10.3 决策错误的教训

`raw-requirements.md` 当时写的是「唯一一条数据只增不减的缺陷，拖越久库越大、回填越慢」—— **把「数据在增长」当成了「问题在恶化」，没量化危害**。20 行数据的增长不叫恶化；「回填越慢」也是伪命题，本来就不该回填。
