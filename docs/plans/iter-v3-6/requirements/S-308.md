# S-308 · 子 agent 缺少停止手段 —— 后台子 agent 一旦成为孤儿就无法终止

> 状态：**✅ 已实施，门禁通过，待真机验收**
> 登记：2026-11-03 16:03
> 实施：2026-11-04（见文末「§实施记录」）
> 来源：老大 2026-11-03 16:03 原话「登记一个需求 刚刚你自己发现的 我们缺少子agent的停止手段」
> 触发场景：本会话派了两个 background 子代理，其中一条方向被否决后**发现无法中止**，只能让它跑完
> 关联：S-191（子 agent 归属会话）、SA-2（父子取消联动）、SA-7（状态列表排序）

## 一、现象

2026-11-03 16:00，本会话为验证换壳方向派了两个 `background=true` 子代理。16:01 老大否决其中一条（Avalonia），需要立即停掉对应的子代理 —— **没有任何手段可以做到**。

查遍 `use_capability` 的 `task` 类别，只有三个：`Task`（启动）、`SubAgentStatus`（查状态）、`SubAgentDetail`（查详情）。**没有 Stop。**

⇒ 只能让它继续跑到结束，白烧算力。

## 二、根因：三层都不通，且第三层是设计缺陷

### 2.1 工具层：只有查，没有停

`ToolModule.cs:159-160` 只注册了两个：

```csharp
registry.Register(new SubAgentStatusTool(), "task");
registry.Register(new SubAgentDetailTool(), "task");
```

外加启动用的 `TaskTool`。**没有任何终止类工具。**

### 2.2 已有的 `Cancel` 是「假取消」：只改状态，不中断运行

`BackgroundSubAgentRegistry.cs:166-177`：

```csharp
public static void Cancel(string toolUseId)
{
    if (_records.TryGetValue(toolUseId, out var existing))
    {
        _records[toolUseId] = existing with
        {
            Status = SubAgentRunStatus.Cancelled,
            CompletedAt = DateTimeOffset.UtcNow
        };
        EvictOldTerminalRecords();
    }
}
```

**通篇没有任何 `CancellationTokenSource`。** 它做的事只有一件：把记录状态改成 `Cancelled`。

⇒ 如果外面调它，UI 会显示「已取消」，但**子 agent 的实际执行一点都不受影响**，还在继续跑、继续烧 token。这是最坏的一类缺陷 —— **状态与实际不符**。

它当前唯一的调用点是 `SubAgentExecutor.Background.cs:140`，在 `catch (OperationCanceledException) when (childState.IsCancellationRequested)` 里 —— 也就是说它是**真取消发生之后的记账**，不是发起取消。位置本身没错，问题是它被当成了唯一的「取消入口」。

### 2.3 唯一真取消通路：父 run 连带 —— 但 background 模式下会失效

`SubAgentExecutor.Background.cs:44-45`，父子联动是有的（SA-2 修过 `ObjectDisposedException`）：

```csharp
var cancellationRegistration = parentState.CancellationToken.Register(
    static state => ((AgentRuntimeRunState)state!).Cancel("parent"),
```

⇒ **用户点「停止」→ 停当前会话的 run → 连带停掉该 run 派出的子 agent。这条是通的。**

**但它对 `background=true` 天生失效**，因为：

| 步骤 | 位置 | 后果 |
|---|---|---|
| 后台子 agent 立即返回 id，父 run 继续或结束 | `TaskTool.cs` 设计意图 | 父 run 不再等它 |
| 父 run 结束 → `cancellationRegistration.Dispose()` | `SubAgentExecutor.Background.cs:192-194` | **父 → 子的取消链路被摘掉** |
| 子 agent 还在跑 | — | **彻底孤儿，任何路径都停不掉** |

⇒ **「后台子 agent 活得比父 run 长」是它的设计目标，而唯一的取消通路却在父 run 结束时被主动 dispose 掉。** 这两件事直接矛盾 —— 不是漏写，是生命周期设计没闭环。

### 2.4 UI 层：零停止入口

查 `SubAgentCard.tsx` 与 `SubAgentExecutionDetail.tsx`：

- `SubAgentCard.tsx:134/145` 的 `e.stopPropagation()` 是**阻止事件冒泡**，与停止执行无关
- `SubAgentExecutionDetail.tsx:276-292` 的 `cancelled` 是 **React effect 的清理标志**，防 setState-after-unmount
- 全仓子 agent 相关组件**没有任何停止按钮**

⇒ 用户侧也没有出路。

### 2.5 附带发现：强杀是唯一手段，且杀完就失忆（2026-11-03 16:09 实证）

老大原话：

> 我刚刚强行把软件关了，现在应该子agent都停了

**这句话本身就是最硬的证据：唯一可用的「停止手段」是杀进程。**

而且杀完立刻暴露第二个缺口。我随即查状态：

```text
SubAgentStatus() -> "No sub-agents registered for this conversation."
```

但同一条磁盘痕迹完全还在：

| 载体 | 状态 |
|---|---|
| `BackgroundSubAgentRegistry`（内存态） | **空的** —— 查不到任何子 agent |
| todo 列表（另一套落盘机制） | 仍在，显示「3/5 completed，1 blocked，1 pending」 |
| `experiments/tauri-shell/`（子 agent 自己写的产物） | 3.6 GB，截图 + 日志齐全 |

⇒ **`BackgroundSubAgentRegistry` 是纯内存字典**（`_records`），重启即清空。后果：

- 强杀之后**无法知道派过哪些子 agent、各自跑到哪一步、有没有半成品产物**
- 唯一能反映进度的反而是**另一套无关的 todo 落盘机制**，纯属巧合
- 如果子 agent 正处在**破坏性操作中途**（写文件、改库、推 Git），重启后既无记录也无从判断该不该回滚

**这不属于「停止」本身，但同属子 agent 生命周期没闭环。** 建议与停止能力一并考虑（见 §4.5），否则「能停」也只是停得干净、事后照样糊涂。

## 三、影响面

| 场景 | 现在能不能停 | 说明 |
|---|---|---|
| 前台子 agent（`background=false`） | ✅ 能 | 父 run 的 `CancellationToken` 自然覆盖 |
| 后台子 agent，父 run **仍在跑** | ⚠️ 只能连坐 | 停整个会话的 run 才能连带停它，不能单独停 |
| 后台子 agent，父 run **已结束** | ❌ **完全不能** | 孤儿。registration 已 dispose，无 CTS 可触达 |
| 全局 PM 派给项目会话的任务 | ❌ 同上 | 跨会话场景下更无入口 |
| agent 自己想停自己派的子 agent | ❌ 不能 | 没有 `SubAgentStop` 工具 |

**第三条是核心缺陷。** `background=true` 的全部价值就是「派出去就不用管、活得比父 run 长」，而这个特性恰好让它不可终止。

## 四、方案（建议，待老大拍板）

### 4.1 基础设施：`toolUseId` → CTS 注册表（这条必须先做）

现在缺的不是一个按钮，是**可触达的取消句柄**。建议在 `BackgroundSubAgentRegistry` 里加一份并行结构：

```text
toolUseId -> CancellationTokenSource（独立于父 run 的那个）
```

- 子 agent 启动时创建自己的 CTS，**并 link 父 CTS**（保留现有父子联动）
- 父 run 结束时**只 Dispose link，不 Dispose 子 CTS** ⇒ 孤儿仍有句柄可停
- 子 agent 自身终止时清理登记，防泄漏

**这是本需求唯一有技术风险的部分** —— 生命周期一旦搞错就是 CTS 泄漏或 ObjectDisposedException（SA-2 已经踩过一次）。

### 4.2 工具层：加 `SubAgentStop`

```
SubAgentStop(toolUseId) -> { stopped: bool, reason: string }
```

复用 `ToolModule.cs:159` 同款注册方式，进 `task` 类别。实际执行改为 `cts.Cancel()` 而不是只改状态。

### 4.3 UI 层：子 agent 卡片加停止按钮

- `SubAgentCard.tsx` 运行中态加一个停止图标（与现有工具卡风格一致）
- `SubAgentExecutionDetail.tsx` 详情页加显式「停止」按钮
- 要走既有 IPC 通道，新增一个 `subagent-stop` 事件 —— **具体通道名待与现有子 agent IPC 对齐后定**

### 4.4 `Cancel()` 语义要改

`BackgroundSubAgentRegistry.Cancel` 现在叫 Cancel 但只是记账，**这个名字会继续骗人**。建议：

- 拆成 `MarkCancelled(toolUseId)`（记账，现状逻辑）与真正的 `RequestStop(toolUseId)`（发 CTS）
- 或者至少加注释说明「本方法不中断执行」

### 4.5 登记表要能扛重启（§2.5 的配套，优先级次之）

当前 `_records` 是纯内存字典，进程一死全丢。建议**最小落盘**：

- 子 agent 启动时写一条轻量记录（`toolUseId` / 会话 / 启动时间 / 状态 / 工作目录）
- 正常终止时更新终态
- **进程重启后读回，把「上次未正常结束」的记录标成 `interrupted`** —— 至少让用户和 agent 知道「有一条子 agent 是被强杀的，不是正常完成」

**不要求持久化执行详情**（那是 `SubAgentReportStore` 的事），只要「曾经存在 + 最后状态」这一层。落盘位置与既有数据目录一致，不新开文件格式。

**这条可以独立于 4.1~4.4 排期**，但技术上同源（生命周期闭环）。

## 五、范围边界

- **不改**父子联动的既有行为（SA-2 的修复不能回退）
- **不改** `TaskTool` 的 `background` 语义
- **不动**子 agent 的状态枚举与 UI 配色
- 不涉及 `GoalSubAgentExecutor`（Goal 体系是另一条线，若同样缺停止需单独登记）

## 六、验收

1. 派一个 `background=true` 子 agent，父 run 结束后**仍能**通过 `SubAgentStop` 停掉它。
2. 停掉后 `SubAgentStatus` 显示 `cancelled`，且**实际执行确实终止**（日志不再有该子 agent 的新输出）。
3. UI 上运行中的子 agent 卡片有可见的停止入口。
4. 停掉后不泄漏 CTS（反复派/停 20 次，进程句柄数不持续上涨）。
5. 父 run 取消仍能连带停子 agent（SA-2 行为不回退）。

| `SubAgentStop` 工具 | 小 |
| `Cancel` 语义拆分 | 小 |
| UI 两处按钮 + IPC | 中 |

约 **1 刀**，但 CTS 生命周期那块要单独验，不能一把过。

## 实施记录（2026-11-04）

### 根因订正

登记时的判断「没有入口」只对了一半。**UI 入口早就摆着，后端从来没实现**：

- `SubAgentsPanel.tsx:324` 的 `stopAgent` 与 `SubAgentCard` 的停止按钮，都调 `agentBridge.cancelSubAgent(toolUseId, agentSessionId)`（`lib/ipc/agent-bridge.ts:81-84`），发出 `worker:request` → `method = "agent/cancel-subagent"`。
- 全仓 `*.cs` grep `agent/cancel-subagent` ⇒ **No matches found**，这个 method 从来没有处理方。

前半段「后台子 agent 是孤儿」成立：后台子 agent 唯一的取消通路是父 run 的 CancellationToken 注册回调，父 run 结束即 dispose，而 background 的价值恰恰是活得比父 run 长。

### 落地方案

- **不另建 CancellationTokenSource**（重点）：全链路只认 `AgentRuntimeRunState` 里那一个 CTS。另建 linked source 停不掉任何东西，且 SA-2 在 link 时序上踩过 `ObjectDisposedException`。
- 新增 `SubAgentRunControl.cs`：`toolUseId → 子 agent 自己的 AgentRuntimeRunState`，提供 `Register` / `TryStop(toolUseId, reason)` / `Unregister`。
- 新增 `Tools/SubAgentStopTool.cs`：工具名 `SubAgentStop`，注册到 `category = "task"`（与 `Task` / `SubAgentStatus` / `SubAgentDetail` 同组）。
- `BackgroundSubAgentRegistry.Cancel` → **改名 `MarkCancelled`**，注释钉死「只记账、不中断执行，别拿它当发起取消的入口」。改名的目的是让「谁真正能停」在编译期就看得见。
- `AgentRuntimeTools.CancelSubAgent` + 注册 `agent/cancel-subagent`，补齐 UI 一直在发但没人接的那条 method。
- 生命周期：`SubAgentExecutor.cs`（前台）与 `SubAgentExecutor.Background.cs`（后台）都 Register；`finally` 里**先 Unregister 再 state.Dispose()**，避免停已释放对象的时序窗口。
- 跨会话误停防护：`sessionId` 与记录里的会话不一致则拒绝；`sessionId` 缺省不拦（工具侧与老调用不带该字段）。
- UI：`SubAgentCard.tsx` header 从 `<button>` 改 `<div role="button">`（避免 button 套 button，键盘行为手工补），`isRunning || isQueued` 时显示停止按钮；`SubAgentsPanel.tsx` 详情态标题行补一个。
- 语言包：`chat.subAgent.stop`（中「停止执行」/ 英「Stop」）、`permission.toolLabels.SubAgentStop`（中「停止子代理」/ 英「Stop Sub-agent」）。

## 六、真机验收（dev 实例，2026-11-04 14:29 报告）

### 已验证

| 项 | 结果 | 证据 |
|---|---|---|
| SubAgentStop 工具可用 | ✅ | 能力表 ready，	ask 类别 |
| 停后台子 agent | ✅ 3/3 | 三次状态都变成 cancelled，Elapsed 定格不再增长 |
| 日志链路闭合 | ✅ | `sub-agent stop requested by agent toolUseId=…` → `background sub-agent cancelled parentRunId=…` |
| 状态与实际一致 | ✅ | 停止后不再产出，不是假取消 |

### 未验（不许标「已验收」）

1. **跨 run 停止**（验收 1）：dev 三次都是在同一回合内停的，没覆盖「父 run 已结束、子 agent 还活着」这个本需求的核心场景；
2. **CTS 不泄漏**（验收 4）：需要派停 20 次观察句柄；
3. **UI 按钮**（验收 3）：dev 实例不看 UI。

另外 dev 三次都**没能抓住「正在执行中」的实例**：#1 存活 34.3 s、#2 存活 239.7 s，全程 `0 calls / 0 iterations，日志除启动外无其他记录 —— 停掉的是「还没真正开始执行工具」的实例。#3 在同一环境 60 s 跑了 40 次工具，说明启动本身可以很快。所以严格说「打断正在执行中的操作」这一条本轮**没有验证成功**。

### 验收修正：停止后详情仍显示「正在执行」

真机发现：子 agent 已停止，但点开右侧详情，最后一个工具还显示「正在执行」。

根因在渲染层，不在执行链：`SubAgentExecutionDetail` 用 `agent.toolCalls` 这份 live 快照覆盖转录里的工具状态，而 `MarkCancelled` 只记账、不中断执行（本需求 §2.2 的既定口径，故意不硬杀），于是快照里最后那一条永远停在 `running`。

修法（`buildLiveToolCallMap`）：`agent.isRunning === false` 时，把残留的 `running` / `streaming` / `pending_approval` 降级为 `canceled`。`canceled` 在各工具卡片里本来就有完整渲染，不用新文案；agent 仍在跑时原样透传，实时显示不受影响。
